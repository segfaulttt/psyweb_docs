
# UC-006. Управление расписанием (Manage Schedule)

**Проект:** PsyWeb  
**Статус:** DRAFT  
**Основной участник:** SPECIALIST  
**Цель:** Настроить рабочее расписание специалиста, на основании которого платформа рассчитывает доступное время консультаций.

---

# 1. Описание

Сценарий описывает управление рабочим расписанием специалиста.

Специалист может:

- выбирать режим расписания;
- задавать регулярные рабочие интервалы;
- задавать рабочее время на конкретные даты;
- устанавливать исключения;
- изменять и удалять рабочие интервалы;
- просматривать действующее расписание;
- выбирать горизонт бронирования;
- управлять часовым поясом в пределах предусмотренных правил.

PsyWeb не требует предварительного создания отдельных AvailabilitySlot.

Доступные начала консультаций рассчитываются динамически на основании рабочего расписания, выбранной услуги и текущей занятости специалиста.

---

# 2. Предусловия

- Пользователь аутентифицирован.
- `UserRole.SPECIALIST`.
- `UserStatus.ACTIVE`.
- Специалист имеет необходимые полномочия на управление расписанием.
- Изменяемое расписание принадлежит данному специалисту.

Наличие активной ServiceOffering не требуется для самого создания расписания.

Однако без подходящей активной услуги клиент не сможет создать Reservation.

---

# 3. Инициирующее событие

Специалист открывает раздел управления расписанием.

---

# 4. Основной сценарий: регулярное расписание

1. Специалист открывает настройки рабочего расписания.
2. Система отображает текущий режим и сохранённые рабочие интервалы.
3. Специалист выбирает режим `REGULAR`.
4. Специалист задаёт рабочие интервалы для необходимых дней недели.
5. Специалист указывает дату начала действия новой конфигурации.
6. Система проверяет корректность интервалов.
7. Система проверяет допустимость применения новой версии расписания.
8. Система сохраняет новую WeeklyScheduleVersion.
9. Действующая конфигурация расписания обновляется согласно правилам версионирования.
10. Система сообщает об успешном сохранении.

---

# 5. Альтернативный сценарий: FLOATING

1. Специалист открывает настройки расписания.
2. Выбирает режим `FLOATING`.
3. Выбирает конкретную календарную дату.
4. Добавляет один или несколько рабочих интервалов.
5. Система проверяет корректность данных.
6. Система сохраняет DateSchedule с типом `MANUAL`.
7. Специалист получает подтверждение.

Для даты, не имеющей MANUAL-расписания в режиме FLOATING, рабочее время отсутствует.

---

# 6. Альтернативный сценарий: исключение из REGULAR

1. Специалист выбирает дату, для которой требуется изменить регулярное расписание.
2. Система отображает применимый недельный шаблон.
3. Специалист задаёт специальное расписание для этой даты.
4. Система проверяет корректность данных.
5. Создаётся или изменяется DateSchedule с типом `OVERRIDE`.
6. Для выбранной даты OVERRIDE полностью заменяет регулярное расписание.
7. Система подтверждает сохранение.

Пустой OVERRIDE обозначает нерабочий день.

---

# 7. Альтернативный сценарий: удаление рабочего времени

1. Специалист выбирает рабочий интервал или конфигурацию выбранной даты.
2. Запрашивает предусмотренное изменение или удаление.
3. Система проверяет полномочия и корректность операции.
4. Система применяет изменение расписания.
5. Система сохраняет конфигурацию.
6. Специалист получает подтверждение.

Изменение рабочих интервалов не должно автоматически отменять существующие ACTIVE Reservation и CONFIRMED Booking.

---

# 8. Альтернативный сценарий: переключение режима

1. Специалист выбирает другой режим расписания.
2. Система проверяет допустимость изменения.
3. Новый режим становится активным.
4. Сохранённая конфигурация неактивного режима остаётся в системе.
5. Последующие расчёты Availability используют выбранный режим.

---

# 9. Альтернативный сценарий: изменение горизонта бронирования

1. Специалист открывает настройки доступности.
2. Выбирает горизонт бронирования.
3. Система проверяет допустимость значения.
4. Система сохраняет настройку.
5. Новые запросы Availability используют обновлённый горизонт.

Допустимые значения:

- 14 дней;
- 30 дней;
- 60 дней;
- 90 дней.

Значение по умолчанию — 30 дней.

---

# 10. Альтернативный сценарий: изменение часового пояса

1. Специалист открывает настройки часового пояса.
2. Выбирает корректный IANA ZoneId.
3. Система проверяет допустимость изменения.
4. Система согласует операцию с конкурентными изменениями расписания и созданием Reservation.
5. Новый ZoneId сохраняется.
6. Последующие расчёты Availability используют новый часовой пояс.

Абсолютные времена существующих Reservation и Booking не изменяются.

---

# 11. Ошибочные сценарии

## 11.1. Некорректный рабочий интервал

1. Система обнаруживает некорректные границы рабочего интервала.
2. Изменение отклоняется.
3. Специалист получает информацию об ошибке.
4. Прежнее расписание сохраняется.

## 11.2. Пересекающиеся интервалы

1. Система обнаруживает запрещённое пересечение рабочих интервалов.
2. Конфигурация не сохраняется.
3. Специалист получает сообщение о конфликте.

## 11.3. Конфликт версий REGULAR

1. Новая WeeklyScheduleVersion конфликтует с правилами действия существующих версий.
2. Система отклоняет изменение.
3. Специалисту предлагается скорректировать конфигурацию.

## 11.4. Недостаточные полномочия

1. Пользователь не имеет права управлять выбранным расписанием.
2. Операция отклоняется.
3. Данные не изменяются.

## 11.5. Конкурентное изменение

1. Во время сохранения расписания выполняется другая операция, влияющая на тот же календарный период.
2. Система применяет согласованный механизм транзакционной координации.
3. При невозможности корректно выполнить изменение операция отклоняется.
4. Частичная конфигурация не сохраняется.

---

# 12. Постусловия

## 12.1. Успешное завершение

- Новая конфигурация расписания сохранена.
- Рабочие интервалы удовлетворяют установленным правилам.
- Активный режим определён.
- Существующие обязательства бронирования сохранены.
- Последующие расчёты Availability учитывают актуальное расписание.

## 12.2. Неуспешное завершение

- Некорректные изменения не сохранены.
- Прежнее согласованное расписание остаётся действительным.
- Существующие Reservation и Booking не повреждены.

---

# 13. Бизнес-правила

## 13.1. Режимы

Поддерживаются REGULAR и FLOATING.

## 13.2. Рабочие интервалы

Рабочие интервалы не должны иметь некорректные или запрещённо пересекающиеся границы.

## 13.3. REGULAR

WeeklyScheduleVersion определяет полный недельный шаблон на соответствующий период.

## 13.4. OVERRIDE

DateSchedule с типом OVERRIDE заменяет расписание конкретной даты в режиме REGULAR.

## 13.5. MANUAL

В режиме FLOATING рабочее время конкретной даты задаётся через MANUAL.

## 13.6. Сохранение данных

Неактивная конфигурация расписания сохраняется при переключении режима.

## 13.7. Исторические обязательства

Обычные изменения Schedule не отменяют ACTIVE Reservation и CONFIRMED Booking.

## 13.8. Динамическая доступность

Schedule определяет рабочее время, но не владеет ScheduleOccupancy.

## 13.9. Конкурентность

Сохранение расписания должно быть согласовано с конкурентным созданием Reservation.

# 15. Примечания

- Рабочее расписание существует независимо от отдельных услуг.
- ServiceOffering определяет длительность консультации и перерыв.
- Availability рассчитывается после выбора услуги.
- Просмотр доступного времени не создаёт удержание.
- Управление расписанием не подразумевает массовую отмену консультаций.
- Для MVP предусмотрены операции над отдельными конфигурациями и интервалами, а не отдельный workflow массовой отмены.
- Технические правила PostgreSQL advisory locks описываются в Backend.

---

# 16. Итог

После выполнения UC-006 специалист имеет согласованную конфигурацию рабочего расписания, пригодную для динамического расчёта доступных консультаций.

**Статус: DRAFT — сценарий актуализирован под Schedule и Dynamic Availability.**
