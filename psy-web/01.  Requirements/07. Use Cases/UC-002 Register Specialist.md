
# UC-002. Регистрация специалиста (Register Specialist)

**Проект:** PsyWeb  
**Статус:** DRAFT  
**Основной участник:** SPECIALIST  
**Дополнительный участник:** ADMIN  
**Цель:** Создать учётную запись специалиста и отправить заявку на профессиональное одобрение.

---

# 1. Описание

Сценарий описывает регистрацию нового специалиста на платформе PsyWeb.

Пользователь предоставляет необходимые регистрационные данные, после чего система создаёт учётную запись и связанную с ней модель Specialist.

Регистрация специалиста и его профессиональное одобрение являются разными процессами.

После успешной регистрации специалист получает активную учётную запись, но остаётся в ожидании модерации.

До одобрения он может пользоваться разрешёнными функциями собственного аккаунта, однако не получает профессиональные полномочия, требующие статуса APPROVED.

Рассмотрение заявки администратором описывается отдельно в UC-003.

---

# 2. Участники

## 2.1. Основной участник

SPECIALIST — пользователь, регистрирующийся для предоставления консультационных услуг.

## 2.2. Дополнительный участник

ADMIN — администратор платформы, которому становится доступна заявка специалиста для последующего рассмотрения.

Администратор не обязан участвовать непосредственно в транзакции регистрации.

---

# 3. Предусловия

- Пользователь не аутентифицирован.
- Пользователь располагает необходимыми регистрационными данными.
- В системе отсутствует учётная запись с таким же каноническим email.

---

# 4. Инициирующее событие

Пользователь выбирает действие регистрации в качестве специалиста.

---

# 5. Основной успешный сценарий

1. Пользователь открывает форму регистрации специалиста.
2. Система отображает необходимые регистрационные поля.
3. Пользователь вводит регистрационные данные.
4. Пользователь отправляет заявку.
5. Система проверяет корректность и полноту предоставленных данных.
6. Система нормализует email согласно единой политике User Domain.
7. Система проверяет отсутствие другой учётной записи с таким каноническим email.
8. Система создаёт User со следующими значениями:
   - `UserRole.SPECIALIST`;
   - `UserStatus.ACTIVE`.
9. Система создаёт связанную модель Specialist с первоначальным модерационным статусом `PENDING`.
10. Система сохраняет связанные данные регистрации.
11. Новая заявка становится доступной для последующего рассмотрения администратором.
12. Система инициирует предусмотренное уведомление администратора о новой заявке.
13. Система сообщает пользователю об успешной регистрации и ожидании профессионального одобрения.

---

# 6. Альтернативные сценарии

## 6.1. Email уже зарегистрирован

**Возникает на шаге 7.**

1. Система обнаруживает существующую учётную запись с таким каноническим email.
2. Регистрация прекращается.
3. Новые User и Specialist не создаются.
4. Пользователь получает сообщение об ошибке.
5. Пользователь может указать другой email.

## 6.2. Некорректные регистрационные данные

**Возникает на шаге 5 или 6.**

1. Система обнаруживает некорректные или неполные данные.
2. Регистрация не выполняется.
3. Пользователь получает информацию об ошибках проверки.
4. Пользователь может исправить данные и повторить попытку.

## 6.3. Конкурентная регистрация одинакового email

**Возникает при сохранении данных.**

1. Несколько запросов регистрации используют одинаковый канонический email.
2. Система предотвращает создание нескольких User с этим email.
3. Не более одного запроса успешно создаёт соответствующую учётную запись.
4. Остальные запросы завершаются предусмотренной ошибкой конфликта.
5. Частично созданные модели регистрации не сохраняются.

## 6.4. Ошибка сохранения

**Возникает на шаге 10.**

1. Система не может завершить сохранение регистрационных данных.
2. Регистрация считается неуспешной.
3. Изменения User и Specialist, относящиеся к одной регистрации, откатываются.
4. Пользователь получает сообщение об ошибке без раскрытия внутренних технических деталей.

## 6.5. Ошибка уведомления администратора

**Возникает на шаге 12.**

1. Учётная запись и заявка уже успешно сохранены.
2. Отправка уведомления завершается ошибкой.
3. Регистрация остаётся успешной.
4. Заявка сохраняется и остаётся доступной для рассмотрения администратором.
5. Ошибка уведомления обрабатывается согласно политике Notification.

---

# 7. Постусловия

## 7.1. Успешное завершение

- Создан новый User.
- Пользователю назначена роль `SPECIALIST`.
- User имеет состояние `ACTIVE`.
- Создана связанная модель Specialist.
- Specialist имеет модерационный статус `PENDING`.
- Регистрационные данные сохранены согласованно.
- Канонический email уникален.
- Заявка доступна для административного рассмотрения.
- Пользователь может пройти аутентификацию.
- Профессиональные полномочия до одобрения недоступны.

## 7.2. Неуспешное завершение

- Новые User и Specialist не созданы.
- Частичные результаты регистрации не сохранены.
- Существующие учётные записи не изменены.

---

# 8. Бизнес-правила

## 8.1. Уникальность email

В системе не допускается существование нескольких User с одинаковым каноническим email.

## 8.2. Нормализация email

Перед проверкой уникальности применяется единая политика:

```text
trim
→ lowercase(Locale.ROOT)
→ validate
```

## 8.3. Роль специалиста

После успешной регистрации User получает:

`UserRole.SPECIALIST`

## 8.4. Состояние аккаунта

После регистрации User получает:

`UserStatus.ACTIVE`

Одобрение администратора не требуется для перехода учётной записи в ACTIVE.

## 8.5. Первоначальный статус Specialist

Новая модель Specialist создаётся в состоянии:

`PENDING`

Это состояние относится к профессиональной модерации, а не к активности User.

## 8.6. Профессиональный допуск

Для профессиональных операций требуется:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
```

## 8.7. Допуск к бронированию

Для принятия новых бронирований дополнительно требуется:

`SpecialistBookingAccess.bookingAllowed = TRUE`

Сам факт регистрации не предоставляет права принимать Reservation.

## 8.8. Ограниченный доступ

Специалист со статусом PENDING может пользоваться только разрешёнными функциями собственной учётной записи.

Точный перечень таких функций определяется моделью авторизации.

## 8.9. Безопасность пароля

Пароль не сохраняется в открытом виде.

Система хранит предусмотренный безопасный passwordHash.

## 8.10. Атомарность регистрации

Создание User и Specialist в рамках одной регистрации должно выполняться согласованно.

Не допускается успешное создание только одной из обязательных моделей при неуспешном завершении регистрации.

## 8.11. Независимость Notification

Ошибка доставки уведомления администратору не должна отменять успешно сохранённую регистрацию.

# 11. Примечания

- Регистрация не означает автоматического одобрения специалиста.
- UserStatus и Specialist approval status являются независимыми состояниями.
- Неодобренный специалист не считается заблокированным пользователем.
- Наличие `UserStatus.ACTIVE` не предоставляет профессиональных полномочий.
- Администратор рассматривает заявку в отдельном сценарии UC-003.
- Точный перечень регистрационных полей определяется продуктовой моделью и API.
- Конкретные REST endpoints не фиксируются в данном документе.
- Уведомление администратора является производным действием и не должно нарушать транзакционную согласованность регистрации.

---

# 12. Итог

После успешного выполнения UC-002 в системе существует:

```text
User
├── role = SPECIALIST
└── status = ACTIVE
        │
        ▼
Specialist
└── approvalStatus = PENDING
```

Специалист может пройти аутентификацию, но не может выполнять профессиональные операции до получения соответствующего допуска.

Заявка ожидает рассмотрения администратором в UC-003.

**Статус: DRAFT — сценарий согласован с целевой моделью User, Specialist и Authentication.**
