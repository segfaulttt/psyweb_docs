
# UC-001. Регистрация клиента (Register Client)

**Проект:** PsyWeb  
**Статус:** DRAFT  
**Основной участник:** CLIENT  
**Цель:** Создать учётную запись клиента для использования платформы.

---

# 1. Описание

Сценарий описывает регистрацию нового клиента PsyWeb.

Клиент предоставляет необходимые регистрационные данные, после чего система проверяет их корректность и создаёт учётную запись.

Регистрация клиента не требует одобрения администратора.

После успешной регистрации пользователь может перейти к аутентификации.

---

# 2. Предусловия

- Пользователь не аутентифицирован.
- Пользователь располагает необходимыми регистрационными данными.
- В системе отсутствует учётная запись с таким же каноническим email.

---

# 3. Инициирующее событие

Пользователь выбирает действие регистрации клиента.

---

# 4. Основной успешный сценарий

1. Пользователь открывает форму регистрации.
2. Система отображает обязательные поля.
3. Пользователь вводит регистрационные данные.
4. Пользователь отправляет форму.
5. Система проверяет корректность и полноту данных.
6. Система нормализует email согласно единой политике User Domain.
7. Система проверяет отсутствие другой учётной записи с таким каноническим email.
8. Система создаёт User с ролью `CLIENT` и состоянием `ACTIVE`.
9. Система создаёт предусмотренные клиентской моделью данные профиля.
10. Система сохраняет результаты регистрации.
11. Система сообщает об успешном создании аккаунта.
12. Пользователь переходит на страницу входа.

---

# 5. Альтернативные сценарии

## 5.1. Email уже зарегистрирован

**Возникает на шаге 7.**

1. Система обнаруживает существующую учётную запись с таким каноническим email.
2. Новая учётная запись не создаётся.
3. Пользователь получает сообщение об ошибке.
4. Пользователь может указать другой email.

## 5.2. Некорректные регистрационные данные

**Возникает на шаге 5 или 6.**

1. Система обнаруживает некорректные или неполные данные.
2. Регистрация не выполняется.
3. Пользователь получает информацию о нарушенных требованиях.
4. Пользователь может исправить данные и повторить попытку.

## 5.3. Конкурентная регистрация одинакового email

**Возникает при сохранении учётной записи.**

1. Два запроса регистрации используют одинаковый канонический email.
2. Система предотвращает создание двух учётных записей с этим email.
3. Один запрос может завершиться успешно.
4. Другой получает предусмотренную ошибку конфликта.
5. Частично созданная учётная запись не должна оставаться сохранённой.

## 5.4. Ошибка сохранения

**Возникает на шаге 10.**

1. Система не может завершить сохранение регистрационных данных.
2. Регистрация считается неуспешной.
3. Изменения, относящиеся к одной операции регистрации, откатываются.
4. Пользователь получает сообщение о неуспешной операции без раскрытия внутренних технических деталей.

---

# 6. Постусловия

## 6.1. Успешное завершение

- Создан новый User.
- Пользователю назначена роль `CLIENT`.
- User имеет состояние `ACTIVE`.
- Сохранены необходимые данные клиентского профиля.
- Канонический email уникален.
- Учётная запись доступна для последующей аутентификации.
- Пользователь не считается автоматически аутентифицированным.

## 6.2. Неуспешное завершение

- Новая учётная запись не создана.
- Частичные результаты регистрации не сохранены.
- Существующие учётные записи не изменены.

---

# 7. Бизнес-правила

## 7.1. Уникальность email

В системе не допускаются две учётные записи с одинаковым каноническим email.

## 7.2. Нормализация

Перед проверкой уникальности email приводится к канонической форме:

```text
trim
→ lowercase(Locale.ROOT)
→ validate
```

## 7.3. Роль клиента

Новой учётной записи присваивается:

`UserRole.CLIENT`

## 7.4. Состояние аккаунта

После успешной регистрации клиент получает:

`UserStatus.ACTIVE`

## 7.5. Одобрение администратора

Регистрация клиента не требует отдельного административного одобрения.

## 7.6. Безопасность пароля

Пароль не должен сохраняться в открытом виде.

Система хранит только предусмотренный безопасный passwordHash.

## 7.7. Атомарность регистрации

Создание связанных данных одной регистрации должно завершаться согласованно.

Не допускается частично созданный аккаунт вследствие неуспешной операции.
