
# 04. Роли пользователей (User Roles)

**Проект:** PsyWeb  
**Статус:** DRAFT  
**Область:** Роли и пользовательские полномочия

---

# 1. Назначение документа

Документ описывает основные роли пользователей PsyWeb, их возможности и ограничения.

Роль определяет категорию пользователя, но не является единственным условием доступа.

Авторизация дополнительно учитывает:

- UserStatus;
- профессиональный статус Specialist;
- SpecialistBookingAccess;
- принадлежность ресурса;
- состояние бизнес-сущности;
- дополнительные условия операции.

---

# 2. Общие принципы

В платформе предусмотрены три основные роли:

- CLIENT;
- SPECIALIST;
- ADMIN.

Для защищённых операций требуется активная учётная запись пользователя.

```text
UserStatus = ACTIVE
```

Отдельные возможности специалиста дополнительно требуют административного одобрения.

Пользователь не может выполнять действия с чужими ресурсами без специально предусмотренных полномочий.

---

# 3. CLIENT

## Описание

CLIENT — зарегистрированный пользователь, который выбирает специалистов и записывается на консультации.

## Основные возможности

Клиент может:

- управлять собственным профилем;
- просматривать каталог специалистов;
- искать специалистов;
- просматривать их публичные профили;
- выбирать ServiceOffering;
- просматривать динамически рассчитанную Availability;
- создавать собственные Reservation;
- подтверждать действующие Reservation;
- отменять собственные ACTIVE Reservation;
- отменять собственные будущие CONFIRMED Booking;
- просматривать предстоящие и исторические консультации;
- отправлять отчёт о результате консультации;
- создавать Review при выполнении условий eligibility;
- редактировать собственный Review;
- просматривать собственные уведомления.

## Дополнительные возможности

После реализации соответствующих расширений клиент сможет:

- пользоваться чатом;
- использовать расширенные фильтры поиска;
- управлять фотографией профиля;
- получать уведомления через дополнительные каналы.

## Ограничения

Клиент не может:

- изменять чужие Booking и Reservation;
- управлять расписанием специалиста;
- создавать ServiceOffering от имени специалиста;
- изменять чужие Review;
- принимать решения по модерации;
- разрешать споры SessionOutcome.

---

# 4. SPECIALIST

## Описание

SPECIALIST — пользователь, зарегистрированный для предоставления консультационных услуг.

Роль SPECIALIST сама по себе не означает завершённую профессиональную модерацию.

## 4.1. Доступ к аккаунту

Специалист с UserStatus.ACTIVE может аутентифицироваться независимо от того, имеет ли его Specialist статус:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

Доступные после входа операции зависят от дополнительных условий.

## 4.2. Управление собственными данными

В пределах предоставленных полномочий специалист может:

- просматривать и изменять собственные данные;
- заполнять информацию для модерации;
- просматривать собственный модерационный статус;
- управлять разрешёнными настройками профиля.

## 4.3. Профессиональные операции

После получения соответствующего допуска специалист может:

- управлять ServiceOffering;
- управлять Schedule;
- настраивать minimumBookingNotice;
- настраивать clientCancellationNotice;
- выбирать горизонт бронирования;
- управлять часовым поясом;
- просматривать собственные Reservation и Booking;
- отправлять отчёты о результате проведённых консультаций.

## 4.4. Допуск к бронированию

Право принимать новые Reservation определяется совокупностью условий:

```text
UserRole = SPECIALIST
AND UserStatus = ACTIVE
AND Specialist.approvalStatus = APPROVED
AND SpecialistBookingAccess.bookingAllowed = TRUE
```

Успешный Login не означает, что все эти условия выполнены.

## 4.5. Отмена консультаций

Продуктовая модель предусматривает отмену консультации специалистом.

Точные условия и последствия этой операции требуют отдельного согласования.

## 4.6. Дополнительные возможности

После реализации соответствующих расширений специалист сможет:

- управлять расширенным публичным профилем;
- загружать фотографии;
- указывать образование и сертификаты;
- использовать чат;
- получать расширенную аналитику.

## Ограничения

Специалист не может:

- управлять чужими ServiceOffering;
- изменять расписание другого специалиста;
- читать чужие Booking без необходимого основания;
- одобрять собственную заявку;
- изменять собственный approvalStatus административным действием;
- самостоятельно снимать административный запрет BookingAccess;
- модерировать чужие Review;
- разрешать споры SessionOutcome.

---

# 5. ADMIN

## Описание

ADMIN — пользователь, отвечающий за предусмотренные административные процессы платформы.

## Основные возможности

Администратор может:

- просматривать заявки специалистов;
- одобрять и отклонять заявки;
- приостанавливать профессиональный допуск;
- управлять предусмотренными состояниями пользователей;
- запрещать и разрешать новые бронирования специалиста;
- разрешать спорные SessionOutcome;
- просматривать предусмотренные данные административного аудита.

## Дополнительные возможности

После реализации расширений администратор сможет:

- модерировать Review по утверждённым правилам;
- просматривать расширенную статистику;
- пользоваться дополнительными инструментами управления платформой.

## Ограничения

Роль ADMIN не предоставляет автоматического права:

- произвольно изменять исторические Booking;
- обходить бизнес-инварианты;
- создавать Review от имени клиента;
- выполнять консультации как специалист;
- изменять чужие данные вне предусмотренных административных операций.

# 7. Независимые состояния

## 7.1. UserStatus

Определяет доступность учётной записи для защищённых операций:

- ACTIVE;
- BLOCKED.

## 7.2. Specialist ApprovalStatus

Определяет состояние профессиональной модерации:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

## 7.3. SpecialistBookingAccess

Определяет отдельное административное разрешение принимать бронирования:

- bookingAllowed = TRUE;
- bookingAllowed = FALSE.

## 7.4. Различие

Наличие `approvalStatus = APPROVED` не означает автоматического `bookingAllowed = TRUE`.

Наличие `UserStatus = ACTIVE` не означает профессионального одобрения.

---

# 8. Принадлежность данных

## CLIENT

Клиент управляет только предусмотренными собственными ресурсами.

## SPECIALIST

Специалист управляет собственными услугами, расписанием и разрешёнными настройками.

## ADMIN

Администратор получает доступ к данным только в рамках предусмотренных административных сценариев.

Проверка роли без проверки принадлежности ресурса недостаточна.

---

# 9. Будущие роли

Дополнительные роли могут быть введены при развитии платформы:

- MODERATOR;
- SUPPORT_MANAGER;
- SUPER_ADMIN.

Для MVP они не требуются.

Их полномочия не следует закладывать в текущую модель без конкретных продуктовых требований.

---

# 10. Итог

PsyWeb использует ролевую модель CLIENT / SPECIALIST / ADMIN с дополнительными проверками состояний и бизнес-условий.

**Роль определяет категорию полномочий, но не заменяет проверку фактического права выполнить операцию.**

**Статус: DRAFT — согласовано с целевой моделью Authentication и Authorization.**
