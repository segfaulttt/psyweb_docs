
# 08. Бизнес-правила (Business Rules)

**Проект:** PsyWeb  
**Статус:** DRAFT  
**Область:** Бизнес-правила платформы

---

# 1. Назначение документа

Документ определяет бизнес-правила PsyWeb — ограничения и условия, которым должны соответствовать операции платформы.

Бизнес-правила описывают требуемое поведение системы независимо от конкретных Java-классов, REST endpoints и SQL-запросов.

Правила реализуются на соответствующих уровнях:

- Application Service;
- Domain;
- PostgreSQL;
- транзакционная координация.

Не каждое бизнес-правило может быть полностью выражено ограничением базы данных.

Для требований, зависящих от времени, нескольких модулей или текущего состояния системы, необходима прикладная проверка.

Документ описывает целевую бизнес-модель. Фактическое состояние реализации отслеживается отдельно.

---

# 2. Учётные записи пользователей

## 2.1. Уникальность email

Каждая учётная запись должна иметь уникальный канонический email.

При сравнении используется единая политика нормализации:

- удаление пробелов в начале и конце;
- приведение к нижнему регистру через Locale.ROOT;
- проверка корректности результата.

Дополнительные преобразования адресов, такие как удаление точек или частей после символа `+`, не применяются.

## 2.2. Состояние аккаунта

В системе используются:

- ACTIVE;
- BLOCKED.

Только ACTIVE User может выполнять защищённые пользовательские операции.

BLOCKED User не может обходить ограничение с помощью ранее выданного JWT.

## 2.3. Роли

Основные роли:

- CLIENT;
- SPECIALIST;
- ADMIN.

Пользователь не может выполнять операции, не предусмотренные его ролью.

## 2.4. Принадлежность ресурсов

Доступ к конкретным Reservation, Booking, Schedule, Review и другим пользовательским ресурсам ограничивается правилами принадлежности и участия.

Наличие подходящей роли не означает права изменять чужие данные.

## 2.5. Административный доступ

Администратор выполняет только предусмотренные административные операции.

Роль ADMIN не отменяет бизнес-инварианты.

# 3. Профессиональный допуск специалиста

## 3.1. Независимость аккаунта и модерации

UserStatus и Specialist approval status представляют разные состояния.

Неодобренный специалист может иметь ACTIVE User и пользоваться разрешёнными функциями собственного аккаунта.

## 3.2. Модерационные состояния

В существующей модели используются:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

## 3.3. Профессиональная пригодность

Профессиональные полномочия требуют одновременно:

```text
UserRole = SPECIALIST
UserStatus = ACTIVE
Specialist.approvalStatus = APPROVED
```

## 3.4. Допуск к бронированию

Право принимать новые бронирования определяется дополнительным условием:

```text
SpecialistBookingAccess.bookingAllowed = TRUE
```

## 3.5. Эффективный допуск

Для создания и подтверждения Reservation специалист должен удовлетворять всем условиям:

```text
UserRole = SPECIALIST
AND UserStatus = ACTIVE
AND approvalStatus = APPROVED
AND bookingAllowed = TRUE
```

## 3.6. Независимость BookingAccess

Повторное одобрение специалиста не должно автоматически снимать отдельное ограничение bookingAllowed.

## 3.7. Влияние на аутентификацию

Отсутствие профессионального допуска или bookingAllowed не означает автоматическую блокировку Login.

# 4. Услуги специалиста

## 4.1. Принадлежность

ServiceOffering принадлежит конкретному специалисту.

Специалист может изменять только собственные услуги.

## 4.2. Активность

Новая Reservation может создаваться только по активной ServiceOffering.

## 4.3. Длительность консультации

Длительность консультации должна быть положительным целым количеством минут.

Она не обязана быть кратной 15 минутам.

## 4.4. Перерыв

ServiceOffering определяет длительность перерыва после консультации.

Перерыв не может иметь отрицательную длительность.

## 4.5. Интервал занятости

Занятость формируется как:

```text
sessionStart
    ↓
sessionEnd = sessionStart + durationMinutes
    ↓
occupiedUntil = sessionEnd + breakDurationMinutes
```

## 4.6. Исторические условия

Условия ServiceOffering, согласованные при создании Reservation, сохраняются в историческом snapshot.

Изменение услуги не должно менять уже созданные Reservation и Booking.

## 4.7. Деактивация

Деактивация ServiceOffering запрещает создание новых Reservation по ней.

Она не должна автоматически отменять существующие Booking.

---

# 5. Рабочее расписание

## 5.1. Владение

Каждый специалист управляет собственным расписанием в пределах разрешённых полномочий.

## 5.2. Режимы расписания

Поддерживаются:

- REGULAR;
- FLOATING.

## 5.3. REGULAR

Регулярное расписание определяется недельным шаблоном.

Изменения недельного расписания сохраняются в версиях.

## 5.4. Версионирование

Для одной календарной даты не должны одновременно действовать несколько конфликтующих WeeklyScheduleVersion.

## 5.5. Полный недельный шаблон

Каждая WeeklyScheduleVersion описывает полный недельный шаблон.

Отсутствующий рабочий интервал означает отсутствие работы в соответствующий период.

## 5.6. FLOATING

В режиме FLOATING рабочее время задаётся для конкретных дат.

Если для даты расписание не установлено, она считается нерабочей.

## 5.7. Исключения

В режиме REGULAR DateSchedule с типом OVERRIDE полностью заменяет регулярное расписание соответствующей даты.

Пустой OVERRIDE означает нерабочий день.

## 5.8. MANUAL

В режиме FLOATING используется DateSchedule с типом MANUAL.

## 5.9. Переключение режимов

Изменение REGULAR/FLOATING не удаляет конфигурацию неактивного режима.

## 5.10. Рабочие интервалы

Рабочие интервалы должны быть корректными и не должны недопустимо пересекаться.

Для обычного рабочего интервала локальное начало должно быть раньше локального окончания.

## 5.11. Существующие обязательства

Обычное изменение расписания не должно автоматически отменять:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 5.12. Новые бронирования

После изменения расписания новые Reservation проверяются по актуальной конфигурации.

---

# 6. Часовые пояса

## 6.1. Часовой пояс специалиста

У специалиста должен быть определён корректный IANA ZoneId.

## 6.2. Локальное расписание

Рабочие интервалы задаются в локальных датах и времени специалиста.

## 6.3. Абсолютное время консультаций

Фактическое начало и окончание консультации сохраняются как абсолютные моменты времени.

## 6.4. Неоднозначное начало

Создание новой Reservation с неоднозначным локальным временем начала не допускается.

## 6.5. Несуществующее начало

Создание Reservation для несуществующего локального времени при переходе на летнее или зимнее время не допускается.

## 6.6. Изменение ZoneId

Изменение часового пояса специалиста не изменяет абсолютные времена уже созданных Reservation и Booking.

## 6.7. Конкурентность

Изменение часового пояса должно согласовываться с одновременным созданием Reservation.

---

# 7. Динамическая доступность

## 7.1. Отсутствие предварительных слотов

В целевой модели отдельные AvailabilitySlot не создаются и не сохраняются.

## 7.2. Основание расчёта

Доступность определяется на основании:

- выбранной ServiceOffering;
- текущего расписания;
- ZoneId;
- действующих ScheduleOccupancy;
- временных ограничений;
- эффективного допуска специалиста.

## 7.3. Сетка начала

Доступные начала должны соответствовать локальной сетке с шагом 15 минут.

## 7.4. Размещение консультации

Консультация должна целиком помещаться внутри одного непрерывного рабочего интервала.

## 7.5. Перерыв

Перерыв после консультации учитывается при проверке пересечений Occupancy.

Он может выходить за пределы рабочего интервала и пересекать локальную полночь.

## 7.6. Предварительный характер

Просмотр доступного времени не удерживает интервал.

## 7.7. Окончательная проверка

Создание Reservation повторно проверяет необходимые условия.

## 7.8. Конкурентные запросы

Если два клиента одновременно выбирают одно и то же время, система должна предотвратить возникновение конфликтующих Occupancy.

# 8. Горизонт бронирования

## 8.1. Настройка

Специалист может выбирать горизонт записи:

- 14 дней;
- 30 дней;
- 60 дней;
- 90 дней.

## 8.2. Значение по умолчанию

По умолчанию используется 30 дней.

## 8.3. Применение

Новые Reservation могут создаваться только в пределах установленного горизонта.

## 8.4. Существующие записи

Уменьшение горизонта не должно автоматически отменять уже созданные Reservation и Booking.

---

# 9. MinimumBookingNotice

## 9.1. Назначение

minimumBookingNotice определяет, за какое минимальное время до начала консультации допускается создание новой Reservation.

## 9.2. Значение

Настройка не может быть отрицательной.

## 9.3. Booking Deadline

Дедлайн рассчитывается как:

```text
bookingDeadline = sessionStart - minimumBookingNotice
```

## 9.4. Правило создания

Новая Reservation допускается только при:

```text
now < bookingDeadline
```

## 9.5. Нулевое значение

Если minimumBookingNotice равно нулю:

```text
bookingDeadline = sessionStart
```

## 9.6. Независимость TTL

Reservation, созданная до дедлайна, может быть подтверждена после него, если:

- Reservation остаётся ACTIVE;
- её TTL не истёк;
- соблюдены остальные условия подтверждения.

## 9.7. Индивидуальные исключения

Механизм индивидуального переопределения minimumBookingNotice для конкретного времени не утверждён после отказа от AvailabilitySlot.

До отдельного решения применяется согласованное правило специалиста.

---

# 10. Reservation

## 10.1. Назначение

Reservation представляет временное удержание интервала консультации.

## 10.2. Статусы

```text
ACTIVE
CONFIRMED
CANCELLED
EXPIRED
```

## 10.3. Создание

Успешное создание Reservation должно одновременно создавать ScheduleOccupancy.

## 10.4. TTL

Каждая ACTIVE Reservation имеет системный срок действия.

Специалист не может изменять TTL.

## 10.5. Подтверждение

Reservation может быть подтверждена, только пока она ACTIVE и не истекла.

## 10.6. Единственность подтверждения

Одна Reservation не может быть подтверждена повторно с созданием дополнительной Booking.

## 10.7. Отмена

ACTIVE Reservation может перейти в CANCELLED по предусмотренному сценарию.

## 10.8. Истечение

ACTIVE Reservation переходит в EXPIRED после истечения TTL при выполнении соответствующей операции обработки.

## 10.9. Терминальность

CONFIRMED, CANCELLED и EXPIRED являются конечными состояниями Reservation.

## 10.10. История

Reservation не удаляется при подтверждении, отмене или истечении.

---

# 11. ScheduleOccupancy

## 11.1. Назначение

ScheduleOccupancy представляет действующую занятость времени специалиста.

## 11.2. Интервал

Используется полуоткрытый интервал:

```text
[sessionStart, occupiedUntil)
```

## 11.3. Пересечения

Действующие Occupancy одного специалиста не должны пересекаться.

## 11.4. Создание

ScheduleOccupancy создаётся вместе с ACTIVE Reservation.

## 11.5. Подтверждение

После подтверждения Reservation Occupancy сохраняется.

## 11.6. Отмена Reservation

При отмене ACTIVE Reservation соответствующая Occupancy удаляется.

## 11.7. Истечение Reservation

При истечении ACTIVE Reservation соответствующая Occupancy удаляется.

## 11.8. Отмена Booking

При допустимой отмене CONFIRMED Booking соответствующая Occupancy освобождается.

## 11.9. Исторические данные

Удаление Occupancy не означает удаление Reservation или Booking.

## 11.10. Завершившиеся интервалы

После окончания occupiedUntil действующая Occupancy может быть очищена без удаления исторических записей.

## 11.11. Ограничение пересечений

PostgreSQL должен предотвращать пересечение действующих интервалов одного специалиста.

---

# 12. Booking

## 12.1. Назначение

Booking представляет подтверждённую запись на консультацию.

## 12.2. Создание

Booking создаётся после успешного подтверждения Reservation.

## 12.3. Единственность

Одна Reservation может быть связана не более чем с одной Booking.

## 12.4. Статусы

Целевая модель использует:

```text
CONFIRMED
CANCELLED
```

## 12.5. История

Booking сохраняется после отмены и завершения назначенного времени.

## 12.6. Изменение условий

Изменение ServiceOffering или расписания специалиста не должно автоматически изменять исторические условия Booking.

## 12.7. Перенос

Отдельная операция переноса консультации не входит в согласованную модель MVP.

## 12.8. Результат консультации

BookingStatus не определяет, состоялась ли консультация фактически.

Для этого используется SessionOutcome.

---

# 13. Отмена консультации

## 13.1. Право клиента

Клиент может отменить собственную CONFIRMED Booking до начала консультации.

## 13.2. Ограничение

Обычная клиентская отмена после начала консультации не допускается.

## 13.3. ClientCancellationNotice

Специалист определяет длительность clientCancellationNotice.

Она не может быть отрицательной.

## 13.4. Дедлайн

```text
clientCancellationDeadline =
    sessionStart - clientCancellationNotice
```

## 13.5. Своевременная отмена

Отмена считается своевременной, если:

```text
cancelledAt < clientCancellationDeadline
```

## 13.6. Поздняя отмена

Отмена считается поздней, если:

```text
clientCancellationDeadline <= cancelledAt < sessionStart
```

## 13.7. Разрешение поздней отмены

Поздняя отмена разрешена до начала консультации.

## 13.8. Последствия

Для MVP поздняя отмена не предусматривает автоматических штрафов или денежных взысканий.

## 13.9. Статус

И своевременная, и поздняя отмена переводят Booking в CANCELLED.

Отдельный LATE_CANCELLED не вводится.

## 13.10. Метаданные

Система сохраняет:

- cancelledAt;
- cancellationInitiator.

## 13.11. Исторические условия

Для определения своевременности используется значение clientCancellationNotice, сохранённое при создании Reservation.

## 13.12. Освобождение времени

Отмена Booking освобождает соответствующую ScheduleOccupancy.

## 13.13. Повторное бронирование

Освобождённый интервал может стать доступным для новой Reservation только при соблюдении текущих бизнес-правил.

---

# 14. Административная блокировка

## 14.1. Отдельный допуск

SpecialistBookingAccess представляет самостоятельное административное разрешение принимать бронирования.

## 14.2. Потеря допуска

При административной потере права принимать бронирования система должна согласованно:

- запретить новые Reservation;
- отменить все ACTIVE Reservation специалиста;
- удалить соответствующие ScheduleOccupancy;
- сохранить предусмотренный аудит.

## 14.3. Атомарность

Изменение допуска и обязательные отмены выполняются атомарно.

## 14.4. CONFIRMED Booking

Подтверждённые Booking автоматически не отменяются.

## 14.5. Конкурентность

Создание и подтверждение Reservation должны согласовываться с административным изменением допуска.

## 14.6. Восстановление

Восстановление approvalStatus не должно автоматически снимать отдельно установленное ограничение bookingAllowed.

---

# 15. Результат консультации

## 15.1. Отдельная модель

Фактический результат консультации определяется через SessionOutcome.

## 15.2. Участники

Клиент и специалист независимо сообщают результат консультации.

## 15.3. Временное окно

Отчёты принимаются в течение 24 часов после завершения консультации:

```text
[sessionEnd, sessionEnd + 24 hours)
```

## 15.4. Допустимые ответы

- OCCURRED;
- DID_NOT_OCCUR.

## 15.5. Причины DID_NOT_OCCUR

- CLIENT_NO_SHOW;
- SPECIALIST_NO_SHOW;
- TECHNICAL_PROBLEM;
- OTHER.

## 15.6. OTHER

При выборе OTHER требуется непустое текстовое пояснение.

## 15.7. Неизменяемость

Каждый участник может представить не более одного неизменяемого отчёта по консультации.

## 15.8. Два OCCURRED

```text
OCCURRED + OCCURRED
→ RESOLVED / OCCURRED
```

## 15.9. Два совместимых DID_NOT_OCCUR

Автоматическое разрешение допускается, когда участники указали одинаковую структурированную причину, отличную от OTHER.

```text
DID_NOT_OCCUR + DID_NOT_OCCUR
→ RESOLVED / DID_NOT_OCCUR
```

## 15.10. Противоречия

Несовместимые результаты или причины переводят Outcome в DISPUTED.

## 15.11. OTHER в двух отчётах

Если среди двух отчётов присутствует OTHER, автоматическое совместное разрешение не выполняется.

В том числе:

```text
OTHER + OTHER
→ DISPUTED
```

## 15.12. Один отчёт

Если к завершению окна получен один отчёт, его результат принимается в соответствии с утверждённым правилом.

Это относится и к одному DID_NOT_OCCUR / OTHER.

## 15.13. Нет отчётов

Если ни один участник не ответил:

```text
PENDING → UNVERIFIED
```

Консультация не считается автоматически успешно проведённой.

## 15.14. Административный спор

DISPUTED Outcome разрешается администратором.

## 15.15. Сохранение истории

Оригинальные отчёты участников не изменяются после административного решения.

## 15.16. Административный результат

Решение администратора сохраняется отдельно.

При DID_NOT_OCCUR указывается причина.

Для OTHER требуется комментарий.

# 16. Отзывы

## 16.1. Eligibility

Клиент может создать Review специалисту при наличии хотя бы одной исторической консультации соответствующей пары с результатом:

```text
SessionOutcome.resolutionStatus = RESOLVED
SessionOutcome.finalOutcome = OCCURRED
```

## 16.2. Способ разрешения

Не имеет значения, как был получен окончательный OCCURRED.

Основанием могут быть:

- два совместимых отчёта;
- один отчёт, принятый после тайм-аута;
- административное разрешение спора.

## 16.3. Недостаточные основания

Не предоставляют права на создание Review:

- PENDING;
- DISPUTED;
- UNVERIFIED;
- RESOLVED / DID_NOT_OCCUR;
- одна только CONFIRMED Booking.

## 16.4. Уникальность

Один клиент может иметь не более одного Review одному специалисту.

## 16.5. Повторные консультации

Дополнительные успешные консультации не позволяют создавать дополнительные Review той же пары.

## 16.6. Редактирование

Клиент может редактировать собственный Review.

Для редактирования не требуется новая успешная консультация.

## 16.7. Rating

Оценка должна находиться в диапазоне:

```text
1..5
```

## 16.8. Историческое основание

Review сохраняет ссылку на Booking, послужившую первоначальным основанием для создания отзыва.

Чат не изменяет напрямую Reservation, Booking или SessionOutcome.

# 18. Публичный профиль специалиста


## 18.1. Условия публичной видимости

Специалист отображается в публичном каталоге только при одновременном выполнении:

- `UserStatus = ACTIVE`;
- `Specialist.approvalStatus = APPROVED`.

При статусах PENDING, REJECTED или SUSPENDED специалист скрывается из публичного каталога.

Если `UserStatus = BLOCKED`, специалист также скрывается независимо от модерационного статуса.

## 18.2. Независимость от BookingAccess

Публичная видимость специалиста не зависит от `SpecialistBookingAccess.bookingAllowed`.

Если специалист имеет `approvalStatus = APPROVED`, но `bookingAllowed = FALSE`:

- специалист остаётся в публичном каталоге;
- клиенты могут просматривать его профиль, услуги и отзывы;
- запись к нему недоступна;
- интерфейс отображает сообщение «Запись временно недоступна».

Создание новых и подтверждение существующих ACTIVE Reservation запрещается.

## 18.3. Приостановка профессионального допуска

При переходе специалиста в SUSPENDED:

- специалист исключается из публичного каталога;
- новые Reservation запрещаются;
- существующие ACTIVE Reservation отменяются;
- соответствующие ScheduleOccupancy освобождаются;
- CONFIRMED Booking сохраняются.

## 18.4. Состояние услуг

Административное ограничение не изменяет автоматически `ServiceOffering.isActive`.

Активная услуга не означает, что к специалисту разрешено записываться.

При создании Reservation система должна независимо проверять активность услуги и эффективный допуск специалиста.

## 18.5. Восстановление допуска

После восстановления `approvalStatus = APPROVED` специалист снова отображается в публичном каталоге при условии `UserStatus = ACTIVE`.

При восстановлении `bookingAllowed = TRUE` возможность записи определяется актуальными условиями бронирования.

Ранее отменённые Reservation автоматически не восстанавливаются.

## 18.6. Самостоятельное скрытие профиля

Возможность самостоятельного скрытия профиля одобренным специалистом рассматривается отдельно.

Необходимо определить, влияет ли такое скрытие на возможность создания новых Reservation.

# 19. Уведомления

## 19.1. Основание

Уведомления формируются по предусмотренным бизнес-событиям.

## 19.2. Примеры

- BookingConfirmed;
- BookingCancelled;
- ReservationExpired;
- SessionOutcomeResolved;
- административное изменение допуска.

## 19.3. Транзакционная граница

Уведомление об успешной операции не должно обрабатываться как подтверждённый факт до COMMIT основной транзакции.

## 19.4. Независимость

Ошибка доставки уведомления не должна отменять успешно зафиксированную Booking.

## 19.5. Надёжность

Конкретные гарантии доставки определяются отдельно.

# 20. Целостность бизнес-состояния

## 20.1. Атомарность

Критические связанные изменения должны выполняться атомарно.

## 20.2. Reservation и Occupancy

Нельзя сохранять ACTIVE Reservation без обязательного удержания времени.

## 20.3. Подтверждение

Нельзя сохранять CONFIRMED Reservation без соответствующей Booking.

## 20.4. Отмена

Отмена Reservation или Booking должна согласованно освобождать занятость, когда освобождение предусмотрено её состоянием.

## 20.5. База данных

PostgreSQL должен обеспечивать критические ограничения целостности там, где это возможно.

## 20.6. Конкурентность

Проверка доступности до транзакции не гарантирует успешного создания Reservation.

## 20.7. Состояния

Запрещены переходы, не предусмотренные жизненным циклом соответствующей сущности.

## 20.8. История

Исторические Reservation и Booking не удаляются только вследствие завершения их жизненного цикла.

# 22. Открытые бизнес-вопросы

Следующие решения ещё требуют окончательного согласования.

## 22.1. Пересекающиеся консультации клиента

Исходные требования предусматривают запрет пересекающихся консультаций одного клиента у разных специалистов.

Необходимо определить:

- распространяется ли запрет на ACTIVE Reservation;
- распространяется ли он на CONFIRMED Booking;
- учитывается ли перерыв после консультации;
- какой механизм обеспечивает конкурентную защиту.

Существующая модель ScheduleOccupancy гарантирует отсутствие конфликтов у специалиста, но не обеспечивает автоматически аналогичный запрет для клиента.

## 22.2. Отмена специалистом

Требуется уточнить:

- допустимые сроки;
- обязательные последствия;
- необходимость уведомления клиента;
- связь с будущей аналитикой надёжности.

## 22.3. Административная блокировка клиента

Необходимо определить последствия блокировки CLIENT для уже существующих ACTIVE Reservation и CONFIRMED Booking.

## 22.4. Публичность профиля

Необходимо согласовать связь между скрытием публичного профиля и доступностью новых бронирований.

## 22.5. Индивидуальный MinimumBookingNotice

После отказа от AvailabilitySlot требуется определить, нужен ли механизм локального переопределения minimumBookingNotice.

## 22.6. Границы времени

Требуют решения:

- рабочие интервалы, заканчивающиеся в 24:00;
- консультации, пересекающие DST-переход;
- включение последней календарной даты booking horizon.

## 22.7. Модерация Review

Необходимо определить правила административного скрытия, удаления и обжалования отзывов.

## 22.8. Внешняя доставка Notification

Нужно согласовать уровень надёжности, необходимые каналы и правила повторной доставки.

# 24. Итог

Основные бизнес-правила PsyWeb:

- User и Specialist имеют независимые состояния;
- право принимать бронирования определяется эффективным допуском;
- ServiceOffering задаёт условия консультации и перерыва;
- Schedule определяет рабочее время;
- Availability рассчитывается динамически;
- Reservation временно удерживает интервал;
- ScheduleOccupancy предотвращает двойное бронирование специалиста;
- Booking создаётся после подтверждения Reservation;
- отмена и истечение освобождают соответствующую занятость;
- поздняя клиентская отмена разрешена до начала консультации;
- административная потеря допуска отменяет ACTIVE Reservation, сохраняя CONFIRMED Booking;
- результат консультации определяется отдельно через SessionOutcome;
- Review разрешён после окончательного OCCURRED;
- один клиент может иметь только один Review одного специалиста;
- критические изменения сохраняют транзакционную согласованность;
- нерешённые бизнес-вопросы не считаются утверждёнными правилами.

**Статус: DRAFT — правила актуализированы в соответствии с целевой архитектурой PsyWeb.**
