# Overview

This document defines core business rules that govern system behavior.

Business Rules are independent from implementation and must be enforced at the application level and, where applicable, at the database level.

---

# 1. User Rules

## BR-001 — Unique Email Constraint
Each user must have a unique email address across the platform.

---

## BR-002 — Account Activation Requirement
Only users with **Active** status can access protected functionality.

---

## BR-003 — Specialist Approval Requirement
Specialist accounts must be approved by an administrator before becoming Active.

---

## BR-004 — Role-Based Access Control
System access is strictly controlled based on user role:
- Client
- Specialist
- Administrator

Users cannot access functionality outside their role permissions.

---

# 2. Booking Rules

## BR-005 — No Double Booking (Global Constraint)
A time slot can be booked by only one client.

---

## BR-006 — Client Appointment Overlap Restriction
A client cannot have overlapping appointments in time.

---

## BR-007 — Specialist Slot Exclusivity
A specialist cannot have overlapping availability slots.

---

## BR-008 — Appointment Creation Dependency
An appointment can only be created if:
- a valid service exists
- a valid availability slot exists
- specialist is active

---

## BR-009 — Atomic Booking Operation
Booking must be executed as an atomic transaction.
Either:
- appointment is fully created and slot is reserved
OR
- no changes are applied

---

# 3. Cancellation Rules

## BR-010 — Cancellation Time Restriction
Appointments cannot be cancelled less than a defined time before start (default: 24 hours, configurable per specialist).

---

## BR-011 — Cancellation Ownership Rule
Only the client or assigned specialist may cancel an appointment.

---

## BR-012 — Slot Restoration Rule
When an appointment is cancelled, the associated slot must be returned to available state (if applicable).

---

# 4. Review Rules

## BR-013 — Review Eligibility

A Client may create a Review for a Specialist only if there exists at least one historical consultation for that Client-Specialist pair with:

```text
SessionOutcome.resolutionStatus = RESOLVED
SessionOutcome.finalOutcome = OCCURRED
```

The way in which the final OCCURRED outcome was obtained does not affect eligibility.

Dual participant confirmation is not required as a separate condition.

The following SessionOutcome states do not provide Review eligibility:

```text
PENDING
DISPUTED
UNVERIFIED
RESOLVED / DID_NOT_OCCUR
```

---

## BR-014 — One Review Per Client-Specialist Relationship

A Client may have at most one Review for the same Specialist.

This invariant is independent from the number of consultations between them.

An existing Review may be edited instead of creating another Review.

---

## BR-015 — Rating Constraint

Review rating must be within the range:

```text
1..5
```

---

# 5. Chat Rules

## BR-016 — Chat Access Restriction
Chat is allowed only if:
- specialist has enabled chat
- users have an existing relationship (appointment or permission context)

---

## BR-017 — Message Ownership Rule
Only authenticated participants of a chat can send or receive messages.

---

# 6. Specialist Rules

## BR-018 — Profile Visibility Control
Specialists can toggle profile visibility (published / hidden).

---

## BR-019 — Service Requirement
Availability slots can only be created if at least one service exists.

---

# 7. System Integrity Rules

## BR-020 — Consistency Requirement
System must ensure consistency between:
- appointments
- availability slots
- user status

---

## BR-021 — Status Integrity Rule
Invalid state transitions are not allowed:
- Rejected → Active (not allowed)
- Cancelled → Active (not allowed)

---

# Notes

## Enforcement Levels

Business Rules must be enforced at:
- Application layer (Spring services)
- Database layer (constraints where possible)
- Transaction boundaries

---

## Design Impact

These rules directly influence:
- database schema design
- service layer logic
- transaction handling
- concurrency strategy

- payments
