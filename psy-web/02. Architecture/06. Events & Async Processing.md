
**System:** PsyWeb Backend  
**Architecture Style:** Event-driven extensions (MVP: synchronous, future: async-ready)

---

# Overview

The system is primarily synchronous (REST-based), but designed with **event-driven architecture readiness** for future scalability.

Certain domain actions generate events that can later be processed asynchronously.

---

# 1. Current State (MVP)

In MVP version:

- all operations are synchronous
- events are emitted internally (in-memory conceptually)
- no message broker is used yet

---

# 2. Future State (Scalable Architecture)

System is designed to support:

- Kafka / RabbitMQ (event broker)
- async notification processing
- decoupled services

---

# 3. Domain Events

## DE-001 — AppointmentCreated

### Trigger:
When a booking is successfully created.

### Payload:
- appointmentId
- clientId
- specialistId
- time slot
- timestamp

### Future Handlers:
- send notification to client
- send notification to specialist
- analytics tracking

---

## DE-002 — AppointmentCancelled

### Trigger:
When appointment is cancelled.

### Future Handlers:
- notify both participants
- release slot in availability service
- update statistics

---

## DE-003 — ReviewCreated

### Trigger:
When client submits a review.

### Future Handlers:
- recalculate specialist rating
- moderation queue (if enabled)
- analytics updates

---

## DE-004 — SpecialistApproved

### Trigger:
Admin approves specialist registration.

### Future Handlers:
- send email notification
- activate profile visibility

---

## DE-005 — MessageSent

### Trigger:
When chat message is sent.

### Future Handlers:
- real-time delivery (WebSocket)
- notification fallback if user offline

# 7. Event Flow Example (Booking)

```text
1. Client books appointment
2. Booking service creates appointment
3. System emits AppointmentCreated event
4. Event is processed by:
   - Notification handler
   - Analytics handler
```

---

# 8. Design Principles

## 1. Core domain remains synchronous
Critical operations:
- booking
- cancellation
- slot management

must remain strongly consistent.

---

## 2. Side effects are asynchronous
Non-critical operations:
- notifications
- analytics
- email sending

should be event-driven.

---

## 3. Loose coupling
Event producers do not depend on consumers.

---

# 9. Future Extensions

System can evolve into:

- full event-driven microservice architecture
- dedicated notification service
- real-time chat service with WebSockets
- analytics pipeline

---

# Notes

This module is intentionally designed as **future-proofing layer** to allow smooth transition from monolith to distributed architecture without rewriting core business logic.
