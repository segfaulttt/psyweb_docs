**System:** PsyWeb Backend  
**Architecture Style:** Synchronous Core with Optional Asynchronous Extensions

---

# Overview

PsyWeb uses synchronous processing for core business operations.

Asynchronous processing may be introduced later for non-critical side effects where delayed execution and eventual consistency are acceptable.

The system does not require an event-driven architecture for the MVP.

Core business state must remain correct even if asynchronous processing is unavailable.

---

# 1. Current State

The MVP uses synchronous service-level interactions inside the modular monolith.

Core operations such as:

- reservation creation
- reservation confirmation
- reservation cancellation and expiration
- booking creation
- booking cancellation
- availability state changes
- specialist approval

are executed through explicit service calls and transactional boundaries.

No message broker is required for the MVP.

Domain or application events may be introduced later when they solve a concrete decoupling or asynchronous-processing requirement.

---

# 2. Synchronous Core

Consistency-sensitive operations must remain synchronous and transactionally coordinated.

Examples include:

- creating an ACTIVE Reservation and holding its AvailabilitySlot
- confirming a Reservation and transitioning the slot to BOOKED
- creating the corresponding Booking
- cancelling or expiring a Reservation and releasing the slot
- cancelling a Booking and releasing the slot
- enforcing booking and availability invariants

These state changes form part of the core business transaction and must not depend on asynchronous event delivery.

---

# 3. Asynchronous Side Effects

Asynchronous processing is appropriate for operations that are not required to maintain immediate core-domain consistency.

Examples include:

- email notifications
- in-app notifications
- analytics
- audit pipelines
- non-critical reporting
- external integrations

Failure of an asynchronous side effect must not leave Reservation, Booking, AvailabilitySlot, User, or Specialist state inconsistent.

---

# 4. Event Candidates

The following events may be introduced later if asynchronous consumers are required.

These are architectural candidates, not mandatory MVP infrastructure.

---

## BookingConfirmed

### Trigger

Published after a Booking has been successfully created and the related transaction has completed successfully.

### Possible Data

- bookingId
- clientId
- specialistId
- slotId
- timestamp

### Possible Consumers

- notification processing
- analytics
- reporting

---

## BookingCancelled

### Trigger

Published after the Booking cancellation and AvailabilitySlot release have completed successfully.

### Possible Data

- bookingId
- clientId
- specialistId
- slotId
- timestamp

### Possible Consumers

- participant notifications
- analytics
- reporting

Slot release is not an asynchronous consumer responsibility. It belongs to the synchronous booking cancellation transaction.

---

## ReservationExpired

### Trigger

Published after an expired Reservation has been persisted and its held AvailabilitySlot has been released.

### Possible Consumers

- analytics
- metrics
- optional client notification

---

## ReviewCreated

### Trigger

Published after a Review has been successfully created.

### Possible Consumers

- notification processing
- analytics
- rating projection updates if such projections are introduced later

---

## SpecialistApproved

### Trigger

Published after the Specialist approval transition has completed successfully.

### Possible Consumers

- email notification
- in-app notification
- analytics

---

## MessageSent

### Trigger

Published after a chat message has been persisted.

### Possible Consumers

- real-time delivery
- notification fallback
- analytics

The exact communication architecture is outside the current MVP booking core.

---

# 5. Event Publication Rule

An event representing a completed business operation must not be treated as completed before the corresponding database transaction succeeds.

For example:

Booking cancellation must first complete:

- Booking state transition
- AvailabilitySlot release
- transaction commit

Only after the core state is successfully persisted may secondary processing such as notifications or analytics be triggered.

The implementation mechanism for transaction-safe event publication should be selected only when asynchronous processing is introduced.

---

# 6. Consistency Model

## Core Domain

Core business state uses strong consistency within the required transaction boundary.

This includes:

- Reservation
- Booking
- AvailabilitySlot
- account and specialist state changes where immediate consistency is required

---

## Secondary Processing

Future asynchronous side effects may use eventual consistency.

Examples:

- notifications
- analytics
- reporting
- external integrations

Temporary delay or failure in these components must not invalidate the core business transaction.

---

# 7. Possible Implementation Options

If asynchronous processing becomes necessary, implementation options may include:

## Internal Application Events

Spring application-level events may be used for lightweight in-process decoupling.

This is suitable only when process-local delivery semantics are sufficient.

---

## External Message Broker

A message broker may be introduced if the system later requires:

- reliable asynchronous delivery
- independent consumers
- retry handling
- cross-service communication
- separate deployment or scaling of consumers

The choice of technology should be based on actual requirements.

Kafka or RabbitMQ are possible options, not predefined architectural requirements.

---

# 8. Transactional Reliability

If reliable asynchronous delivery becomes business-critical, event publication must account for the database transaction boundary.

The system must avoid scenarios where:

- business data commits but the required event is permanently lost
- an event is published for a transaction that later rolls back

Patterns such as transactional event publication or an outbox may be evaluated if such reliability requirements appear.

They are not required for the current MVP.

---

# 9. Module Boundaries

Events do not change module ownership rules.

A module must not use asynchronous events as a workaround for directly changing another module's domain state.

For example:

Booking may notify other modules that a Booking was cancelled.

However, the AvailabilitySlot state required by that cancellation must still be changed through the Availability module's service boundary as part of the consistency-sensitive operation.

Events are intended primarily for decoupled reactions, not for bypassing synchronous domain ownership.

---

# 10. Design Principles

## 1. Core Correctness First

Core business state must remain correct without relying on asynchronous processing.

---

## 2. Async for Secondary Effects

Asynchronous processing should be introduced primarily for non-critical side effects.

---

## 3. Explicit Consistency Boundaries

The system must clearly distinguish:

- state that must change atomically
- state that may update later

---

## 4. No Premature Infrastructure

Message brokers, distributed event processing, and additional infrastructure should only be introduced when concrete requirements justify their operational complexity.

---

## 5. Producer Independence

When events are introduced, producers should describe completed business facts without depending on specific consumers.

---

# Future Evolution

Possible future evolution includes:

- asynchronous notification delivery
- dedicated real-time chat delivery
- analytics consumers
- integration events between independently deployed services

These changes are optional architectural extensions and are not prerequisites for the modular monolith MVP.

---

# Notes

PsyWeb is not designed around the assumption that it must eventually become a fully event-driven microservice system.

The primary architectural goal is correct and understandable business state.

Asynchronous processing is an optional tool for decoupling secondary work when the product or operational requirements justify it.
