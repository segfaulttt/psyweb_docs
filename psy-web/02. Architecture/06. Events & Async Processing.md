
# 06. События и асинхронная обработка (Events & Async Processing)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Модель обработки:** Synchronous Core + Optional Asynchronous Processing  
**Статус:** DRAFT — целевая архитектура событийного взаимодействия

---

# 1. Назначение документа

Документ определяет принципы синхронного и асинхронного взаимодействия компонентов PsyWeb.

В нём рассматриваются:

- синхронное выполнение критических бизнес-операций;
- транзакционные границы;
- события приложения;
- возможные асинхронные обработчики;
- уведомления;
- гарантии согласованности;
- публикация событий после COMMIT;
- надёжность доставки;
- потенциальное использование transactional outbox;
- границы ответственности бизнес-модулей.

Основная цель — обеспечить корректность бизнес-состояния независимо от доступности дополнительных асинхронных компонентов.

PsyWeb не требует полноценной event-driven architecture для MVP.

---

# 2. Архитектурный подход

## 2.1. Синхронное ядро

Основные бизнес-операции выполняются синхронно через сервисные контракты модулей.

## 2.2. Асинхронные расширения

Асинхронная обработка может применяться к производным действиям, которые не обязаны завершаться одновременно с основной операцией.

## 2.3. Модульный монолит

Все основные модули функционируют внутри одного Spring Boot приложения.

## 2.4. База данных

PostgreSQL обеспечивает транзакционную согласованность основных бизнес-состояний.

## 2.5. Message broker

Kafka, RabbitMQ и другие внешние брокеры сообщений не являются обязательными компонентами MVP.

## 2.6. Основной принцип

**Асинхронные события не должны заменять обязательные синхронные изменения, от которых зависит целостность Booking.**

---

# 3. Текущая и целевая реализация

## 3.1. Исходная модель

Первоначальная реализация PsyWeb использовала:

- AvailabilitySlot;
- Reservation;
- Booking;
- синхронные сервисные операции;
- PostgreSQL-транзакции;
- фоновую обработку истечения Reservation.

## 3.2. Целевая модель

Новая архитектура использует:

- ServiceOffering;
- Schedule;
- Dynamic Availability;
- Reservation;
- Booking;
- ScheduleOccupancy;
- SessionOutcome;
- Review;
- Notification.

## 3.3. Изменение ответственности

Availability больше не владеет сохраняемыми временными слотами.

Действующая занятость представлена ScheduleOccupancy, которой владеет Booking.

## 3.4. Состояние событий

Описанные далее события являются кандидатами для реализации.

Они не считаются автоматически существующими Java-классами или уже работающими механизмами.

---

# 4. Синхронное бизнес-ядро

## 4.1. Общий принцип

Операции, формирующие одно согласованное изменение бизнес-состояния, выполняются в соответствующей транзакции.

## 4.2. Основные операции

К синхронным операциям относятся:

- создание Reservation;
- создание ScheduleOccupancy;
- подтверждение Reservation;
- создание Booking;
- отмена Reservation;
- истечение Reservation;
- отмена Booking;
- удаление соответствующей Occupancy;
- административная блокировка специалиста;
- изменение допуска;
- конкурентное изменение расписания;
- сохранение результата SessionOutcome;
- разрешение споров;
- создание Review с проверкой eligibility.

## 4.3. Атомарность

Если одна из обязательных частей операции завершается ошибкой, нельзя сохранять противоречивое частичное состояние.

## 4.4. События

Событие не должно выполнять обязательную часть основной транзакции вместо сервиса-владельца.

---

# 5. Создание Reservation

## 5.1. Назначение

Создание Reservation временно удерживает выбранное время специалиста.

## 5.2. Синхронная операция

```text id="gdn3tr"
ReservationApplicationService
    ↓
Проверка бизнес-условий
    ↓
Создание ACTIVE Reservation
    ↓
Создание ScheduleOccupancy
    ↓
COMMIT
```

## 5.3. Гарантия

Reservation и ScheduleOccupancy должны быть созданы атомарно.

## 5.4. Асинхронная реакция

После успешного COMMIT может быть сформировано событие:

`ReservationCreated`

## 5.5. Возможные потребители

- Notification;
- Analytics;
- Logging.

## 5.6. Ограничение

Событие ReservationCreated не должно использоваться для асинхронного создания ScheduleOccupancy.

---

# 6. Подтверждение Reservation

## 6.1. Назначение

ACTIVE Reservation преобразуется в подтверждённую запись.

## 6.2. Синхронная операция

```text id="32fnse"
Reservation ACTIVE
    ↓
Проверка TTL и допуска
    ↓
Reservation CONFIRMED
    ↓
Booking CONFIRMED
    ↓
ScheduleOccupancy сохраняется
    ↓
COMMIT
```

## 6.3. Событие

После успешной фиксации может публиковаться:

`BookingConfirmed`

## 6.4. Возможные потребители

- Notification;
- Analytics;
- Reporting;
- будущие внешние интеграции.

## 6.5. Запрет

Создание Booking не должно зависеть от успешной доставки BookingConfirmed.

---

# 7. Отмена и истечение Reservation

## 7.1. Отмена

Синхронно выполняются:

```text id="nxv02d"
Reservation ACTIVE → CANCELLED
    +
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 7.2. Истечение

Синхронно выполняются:

```text id="ej0tju"
Reservation ACTIVE → EXPIRED
    +
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 7.3. События

Возможные события:

- ReservationCancelled;
- ReservationExpired.

## 7.4. Потребители

- Notification;
- Analytics;
- Metrics.

## 7.5. Ограничение

Удаление Occupancy является частью основной операции.

Его нельзя откладывать до асинхронного обработчика.

## 7.6. История

Reservation сохраняется после отмены или истечения.

---

# 8. Отмена Booking

## 8.1. Назначение

Отмена подтверждённой консультации освобождает ранее занятое время.

## 8.2. Синхронная операция

```text id="nrir3r"
Booking CONFIRMED → CANCELLED
    +
Cancellation Metadata
    +
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 8.3. Событие

После успешной фиксации может публиковаться:

`BookingCancelled`

## 8.4. Возможные данные

- bookingId;
- clientId;
- specialistId;
- occurredAt;
- cancellationInitiator.

## 8.5. Поздняя отмена

Признак поздней отмены определяется на основании сохранённых временных условий.

Отдельный BookingStatus.LATE_CANCELLED не требуется.

## 8.6. Потребители

- уведомления участников;
- аналитика отмен;
- будущая аналитика надёжности.

## 8.7. Запрет

Освобождение ScheduleOccupancy нельзя выполнять только при получении BookingCancelled.

---

# 9. Административная блокировка

## 9.1. Назначение

При административной потере допуска специалиста необходимо согласованно обработать ACTIVE Reservation.

## 9.2. Синхронная операция

```text id="r6ls4a"
AdministrativeBlockingService
    ↓
Изменение допуска
    ↓
Отмена ACTIVE Reservation
    ↓
Удаление соответствующих Occupancy
    ↓
Административный аудит
    ↓
COMMIT
```

## 9.3. Подтверждённые Booking

CONFIRMED Booking автоматически не отменяются.

## 9.4. Возможное событие

`SpecialistBookingAccessChanged`

## 9.5. Возможные потребители

- Notification;
- Analytics;
- Admin reporting.

## 9.6. Ограничение

Нельзя выполнять обязательную отмену ACTIVE Reservation через отложенный асинхронный обработчик.

Иначе между блокировкой и обработкой события возникнет несогласованное состояние.

# 10. Изменение расписания

## 10.1. Назначение

Специалист может изменять рабочую конфигурацию.

## 10.2. Возможные операции

- изменение WeeklyScheduleVersion;
- изменение DateSchedule;
- переключение REGULAR/FLOATING;
- изменение ZoneId;
- изменение настроек расписания.

## 10.3. Синхронная часть

Изменение расписания выполняется в согласованной транзакции с необходимой календарной координацией.

## 10.4. Существующие обязательства

Обычные изменения расписания не отменяют:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 10.5. Возможные события

- SpecialistScheduleChanged;
- SpecialistTimeZoneChanged.

## 10.6. Потребители

- Notification, если предусмотрено уведомление;
- Analytics;
- будущий cache invalidation.

## 10.7. Ограничение

Событие об изменении расписания не заменяет транзакционный механизм проверки конкурентных Reservation.

# 11. SessionOutcome

## 11.1. Назначение

SessionOutcome определяет фактический результат консультации.

## 11.2. Отчёты участников

Клиент и специалист независимо отправляют отчёты.

## 11.3. Синхронная часть

Сохранение отчёта и необходимое изменение состояния SessionOutcome должны выполняться согласованно.

## 11.4. Совместимые отчёты

При наличии совместимых данных Outcome может автоматически получить окончательный результат.

## 11.5. Спорные отчёты

Противоречивые ответы переводят Outcome в DISPUTED.

## 11.6. Временное окно

Для MVP предусмотрено 24 часа после консультации.

## 11.7. Фоновая обработка

После завершения окна система может обрабатывать Outcome, требующие разрешения по тайм-ауту.

## 11.8. Событие

После окончательного разрешения может формироваться:

`SessionOutcomeResolved`

## 11.9. Возможные потребители

- Notification;
- Analytics;
- Review-related projections.

## 11.10. Ограничение

Финальный результат Outcome нельзя определять внутри Notification.

## 12.1. Назначение

Review содержит отзыв клиента о специалисте.

## 12.2. Условие

Первоначальное создание Review разрешено после подтверждённо успешной консультации.

## 12.3. Синхронная операция

## 12.4. Уникальность

`UNIQUE(client_id, specialist_id)`

## 12.5. Возможные события

- ReviewCreated;
- ReviewUpdated.

## 12.6. Потребители

- Notification;
- Analytics;
- rating projection, если будет введена.

## 12.7. Ограничение

Событие ReviewCreated не заменяет проверку права на отзыв.

# 15. Структура событий

## 15.1. Общий принцип

Событие представляет immutable описание произошедшего факта.

## 15.2. Возможные поля

- eventId;
- eventType;
- aggregateId;
- occurredAt;
- actorId;
- дополнительные предметные данные.

## 15.3. Необязательность универсальной модели

Не требуется вводить единый универсальный Event DTO для всех событий, если конкретные обработчики могут использовать более простые контракты.

## 15.4. Минимизация данных

События должны содержать только сведения, необходимые для предусмотренных обработчиков.

## 15.5. Чувствительные сведения

Нельзя включать без необходимости:

- passwordHash;
- JWT;
- конфиденциальные данные консультаций;
- свободный текст SessionOutcomeReport;
- избыточную персональную информацию.

## 15.6. Идентификаторы

Для событий, которые могут обрабатываться повторно, eventId может использоваться для дедупликации.

# 16. Публикация после COMMIT

## 16.1. Основное требование

Событие, обозначающее успешно завершённую операцию, не должно обрабатываться как окончательный факт до успешного COMMIT соответствующей транзакции.

## 16.2. Пример

```text id="zr74pv"
BookingService
    ↓
Booking CONFIRMED
    ↓
Transaction COMMIT
    ↓
BookingConfirmed
    ↓
Notification
```

## 16.3. Rollback

Если транзакция откатилась, обработчик не должен отправлять уведомление об успешном подтверждении.

## 16.4. Spring

Для внутрипроцессных реакций может использоваться:

`@TransactionalEventListener(phase = AFTER_COMMIT)`

## 16.5. Ограничение

AFTER_COMMIT определяет фазу выполнения обработчика.

Он сам по себе не гарантирует сохранение события и последующую доставку при аварийном завершении приложения.

## 16.6. Дальнейшие операции с БД

Если AFTER_COMMIT обработчик должен записывать новые данные, его транзакционная граница должна быть определена отдельно.

Нельзя автоматически предполагать, что запись в обработчике надёжно фиксируется в уже завершённой основной транзакции.

---

# 17. Надёжность доставки событий

## 17.1. Проблема

Возможна ситуация:

```text id="biqc57"
Business Transaction COMMIT
    ↓
Application Crash
    ↓
Event Handler Not Executed
```

## 17.2. Следствие

Основная операция успешно завершена.

Но событие может быть потеряно.

## 17.3. AFTER_COMMIT

Обычный AFTER_COMMIT listener не устраняет этот риск.

## 17.4. MVP

Если гарантированная доставка события не требуется, допустима более простая внутрипроцессная обработка.

## 17.5. Критические события

Если потеря события становится недопустимой, необходимо использовать механизм с долговременной фиксацией факта публикации.

## 17.6. Вариант

Transactional outbox.

## 17.7. Решение

Уровень надёжности должен определяться конкретными продуктовыми требованиями Notification и других потребителей.

---

# 18. Transactional Outbox

## 18.1. Назначение

Transactional outbox обеспечивает атомарное сохранение бизнес-изменения и записи о событии.

## 18.2. Принцип

```text id="yl851x"
Business Transaction
    ├── UPDATE Booking
    └── INSERT OutboxEvent
             ↓
           COMMIT
             ↓
       Outbox Processor
             ↓
        Event Delivery
```

## 18.3. Гарантия

Если транзакция не зафиксирована, запись события также не сохраняется.

Если транзакция зафиксирована, запись события остаётся доступной для последующей обработки.

## 18.4. Повторная доставка

Outbox не исключает повторную доставку.

## 18.5. Идемпотентность

Потребители должны учитывать возможность повторной обработки.

## 18.6. Дополнительная сложность

Outbox требует:

- дополнительную таблицу;
- механизм обработки;
- учёт повторных попыток;
- очистку обработанных событий;
- мониторинг ошибок.

## 18.7. Статус

Transactional outbox не объявляется обязательной частью MVP без отдельного решения.

---

# 19. Варианты реализации

## 19.1. Синхронный сервисный вызов

Подходит для операций, которым нужна непосредственная согласованность.

Примеры:

- Booking confirmation;
- Reservation expiration;
- административная блокировка;
- изменение конфигурации Schedule.

## 19.2. Spring Application Events

Могут использоваться для слабосвязанных реакций внутри одного приложения.

## 19.3. @TransactionalEventListener

Позволяет связать обработку с фазой транзакции.

## 19.4. @Async

Может использоваться для асинхронного выполнения отдельных задач.

При этом необходимо отдельно учитывать:

- границы транзакций;
- обработку ошибок;
- потери при остановке процесса;
- завершение приложения;
- повторные попытки.

## 19.5. Message Broker

Может использоваться при необходимости:

- независимых потребителей;
- распределённой обработки;
- масштабирования доставки;
- повторных попыток;
- межсервисного взаимодействия.

## 19.6. Примеры

- RabbitMQ;
- Kafka.

## 19.7. Отсутствие обязательности

Выбор брокера не фиксируется архитектурой MVP.

# 20. Модель согласованности

## 20.1. Strong Consistency

Для критического состояния требуется согласованное изменение в рамках транзакционной модели PostgreSQL.

## 20.2. Основные объекты

- Reservation;
- Booking;
- ScheduleOccupancy;
- SpecialistBookingAccess;
- необходимые административные изменения допуска;
- связанные изменения SessionOutcome.

## 20.3. Eventual Consistency

Допускается для:

- уведомлений;
- аналитики;
- некоторых производных представлений;
- внешних интеграций.

## 20.4. Разделение

Производная система может временно отставать от источника истины.

Но она не должна подменять источник истины.

## 20.5. Пример

Notification может отобразиться позже подтверждения Booking.

Это допустимо.

Но Booking не должна оставаться неподтверждённой до обработки уведомления.

# 21. Notification

## 21.1. Назначение

Notification управляет уведомлениями пользователей.

## 21.2. Каналы

Для MVP может использоваться внутриплатформенное уведомление.

В будущем могут быть добавлены:

- email;
- push;
- другие каналы.

## 21.3. Источник данных

Notification реагирует на бизнес-факты.

## 21.4. Владение

Notification владеет собственным состоянием уведомления.

## 21.5. Независимость

Notification не должен изменять Booking или Outcome.

## 21.6. Ошибки

Ошибка доставки уведомления не должна отменять успешно зафиксированную Booking.

## 21.7. Прочтение

Состояние readAt относится к факту прочтения пользователем.

Оно не равно подтверждённой внешней доставке.

# 22. Асинхронные фоновые задачи

## 22.1. Назначение

Фоновые задачи используются для операций, не требующих непосредственного HTTP-запроса.

## 22.2. Reservation Expiration Scheduler

Expiration Scheduler обрабатывает ACTIVE Reservation с истёкшим TTL.

## 22.3. Особенность

Scheduler выполняет критическую бизнес-операцию, несмотря на фоновый способ запуска.

## 22.4. Требование

Переход Reservation в EXPIRED и удаление Occupancy должны выполняться транзакционно.

## 22.5. Конкурентность

Scheduler должен согласовываться с подтверждением и отменой Reservation.

## 22.6. PostgreSQL

Для выборки может использоваться:

`FOR UPDATE SKIP LOCKED`

## 22.7. SessionOutcome Timeout

Отдельная фоновая задача может завершать окно предоставления отчётов и разрешать ожидающие SessionOutcome по утверждённым правилам.

## 22.8. Важное различие

**Фоновое выполнение не означает eventual consistency внутри самой бизнес-операции.**

Scheduler может запускаться асинхронно относительно HTTP-запросов, но его собственные изменения должны оставаться атомарными.

## 23.1. Основной принцип

## 23.2. Booking

## 23.3. Schedule

## 23.8. Межмодульные операции

## 23.9. Event-driven взаимодействие

События используются для реакций на завершённые факты, а не для обхода границ модулей.

# 24. Обработка ошибок

## 24.1. Синхронные операции

Ошибка обязательного шага приводит к предусмотренной обработке транзакции.

## 24.2. Асинхронные операции

Ошибка асинхронного обработчика не должна оставлять критическое бизнес-состояние частично изменённым.

## 24.3. Логирование

Неожиданные ошибки обработчиков должны фиксироваться для диагностики.

## 24.4. Повторные попытки

Retry вводится при наличии конкретного сценария восстановления.

## 24.5. Идемпотентность

При повторной доставке событие не должно создавать недопустимые повторные изменения.

## 24.6. Dead-letter

Отдельная инфраструктура dead-letter processing может быть добавлена вместе с брокером или системой надёжной доставки.

Для базового MVP она не обязательна.

# 25. Тестирование

## 25.1. Транзакционная атомарность

Проверяются:

- Reservation + Occupancy;
- Reservation confirmation + Booking;
- Reservation expiration + Occupancy release;
- Booking cancellation + Occupancy release;
- administrative blocking + ACTIVE Reservation cancellation.

## 25.2. После COMMIT

Проверяется отсутствие успешного уведомления при ROLLBACK основной операции.

## 25.3. Асинхронные ошибки

Ошибка Notification не должна отменять уже зафиксированную бизнес-операцию.

## 25.4. Повторная обработка

Если реализован retry, проверяется идемпотентность обработчиков.

## 25.5. Scheduler

Проверяется конкурентная работа Expiration Scheduler и Confirmation.

## 25.6. Outcome

Проверяется фоновое разрешение результатов после завершения reporting window.

## 25.7. Outbox

Если выбран outbox, дополнительно проверяются:

- атомарная запись;
- обработка;
- повторная доставка;
- восстановление после сбоя;
- конкурентные обработчики.

## 25.8. Уровень проверки

Критические операции проверяются на PostgreSQL через интеграционные тесты.

# 26. Архитектурные правила

## EV-001. Synchronous Core

Критические изменения выполняются синхронно и транзакционно.

## EV-002. Async Side Effects

Асинхронность допускается для производных операций.

## EV-003. No AvailabilitySlot

Целевая модель не использует сохранённые AvailabilitySlot.

## EV-004. Occupancy Ownership

ScheduleOccupancy принадлежит Booking.

## EV-005. Transaction Commit

Событие завершённой бизнес-операции не обрабатывается как успешный факт до COMMIT.

## EV-006. No Guaranteed Delivery from AFTER_COMMIT

AFTER_COMMIT сам по себе не гарантирует доставку после аварийного завершения приложения.

## EV-007. Business Invariants First

События не заменяют проверки предметных инвариантов.

## EV-008. Module Ownership

Обработчики не обходят границы модулей.

## EV-009. No Mandatory Broker

Внешний брокер не обязателен для MVP.

## EV-010. Optional Outbox

Transactional outbox вводится при подтверждённой необходимости надёжной доставки.

## EV-011. Idempotent Consumers

Обработчики с повторной доставкой должны поддерживать безопасное повторное выполнение.

## EV-012. Separate Outcome

SessionOutcome не подменяется BookingStatus.

## EV-013. Independent Notifications

Ошибка доставки Notification не изменяет успешно зафиксированную Booking.

## EV-014. Background Transaction Safety

Фоновые бизнес-операции сохраняют транзакционную атомарность.

# 28. Итог

PsyWeb использует архитектуру:

**Synchronous Core + Optional Asynchronous Extensions**

Основные принципы:

- критические бизнес-операции выполняются синхронно;
- PostgreSQL обеспечивает транзакционную согласованность;
- Reservation и ScheduleOccupancy создаются атомарно;
- подтверждение Reservation создаёт Booking в одной транзакции;
- отмена и истечение освобождают Occupancy синхронно;
- административная потеря допуска атомарно отменяет ACTIVE Reservation;
- SessionOutcome определяет результат консультации независимо от BookingStatus;
- Notification и Analytics могут обрабатываться асинхронно;
- события завершённых операций обрабатываются после COMMIT;
- AFTER_COMMIT не обеспечивает гарантированную доставку;
- transactional outbox и message broker остаются необязательными архитектурными расширениями;
- фоновая обработка не отменяет требований транзакционной согласованности;
- события не нарушают границы владения бизнес-модулей.

**Статус: DRAFT — принципы определены, механизм событий и гарантии доставки уточняются при реализации.**
