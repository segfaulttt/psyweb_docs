
# 04. Процесс аутентификации (Authentication Flow)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Целевая модель:** Stateless JWT Authentication  
**Статус:** DRAFT — целевая архитектура аутентификации

---

# 1. Назначение документа

Документ описывает процесс аутентификации пользователей PsyWeb.

Аутентификация устанавливает личность пользователя, выполняющего запрос.

Она отвечает на вопрос:

**Кто обращается к системе?**

Авторизация отдельно определяет, какие операции разрешено выполнять этому пользователю.

PsyWeb разграничивает:

- аутентификацию;
- состояние учётной записи;
- роль пользователя;
- профессиональный допуск специалиста;
- разрешение специалисту принимать бронирования;
- права на конкретные ресурсы;
- предметные ограничения.

Успешная аутентификация не означает автоматического разрешения любых бизнес-операций.

# 2. Текущая и целевая реализация

## 2.1. Исходная реализация

В первоначальном backend уже предусмотрены:

- UserRole;
- UserStatus;
- нормализация email;
- поиск User по идентификатору;
- поиск User по email;
- поиск ACTIVE User;
- SpecialistStatus;
- проверка профессионального допуска специалиста.

В UserStatus используются:

```text
ACTIVE
BLOCKED
```

В существующем SpecialistStatus используются:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

## 2.2. Целевая инфраструктура

Для MVP предусмотрены:

- Authentication Controller;
- Authentication Service;
- BCrypt;
- JWT Service;
- JWT Authentication Filter;
- Spring Security Filter Chain;
- SecurityContext.

В исходной документации полноценная инфраструктура аутентификации ещё не была реализована.

Поэтому описанные ниже HTTP-операции относятся к целевой архитектуре.

## 2.3. Разделение

Наличие компонента в этом документе не означает, что он уже существует в актуальном PsyWeb/main.

Фактическое состояние реализации устанавливается по исходному коду.

# 3. Выбранная модель аутентификации

## 3.1. JWT

Для MVP используется JWT access token.

## 3.2. Stateless

Backend не хранит обычную серверную HTTP-сессию для каждого аутентифицированного пользователя.

## 3.3. Spring Security

Spring Security проверяет защищённые запросы и устанавливает контекст аутентифицированного пользователя.

## 3.4. Актуальное состояние

JWT устанавливает идентичность, но не заменяет актуальное состояние User в PostgreSQL.

## 3.5. Граница ответственности

Модули Booking, Schedule, Availability, Review и Outcome не реализуют собственные механизмы проверки пароля или JWT.

---

# 4. Основные компоненты

Целевая инфраструктура:

```text
Auth
│
├── Authentication Controller
├── Authentication Service
├── PasswordEncoder (BCrypt)
├── JWT Service
├── JWT Authentication Filter
├── Spring Security Configuration
└── SecurityContext Integration
```

## 4.1. Authentication Controller

Принимает запросы Login и возвращает предусмотренный API-контрактом результат.

## 4.2. Authentication Service

Координирует проверку учётных данных и выдачу JWT.

## 4.3. User Service

Предоставляет данные User через публичный контракт.

## 4.4. PasswordEncoder

Проверяет соответствие пароля сохранённому passwordHash.

## 4.5. JWT Service

Создаёт и проверяет JWT.

## 4.6. Security Filter

Обрабатывает JWT для защищённых запросов.

## 4.7. SecurityContext

Содержит аутентифицированную идентичность текущего пользователя.

# 5. Login Flow

## 5.1. Общая схема

```text
Client
    ↓
Login Request
    ↓
Authentication Controller
    ↓
Authentication Service
    ↓
User Lookup
    ↓
Password Verification
    ↓
Current UserStatus Check
    ↓
JWT Generation
    ↓
Login Response
```

## 5.2. Входные данные

Пользователь передаёт:

- email;
- password.

Точный endpoint и структура Request DTO определяются API-документацией.

## 5.3. Нормализация email

Перед поиском используется единая политика User Domain:

```text
trim
    ↓
lowercase(Locale.ROOT)
    ↓
validate
```

## 5.4. Единое правило

Authentication не должен реализовывать собственный алгоритм нормализации email, отличный от User.

## 5.5. Проверка credentials

Authentication Service проверяет переданный пароль по сохранённому passwordHash.

## 5.6. Состояние аккаунта

Успешный Login требует:

```text
Valid credentials
AND UserStatus.ACTIVE
```

## 5.7. Заблокированный аккаунт

При UserStatus.BLOCKED аутентификация запрещена.

## 5.8. Отсутствующий аккаунт

Если User не найден, Login отклоняется.

## 5.9. Ошибки

Ошибки Login не должны раскрывать чувствительные сведения или passwordHash.

---

# 6. SpecialistStatus и Login

## 6.1. Основной принцип

Модерационный статус специалиста не является состоянием аутентификации.

## 6.2. Возможность входа

ACTIVE пользователь с ролью SPECIALIST может аутентифицироваться при любом из состояний:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

## 6.3. Профессиональный допуск

Профессиональные полномочия требуют:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
```

## 6.4. Неодобренные специалисты

PENDING, REJECTED и SUSPENDED специалист может иметь ограниченный доступ к собственной учётной записи.

Например:

- просмотр профиля;
- просмотр статуса модерации;
- выполнение явно разрешённых действий.

## 6.5. Разделение

Успешный Login не означает, что специалист получил профессиональные полномочия.

---

# 7. SpecialistBookingAccess

## 7.1. Назначение

SpecialistBookingAccess представляет отдельное административное разрешение принимать новые бронирования.

## 7.2. Основное поле

`bookingAllowed`

## 7.3. Эффективный допуск

Для создания и подтверждения Reservation необходимо:

```text
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

При этом у связанного User должна быть роль SPECIALIST.

## 7.4. Независимость

bookingAllowed не заменяет UserStatus или approvalStatus.

## 7.5. Login

Значение bookingAllowed не влияет непосредственно на возможность аутентифицироваться в ACTIVE аккаунте.

## 7.6. Бизнес-операции

Проверка bookingAllowed выполняется соответствующими прикладными сервисами.

JWT Filter не должен самостоятельно реализовывать бизнес-политику бронирования.

---

# 8. JWT Generation

## 8.1. Создание

После успешной аутентификации backend выдаёт подписанный JWT access token.

## 8.2. Минимальные данные

Целевой JWT содержит:

- userId;
- role;
- expiration.

Также могут использоваться стандартные технические claims JWT.

## 8.3. Изменяемые состояния

Не следует считать авторитетными долгоживущие claims, отражающие:

- UserStatus;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

## 8.4. Причина

Перечисленные значения могут измениться после выдачи токена.

## 8.5. Подпись

Токен должен иметь проверяемую криптографическую подпись.

Конкретный алгоритм и механизм хранения ключей определяются Security-конфигурацией.

---

# 9. Protected Request Flow

## 9.1. Общая схема

```text
HTTP Request
    ↓
Bearer JWT
    ↓
Spring Security Filter Chain
    ↓
JWT Validation
    ↓
Extract userId / role
    ↓
Load Current User
    ↓
Require UserStatus.ACTIVE
    ↓
Authentication
    ↓
SecurityContext
    ↓
Authorization
    ↓
Controller
    ↓
Application Service
```

## 9.2. Проверка JWT

Security Layer проверяет:

- наличие токена там, где он требуется;
- подпись;
- срок действия;
- структуру;
- необходимые claims.

## 9.3. Недействительный JWT

Недействительный или просроченный токен не устанавливает аутентифицированную идентичность.

## 9.4. Текущий User

После проверки JWT система получает актуальное состояние User.

## 9.5. BLOCKED

Если UserStatus.BLOCKED, защищённый запрос отклоняется.

## 9.6. SecurityContext

После успешной проверки формируется Authentication.

## 9.7. Авторизация

Дальнейшие проверки определяются ролью, принадлежностью ресурса и предметными правилами.

---

# 10. JWT после административной блокировки

## 10.1. Проблема

Пользователь может получить JWT, после чего администратор заблокирует аккаунт.

## 10.2. Пример

```text
UserStatus.ACTIVE
    ↓
Successful Login
    ↓
JWT Issued
    ↓
Administrator Blocks User
    ↓
UserStatus.BLOCKED
    ↓
Request with Previously Issued JWT
    ↓
JWT Signature Valid
    ↓
Current UserStatus Checked
    ↓
Request Rejected
```

## 10.3. Основной принцип

Криптографическая действительность JWT не означает сохранение прежних полномочий.

## 10.4. MVP

Для MVP допустима дополнительная загрузка User из PostgreSQL при защищённом запросе.

## 10.5. Token blacklist

Отдельный blacklist токенов не является обязательным компонентом первоначальной архитектуры.

---

# 11. SecurityContext

## 11.1. Назначение

SecurityContext содержит сведения об аутентифицированном пользователе в рамках обработки запроса.

## 11.2. Использование

На его основании определяется идентичность пользователя, инициирующего операцию.

## 11.3. Примеры

- CLIENT подтверждает собственную Reservation;
- SPECIALIST изменяет собственное расписание;
- ADMIN выполняет модерацию;
- участник консультации предоставляет отчёт Outcome.

## 11.4. Доверенная идентичность

Сведения об инициаторе защищённой операции должны браться из аутентифицированного контекста.

## 11.5. Ограничение

Произвольный userId, переданный в JSON, не доказывает, что запрос выполняет соответствующий пользователь.

## 11.6. Домен

Domain Entities не должны напрямую зависеть от Spring SecurityContext.

---

# 12. Authentication и Authorization

## 12.1. Разграничение

Authentication определяет личность.

Authorization определяет разрешённые действия.

## 12.2. Этапы

```text
Authentication
    ↓
Current Account Status
    ↓
Role
    ↓
Resource Ownership / Participation
    ↓
Professional Eligibility
    ↓
Booking Eligibility if Required
    ↓
Domain-State Validation
```

## 12.3. Примеры

ACTIVE клиент не может подтвердить чужую Reservation.

APPROVED специалист с bookingAllowed = FALSE не может принимать новые Reservation.

ADMIN не может обходить предметные инварианты Booking.

## 12.4. Ответственность

Общая авторизация относится к Security Layer.

Предметная авторизация относится к Application Service и соответствующим доменным политикам.

## 12.5. Подробности

Полная модель определена в:

`05. Authorization Model.md`

---

# 13. Password Security

## 13.1. BCrypt

Для целевого MVP используется BCrypt.

## 13.2. Хранение

Пароль не сохраняется в открытом виде.

## 13.3. Password hash

User хранит passwordHash.

## 13.4. Проверка

Authentication Service использует настроенный PasswordEncoder.

## 13.5. Запреты

Нельзя:

- логировать исходный пароль;
- возвращать passwordHash через API;
- помещать пароль в JWT;
- включать пароль в доменные события.

---

# 14. JWT Expiration

## 14.1. Срок действия

JWT имеет ограниченное время действия.

## 14.2. Истечение

После expiration токен больше не принимается.

## 14.3. Повторный вход

Для MVP после истечения JWT пользователь проходит повторную аутентификацию.

## 14.4. Refresh token

Refresh-token инфраструктура не является обязательной частью первоначального MVP.

Возможность её добавления рассматривается отдельно.

---

# 15. Logout

## 15.1. Stateless

В модели JWT backend не хранит обычную серверную HTTP-сессию пользователя.

## 15.2. Действие клиента

При обычном Logout клиент удаляет сохранённый access token.

## 15.3. Ранее выданный токен

Удаление токена на одном устройстве само по себе не отзывает другие копии JWT.

## 15.4. Expiration

Ранее выданный токен остаётся криптографически действительным до expiration, если отдельный механизм revocation не реализован.

## 15.5. BLOCKED

Заблокированный User не может пользоваться защищёнными операциями даже при действительной подписи JWT.

---

# 16. Правила аутентификации

## AU-001. Valid Credentials

Успешная аутентификация требует корректных учётных данных.

## AU-002. Active User

Login требует:

`UserStatus.ACTIVE`

## AU-003. SpecialistStatus

Модерационный статус специалиста не определяет возможность Login.

## AU-004. Minimal JWT

JWT содержит необходимые стабильные данные идентичности и технические claims.

## AU-005. Current Account State

Защищённые запросы проверяют актуальный UserStatus.

## AU-006. Authentication vs Authorization

Успешная аутентификация не заменяет проверку прав на конкретную операцию.

## AU-007. BookingAccess

bookingAllowed не является состоянием аутентификации.

Его значение проверяется при соответствующих операциях бронирования.

## AU-008. Trusted Identity

Идентичность инициатора защищённого действия определяется через SecurityContext.

# 17. Обработка ошибок

## 17.1. Authentication Failure

Примеры:

- неправильные credentials;
- отсутствующий JWT;
- неправильная подпись;
- expired JWT.

## 17.2. Authorization Failure

Примеры:

- неправильная роль;
- отсутствие права на ресурс;
- недопустимое действие специалиста.

## 17.3. HTTP

Для неаутентифицированного запроса используется категория:

`401 Unauthorized`

Для аутентифицированного пользователя без необходимых полномочий:

`403 Forbidden`

## 17.4. Разделение

Не каждое нарушение бизнес-предусловия должно считаться ошибкой аутентификации или авторизации.

## 17.5. Единый формат

Security-ошибки должны по возможности использовать согласованный формат ErrorResponse.

# 19. Итог

Для PsyWeb выбрана stateless JWT authentication.

Основные правила:

- Authentication устанавливает идентичность пользователя;
- UserStatus определяет, разрешён ли доступ аккаунту;
- SpecialistStatus не определяет возможность Login;
- профессиональный допуск специалиста проверяется отдельно;
- BookingAccess представляет самостоятельное административное ограничение;
- JWT не является постоянным источником изменяемых полномочий;
- защищённые запросы проверяют актуальное состояние User;
- SecurityContext предоставляет доверенную идентичность;
- предметные операции выполняют собственные проверки авторизации;
- Refresh token и token blacklist не являются обязательными компонентами первоначального MVP.

**Статус: DRAFT — архитектурный процесс аутентификации согласован, реализация проверяется отдельно.**
