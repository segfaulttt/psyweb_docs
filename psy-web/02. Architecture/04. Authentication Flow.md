
# 04. Процесс аутентификации (Authentication Flow)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Целевая модель:** Stateless JWT Access Authentication + Stateful Refresh Sessions  
**Статус:** DRAFT — целевая архитектура согласована, реализация выполняется поэтапно

---

# 1. Назначение документа

Документ описывает целевую архитектуру аутентификации пользователей PsyWeb: вход в аккаунт, выдачу и проверку access tokens, обновление аутентификации, управление refresh-сессиями и завершение входа.

Аутентификация устанавливает личность пользователя, выполняющего запрос.

Она отвечает на вопрос:

**Кто обращается к системе?**

Авторизация отдельно определяет, какие операции разрешено выполнять этому пользователю.

PsyWeb разграничивает:

- аутентификацию;
- состояние учётной записи;
- роль пользователя;
- профессиональный допуск специалиста;
- разрешение специалисту принимать бронирования;
- права на конкретные ресурсы;
- предметные ограничения.

Успешная аутентификация не означает автоматического разрешения любых бизнес-операций.

# 2. Текущая и целевая реализация

## 2.1. Существующая предметная модель

В backend PsyWeb предусмотрены:

- UserRole;
- UserStatus;
- нормализация email;
- поиск User по идентификатору;
- поиск User по email;
- поиск ACTIVE User;
- SpecialistStatus;
- проверка профессионального допуска специалиста;
- регистрация пользователей с безопасным хранением паролей.

В UserStatus используются:

```text
ACTIVE
BLOCKED
```

В SpecialistStatus используются:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Для хеширования пользовательских паролей используется Argon2id.

## 2.2. Целевая инфраструктура

Для MVP предусмотрены:

- AuthController;
- AuthService;
- PasswordEncoder (Argon2id);
- JwtService;
- RefreshSessionService;
- RefreshSession и RefreshToken;
- Spring Security Filter Chain;
- JWT authentication;
- SecurityContext;
- CSRF protection для cookie-based операций;
- управление refresh-сессиями и их отзывом.

Аутентификация использует два разных механизма:

1. Короткоживущий JWT access token.
2. Долгоживущий opaque refresh token с серверным состоянием.

## 2.3. Разделение проектирования и реализации

Описанная в документе архитектура является целевой.

Наличие компонента в документации не означает, что он уже реализован в актуальной ветке `main`.

Фактическое состояние реализации определяется по исходному коду PsyWeb.

# 3. Выбранная модель аутентификации

## 3.1. Access token

Для доступа к защищённым REST API используется подписанный JWT access token.

Срок действия:

**15 минут.**

React хранит access token только в памяти приложения.

Access token не сохраняется в localStorage или sessionStorage.

## 3.2. Refresh token

Для продления аутентификации используется криптографически случайный opaque refresh token.

Он не является JWT.

Refresh token передаётся браузеру через HttpOnly cookie.

Сервер не хранит исходное значение токена в PostgreSQL, а сохраняет его криптографический хеш и связанные метаданные.

## 3.3. Refresh session

При успешном login создаётся отдельная refresh-сессия пользователя.

Срок жизни сессии:

**7 дней с момента входа.**

Срок абсолютный: успешная rotation не продлевает первоначальную дату завершения сессии.

Разные устройства имеют независимые refresh-сессии.

## 3.4. Stateless access authentication

Backend не использует обычные серверные HTTP-сессии для хранения состояния аутентифицированного пользователя.

Защищённые REST-запросы используют Bearer access JWT.

При этом refresh-сессии имеют собственное серверное состояние в PostgreSQL.

Следовательно, целевая архитектура сочетает:

- stateless access authentication;
- stateful refresh-token lifecycle.

## 3.5. Spring Security

Spring Security проверяет защищённые запросы и формирует Authentication в SecurityContext.

Для JWT предпочтительно использовать стандартные компоненты Spring Security, если они удовлетворяют требованиям PsyWeb.

Собственный JWT-filter не является обязательным архитектурным требованием.

## 3.6. Актуальное состояние аккаунта

JWT устанавливает идентичность пользователя, но не заменяет актуальное состояние User в PostgreSQL.

Для каждого защищённого запроса проверяется:

`UserStatus.ACTIVE`

Блокировка аккаунта запрещает выполнение новых защищённых операций даже при наличии ещё действующего JWT.

## 3.7. Граница ответственности

Модули Booking, Schedule, Availability, Review и Outcome не реализуют собственные механизмы проверки пароля, подписи JWT или refresh rotation.

Они используют доверенную аутентифицированную идентичность и собственные правила авторизации.

# 4. Основные компоненты

Целевая инфраструктура:

```text
Auth Module
│
├── AuthController
├── AuthService
├── JwtService
├── RefreshSessionService
├── RefreshSession
├── RefreshToken
├── RefreshSessionRepository
├── RefreshTokenRepository
└── Security Integration

User Module
│
├── UserService
├── User
└── PasswordEncoder (Argon2id integration)

Security Infrastructure
│
├── SecurityFilterChain
├── JWT Authentication
├── SecurityContext
├── AuthenticationEntryPoint
├── AccessDeniedHandler
└── CSRF Protection
```

Схема показывает логические обязанности, а не окончательное расположение каждого Java-класса.

## 4.1. AuthController

Принимает HTTP-запросы аутентификации.

Отвечает за:

- приём и валидацию DTO;
- передачу данных в AuthService;
- установку и очистку cookies;
- формирование HTTP-ответов.

Не реализует бизнес-логику refresh rotation.

## 4.2. AuthService

Координирует сценарии:

- login;
- refresh;
- logout;
- logout-all.

Обеспечивает согласованность выпуска токенов и взаимодействия с другими сервисами.

## 4.3. UserService

Предоставляет данные User через публичный контракт User module.

Auth module не должен обращаться напрямую к UserRepository.

User module владеет:

- данными пользователя;
- проверкой состояния аккаунта;
- правилами изменения UserStatus;
- согласованием операций аутентификации с административной блокировкой.

## 4.4. PasswordEncoder

Для проверки пользовательских паролей используется Argon2id.

Пароль сравнивается с сохранённым passwordHash через настроенный PasswordEncoder.

## 4.5. JwtService

Создаёт и криптографически проверяет JWT access tokens.

Не управляет refresh-сессиями и не реализует предметную авторизацию.

## 4.6. RefreshSessionService

Управляет жизненным циклом refresh-сессий:

- создание;
- rotation;
- определение повторного использования токенов;
- отзыв;
- отзыв всех сессий пользователя;
- сохранение истории токенов.

## 4.7. SecurityContext

Содержит доверенную идентичность аутентифицированного пользователя в рамках обработки запроса.

Domain Entities не должны зависеть от Spring SecurityContext.

# 5. Login Flow

## 5.1. Общая схема

```text
React Frontend
    ↓
POST /api/auth/login
    ↓
AuthController
    ↓
AuthService
    ↓
User Lookup
    ↓
Password Verification (Argon2id)
    ↓
Current UserStatus Check
    ↓
Access JWT Generation
    ↓
Refresh Session Creation
    ↓
Persist Refresh Token Hash
    ↓
Transaction Commit
    ↓
HTTP 200 + Access JWT
    +
Set-Cookie: Refresh Token
```

## 5.2. Входные данные

Пользователь передаёт:

- email;
- password.

Целевой endpoint:

`POST /api/auth/login`

## 5.3. Нормализация email

Перед поиском используется единая политика User Domain:

```text
trim
    ↓
lowercase(Locale.ROOT)
    ↓
validate
```

Auth module не должен реализовывать собственную политику нормализации email, отличную от User module.

## 5.4. Проверка credentials

AuthService проверяет переданный пароль по сохранённому Argon2id passwordHash.

Пароль не сохраняется и не включается в токены.

## 5.5. Состояние аккаунта

Успешный login требует:

```text
Valid credentials
AND UserStatus.ACTIVE
```

## 5.6. Заблокированный аккаунт

При UserStatus.BLOCKED вход запрещён.

Проверка состояния пользователя должна быть согласована с конкурентной административной блокировкой.

## 5.7. Отсутствующий аккаунт

Если User не найден, login отклоняется.

## 5.8. Успешный результат

При успешном входе:

- создаётся новая refresh-сессия;
- создаётся первая запись RefreshToken;
- исходный refresh token помещается в HttpOnly cookie;
- access JWT возвращается в JSON.

Refresh token не возвращается в JSON.

## 5.9. Ошибки

Неверный email, пароль и иные ошибки проверки credentials не должны раскрывать passwordHash или наличие конкретного аккаунта.

Для неуспешной аутентификации используется HTTP 401.

Необходимо предусмотреть ограничение частоты попыток login.

# 6. SpecialistStatus и Login

## 6.1. Основной принцип

Модерационный статус специалиста не является состоянием аутентификации.

## 6.2. Возможность входа

ACTIVE пользователь с ролью SPECIALIST может войти при любом из состояний:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

## 6.3. Профессиональный допуск

Профессиональные полномочия требуют:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
```

## 6.4. Неодобренные специалисты

PENDING, REJECTED и SUSPENDED специалист может иметь ограниченный доступ к своей учётной записи.

Например:

- просмотр профиля;
- просмотр статуса модерации;
- выполнение разрешённых действий.

## 6.5. Разделение

Успешный login не означает получение профессиональных полномочий.

SpecialistStatus не помещается в JWT как источник актуальных прав.

---

# 7. SpecialistBookingAccess

## 7.1. Назначение

SpecialistBookingAccess представляет отдельное административное разрешение принимать новые бронирования.

## 7.2. Основное поле

`bookingAllowed`

## 7.3. Эффективный допуск

Для создания и подтверждения Reservation требуется:

```text
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

Связанный User должен иметь роль SPECIALIST.

## 7.4. Независимость

bookingAllowed не заменяет UserStatus или approvalStatus.

## 7.5. Login

Значение bookingAllowed не влияет непосредственно на возможность входа в ACTIVE аккаунт.

## 7.6. Бизнес-операции

Проверка bookingAllowed выполняется соответствующими прикладными сервисами.

JWT authentication не должен реализовывать предметную политику бронирования.

---

# 8. JWT Generation

## 8.1. Создание

После успешной аутентификации backend выдаёт подписанный JWT access token.

## 8.2. Срок действия

Access JWT действует 15 минут.

## 8.3. Claims

Минимальные данные:

- `sub` — идентификатор пользователя;
- `role` — роль пользователя;
- `exp` — окончание срока действия.

Также используются стандартные технические claims, необходимые для проверки токена, включая:

- `iss`;
- `aud`;
- `iat`.

## 8.4. Изменяемые состояния

В JWT не помещаются:

- UserStatus;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

Эти значения могут измениться после выдачи токена.

## 8.5. Подпись

Токен должен иметь проверяемую криптографическую подпись.

Backend проверяет допустимый алгоритм подписи, issuer, audience и expiration.

Криптографические ключи загружаются из внешней конфигурации или системы управления секретами.

Реальные signing keys не хранятся в публичном Git-репозитории.

## 8.6. Содержимое JWT

JWT подписан, но не обязательно зашифрован.

В него запрещено включать:

- пароль;
- passwordHash;
- refresh token;
- секретные ключи;
- ненужные персональные данные.

# 9. Protected Request Flow

## 9.1. Общая схема

```text
HTTP Request
    ↓
Authorization: Bearer <access JWT>
    ↓
Spring Security Filter Chain
    ↓
JWT Validation
    ↓
Extract Identity
    ↓
Load Current User
    ↓
Require UserStatus.ACTIVE
    ↓
Authentication
    ↓
SecurityContext
    ↓
Authorization
    ↓
Controller
    ↓
Application Service
```

## 9.2. Проверка JWT

Security Layer проверяет:

- наличие токена для защищённого endpoint;
- подпись;
- разрешённый алгоритм;
- срок действия;
- issuer;
- audience;
- структуру;
- необходимые claims.

## 9.3. Недействительный JWT

Недействительный или просроченный JWT не устанавливает аутентифицированную идентичность.

## 9.4. Текущий User

После проверки JWT система загружает актуальное состояние пользователя.

Роль и статус для принятия решений должны согласовываться с доверенным текущим состоянием аккаунта.

## 9.5. BLOCKED

Если UserStatus.BLOCKED, защищённый запрос отклоняется.

## 9.6. SecurityContext

После успешной проверки создаётся Authentication.

## 9.7. Авторизация

Дальнейшие проверки определяются:

- ролью;
- принадлежностью ресурса;
- участием в операции;
- профессиональным допуском;
- предметными правилами.

## 9.8. RefreshSession

Обычный запрос с access JWT не требует поиска RefreshSession.

Мгновенный отзыв ранее выданных access tokens по состоянию refresh-сессии не входит в MVP.

# 10. JWT после административной блокировки

## 10.1. Проблема

Пользователь может получить access JWT, после чего администратор заблокирует аккаунт.

## 10.2. Пример

```text
UserStatus.ACTIVE
    ↓
Successful Login
    ↓
Access JWT Issued
    ↓
Administrator Blocks User
    ↓
UserStatus.BLOCKED
    ↓
Request with Previously Issued JWT
    ↓
JWT Signature Valid
    ↓
Current UserStatus Checked
    ↓
Request Rejected
```

## 10.3. Основной принцип

Криптографическая действительность JWT не означает сохранение прежних полномочий.

## 10.4. MVP

Для защищённых запросов используется актуальная проверка UserStatus в PostgreSQL.

Новые login и refresh после завершения блокировки не должны успешно выдавать доступ.

Уже выполнявшиеся запросы не обязаны прерываться посередине выполнения.

## 10.5. Token blacklist

Отдельный access-token blacklist не требуется для MVP.

Мгновенный отзыв access JWT при обычном logout или отзыве refresh-сессии относится к post-MVP.

# 11. Refresh Token Lifecycle

## 11.1. Создание сессии

При login создаётся RefreshSession и первый RefreshToken.

Сессия принадлежит конкретному пользователю.

## 11.2. Срок действия

RefreshSession действует 7 дней с момента login.

Срок не продлевается при обновлении токенов.

## 11.3. Rotation

При успешном refresh:

1. Проверяется предъявленный refresh token.
2. Проверяется состояние связанной сессии.
3. Проверяется актуальный UserStatus.
4. Предыдущий токен помечается использованным.
5. Создаётся новый refresh token.
6. Создаётся новый access JWT.
7. Изменения фиксируются транзакционно.
8. Браузеру выдаётся новая refresh cookie.

## 11.4. Одноразовость

В одной активной refresh-сессии одновременно допускается не более одного текущего неиспользованного refresh token.

История предыдущих поколений сохраняется.

## 11.5. Повторное использование

Если ранее использованный refresh token предъявляется повторно, система обнаруживает replay по сохранённому хешу и принадлежности к сессии.

При подтверждённом replay затронутая refresh-сессия отзывается.

Исходное значение токена не записывается в журналы событий.

## 11.6. Отсутствие grace period

Для MVP не предусматривается период, в течение которого использованный refresh token допускается повторно.

При сетевых сбоях или потере HTTP-ответа после успешной rotation может потребоваться повторный login.

## 11.7. История токенов

История всех поколений сохраняется на протяжении жизни сессии.

После завершения сессии история сохраняется ещё 24 часа для технической очистки и диагностики.

Затем записи удаляются фоновой задачей.

## 11.8. Несколько устройств

Каждый независимый вход на новом устройстве создаёт отдельную refresh-сессию.

Отзыв одной сессии не должен автоматически отзывать другие.

# 12. Concurrency и согласованность

## 12.1. Основной принцип

Обновление refresh token должно быть атомарным.

Нельзя допускать успешную выдачу двух актуальных refresh tokens одной сессии из-за конкурентных запросов.

## 12.2. Транзакции

Для управления RefreshSession и RefreshToken используются транзакции PostgreSQL.

При rotation состояние токена повторно проверяется после получения необходимых блокировок.

## 12.3. Порядок блокировок

Для операций, которым требуется блокировать несколько сущностей, применяется согласованный порядок:

```text
User
    ↓
RefreshSession
    ↓
RefreshToken
```

Это снижает риск взаимных блокировок.

## 12.4. Блокировка User

Проверка UserStatus при login и refresh согласовывается с административным изменением состояния аккаунта.

Auth module использует публичный контракт User module, а не обращается напрямую к UserRepository.

## 12.5. Replay и rollback

Отзыв refresh-сессии при обнаруженном replay должен быть сохранён в PostgreSQL до формирования HTTP-ответа об ошибке.

Нельзя допускать, чтобы RuntimeException автоматически откатывал уже выполненный отзыв.

## 12.6. Граница атомарности

PostgreSQL гарантирует транзакционную согласованность сохранённых данных.

Однако commit транзакции и доставка HTTP-ответа браузеру не являются одной атомарной операцией.

Этот сценарий учитывается в политике обработки неуспешного refresh.

# 13. Несколько вкладок браузера

## 13.1. Общая cookie

Вкладки одного браузерного профиля могут использовать одну refresh cookie.

При этом память JavaScript у каждой вкладки независимая.

## 13.2. Проблема

Несколько вкладок могут одновременно отправить refresh-запрос с одним и тем же токеном.

При строгой rotation это создаёт риск ложного обнаружения replay.

## 13.3. Выбранная стратегия

Используется вариант C:

- single-flight внутри одной вкладки;
- межвкладочная координация;
- атомарная серверная rotation.

## 13.4. Frontend-механизмы

Для координации рассматриваются:

- BroadcastChannel;
- Web Locks API;
- эквивалентные механизмы с корректным управлением конкурентными запросами.

## 13.5. Граница безопасности

Frontend-координация не является серверной гарантией безопасности.

Backend самостоятельно обеспечивает одноразовость токенов и атомарность rotation.

# 14. HTTP Authentication API

## 14.1. Login

```text
POST /api/auth/login
```

Входные данные:

- email;
- password.

При успехе:

- HTTP 200;
- access JWT в JSON;
- refresh token в HttpOnly cookie.

## 14.2. Refresh

```text
POST /api/auth/refresh
```

Не требует действующего access JWT.

Требует:

- действительного refresh token в cookie;
- успешной CSRF-проверки.

При успехе:

- HTTP 200;
- новый access JWT в JSON;
- новая refresh cookie.

## 14.3. Logout

```text
POST /api/auth/logout
```

Отзывает текущую refresh-сессию.

Не требует действующего access JWT, но использует refresh cookie для определения текущей сессии.

Применяются проверки Origin и CSRF.

При успехе:

- HTTP 204;
- очистка refresh cookie.

Повторное выполнение logout должно быть безопасным.

## 14.4. Logout All

```text
POST /api/auth/logout-all
```

Требует действующий access JWT.

Отзывает все refresh-сессии текущего пользователя.

Идентификатор пользователя определяется из аутентифицированного контекста.

При успехе:

- HTTP 204;
- очистка refresh cookie текущего браузера.

## 14.5. Current User

```text
GET /api/auth/me
```

Требует действующий access JWT.

Возвращает минимальный безопасный DTO текущего пользователя.

Не возвращает JPA-сущность, пароль или passwordHash.

## 14.6. Error Responses

Основные HTTP-коды:

- 200 — успешный login, refresh или получение текущего пользователя;
- 204 — успешный logout или logout-all;
- 400 — некорректные входные данные;
- 401 — отсутствие или недействительность аутентификации;
- 403 — отсутствие прав либо неуспешная CSRF-проверка.

Формат ошибок должен быть согласован с существующим GlobalExceptionHandler.

Ответы, содержащие токены, должны исключаться из кэширования, например через `Cache-Control: no-store`.

# 15. Browser Security

## 15.1. Production deployment

Целевая схема — same-origin размещение React frontend и REST API.

Например:

```text
https://psyweb.example/
https://psyweb.example/api/...
```

Это архитектурный пример, а не утверждённый production-домен.

## 15.2. Development

При локальной разработке используется Vite proxy.

React обращается к API по относительным маршрутам `/api/...`.

## 15.3. Access token storage

Access JWT хранится только в памяти React.

Не используется долговременное browser storage.

## 15.4. Refresh cookie

Для production предусматриваются:

- HttpOnly;
- Secure;
- SameSite=Strict;
- Path=/;
- отсутствие Domain;
- префикс `__Host-` при соблюдении его требований.

Точные dev/prod параметры должны быть проверены при конфигурации HTTPS и Spring Security.

## 15.5. CSRF

Для операций, использующих cookies, применяется CSRF-защита.

Целевой механизм — SPA-compatible интеграция Spring Security с CookieCsrfTokenRepository.

React передаёт CSRF-токен через заголовок:

`X-XSRF-TOKEN`

Для первоначального получения токена предусматривается:

```text
GET /api/auth/csrf
```

Также проверяется допустимый Origin изменяющих запросов.

Нельзя глобально отключать CSRF только из-за использования JWT.

## 15.6. CORS

Production-конфигурация не должна разрешать произвольные origins.

При same-origin взаимодействии frontend и API не нуждаются в открытом CORS для собственных запросов.

## 15.7. XSS

HttpOnly защищает значение refresh cookie от прямого чтения через JavaScript, но не устраняет все последствия XSS.

Необходимы безопасная обработка пользовательского содержимого, защита от внедрения скриптов и подходящая Content Security Policy.

## 15.8. Секреты

Запрещено включать в публичный репозиторий:

- реальные JWT signing keys;
- исходные refresh tokens;
- пароли;
- production secrets;
- заполненные секретами .env;
- дампы базы с персональными данными;
- журналы с authentication credentials.

Разрешены исходники, миграции, документация и шаблоны конфигурации с фиктивными значениями.

# 16. Password Security

## 16.1. Argon2id

Для хеширования пользовательских паролей используется Argon2id.

## 16.2. Хранение

Пароли не сохраняются в открытом виде.

User хранит passwordHash.

## 16.3. Проверка

AuthService использует настроенный PasswordEncoder через согласованный контракт.

## 16.4. Refresh Token Hashing

Для криптографически случайных refresh tokens используется SHA-256.

Argon2id не требуется для токенов, сгенерированных из достаточного количества криптографически случайных байтов.

Исходное значение refresh token в базе не хранится.

## 16.5. Запреты

Нельзя:

- логировать исходный пароль;
- возвращать passwordHash через API;
- помещать пароль в JWT;
- включать пароль в доменные события;
- логировать raw refresh tokens;
- хранить исходные refresh tokens в PostgreSQL.

# 17. SecurityContext

## 17.1. Назначение

SecurityContext содержит сведения об аутентифицированном пользователе в рамках обработки запроса.

## 17.2. Использование

На его основании определяется идентичность пользователя, инициирующего операцию.

## 17.3. Примеры

- CLIENT подтверждает собственную Reservation;
- SPECIALIST изменяет собственное расписание;
- ADMIN выполняет модерацию;
- участник консультации предоставляет отчёт Outcome.

## 17.4. Доверенная идентичность

Сведения об инициаторе защищённой операции берутся из аутентифицированного контекста.

## 17.5. Ограничение

Произвольный userId, переданный в JSON, не доказывает принадлежность запроса соответствующему пользователю.

## 17.6. Домен

Domain Entities не должны напрямую зависеть от Spring SecurityContext.

# 18. Authentication и Authorization

## 18.1. Разграничение

Authentication определяет личность.

Authorization определяет разрешённые действия.

## 18.2. Этапы

```text
Authentication
    ↓
Current Account Status
    ↓
Role
    ↓
Resource Ownership / Participation
    ↓
Professional Eligibility
    ↓
Booking Eligibility if Required
    ↓
Domain-State Validation
```

## 18.3. Примеры

ACTIVE клиент не может подтвердить чужую Reservation.

APPROVED специалист с bookingAllowed = FALSE не может принимать новые Reservation.

ADMIN не может обходить предметные инварианты Booking.

## 18.4. Ответственность

Общая авторизация относится к Security Layer.

Предметная авторизация относится к Application Service и соответствующим доменным политикам.

## 18.5. Подробности

Полная модель определена в:

`05. Authorization Model.md`

# 19. Правила аутентификации

## AU-001. Valid Credentials

Успешный login требует корректных учётных данных.

## AU-002. Active User

Login и refresh требуют:

`UserStatus.ACTIVE`

## AU-003. SpecialistStatus

Модерационный статус специалиста не определяет возможность login.

## AU-004. Minimal JWT

Access JWT содержит необходимые данные идентичности и технические claims.

## AU-005. Current Account State

Защищённые запросы проверяют актуальный UserStatus.

## AU-006. Authentication vs Authorization

Успешная аутентификация не заменяет проверку прав на конкретную операцию.

## AU-007. BookingAccess

bookingAllowed не является состоянием аутентификации.

Его значение проверяется при соответствующих операциях бронирования.

## AU-008. Trusted Identity

Идентичность инициатора защищённого действия определяется через SecurityContext.

## AU-009. Refresh Rotation

Успешный refresh инвалидирует предыдущий refresh token и создаёт новый.

## AU-010. Refresh Session Expiration

Refresh-сессия имеет абсолютный срок действия 7 дней.

## AU-011. Refresh Replay Detection

Повторное использование старого refresh token обнаруживается на основании сохранённой истории.

## AU-012. Session Revocation

Logout отзывает текущую refresh-сессию.

Logout-all отзывает все refresh-сессии пользователя.

## AU-013. Token Storage

Access JWT не сохраняется в browser persistent storage.

Исходный refresh token не сохраняется в PostgreSQL.

## AU-014. Browser Security

Cookie-based операции должны проходить предусмотренные CSRF и Origin проверки.

# 20. Обработка ошибок

## 20.1. Authentication Failure

Примеры:

- неправильные credentials;
- отсутствующий JWT;
- неправильная подпись;
- expired JWT;
- неизвестный refresh token;
- истёкшая или отозванная refresh-сессия;
- обнаруженный refresh-token replay.

## 20.2. Authorization Failure

Примеры:

- неправильная роль;
- отсутствие права на ресурс;
- недопустимое действие специалиста.

## 20.3. HTTP

Для неаутентифицированного запроса:

`401 Unauthorized`

Для аутентифицированного пользователя без необходимых полномочий:

`403 Forbidden`

Неуспешная CSRF-проверка также может приводить к HTTP 403.

## 20.4. Разделение

Не каждое нарушение бизнес-предусловия считается ошибкой аутентификации или авторизации.

## 20.5. Единый формат

Security-ошибки должны использовать согласованный формат ErrorResponse.

## 20.6. Безопасность ошибок

Ответы и логи не должны раскрывать:

- пароли;
- passwordHash;
- JWT signing keys;
- исходные refresh tokens;
- чувствительные внутренние сведения о сессиях.

# 22. Итог

Для PsyWeb выбрана комбинированная архитектура:

**Stateless JWT Access Authentication + Stateful Refresh Sessions.**

Основные правила:

- access JWT действует 15 минут;
- refresh-сессия действует 7 дней;
- access JWT хранится в памяти React;
- refresh token хранится в HttpOnly cookie;
- refresh tokens проходят строгую rotation;
- PostgreSQL хранит хеши и историю токенов;
- frontend координирует refresh между вкладками;
- backend самостоятельно обеспечивает атомарность rotation;
- logout отзывает текущую refresh-сессию;
- logout-all отзывает все refresh-сессии пользователя;
- UserStatus проверяется по актуальному состоянию;
- SpecialistStatus не определяет возможность login;
- профессиональный допуск и BookingAccess проверяются отдельно;
- SecurityContext предоставляет доверенную идентичность;
- cookie-based операции защищаются от CSRF;
- мгновенный отзыв access JWT при logout относится к post-MVP;
- реальные секреты не сохраняются в публичном Git-репозитории.

**Статус: DRAFT — целевая архитектура аутентификации согласована, реализация выполняется отдельно.**
