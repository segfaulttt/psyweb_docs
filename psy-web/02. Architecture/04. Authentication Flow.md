**System:** PsyWeb Backend  
**Target Auth Type:** JWT (Stateless Authentication)

---

# Overview

This document defines the architectural authentication flow of PsyWeb.

Authentication establishes the identity of the caller.

Authorization separately determines whether that authenticated caller may perform a particular operation.

The approved target model uses stateless JWT authentication, but the current `PsyWeb/main` does not yet contain the complete authentication/security infrastructure.

Therefore, this document explicitly separates:

- current domain/service capabilities;
- target authentication infrastructure.

---

# Current Implementation Status

The current backend already provides the domain state required by the future authentication flow:

- `UserRole.CLIENT / SPECIALIST / ADMIN`;
- `UserStatus.ACTIVE / BLOCKED`;
- User lookup by id;
- User lookup by normalized email;
- ACTIVE-only User lookup;
- canonical email normalization;
- `SpecialistStatus.PENDING / APPROVED / REJECTED / SUSPENDED`;
- professional Specialist eligibility.

The current backend does not yet implement the complete:

- `AuthController`;
- authentication service;
- BCrypt login flow;
- JWT generation;
- JWT authentication filter;
- authenticated HTTP principal;
- Spring Security authorization chain.

The remaining sections describe the approved target architecture.

---

# Key Target Components

The target authentication infrastructure contains:

- Authentication Controller;
- Authentication Service;
- User Service;
- Password Encoder using BCrypt;
- JWT Service;
- JWT Authentication Filter;
- Spring Security Filter Chain;
- SecurityContext.

Business modules must not implement their own authentication logic.

---

# 1. Login Flow

Target login flow:

```text
Client
→ Authentication Controller
→ Authentication Service
→ User lookup
→ password verification
→ current UserStatus validation
→ JWT generation
→ response
```

---

## Step 1: User submits credentials

The client provides:

- email;
- password.

The exact endpoint and DTO belong to the API/security implementation.

---

## Step 2: Email normalization and User lookup

Authentication uses the same canonical email policy as the User domain.

The currently implemented normalization rule is:

```text
trim
→ lowercase using Locale.ROOT
→ validate normalized email
```

The Authentication module must reuse this canonical rule rather than introduce separate normalization behavior.

The User service already supports lookup by normalized email.

---

## Step 3: Credential and account validation

The target authentication service:

- loads the User account;
- verifies the submitted password against the persisted password hash;
- requires `UserStatus.ACTIVE`.

Authentication must fail when:

- the account does not exist;
- the credentials are invalid;
- `UserStatus = BLOCKED`.

The current User state model contains only:

```text
ACTIVE
BLOCKED
```

There is no account-level `PENDING` state.

---

# 2. SpecialistStatus and Authentication

`SpecialistStatus` is not credential or account-authentication state.

An ACTIVE User with role SPECIALIST may authenticate when the linked Specialist is:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Professional access is evaluated separately.

The current professional eligibility rule is:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

Therefore:

- PENDING specialists may authenticate but are not professionally eligible;
- REJECTED specialists may authenticate but are not professionally eligible;
- SUSPENDED specialists may authenticate but are not professionally eligible;
- APPROVED specialists still require an ACTIVE User account.

This separation allows non-APPROVED specialists to retain explicitly permitted account/moderation access without granting professional capabilities.

---

# 3. JWT Generation

After successful target login, the backend generates a signed JWT access token.

The MVP token contains only stable identity data required for authentication and coarse authorization:

- `userId`;
- role;
- expiration.

Mutable domain state is not stored as an authoritative JWT claim.

In particular, the token does not persist:

- `UserStatus`;
- `SpecialistStatus`.

Both may change after token issuance.

---

# 4. Authenticated Request Flow

Target protected-request flow:

```text
Client
→ Bearer JWT
→ JWT Authentication Filter
→ validate signature and expiration
→ extract userId and role
→ load current User
→ require UserStatus.ACTIVE
→ establish SecurityContext
→ authorization
→ Controller
→ Service
```

---

## Current User Validation

JWT validity alone is not sufficient for protected access.

The security layer must check the current persisted User state on protected requests.

This prevents an old token from bypassing:

```text
UserStatus.ACTIVE → UserStatus.BLOCKED
```

Example:

```text
User logs in while ACTIVE
→ JWT is issued
→ administrator blocks User
→ JWT has not expired
→ next protected request reloads current User
→ BLOCKED is detected
→ access is denied
```

For MVP, this additional persistence lookup is accepted.

A JWT blacklist or distributed token-revocation store is not required.

---

# 5. SecurityContext

After successful token and current-account validation, the security layer creates the authenticated principal and stores it in Spring Security's `SecurityContext`.

The principal provides identity for downstream authorization.

The SecurityContext does not replace persisted business state.

Service/domain authorization may still require:

- current Specialist state;
- resource ownership;
- resource participation;
- current lifecycle state.

---

# 6. Transition to Authorization

Successful authentication does not automatically grant access to a business operation.

Authorization may additionally evaluate:

```text
UserRole
+
current UserStatus
+
SpecialistStatus
+
ownership / participation
+
business state
```

These concerns answer different questions:

```text
Authentication
→ Who is making the request?

UserStatus
→ Is the account currently enabled?

UserRole
→ What type of actor is this?

SpecialistStatus
→ Is the specialist professionally eligible?

Ownership / Participation
→ May this actor access this resource?

Business State
→ Is the requested operation valid now?
```

The detailed authorization contract is defined in `05. Authorization Model.md`.

---

# 7. Password Security

The target login implementation uses BCrypt.

Rules:

- raw passwords are never persisted;
- raw passwords must not be logged;
- only password hashes are stored;
- login compares the submitted password with the persisted hash through the configured password encoder.

The current User model already persists the value as `passwordHash`, but the complete BCrypt authentication flow is not yet implemented.

---

# 8. Token Expiration

JWT access tokens have a finite lifetime.

After expiration:

- the token is no longer accepted;
- the client must authenticate again unless a renewal mechanism is introduced later.

Refresh-token infrastructure is not required for the MVP.

---

# 9. Logout

The target authentication model is stateless.

Ordinary logout therefore consists of removing the access token on the client.

No authenticated server-side HTTP session must be destroyed.

An issued access token remains cryptographically valid until expiration unless explicit revocation infrastructure is introduced later.

Current-User validation still prevents a BLOCKED account from continuing to use an otherwise valid token for protected operations.

---

# 10. Authentication Rules

## AU-001 — Valid Credentials Required

Login requires valid credentials.

---

## AU-002 — Active Account Required

Successful login requires:

```text
UserStatus.ACTIVE
```

`UserStatus.BLOCKED` prevents authentication.

---

## AU-003 — SpecialistStatus Is Not Login State

For an ACTIVE SPECIALIST User, login does not require `SpecialistStatus.APPROVED`.

The following states may still authenticate:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Professional eligibility is evaluated separately.

---

## AU-004 — Minimal JWT Claims

The MVP JWT contains:

```text
userId
role
expiration
```

Mutable User and Specialist states remain authoritative in persistence.

---

## AU-005 — Current Account State Must Be Enforced

A previously issued JWT must not bypass a later transition:

```text
ACTIVE → BLOCKED
```

Protected requests therefore require the current persisted User to remain ACTIVE.

---

## AU-006 — Authentication Does Not Replace Authorization

A valid authenticated principal establishes identity only.

Access to specific operations remains subject to role, ownership, Specialist eligibility, and business-state rules.

# Notes

The architectural rule is intentionally strict:

```text
JWT identity
≠
current business eligibility
```

Authentication infrastructure must use the current domain state rather than duplicate mutable authorization state inside long-lived JWT claims.
