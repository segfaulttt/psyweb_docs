
**System:** PsyWeb Backend  
**Auth Type:** JWT (Stateless Authentication)

---

# Overview

This document describes how user authentication works in PsyWeb using JWT-based security.

Authentication determines the identity of the user making a request.

The system uses stateless authentication: authenticated requests do not rely on server-side HTTP sessions.

---

# Key Components

- Authentication Controller
- Authentication Service
- User Service
- Password Encoder (BCrypt)
- JWT Service
- JWT Authentication Filter
- Spring Security Filter Chain
- SecurityContext

---

# 1. Login Flow

## Step 1: User submits credentials

User sends request:

```text
POST /auth/login
```

Payload:
- email
- password

---

## Step 2: Authentication request reaches controller

Controller delegates to authentication service.

---

## Step 3: Credential and account validation

Authentication service:

- finds the User account by email
- verifies the submitted password against the stored BCrypt hash
- verifies that UserStatus is ACTIVE

Authentication fails if:

- the account does not exist
- the password is invalid
- UserStatus is BLOCKED

SpecialistStatus is not part of credential validation.

A specialist may have SpecialistStatus.PENDING or SpecialistStatus.REJECTED while the linked User account remains ACTIVE. Restrictions on specialist functionality are handled by authorization rules rather than by authentication.

---

## Step 4: JWT generation

If authentication succeeds, the system generates a signed JWT.

The token contains the minimum identity and authorization information required for authenticated requests:

- userId
- role
- expiration time

SpecialistStatus is not stored in the JWT.

UserStatus should not be treated as a long-lived authorization source inside the token because account state may change after the token has been issued.

---

## Step 5: Token returned to client

Response:

```json
{
  "token": "jwt.token.here"
}
```

---

# 2. Authenticated Request Flow

## Step 6: Client sends request with token

```text
Authorization: Bearer <JWT>
```

---

## Step 7: JWT Filter intercepts request

For protected requests, the JWT authentication filter:

- extracts the Bearer token
- validates the token signature
- verifies token expiration
- extracts the authenticated user identity and role

If the token is missing, invalid, or expired where authentication is required:

→ request is rejected with 401 Unauthorized

---

## Step 8: SecurityContext setup

If the token is valid, the security layer creates an Authentication object representing the authenticated principal.

The Authentication object is stored in the SecurityContext for the current request.

The authenticated principal provides the identity required by downstream authorization and business operations.

---

# 3. Transition to Authorization

Successful authentication establishes the identity of the caller but does not automatically grant access to a protected operation.

After authentication, authorization rules may evaluate:

- UserRole
- current UserStatus
- SpecialistStatus, when applicable
- resource ownership or participation
- business state

Authorization rules are defined in `05. Authorization Model.md`.

If authentication succeeds but access is denied:

→ 403 Forbidden

---

# 4. Password Security

## Password Storage

- passwords are never stored in plain text
- only BCrypt password hashes are persisted
- raw passwords must not be logged or stored

---

## Password Verification

During authentication:

raw password + stored BCrypt hash
→ BCrypt verification
→ match / no match

---

# 5. Token Structure

The JWT contains only the claims required for authentication and coarse-grained authorization.

Current token claims:

- subject / userId
- role
- expiration time

The token is cryptographically signed by the backend.

SpecialistStatus is not stored in the token.

Mutable business state should not be duplicated in JWT claims unless the consequences of stale token data are explicitly handled.

---

# 6. Token Expiration

JWT access tokens have a limited lifetime.

When an access token expires:

- it is no longer accepted for authenticated requests
- protected requests using that token receive 401 Unauthorized
- the user must authenticate again unless a separate token renewal mechanism is introduced later

The MVP does not require a refresh-token mechanism unless product requirements introduce one.

---

# 7. Logout Flow

With stateless JWT authentication, the MVP does not maintain a server-side session that must be destroyed during ordinary logout.

For standard logout:

- the client removes its access token
- subsequent requests without a valid token are unauthenticated

A previously issued JWT remains cryptographically valid until it expires unless a server-side token revocation mechanism is introduced.

Token revocation is not part of the initial MVP design.

---

# 8. Authentication Rules

## AU-001 — Valid Credentials Required

Authentication requires a valid account identifier and matching password.

---

## AU-002 — Active Account Required

Only users with UserStatus.ACTIVE may authenticate successfully.

UserStatus.BLOCKED prevents successful authentication.

---

## AU-003 — Specialist Approval Is Not Authentication State

SpecialistStatus does not determine whether credentials are valid.

PENDING and REJECTED specialists may authenticate if their User account is ACTIVE, but specialist-specific functionality remains restricted by authorization rules.

---

## AU-004 — JWT Validation Required

A JWT used for a protected request must have a valid signature and must not be expired.

---

## AU-005 — Authentication Does Not Replace Authorization

A valid JWT establishes caller identity.

Access to a specific operation is determined separately by the authorization model.

---

## AU-006 — Mutable Account State Must Be Enforced

A previously issued JWT must not permanently bypass a later UserStatus change.

If an account becomes BLOCKED, protected business operations must no longer be allowed solely because the caller possesses an otherwise valid unexpired JWT.

The concrete enforcement strategy is part of the security implementation design.

---

# 9. Example Full Flow

## Login

1. Client sends POST /auth/login
2. Authentication service loads the User account by email
3. Submitted password is verified against the stored BCrypt hash
4. UserStatus.ACTIVE is verified
5. JWT is generated
6. Token is returned to the client

## Protected Request

1. Client sends a request with the Bearer token
2. JWT authentication filter validates the token
3. Authenticated principal is created
4. SecurityContext is populated for the request
5. Authorization rules are evaluated
6. Controller delegates the operation to the service layer
7. Business rules are evaluated
8. Response is returned

---

# Notes

## Authentication vs Authorization

Authentication and authorization are separate concerns.

Authentication answers:

> Who is making the request?

Authorization answers:

> Is this authenticated user allowed to perform this operation?

Specialist approval is an authorization concern, not a credential-validation concern.

---

## Stateless Design

The backend does not maintain authenticated HTTP sessions for JWT-based requests.

Stateless authentication simplifies horizontal scaling but means that token expiration and mutable account state must be handled explicitly.

---

## Security Layer Position

JWT authentication occurs before protected controller execution through the Spring Security filter chain.

Authorization may be enforced through Spring Security and service-level business rules according to `05. Authorization Model.md`.
