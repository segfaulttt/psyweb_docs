
**System:** Spring Boot Modular Monolith

# Overview

This document describes how an HTTP request is processed inside PsyWeb — from the HTTP entry point through security, application and domain processing, persistence, and back to the client.

The exact path may vary depending on the use case. A business operation may coordinate multiple modules and repositories within a single transaction.

---

# High-Level Flow

Typical request processing:

Client
→ Spring Security Filter Chain
→ Controller
→ Service
→ Domain / Repository
→ PostgreSQL
→ Response

For cross-module business operations, a service may coordinate other module services:

Controller
→ Orchestrating Service
   ├── Module Service
   ├── Module Service
   └── Repository
→ PostgreSQL
→ Response

---

# 1. Request Entry Point

## Step 1: Client Request

A client sends an HTTP request:

- REST API call (e.g. booking, login, search)
- JSON payload (if applicable)

---

## Step 2: Spring Security Filter Chain

Before a protected request reaches the controller, it passes through the Spring Security filter chain.

For JWT-authenticated requests, the security layer:

- extracts the Bearer token
- validates the token
- establishes the authenticated principal
- populates the SecurityContext for the request

If valid authentication is required but cannot be established:

→ request is rejected with 401 Unauthorized

Authorization rules may additionally reject an authenticated request with 403 Forbidden.

Public endpoints may pass through the security chain without requiring authentication.

---

# 2. Controller Layer

## Step 3: REST Controller

Controller responsibilities:

- map HTTP requests to application operations
- deserialize and validate request DTOs
- obtain authenticated caller information when required
- delegate business operations to the service layer
- map results to API responses

### Important Rule

Controllers contain **no business logic**.

Controller-level validation covers request structure and basic input constraints.

Business validation belongs to the service and domain layers.

---

# 3. Service Layer

## Step 4: Business Processing

The service layer executes application use cases and coordinates business operations.

Responsibilities may include:

- enforcing business rules that span multiple entities or modules
- loading required domain state
- invoking domain behavior
- coordinating other module services through their public boundaries
- managing transaction boundaries
- persisting state through repositories owned by the module
- enforcing ownership and business-level authorization where required

Examples:

- creating a temporary reservation for an available slot
- confirming a reservation and creating a booking
- validating client ownership
- validating specialist eligibility
- cancelling a booking and coordinating the corresponding availability state transition

## Transaction Boundary

Business operations that modify related persistent state must use an appropriate transaction boundary.

Typical transactional operations include:

- creating a reservation and holding its slot
- confirming a reservation and creating a booking
- cancelling or expiring a reservation and releasing its slot
- cancelling a booking and applying the corresponding availability state transition
- creating or modifying availability

A transaction must include all state changes that form one consistency-sensitive business operation.

For example, booking confirmation must not persist only part of:

- Reservation state transition
- AvailabilitySlot state transition
- Booking creation

If the operation fails, partial persistent state must not remain committed.

---

# 4. Repository Layer

## Step 5: Data Access

Repositories provide persistence access for entities owned by their module.

Responsibilities:

- entity retrieval
- persistence operations
- database queries
- persistence-specific lookup operations

Technology:

- Spring Data JPA

Rules:

- repositories contain no business orchestration
- a module must not directly access repositories owned by another module
- cross-module operations must use the owning module's service-level boundary

---

# 5. Database Layer

## Step 6: PostgreSQL Execution

PostgreSQL is the persistent source of truth for critical data integrity.

The database participates in consistency enforcement through:

- primary and foreign keys
- unique constraints
- check constraints
- indexes
- transaction isolation and locking where required

Application-level checks express business intent and provide meaningful errors, while database-level guarantees protect critical invariants against concurrent requests.

---

# 6. Response Flow

## Step 7: Service → Controller → Client

After successful execution:

1. Service completes the business operation
2. Transaction commits when applicable
3. Controller maps the result to an API response model
4. Response is serialized
5. Client receives the HTTP response

Domain entities should not be exposed as the external API contract by default.

---

# Error Handling Flow

Application errors should be translated into consistent HTTP responses through centralized exception handling.

The intended API error-handling mechanism is Spring `@ControllerAdvice`.

Different failure categories should remain distinguishable.

Examples:

- authentication failure → 401 Unauthorized
- authorization failure → 403 Forbidden
- requested resource not found → 404 Not Found
- invalid request data → 400 Bad Request
- business conflict or invalid resource state → appropriate client error response

Domain and service layers should not depend on HTTP-specific status codes.

---

# Authentication and Authorization Inside Lifecycle

For a protected request:

1. JWT is extracted from the Authorization header
2. Token validity is verified
3. Authenticated principal is established
4. SecurityContext is populated for the request
5. Coarse-grained authorization rules are evaluated
6. Controller delegates the operation to the service layer
7. Service-level authorization and business rules are evaluated when domain data is required

Loading the current User entity from the database is not necessarily part of JWT authentication itself.

A service may load current account or domain state when required to enforce mutable authorization rules such as UserStatus, SpecialistStatus, or ownership.

# Booking Lifecycle Examples

The booking process contains a temporary Reservation stage before a confirmed Booking exists.

---

## Example 1: Create Reservation

A CLIENT selects an available specialist time slot.

Typical flow:

1. Request passes authentication and authorization
2. Controller delegates reservation creation to Booking module
3. Booking service validates the client
4. Availability module verifies that the slot can be reserved
5. Reservation is created with ACTIVE status and an expiration time
6. AvailabilitySlot transitions from FREE to RESERVED
7. Reservation and slot changes are committed atomically
8. Reservation information is returned to the client

The database must prevent concurrent requests from creating conflicting active reservations for the same slot.

### Reservation Booking Deadline

A FREE AvailabilitySlot is not necessarily bookable.

A specialist defines a default minimum booking notice. A specific AvailabilitySlot may optionally override this value.

The effective minimum booking notice is:

- the AvailabilitySlot override, when present;
- otherwise, the Specialist default.

The booking deadline is calculated as:

`bookingDeadline = slot.startTime - effectiveMinimumBookingNotice`

A new Reservation may be created only before the booking deadline.

If the effective minimum booking notice is zero, the booking deadline is equal to the slot start time.

An ACTIVE Reservation created before the booking deadline may still be confirmed after the deadline while the Reservation remains ACTIVE and has not reached its own `expiresAt`.

The booking deadline affects whether a new Reservation may be created. It does not introduce an additional AvailabilitySlot status.

---

## Example 2: Confirm Reservation

A CLIENT confirms their existing reservation before it expires.

Typical flow:

1. Request passes authentication and authorization
2. Reservation is loaded
3. Ownership is verified
4. Reservation must still be ACTIVE and unexpired
5. Client eligibility is verified
6. Specialist eligibility is verified
7. Reservation transitions to CONFIRMED
8. AvailabilitySlot transitions from RESERVED to BOOKED
9. Booking is created with CONFIRMED status
10. All related changes commit atomically
11. Booking information is returned to the client

If confirmation fails, the system must not persist a partial confirmation state.

---

## Example 3: Reservation Cancellation or Expiration

An ACTIVE reservation may stop holding a slot because it is cancelled or expires.

Typical flow:

1. Reservation is identified
2. Cancellation or expiration conditions are validated
3. Reservation transitions to CANCELLED or EXPIRED
4. AvailabilitySlot is released back to FREE
5. Both state changes commit atomically

After the slot is released, it returns to FREE.

Whether another Reservation may be created for the slot is determined independently by its booking deadline.

When a client cancels a confirmed Booking, the Booking occupancy is released and the AvailabilitySlot returns from BOOKED to FREE.

Whether the FREE slot can receive a new Reservation is determined independently by its booking deadline.

Therefore, a slot may be FREE but no longer bookable.

---

---

## Example 4: Post-Session Outcome

After a confirmed consultation has reached its scheduled session time, both participants independently report whether the session occurred.

The outcome reporting process is separate from the normal Booking cancellation flow.

Typical flow:

1. CLIENT reports the session outcome
2. SPECIALIST reports the session outcome
3. Each participant reports either:
   - OCCURRED
   - DID_NOT_OCCUR
4. If a participant reports DID_NOT_OCCUR, a structured reason is required
5. The reason must distinguish at least:
   - client no-show
   - specialist no-show
   - technical problem
   - other
6. If OTHER is selected, a free-text explanation is required
7. Compatible reports may be resolved automatically
8. If both participants report OCCURRED:
   - Booking transitions to COMPLETED
9. If both participants report compatible DID_NOT_OCCUR outcomes:
   - the Booking is resolved as non-completed according to the reported outcome
10. If the reports conflict:
    - the Booking enters a dispute case
    - an administrator resolves the conflict
11. A normal Booking cancellation must not be duplicated through post-session outcome reporting

The post-session outcome process does not replace the ordinary cancellation flow.

A Booking that was correctly cancelled through the normal cancellation workflow is not treated as an unresolved post-session outcome case.

---

---

## Post-Session Outcome Resolution

The system stores the outcome reported by each participant independently.

The two reports are evaluated together:

| Client report | Specialist report | Result |
|---------------|-------------------|--------|
| OCCURRED | OCCURRED | Booking COMPLETED |
| DID_NOT_OCCUR | DID_NOT_OCCUR | Automatically resolved when the reasons are compatible |
| OCCURRED | DID_NOT_OCCUR | Dispute case |
| DID_NOT_OCCUR | OCCURRED | Dispute case |

A DID_NOT_OCCUR report requires a structured reason.

Minimum reason categories:

- CLIENT_NO_SHOW
- SPECIALIST_NO_SHOW
- TECHNICAL_PROBLEM
- OTHER

OTHER requires a free-text explanation.

Conflicting reports are not automatically converted into a final Booking outcome. They require administrative resolution.

The administrator is involved only when the participants' reports cannot be resolved automatically.

# Key Principles

## 1. Separation of Concerns

- Controller → HTTP/API concerns
- Service → use-case orchestration and transaction boundaries
- Domain → entity state and domain invariants
- Repository → persistence access
- Database → persistent integrity guarantees

Cross-module state changes must respect module ownership.

---

## 2. Post-Session Outcome Resolution

Post-session outcome reporting is part of the Booking lifecycle.

The system does not require an administrator for every session outcome.

CLIENT and SPECIALIST report the outcome independently. Compatible reports are resolved automatically, while conflicting reports become an administrative dispute.

This keeps the normal case automatic while preserving an explicit resolution path for conflicting claims.

---

## 3. Stateless Authentication

- authenticated requests do not rely on server-side HTTP sessions
- JWT is used to establish caller identity
- mutable authorization state is handled separately from token identity

See `04. Authentication Flow.md` and `05. Authorization Model.md` for detailed security rules.

---

## 4. Transaction Safety

- consistency-sensitive operations are atomic
- related state transitions belong to the same transaction where strong consistency is required
- failures must not leave partially persisted business state
- transaction behavior must be verified with integration tests where rollback and database constraints are significant

---

## 5. Persistent Consistency

- PostgreSQL is authoritative for persisted state
- application logic expresses and coordinates business rules
- database constraints protect critical persistent invariants
- concurrency-sensitive correctness must not rely solely on pre-check queries

---

## 6. Module Ownership

Each module owns the lifecycle of its domain entities.

Examples:

- User module owns User
- Specialist module owns Specialist
- Availability module owns AvailabilitySlot
- Booking module owns Reservation and Booking

A module may coordinate another module through its service boundary but must not directly modify the other module's entities or repositories.

---

# Future Extensions

The request lifecycle may evolve when concrete requirements justify additional infrastructure.

Possible extensions include:

- asynchronous processing for non-critical side effects such as notifications
- caching where measured performance requirements justify it
- dedicated real-time communication infrastructure for chat

Core consistency-sensitive operations such as reservation, booking, and availability state transitions should remain explicitly coordinated even if surrounding infrastructure evolves.
