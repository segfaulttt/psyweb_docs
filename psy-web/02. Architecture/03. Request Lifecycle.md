
# 03. Жизненный цикл запроса (Request Lifecycle)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — целевая архитектура обработки запросов

---

# 1. Назначение документа

Документ описывает обработку HTTP-запросов в PsyWeb: от получения запроса клиентского приложения до выполнения бизнес-операции, обращения к PostgreSQL и формирования ответа.

Рассматриваются:

- входящий HTTP-запрос;
- аутентификация через Spring Security;
- авторизация;
- Controller;
- Application Service;
- доменные правила;
- Repository;
- PostgreSQL;
- формирование ответа;
- обработка ошибок;
- основные бизнес-сценарии.

Подробный порядок PostgreSQL-блокировок, транзакционных операций и внутренних сервисных вызовов описывается отдельно:

`04. Backend/03. Request Lifecycle.md`

Этот документ фиксирует архитектурную последовательность и распределение ответственности.

# 2. Текущая и целевая реализация

## 2.1. Существующий backend

В первоначальной реализации PsyWeb уже существуют:

- сервисный слой;
- доменные сущности;
- Spring Data JPA;
- PostgreSQL;
- отдельные бизнес-транзакции;
- Reservation;
- Booking;
- обработка истечения Reservation;
- доменные исключения.

Первоначальные операции бронирования используют AvailabilitySlot.

Эта модель заменяется новой целевой архитектурой.

## 2.2. Целевая HTTP-инфраструктура

Для MVP предусмотрены:

- Spring Security;
- JWT;
- REST Controller;
- Request DTO;
- Response DTO;
- централизованная обработка ошибок.

В исходной документации эти компоненты отмечены как частично или полностью не реализованные.

Поэтому описанный далее HTTP-процесс является целевой архитектурой.

Его наличие в документации не означает, что он уже полностью существует в PsyWeb/main.

# 3. Высокоуровневая схема

## 3.1. Обычный запрос

```text
Client
    ↓
HTTP Request
    ↓
Spring Security Filter Chain
    ↓
Controller
    ↓
Application Service
    ↓
Domain / Repository
    ↓
PostgreSQL
    ↓
Application Result
    ↓
Response DTO
    ↓
HTTP Response
```

## 3.2. Межмодульная операция

```text
Controller
    ↓
Orchestrating Application Service
    ├── Module Query
    ├── Module Command
    ├── Domain Policy
    └── Owning Repository
             ↓
         PostgreSQL
    ↓
Response
```

Прикладной сценарий может координировать несколько модулей в одной транзакции.

Это не даёт одному модулю права напрямую изменять чужие Repository.

# 4. HTTP Request

## 4.1. Вход

Клиентское приложение отправляет REST-запрос.

Запрос может содержать:

- HTTP method;
- URL;
- query parameters;
- JSON body;
- Authorization header.

## 4.2. Примеры операций

- Login;
- получение специалистов;
- получение ServiceOffering;
- просмотр Availability;
- создание Reservation;
- подтверждение Reservation;
- отмена Booking;
- редактирование Schedule;
- отправка SessionOutcomeReport;
- создание Review.

## 4.3. Контракты

Точные endpoint, HTTP methods и DTO определяются API-документацией.

Архитектурный документ не фиксирует их преждевременно.

---

# 5. Spring Security Filter Chain

## 5.1. Назначение

Защищённый HTTP-запрос проходит через Spring Security до передачи в Controller.

## 5.2. JWT

Целевой процесс:

```text
Bearer JWT
    ↓
Token validation
    ↓
Extract userId / role
    ↓
Load current User
    ↓
Require UserStatus.ACTIVE
    ↓
Create Authentication
    ↓
SecurityContext
```

## 5.3. Актуальное состояние аккаунта

JWT не должен использоваться как постоянный источник сведений об изменяемых статусах пользователя.

Если после выдачи токена UserStatus изменился на BLOCKED, дальнейшие защищённые операции должны отклоняться.

## 5.4. Роли

В системе предусмотрены:

- CLIENT;
- SPECIALIST;
- ADMIN.

## 5.5. Специалист

Специалист с ACTIVE аккаунтом может пройти аутентификацию независимо от модерационного статуса.

Профессиональные полномочия проверяются отдельно.

## 5.6. Граница ответственности

Security Filter Chain не должен вычислять Availability или изменять Reservation.

Эти функции принадлежат соответствующим бизнес-модулям.

---

# 6. Авторизация

## 6.1. Общие проверки

Spring Security определяет, может ли пользователь обращаться к защищённой операции с учётом роли и состояния аккаунта.

## 6.2. Проверки ресурса

Прикладной сервис дополнительно проверяет:

- принадлежность;
- участие;
- профессиональный допуск;
- специальные административные разрешения.

## 6.3. Пример

Клиент с ролью CLIENT может иметь право вызвать подтверждение Reservation.

Но это не даёт ему права подтверждать Reservation другого клиента.

## 6.4. Допуск специалиста

Для новых Reservation и их подтверждения требуется:

```text
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

## 6.5. Конкурентные изменения

Проверки изменяемого допуска должны быть согласованы с административной блокировкой.

Подробный протокол находится в Transaction and Concurrency Model.

---

# 7. Controller Layer

## 7.1. Назначение

Controller принимает HTTP-запрос и делегирует выполнение Application Service.

## 7.2. Обязанности

- mapping endpoint;
- десериализация;
- Bean Validation;
- получение идентичности вызывающего пользователя;
- вызов Application Service;
- формирование Response DTO.

## 7.3. Запрет бизнес-логики

Controller не должен:

- создавать Reservation Entity;
- изменять BookingStatus;
- вычислять Calendar Occupancy;
- получать PostgreSQL advisory locks;
- управлять бизнес-транзакциями;
- разрешать SessionOutcome.

## 7.4. DTO

JPA-сущности не должны возвращаться напрямую через REST API.

---

# 8. Application Service Layer

## 8.1. Назначение

Application Service выполняет пользовательский сценарий.

## 8.2. Ответственность

- координация модулей;
- проверки прав;
- загрузка необходимых данных;
- применение доменных правил;
- определение транзакционной границы;
- изменение состояния;
- формирование результата.

## 8.3. Примеры

- ReservationApplicationService;
- SchedulingApplicationService;
- AdministrativeBlockingService;
- сервисы Booking;
- сервисы Outcome.

## 8.4. Межмодульное взаимодействие

Модули взаимодействуют через публичные контракты.

## 8.5. Транзакции

Изменения, составляющие одну атомарную бизнес-операцию, выполняются в одной транзакции PostgreSQL.

---

# 9. Domain Layer

## 9.1. Назначение

Domain содержит предметные сущности и правила.

## 9.2. Примеры

Reservation определяет допустимые переходы собственного состояния.

Booking определяет допустимые переходы подтверждённой записи.

AvailabilityPolicy определяет правила допустимого размещения консультации.

OutcomeResolutionPolicy определяет условия разрешения результата консультации.

## 9.3. Разделение ответственности

Application Service определяет порядок выполнения сценария.

Domain определяет допустимость отдельных предметных действий.

---

# 10. Repository Layer

## 10.1. Назначение

Repository предоставляет доступ к данным PostgreSQL.

## 10.2. Технология

Spring Data JPA / Hibernate.

## 10.3. Обязанности

- получение сущностей;
- сохранение;
- удаление;
- специализированные запросы;
- необходимые операции блокировки.

## 10.4. Владение

Repository принадлежит соответствующему модулю.

## 10.5. Ограничение

Модуль не должен напрямую изменять данные другого модуля через его Repository в обход публичного контракта.

---

# 11. PostgreSQL

## 11.1. Источник истины

PostgreSQL обеспечивает постоянное хранение бизнес-состояния.

## 11.2. Ограничения

Используются:

- PRIMARY KEY;
- FOREIGN KEY;
- UNIQUE;
- CHECK;
- exclusion constraints.

## 11.3. Транзакции

Критические изменения выполняются атомарно.

## 11.4. Конкурентность

Для согласования операций применяются:

- row locks;
- transaction-level advisory locks;
- ограничения PostgreSQL.

## 11.5. Согласованность

Предварительная проверка в приложении не заменяет database constraints.

---

# 12. Формирование ответа

## 12.1. Успешная операция

После выполнения бизнес-сценария результат передаётся в API-слой.

## 12.2. DTO

Формируется безопасный Response DTO.

## 12.3. Транзакция

Если операция изменяет согласованное состояние, необходимые изменения должны быть зафиксированы до представления результата как успешно выполненного.

## 12.4. Сериализация

Response DTO преобразуется в JSON.

## 12.5. Результат

Клиент получает HTTP Response.

---

# 13. Обработка ошибок

## 13.1. Общая стратегия

Ошибки преобразуются в согласованные HTTP-ответы.

## 13.2. Доменные исключения

В существующей реализации используется:

```text
DomainException
    ↑ implements
BaseDomainException
    |
    ├── ValidationException
    ├── NotFoundException
    ├── ConflictException
    ├── ForbiddenException
    ├── InvalidStateException
    └── ExpiredException
```

## 13.3. REST

Целевой HTTP-обработчик использует @RestControllerAdvice.

## 13.4. Категории ошибок

- 400 — некорректный запрос;
- 401 — отсутствие корректной аутентификации;
- 403 — недостаточные полномочия;
- 404 — ресурс не найден;
- 409 — бизнес-конфликт;
- 500 — неожиданная системная ошибка.

## 13.5. Ограничение

Domain и Application Service не должны зависеть от HTTP status codes.

## 13.6. Rollback

При неуспешной бизнес-операции нельзя оставлять частично зафиксированное состояние.

Сценарии, намеренно сохраняющие отдельный переход при возврате ошибки, требуют специально определённой транзакционной обработки.

# 14. Пример: получение Availability

## 14.1. Сценарий

Клиент выбирает ServiceOffering и диапазон дат.

## 14.2. Обработка

```text
HTTP Request
    ↓
AvailabilityController
    ↓
AvailabilityService
    ├── ServiceOfferingQuery
    ├── ScheduleQuery
    ├── BookingPolicy Query
    └── OccupancyQuery
    ↓
AvailabilityPolicy
    ↓
AvailableStartResponse
```

## 14.3. Результат

Клиент получает предварительные доступные начала консультаций.

## 14.4. Отсутствие удержания

Просмотр Availability не создаёт Reservation и ScheduleOccupancy.

## 14.5. Конкурентность

Один и тот же вариант времени могут одновременно увидеть несколько клиентов.

Создание Reservation выполняет повторную окончательную проверку.

---

# 15. Пример: создание Reservation

## 15.1. Сценарий

Клиент выбирает ServiceOffering и начало консультации.

## 15.2. Процесс

```text
HTTP Request
    ↓
Authentication / Authorization
    ↓
ReservationController
    ↓
ReservationApplicationService
    ├── ServiceOffering
    ├── SpecialistBookingAccess
    ├── SpecialistBookingPolicy
    ├── SpecialistTimeZoneGuard
    ├── Schedule
    ├── AvailabilityPolicy
    └── Booking persistence
         ├── Reservation
         └── ScheduleOccupancy
    ↓
COMMIT
    ↓
ReservationResponse
```

## 15.3. Бизнес-правила

Проверяются:

- роль и состояние клиента;
- действительность услуги;
- эффективный допуск специалиста;
- рабочее расписание;
- bookingHorizonDays;
- minimumBookingNotice;
- 15-минутная сетка;
- допустимость локального времени;
- отсутствие пересечения Occupancy.

## 15.4. Snapshot

Reservation фиксирует согласованные условия ServiceOffering и необходимые правила отмены.

## 15.5. TTL

Reservation имеет системный expiresAt.

## 15.6. Атомарность

ACTIVE Reservation и ScheduleOccupancy создаются в одной транзакции.

## 15.7. Конкурентность

При конфликте интервал не резервируется.

Окончательная защита от пересечений обеспечивается PostgreSQL.

---

# 16. Пример: подтверждение Reservation

## 16.1. Сценарий

Клиент подтверждает собственную ACTIVE Reservation.

## 16.2. Процесс

```text
HTTP Request
    ↓
Authentication / Authorization
    ↓
Booking Application Service
    ↓
Reservation ownership
    ↓
Reservation ACTIVE / TTL check
    ↓
Specialist booking eligibility
    ↓
Reservation → CONFIRMED
    ↓
Booking created
    ↓
Occupancy preserved
    ↓
COMMIT
    ↓
BookingResponse
```

## 16.3. Основные условия

- Reservation принадлежит клиенту;
- Reservation ACTIVE;
- текущее время меньше expiresAt;
- специалист сохраняет эффективный допуск.

## 16.4. Изменение расписания

Обычные изменения рабочего графика после создания Reservation не отменяют право подтвердить её в пределах TTL.

## 16.5. Результат

Создаётся одна CONFIRMED Booking.

## 16.6. Атомарность

Нельзя зафиксировать CONFIRMED Reservation без соответствующей Booking.

---

# 17. Пример: отмена и истечение Reservation

## 17.1. Отмена

Клиент или другой уполномоченный инициатор отменяет ACTIVE Reservation.

## 17.2. Изменения

```text
ACTIVE Reservation
    ↓
CANCELLED Reservation
    +
DELETE ScheduleOccupancy
```

## 17.3. Истечение

После TTL:

```text
ACTIVE Reservation
    ↓
EXPIRED Reservation
    +
DELETE ScheduleOccupancy
```

## 17.4. История

Reservation сохраняется.

## 17.5. Конкурентность

Отмена, истечение и подтверждение должны быть согласованы строковой блокировкой Reservation.

## 17.6. Доступность после освобождения

Удаление Occupancy освобождает интервал.

Однако новое бронирование по-прежнему требует соблюдения актуального расписания и дедлайнов.

---

# 18. Пример: отмена Booking

## 18.1. Сценарий

Клиент отменяет собственную CONFIRMED Booking до начала консультации.

## 18.2. Процесс

```text
CONFIRMED Booking
    ↓
Проверка права клиента
    ↓
Проверка now < sessionStart
    ↓
Расчёт своевременной/поздней отмены
    ↓
Booking → CANCELLED
    ↓
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 18.3. ClientCancellationNotice

При отмене используется исторический snapshot условия.

## 18.4. Поздняя отмена

Если отмена произошла после дедлайна, но до начала консультации, она остаётся допустимой.

Для MVP поздняя отмена не приводит к автоматическому штрафу.

## 18.5. Статус

Обе разновидности отмены используют:

`BookingStatus.CANCELLED`

## 18.6. История

Booking сохраняется.

## 18.7. Повторная запись

Другое бронирование возможно только при выполнении текущих правил Availability.

---

# 19. Пример: административная блокировка

## 19.1. Сценарий

Администратор лишает специалиста эффективного допуска к бронированию.

## 19.2. Процесс

```text
Admin Request
    ↓
Security / ADMIN authorization
    ↓
AdministrativeBlockingService
    ↓
BookingAccess coordination
    ↓
Изменение допуска
    ↓
Отмена всех ACTIVE Reservation
    ↓
Удаление соответствующих Occupancy
    ↓
Административный аудит
    ↓
COMMIT
```

## 19.3. CONFIRMED Booking

Подтверждённые Booking сохраняются.

## 19.4. Атомарность

Изменение допуска и обязательная отмена ACTIVE Reservation должны выполняться в одной транзакции.

## 19.5. Новые операции

После блокировки новые Reservation и подтверждения ACTIVE Reservation запрещаются.

# 20. Пример: изменение расписания

## 20.1. Сценарий

Специалист изменяет своё рабочее расписание.

## 20.2. Возможные операции

- изменение DateSchedule;
- изменение WeeklyScheduleVersion;
- переключение REGULAR/FLOATING;
- изменение ZoneId.

## 20.3. Координация

Изменения расписания должны быть согласованы с конкурентным созданием Reservation.

## 20.4. Существующие обязательства

Обычные изменения сохраняют:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 20.5. Новые Reservation

После изменения новые записи проверяются по актуальной конфигурации.

## 20.6. Часовой пояс

Изменение ZoneId не меняет сохранённые абсолютные времена существующих Reservation и Booking.

# 21. Пример: SessionOutcome

## 21.1. Назначение

После консультации клиент и специалист сообщают, состоялась ли она.

## 21.2. Отдельная модель

BookingStatus не является доказательством фактического проведения консультации.

Для результата используется:

- SessionOutcome;
- SessionOutcomeReport;
- DisputeResolution.

## 21.3. Начало окна

После завершения неотменённой консультации начинается окно предоставления отчётов.

## 21.4. Временное ограничение

Утверждённое окно:

```text
[sessionEnd, sessionEnd + 24 hours)
```

## 21.5. Результаты участников

Каждый участник независимо выбирает:

- OCCURRED;
- DID_NOT_OCCUR.

## 21.6. Причины DID_NOT_OCCUR

Предусмотрены:

- CLIENT_NO_SHOW;
- SPECIALIST_NO_SHOW;
- TECHNICAL_PROBLEM;
- OTHER.

Для OTHER требуется непустой текст.

## 21.7. Неизменяемость отчётов

Каждый участник может представить не более одного неизменяемого отчёта по консультации.

---

# 22. Автоматическое разрешение SessionOutcome

## 22.1. Оба участника сообщили OCCURRED

```text
OCCURRED + OCCURRED
    ↓
RESOLVED / OCCURRED
```

## 22.2. Совместимые отрицательные ответы

Если оба участника сообщили DID_NOT_OCCUR с одинаковой структурированной причиной, отличной от OTHER:

```text
DID_NOT_OCCUR + DID_NOT_OCCUR
    ↓
RESOLVED / DID_NOT_OCCUR
```

## 22.3. Противоречивые результаты

Если заявления не совпадают:

```text
PENDING → DISPUTED
```

## 22.4. Различные причины

Если участники указали разные причины DID_NOT_OCCUR, создаётся спор.

## 22.5. OTHER

Если один из двух отчётов содержит OTHER, автоматическое совместное разрешение не выполняется.

Даже:

`OTHER + OTHER`

переходит в DISPUTED.

Система не должна сравнивать свободный текст и самостоятельно выводить согласованность причин.

## 22.6. Один ответ

Если к завершению окна имеется ровно один отчёт, результат разрешается на основании этого отчёта.

Это правило применяется и к одному DID_NOT_OCCUR / OTHER.

## 22.7. Нет ответов

Если ни один участник не ответил:

`PENDING → UNVERIFIED`

Консультация не считается автоматически успешно проведённой.

---

# 23. Административное разрешение спора

## 23.1. Условие

При несовместимых отчётах:

`PENDING → DISPUTED`

## 23.2. Администратор

Уполномоченный ADMIN рассматривает спор.

## 23.3. Решение

Администратор устанавливает:

- OCCURRED;

или:

- DID_NOT_OCCUR с предусмотренной причиной.

## 23.4. OTHER

При административной причине OTHER требуется непустой комментарий.

## 23.5. История

Исходные SessionOutcomeReport остаются неизменными.

Решение сохраняется отдельно в DisputeResolution.

## 23.6. Итог

После разрешения:

`DISPUTED → RESOLVED`

## 23.7. Граница ответственности

Admin координирует рассмотрение, но Outcome остаётся владельцем конечного результата.

---

# 24. Review Eligibility

## 24.1. Основное условие

Право создать Review возникает при:

```text
SessionOutcome.resolutionStatus = RESOLVED

AND SessionOutcome.finalOutcome = OCCURRED
```

## 24.2. Недостаточные основания

Review не разрешается только на основании:

- Reservation;
- CONFIRMED Booking;
- окончания времени консультации;
- PENDING Outcome;
- DISPUTED Outcome;
- UNVERIFIED Outcome;
- DID_NOT_OCCUR.

## 24.3. Один отзыв

Клиент может оставить одному специалисту только один Review.

## 24.4. Редактирование

Существующий Review можно редактировать.

## 24.5. Историческое основание

Review сохраняет ссылку на Booking, подтвердившую первоначальное право на отзыв.

---

# 25. События и Notification

## 25.1. Назначение

Значимые бизнес-операции могут порождать события.

## 25.2. Примеры

- ReservationCreated;
- ReservationCancelled;
- ReservationExpired;
- BookingConfirmed;
- BookingCancelled;
- SessionOutcomeResolved;
- ReviewCreated.

## 25.3. Обработка после COMMIT

Уведомление не должно представлять откатившуюся бизнес-операцию как успешно завершённую.

## 25.4. Eventual consistency

Для Notification допускается асинхронная обработка и небольшая задержка.

## 25.5. Надёжность

Если потребуется надёжно сохранять события, может применяться transactional outbox.

## 25.6. Граница

Notification не изменяет результаты Booking и Outcome.

# 26. Архитектурные принципы

## 26.1. Разделение слоёв

- Controller — HTTP;
- Application Service — пользовательские сценарии;
- Domain — предметные правила;
- Repository — сохранение;
- PostgreSQL — целостность данных.

## 26.2. Владение

Каждый модуль управляет собственными данными.

## 26.3. Транзакционная согласованность

Согласованные изменения выполняются атомарно.

## 26.4. Конкурентность

Корректность бронирования обеспечивается PostgreSQL, а не только предварительными проверками приложения.

## 26.5. Разделение времени

Рабочее расписание использует локальные даты и время.

Reservation и Booking используют абсолютные моменты.

## 26.6. История

Reservation и Booking сохраняются после завершения соответствующих операций.

## 26.7. Независимые состояния

Booking, Reservation и SessionOutcome не объединяются в один универсальный статус.

# 28. Текущее состояние и целевая модель

## 28.1. Существующая реализация

В исходной реализации присутствуют:

- доменные сервисы;
- JPA Repository;
- Reservation;
- Booking;
- обработка TTL;
- PostgreSQL;
- часть проверок авторизации на уровне сервисов.

## 28.2. Устаревшая часть

Исходный жизненный цикл AvailabilitySlot больше не используется в целевой модели.

## 28.3. Целевая модель

Утверждена архитектура с:

- ServiceOffering;
- Schedule;
- Dynamic Availability;
- ScheduleOccupancy;
- SpecialistBookingAccess;
- Reservation;
- Booking;
- SessionOutcome;
- Review после подтверждённого результата.

## 28.4. Реализация

Фактическое соответствие целевой модели определяется по исходному коду и миграциям PsyWeb.

# 29. Итог

Целевой жизненный цикл HTTP-запроса PsyWeb:

```text
Client
    ↓
Spring Security
    ↓
Controller
    ↓
Application Service
    ↓
Domain / Repository
    ↓
PostgreSQL
    ↓
COMMIT
    ↓
Response DTO
    ↓
HTTP Response
```

Основной бизнес-процесс:

```text
ServiceOffering
    ↓
Dynamic Availability
    ↓
ACTIVE Reservation + ScheduleOccupancy
    ↓
CONFIRMED Reservation + CONFIRMED Booking
    ↓
Consultation
    ↓
SessionOutcome
    ↓
Review eligibility
```

Основные гарантии:

- аутентификация не заменяет авторизацию;
- Controller не содержит бизнес-логики;
- Application Service управляет транзакционным сценарием;
- PostgreSQL защищает критические инварианты;
- просмотр Availability не удерживает время;
- Reservation и Occupancy создаются атомарно;
- подтверждение создаёт одну Booking;
- отмена и истечение освобождают Occupancy;
- обычные изменения расписания сохраняют существующие обязательства;
- административная блокировка атомарно отменяет ACTIVE Reservation;
- результат консультации определяется отдельно через SessionOutcome;
- Review создаётся только после подтверждённого успешного результата.

**Статус: DRAFT — целевой жизненный цикл определён, соответствие текущей реализации проверяется отдельно.**
