
**System:** Spring Boot Modular Monolith

---

# Overview

This document describes how an HTTP request is processed inside the system — from entry point to database and back.

---

# High-Level Flow

```text
Client → Spring Security Filter Chain → Controller → Service → Repository → Database
                                                         ↓
                                                      Response
```

---

# 1. Request Entry Point

## Step 1: Client Request

A client sends an HTTP request:

- REST API call (e.g. booking, login, search)
- JSON payload (if applicable)

---

## Step 2: Spring Security Filter Chain

Before reaching controllers, request passes through:

- JWT Authentication Filter
- Security Context Filter

### Responsibilities:
- validate JWT token
- extract user identity
- set SecurityContext
- reject unauthorized requests early

If invalid:
→ request is rejected (401 Unauthorized)

---

# 2. Controller Layer

## Step 3: REST Controller

Controller responsibilities:

- map HTTP request to method
- validate request DTO
- delegate logic to service layer

### Important Rule:
Controllers contain **no business logic**

Example responsibilities:
- input validation (basic)
- request mapping
- response formatting

---

# 3. Service Layer (Core Business Logic)

## Step 4: Business Processing

Service layer is the **heart of the system**.

Responsibilities:
- enforce business rules
- coordinate domain logic
- manage transactions
- call repositories

### Examples:
- check slot availability
- validate user status
- enforce booking rules
- handle cancellation logic

---

## Transaction Boundary

Most critical operations are wrapped in:

```text
@Transactional
```

Example:
- booking appointment
- cancelling appointment
- creating availability slots

Ensures:
- atomicity
- consistency
- rollback on failure

---

# 4. Repository Layer

## Step 5: Data Access

Repositories handle:

- database queries
- persistence operations
- entity retrieval

Technology:
- Spring Data JPA

Rules:
- no business logic
- only data access

---

# 5. Database Layer

## Step 6: PostgreSQL Execution

Database is the **source of truth**.

Responsibilities:
- enforce constraints (unique, foreign keys)
- maintain consistency
- execute transactions

---

# 6. Response Flow

## Step 7: Service → Controller → Client

After successful execution:

1. Service returns domain result
2. Controller maps result to DTO
3. Response is serialized to JSON
4. Client receives response

---

# Error Handling Flow

## Global Exception Handler

All exceptions are processed via:

- @ControllerAdvice

### Responsibilities:
- convert exceptions to HTTP status codes
- standardize error response format

---

# Authentication Flow Inside Lifecycle

If request is protected:

1. JWT extracted from header
2. Token validated
3. User loaded from database
4. User injected into SecurityContext
5. Service layer uses current user context

---

# Booking Example Flow (Real Scenario)

```text
POST /appointments/book
```

1. Request enters filter chain
2. JWT validated
3. Controller receives request
4. Service checks:
   - slot availability
   - user conflicts
   - specialist status
5. Transaction starts
6. Appointment created
7. Slot marked as booked
8. Transaction commits
9. Response returned

---

# Key Principles

## 1. Separation of Concerns

- Controller → API layer
- Service → business logic
- Repository → data access

---

## 2. Stateless Backend

- no session state stored in server
- JWT used for authentication

---

## 3. Transaction Safety

- critical operations are atomic
- failures trigger rollback

---

## 4. Single Source of Truth

- PostgreSQL is authoritative
- application enforces rules, DB guarantees consistency

---
