
**System:** PsyWeb Backend  
**Security Model:** Role-Based Access Control (RBAC)

---

# Overview

The system uses **Role-Based Access Control (RBAC)** combined with **User Status validation** to determine access to resources.

Authorization happens after authentication and is enforced at:

- Controller level (@PreAuthorize)
- Service layer (business rules)
- Domain rules (business constraints)

---

# 1. Roles

## ROLE_CLIENT

### Description:
End user who books consultations.

### Permissions:
- search specialists
- book appointments
- cancel own appointments
- leave reviews
- use chat (if enabled)

---

## ROLE_SPECIALIST

### Description:
Professional providing consultation services.

### Permissions:
- manage profile
- create services
- manage availability slots
- view appointments
- cancel appointments
- respond in chat (if enabled)
- view reviews

---

## ROLE_ADMIN

### Description:
System administrator.

### Permissions:
- approve/reject specialists
- manage users
- moderate reviews
- view system statistics
- override restrictions (future extension)

---

# 2. Status-Based Access Control

User role is not enough — **status is also required**.

## ACTIVE

- full access according to role

---

## PENDING_APPROVAL

- limited access
- only registration + login allowed

---

## REJECTED

- no access to system functionality except login rejection message

---

## SUSPENDED

- access denied to all protected resources

# 4. Authorization Rules

## AR-001 — Role Check Required
Every protected endpoint must validate user role.

---

## AR-002 — Status Check Required
Only ACTIVE users may access business functionality.

---

## AR-003 — Ownership Rule
Users can only access or modify their own data unless explicitly allowed.

Example:
- client can only cancel their own appointments
- specialist can only modify their own services

---

## AR-004 — Admin Override Rule
Admin may access system-wide data but must still be authenticated.

---

# 5. Method-Level Security

System uses Spring Security annotations:

```java
@PreAuthorize("hasRole('CLIENT')")
```

or

```java
@PreAuthorize("hasRole('SPECIALIST')")
```

or combined rules:

```java
@PreAuthorize("hasRole('CLIENT') and @securityService.isOwner(#appointmentId)")
```

---

# 6. Business-Level Authorization

Some rules cannot be enforced at controller level and are handled in service layer:

- appointment ownership validation
- slot modification rights
- review eligibility
- cancellation policy enforcement

---

# 7. Combined Security Model

Access decision is based on:

```text
Authentication (Who you are)
+
Role (What you are)
+
Status (Are you allowed to use system)
+
Ownership (Is this your data)
```

---

# 8. Denial Cases

## 401 Unauthorized
- missing or invalid JWT

## 403 Forbidden
- valid user but insufficient permissions

---

# 9. Future Extensions

This model can be extended with:

- admin impersonation mode
- audit logging of all sensitive actions
