
# 05. Модель авторизации (Authorization Model)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Модель безопасности:** RBAC + Account Status + Domain Authorization  
**Статус:** DRAFT — целевая модель авторизации

---

# 1. Назначение документа

Документ описывает основные правила авторизации пользователей PsyWeb.

Авторизация определяет, имеет ли пользователь право выполнить конкретную операцию.

Для принятия решения учитываются:

- UserRole;
- UserStatus;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed;
- принадлежность ресурса;
- участие пользователя в консультации;
- текущее бизнес-состояние объекта;
- временные и административные ограничения.

PsyWeb использует сочетание:

- Role-Based Access Control;
- проверок состояния аккаунта;
- проверок владельца ресурса;
- проверок профессионального допуска;
- предметных правил.

Аутентификация и авторизация не являются одним механизмом.

---

# 2. Основные уровни проверки

## 2.1. Authentication

Устанавливает личность пользователя.

## 2.2. Account Status

Определяет, разрешено ли учётной записи выполнять защищённые операции.

## 2.3. Role-Based Authorization

Проверяет соответствие UserRole требуемой категории пользователя.

## 2.4. Resource Authorization

Проверяет принадлежность ресурса или участие пользователя в соответствующем процессе.

## 2.5. Specialist Eligibility

Определяет профессиональный допуск специалиста.

## 2.6. Booking Eligibility

Определяет право специалиста принимать новые Reservation и подтверждения.

## 2.7. Domain Validation

Определяет, допустима ли операция при текущем бизнес-состоянии.

Успешная авторизация не гарантирует успешное выполнение бизнес-операции.

---

# 3. Роли пользователей

В PsyWeb используются:

```text
CLIENT
SPECIALIST
ADMIN
```

Роль определяет категорию участника платформы.

Роль не предоставляет автоматически доступ ко всем данным соответствующего модуля.

---

# 4. CLIENT

## 4.1. Назначение

CLIENT является пользователем, который ищет специалистов и получает консультационные услуги.

## 4.2. Основные возможности

Клиент может:

- просматривать публичную информацию о специалистах;
- выбирать ServiceOffering;
- получать доступные варианты времени;
- создавать Reservation;
- подтверждать собственные Reservation;
- отменять собственные ACTIVE Reservation;
- просматривать собственные Booking;
- отменять собственные CONFIRMED Booking при соблюдении бизнес-правил;
- сообщать результат собственных консультаций;
- создавать и редактировать Review при наличии права;
- получать собственные Notification;
- использовать Communication, если функциональность реализована.

## 4.3. Условия

Защищённые клиентские операции требуют:

```text
UserRole.CLIENT
AND UserStatus.ACTIVE
```

## 4.4. Принадлежность

Клиент не может выполнять операции с чужими Reservation или Booking.

## 4.5. Reservation

Возможность создать Reservation дополнительно зависит от:

- выбранной ServiceOffering;
- допуска специалиста;
- рабочего расписания;
- временных ограничений;
- отсутствия конфликтующей Occupancy.

## 4.6. Review

Право создать Review возникает только после подтверждённо успешной консультации с соответствующим специалистом.

---

# 5. SPECIALIST

## 5.1. Назначение

SPECIALIST предоставляет профессиональные услуги через платформу.

## 5.2. Возможности

При наличии соответствующих полномочий специалист может:

- управлять собственным профилем;
- управлять ServiceOffering;
- управлять рабочим расписанием;
- просматривать собственные консультации;
- участвовать в предусмотренных Booking-сценариях;
- отправлять отчёты SessionOutcome;
- использовать Communication, если функциональность реализована.

## 5.3. Аутентификация

Наличие UserRole.SPECIALIST не означает автоматического профессионального допуска.

ACTIVE специалист может войти в аккаунт даже до одобрения.

## 5.4. Профессиональные операции

Для операций, требующих профессионального допуска, используются:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
```

## 5.5. Отдельное разрешение бронирования

Для создания и подтверждения Reservation дополнительно требуется:

```text
SpecialistBookingAccess.bookingAllowed = TRUE
```

Это условие проверяется для специалиста, к которому записывается клиент.

## 5.6. Принадлежность

Специалист может изменять только собственные ServiceOffering и Schedule.

## 5.7. Ограниченные состояния

Специалисты со статусами PENDING, REJECTED и SUSPENDED не получают профессиональных полномочий.

Однако могут сохранять разрешённый доступ к собственному аккаунту.

---

# 6. ADMIN

## 6.1. Назначение

ADMIN выполняет предусмотренные административные операции платформы.

## 6.2. Основные возможности

Администратор может:

- рассматривать заявки специалистов;
- одобрять и отклонять заявки;
- приостанавливать профессиональную деятельность;
- восстанавливать допуск;
- блокировать пользовательские аккаунты;
- изменять отдельное разрешение BookingAccess;
- разрешать споры SessionOutcome;
- выполнять предусмотренные административные операции;
- просматривать необходимые данные аудита.

## 6.3. Условия

```text
UserRole.ADMIN
AND UserStatus.ACTIVE
```

## 6.4. Ограничения

ADMIN не может обходить:

- ограничения PostgreSQL;
- инварианты Reservation;
- правила переходов Booking;
- уникальность Review;
- правила разрешения Outcome;
- границы владения данными.

## 6.5. Межмодульные операции

Admin инициирует изменения через сервисные контракты модулей-владельцев.

---

# 7. UserStatus

## 7.1. Назначение

UserStatus определяет состояние учётной записи.

## 7.2. Значения

В существующей реализации:

```text
ACTIVE
BLOCKED
```

## 7.3. ACTIVE

Пользователь может проходить дальнейшие проверки авторизации.

## 7.4. BLOCKED

Пользователь не может выполнять защищённые операции.

## 7.5. JWT

Ранее выданный JWT не должен позволять заблокированному пользователю обходить проверку UserStatus.

## 7.6. Поиск User

Необходимо различать:

- поиск User независимо от состояния;
- поиск только ACTIVE User.

## 7.7. Внутренние операции

Административные операции могут получать BLOCKED User для модерации и аудита.

Это не означает, что заблокированный пользователь получает право использовать платформу.

---

# 8. Specialist Approval Status

## 8.1. Назначение

Модерационный статус отражает профессиональное одобрение специалиста.

## 8.2. Существующая модель

Исходный enum SpecialistStatus содержит:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

В целевой документации используется поле:

`Specialist.approvalStatus`

Окончательное название Java enum требуется согласовать с реализацией.

## 8.3. PENDING

Специалист ожидает рассмотрения.

## 8.4. APPROVED

Специалист прошёл модерацию.

## 8.5. REJECTED

Заявка специалиста отклонена.

## 8.6. SUSPENDED

Профессиональная деятельность специалиста приостановлена.

## 8.7. Существующие переходы

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

Другие переходы требуют отдельного решения.

## 8.8. Аутентификация

Ни один из этих статусов сам по себе не запрещает Login в ACTIVE User.

## 8.9. Независимость

UserStatus.BLOCKED и SpecialistStatus.SUSPENDED не являются взаимозаменяемыми состояниями.

---

# 9. SpecialistBookingAccess

## 9.1. Назначение

SpecialistBookingAccess представляет самостоятельное административное разрешение на бронирование.

## 9.2. Основное поле

`bookingAllowed`

## 9.3. TRUE

Отсутствует отдельная блокировка BookingAccess.

Однако все остальные проверки допуска сохраняются.

## 9.4. FALSE

Новые Reservation и подтверждения существующих ACTIVE Reservation запрещаются.

## 9.5. Независимость

bookingAllowed не заменяет:

- UserStatus;
- approvalStatus;
- UserRole.

## 9.6. Восстановление

Повторное одобрение специалиста не должно автоматически снимать отдельное ограничение bookingAllowed.

## 9.7. Login

bookingAllowed не определяет возможность аутентификации.

---

# 10. Эффективный допуск к бронированию

## 10.1. Полное условие

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
AND SpecialistBookingAccess.bookingAllowed = TRUE
```

## 10.2. Проверка при создании Reservation

ReservationApplicationService должен проверять эффективный допуск внутри критической транзакции.

## 10.3. Проверка при подтверждении

Подтверждение ACTIVE Reservation также требует эффективного допуска.

## 10.4. Проверка Availability

AvailabilityService не должен предлагать новые доступные начала специалиста, если эффективный допуск отсутствует.

## 10.5. Независимость от текущей Booking

Отсутствие допуска к новым бронированиям не означает автоматическую отмену уже подтверждённых Booking.

---

# 11. Административная потеря допуска

## 11.1. Назначение

Административное лишение права принимать бронирования должно быть согласовано с активными удержаниями времени.

## 11.2. Требуемые изменения

В одной транзакции выполняются:

1. Координация через SpecialistBookingAccess.
2. Изменение соответствующего состояния допуска.
3. Поиск ACTIVE Reservation специалиста.
4. Отмена ACTIVE Reservation.
5. Удаление их ScheduleOccupancy.
6. Сохранение административного аудита.

## 11.3. CONFIRMED Booking

Подтверждённые Booking автоматически не отменяются.

## 11.4. Конкурентность

Нельзя допустить создание новой ACTIVE Reservation одновременно с фиксацией административного запрета.

## 11.5. PostgreSQL

Для координации применяются согласованные строковые блокировки.

Точный порядок описан в Transaction and Concurrency Model.

## 11.6. Разделение

Административный сценарий не является операцией Authentication.

JWT Filter не должен выполнять отмену Reservation.

---

# 12. Матрица доступа

Таблица показывает базовые права. Каждая операция дополнительно проверяет состояние аккаунта, принадлежность ресурса и бизнес-предусловия.

| Операция | CLIENT | APPROVED SPECIALIST | PENDING / REJECTED / SUSPENDED | ADMIN |
|---|---|---|---|---|
| Login при ACTIVE User | Да | Да | Да | Да |
| Просмотр публичных специалистов | Да | Да | Да | Да |
| Создание Reservation | Да | Нет | Нет | Нет |
| Подтверждение собственной Reservation | Да | Нет | Нет | Нет |
| Отмена собственной Reservation | Да | Нет | Нет | Нет |
| Просмотр собственных Booking клиента | Да | Нет | Нет | Нет |
| Управление собственным Schedule | Нет | Да | Ограничено | Нет |
| Управление собственными ServiceOffering | Нет | Да | Ограничено | Нет |
| Просмотр Booking специалиста | Нет | Да | По отдельным правилам | Административный доступ |
| Отчёт SessionOutcome | Своя консультация | Своя консультация | По отдельным правилам | Нет |
| Создание Review | При наличии eligibility | Нет | Нет | Нет |
| Модерация специалистов | Нет | Нет | Нет | Да |
| Блокировка пользователей | Нет | Нет | Нет | Да |
| Разрешение споров Outcome | Нет | Нет | Нет | Да |

## 12.1. Публичные операции

Часть публичных запросов может быть доступна без Authentication.

Это определяется API-контрактами.

## 12.2. Ограниченные специалисты

Точный перечень разрешённых действий для PENDING, REJECTED и SUSPENDED требует дополнительной формализации.

## 12.3. Административный доступ

ADMIN получает доступ только в рамках предусмотренного административного сценария.

---

# 13. Принадлежность ресурсов

## 13.1. Основное правило

Пользователь может управлять только ресурсами, которые принадлежат ему либо в которых он участвует, если отдельный административный сценарий не предусматривает иное.

## 13.2. Reservation

CLIENT может подтверждать и отменять только собственные Reservation.

## 13.3. Booking

CLIENT может выполнять разрешённые операции только с собственными Booking.

## 13.4. Schedule

SPECIALIST может управлять собственным расписанием.

## 13.5. ServiceOffering

SPECIALIST может изменять собственные услуги.

## 13.6. SessionOutcome

Отчёт может отправлять только участник соответствующей консультации.

## 13.7. Review

Review может редактировать только автор.

## 13.8. Notification

Пользователь может просматривать собственные Notification.

---

# 14. Авторизация Reservation

## 14.1. Создание

Создание Reservation требует:

- CLIENT;
- ACTIVE User;
- существующую активную ServiceOffering;
- эффективный допуск специалиста;
- соблюдение правил Availability;
- отсутствие конфликтующей Occupancy.

## 14.2. Подтверждение

Подтверждение требует:

- принадлежность Reservation клиенту;
- статус ACTIVE;
- отсутствие истечения TTL;
- эффективный допуск специалиста.

## 14.3. Отмена

CLIENT может отменить собственную ACTIVE Reservation.

## 14.4. Истечение

Expiration Scheduler выполняет внутреннюю системную операцию.

Она не инициируется пользовательской ролью CLIENT.

## 14.5. Конкурентность

Авторизация не заменяет транзакционную защиту от одновременного подтверждения, отмены или истечения.

---

# 15. Авторизация Booking

## 15.1. Просмотр

Клиент и специалист могут просматривать Booking, в которой они участвуют, согласно разрешённым сценариям.

## 15.2. Отмена клиентом

Клиент может отменить собственную CONFIRMED Booking до начала консультации.

## 15.3. Поздняя отмена

Поздняя отмена до начала консультации разрешена.

Для MVP она не влечёт автоматический штраф.

## 15.4. После начала консультации

Обычная клиентская отмена запрещена.

## 15.5. Отмена специалистом

Специалист может отменять собственные Booking в рамках отдельно утверждённого сценария.

## 15.6. Административные операции

Исключительные административные действия требуют явного основания и соответствующего сервисного контракта.

---

# 16. Авторизация Schedule

## 16.1. Владение

Рабочим расписанием управляет соответствующий специалист.

## 16.2. Режимы

Поддерживаются:

- REGULAR;
- FLOATING.

## 16.3. Изменение

Изменение расписания требует проверки принадлежности и применимых профессиональных полномочий.

## 16.4. Обязательства

Обычные изменения Schedule не отменяют существующие ACTIVE Reservation и CONFIRMED Booking.

## 16.5. Конкурентность

Изменения расписания согласуются с созданием Reservation через календарные блокировки.

---

# 17. Авторизация SessionOutcome

## 17.1. Участники

Отчёты о результате консультации могут отправлять:

- клиент соответствующей Booking;
- специалист соответствующей Booking.

## 17.2. Окно

Для MVP предусмотрено 24 часа после завершения консультации.

## 17.3. Значения

Участник сообщает:

- OCCURRED;
- DID_NOT_OCCUR.

## 17.4. Причины

При DID_NOT_OCCUR указывается предусмотренная причина.

## 17.5. Ограничения

Нельзя отправлять отчёт за другого участника.

## 17.6. Споры

Противоречивые отчёты переходят в DISPUTED.

## 17.7. Решение

Разрешение спора принадлежит уполномоченному ADMIN.

## 17.8. Отдельный результат

BookingStatus не заменяет SessionOutcome.

---

# 18. Авторизация Review

## 18.1. Создание

Review может создать CLIENT после подтверждённо успешной консультации с соответствующим специалистом.

## 18.2. Проверенное основание

Требуется:

```text
SessionOutcome.resolutionStatus = RESOLVED
AND SessionOutcome.finalOutcome = OCCURRED
```

## 18.3. Уникальность

Один Review на пару:

`(clientId, specialistId)`

## 18.4. Редактирование

Клиент может редактировать собственный Review.

## 18.5. Чужие Review

Редактирование чужих Review запрещено.

## 18.6. Административная модерация

Дополнительные полномочия по скрытию или удалению отзывов требуют отдельного решения.

---

# 19. Method-Level Security

## 19.1. Основной подход

Spring Security может выполнять общую проверку роли.

Примеры:

```java
@PreAuthorize("hasRole('CLIENT')")
```

```java
@PreAuthorize("hasRole('SPECIALIST')")
```

```java
@PreAuthorize("hasRole('ADMIN')")
```

## 19.2. Ограничение

Ролевая аннотация не заменяет проверку принадлежности ресурса.

## 19.3. Предметные проверки

Сервисный слой проверяет:

- ownership;
- participation;
- specialist eligibility;
- бизнес-состояние;
- временные ограничения.

## 19.4. Текущая реализация

Method-level Security относится к целевой инфраструктуре, пока его реализация не подтверждена актуальным кодом.

---

# 20. Ошибки авторизации

## 20.1. 401 Unauthorized

Применяется, когда запрос не может установить корректную аутентифицированную идентичность.

Примеры:

- отсутствующий JWT;
- недействительный JWT;
- просроченный JWT.

## 20.2. 403 Forbidden

Применяется, когда аутентифицированный пользователь не обладает необходимыми полномочиями.

Примеры:

- неподходящая роль;
- нарушение принадлежности;
- недостаточные административные права.

## 20.3. BLOCKED

Заблокированный аккаунт отклоняется при проверке актуального UserStatus.

Точный HTTP-ответ зависит от границы, на которой Security прекращает обработку.

## 20.4. Бизнес-конфликт

Некоторые операции запрещены не из-за полномочий, а из-за предметного состояния.

Примеры:

- Reservation истекла;
- выбранное время занято;
- Booking уже отменена;
- нарушен временной дедлайн.

Они не должны автоматически становиться 403.

# 21. Архитектурные правила

## AR-001. Authentication Required

Защищённые операции требуют аутентификации.

## AR-002. Role Check

Для операции проверяется необходимая UserRole.

## AR-003. Active Account

Защищённые операции требуют UserStatus.ACTIVE.

## AR-004. Specialist Approval

Профессиональные операции требуют одобренного специалиста.

## AR-005. BookingAccess

Создание и подтверждение Reservation требуют отдельного разрешения bookingAllowed.

## AR-006. Ownership

Пользователь может управлять только разрешёнными ресурсами.

## AR-007. Business-State Validation

Авторизация не заменяет проверку состояния сущности.

## AR-008. Administrative Authority

ADMIN выполняет только предусмотренные административные сценарии.

## AR-009. Module Ownership

Авторизация не даёт права обходить границы модулей.

## AR-010. Transactional Booking Eligibility

Проверки допуска к бронированию должны согласовываться с конкурентной административной блокировкой.

## AR-011. Outcome Participation

Отчёт SessionOutcome может отправить только участник консультации.

## AR-012. Review Eligibility

Создание Review требует подтверждённо успешной консультации.

# 24. Итог

Модель авторизации PsyWeb объединяет:

```text
Authentication
    ↓
UserStatus
    ↓
UserRole
    ↓
Ownership / Participation
    ↓
Specialist Professional Eligibility
    ↓
Booking Eligibility (when required)
    ↓
Domain-State Validation
```

Основные принципы:

- роль пользователя не гарантирует доступ к любому ресурсу;
- BLOCKED User не выполняет защищённые операции;
- Specialist approval state не является состоянием Login;
- отдельный BookingAccess определяет дополнительное ограничение бронирования;
- административная потеря допуска отменяет ACTIVE Reservation, сохраняя CONFIRMED Booking;
- управление ресурсами требует проверки принадлежности;
- SessionOutcome доступен участникам консультации;
- Review разрешён после подтверждённого успешного результата;
- Admin не обходит бизнес-инварианты;
- Spring Security и доменная авторизация дополняют друг друга.

**Статус: DRAFT — целевая модель согласована, конкретная реализация Security и отдельные административные полномочия требуют дальнейшей проработки.**
