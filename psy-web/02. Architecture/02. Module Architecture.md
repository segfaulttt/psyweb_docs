
# 02. Модульная архитектура PsyWeb (Module Architecture)

**Проект:** PsyWeb  
**Архитектурный стиль:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — целевая структура модулей и границ ответственности

---

# 1. Назначение документа

Документ описывает модульную структуру backend PsyWeb.

Он определяет:

- состав бизнес-модулей;
- ответственность каждого модуля;
- владение доменными данными;
- допустимые зависимости;
- публичные контракты;
- правила межмодульного взаимодействия;
- расположение транзакционной оркестрации;
- различие между существующей реализацией и целевой архитектурой.

Основной принцип:

**Каждый бизнес-модуль владеет своими данными, инвариантами и жизненным циклом.**

Другие модули взаимодействуют с ним через явно определённые сервисные контракты.

Прямая модификация чужих JPA-сущностей и Repository запрещена.

---

# 2. Общая структура

## 2.1. Целевая структура

```text
com.psyweb
│
├── auth
├── user
├── client
├── specialist
├── service
├── schedule
├── availability
├── booking
├── outcome
├── review
├── notification
├── admin
├── chat
└── common
```

Это логическая структура.

Точное дерево Java-пакетов определяется при реализации.

Не требуется создавать все модули и классы заранее.

## 2.2. Категории

Бизнес-модули:

- User;
- Client;
- Specialist;
- Service;
- Schedule;
- Availability;
- Booking;
- Outcome;
- Review;
- Admin;
- Notification;
- Chat.

Вспомогательные модули:

- Auth;
- Common.

## 2.3. Состав модуля

В зависимости от ответственности модуль может содержать:

```text
api
service
domain
repository
exception
dto
```

Это пример, а не обязательная физическая структура каждого модуля.

Не каждый модуль должен иметь собственные Controller или Repository.

Например, Availability может вычислять результат на основании данных других модулей, не владея отдельной таблицей AvailabilitySlot.

# 3. Основные правила модульности

## 3.1. Владение

У каждой доменной сущности должен быть один модуль-владелец.

## 3.2. Внешние контракты

Другие модули обращаются к владельцу через явно определённые публичные интерфейсы.

## 3.3. Repository

Repository остаётся внутренней частью модуля.

## 3.4. JPA Entity

Не следует передавать изменяемые JPA-сущности через публичные межмодульные контракты.

## 3.5. Ацикличность

Межмодульные зависимости не должны образовывать циклы.

## 3.6. Оркестрация

Межмодульный бизнес-сценарий координируется Application Service.

## 3.7. Транзакции

Если несколько изменений должны быть атомарными, они выполняются в одной транзакции.

## 3.8. Common

Общая техническая логика может находиться в Common.

Бизнес-правила не переносятся туда только ради повторного использования.

# 4. Auth Module

## 4.1. Ответственность

Auth отвечает за аутентификацию и инфраструктуру безопасности.

## 4.2. Целевые компоненты

- AuthController;
- AuthService;
- проверка паролей;
- BCrypt PasswordEncoder;
- JWT generation;
- JWT validation;
- Spring Security Filter Chain;
- SecurityContext integration.

## 4.3. Аутентификация

Успешный Login требует:

```text
Valid credentials
AND UserStatus.ACTIVE
```

## 4.4. Специалисты

Специалист с ACTIVE User может войти независимо от модерационного статуса.

Модерация определяет профессиональные полномочия, но не сам факт аутентификации.

## 4.5. JWT

JWT содержит необходимые сведения об идентичности.

Изменяемые UserStatus, approvalStatus и bookingAllowed не должны использоваться как долговременный источник авторизации внутри токена.

## 4.6. Владение

Auth владеет:

- процессом Login;
- проверкой credentials;
- token-related logic;
- security infrastructure.

## 4.7. Зависимости

Auth использует публичные контракты User.

## 4.8. Не владеет

- User;
- UserRole;
- UserStatus;
- Specialist;
- SpecialistApprovalStatus;
- BookingAccess;
- Reservation;
- Booking.

## 4.9. Состояние реализации

В исходной документации JWT-инфраструктура отмечена как целевая, ещё не завершённая функциональность.

Наличие Auth в архитектуре не означает её фактическую реализацию.

---

# 5. User Module

## 5.1. Ответственность

User управляет учётными записями пользователей.

## 5.2. Основные компоненты

- User;
- UserRole;
- UserStatus;
- UserService;
- UserRepository;
- account validation.

## 5.3. Роли

```text
CLIENT
SPECIALIST
ADMIN
```

## 5.4. Статусы

В текущей реализации:

```text
ACTIVE
BLOCKED
```

## 5.5. Владение

User владеет:

- идентичностью аккаунта;
- email;
- passwordHash;
- ролью;
- состоянием аккаунта;
- жизненным циклом учётной записи.

## 5.6. Контракты

Другим модулям могут предоставляться:

- поиск User;
- проверка актуального состояния;
- получение идентичности;
- разрешённое изменение UserStatus.

## 5.7. Административные изменения

Если изменение UserStatus специалиста лишает его права принимать бронирования, операция должна использовать согласованный административный протокол.

Нельзя напрямую установить BLOCKED, оставив ACTIVE Reservation без обязательной обработки.

## 5.8. Зависимости

User может использовать Common.

## 5.9. Не владеет

- профессиональным профилем специалиста;
- расписанием;
- бронированиями;
- JWT;
- SessionOutcome.

---

# 6. Client Module

## 6.1. Ответственность

Client управляет клиентской частью пользовательской модели.

## 6.2. Основные данные

- Client;
- персональные сведения клиента, необходимые платформе.

## 6.3. Связь с User

Client использует идентичность User.

## 6.4. Зависимости

- User;
- Common при необходимости.

## 6.5. Не владеет

- Reservation;
- Booking;
- Review;
- SessionOutcome.

Клиент участвует в соответствующих сценариях, но предметные данные принадлежат профильным модулям.

---

# 7. Specialist Module

## 7.1. Ответственность

Specialist владеет профессиональной идентичностью специалиста и правилами его модерационного жизненного цикла.

## 7.2. Основная модель

- Specialist;
- Specialist approval state;
- lifecycle validation;
- professional eligibility.

## 7.3. Существующая реализация

В первоначальном коде используются:

- SpecialistStatus;
- minimumBookingNotice;
- clientCancellationNotice;
- SpecialistService;
- проверки профессиональной пригодности.

В новой целевой модели временные настройки бронирования вынесены в отдельную конфигурацию.

## 7.4. Существующие значения SpecialistStatus

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

## 7.5. Существующие переходы

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

Эти переходы отражают зафиксированную исходную реализацию.

Их изменение требует отдельного согласования.

## 7.6. Целевая терминология

В целевой документации используется:

`Specialist.approvalStatus`

Окончательное название Java enum должно быть синхронизировано с существующим кодом.

## 7.7. Профессиональный допуск

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND approvalStatus.APPROVED
```

## 7.8. Допуск к бронированию

Для создания и подтверждения Reservation дополнительно требуется:

`SpecialistBookingAccess.bookingAllowed = TRUE`

## 7.9. SpecialistBookingAccess

Представляет отдельное административное разрешение принимать бронирования.

Также используется как точка транзакционной координации между бронированием и административной блокировкой.

## 7.10. SpecialistBookingPolicy

Хранит:

- minimumBookingNotice;
- clientCancellationNotice.

## 7.11. Владение конфигурацией

Специализированные конфигурационные модели специалиста должны иметь явного владельца.

Booking может получать их значения через публичные контракты, но не должен произвольно изменять конфигурацию.

## 7.12. Модерация

Specialist выполняет собственные допустимые переходы состояний.

Admin инициирует соответствующий административный сценарий через публичный контракт.

## 7.13. История модерации

SpecialistModerationAction сохраняет информацию о принятых модерационных действиях.

Точный владелец persistence-модели административного аудита определяется согласованной архитектурой Admin и Specialist.

## 7.14. Отдельные направления

Публичный профиль и документы о квалификации не смешиваются с базовой сущностью Specialist.

## 7.15. Зависимости

- User;
- Common;
- публичные технические контракты при необходимости.

## 7.16. Не владеет

- Schedule;
- Availability;
- Reservation;
- Booking;
- SessionOutcome;
- Review.

## 7.17. Запрет обратной зависимости

Specialist не зависит от Admin.

Admin может инициировать допустимые действия через Specialist.

# 8. Service Module

## 8.1. Ответственность

Service управляет услугами специалистов.

## 8.2. Основная сущность

`ServiceOffering`

## 8.3. Данные

- title;
- description;
- durationMinutes;
- breakDurationMinutes;
- price;
- currency;
- isActive.

## 8.4. Владение

Service владеет:

- ServiceOffering;
- проверкой условий услуги;
- созданием и редактированием;
- деактивацией;
- предоставлением проверенных данных для создания Reservation.

## 8.5. Межмодульный контракт

Концептуально:

`ServiceOfferingQuery`

Он предоставляет необходимые данные другим модулям, не раскрывая изменяемую JPA Entity.

## 8.6. Snapshot

Service предоставляет данные, на основании которых Booking создаёт исторический snapshot Reservation.

## 8.7. Конкурентность

Изменение ServiceOffering должно согласовываться с её использованием при создании Reservation.

## 8.8. Зависимости

- Specialist;
- Common при необходимости.

## 8.9. Не владеет

- рабочим расписанием;
- доступными началами;
- Reservation;
- Booking;
- Occupancy.

---

# 9. Schedule Module

## 9.1. Ответственность

Schedule управляет правилами рабочего времени специалиста.

## 9.2. Основные объекты

- SpecialistScheduleSettings;
- WeeklyScheduleVersion;
- WeeklyWorkingInterval;
- DateSchedule;
- DateScheduleInterval.

## 9.3. Режимы

```text
REGULAR
FLOATING
```

## 9.4. REGULAR

Использует версионируемое недельное расписание.

WeeklyScheduleVersion представляет полный недельный шаблон на определённый период.

## 9.5. FLOATING

Использует расписание отдельных дат.

## 9.6. DateSchedule

Поддерживает:

- OVERRIDE;
- MANUAL.

## 9.7. Границы ответственности

Schedule отвечает за:

- хранение и изменение расписания;
- правила версионирования;
- корректность рабочих интервалов;
- правила переключения режимов;
- согласованность изменений расписания.

## 9.8. Конкурентность

Изменения расписания координируются с созданием Reservation через календарные advisory locks.

## 9.9. Существующие обязательства

Обычное изменение расписания сохраняет:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 9.10. Межмодульные контракты

Концептуально:

- ScheduleQuery;
- ScheduleCommand;
- SchedulingApplicationService.

## 9.11. Зависимости

Schedule использует Specialist и общую техническую инфраструктуру по необходимости.

## 9.12. Не владеет

- ServiceOffering;
- Reservation;
- Booking;
- ScheduleOccupancy;
- SessionOutcome.

---

# 10. Availability Module

## 10.1. Ответственность

Availability вычисляет доступные начала консультаций.

## 10.2. Основной принцип

Availability не владеет хранимыми AvailabilitySlot.

## 10.3. Источники данных

Расчёт использует:

- ServiceOffering;
- Schedule;
- текущий ZoneId;
- BookingPolicy;
- SpecialistBookingAccess;
- ScheduleOccupancy.

## 10.4. Основные компоненты

Концептуально:

- AvailabilityService;
- AvailabilityPolicy;
- AvailableStart;
- интерпретация рабочих окон.

## 10.5. Результат

Availability предоставляет предварительные варианты начала консультации.

## 10.6. Отсутствие удержания

Получение Availability не изменяет Reservation или Occupancy.

## 10.7. Гарантии

Доступность не резервируется при просмотре.

Два клиента могут одновременно увидеть одинаковое время.

## 10.8. Окончательная проверка

ReservationApplicationService повторно выполняет необходимые проверки внутри транзакции.

## 10.9. Зависимости

Availability использует публичные контракты:

- Service;
- Specialist;
- Schedule;
- Booking для чтения Occupancy.

## 10.10. Отсутствие циклов

Booking не должен зависеть от реализации AvailabilityService, если это создаёт обратную зависимость.

Общие правила проверки времени предоставляются через согласованный контракт AvailabilityPolicy.

Его расположение должно обеспечивать ацикличную структуру зависимостей.

## 10.11. Не владеет

- ScheduleOccupancy;
- Reservation;
- Booking;
- ServiceOffering;
- рабочим расписанием.

---

# 11. Booking Module

## 11.1. Ответственность

Booking отвечает за жизненный цикл записи на консультацию.

## 11.2. Основные сущности

- Reservation;
- Booking;
- ScheduleOccupancy.

## 11.3. Reservation

Reservation представляет временное удержание.

Статусы:

```text
ACTIVE
CONFIRMED
CANCELLED
EXPIRED
```

## 11.4. Booking

Booking представляет подтверждённую запись.

Целевые статусы:

```text
CONFIRMED
CANCELLED
```

## 11.5. ScheduleOccupancy

Содержит действующие интервалы занятости специалиста.

## 11.6. Создание Reservation

При успешной операции создаются:

- ACTIVE Reservation;
- ScheduleOccupancy.

## 11.7. Подтверждение

При подтверждении:

- Reservation становится CONFIRMED;
- создаётся Booking;
- Occupancy сохраняется.

## 11.8. Отмена и истечение

При отмене или истечении ACTIVE Reservation Occupancy удаляется.

## 11.9. Отмена Booking

Допустимая отмена CONFIRMED Booking освобождает Occupancy.

## 11.10. TTL

Reservation TTL является системным правилом Booking.

Специалист не управляет этим значением.

## 11.11. Snapshot

Reservation сохраняет исторические условия услуги и необходимые настройки отмены.

## 11.12. Конкурентность

Booking использует:

- PostgreSQL transactions;
- row locks;
- advisory locks;
- exclusion constraints;
- UNIQUE;
- CHECK.

## 11.13. Существующая реализация

В исходном backend уже были реализованы ReservationService, BookingService и Expiration Scheduler для старой модели AvailabilitySlot.

Новая целевая модель требует их согласованного рефакторинга.

## 11.14. Основные контракты

Концептуально:

- ReservationApplicationService;
- BookingService;
- ReservationExpirationService;
- OccupancyQuery;
- BookingObligationQuery.

## 11.15. Зависимости

Booking взаимодействует с:

- User;
- Specialist;
- Service;
- Schedule;
- AvailabilityPolicy;
- Common при необходимости.

## 11.16. Не владеет

- ServiceOffering;
- рабочим расписанием;
- Specialist approval state;
- UserStatus;
- SessionOutcome;
- Review.

---

# 12. Outcome Module

## 12.1. Ответственность

Outcome отвечает за определение результата консультации.

## 12.2. Основные модели

- SessionOutcome;
- SessionOutcomeReport;
- DisputeResolution.

## 12.3. Входные данные

Результат формируется на основании отчётов клиента и специалиста.

## 12.4. Окно

Для MVP предусмотрено 24 часа после окончания консультации.

## 12.5. Результаты

Outcome различает:

- подтверждённо успешную консультацию;
- несостоявшуюся консультацию;
- спорный результат;
- непроверенный результат.

## 12.6. Автоматическое разрешение

Совместимые отчёты разрешаются автоматически.

## 12.7. Споры

При противоречивых отчётах требуется административное разрешение.

## 12.8. Владение

Outcome владеет:

- отчётами;
- правилами разрешения;
- итоговым результатом;
- состоянием спора;
- историей разрешения.

## 12.9. Межмодульные контракты

Концептуально:

- OutcomeReportCommand;
- OutcomeResolutionCommand;
- VerifiedOutcomeQuery.

## 12.10. Зависимости

Outcome использует данные Booking через публичные контракты.

## 12.11. Не владеет

- Reservation;
- Booking;
- ScheduleOccupancy;
- Review;
- UserStatus.

---

# 13. Review Module

## 13.1. Ответственность

Review управляет отзывами клиентов о специалистах.

## 13.2. Основная сущность

Review.

## 13.3. Уникальность

Один клиент может иметь только один Review на одного специалиста.

PostgreSQL обеспечивает:

`UNIQUE(client_id, specialist_id)`

## 13.4. Право на создание

Review разрешается после хотя бы одной подтверждённо успешной консультации пары клиент–специалист.

## 13.5. Редактирование

Клиент может редактировать свой rating и comment.

## 13.6. EligibilityBooking

Review сохраняет ссылку на Booking, послужившую первоначальным основанием для отзыва.

## 13.7. Рейтинг

Review отвечает за получение отзывов и расчёт агрегированной оценки специалиста.

## 13.8. Зависимости

- User / Client;
- Specialist;
- Outcome;
- Booking через публичные контракты.

## 13.9. Не владеет

- Booking;
- SessionOutcome;
- Specialist;
- административным статусом специалиста.

---

# 14. Notification Module

## 14.1. Ответственность

Notification управляет системными уведомлениями.

## 14.2. Основная модель

Notification.

## 14.3. Владение

- создание уведомлений;
- хранение;
- получение;
- readAt;
- возможная внешняя доставка.

## 14.4. События

Notification может реагировать на:

- ReservationCreated;
- ReservationExpired;
- BookingConfirmed;
- BookingCancelled;
- SessionOutcomeResolved;
- ReviewCreated;
- SpecialistBlocked.

## 14.5. Интеграция

Предпочтительно использовать явные события и минимальные межмодульные контракты.

## 14.6. Асинхронность

Допускается eventual consistency.

## 14.7. Надёжность

Если требуется гарантированная передача события, может применяться transactional outbox.

## 14.8. Не владеет

- Reservation;
- Booking;
- Review;
- SessionOutcome;
- административными состояниями.

# 15. Admin Module

## 15.1. Ответственность

Admin координирует административные операции.

## 15.2. Основные возможности

- модерация специалистов;
- управление блокировками;
- восстановление допуска;
- административный аудит;
- разрешение споров Outcome;
- другие согласованные действия.

## 15.3. Владение

Admin владеет административными сценариями и собственными данными аудита в рамках выбранной модели.

## 15.4. Модерация

Переходы Specialist approval state выполняются через Specialist.

## 15.5. Блокировка специалиста

Административная потеря допуска должна атомарно:

1. Запретить новые Reservation.
2. Отменить все ACTIVE Reservation.
3. Удалить их Occupancy.
4. Сохранить аудит.

CONFIRMED Booking автоматически не отменяются.

## 15.6. Координация

Для такого сценария используется AdministrativeBlockingService.

## 15.7. Разрешение споров

Admin вызывает OutcomeResolutionCommand.

Результат консультации остаётся собственностью Outcome.

## 15.8. Зависимости

Admin может взаимодействовать с:

- User;
- Specialist;
- Booking;
- Outcome;
- Review при реализации модерации.

## 15.9. Не владеет

- User;
- Specialist;
- Reservation;
- Booking;
- Schedule;
- SessionOutcome;
- Review.

## 15.10. Состояние реализации

В исходной документации отдельный Admin Application Service ещё не был реализован.

Этот модуль относится к целевой архитектуре.

# 18. Направления зависимостей

## 18.1. Основной принцип

Зависимости должны оставаться ациклическими.

## 18.2. Концептуальная схема

```text
Auth ───────────────→ User

Client ─────────────→ User

Specialist ─────────→ User

Service ────────────→ Specialist

Schedule ───────────→ Specialist

Outcome ────────────→ Booking

Review ─────────────→ Outcome
Review ─────────────→ Booking

Admin ──────────────→ User
Admin ──────────────→ Specialist
Admin ──────────────→ Booking
Admin ──────────────→ Outcome

Chat ───────────────→ User
Chat ───────────────→ Booking

Business Modules ──→ Common
```

## 18.3. Availability и Booking

Availability читает расписание, услуги и занятость через публичные контракты.

Booking использует общие согласованные правила проверки допустимости времени.

Чтобы не создавать цикл Booking ↔ Availability, требуется отдельная граница политики доступности.

Концептуально:

```text
AvailabilityService
        │
        ▼
AvailabilityPolicy

ReservationApplicationService
        │
        ▼
AvailabilityPolicy
```

AvailabilityPolicy не должна зависеть от ReservationApplicationService.

## 18.4. Порядок проектирования

Точные Java package dependencies утверждаются вместе с сервисными контрактами.

Концептуальная схема не означает прямого импорта всех перечисленных модулей друг в друга.

# 19. Межмодульное взаимодействие

## 19.1. Основной механизм

По умолчанию используется синхронное взаимодействие через публичные интерфейсы.

## 19.2. Query-контракты

Предоставляют необходимые сведения.

Примеры:

- ServiceOfferingQuery;
- ScheduleQuery;
- OccupancyQuery;
- VerifiedOutcomeQuery;
- BookingObligationQuery.

## 19.3. Command-контракты

Выполняют разрешённые изменения.

Примеры:

- SpecialistModerationCommand;
- OutcomeResolutionCommand;
- административная отмена Reservation через Booking.

## 19.4. Передаваемые данные

Предпочтительно использовать:

- идентификаторы;
- immutable DTO;
- value objects;
- специализированные результаты.

## 19.5. Repository

Внешний модуль не должен напрямую работать с Repository владельца данных.

## 19.6. JPA

Не рекомендуется раскрывать изменяемые JPA Entity через межмодульные интерфейсы.

## 19.7. Транзакции

Публичные сервисные контракты должны учитывать транзакционный контекст вызывающей операции.

# 21. Транзакционная модель

## 21.1. База данных

Используется PostgreSQL.

## 21.2. Изоляция

Базовый уровень:

`READ COMMITTED`

## 21.3. Booking

Критические операции выполняются атомарно.

## 21.4. Occupancy

Пересечения защищаются GiST exclusion constraint.

## 21.5. Reservation

Конкурирующие изменения одной Reservation согласуются FOR UPDATE.

## 21.6. BookingAccess

Создание и подтверждение Reservation используют FOR SHARE.

Административное лишение допуска использует FOR UPDATE.

## 21.7. Schedule

Изменения расписания и создание Reservation используют календарные advisory locks.

## 21.8. TimeZoneGuard

Изменение ZoneId координируется отдельной строковой блокировкой.

## 21.9. Порядок

Все участвующие сервисы обязаны соблюдать согласованный порядок захвата ресурсов.

## 21.10. Проверка

Фактическое поведение блокировок должно подтверждаться интеграционными тестами PostgreSQL.

---

# 22. Событийное взаимодействие

## 22.1. Назначение

События могут использоваться для уведомлений и других производных операций.

## 22.2. Примеры

- ReservationCreated;
- ReservationCancelled;
- ReservationExpired;
- BookingConfirmed;
- BookingCancelled;
- SessionOutcomeResolved;
- ReviewCreated;
- SpecialistBlocked.

## 22.3. Транзакционная граница

Внешние сообщения не должны отправляться как подтверждённый результат до успешного COMMIT исходной операции.

## 22.4. Eventual consistency

Для Notification допускается eventual consistency.

## 22.5. Outbox

При необходимости гарантировать сохранение событий может использоваться transactional outbox.

## 22.6. Ограничение

Критические изменения Booking и Occupancy не должны выполняться через независимые асинхронные уведомления.

# 23. Архитектурные запреты

1. Не обращаться напрямую к Repository другого бизнес-модуля.
2. Не изменять чужие JPA Entity в обход владельца.
3. Не создавать циклические зависимости.
4. Не хранить AvailabilitySlot в целевой модели.
5. Не размещать ScheduleOccupancy в Availability.
6. Не переносить бизнес-правила в Common.
7. Не дублировать SpecialistBookingEligibility в каждом модуле.
8. Не создавать Booking напрямую из произвольного клиентского запроса.
9. Не считать BookingStatus достаточным доказательством проведения консультации.
10. Не определять Review eligibility только по статусу CONFIRMED Booking.
11. Не выполнять административную блокировку без обработки ACTIVE Reservation.
12. Не отменять автоматически CONFIRMED Booking при обычном изменении расписания.
13. Не переносить транзакционную согласованность Booking на Notification.
14. Не передавать изменяемые JPA-сущности через публичные межмодульные контракты.
15. Не внедрять микросервисы или message broker без обоснованной необходимости.

# 25. Открытые вопросы

## 25.1. Ownership конфигурации

Необходимо окончательно закрепить физическое размещение и сервисные контракты SpecialistBookingAccess, SpecialistBookingPolicy и SpecialistTimeZoneGuard.

## 25.2. AvailabilityPolicy

Требуется окончательно определить package ownership и расположение общей политики, используемой AvailabilityService и ReservationApplicationService.

## 25.3. Публичные контракты

Точные интерфейсы Query и Command уточняются при реализации соответствующих модулей.

## 25.4. Outcome

Требуется окончательно согласовать точный набор статусов и классов SessionOutcome.

## 25.5. Административный аудит

Необходимо согласовать границу persistence-модели SpecialistModerationAction между Admin и Specialist.

## 25.6. Текущая реализация

Нужна отдельная проверка текущего PsyWeb/main перед рефакторингом.

# 26. Итог

Модульная архитектура PsyWeb строится вокруг явного владения предметными данными.

Ключевые решения:

- Auth отвечает за аутентификацию;
- User управляет учётными записями;
- Client и Specialist расширяют пользовательскую модель;
- Service владеет ServiceOffering;
- Schedule хранит рабочее расписание;
- Availability вычисляет доступность;
- Booking владеет Reservation, Booking и ScheduleOccupancy;
- Outcome определяет результат консультации;
- Review управляет отзывами и рейтингом;
- Admin координирует административные операции;
- Notification отвечает за уведомления;
- Chat остаётся будущей функциональностью;
- Common содержит только действительно общие технические компоненты.

**Статус: DRAFT — целевые границы модулей определены, точные Java-контракты уточняются по мере реализации.**
