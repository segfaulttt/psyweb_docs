
**System Type:** Modular Monolith (Spring Boot)

---

# Overview

The system is divided into **business-oriented modules**, each owning a distinct part of the application's business model and lifecycle.

A business module may contain:

- API layer — controllers and API-specific models
- Service layer — use cases, business orchestration, and transaction boundaries
- Repository layer — persistence access owned by the module
- Domain model — entities, value objects, states, and domain rules

Not every module is required to contain every layer.

Modules communicate through explicit service-level boundaries and must not directly access repositories owned by other modules.

---

# High-Level Module Structure

```text
com.psyweb
│
├── auth
├── user
├── specialist
├── booking
├── availability
├── review
├── chat
├── notification
├── admin
└── common
```

The modules fall into two broad categories:

- **Business modules:** user, specialist, availability, booking, review, chat, notification, admin
- **Supporting modules:** auth, common

Business modules own business state and rules.

Supporting modules provide cross-cutting technical capabilities and must not become owners of unrelated business logic.

# 1. Auth Module

## Responsibility

Authentication/security is an approved target supporting module.

It is responsible for authenticating Users and integrating account identity with Spring Security without owning User or Specialist business state.

The current `PsyWeb/main` does not yet contain the final Auth module or JWT/Spring Security request infrastructure.

## Target Contains

- login orchestration;
- credential verification;
- password encoding;
- JWT generation and validation;
- Spring Security filters and configuration;
- authenticated-user context integration.

## Target Authentication Rules

Login requires:

```text
valid credentials
+
UserStatus.ACTIVE
```

A `BLOCKED` User cannot authenticate.

For a User with role:

```text
SPECIALIST
```

authentication is independent from `SpecialistStatus`.

An ACTIVE specialist may authenticate while the Specialist is:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Professional Specialist operations require the separate eligibility rule:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

The target JWT contains stable identity claims such as:

```text
userId
role
expiration
```

Mutable state such as `UserStatus` or `SpecialistStatus` must not be treated as durable authorization truth inside the token.

Protected requests must reload current account state where required so an old token cannot bypass later account blocking.

## Owns

Target Auth owns:

- authentication-specific orchestration;
- credential verification;
- token-related logic;
- security infrastructure.

## Depends on

- user.

Specialist professional eligibility may be evaluated through the appropriate Specialist boundary when a professional operation requires it.

## Does Not Own

- User entity lifecycle;
- UserRole;
- UserStatus;
- Specialist lifecycle;
- SpecialistStatus;
- professional eligibility state.

## Current vs Target

### Current

```text
UserRole
UserStatus.ACTIVE / BLOCKED
email normalization and lookup
SpecialistStatus
professional eligibility rules
```

### Target / backlog

```text
Auth module
login endpoint/service
password authentication flow
JWT generation and validation
JWT authentication filter
final Spring Security configuration
SecurityContext-based request authentication
```

# 3. Specialist Module

## Responsibility

Owns specialist-specific identity, professional state, lifecycle, and Specialist-level operational settings.

A Specialist extends the business capabilities of a User account with specialist-specific data.

Specialist is not a separate authentication identity.

`UserStatus` and `SpecialistStatus` represent separate concerns.

---

## Current Core Specialist

The current Specialist core contains:

- shared identity with User;
- first name;
- last name;
- `SpecialistStatus`;
- `minimumBookingNotice`;
- `clientCancellationNotice`;
- Specialist lifecycle validation;
- professional eligibility rules.

The current Java temporal settings use:

```text
java.time.Duration
```

and are persisted as whole integer minutes through the shared Duration converter.

---

## Specialist Status

The current enum is:

```text
SpecialistStatus
```

with values:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

A newly created Specialist starts in:

```text
PENDING
```

Current implemented transitions are:

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

Invalid transitions are rejected by the Specialist domain.

---

## Professional Eligibility

The current professional eligibility rule requires:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

`REJECTED` and `SUSPENDED` do not imply:

```text
UserStatus.BLOCKED
```

Account-level blocking and professional eligibility remain separate.

---

## Current Service Boundary

The current `SpecialistService` provides lifecycle operations for:

```text
approve
reject
resubmit
suspend
reinstate
```

The Specialist module owns the state transition itself.

Administrative workflows must request these transitions through the Specialist service boundary rather than directly modifying Specialist persistence.

---

## Target Suspension Orchestration

The Specialist state transition:

```text
APPROVED → SUSPENDED
```

is already implemented.

The complete administrative suspension use case is still target/backlog.

The target use case must additionally coordinate future availability and related active Reservation / confirmed Booking state consistently.

That orchestration must respect the approved temporal boundary:

```text
slot.startTime > suspendedAt
```

for future sessions.

The detailed Availability state-machine/service-boundary implementation remains owned by the dedicated Availability documentation work.

---

## Target Moderation History

Immutable moderation history is also target/backlog functionality.

The approved model uses:

```text
SpecialistModerationAction
```

for actions such as:

```text
APPROVED
REJECTED
RESUBMITTED
SUSPENDED
REINSTATED
```

Moderation reasons/history must not be stored by repeatedly overwriting a single field on Specialist.

---

## Separate Specialist Concerns

Public presentation and professional credential models remain separate from Specialist core.

### Public Profile

Future public-profile functionality may contain:

- biography or introduction;
- photos and media;
- presentation sections;
- configurable public-page content.

A generic `bio` field is not required in Specialist core.

### Professional Qualifications

Professional qualification models may contain:

- education;
- diplomas;
- retraining;
- additional qualifications;
- specializations.

Qualification verification is distinct from Specialist approval.

A credential verification state must not reuse `SpecialistStatus`.

---

## Owns

The Specialist module owns:

- Specialist entity lifecycle;
- SpecialistStatus;
- allowed lifecycle transitions;
- professional eligibility logic;
- Specialist-level temporal settings.

## Depends on

- user;
- common technical infrastructure where required.

## Does Not Own

- User account lifecycle;
- AvailabilitySlot lifecycle;
- Reservation lifecycle;
- Booking lifecycle;
- Review lifecycle;
- administrative orchestration.

## Does Not Depend on

- admin.

The Specialist module exposes lifecycle operations that administrative use cases may invoke without creating a reverse dependency on Admin.

# 5. Booking Module

## Responsibility

Owns the current Reservation and Booking lifecycle and coordinates booking-related operations across User, Specialist, and Availability boundaries.

The module does not take ownership of entities belonging to those other modules.

---

## Current Contains

The current `PsyWeb/main` contains:

```text
Reservation
ReservationStatus
Booking
BookingStatus
ReservationProperties
ReservationExpirationScheduler
ReservationRepository
BookingRepository
ReservationService
BookingService
```

Current functionality includes:

- temporary Reservation creation;
- Reservation TTL and `expiresAt`;
- Reservation cancellation;
- Reservation expiration;
- scheduled cleanup of overdue Reservations;
- Reservation confirmation;
- Booking creation;
- Booking cancellation;
- pessimistic Reservation locking;
- expiration batching with PostgreSQL `FOR UPDATE SKIP LOCKED`;
- database protection against multiple ACTIVE Reservations for one Slot;
- controlled time through injected `Clock`.

---

## Current Ownership

The Booking module currently owns:

- Reservation lifecycle;
- Booking lifecycle;
- Reservation TTL configuration;
- Reservation expiration processing;
- booking-related transactional orchestration.

It coordinates AvailabilitySlot changes through the Availability module boundary.

It does not own AvailabilitySlot lifecycle or persistence.

---

This post-session model is not yet implemented in the current `PsyWeb/main`.

Its presence in the architecture describes target/backlog state.

---

# 9. Admin Module

## Responsibility

Admin is the approved application-level orchestration boundary for administrative use cases across business modules.

It does not own copies of entities belonging to User, Specialist, Booking, Availability, or other domains.

The current `PsyWeb/main` does not yet contain a dedicated Admin application module/service/controller implementation.

Therefore, the Admin module described here is primarily target/backlog architecture.

---

## Target Responsibilities

Administrative use cases include:

- Specialist approval/rejection orchestration;
- Specialist suspension/reinstatement orchestration;
- User moderation;
- administrative queries;
- future SessionOutcome dispute resolution;
- other platform-management workflows that require ADMIN authority.

---

## Specialist Moderation Boundary

The Admin layer may initiate:

```text
PENDING → APPROVED
PENDING → REJECTED
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

but the Specialist state transition itself belongs to:

```text
SpecialistService
```

Resubmission:

```text
REJECTED → PENDING
```

is also owned by the Specialist lifecycle rather than direct Admin persistence access.

The Admin module must not directly mutate:

```text
Specialist.approvalStatus
```

or access `SpecialistRepository` as a shortcut around the owning service boundary.

---

## Target Moderation History

When immutable Specialist moderation history is implemented, the administrative moderation use case will also persist:

```text
SpecialistModerationAction
```

according to the approved moderation contract.

This is target/backlog functionality.

---

## Target Session Disputes

When the SessionOutcome model is implemented, Admin participates only in genuine:

```text
DISPUTED
```

outcomes.

The administrative use case creates:

```text
DisputeResolution
```

through the owning Session/Booking business boundary.

Admin must not rewrite original SessionReports or directly manipulate SessionOutcome persistence.

This flow is also target/backlog functionality.

---

## Depends on

Target Admin orchestration may depend on:

- user;
- specialist;
- booking/session functionality;
- other modules only when required by a concrete administrative use case.

## Does Not Own

- User;
- Specialist;
- AvailabilitySlot;
- Reservation;
- Booking;
- SessionOutcome;
- other domain entities owned by their respective modules.

## Current vs Target

### Current

```text
SpecialistService lifecycle operations exist.
No dedicated Admin application module is implemented.
```

### Target / backlog

```text
ADMIN-authenticated orchestration endpoints/services
Specialist moderation orchestration
immutable moderation history
suspension cascade coordination
SessionOutcome dispute resolution
```

# 10. Common Module

## Responsibility

Contains a minimal set of technical components that are genuinely shared across multiple modules and do not belong to a specific business domain.

## May Contain

- shared technical exceptions
- generic infrastructure utilities
- cross-cutting technical abstractions

## Must Not Contain

- business entities
- domain-specific business rules
- module-specific DTOs
- repositories
- services belonging to a business domain
- constants that logically belong to a specific module

The Common module should remain small. Code should not be moved to Common merely because it is used in more than one place.

---

# Dependency Rules

## General Rule

A module owns its domain model, persistence, and lifecycle rules.

Other modules may use the owning module through explicit service-level boundaries but must not bypass those boundaries to modify its state.

---

## Allowed

- calling another module's public service API
- referencing another module's domain identity when required by the business model
- using minimal shared technical components from Common
- orchestrating several modules inside a transactional business use case where required

---

## Forbidden

- direct access to another module's repository
- direct modification of another module's entities
- circular module dependencies
- placing domain logic in controllers
- moving business logic to Common to avoid defining a proper module boundary
- duplicating another module's business state

---

## Dependency Direction

Current core dependency direction should remain acyclic:

```text
user

specialist
└── user

availability
└── specialist

booking
├── user
├── specialist
└── availability

admin
├── user
└── specialist

review
├── user
├── specialist
└── booking

# Inter-Module Communication

The default communication mechanism inside the modular monolith is synchronous service-level interaction.

Domain or application events may be introduced later for workflows that benefit from decoupled processing, such as notifications.

Events should not be introduced merely to avoid normal synchronous service calls.

Cross-module communication must preserve module ownership rules regardless of the communication mechanism.

---

# Future Evolution

The module boundaries are intended to make future architectural changes easier without requiring them prematurely.

Possible future evolution includes:

- extracting Booking if it develops independent scaling or operational requirements
- implementing Chat as a dedicated real-time component
- moving Notification delivery to asynchronous processing

Extraction into separate services would still require explicit changes to communication, transaction boundaries, deployment, and data ownership. The modular monolith is not treated as a temporary architecture that must eventually become microservices.

---

# Architectural Goals

This module structure is designed to:

- make business ownership explicit
- preserve clear domain boundaries
- prevent accidental cross-module persistence access
- reduce coupling and circular dependencies
- keep transaction orchestration understandable
- support isolated testing of business modules
- allow the architecture to evolve without premature distribution
