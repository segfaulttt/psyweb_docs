
**System Name:** PsyWeb (Working Title)

**Architecture Style:** Modular Monolith (MVP Stage)

---

# Overview

The system is designed as a **modular monolith backend application** built with Spring Boot.

It will later allow optional migration to microservices if scaling requires it.

---

# Core Idea

The platform connects:

- Clients (who search and book specialists)
- Specialists (who provide consultations)
- Administrators (who manage and moderate the system)

---

# Key Domains

The system is divided into the following core domains:

## 1. User Management Domain
Handles:
- registration
- authentication
- roles
- account status

---

## 2. Specialist Domain
Handles:
- specialist profiles
- services
- availability slots
- approval workflow

---

## 3. Booking Domain
Handles:
- appointment creation
- cancellation
- conflict prevention
- slot reservation

---

## 4. Communication Domain
Handles:
- chat between users
- messaging rules
- optional communication layer

---

## 5. Review Domain
Handles:
- rating system
- feedback after appointments
- specialist reputation

---

## 6. Administration Domain
Handles:
- specialist approval
- moderation
- user management
- system oversight

---

# Architecture Principles

## 1. Modular Separation

Each domain is isolated inside its own module:
- domain logic is independent
- minimal cross-module coupling

---

## 2. Transaction Safety

Critical operations (like booking) must be:
- atomic
- consistent
- isolated from concurrent requests

---

## 3. Database-Centric Consistency

PostgreSQL is the source of truth:
- constraints enforce integrity
- transactions ensure correctness

---

## 4. Stateless Backend

Application layer is stateless:
- session handled via JWT
- scalability friendly

---

## 5. API-First Design

All features exposed via REST API:
- documented via OpenAPI
- consumed by frontend/mobile clients

---

# Technology Assumptions

- Java 17+
- Spring Boot
- Spring Security (JWT-based auth)
- PostgreSQL
- Flyway (migrations)
- Docker (containerization)
- OpenAPI (Swagger)

---

# Scalability Direction (Future)

The system is designed so that:

- Booking domain can be extracted into microservice
- Chat can become separate real-time service
- Notification system can become async service (Kafka/RabbitMQ)

---

# Notes

This architecture prioritizes:

- correctness
- simplicity
- maintainability

over premature microservices complexity.
