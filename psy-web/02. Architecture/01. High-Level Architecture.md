
# 01. Высокоуровневая архитектура PsyWeb (High-Level Architecture)

**Проект:** PsyWeb  
**Архитектурный стиль:** Modular Monolith  
**Backend:** Java 21, Spring Boot  
**База данных:** PostgreSQL  
**Миграции:** Flyway  
**Статус:** DRAFT — целевая архитектура MVP

# 2. Общее описание системы

PsyWeb — платформа для организации консультаций между клиентами и специалистами.

Платформа объединяет три основные категории пользователей:

- **Клиенты** — находят специалистов, выбирают услуги и записываются на консультации.
- **Специалисты** — предоставляют услуги, управляют собственным расписанием и взаимодействуют с клиентами.
- **Администраторы** — модерируют платформу, управляют административными ограничениями и разрешают предусмотренные системой спорные ситуации.

Основной бизнес-процесс:

```text
Клиент выбирает специалиста
    ↓
Выбирает услугу
    ↓
Просматривает доступное время
    ↓
Создаёт временную Reservation
    ↓
Подтверждает запись
    ↓
Создаётся Booking
    ↓
Проводится консультация
    ↓
Участники сообщают результат
    ↓
Формируется SessionOutcome
    ↓
При подтверждённом успешном результате
клиент может оставить Review
```

Платформа должна обеспечивать корректность записи на консультации даже при одновременных запросах нескольких клиентов.

# 3. Архитектурный стиль

## 3.1. Модульный монолит

Для MVP выбран Modular Monolith.

Приложение разрабатывается как единый Spring Boot backend, разделённый на логические бизнес-модули.

Каждый модуль имеет:

- определённую ответственность;
- собственную предметную модель;
- собственные бизнес-правила;
- собственные компоненты хранения;
- явно определённые контракты взаимодействия.

## 3.2. Причины выбора

Модульный монолит позволяет:

- упростить первоначальную разработку;
- сохранить единую транзакционную модель;
- избежать распределённых транзакций;
- снизить инфраструктурную сложность;
- сохранить явные границы предметных областей;
- обеспечить удобное локальное тестирование;
- развивать функциональность поэтапно.

## 3.3. Отличие от обычного монолита

Модульность не должна ограничиваться распределением Java-классов по пакетам.

Необходимо соблюдать границы владения.

Например, Booking не должен напрямую изменять таблицы Schedule через чужие Repository.

## 3.4. Отличие от микросервисов

Для MVP не требуются:

- отдельная база данных на каждый модуль;
- независимый деплой модулей;
- распределённые транзакции;
- API Gateway для внутренних вызовов;
- обязательный message broker.

Выделение модулей в отдельные сервисы может рассматриваться позднее при наличии конкретных требований.

# 4. Общая структура backend

Целевая структура:

```text
PsyWeb Backend
│
├── Auth / Security
│
├── User
│
├── Client
│
├── Specialist
│
├── Service
│
├── Schedule
│
├── Availability
│
├── Booking
│   ├── Reservation
│   ├── Booking
│   └── ScheduleOccupancy
│
├── Outcome
│
├── Review
│
├── Notification
│
├── Admin
│
├── Communication (future)
│
└── Common
```

Это логическая схема ответственности, а не обязательное точное дерево Java-пакетов.

Физическая структура определяется в Module Architecture.

# 5. User Domain

## 5.1. Назначение

User отвечает за учётные записи пользователей платформы.

## 5.2. Ответственность

Модуль владеет:

- User;
- UserRole;
- UserStatus;
- email;
- passwordHash;
- состоянием учётной записи;
- базовыми правилами жизненного цикла User.

## 5.3. Роли

Для MVP предусмотрены:

- CLIENT;
- SPECIALIST;
- ADMIN.

## 5.4. Состояние аккаунта

В существующей реализации используются:

- ACTIVE;
- BLOCKED.

Дополнительные состояния должны вводиться только после отдельного согласования.

## 5.5. Граница ответственности

User не выполняет аутентификацию JWT самостоятельно.

Auth использует User для проверки учётных данных и актуального состояния аккаунта.

---

# 6. Client Domain

## 6.1. Назначение

Client представляет клиентскую часть пользовательской модели.

## 6.2. Ответственность

Модуль хранит сведения о клиенте, необходимые для работы платформы.

## 6.3. Связь с User

Client связан с User.

User отвечает за общую учётную запись.

Client отвечает за клиентский профиль и клиентскую предметную информацию.

## 6.4. Границы

Client не управляет Reservation и Booking непосредственно.

Соответствующие операции принадлежат Booking Domain.

---

# 7. Specialist Domain

## 7.1. Назначение

Specialist представляет профессиональную часть пользовательской модели.

## 7.2. Основная модель

Specialist содержит:

- идентичность специалиста;
- необходимую профильную информацию;
- модерационный статус;
- данные, необходимые для связи со связанными бизнес-модулями.

## 7.3. Модерация

В существующей реализации используются состояния:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

В целевой архитектуре модерационное состояние обозначается как:

`Specialist.approvalStatus`

## 7.4. Профессиональный допуск

Одобренный специалист должен иметь:

- UserRole.SPECIALIST;
- UserStatus.ACTIVE;
- approvalStatus.APPROVED.

## 7.5. Отдельный допуск к бронированию

Профессиональный допуск не заменяет административное разрешение принимать записи.

Для новых Reservation и их подтверждения дополнительно требуется:

`SpecialistBookingAccess.bookingAllowed = TRUE`

## 7.6. Разделение данных

Настройки бронирования, расписания и часового пояса могут храниться в самостоятельных конфигурационных моделях.

Это позволяет независимо обновлять и блокировать разные группы данных.

## 7.7. Владение

Specialist не владеет:

- ScheduleOccupancy;
- Reservation;
- Booking;
- результатами консультаций.

---

# 8. Публичный профиль специалиста

## 8.1. Отдельная ответственность

Публичное представление специалиста отделяется от его базовой идентичности.

## 8.2. Возможное содержимое

В будущем публичный профиль может содержать:

- биографию;
- фотографию;
- презентационные материалы;
- описание подхода к работе;
- дополнительные разделы страницы;
- другую информацию, предназначенную для клиентов.

## 8.3. Граница MVP

Полноценный конструктор публичной страницы не является обязательной частью MVP.

## 8.4. Архитектурное правило

Расширение публичного профиля не должно требовать переработки идентичности Specialist или жизненного цикла Booking.

---

# 9. Образование и квалификация специалиста

## 9.1. Отдельная предметная область

Профессиональные документы и подтверждение квалификации не должны смешиваться с базовой сущностью Specialist.

## 9.2. Возможные данные

- высшее образование;
- дипломы;
- переподготовка;
- дополнительная квалификация;
- специализации;
- подтверждающие документы;
- результаты проверки.

## 9.3. Верификация

Проверка отдельных документов не должна заменяться одним универсальным булевым полем verified у Specialist.

## 9.4. Граница MVP

Полноценная система документов и квалификаций может развиваться отдельно.

Однако административное одобрение специалиста остаётся обязательной частью его допуска к профессиональной деятельности.

---

# 10. Service Domain

## 10.1. Назначение

Service отвечает за услуги, предлагаемые специалистами.

## 10.2. Основная сущность

`ServiceOffering`

## 10.3. Данные услуги

Услуга определяет:

- название;
- описание;
- длительность консультации;
- длительность перерыва;
- стоимость;
- валюту;
- активность.

## 10.4. Выбор услуги

Клиент сначала выбирает конкретную ServiceOffering.

После этого система рассчитывает доступные начала консультаций.

## 10.5. Исторические условия

Изменение услуги не должно менять условия уже созданных Reservation и Booking.

Для этого используется snapshot.

## 10.6. Граница ответственности

Service не владеет календарной занятостью и не создаёт Reservation.

---

# 11. Schedule Domain

## 11.1. Назначение

Schedule управляет правилами рабочего времени специалиста.

## 11.2. Режимы

Поддерживаются:

- REGULAR;
- FLOATING.

## 11.3. REGULAR

Регулярное расписание формируется из версий недельного шаблона.

Основные объекты:

- WeeklyScheduleVersion;
- WeeklyWorkingInterval.

## 11.4. FLOATING

Плавающее расписание задаётся отдельно для конкретных дат.

Используется:

- DateSchedule;
- DateScheduleInterval.

## 11.5. Исключения из расписания

В режиме REGULAR конкретная дата может переопределять недельный шаблон через OVERRIDE.

## 11.6. Сохранение конфигурации

При переключении режима данные неактивного расписания сохраняются.

## 11.7. Изменение графика

Обычные изменения расписания не отменяют автоматически:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 11.8. Граница ответственности

Schedule владеет правилами рабочего времени, но не статусами Reservation или Booking.

---

# 12. Availability Domain

## 12.1. Назначение

Availability вычисляет возможные начала консультаций.

## 12.2. Динамическая модель

Доступность не хранится в виде заранее созданных AvailabilitySlot.

Она рассчитывается на основании:

- ServiceOffering;
- рабочего расписания;
- временных ограничений;
- ZoneId специалиста;
- существующей ScheduleOccupancy;
- эффективного допуска специалиста.

## 12.3. Результат

AvailabilityService возвращает предварительный список возможных начал.

## 12.4. Отсутствие удержания

Получение Availability не создаёт Reservation.

## 12.5. Конкурентность

Два клиента могут одновременно увидеть одинаковое доступное время.

## 12.6. Окончательная проверка

Окончательное решение о возможности занять интервал принимает сценарий создания Reservation.

## 12.7. Граница ответственности

Availability не владеет Reservation, Booking или ScheduleOccupancy.

---

# 13. Booking Domain

## 13.1. Назначение

Booking является транзакционным ядром платформы.

## 13.2. Основные объекты

- Reservation;
- Booking;
- ScheduleOccupancy.

## 13.3. Reservation

Reservation представляет временное удержание выбранного времени.

Она имеет собственный TTL.

## 13.4. Booking

Booking представляет подтверждённую запись на консультацию.

## 13.5. ScheduleOccupancy

ScheduleOccupancy представляет действующую занятость времени специалиста.

## 13.6. Создание Reservation

При успешной операции атомарно создаются:

- ACTIVE Reservation;
- ScheduleOccupancy.

## 13.7. Подтверждение

При подтверждении:

- Reservation переходит в CONFIRMED;
- создаётся Booking;
- Occupancy сохраняется.

## 13.8. Отмена и истечение

При отмене или истечении ACTIVE Reservation Occupancy удаляется.

## 13.9. Отмена Booking

Допустимая отмена CONFIRMED Booking освобождает Occupancy.

## 13.10. История

Reservation и Booking сохраняются как исторические данные.

## 13.11. Конкурентность

Booking использует транзакции PostgreSQL, строковые блокировки и согласованную календарную координацию.

## 13.12. Граница ответственности

Booking не определяет самостоятельно рабочее расписание и не устанавливает факт успешного проведения консультации.

---

# 14. Outcome Domain

## 14.1. Назначение

Outcome определяет результат проведения консультации.

## 14.2. Независимость от Booking

BookingStatus не должен использоваться как единственный источник истины о фактическом проведении консультации.

## 14.3. Отчёты участников

Клиент и специалист независимо сообщают, состоялась ли консультация.

## 14.4. Окно

Для MVP предусмотрено 24 часа после завершения консультации.

## 14.5. Автоматическое разрешение

Совместимые результаты разрешаются по утверждённым правилам.

## 14.6. Споры

Противоречивые результаты передаются администратору.

## 14.7. Отсутствие подтверждения

Если ни одна сторона не ответила, консультация не считается автоматически успешно проведённой.

## 14.8. Связь с Review

Подтверждённо успешный SessionOutcome создаёт основание для Review.

---

# 15. Review Domain

## 15.1. Назначение

Review отвечает за отзывы клиентов о специалистах.

## 15.2. Основное правило

Один клиент может иметь только один Review на одного специалиста.

## 15.3. Условия создания

Для первоначального создания Review требуется хотя бы одна подтверждённо успешная консультация этой пары.

## 15.4. Редактирование

Клиент может редактировать оценку и комментарий.

## 15.5. Рейтинг

Агрегированный рейтинг рассчитывается по актуальным Review.

## 15.6. Граница ответственности

Review не определяет исход консультации и не изменяет Booking.

---

# 16. Admin Domain

## 16.1. Назначение

Admin отвечает за административные операции платформы.

## 16.2. Основные возможности

- модерация специалистов;
- блокировка пользователей;
- управление административным допуском;
- разрешение споров;
- аудит;
- предусмотренные исключительные операции.

## 16.3. Транзакционная блокировка специалиста

При административной потере допуска:

- запрещаются новые Reservation;
- все ACTIVE Reservation специалиста отменяются;
- их Occupancy удаляются;
- CONFIRMED Booking сохраняются.

## 16.4. Атомарность

Изменение допуска и обязательные отмены выполняются в одной транзакции.

## 16.5. Разрешение споров

Admin рассматривает спорные SessionOutcome через контракт Outcome.

## 16.6. Граница ответственности

Admin не должен напрямую изменять Repository других модулей в обход их бизнес-правил.

---

# 17. Notification Domain

## 17.1. Назначение

Notification информирует пользователей о значимых событиях платформы.

## 17.2. Возможные события

- подтверждение Booking;
- отмена Booking;
- истечение Reservation;
- изменение административного статуса;
- разрешение SessionOutcome;
- создание Review.

## 17.3. Независимость

Ошибка внешней доставки уведомления не должна отменять успешную бизнес-операцию.

## 17.4. Модель

Notification может хранить внутриплатформенные уведомления.

Внешняя доставка через email и другие каналы может развиваться отдельно.

## 17.5. Асинхронность

Допускается асинхронная обработка событий после успешной фиксации основного бизнес-состояния.

## 17.6. Message broker

Kafka и RabbitMQ не являются обязательными для MVP.

---

# 18. Communication Domain

## 18.1. Статус

Будущая функциональность.

## 18.2. Возможности

- чат клиента и специалиста;
- отправка сообщений;
- правила доступа;
- интеграция с Notification.

## 18.3. Архитектурное разделение

Communication не должен определять состояние Booking или результат SessionOutcome.

## 18.4. Развитие

Для сообщений в реальном времени в будущем могут использоваться WebSocket или другие подходящие технологии.

---

# 19. Common Module

## 19.1. Назначение

Common содержит небольшие переиспользуемые технические компоненты.

## 19.2. Возможное содержимое

- базовые исключения;
- универсальные DTO;
- технические утилиты;
- общие инфраструктурные контракты.

## 19.3. Ограничения

Common не должен содержать:

- бизнес-политики Booking;
- правила Schedule;
- логику Review;
- Repository бизнес-модулей;
- межмодульную оркестрацию.

## 19.4. Направление зависимостей

Бизнес-модули могут использовать Common.

Common не зависит от бизнес-модулей.

---

# 20. Взаимодействие модулей

## 20.1. Принцип

Модули взаимодействуют через явные сервисные контракты.

## 20.2. Пример Reservation

```text
ReservationApplicationService
    │
    ├── ServiceOfferingQuery
    │
    ├── SpecialistBookingEligibility
    │
    ├── BookingPolicy
    │
    ├── ScheduleQuery
    │
    ├── AvailabilityPolicy
    │
    └── Booking persistence
          ├── Reservation
          └── ScheduleOccupancy
```

## 20.3. Пример Outcome

```text
Outcome Application Service
    │
    ├── Booking participant data
    │
    ├── SessionOutcome
    │
    └── OutcomeResolutionPolicy
```

## 20.4. Пример Review

```text
ReviewService
    │
    ├── Authenticated client
    │
    ├── VerifiedOutcomeQuery
    │
    └── Review persistence
```

## 20.5. Запреты

Модуль не должен:

- напрямую изменять чужие JPA-сущности;
- использовать чужой Repository как обход контракта;
- создавать скрытые циклические зависимости;
- копировать бизнес-правила другого модуля без необходимости.

# 21. Транзакционная согласованность

## 21.1. Основной принцип

Критические бизнес-операции должны быть атомарными.

## 21.2. Создание Reservation

Reservation и ScheduleOccupancy создаются в одной транзакции.

## 21.3. Подтверждение

Переход Reservation и создание Booking происходят атомарно.

## 21.4. Отмена

Отмена Reservation или Booking и освобождение Occupancy выполняются согласованно.

## 21.5. Административная блокировка

Потеря допуска специалиста и отмена ACTIVE Reservation выполняются атомарно.

## 21.6. PostgreSQL

PostgreSQL является источником истины для сохранённых состояний и ограничений целостности.

## 21.7. Защита конкурентности

Используются:

- row locks;
- transaction-level advisory locks;
- UNIQUE;
- CHECK;
- FOREIGN KEY;
- exclusion constraints.

Подробности определяются в Transaction and Concurrency Model.

# 22. Работа со временем

## 22.1. Абсолютное время

Reservation и Booking используют абсолютные временные значения.

## 22.2. Локальное расписание

Рабочий график определяется через LocalDate, LocalTime и ZoneId.

## 22.3. DST

Для новых консультаций запрещаются неоднозначные и несуществующие локальные начала.

## 22.4. Изменение часового пояса

Смена ZoneId специалиста не изменяет уже сохранённые абсолютные времена консультаций.

## 22.5. Открытые вопросы

Правила консультаций, пересекающих DST-переход, требуют отдельного согласования.

# 23. Аутентификация

## 23.1. Целевая модель

Для MVP выбрана stateless JWT authentication.

## 23.2. Основные компоненты

- Spring Security;
- JWT;
- AuthService;
- Authentication;
- SecurityContext.

## 23.3. Состояние пользователя

Защищённые запросы должны учитывать актуальный UserStatus.

## 23.4. Разделение

Authentication определяет личность пользователя.

Authorization определяет его право на операцию.

Исходная документация отмечает, что полноценная JWT-инфраструктура ещё не была реализована.

Фактическое состояние необходимо проверять по текущему исходному коду PsyWeb.

# 28. Эволюция архитектуры

## 28.1. Принцип

PsyWeb должен оставаться модульным монолитом, пока нет объективной необходимости усложнять инфраструктуру.

## 28.2. Возможное выделение Booking

При существенном росте нагрузки Booking может стать кандидатом на выделение в самостоятельный сервис.

Однако это потребует нового решения о межсервисной согласованности.

## 28.3. Communication

Чат может развиваться как отдельный компонент с поддержкой real-time communication.

## 28.4. Notification

Доставка уведомлений может использовать асинхронную обработку.

## 28.5. Message broker

Kafka или RabbitMQ могут быть добавлены при наличии подтверждённой необходимости.

## 28.6. Дополнительные возможности

В будущем могут появиться:

- платежи;
- видеоконсультации;
- аналитика;
- интеграции с календарями;
- расширенная система профессиональных документов.

Эти возможности не должны преждевременно усложнять MVP.

# 29. Архитектурные приоритеты

Приоритеты PsyWeb:

1. Корректность бизнес-состояния.
2. Целостность данных.
3. Защита конкурентных операций.
4. Явное владение данными.
5. Поддерживаемость.
6. Простота.
7. Тестируемость.
8. Возможность развития.

Архитектура намеренно избегает:

- преждевременного разделения на микросервисы;
- неоправданной инфраструктурной сложности;
- неявных межмодульных зависимостей;
- дублирования бизнес-состояний;
- избыточных общих абстракций.

# 30. Итог

PsyWeb реализуется как модульный монолит на Spring Boot с PostgreSQL.

Основные архитектурные решения:

- бизнес-модули имеют явные границы владения;
- User, Client и Specialist разделяют ответственность за пользовательские данные;
- публичный профиль и квалификации отделены от базовой модели Specialist;
- ServiceOffering определяет условия консультации;
- Schedule хранит рабочее расписание;
- Availability рассчитывается динамически;
- Booking владеет Reservation, Booking и ScheduleOccupancy;
- PostgreSQL защищает критические ограничения;
- SessionOutcome отдельно определяет факт проведения консультации;
- Review разрешён после подтверждённо успешной консультации;
- Admin координирует административные операции;
- Notification обрабатывает производные события;
- JWT и REST API являются целевой архитектурой;
- модульный монолит остаётся основным архитектурным стилем MVP.

**Статус: DRAFT — целевая архитектура согласована, её реализация выполняется поэтапно.**
