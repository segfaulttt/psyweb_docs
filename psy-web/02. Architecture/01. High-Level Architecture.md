
**System Name:** PsyWeb (Working Title)

**Architecture Style:** Modular Monolith (MVP Stage)

---

# Overview

PsyWeb is designed as a **modular monolith backend application** built with Spring Boot.

The system is organized around business modules with explicit boundaries and minimal coupling between them.

The modular monolith architecture is used for the MVP to keep development, deployment, and transactional consistency simple while preserving the possibility of extracting individual modules into separate services later if scaling or operational requirements justify it.

---

# Core Idea

The platform connects:

- Clients, who search for specialists, reserve available time slots, and book consultations
- Specialists, who provide consultations and manage their professional presence and availability
- Administrators, who moderate specialists, users, and platform operations

---

# Key Domains

The system is divided into the following business domains.

## 1. User Domain

Handles:

- user accounts
- roles
- account status
- account-level lifecycle

Authentication uses User data but is handled by a separate authentication/security component.

---

## 2. Specialist Domain

The Specialist domain owns the specialist-specific extension of a User account.

### Core Specialist Scope

The core Specialist model contains:

- specialist identity data required by the platform;
- specialist approval status and approval lifecycle;
- specialist-level operational settings required by core workflows.

The core Specialist model does not represent the entire public-facing specialist page.

### Public Profile

Public-facing presentation is a separate concern from Specialist core identity.

A future public profile model may contain:

- biography or introductory text;
- profile photo and media;
- presentation-oriented sections;
- configurable public page content;
- other information intended primarily for client-facing presentation.

A generic `bio` field is not considered part of the required Specialist core model.

A future page builder or richer profile constructor is optional product scope and is not required for the MVP architecture.

### Professional Qualifications and Verification

Professional credentials are also modeled separately from core Specialist identity.

This concern may include:

- higher education records;
- diplomas and supporting documents;
- professional retraining;
- additional qualifications;
- specializations;
- verification state for submitted credentials.

Qualification and document verification must not be represented by a single generic `verified` flag on the Specialist core entity.

### MVP Boundary

For the MVP, Specialist core requires:

- specialist identity;
- approval state;
- fields and settings required by booking and availability workflows.

Public profile composition, rich page customization, and the complete professional qualifications subsystem may evolve separately without changing the identity of the Specialist core entity.

The Specialist domain does not own scheduling or booking state.

---

## 3. Availability Domain

Handles:

- specialist availability slots
- slot lifecycle
- availability state changes
- schedule conflict prevention

The Availability domain owns the state of specialist time slots.

Other modules must not modify availability entities directly.

---

## 4. Booking Domain

The current Booking domain implements:

- temporary Reservation creation;
- Reservation TTL and expiration;
- automatic expiration cleanup;
- Reservation confirmation;
- Booking creation;
- Booking cancellation;
- Reservation and Booking concurrency protection;
- coordination of AvailabilitySlot reservation and release.

Reservation and Booking are separate domain concepts:

- Reservation temporarily holds a slot before booking confirmation;
- Booking represents a confirmed consultation.

Post-session attendance and session-result processing are designed as a separate target model based on:

```text
SessionOutcome
SessionReport
DisputeResolution
```

That post-session model is approved architecture but is not yet implemented in the current `PsyWeb/main`.

---

## 5. Communication Domain

Handles:

- chat between users
- messaging rules
- communication-related access rules

This domain may be implemented after the MVP booking core is complete.

---

## 6. Review Domain

Handles:

- ratings
- feedback after consultations
- specialist reputation

---

## 7. Administration Domain

Handles:

- specialist moderation and approval workflows
- user moderation
- administrative operations
- platform oversight

Administration orchestrates administrative use cases but does not own User or Specialist persistence directly.

---

## 8. Notification Domain

Handles:

- system notifications
- booking-related notifications
- reminder delivery

The initial implementation may remain synchronous or minimal and can evolve to asynchronous processing later if required.

# Architecture Principles

## 1. Modular Separation

Each business domain is isolated inside its own module.

Modules should:

- own their domain entities and business rules
- expose operations through service boundaries
- avoid direct access to repositories owned by other modules
- avoid direct modification of entities owned by other modules
- keep cross-module dependencies explicit and minimal
- avoid circular dependencies

Cross-module collaboration should happen through service-level APIs rather than direct persistence access.

---

## 2. Transaction Safety

Critical business operations must preserve consistency across all affected state changes.

Operations such as reservation creation, reservation confirmation, booking creation, cancellation, and slot state transitions must be:

- atomic
- transactionally consistent
- protected against concurrent conflicts
- designed so that partial state changes cannot remain persisted

Transaction boundaries belong primarily to service-level business operations.

---

## 3. Database-Centric Consistency

PostgreSQL is the persistent source of truth for critical data integrity.

The database should enforce business-critical invariants where practical through:

- primary and foreign keys
- unique constraints
- check constraints
- indexes
- transactional guarantees

Application-level validation improves error handling and expresses business rules, but it must not be the only protection against concurrency-related integrity violations.

---

## 4. Stateless Authentication

Stateless JWT authentication is the approved target authentication architecture.

The target flow uses:

```text
Spring Security
JWT access token
no server-side authenticated HTTP session
```

However, the current `PsyWeb/main` does not yet contain the final authentication/security infrastructure:

```text
AuthController
login service
JWT generation/validation
JWT authentication filter
final Spring Security configuration
```

The current backend already contains the account and professional-state rules that the future authentication layer must use, including:

```text
UserStatus.ACTIVE / BLOCKED
SpecialistStatus
Specialist professional eligibility
canonical email normalization
```

Therefore JWT/Spring Security behavior in architecture documentation must be read as target state until the corresponding authentication implementation is added.

---

## 5. API-Oriented Backend

REST is the target client-facing API architecture.

The intended API layer should:

- remain thin;
- delegate business operations to services;
- avoid containing domain logic;
- use explicit request and response models;
- be documented through OpenAPI where applicable.

The current backend is still primarily domain/service/persistence implementation and does not yet contain the complete final REST/controller surface.

The backend may later expose non-REST interfaces for features where REST is not the best fit, such as real-time communication.

---

## 6. Domain Ownership

Each business entity has a single owning module.

For example:

- User is owned by the User domain
- Specialist is owned by the Specialist domain
- AvailabilitySlot is owned by the Availability domain
- Reservation and Booking are owned by the Booking domain

A module may reference entities from another domain when necessary, but lifecycle changes to those entities should be performed through the owning module's service boundary.

---

## 7. Explicit Business State

Independent business concerns must use independent state models.

For example:

- account state belongs to User
- specialist approval state belongs to Specialist
- slot availability state belongs to Availability
- reservation state belongs to Reservation
- booking state belongs to Booking

These states must not be merged into a single generic status model.

# Technology Stack

Current backend foundations include:

- Java;
- Spring Boot;
- Spring Data JPA;
- PostgreSQL;
- Flyway;
- JUnit 5;
- Mockito;
- Testcontainers.

Approved target/API infrastructure additionally includes:

- Spring Security;
- JWT-based stateless authentication;
- REST controllers;
- OpenAPI / Swagger where API documentation is introduced.

Target infrastructure must not be interpreted as already implemented merely because it is part of the selected architecture.

---

# Evolution Direction

The modular structure allows individual parts of the system to evolve independently if future requirements justify it.

Possible future directions include:

- extracting Booking into a separate service if booking load or scaling requirements become substantially different from the rest of the platform
- implementing Communication as a dedicated real-time component
- moving Notification delivery to asynchronous processing
- introducing a message broker if reliable asynchronous communication becomes necessary

These changes are not part of the MVP architecture and should only be introduced when supported by concrete product or operational requirements.

---

# Architectural Priorities

The architecture prioritizes:

1. correctness of business state
2. data integrity
3. clear module ownership
4. maintainability
5. simplicity
6. testability

The system intentionally avoids premature distribution, unnecessary abstractions, and infrastructure complexity that is not justified by current requirements.
