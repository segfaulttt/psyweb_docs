# 1. Назначение

Документ фиксирует состояние основных security-механизмов PsyWeb на основании текущего backend-кода.

Задачи документа:

- отделить реализованные механизмы от целевой архитектуры;
- указать основные классы и конфигурации;
- выявить очевидные незавершённые направления;
- предоставить точку входа для дальнейшей проверки безопасности.

Документ не является результатом penetration testing, OWASP audit или подтверждением production readiness.

Подробные архитектурные решения описаны в:

- `04. Backend/04. Authentication Flow.md`;
- `04. Backend/05. Authorization Model.md`.

Текущее состояние реализации следует проверять по коду, поскольку документация может описывать целевую модель, ещё не полностью реализованную.

# 2. Authentication

## 2.1. JWT

**Состояние:** реализована основная инфраструктура.

В backend присутствуют:

- `JwtConfiguration`;
- `JwtProperties`;
- `JwtKeyPair`;
- `AccessTokenService`;
- `AccessTokenClaimsValidator`.

Используется Spring Security OAuth2 Resource Server.

JWT подписывается алгоритмом RS256.

При проверке JWT предусмотрены проверки подписи, времени действия, issuer, audience и дополнительных claims.

Секретные ключи не должны храниться непосредственно в исходном коде.

## 2.2. Login

**Состояние:** endpoint и сервисная логика присутствуют.

`AuthController` предоставляет:

`POST /api/auth/login`

При успешном входе возвращается access token и устанавливается refresh cookie.

Неуспешные попытки должны обрабатываться без раскрытия чувствительной информации об аккаунте.

## 2.3. Refresh Sessions

**Состояние:** реализована основная доменная и сервисная инфраструктура.

В коде присутствуют:

- `RefreshSession`;
- `RefreshToken`;
- `RefreshSessionService`;
- репозитории для хранения сессий и токенов;
- логика rotation;
- обработка повторного использования refresh token;
- операции отзыва сессий.

Refresh-сессии имеют абсолютный срок действия семь дней.

Конкурентные сценарии требуют отдельной проверки интеграционными тестами.

## 2.4. Logout

**Состояние:** endpoints присутствуют.

Предусмотрены:

- `POST /api/auth/logout`;
- `POST /api/auth/logout-all`.

Текущий logout отзывает соответствующую refresh-сессию.

Logout-all отзывает refresh-сессии пользователя.

Отзыв refresh-сессии не гарантирует мгновенной недействительности ранее выданного access JWT.

# 3. Password Security

## 3.1. Password Hashing

**Состояние:** реализовано.

`PasswordEncoderConfig` использует `Argon2PasswordEncoder`.

Таким образом, фактический алгоритм хеширования паролей в текущей реализации — Argon2, а не BCrypt.

Пароли должны храниться в виде хешей.

## 3.2. Password Reset

**Состояние:** частичная реализация.

В коде присутствуют:

- `PasswordResetService`;
- `PasswordResetServiceImpl`;
- `PasswordResetToken`;
- `PasswordResetTokenRepository`;
- endpoints запроса и подтверждения сброса пароля.

Срок действия reset token в текущем сервисе составляет 30 минут.

При этом полноценную доставку password-reset уведомлений нельзя считать подтверждённой.

В профиле `local` присутствует `LocalPasswordResetNotificationSender`, в котором фактическая отправка уведомления не реализована.

Необходимо отдельно завершить и проверить весь пользовательский процесс восстановления доступа.

# 4. Authorization

**Состояние:** реализована часть механизмов авторизации.

В коде присутствуют:

- `AuthorizationPolicy`;
- `CurrentActor`;
- `CurrentActorProvider`;
- `RoleAuthorizationManager`;
- `SecurityCurrentActorProvider`;
- проверки полномочий в соответствующих сервисах.

`SecurityConfig` устанавливает ограничения для HTTP endpoints.

Для `/api/admin/**` используется проверка административной роли.

Неизвестные запросы по умолчанию отклоняются через `denyAll()`.

Полную корректность проверок принадлежности ресурсов и бизнес-полномочий необходимо оценивать отдельно для каждого реализованного сценария.

Наличие роли само по себе не заменяет проверку принадлежности ресурса и актуальных бизнес-условий.

# 5. HTTP Security

## 5.1. CSRF

**Состояние:** конфигурация присутствует.

В `SecurityConfig` используется SPA-compatible CSRF configuration Spring Security.

`AuthController` предоставляет endpoint получения CSRF token:

`GET /api/auth/csrf`

Необходимо поддерживать согласованное использование CSRF token для защищаемых изменяющих запросов.

## 5.2. CORS

**Состояние:** реализована конфигурация.

В коде присутствуют:

- `CorsConfig`;
- `CorsProperties`.

Разрешённые origins задаются конфигурацией.

Для production origins предусмотрена проверка использования HTTPS.

Произвольные внешние origins не должны автоматически получать разрешение.

## 5.3. Security Headers

**Состояние:** часть заголовков настроена.

В `SecurityConfig` присутствуют настройки:

- Content-Security-Policy;
- Referrer-Policy.

Полнота набора security headers должна оцениваться отдельно при подготовке production deployment.

## 5.4. Refresh Cookie

**Состояние:** реализована фабрика cookie.

`RefreshCookieFactory` задаёт:

- HttpOnly;
- Secure;
- SameSite=Strict;
- Path=/.

Используемое имя cookie:

`__Host-refreshToken`

Это фактическое имя в текущем коде, которое может отличаться от примеров в более ранней архитектурной документации.

## 5.5. Stateless HTTP Authentication

**Состояние:** настроено.

В `SecurityConfig` используется `SessionCreationPolicy.STATELESS`.

Отключены стандартные form login и HTTP Basic authentication.

Для JWT-запросов используется OAuth2 Resource Server.

# 6. Rate Limiting

**Состояние:** реализован базовый механизм для auth endpoints.

В коде присутствуют:

- `AuthRateLimitFilter`;
- `AuthRateLimiter`;
- `InMemoryAuthRateLimiter`;
- `AuthRateLimitProperties`.

Ограничения применяются к предусмотренным authentication endpoints, включая:

- login;
- refresh;
- password reset request;
- password reset confirm.

При превышении лимита предусмотрен HTTP 429 и заголовок `Retry-After`.

Текущий in-memory механизм не следует считать полноценной распределённой защитой для нескольких экземпляров приложения.

---

# 7. Validation и Error Handling

В backend используются:

- Jakarta Bean Validation для соответствующих HTTP request DTO;
- отдельная password policy;
- исключения authentication и authorization;
- специализированные обработчики ошибок Security.

Классы:

- `ApiAuthenticationEntryPoint`;
- `ApiAccessDeniedHandler`;
- `SecurityErrorResponseWriter`.

Наличие этих механизмов не означает, что все API endpoints уже прошли security regression testing.

---

# 8. Незавершённые проверки

Отдельной работы требуют:

1. Полный security regression suite.
2. Проверка всех публичных и защищённых endpoints.
3. Полная проверка password recovery/reset.
4. Production security headers.
5. Security audit logging.
6. Безопасность логирования токенов и чувствительных данных.
7. Dependency vulnerability scanning.
8. Политика смены ключей JWT.
9. Security hardening перед MVP release.
10. Проверка защиты от распространённых web-уязвимостей, включая XSS и SQL injection.

Перечисление направления не означает, что защита полностью отсутствует.

Оно означает, что соответствующая работа или её полнота не подтверждена данным обзором.

В текущем `psyweb/main` присутствует значительная часть инфраструктуры безопасности:

- JWT authentication;
- refresh sessions и rotation;
- logout;
- Argon2 password hashing;
- базовая authorization infrastructure;
- CSRF и CORS configuration;
- refresh cookie security;
- auth rate limiting;
- security error handling.

При этом отдельные сценарии и проверки остаются незавершёнными.
