# 1. Назначение

Документ описывает существующие REST endpoints модуля Authentication.

Источник реализации:

- `auth/web/controller/AuthController.java`;
- `auth/web/dto/request`;
- `auth/web/dto/response`;

- `auth/config/SecurityConfig.java`.

Документ фиксирует текущее поведение и не определяет будущую политику версионирования API.

# 2. Реализованные endpoints

| Метод | Endpoint | Назначение | Успех |
|---|---|---|---|
| POST | `/api/auth/register/client` | Регистрация клиента | 201 |
| POST | `/api/auth/register/specialist` | Регистрация специалиста | 201 |
| GET | `/api/auth/csrf` | Получение CSRF token | 200 |
| POST | `/api/auth/login` | Аутентификация | 200 |
| POST | `/api/auth/refresh` | Обновление аутентификации | 200 |
| POST | `/api/auth/logout` | Завершение текущей refresh-сессии | 204 |
| POST | `/api/auth/logout-all` | Отзыв всех refresh-сессий | 204 |
| POST | `/api/auth/password-reset/request` | Запрос сброса пароля | 202 |
| POST | `/api/auth/password-reset/confirm` | Подтверждение сброса | 204 |

В текущей конфигурации Spring Security все перечисленные операции, кроме `logout-all`, имеют `permitAll()` на уровне HTTP authorization. Это не отменяет CSRF, проверку входных данных и дополнительные бизнес-проверки.

`logout-all` требует аутентификации.

# 3. Регистрация

## 3.1. Регистрация CLIENT

`POST /api/auth/register/client`

Request DTO: `ClientRegistrationRequest`.

Поля:

- `email`;
- `password`;
- `firstName`;
- `lastName`.

Email должен быть непустым и соответствовать формату email.

Имя и фамилия обязательны; ограничения длины в DTO составляют 2–100 символов.

Пароль дополнительно проверяется соответствующей password policy.

## 3.2. Регистрация SPECIALIST

`POST /api/auth/register/specialist`

Request DTO: `SpecialistRegistrationRequest`.

Поля:

- `email`;
- `password`;
- `firstName`;
- `lastName`;
- `timeZone`.

`timeZone` имеет Java-тип `ZoneId` и является обязательным полем.

Регистрация не означает профессионального одобрения специалиста.

## 3.3. Результат регистрации

Response DTO: `RegistrationResponse`.

Содержит:

- `userId`;
- `role`.

HTTP 201 означает успешное создание аккаунта, а не автоматическую аутентификацию.

Возможные документированные ошибки:

- 400 — некорректные регистрационные данные;
- 403 — отсутствует или недействителен необходимый CSRF token;
- 409 — email уже зарегистрирован.

# 4. Login

`POST /api/auth/login`

Request DTO: `LoginRequest`.

Поля:

- `email`;
- `password`.

В DTO оба поля обязательны. Максимальная длина email — 100, password — 200 символов.

При успешной аутентификации возвращается `AuthenticationResponse`:

```json
{
  "accessToken": "<jwt>",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

Значение JWT в примере условное.

Refresh token устанавливается отдельно через `Set-Cookie`.

Коды, указанные в контроллере:

- 200 — успешный login;
- 400 — ошибка данных запроса;
- 401 — неверные учётные данные;
- 403 — CSRF failure;
- 429 — превышение лимита запросов.

Ошибки аутентификации не должны раскрывать существование конкретного аккаунта.

---

# 5. Refresh

`POST /api/auth/refresh`

Endpoint использует refresh cookie.

При успешной операции:

- выполняется проверка refresh token;
- выполняется token rotation;
- возвращается новый access JWT;
- устанавливается обновлённая refresh cookie.

Response DTO: `AuthenticationResponse`.

Документированные ответы:

- 200 — refresh выполнен;
- 401 — refresh token недействителен, истёк или использован повторно;
- 403 — CSRF failure;
- 429 — превышение лимита запросов.

Строгая rotation требует осторожной обработки конкурентных refresh-запросов.

# 6. Logout

## 6.1. Текущая сессия

`POST /api/auth/logout`

Endpoint отзывает refresh-сессию, если соответствующий refresh token предоставлен.

После операции сервер возвращает HTTP 204 и очищающую cookie.

## 6.2. Все сессии

`POST /api/auth/logout-all`

Требует действующей аутентификации.

Идентичность пользователя определяется сервером через `CurrentActorProvider`.

При успешном выполнении возвращается HTTP 204 и очищается cookie текущего браузера.

Отзыв refresh-сессий не означает мгновенного отзыва всех ранее выданных access JWT.

# 7. Password Reset

## 7.1. Запрос восстановления

`POST /api/auth/password-reset/request`

Request DTO: `PasswordResetRequest`.

Поле:

- `email`.

Успешный HTTP-ответ: 202 Accepted.

## 7.2. Подтверждение восстановления

`POST /api/auth/password-reset/confirm`

Request DTO: `PasswordResetConfirmRequest`.

Поля:

- `token`;
- `newPassword`.

Успешный HTTP-ответ: 204 No Content.

Дополнительно проверяются срок действия reset token и password policy.

## 7.3. Ограничение реализации

Endpoints и сервисная логика существуют.

Однако это не означает готовность полного пользовательского восстановления пароля.

В текущем `local` profile используется `LocalPasswordResetNotificationSender`, в котором фактическая доставка reset token не реализована.

Поэтому интеграцию с реальным каналом доставки необходимо проверять отдельно.

# 8. CSRF и Cookies

Для получения CSRF token существует:

`GET /api/auth/csrf`

Контроллер возвращает объект `CsrfToken` и устанавливает `Cache-Control: no-store`.

Refresh cookie создаётся в `RefreshCookieFactory`.

Текущее имя:

`__Host-refreshToken`

Параметры:

- HttpOnly;
- Secure;
- SameSite=Strict;
- Path=/.

Срок действия cookie определяется оставшимся временем refresh-сессии.

Изменяющие запросы должны учитывать действующую конфигурацию CSRF.
