
# 03. API Error Responses

**Проект:** PsyWeb  
**Раздел:** 08. API  
**Статус:** CURRENT IMPLEMENTATION — на основании `psyweb/main`  
**Задача:** PSY-206

---

# 1. Назначение

Документ фиксирует фактические структуры HTTP-ошибок и обработчики исключений текущего backend.

Источники реализации:

- `common/web/exception/GlobalExceptionHandler.java`;
- `common/web/dto/ApiError.java`;
- `common/web/dto/ValidationApiError.java`;
- `auth/security/ApiAuthenticationEntryPoint.java`;
- `auth/security/ApiAccessDeniedHandler.java`;
- `auth/security/SecurityErrorResponseWriter.java`;
- `auth/ratelimit/AuthRateLimitFilter.java`.

Документ не вводит новые статусы, ошибки или правила совместимости API.

---

# 2. Базовый формат ошибки

В текущем backend используется `ApiError`.

Поля:

| Поле | Тип | Назначение |
|---|---|---|
| `code` | String | Машиночитаемый код ошибки |
| `message` | String | Сообщение об ошибке |
| `path` | String | URI запроса |
| `timestamp` | Instant | Момент формирования ответа |

Пример структуры:

```json
{
  "code": "INTERNAL_SERVER_ERROR",
  "message": "Internal server error",
  "path": "/api/example",
  "timestamp": "2026-11-26T10:00:00Z"
}
```

URI и дата приведены для иллюстрации.

Реальные значения формируются на стороне сервера.

---

# 3. Ошибки валидации

Для ошибок Bean Validation используется `ValidationApiError`.

Он содержит общие поля `ApiError` и дополнительное поле `fieldErrors`.

`fieldErrors` представляет отображение:

```text
fieldName -> list of error messages
```

Пример структуры:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "path": "/api/auth/login",
  "timestamp": "2026-11-26T10:00:00Z",
  "fieldErrors": {
    "email": [
      "must be a well-formed email address"
    ]
  }
}
```

Тексты отдельных ошибок могут зависеть от применённых validation annotations и их конфигурации.

HTTP status: 400 Bad Request.

---

# 4. Domain Exceptions

`GlobalExceptionHandler` сопоставляет категории исключений с HTTP-статусами.

| Exception | HTTP |
|---|---|
| `NotFoundException` | 404 |
| `ValidationException` | 400 |
| `InvalidStateException` | 409 |
| `ConflictException` | 409 |
| `ForbiddenException` | 403 |
| `ExpiredException` | 409 |
| `UnauthorizedException` | 401 |

Для этих исключений формируется `ApiError` с кодом и сообщением соответствующего исключения.

Конкретные доменные коды не перечисляются здесь, поскольку определяются классами соответствующих исключений.

---

# 5. Некорректный JSON

`HttpMessageNotReadableException` обрабатывается отдельно.

Ответ:

- HTTP 400;
- `code = MALFORMED_REQUEST_BODY`;
- `message = Malformed request body`.

В ответ не включаются внутренние детали ошибки JSON parser.

---

# 6. Authentication Errors

В Spring Security предусмотрен `ApiAuthenticationEntryPoint`.

Для отказа в аутентификации он формирует:

- HTTP 401;
- `code = UNAUTHORIZED`;
- `message = Authentication required`.

Используется `SecurityErrorResponseWriter`, формирующий структуру `ApiError`.

Для Bearer authentication также применяется стандартный `BearerTokenAuthenticationEntryPoint`.

---

# 7. Authorization Errors

`ApiAccessDeniedHandler` формирует:

- HTTP 403;
- `code = FORBIDDEN`;
- `message = Access denied`.

Response body соответствует `ApiError`.

Различие 401 и 403 должно учитываться frontend:

- 401 относится к отсутствующей или недействительной аутентификации;
- 403 относится к отказу в доступе в соответствующем security flow.

Это не означает, что каждый HTTP 403 обязательно сформирован именно `ApiAccessDeniedHandler`.

Например, CSRF failures могут обрабатываться на уровне security filter chain.

---

# 8. Unexpected Exceptions

Для необработанных исключений `GlobalExceptionHandler` возвращает:

- HTTP 500;
- `code = INTERNAL_SERVER_ERROR`;
- `message = Internal server error`.

Внутренняя информация об исключении не передаётся клиенту в этом JSON-ответе.

Исключение логируется сервером.

Это не заменяет отдельную проверку безопасности логов и политики редактирования чувствительных данных.

---

# 9. Rate Limiting

Для предусмотренных auth endpoints используется `AuthRateLimitFilter`.

При превышении лимита фильтр устанавливает:

- HTTP 429 Too Many Requests;
- `Retry-After`;
- `Cache-Control: no-store`.

Текущий код фильтра не формирует `ApiError` JSON body для этого случая.

Поэтому нельзя считать, что абсолютно все ошибочные HTTP-ответы имеют одинаковую JSON-структуру.

Frontend должен корректно учитывать статус и заголовки даже при отсутствии JSON body.

---

# 10. Границы контракта

Данный документ описывает текущую реализацию.

Он не является окончательной политикой:

- API versioning;
- backward compatibility;
- deprecation;
- полного error code registry;
- обработки всех возможных Spring Security exceptions;
- обязательной унификации всех ошибок.

Такие изменения должны оформляться отдельными задачами и проверяться по реализации.

---

# 11. Итог

Текущий backend использует:

- `ApiError` для общих и доменных ошибок;
- `ValidationApiError` для Bean Validation;
- отдельные security handlers для authentication и authorization;
- отдельную обработку malformed JSON;
- HTTP 429 с `Retry-After` для auth rate limiting.

**Не каждый ошибочный ответ обязательно содержит JSON body.**

**Статус: CURRENT IMPLEMENTATION — структура HTTP ошибок сверена с текущими обработчиками `psyweb/main`.**
