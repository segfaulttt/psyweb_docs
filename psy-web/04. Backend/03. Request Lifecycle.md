
# 03. Жизненный цикл запроса (Request Lifecycle)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — целевая архитектура согласована, реализация выполняется поэтапно

---

# 1. Назначение документа

Документ описывает обработку запросов и прикладных сценариев в backend PsyWeb.

Рассматривается полный путь операции:

- получение HTTP-запроса;
- аутентификация пользователя;
- авторизация;
- валидация входных данных;
- выполнение прикладного сценария;
- обращение к доменным сервисам;
- управление транзакциями;
- взаимодействие с PostgreSQL;
- формирование ответа;
- обработка ошибок;
- публикация событий после фиксации бизнес-операции.

Особое внимание уделяется операциям Reservation, Booking и Schedule, поскольку они требуют согласованного изменения данных и защиты от конкурентных запросов.

Документ разделяет:

1. Текущую реализацию backend.
2. Целевую архитектуру.
3. Открытые вопросы, требующие уточнения перед реализацией.

Наличие сценария в целевой архитектуре не означает, что соответствующий код уже существует.

---

# 2. Текущая и целевая архитектура

## 2.1. Текущая реализация

На момент исходной документации backend уже содержал существенную часть сервисной и доменной логики:

- User;
- Specialist;
- AvailabilitySlot;
- Reservation;
- Booking;
- транзакционные операции;
- Spring Data JPA;
- PostgreSQL;
- обработку части доменных исключений;
- внедряемый Clock;
- обработчик истечения Reservation.

В частности, были реализованы сервисные операции создания, подтверждения, отмены и истечения Reservation.

Однако эта реализация относится к первоначальной модели предварительно создаваемых AvailabilitySlot.

После утверждения новой архитектуры эти операции требуют переработки.

Данный документ не утверждает, что такая переработка уже выполнена.

Актуальное состояние реализации должно проверяться по исходному коду приложения PsyWeb.

## 2.2. Целевая архитектура

Целевой HTTP-процесс:

```text
Client
    ↓
Spring Security Filter Chain
    ↓
Controller
    ↓
Application Service
    ↓
Domain Services / Domain Policies
    ↓
Module Repositories
    ↓
PostgreSQL
    ↓
Application Service
    ↓
Response DTO
    ↓
HTTP Response
```

Для межмодульной операции Application Service может координировать несколько модулей:

```text
Controller
    ↓
Application Service
    ├── Service Module
    ├── Specialist Module
    ├── Schedule Module
    └── Booking Module
            ↓
        PostgreSQL
```

Порядок фактического взаимодействия определяется бизнес-сценарием и транзакционным протоколом.

## 2.3. Отличие целевой модели

Новая архитектура не использует хранимые AvailabilitySlot.

Вместо этого:

- специалист определяет рабочее расписание;
- клиент выбирает ServiceOffering;
- AvailabilityService рассчитывает возможные начала консультаций;
- ReservationApplicationService окончательно проверяет доступность;
- создаются Reservation и ScheduleOccupancy;
- после подтверждения создаётся Booking;
- результат проведения консультации определяется отдельно через SessionOutcome.

# 3. Получение HTTP-запроса

## 3.1. Клиентское приложение

Клиент отправляет HTTP-запрос к REST API PsyWeb.

Запрос может содержать:

- HTTP-метод;
- URL;
- JSON-тело;
- параметры запроса;
- заголовки;
- Bearer JWT для защищённых операций.

## 3.2. Примеры операций

Целевой API предусматривает:

- регистрацию;
- вход;
- получение услуг специалиста;
- получение доступного времени;
- создание Reservation;
- подтверждение Reservation;
- отмену Reservation;
- отмену Booking;
- редактирование расписания;
- отправку отчёта о консультации;
- создание и редактирование Review;
- административные операции.

Точные URL, HTTP-методы и DTO определяются отдельными API-контрактами.

## 3.3. Контроллер

Контроллер является HTTP-границей приложения.

Он не выполняет предметную транзакционную логику самостоятельно.

---

# 4. Spring Security Filter Chain

## 4.1. Назначение

До выполнения защищённого запроса Spring Security определяет, может ли вызывающий пользователь обращаться к приложению.

## 4.2. JWT-аутентификация

Целевой процесс:

```text
HTTP Request
    ↓
Получение Bearer JWT
    ↓
Проверка подписи токена
    ↓
Проверка срока действия
    ↓
Извлечение идентичности
    ↓
Проверка актуального состояния User
    ↓
Создание Authentication
    ↓
SecurityContext
```

## 4.3. Содержимое JWT

JWT может содержать стабильные сведения:

- userId;
- role;
- expiration.

Точный формат определяется Authentication Flow.

## 4.4. Изменяемые состояния

Не следует считать долговременной истиной сведения, которые могут измениться после выдачи токена.

Например:

- User.status;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

Эффективный допуск специалиста к бронированию дополнительно проверяется в соответствующих бизнес-операциях.

## 4.5. Заблокированный пользователь

Наличие криптографически корректного JWT не должно предоставлять заблокированному пользователю доступ к защищённым операциям.

## 4.6. Граница ответственности

Security Filter Chain отвечает за аутентификацию и общие ограничения доступа.

Он не проверяет:

- свободно ли время консультации;
- истёк ли TTL Reservation;
- пересекается ли Occupancy;
- допустимо ли изменение расписания;
- состоялась ли консультация.

Эти проверки принадлежат прикладным и доменным сервисам.

---

# 5. Авторизация

## 5.1. Два уровня

Авторизация включает:

1. Проверку общих полномочий.
2. Проверку прав на конкретный ресурс.

## 5.2. Общие полномочия

Например:

- CLIENT может создавать собственные Reservation;
- SPECIALIST может управлять собственным расписанием;
- ADMIN может выполнять разрешённые административные операции.

## 5.3. Принадлежность ресурса

Даже имея правильную роль, пользователь не может автоматически выполнять операции над любыми объектами.

Например, при подтверждении Reservation проверяется принадлежность записи клиенту.

При изменении расписания проверяется принадлежность расписания специалисту.

## 5.4. Доверенная идентичность

Идентификатор инициатора определяется через SecurityContext.

Нельзя доверять переданному в HTTP-запросе clientId или administratorId как доказательству личности.

## 5.5. Авторизация внутри транзакции

Когда решение зависит от изменяемого состояния, необходимые проверки выполняются повторно внутри критического бизнес-сценария.

Предварительной проверки на уровне Controller недостаточно.

---

# 6. Controller Layer

## 6.1. Ответственность

Controller выполняет:

- сопоставление HTTP-запроса с endpoint;
- десериализацию;
- проверку DTO;
- получение идентичности вызывающего пользователя;
- вызов Application Service;
- преобразование результата в Response DTO.

## 6.2. Ограничения

Controller не должен:

- обращаться напрямую к Repository для выполнения сложной операции;
- изменять ReservationStatus;
- создавать ScheduleOccupancy;
- получать PostgreSQL advisory locks;
- управлять несколькими доменными транзакциями;
- вычислять bookingDeadline;
- определять успешность SessionOutcome.

## 6.3. Транзакции

Основная транзакционная граница бизнес-сценария располагается в прикладном сервисе.

Controller не должен становиться владельцем такой транзакции.

---

# 7. Валидация запроса

## 7.1. Техническая валидация

На HTTP-границе проверяются:

- обязательные поля;
- корректность форматов;
- типы значений;
- допустимые диапазоны простых параметров;
- синтаксическая корректность запроса.

## 7.2. Предметная валидация

В Application Service и Domain Policy проверяются:

- право пользователя выполнить операцию;
- допустимость перехода состояния;
- существование и активность услуги;
- эффективный допуск специалиста;
- принадлежность выбранного времени рабочему расписанию;
- соблюдение дедлайнов;
- отсутствие конфликтующей Occupancy.

## 7.3. Повторная проверка

Проверка DTO не гарантирует неизменность данных между получением запроса и транзакционным изменением.

Критические бизнес-предусловия должны проверяться по актуальным данным.

---

# 8. Application Service

## 8.1. Назначение

Application Service представляет границу выполнения конкретного пользовательского сценария.

Он отвечает за:

- оркестрацию;
- транзакционную границу;
- получение данных через контракты модулей;
- управление порядком операций;
- применение доменных правил;
- согласованное изменение состояния;
- преобразование известных конфликтов;
- формирование результата.

## 8.2. Примеры

Целевые прикладные сервисы:

- ReservationApplicationService;
- SchedulingApplicationService;
- BookingService или соответствующий прикладной координатор;
- AdministrativeBlockingService.

Названия являются частью целевого проектирования сервисного слоя.

## 8.3. Межмодульная координация

Один прикладной сценарий может затрагивать несколько модулей.

Это не означает, что один модуль получает право напрямую изменять Repository другого.

## 8.4. Границы транзакций

Согласованные изменения, которые должны происходить атомарно, выполняются в одной транзакции PostgreSQL.

## 8.5. Запрет распределённой бизнес-операции

Для основной модели бронирования не требуется распределённая транзакция между микросервисами.

PsyWeb является модульным монолитом с общей транзакционной базой данных.

---

# 9. Domain Layer

## 9.1. Ответственность

Доменный слой содержит:

- сущности;
- состояния;
- локальные инварианты;
- переходы состояний;
- бизнес-политики;
- value objects.

## 9.2. Примеры

Reservation определяет допустимые переходы:

```text
ACTIVE → CONFIRMED
ACTIVE → CANCELLED
ACTIVE → EXPIRED
```

Booking определяет допустимые изменения собственного состояния.

AvailabilityPolicy проверяет условия размещения консультации.

OutcomeResolutionPolicy определяет правила разрешения результатов консультаций.

## 9.3. Разделение обязанностей

Application Service определяет последовательность шагов.

Доменная модель определяет допустимость предметных операций.

## 9.4. Ограничения

Доменный слой не должен зависеть от HTTP-запросов или контроллеров.

---

# 10. Repository Layer

## 10.1. Назначение

Repository предоставляет операции хранения и получения данных.

В PsyWeb используется Spring Data JPA и PostgreSQL.

## 10.2. Обязанности

Repository выполняет:

- поиск сущностей;
- сохранение;
- удаление;
- специализированные SQL-запросы;
- запросы со строковыми блокировками;
- выборку записей для фоновой обработки.

## 10.3. Владение

Repository принадлежит соответствующему модулю.

Например:

- ReservationRepository принадлежит Booking;
- ScheduleRepository принадлежит Schedule;
- ReviewRepository принадлежит Review.

## 10.4. Межмодульный доступ

Другие модули не должны использовать чужой Repository как обход его бизнес-контрактов.

## 10.5. Согласованность данных

Repository не заменяет доменные проверки или транзакционную оркестрацию.

---

# 11. PostgreSQL

## 11.1. Роль базы данных

PostgreSQL является окончательной границей обеспечения целостности конкурентных изменений.

## 11.2. Ограничения

Используются:

- PRIMARY KEY;
- FOREIGN KEY;
- UNIQUE;
- CHECK;
- exclusion constraints.

## 11.3. Занятость консультаций

Для ScheduleOccupancy применяется GiST exclusion constraint.

Он запрещает пересекающиеся интервалы одного специалиста.

## 11.4. Строковые блокировки

Используются:

- FOR SHARE;
- FOR UPDATE;
- FOR UPDATE SKIP LOCKED.

## 11.5. Advisory locks

Для календарных операций применяются transaction-level advisory locks PostgreSQL.

## 11.6. Уровень изоляции

Базовый уровень изоляции:

READ COMMITTED.

Бизнес-инварианты обеспечиваются сочетанием транзакций, согласованного порядка блокировок и ограничений PostgreSQL.

---

# 12. Предварительный расчёт Availability

## 12.1. Входные данные

Клиент выбирает ServiceOffering и диапазон локальных дат.

## 12.2. Обработка

```text
AvailabilityController
    ↓
AvailabilityService
    ↓
ServiceOfferingQuery
    ↓
Specialist / Schedule Queries
    ↓
OccupancyQuery
    ↓
AvailabilityPolicy
    ↓
AvailableStart DTO
```

## 12.3. Источники данных

Используются:

- ServiceOffering;
- SpecialistBookingAccess;
- SpecialistBookingPolicy;
- SpecialistScheduleSettings;
- SpecialistTimeZoneGuard;
- WeeklyScheduleVersion;
- DateSchedule;
- ScheduleOccupancy.

## 12.4. Результат

Возвращается список предварительно допустимых начал консультаций.

## 12.5. Отсутствие удержания

Получение доступности не создаёт Reservation и ScheduleOccupancy.

Два клиента могут одновременно увидеть один и тот же вариант времени.

## 12.6. Гарантии

AvailabilityService не гарантирует, что время останется доступным до последующего запроса.

Окончательная проверка выполняется при создании Reservation.

---

# 13. Создание Reservation

## 13.1. Назначение

Создание Reservation временно удерживает выбранное время консультации.

В целевой модели отсутствует переход AvailabilitySlot FREE → RESERVED.

Вместо него атомарно создаются:

- ACTIVE Reservation;
- ScheduleOccupancy.

## 13.2. Входные данные

Клиент передаёт:

- serviceOfferingId;
- выбранный sessionStart.

Идентичность клиента определяется через SecurityContext.

## 13.3. Основные предусловия

Проверяются:

1. Право клиента создавать Reservation.
2. Существование и активность ServiceOffering.
3. Эффективный допуск специалиста.
4. Соответствие bookingHorizonDays.
5. Соответствие 15-минутной сетке.
6. Допустимость локального начала по DST.
7. Размещение консультации в одном непрерывном рабочем интервале.
8. Соблюдение minimumBookingNotice.
9. Отсутствие конфликтующей Occupancy.

## 13.4. Эффективный допуск специалиста

```text
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

Все административные изменения, лишающие специалиста допуска, должны использовать общий протокол BookingAccess.

## 13.5. Транзакционный процесс

```text
BEGIN
    ↓
ServiceOffering FOR SHARE
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
SpecialistBookingPolicy FOR SHARE
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
Расчёт sessionStart, sessionEnd, occupiedUntil
    ↓
Определение календарных дат занятости
    ↓
Calendar advisory locks
    ↓
Чтение актуального расписания
    ↓
Проверка временных бизнес-правил
    ↓
Проверка действующих Occupancy
    ↓
Обработка конфликтующих истёкших Reservation
    ↓
INSERT Reservation
    ↓
INSERT ScheduleOccupancy
    ↓
COMMIT
```

## 13.6. Snapshot

Reservation фиксирует:

- условия ServiceOffering;
- длительность консультации;
- перерыв;
- цену;
- валюту;
- clientCancellationNoticeSnapshot.

## 13.7. TTL

При создании задаётся:

`expiresAt = createdAt + platformReservationTTL`

TTL принадлежит платформе.

## 13.8. Конкурентность

Календарные блокировки согласуют создание Reservation с изменением расписания.

Exclusion constraint PostgreSQL предотвращает пересекающиеся Occupancy.

## 13.9. Результат

При успехе клиент получает данные созданной Reservation, включая expiresAt.

При конфликте время не резервируется.

---

# 14. Подтверждение Reservation

## 14.1. Назначение

Подтверждение переводит действующую Reservation в CONFIRMED и создаёт Booking.

## 14.2. Предусловия

Необходимо проверить:

- существование Reservation;
- принадлежность клиенту;
- статус ACTIVE;
- наличие корректной Occupancy;
- действующий допуск специалиста;
- отсутствие истечения TTL.

## 14.3. Порядок блокировок

```text
BEGIN
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка бизнес-условий
    ↓
Получение актуального времени
    ↓
Проверка now < expiresAt
    ↓
Reservation ACTIVE → CONFIRMED
    ↓
INSERT Booking
    ↓
Сохранение Occupancy
    ↓
COMMIT
```

## 14.4. Уникальность

Одна Reservation может создать не более одной Booking.

PostgreSQL защищает это через:

`UNIQUE(bookings.reservation_id)`

## 14.5. Отсутствие повторного поиска доступности

Подтверждение не должно заново проверять рабочее расписание.

Если Reservation была создана корректно и остаётся ACTIVE, обычное изменение графика не отменяет право на подтверждение до expiresAt.

## 14.6. Изменение ServiceOffering

Изменения услуги после создания Reservation не изменяют её исторический snapshot.

## 14.7. Истечение TTL

При `now >= expiresAt` подтверждение не допускается.

Если подтверждение обнаруживает истечение, дальнейшая обработка состояния и освобождение Occupancy должна выполняться по согласованному транзакционному протоколу.

Нельзя случайно откатить сохранённый переход в EXPIRED из-за исключения, выброшенного внутри той же транзакции.

## 14.8. Результат

При успешном подтверждении создаётся Booking со статусом CONFIRMED.

Исходная Reservation остаётся CONFIRMED, а Occupancy сохраняется.

---

# 15. Отмена ACTIVE Reservation

## 15.1. Назначение

Отмена освобождает временно удерживаемый интервал до подтверждения консультации.

## 15.2. Процесс

```text
BEGIN
    ↓
Проверка полномочий
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка статуса
    ↓
ACTIVE → CANCELLED
    ↓
Сохранение cancellation metadata
    ↓
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 15.3. История

Reservation не удаляется.

Сохраняются:

- cancelledAt;
- cancellationInitiator;
- cancellationReason, если применимо.

## 15.4. Конкурентность

Отмена должна быть согласована с:

- подтверждением;
- истечением TTL;
- административной блокировкой;
- повторной отменой.

## 15.5. Недопустимые состояния

CONFIRMED, CANCELLED и EXPIRED Reservation нельзя отменять как ACTIVE.

---

# 16. Истечение Reservation

## 16.1. Назначение

Истечение завершает временное удержание, которое не было подтверждено в установленный срок.

## 16.2. Условие

Reservation считается подлежащей обработке истечения при:

`status = ACTIVE AND now >= expiresAt`

## 16.3. Scheduler

Фоновая задача периодически выбирает просроченные ACTIVE Reservation.

## 16.4. Транзакционный процесс

```text
Получение кандидатов
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка статуса
    ↓
Получение актуального времени
    ↓
Проверка now >= expiresAt
    ↓
ACTIVE → EXPIRED
    ↓
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 16.5. SKIP LOCKED

Для пакетной обработки используется:

`FOR UPDATE SKIP LOCKED`

Это позволяет нескольким обработчикам пропускать уже заблокированные записи.

## 16.6. Актуальное время

После ожидания строковой блокировки необходимо использовать актуальное время.

PostgreSQL `now()` фиксирует начало транзакции и не должен использоваться как единственный источник времени после длительного ожидания.

## 16.7. Конкурентное подтверждение

Подтверждение и истечение одной Reservation должны быть сериализованы строковой блокировкой.

Успешным становится только допустимый переход.

## 16.8. Идемпотентность

Повторный запуск scheduler не должен изменять уже завершённую Reservation.

---

# 17. Очистка просроченного удержания при новой Reservation

## 17.1. Проблема

Истёкшая по времени Reservation может оставаться ACTIVE до запуска scheduler.

Её Occupancy продолжает занимать интервал в базе данных.

## 17.2. Целевое поведение

Новая операция создания Reservation может обработать конфликтующую просроченную Reservation внутри собственной транзакции.

## 17.3. Процесс

```text
Calendar advisory locks
    ↓
Поиск конфликтующей Occupancy
    ↓
Определение соответствующей Reservation
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка status и expiresAt
    ↓
Если ACTIVE и срок истёк:
    ACTIVE → EXPIRED
    DELETE Occupancy
    ↓
Повторная проверка доступности
    ↓
Создание новой Reservation
    ↓
Создание новой Occupancy
    ↓
COMMIT
```

## 17.4. Важное ограничение

Нельзя удалять Occupancy подтверждённой Booking из-за того, что expiresAt её исходной Reservation находится в прошлом.

CONFIRMED Reservation не истекает по TTL повторно.

---

# 18. Отмена CONFIRMED Booking

## 18.1. Назначение

Отмена Booking завершает подтверждённую запись и освобождает её Occupancy.

## 18.2. Отмена клиентом

Обычная клиентская отмена допустима только до начала консультации:

`now < sessionStart`

## 18.3. Своевременная и поздняя отмена

Используется историческое значение:

`clientCancellationNoticeSnapshot`

Дедлайн:

`clientCancellationDeadline = sessionStart - clientCancellationNoticeSnapshot`

Отмена считается поздней при:

`cancelledAt >= clientCancellationDeadline`

## 18.4. Поздняя отмена в MVP

Поздняя отмена допускается до начала консультации.

Она:

- не создаёт денежного штрафа;
- не вызывает автоматического наказания;
- не требует отдельного BookingStatus.

## 18.5. Транзакционный процесс

```text
BEGIN
    ↓
Проверка инициатора
    ↓
Reservation FOR UPDATE
    ↓
Booking FOR UPDATE
    ↓
Проверка BookingStatus
    ↓
Получение актуального времени
    ↓
Проверка now < sessionStart
    ↓
Определение поздней отмены
    ↓
CONFIRMED → CANCELLED
    ↓
Сохранение cancellation metadata
    ↓
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 18.6. История

Booking и исходная Reservation сохраняются.

Reservation остаётся CONFIRMED.

## 18.7. Повторная доступность

Удаление Occupancy освобождает интервал.

Но новая Reservation всё равно должна соответствовать текущему расписанию, minimumBookingNotice и остальным правилам.

---

# 19. Изменение расписания

## 19.1. Назначение

Специалист может изменять:

- WeeklyScheduleVersion;
- DateSchedule;
- режим REGULAR/FLOATING;
- bookingHorizonDays.

## 19.2. Прикладной координатор

Для составных операций используется SchedulingApplicationService.

## 19.3. Конкурентность

Изменения расписания должны согласовываться с созданием Reservation посредством календарных advisory locks.

## 19.4. Изменение отдельной даты

Операция защищает соответствующие календарные даты.

## 19.5. Изменение недельного шаблона

Изменение WeeklyScheduleVersion может затрагивать множество дат.

Используется специальный протокол блокировок защищённого горизонта бронирования.

## 19.6. Существующие ACTIVE Reservation

Обычные изменения расписания сохраняют существующие ACTIVE Reservation.

Они могут быть подтверждены, отменены или истечь по TTL.

## 19.7. Подтверждённые Booking

Существующие CONFIRMED Booking не переносятся и не отменяются автоматически.

## 19.8. Предупреждение

Специалист должен получать предупреждение об изменениях, затрагивающих существующие обязательства.

## 19.9. Новые Reservation

После фиксации нового расписания новые Reservation рассчитываются по обновлённым правилам.

---

# 20. Изменение часового пояса

## 20.1. Назначение

Специалист может изменить ZoneId.

## 20.2. Согласованность

Создание Reservation получает:

`SpecialistTimeZoneGuard FOR SHARE`

Изменение ZoneId использует:

`SpecialistTimeZoneGuard FOR UPDATE`

## 20.3. Существующие записи

Следующие значения не пересчитываются:

- Reservation.sessionStart;
- Reservation.sessionEnd;
- Occupancy.occupiedUntil;
- Reservation.expiresAt.

## 20.4. Рабочее расписание

Локальные рабочие шаблоны продолжают хранить собственные локальные даты и часы.

После смены ZoneId они интерпретируются в новом часовом поясе.

## 20.5. Предупреждение

Если изменение затрагивает существующие обязательства, специалист должен явно подтвердить понимание последствий.

---

# 21. Административная блокировка специалиста

## 21.1. Утверждённое правило

При потере эффективного допуска:

- запрещаются новые Reservation;
- запрещается подтверждение ACTIVE Reservation;
- все ACTIVE Reservation специалиста отменяются;
- их Occupancy удаляются;
- CONFIRMED Booking сохраняются.

## 21.2. Координация

Операция использует AdministrativeBlockingService или согласованный административный координатор.

## 21.3. Порядок блокировок

```text
BEGIN
    ↓
Проверка прав ADMIN
    ↓
SpecialistBookingAccess FOR UPDATE
    ↓
Согласованное изменение допуска
    ↓
Получение ACTIVE Reservation специалиста
    ↓
Reservation FOR UPDATE в стабильном порядке
    ↓
ACTIVE → CANCELLED
    ↓
cancellationInitiator = ADMIN
    ↓
DELETE Occupancy
    ↓
Сохранение административного аудита
    ↓
COMMIT
```

## 21.4. Атомарность

Недопустимо фиксировать блокировку, оставляя ACTIVE Reservation для последующей независимой фоновой отмены.

## 21.5. Конкурентное подтверждение

Подтверждение Reservation получает BookingAccess FOR SHARE до Reservation FOR UPDATE.

Если подтверждение завершилось первым, возникшая Booking сохраняется.

Если блокировка завершилась первой, подтверждение отклоняется.

## 21.6. Конкурентное создание

Создание Reservation также получает BookingAccess FOR SHARE.

После получения эксклюзивной блокировки административная операция должна обнаружить все оставшиеся ACTIVE Reservation и отменить их.

## 21.7. Восстановление

Повторное одобрение специалиста не снимает отдельное ограничение bookingAllowed = FALSE.

Восстановление выполняется явной разрешённой операцией.

---

# 22. Результат консультации

## 22.1. Разделение ответственности

Booking представляет подтверждённую запись.

SessionOutcome определяет, состоялась ли консультация.

## 22.2. Начало обработки

После окончания консультации участники могут сообщить её результат по утверждённому процессу Outcome.

## 22.3. Окно подтверждения

Для MVP установлено окно 24 часа после окончания консультации.

## 22.4. Отчёты участников

Клиент и специалист независимо сообщают:

- OCCURRED;
- DID_NOT_OCCUR.

При отрицательном результате указывается структурированная причина.

## 22.5. Автоматическое разрешение

Outcome обрабатывает:

- совместимые подтверждения проведения;
- совместимые отрицательные отчёты;
- единственный ответ после завершения окна;
- отсутствие ответов.

## 22.6. Споры

Противоречивые заявления передаются на административное разрешение.

## 22.7. Непроверенный результат

Если ни одна сторона не ответила, нельзя автоматически считать консультацию успешно состоявшейся.

## 22.8. Review

Право на Review возникает только после подтверждённо успешного SessionOutcome.

Сам статус CONFIRMED Booking такого права не создаёт.

---

# 23. Доменные события

## 23.1. Назначение

После успешного изменения бизнес-состояния система может формировать событие.

## 23.2. Примеры

- ReservationCreated;
- ReservationCancelled;
- ReservationExpired;
- BookingConfirmed;
- BookingCancelled;
- SessionOutcomeResolved;
- ReviewCreated;
- SpecialistBlocked.

## 23.3. Граница транзакции

Внешняя доставка уведомления не должна выполняться как подтверждённое действие до успешной фиксации бизнес-транзакции.

## 23.4. Асинхронность

Notification может обрабатывать событие асинхронно.

## 23.5. Transactional outbox

Для гарантированного сохранения намерения доставить событие может использоваться transactional outbox.

Обязательное применение outbox для MVP пока требует отдельного решения.

## 23.6. Повторная обработка

Обработчики должны учитывать возможные повторы и идемпотентность.

---

# 24. Обработка ошибок

## 24.1. Доменные исключения

Бизнес-ошибки выражаются типизированными исключениями.

Примеры:

- ReservationExpiredException;
- InvalidReservationStateException;
- InvalidBookingStateException;
- BookingConflictException;
- ScheduleConflictException;
- SpecialistBookingBlockedException.

Названия должны быть согласованы с фактической иерархией исключений приложения.

## 24.2. Общая иерархия

В исходной реализации используется собственная иерархия доменных исключений.

Её окончательная структура описывается Exception Handling Strategy.

## 24.3. REST-преобразование

HTTP-слой преобразует исключения в безопасные ответы API через централизованный механизм обработки ошибок.

## 24.4. Разделение

Domain и Application Service не должны зависеть от HTTP status codes.

## 24.5. Конкурентные ошибки

Нарушения UNIQUE или exclusion constraints переводятся в соответствующие бизнес-ошибки на границе владельца операции.

## 24.6. Откат

При ошибке бизнес-транзакция откатывается, если только специальный сценарий не предусматривает намеренно сохраняемый переход состояния.

Такие сценарии требуют явно определённой транзакционной обработки.

---

# 25. Транзакционные инварианты

Следующие изменения должны быть согласованы в одной транзакции:

1. Создание Reservation и ScheduleOccupancy.
2. Подтверждение Reservation и создание Booking.
3. Отмена ACTIVE Reservation и освобождение Occupancy.
4. Истечение Reservation и освобождение Occupancy.
5. Отмена CONFIRMED Booking и освобождение Occupancy.
6. Административная блокировка и отмена всех ACTIVE Reservation специалиста.
7. Согласованное изменение расписания.
8. Разрешение SessionOutcome и сохранение результата административного решения, когда оно требуется.

Нельзя оставлять частично зафиксированное состояние.

# 26. Правила конкурентной обработки

## 26.1. Основной принцип

Проверка бизнес-предусловий до транзакции не заменяет проверку после получения нужных блокировок.

## 26.2. Reservation creation

Используются:

- ServiceOffering FOR SHARE;
- BookingAccess FOR SHARE;
- BookingPolicy FOR SHARE;
- TimeZoneGuard FOR SHARE;
- календарные advisory locks;
- exclusion constraint.

## 26.3. Confirmation

Используются:

- BookingAccess FOR SHARE;
- Reservation FOR UPDATE.

## 26.4. Expiration

Используется:

- Reservation FOR UPDATE.

## 26.5. Cancellation

При необходимости получения двух строк соблюдается порядок:

`Reservation → Booking`

## 26.6. Schedule

Календарные блокировки используются в стабильном порядке.

## 26.7. Administrative Blocking

Используется:

`BookingAccess FOR UPDATE → Reservation FOR UPDATE`

## 26.8. Deadlocks

Окончательный порядок блокировок требует проверки реальным PostgreSQL с учётом Hibernate flush и ограничений внешних ключей.

# 27. Работа со временем

## 27.1. Clock

Для бизнес-операций используется внедряемый java.time.Clock.

## 27.2. Момент проверки

Временные условия должны проверяться по актуальному времени после ожидания критических блокировок.

## 27.3. Абсолютные значения

Времена консультаций и Occupancy сохраняются как Instant.

В PostgreSQL используется TIMESTAMPTZ.

## 27.4. Локальное расписание

Рабочее расписание использует LocalDate, LocalTime и ZoneId специалиста.

## 27.5. DST

Начало консультации должно иметь ровно один допустимый UTC offset.

Несуществующие и неоднозначные локальные начала запрещены.

## 27.6. Открытый вопрос

Поведение консультаций, пересекающих DST-переход, требует отдельного утверждённого правила.

# 31. Итог

Целевой жизненный цикл запроса PsyWeb:

```text
HTTP Request
    ↓
Spring Security
    ↓
Controller
    ↓
Application Service
    ↓
Domain Policies / Domain Services
    ↓
Repository
    ↓
PostgreSQL
    ↓
COMMIT
    ↓
Response DTO
    ↓
HTTP Response
```

Прикладной жизненный цикл записи:

```text
ServiceOffering
    ↓
Dynamic Availability
    ↓
ACTIVE Reservation + ScheduleOccupancy
    ↓
CONFIRMED Reservation + CONFIRMED Booking
    ↓
Consultation
    ↓
SessionOutcome
    ↓
Review eligibility
```

Альтернативные исходы:

```text
ACTIVE Reservation → CANCELLED
ACTIVE Reservation → EXPIRED

CONFIRMED Booking → CANCELLED
```

Основные гарантии:

- бизнес-логика не размещается в Controller;
- аутентификация не подменяет предметную авторизацию;
- критические операции выполняются транзакционно;
- межмодульные границы сохраняются;
- PostgreSQL защищает целостность конкурентных изменений;
- предварительная Availability не удерживает время;
- создание Reservation является окончательной проверкой доступности;
- административная блокировка атомарно отменяет ACTIVE Reservation;
- обычные изменения расписания сохраняют существующие обязательства;
- SessionOutcome не подменяется статусом Booking;
- события Notification не определяют исход бизнес-транзакции.

**Статус: DRAFT — целевая архитектура согласована, фактическое соответствие реализации требует отдельной проверки.**
