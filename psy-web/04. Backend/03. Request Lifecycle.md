## Overview

This section describes the full lifecycle of an HTTP request in the PsyWeb backend system, from the moment it enters the system to the final response.

The goal of this pipeline is to ensure:

- secure request processing
- clear separation of concerns
- consistent business logic execution
- controlled transactional boundaries

---

# Request Flow

All incoming requests follow a standard layered pipeline:

```
Client → Security Filter → Controller → Service → Repository → Database → Response
```

---

# Step-by-step lifecycle

## 1. Client Request

The client (web or mobile application) sends an HTTP request to the backend API.

Examples:

- login request
- booking creation
- slot query

---

## 2. Security Filter Layer

Before reaching controllers, the request passes through Spring Security filters.

Responsibilities:

- JWT token extraction
- token validation
- authentication setup in SecurityContext
- request rejection if token is invalid or missing

If authentication fails, request stops here with 401 Unauthorized.

---

## 3. Controller Layer

The controller is responsible for:

- mapping HTTP endpoints
- validating request payloads (DTO validation)
- delegating execution to service layer

Rules:

- controllers must remain thin
- no business logic allowed here

---

## 4. Service Layer (Core Business Logic)

This is the most important layer in the system.

Responsibilities:

- enforce business rules
- handle booking logic and constraints
- coordinate multiple repositories if needed
- manage transactional boundaries

Examples:

- preventing double booking
- validating slot availability
- enforcing cancellation rules

All domain decisions happen here.

---

## 5. Repository Layer

Responsible for:

- database access
- executing CRUD operations
- query execution via Spring Data JPA

Rules:

- no business logic
- only data retrieval and persistence

---

## 6. Database Layer (PostgreSQL)

This is the source of truth for all system data:

- users
- bookings
- slots
- reviews

All constraints defined in schema (FK, UNIQUE, CHECK) are enforced here as a safety net.

---

## 7. Response Flow

After successful execution:

- service returns domain result
- controller maps it to response DTO
- HTTP response is sent to client

---

# Critical Design Rules

## 1. Business logic isolation

All business rules must live in service layer, not controllers or repositories.

---

## 2. Transaction boundary

Each consistency-sensitive business operation must execute within an appropriate transactional scope.

This includes:

* creating an ACTIVE Reservation together with `AvailabilitySlot FREE → RESERVED`;
* confirming a Reservation together with Booking creation and `AvailabilitySlot RESERVED → BOOKED`;
* cancelling or expiring an ACTIVE Reservation together with `RESERVED → FREE`;
* cancelling a Booking together with the corresponding AvailabilitySlot transition;
* specialist availability removal together with consistent handling of an associated Reservation or Booking.

Partial state must not remain committed.

---

## 3. Security enforcement order

Security validation always happens before business logic execution.

---

## 4. Database as source of truth

Even if service layer validates logic, DB constraints must protect data integrity.

---

## 5. Thin controllers principle

Controllers only:

- validate input
- call service
- return response

---

# Example Flow: Reservation and Booking

## Create Reservation

```text
Client
→ JWT Filter
→ BookingController
→ BookingService
→ validate client
→ AvailabilityService validates slot state and bookability
→ create ACTIVE Reservation
→ AvailabilitySlot FREE → RESERVED
→ commit transaction
→ Reservation response
```

## Confirm Reservation

```text
Client
→ JWT Filter
→ BookingController
→ BookingService
→ validate Reservation ownership and expiration
→ confirm Reservation
→ create Booking
→ AvailabilityService performs RESERVED → BOOKED
→ commit transaction
→ Booking response
```

There is no direct `FREE → BOOKED` AvailabilitySlot transition.

Booking creation occurs only after confirmation of an existing ACTIVE Reservation.

---

# Summary

The request lifecycle is designed to ensure:

- secure entry point via JWT filters
- strict layering of responsibilities
- centralized business logic in services
- transactional consistency in booking flows
- reliable persistence in PostgreSQL
