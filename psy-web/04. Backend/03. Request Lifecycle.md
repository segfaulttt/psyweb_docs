## Overview

This document describes request/use-case processing in the PsyWeb backend.

The current implementation already contains substantial:

```text
Service
Domain
Repository
PostgreSQL
```

processing.

The final client-facing HTTP/security pipeline is approved target architecture but is not yet fully implemented.

Therefore this document distinguishes:

```text
current service-level lifecycle
```

from:

```text
target HTTP request lifecycle
```

---

# Current Processing Model

The current implemented core follows:

```text
Service
→ Domain
→ Repository
→ PostgreSQL
```

A service may coordinate another module's service when a business operation spans module boundaries.

For example:

```text
BookingService
→ AvailabilitySlotService
→ AvailabilitySlot state transition
```

The caller of these services is not yet necessarily a REST Controller.

---

# Target HTTP Request Flow

The approved target API pipeline is:

```text
Client
→ Spring Security Filter Chain
→ Controller
→ Service
→ Domain / Repository
→ PostgreSQL
→ Response
```

This target layer will eventually provide:

```text
HTTP endpoint mapping
request DTO validation
JWT authentication
SecurityContext integration
response DTO mapping
centralized REST error handling
```

The current `PsyWeb/main` does not yet contain the complete final implementation of those components.

---

# 1. Target Security Entry Point

For a future protected HTTP request:

```text
Bearer JWT
→ token validation
→ caller identity extraction
→ current User validation
→ authenticated request context
→ authorization
```

The target JWT contains stable identity claims such as:

```text
userId
role
expiration
```

Mutable state such as:

```text
UserStatus
SpecialistStatus
```

must not be treated as permanent authorization truth inside the token.

A protected operation requiring an enabled account must use current account state rather than relying only on an older token.

The final JWT filter/Spring Security integration is target/backlog functionality.

---

# 2. Target Controller Layer

Controllers are part of the approved API architecture.

Their responsibilities are limited to:

```text
HTTP mapping
request deserialization
request DTO validation
authenticated caller extraction
service invocation
response DTO mapping
```

Controllers must not own domain business rules.

The complete controller surface is not yet implemented in the current backend.

---

# 3. Current Service Layer

The Service layer is currently the primary application/use-case boundary.

Responsibilities include:

- input validation relevant to the use case;
- loading domain state;
- enforcing cross-entity business rules;
- invoking domain transitions;
- coordinating other module services;
- defining transaction boundaries;
- translating known persistence conflicts into business exceptions where implemented.

Service methods operate independently from the future HTTP transport layer.

---

# 4. Current Domain Layer

Domain entities own local invariants and lifecycle transitions.

Examples include:

```text
Specialist lifecycle transitions
AvailabilitySlot state transitions
Reservation state transitions
Booking state transitions
```

A Service orchestrates the use case.

The Entity decides whether its own requested transition is valid.

---

# 5. Current Repository Layer

Repositories provide module-owned persistence access through Spring Data JPA.

They are responsible for:

```text
entity lookup
persistence
business-specific queries
locking queries
database-oriented selection
```

Repositories do not own business workflow orchestration.

Another module must not directly use a repository as a shortcut around the owning module boundary.

---

# 6. PostgreSQL

PostgreSQL provides the persistent integrity boundary.

Current guarantees include, among others:

```text
foreign keys
CHECK constraints
User email uniqueness
lowercase email guard
one ACTIVE Reservation per Slot
```

Application checks may provide earlier and clearer business failures.

Database guarantees remain necessary for concurrency-sensitive invariants.

---

# Current Flow: Reservation Creation

Reservation creation is currently owned by:

```text
ReservationService.createReservation(...)
```

The current flow is:

```text
validate clientId / slotId
→ application pre-check for existing ACTIVE Reservation
→ load ACTIVE User
→ request AvailabilitySlot FREE → RESERVED
→ capture now from injected Clock
→ create ACTIVE Reservation
→ expiresAt = now + ReservationProperties.ttl
→ saveAndFlush Reservation
```

The operation is transactional.

The slot state change and Reservation creation therefore participate in the same transaction.

---

## Reservation Concurrency Protection

The application first checks whether an ACTIVE Reservation already exists for the Slot.

That pre-check is not the final concurrency guarantee.

PostgreSQL also protects:

```text
at most one ACTIVE Reservation per Slot
```

through the partial unique index:

```text
unique_active_reservation_slot
```

A known database conflict on that constraint is translated into:

```text
ActiveReservationAlreadyExistsException
```

rather than exposed as the raw persistence exception.

---

## Current Eligibility Boundary

Current Reservation creation requires the User loaded by the service to have:

```text
UserStatus.ACTIVE
```

The current implementation does not yet enforce the complete target API/security role flow at this boundary.

In particular, REST/JWT-level CLIENT authorization must not be described as current merely because the eventual business operation is a client operation.

Detailed User lookup semantics belong to the dedicated User documentation task.

---

## Booking Deadline Boundary

The current Specialist model already stores:

```text
minimumBookingNotice
```

but Reservation creation does not yet enforce the final:

```text
bookingDeadline
```

rule.

The target rule is:

```text
now < slot.startTime - effectiveMinimumBookingNotice
```

with future support for an optional per-slot override.

Therefore booking-deadline enforcement is target/backlog functionality.

---

# Current Flow: Reservation Confirmation

Reservation confirmation is currently owned by:

```text
BookingService.confirmReservation(...)
```

The current transaction performs:

```text
validate reservationId / clientId
→ lock Reservation for update
→ capture now from injected Clock
→ verify Reservation ownership
→ detect expiration
→ require ACTIVE Reservation
→ require ACTIVE User
→ AvailabilitySlot RESERVED → BOOKED
→ require eligible Specialist
→ Reservation ACTIVE → CONFIRMED
→ create CONFIRMED Booking
→ persist Booking
```

Specialist professional eligibility requires current:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

---

## Reservation Locking

Confirmation loads the Reservation using pessimistic write locking.

This prevents concurrent operations from independently treating the same Reservation as safely mutable.

Cancellation and explicit expiration use the same locking strategy.

---

## Expired Confirmation

Expiration uses the boundary:

```text
now >= expiresAt
```

If confirmation discovers an expired Reservation:

```text
Reservation → EXPIRED
AvailabilitySlot RESERVED → FREE
Booking is not created
```

The confirmation transaction is configured so the expiration state is not rolled back merely because:

```text
ReservationExpiredException
```

is returned as the business failure.

---

# Current Flow: Reservation Cancellation

Current cancellation is:

```text
lock Reservation
→ Reservation ACTIVE → CANCELLED
→ AvailabilitySlot RESERVED → FREE
→ commit
```

The operation is transactional.

The current Reservation persistence model does not yet contain all target cancellation metadata required by later administrative workflows.

---

# Current Flow: Reservation Expiration Scheduler

Reservation expiration also runs automatically.

The scheduler delegates to the Reservation service using configured:

```text
psyweb.reservation.expiration-scan-interval
```

Current configuration is:

```text
1m
```

The service captures one:

```text
now
```

from injected Clock and loads one batch of overdue ACTIVE Reservations.

Current batch size:

```text
100
```

Current query semantics:

```text
status = ACTIVE
AND expires_at <= now
```

with:

```text
ORDER BY expires_at, id
FOR UPDATE SKIP LOCKED
```

Each still-expired Reservation is transitioned:

```text
ACTIVE → EXPIRED
```

and its Slot is released:

```text
RESERVED → FREE
```

The scheduler does not require a distributed lock or message broker for the current design.

---

# Current Flow: Booking Cancellation

Current Booking cancellation is:

```text
load Booking
→ capture now from injected Clock
→ Booking → CANCELLED
→ AvailabilitySlot BOOKED → FREE
→ commit
```

The current implementation does not yet enforce the complete approved:

```text
clientCancellationNotice
late cancellation classification
cancellation initiator/reason metadata
```

workflow.

Those behaviors remain target/backlog until their owning implementation work is completed.

---

# Controlled Time

Current temporal service logic uses injected:

```text
java.time.Clock
```

rather than direct uncontrolled system time.

Production obtains the Clock from:

```text
TimeConfiguration
```

Current production implementation uses:

```text
Clock.systemDefaultZone()
```

Tests may replace it with:

```text
Clock.fixed(...)
```

for deterministic scenarios.

This does not define the platform's final timezone policy.

Timezone semantics belong to separate documentation/backlog work.

---

# Availability Overlap Boundary

Current AvailabilitySlot creation performs an application-level overlap check.

The predicate follows half-open interval semantics:

```text
newStart < existingEnd
&&
newEnd > existingStart
```

The final target also requires PostgreSQL to prevent concurrent overlapping active Slots through an exclusion constraint.

That database constraint is not yet implemented.

Detailed Availability state-machine and ownership rules remain in their dedicated documentation scope.

---

# Target Post-Session Flow

After the approved post-session model is implemented, a non-cancelled confirmed Booking will enter the outcome workflow when:

```text
now >= slot.endTime
```

The target lifecycle uses:

```text
SessionOutcome
SessionReport
DisputeResolution
```

for:

```text
participant reporting
automatic resolution
report timeout
UNVERIFIED outcomes
DISPUTED outcomes
administrative resolution
```

This entire post-session model remains target/backlog and is not part of the current request lifecycle implementation.

---

# Error Flow

The current backend already throws typed domain exceptions through the shared hierarchy:

```text
DomainException
→ BaseDomainException
→ semantic category
→ module-specific exception
```

For example:

```text
ReservationExpiredException
ActiveReservationAlreadyExistsException
ReservationOwnershipException
InvalidReservationStateException
```

The final REST translation layer based on centralized:

```text
@ControllerAdvice / @RestControllerAdvice
```

is target/backlog.

Domain and service layers must remain independent from HTTP status codes.

---

# Transaction Rules

Consistency-sensitive state transitions belong to a transactional use case.

Current examples include:

```text
Reservation creation + Slot reservation
Reservation cancellation + Slot release
Reservation expiration + Slot release
Reservation confirmation + Slot booking + Booking creation
Booking cancellation + Slot release
```

Partial persistent state must not remain after a failed operation except where an explicitly designed business failure intentionally persists a state transition, such as expired Reservation handling during confirmation.

# Summary

The current backend request/use-case lifecycle is primarily service-driven.

The final HTTP architecture will wrap those services with:

```text
Security
→ Controller
→ Service
```

without moving business rules into the transport layer.

Documentation must continue to distinguish already implemented service/domain behavior from approved but not yet implemented API/security and post-session workflows.
