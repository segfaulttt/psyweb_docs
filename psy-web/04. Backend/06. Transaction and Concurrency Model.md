## Overview

This section defines how the system handles concurrent operations in the booking domain. The primary goal is to guarantee data consistency under high concurrency, especially in scenarios where multiple clients attempt to book the same availability slot simultaneously.

The booking system is designed as a strongly consistent transactional system.

---

# Core Problem

The critical concurrency problem in the system is:

> Multiple clients attempting to book the same availability slot at the same time.

This can lead to:

- double booking
- inconsistent slot state
- race conditions between service layer and database state

---

# Concurrency Strategy

The system uses a combined approach:

## 1. Database-level constraints

## 2. Transactional service-layer logic

## 3. Locking mechanisms where required

---

# Transactional Boundaries

Consistency-sensitive booking operations are executed within explicit transaction boundaries.

## Reservation Creation

`BookingService.createReservation()`
→ start transaction
→ load and lock AvailabilitySlot when required
→ validate slot is `FREE`
→ validate booking deadline
→ create ACTIVE Reservation
→ transition AvailabilitySlot `FREE → RESERVED`
→ commit transaction

Reservation creation and the slot transition must succeed or fail together.

---

## Reservation Confirmation

`BookingService.confirmReservation()`
→ start transaction
→ load Reservation and associated AvailabilitySlot
→ validate Reservation is ACTIVE and unexpired
→ validate AvailabilitySlot is `RESERVED`
→ transition Reservation to CONFIRMED
→ create Booking
→ transition AvailabilitySlot `RESERVED → BOOKED`
→ commit transaction

Reservation confirmation, Booking creation, and the AvailabilitySlot transition form one atomic operation.

---

## Reservation Cancellation or Expiration

Cancellation or expiration of an ACTIVE Reservation must coordinate:

* Reservation transition to `CANCELLED` or `EXPIRED`;
* AvailabilitySlot transition `RESERVED → FREE`.

The related changes must commit atomically.

---

## Booking Cancellation or Specialist Slot Removal

Booking cancellation and specialist availability removal must also coordinate Booking and AvailabilitySlot state consistently.

Depending on the operation:

* client Booking cancellation: `BOOKED → FREE`;
* specialist availability removal: `BOOKED → CANCELLED`.

Partial persistence is not allowed.

---

# Locking Strategy Options

The system supports two main approaches.

## Option 1. Pessimistic Locking (Recommended for booking)

### Behavior:

- slot row is locked during transaction
- other transactions must wait

### Implementation:

- `SELECT ... FOR UPDATE`

### Pros:

- prevents race conditions completely
- strong consistency guarantee

### Cons:

- reduced throughput under high load

---

## Option 2. Optimistic Locking

### Behavior:

- no lock during read
- version check during update

### Implementation:

- `@Version` field in entity

### Pros:

- higher performance under low contention
- non-blocking reads

### Cons:

- requires retry logic on conflict
- not ideal for high-contention slots

---

# Recommended Strategy for PsyWeb

The highest-contention operation is creation of a temporary Reservation for the same AvailabilitySlot by multiple clients.

The recommended approach is:

## Primary: Pessimistic Locking for Reservation Creation

The AvailabilitySlot row may be locked while validating and creating the Reservation so competing transactions cannot both observe and claim the slot as `FREE`.

## Secondary: Database-Level Integrity Guarantees

The database provides an additional safety layer for critical invariants.

In particular, only one `ACTIVE` Reservation may exist for a slot at a time.

Application-level state checks must not be the only concurrency protection.

---

# Database-Level Protection

Even when application-level locking is used, PostgreSQL protects business-critical persistent invariants.

Database constraints are a safety boundary, not a replacement for transactional domain logic.

---

## 1. One ACTIVE Reservation per Slot

A slot may have multiple historical Reservations, but only one may be `ACTIVE` at a time.

This is enforced with a partial unique index equivalent to:

`reservation(slot_id) WHERE status = 'ACTIVE'`

This protects the temporary hold invariant against concurrent Reservation creation.

---

## 2. One CONFIRMED Booking Occupancy per Slot

`booking.slot_id` is intentionally not globally unique.

A cancelled Booking may release the slot, after which another Reservation and Booking may be created for the same AvailabilitySlot.

Therefore, one slot may have multiple historical Booking records.

However, only one Booking may remain:

`status = CONFIRMED`

for the slot at a time.

This is protected with a partial unique index equivalent to:

`booking(slot_id) WHERE status = 'CONFIRMED'`

The constraint prevents concurrent or inconsistent confirmation flows from producing multiple current Booking occupancies for the same slot while preserving cancelled Booking history.

---

## 3. Reservation Produces at Most One Booking

`booking.reservation_id` is unique.

A Reservation may therefore produce at most one Booking.

This protects against repeated or concurrent confirmation attempts creating duplicate Bookings from the same Reservation.

---

## 4. Concurrent AvailabilitySlot Creation

Two concurrent requests must not both create overlapping active AvailabilitySlots for the same specialist.

A normal application flow still performs overlap validation before persistence.

However:

`query for overlap → observe none → insert`

is not by itself concurrency-safe.

The database must provide a serialization or constraint mechanism that prevents conflicting active intervals from both being committed.

The exact PostgreSQL implementation is finalized separately.

Possible implementation strategies may include:

* an exclusion constraint over specialist and time range;
* another database-backed locking or serialization strategy with equivalent correctness.

The architectural requirement is independent of the final mechanism:

> overlapping active specialist availability cannot be committed successfully by concurrent transactions.

Historical `CANCELLED` slots must not participate in the active-overlap restriction.

---

## 5. Domain State Value Protection

Enum-like domain states persisted as VARCHAR use database CHECK constraints.

The database must reject values outside the currently documented state models.

Application enums and database CHECK constraints must evolve together through Flyway migrations.

---

## 6. Foreign Key Integrity

Foreign keys ensure that:

* Reservation cannot reference a nonexistent AvailabilitySlot;
* Booking cannot reference a nonexistent Reservation;
* Booking cannot reference nonexistent AvailabilitySlot, User, Specialist, or Service records;
* dependent records preserve the relational model expected by transactional business operations.

---

## 7. Defense in Depth

Critical concurrency correctness uses multiple layers:

1. domain and service validation;
2. explicit transaction boundaries;
3. row locking or other concurrency control where required;
4. database constraints for persistable invariants.

No single application pre-check is treated as sufficient protection against concurrent writes.

---

# Transaction Isolation Level

Recommended isolation level:

## READ COMMITTED (default PostgreSQL)

Combined with:

- explicit row locking for critical operations

Higher isolation levels are not required due to explicit locking strategy.

# Reservation Flow Under Concurrency

Consider two clients attempting to reserve the same slot concurrently.

```text
T1 → request Reservation for slot A
T2 → request Reservation for slot A

T1 acquires lock on slot A
T2 waits

T1:
  validates slot status = FREE
  validates booking deadline
  creates ACTIVE Reservation
  updates slot status = RESERVED
  commits

T2:
  acquires lock after T1 commit
  observes slot status = RESERVED
  Reservation creation is rejected
```

The partial unique constraint for an ACTIVE Reservation provides an additional database-level guarantee if concurrent execution reaches persistence unexpectedly.

The result is:

* one successful ACTIVE Reservation;
* one `RESERVED` AvailabilitySlot;
* no conflicting temporary holds;
* no direct Booking creation during this step.

---

# Failure Handling Strategy

When concurrency conflict occurs:

- system throws domain-specific exception
- client receives controlled error response
- no partial updates are allowed

Examples:

- SlotAlreadyBookedException
- BookingConflictException

---

# Consistency Rules

The system enforces the following invariants:

## 1. One ACTIVE Reservation per Slot

A slot may have multiple historical Reservations, but only one Reservation may hold it at a time.

---

## 2. One Active Booking Occupancy per Slot

A slot may have multiple historical Bookings after cancellation and rebooking, but conflicting active occupancy is not allowed.

---

## 3. Reservation Creation Is Atomic

Creating an ACTIVE Reservation and transitioning the slot:

`FREE → RESERVED`

must succeed or fail together.

---

## 4. Reservation Confirmation Is Atomic

The following changes form one consistency-sensitive operation:

* Reservation `ACTIVE → CONFIRMED`;
* Booking creation;
* AvailabilitySlot `RESERVED → BOOKED`.

No partial state may be committed.

---

## 5. Release Operations Are Consistent

Reservation cancellation or expiration must coordinate:

`RESERVED → FREE`

Client Booking cancellation must coordinate:

`BOOKED → FREE`

Specialist availability removal must coordinate the related Reservation or Booking handling with:

`AvailabilitySlot → CANCELLED`

---

## 6. Historical Data Is Preserved

Reservation and Booking history is retained.

Concurrency guarantees restrict current holds and occupancy rather than enforcing a permanent one-Reservation or one-Booking relationship for the lifetime of a slot.

# Integration Test Verification

The concurrency guarantees in this document require PostgreSQL-backed integration verification.

Sequential unit tests are not sufficient proof for behavior involving:

- partial unique constraints;
- database row locking;
- transaction rollback;
- concurrent Reservation creation;
- concurrent AvailabilitySlot creation;
- Booking occupancy constraints.

The required invariant-to-test mapping is defined in:

`16. Integration Test Traceability.md`

Concurrency tests must use independent transactions and intentionally create the conflicting execution window rather than relying on accidental thread scheduling.

- Pessimistic locking introduces contention
- However, booking conflicts are expected behavior in this domain
- System optimizes for correctness, not throughput in booking operations

# Summary

The concurrency model ensures:

- strict prevention of double booking
- transactional integrity of booking flow
- safe handling of concurrent slot requests
- predictable system behavior under load
