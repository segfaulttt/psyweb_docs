
# 06. Транзакционная модель и конкурентная обработка PsyWeb

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**СУБД:** PostgreSQL 16+  
**Язык:** Java 21  
**Базовая изоляция:** READ COMMITTED  
**Статус:** DRAFT — архитектурные решения утверждены, детали реализации требуют проверки

---

# 1. Назначение документа

Документ определяет транзакционную модель PsyWeb и правила конкурентного доступа к данным.

Основная цель — обеспечить строгую согласованность операций записи на консультации при одновременной работе клиентов, специалистов, администраторов и фоновых обработчиков.

Документ описывает:

- источники истины;
- транзакционные границы;
- механизмы PostgreSQL;
- уровни блокировок;
- единый порядок получения ресурсов;
- создание и подтверждение Reservation;
- отмену Booking;
- истечение временных удержаний;
- изменение расписания;
- изменение услуг и настроек специалиста;
- административную блокировку;
- смену часового пояса;
- обработку DST;
- обнаружение и обработку конкурентных конфликтов;
- требования к интеграционному тестированию.

Основные бизнес-решения зафиксированы. Окончательная SQL-реализация и поведение Hibernate должны быть проверены до реализации критических сценариев.

# 2. Архитектурные принципы

## 2.1. Strong consistency

Операции, изменяющие Reservation, Booking и ScheduleOccupancy, требуют строгой согласованности.

Недопустимы:

- двойное бронирование;
- подтверждение истёкшей Reservation;
- существование ACTIVE Reservation без необходимого удержания;
- потеря согласованной Booking при изменении расписания;
- освобождение чужой Occupancy;
- частично выполненная отмена;
- противоречивое состояние после административной блокировки.

## 2.2. Атомарность

Операции, относящиеся к одному бизнес-сценарию, выполняются в одной транзакции PostgreSQL.

Если какая-либо обязательная часть операции не выполнена, вся операция откатывается.

## 2.3. Минимальная область блокировки

Обычная запись клиента не должна блокировать все остальные записи специалиста.

Предпочтительны:

- совместные блокировки конфигурации;
- advisory locks конкретных календарных дат;
- строковые блокировки конкретных Reservation;
- ограничения PostgreSQL.

## 2.4. Database as final safeguard

Предварительные проверки приложения недостаточны.

Критические инварианты дополнительно защищаются ограничениями PostgreSQL.

## 2.5. Многопроцессная корректность

Механизмы конкурентности должны работать при нескольких экземплярах PsyWeb.

Java synchronized, ReentrantLock и другие локальные JVM-блокировки не могут быть единственной защитой.

# 3. Источники истины

| Модель | Ответственность |
|---|---|
| ServiceOffering | Текущие условия услуги |
| SpecialistBookingAccess | Допуск специалиста к новым записям |
| SpecialistBookingPolicy | Текущие правила предварительной записи и отмены |
| SpecialistScheduleSettings | Режим и горизонт расписания |
| SpecialistTimeZoneGuard | Согласованность временной конфигурации |
| WeeklyScheduleVersion | Версионируемые регулярные рабочие часы |
| DateSchedule | Рабочие интервалы отдельной даты |
| Reservation | Временное удержание и исторический snapshot |
| ScheduleOccupancy | Действующая занятость |
| Booking | Подтверждённая запись |
| SessionOutcome | Установленный результат консультации |
| Review | Отзыв клиента на специалиста |

SpecialistBookingAccess, SpecialistBookingPolicy и SpecialistTimeZoneGuard обозначают логические ресурсы.

Их окончательное физическое представление в PostgreSQL определяется при завершении DDL.

**Физическое разделение строк имеет значение для конкурентности:** разные логические ресурсы, расположенные в одной строке PostgreSQL, не обеспечивают независимую блокировку полей.

# 4. PostgreSQL READ COMMITTED

## 4.1. Основной уровень изоляции

Для PsyWeb выбран READ COMMITTED.

Каждый SQL-запрос получает видимость подтверждённых изменений согласно правилам PostgreSQL.

## 4.2. Ограничения

READ COMMITTED самостоятельно не предотвращает:

- конкурентную вставку пересекающихся интервалов;
- изменение расписания между проверкой и вставкой;
- конфликтующие переходы состояния Reservation;
- использование устаревших настроек специалиста.

Поэтому дополнительно применяются:

1. Exclusion constraints.
2. SELECT FOR UPDATE.
3. SELECT FOR SHARE.
4. Transaction-level advisory locks.
5. Повторное чтение данных после блокировок.
6. Атомарные транзакционные команды.

## 4.3. Hibernate persistence context

Повторный запрос из Java не всегда означает получение заново загруженного состояния сущности.

Hibernate может вернуть уже находящуюся в persistence context сущность.

После ожидания блокировок необходимо гарантировать актуальность критических данных.

Допустимые варианты зависят от конкретного запроса:

- явный refresh;
- подходящий locking query;
- повторное чтение в виде DTO/projection;
- корректное управление persistence context.

Сервис не должен принимать решение на основании устаревшего объекта, загруженного до получения блокировки.

# 5. ScheduleOccupancy

## 5.1. Назначение

ScheduleOccupancy представляет действующий занятый интервал специалиста.

Она не является заранее созданным AvailabilitySlot.

## 5.2. Временной интервал

Консультация:

`[sessionStart, sessionEnd)`

Занятость:

`[sessionStart, occupiedUntil)`

Где:

`occupiedUntil = sessionEnd + breakDuration`

Все границы сохраняются как абсолютные моменты времени.

## 5.3. Жизненный цикл

| Событие | Действие с Occupancy |
|---|---|
| Создание Reservation | CREATE |
| Подтверждение Reservation | Сохраняется |
| Отмена ACTIVE Reservation | DELETE |
| Истечение Reservation | DELETE |
| Допустимая отмена Booking | DELETE |
| Достижение occupiedUntil | DELETE при фоновой очистке |
| Подтверждение SessionOutcome | Не влияет |

## 5.4. Отсутствие статуса

Occupancy не содержит:

- FREE;
- RESERVED;
- BOOKED;
- RELEASED;
- EXPIRED.

Также не требуется releasedAt.

Существование строки представляет удерживаемый интервал.

## 5.5. История

Удаление Occupancy не удаляет:

- Reservation;
- Booking;
- cancellation metadata;
- SessionOutcome;
- Review.

# 6. Защита от пересечений

## 6.1. PostgreSQL exclusion constraint

Основной механизм:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE schedule_occupancies
ADD CONSTRAINT ex_occupancy_overlap
EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
);
```

## 6.2. Гарантия

PostgreSQL не позволяет успешно зафиксировать две пересекающиеся Occupancy одного специалиста.

Например:

- A: [14:00, 15:30);
- B: [14:30, 16:00).

Обе строки не могут одновременно существовать.

## 6.3. Соприкасающиеся интервалы

Интервалы:

- A: [14:00, 15:30);
- B: [15:30, 16:30).

Не пересекаются.

## 6.4. Ограничения exclusion constraint

Ограничение не проверяет:

- рабочие интервалы;
- действующий режим расписания;
- активность услуги;
- допуск специалиста;
- минимальный срок записи;
- горизонт доступности;
- временной пояс.

Эти проверки выполняются в согласованных транзакционных сценариях.

# 7. Типы блокировок

## 7.1. SELECT FOR SHARE

Используется для согласованного чтения конфигурации, которую параллельно нельзя изменять.

Примеры:

- ServiceOffering;
- SpecialistBookingAccess;
- SpecialistBookingPolicy;
- SpecialistTimeZoneGuard.

Несколько транзакций могут одновременно удерживать совместные блокировки одной строки.

Конкурентный UPDATE этой строки должен ожидать освобождения несовместимых блокировок.

## 7.2. SELECT FOR UPDATE

Используется при изменении бизнес-состояния или сериализации отдельных команд.

Примеры:

- Reservation;
- Booking;
- SpecialistScheduleSettings при редактировании конфигурации;
- SpecialistBookingAccess при административной блокировке;
- SpecialistTimeZoneGuard при смене ZoneId.

## 7.3. Transaction-level advisory locks

Используются для календарной координации.

Основная PostgreSQL-функция:

`pg_advisory_xact_lock`

Блокировки автоматически освобождаются при COMMIT или ROLLBACK.

## 7.4. Почему не глобальная блокировка Specialist

Блокировать строку Specialist при каждой Reservation не требуется.

Это необоснованно сериализовало бы независимые записи на разные даты.

Вместо этого операции блокируют только необходимые ресурсы.

# 8. Ключи календарных advisory locks

## 8.1. Логический ключ

Календарная блокировка однозначно определяется парой:

`(specialistId, localDate)`

Для разных специалистов и дат используются логически разные блокировки.

## 8.2. Представление

Предпочтительный вариант:

```text
namespace = CALENDAR_DAY
specialistId = Long
localDate = LocalDate

→ stable 64-bit lock key
```

Полученный ключ передаётся в PostgreSQL как BIGINT.

## 8.3. Требования

Алгоритм должен быть:

- детерминированным;
- стабильным между запусками;
- одинаковым во всех экземплярах;
- независимым от JVM identity;
- независимым от случайной соли;
- независимым от локального часового пояса сервера.

## 8.4. Коллизии

При хешировании нескольких значений в 64 бита теоретически возможны коллизии.

Коллизия приводит к избыточному ожиданию независимых операций.

Она не должна приводить к пропуску обязательной общей блокировки для одинаковой логической пары.

Используется стабильная качественная 64-битная функция.

Её точный алгоритм фиксируется перед реализацией.

## 8.5. Пространства имён

Ключи календарных блокировок не должны намеренно пересекаться с ключами других логических ресурсов.

При появлении новых видов advisory locks схема имён должна оставаться согласованной.

## 8.6. Порядок

При необходимости получить несколько дневных блокировок все операции используют один стабильный порядок.

Например:

`localDate ASC`

Нельзя захватывать даты в порядке обхода HashSet или другой структуры с непредсказуемой итерацией.

# 9. SpecialistBookingAccess

## 9.1. Назначение

Логический ресурс управляет допуском специалиста к новым Reservation.

Он отделён от обычного редактирования профиля.

## 9.2. Создание Reservation

Транзакция получает:

`SpecialistBookingAccess FOR SHARE`

Затем проверяет разрешённость новых записей.

## 9.3. Подтверждение Reservation

Подтверждение также получает:

`SpecialistBookingAccess FOR SHARE`

До блокировки конкретной Reservation.

Это необходимо для согласования с административной блокировкой.

## 9.4. Административная блокировка

Административная команда использует:

`SpecialistBookingAccess FOR UPDATE`

После её успешного завершения новые Reservation и подтверждения запрещаются.

## 9.5. Параллельность

Несколько клиентов могут одновременно читать BookingAccess под FOR SHARE.

Это не превращает обычные резервирования в последовательные операции.

---

# 10. SpecialistBookingPolicy

## 10.1. Назначение

Содержит текущие правила:

- minimumBookingNotice;
- clientCancellationNotice.

## 10.2. Чтение при резервировании

При создании Reservation применяется:

`SpecialistBookingPolicy FOR SHARE`

Это предотвращает изменение правил в процессе фиксации согласованных условий.

## 10.3. Изменение

Изменение политики выполняется с эксклюзивной блокировкой соответствующей строки.

## 10.4. MinimumBookingNotice

Дедлайн новой записи:

`bookingDeadline = sessionStart - minimumBookingNotice`

Новая Reservation допустима только при:

`now < bookingDeadline`

Если minimumBookingNotice равен нулю, дедлайн совпадает с sessionStart.

Ранее созданная ACTIVE Reservation может быть подтверждена после изменения настройки, пока не истёк её TTL.

## 10.5. ClientCancellationNotice

Политика отмены фиксируется в snapshot Reservation.

После подтверждения Booking использует именно историческое значение.

Изменение настройки специалистом не изменяет условия уже созданной записи.

## 10.6. Поздняя отмена

Для уже согласованной Booking:

`clientCancellationDeadline = sessionStart - clientCancellationNoticeSnapshot`

Поздняя отмена определяется по cancelledAt относительно этого дедлайна.

В MVP поздняя отмена не влечёт автоматической денежной санкции.

# 11. ServiceOffering FOR SHARE

## 11.1. Проблема

Специалист может изменить:

- длительность консультации;
- перерыв;
- цену;
- валюту;
- активность услуги.

Одновременно клиент может создавать Reservation.

## 11.2. Правило

Reservation фиксирует один согласованный набор условий ServiceOffering.

## 11.3. Блокировка

При создании Reservation используется:

`SELECT ... FOR SHARE`

Для соответствующей ServiceOffering.

## 11.4. Параллельность

Несколько клиентов могут одновременно читать одну ServiceOffering под FOR SHARE.

Они не блокируют друг друга из-за этой строки.

## 11.5. Конкурентное редактирование

Изменение ServiceOffering ожидает завершения транзакций, удерживающих несовместимую блокировку.

## 11.6. Snapshot

В Reservation фиксируются:

- название услуги;
- длительность;
- перерыв;
- цена;
- валюта;
- применимые исторические правила отмены;
- согласованное время.

## 11.7. Порядок

Сначала загружаются согласованные условия услуги, затем рассчитывается полный занятый интервал и определяются необходимые календарные блокировки.

Нельзя проверить расписание для одной длительности и создать Occupancy с другой.

---

# 12. SpecialistTimeZoneGuard

## 12.1. Назначение

Защищает интерпретацию локальных календарных дат и рабочего времени при конкурентной смене ZoneId.

## 12.2. Создание Reservation

Использует:

`TimeZoneGuard FOR SHARE`

## 12.3. Изменение расписания

Операции, которым нужна стабильная временная интерпретация, также используют совместную блокировку TimeZoneGuard.

## 12.4. Изменение timeZone

Использует:

`TimeZoneGuard FOR UPDATE`

## 12.5. Параллельность

Несколько резервирований могут одновременно читать временную конфигурацию.

Изменение ZoneId дожидается завершения операций, использующих прежнюю конфигурацию.

## 12.6. Важный инвариант

ZoneId должен оставаться стабильным на протяжении всей критической части операции, где:

- локальное время преобразуется в Instant;
- вычисляются календарные даты;
- получаются date advisory locks;
- проверяется расписание;
- создаётся Occupancy.

---

# 13. Транзакционная оркестрация

## 13.1. SchedulingApplicationService

Для межмодульных операций используется прикладной координатор.

Он расположен над модулями:

- Schedule;
- Booking;
- Service;
- Specialist.

## 13.2. Задачи координатора

- определение транзакционной границы;
- получение блокировок;
- повторное чтение конфигурации;
- применение бизнес-правил;
- вызов команд владельцев сущностей;
- согласованное завершение операции.

## 13.3. Запрет циклов

Booking implementation не должен зависеть от Schedule implementation.

Schedule implementation не должен зависеть от Booking implementation.

Координатор может использовать публичные контракты обоих модулей.

## 13.4. Владелец данных

Координатор не становится владельцем Reservation, Booking или Schedule.

Изменение состояния выполняется через соответствующие доменные команды.

---

# 14. Единый порядок блокировок

## 14.1. Принцип

Ресурсы, используемые совместно несколькими сценариями, захватываются в согласованном порядке.

## 14.2. Создание Reservation

Целевой порядок:

```text
BEGIN
    ↓
ServiceOffering FOR SHARE
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
SpecialistBookingPolicy FOR SHARE
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
Вычисление дат и временного интервала
    ↓
Calendar advisory locks ASC
    ↓
Актуальные проверки расписания и занятости
    ↓
При необходимости Reservation FOR UPDATE
для истёкших конфликтующих удержаний
    ↓
INSERT Reservation
    ↓
INSERT ScheduleOccupancy
    ↓
COMMIT
```

## 14.3. Подтверждение Reservation

```text
BEGIN
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
Reservation FOR UPDATE
    ↓
Проверка статуса и TTL
    ↓
UPDATE Reservation
    ↓
INSERT Booking
    ↓
COMMIT
```

## 14.4. Изменение недельного расписания

```text
BEGIN
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
SpecialistScheduleSettings FOR UPDATE
    ↓
Calendar advisory locks ASC
    ↓
Проверка актуальных обязательств
    ↓
Изменение WeeklyScheduleVersion
    ↓
COMMIT
```

## 14.5. Изменение конкретной даты

```text
BEGIN
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
Calendar advisory locks
    ↓
Проверка обязательств
    ↓
Изменение DateSchedule
    ↓
COMMIT
```

## 14.6. Административная блокировка

```text
BEGIN
    ↓
SpecialistBookingAccess FOR UPDATE
    ↓
Reservation rows FOR UPDATE
    ↓
Отмена ACTIVE Reservation
    ↓
DELETE связанных Occupancy
    ↓
Сохранение административного решения
    ↓
COMMIT
```

## 14.7. Ограничения

Порядок для операций отмены Booking, фоновой очистки, изменения графика с явной отменой существующих записей и некоторых FK-блокировок должен быть проверен отдельно.

Не допускается захват календарных advisory locks после получения Reservation row lock, если это может создать обратный порядок с обычным резервированием.

Показанные последовательности являются утверждённой архитектурной основой, но не доказательством отсутствия всех возможных PostgreSQL deadlock.

# 15. Создание Reservation

## 15.1. Основной сценарий

```text
BEGIN

1. Проверить аутентифицированного клиента.

2. Получить ServiceOffering FOR SHARE.

3. Проверить активность услуги.

4. Определить specialistId.

5. Получить SpecialistBookingAccess FOR SHARE.

6. Проверить допуск специалиста.

7. Получить SpecialistBookingPolicy FOR SHARE.

8. Получить SpecialistTimeZoneGuard FOR SHARE.

9. Прочитать ZoneId.

10. Вычислить sessionStart, sessionEnd,
    occupiedUntil и затронутые локальные даты.

11. Проверить правила DST.

12. Захватить Calendar advisory locks.

13. Повторно получить актуальное расписание.

14. Проверить рабочее окно.

15. Проверить сетку начала консультации.

16. Проверить горизонт бронирования.

17. Проверить minimumBookingNotice.

18. Найти конфликтующие Occupancy.

19. Согласованно обработать просроченные
    ACTIVE Reservation, если они конфликтуют.

20. Повторно проверить доступность.

21. Сформировать исторический snapshot.

22. Создать ACTIVE Reservation.

23. Создать ScheduleOccupancy.

24. COMMIT.
```

## 15.2. Атомарность

Reservation и Occupancy создаются в одной транзакции.

## 15.3. Исторические условия

Snapshot не изменяется при последующем обновлении ServiceOffering или SpecialistBookingPolicy.

## 15.4. Конкурентная гарантия

Если другой запрос уже занял пересекающийся интервал, PostgreSQL exclusion constraint отклоняет конфликтующую вставку.

---

# 16. Две конкурентные Reservation

## 16.1. Сценарий

Два клиента одновременно выбирают пересекающиеся интервалы одного специалиста.

## 16.2. Протокол

Обе операции получают календарные блокировки затронутых дат в согласованном порядке.

Первая операция проверяет данные и создаёт Occupancy.

Вторая после ожидания повторно проверяет занятость.

## 16.3. Гарантия

Успешно создаётся не более одной пересекающейся Occupancy.

Даже при ошибке предварительной проверки PostgreSQL не позволяет зафиксировать запрещённое пересечение.

## 16.4. Ошибка

Конфликт преобразуется в доменное исключение, указывающее, что выбранное время уже недоступно.

---

# 17. Reservation против DateSchedule

## 17.1. Сценарий

Клиент резервирует время, пока специалист закрывает или редактирует конкретную дату.

## 17.2. Общая блокировка

Обе операции используют Calendar advisory lock соответствующей даты.

## 17.3. Клиент завершил первым

Специалист видит новую Reservation и применяет правила обработки конфликта.

## 17.4. Специалист завершил первым

Клиент повторно читает график и не может создать Reservation на закрытое время.

## 17.5. Существующие Booking

Подтверждённые Booking не отменяются молча.

Они могут сохраняться даже после изменения доступности для новых записей.

---

# 18. Reservation против WeeklyScheduleVersion

## 18.1. Основная проблема

Изменение регулярного графика затрагивает множество будущих календарных дат.

Блокировка только effectiveFrom недостаточна.

## 18.2. Гибридная стратегия

Для редактирования недельного графика используются:

1. TimeZoneGuard FOR SHARE.
2. SpecialistScheduleSettings FOR UPDATE.
3. Дневные advisory locks защищённого горизонта.
4. Повторная проверка версий и обязательств.

## 18.3. Сериализация редактирования

Два конкурентных изменения недельного графика одного специалиста не выполняются независимо друг от друга.

Их координирует строковая блокировка SpecialistScheduleSettings.

Обычная Reservation не должна получать эту эксклюзивную блокировку.

## 18.4. Горизонт

Максимальный горизонт новых записей — 90 дней.

Для консервативной реализации изменения недельного шаблона рассматривается блокировка полного защищённого горизонта.

## 18.5. Движущийся горизонт

Нельзя вычислить список дат заранее, затем длительно ждать блокировки и не проверить актуальность диапазона.

После получения блокировок повторно проверяется:

- текущая локальная дата;
- действующий горизонт;
- достаточность защищённого диапазона.

Если диапазон стал недостаточным, операция откатывается и повторяется с новым набором дат.

## 18.6. Существующие обязательства

Проверка существующих Booking и Reservation не ограничивается только горизонтом создания новых записей.

Обязательства могут сохраняться за его пределами.

## 18.7. Важное ограничение

Захват полного горизонта — выбранная консервативная стратегия MVP.

Точные границы, допустимый запас и условия повторения необходимо подтвердить интеграционными тестами.

## 18.8. Сохранение версий

Изменения WeeklyScheduleVersion и WeeklyWorkingInterval выполняются атомарно.

Пересечение периодов версий запрещается ограничением PostgreSQL.

---

# 19. Подтверждение Reservation

## 19.1. Предусловия

Reservation должна:

- существовать;
- принадлежать соответствующему клиенту;
- иметь статус ACTIVE;
- не быть просроченной;
- иметь необходимое удержание времени;
- допускать подтверждение с учётом состояния специалиста.

## 19.2. Блокировки

Сначала:

`SpecialistBookingAccess FOR SHARE`

Затем:

`Reservation FOR UPDATE`

## 19.3. Проверка времени

После получения блокировки Reservation определяется свежий момент времени.

Условие:

`now < expiresAt`

При равенстве подтверждение недопустимо.

## 19.4. Изменения

В одной транзакции:

- Reservation → CONFIRMED;
- создаётся Booking;
- Occupancy сохраняется.

## 19.5. Защита от повторного подтверждения

UNIQUE(bookings.reservation_id) предотвращает повторное создание Booking для одной Reservation.

---

# 20. Истечение Reservation

## 20.1. TTL

TTL фиксирован платформой и не управляется специалистом.

## 20.2. Scheduler

Периодическая задача выбирает Reservation:

`status = ACTIVE AND expiresAt <= now`

## 20.3. Обработка

```text
BEGIN

1. Получить Reservation FOR UPDATE.

2. Повторно проверить статус.

3. Получить актуальное время.

4. Проверить expiresAt <= now.

5. Изменить статус на EXPIRED.

6. Удалить Occupancy.

7. COMMIT.
```

## 20.4. Пакетная обработка

Допускается SELECT FOR UPDATE SKIP LOCKED.

Это позволяет конкурентным обработчикам пропускать занятые строки.

Пропущенные Reservation должны быть обработаны последующими запусками.

## 20.5. Идемпотентность

Повторная обработка EXPIRED Reservation не должна изменять её повторно.

---

# 21. Confirm против Expire

## 21.1. Проблема

Подтверждение и истечение могут одновременно изменить одну Reservation.

## 21.2. Защита

Обе операции используют Reservation FOR UPDATE.

## 21.3. Подтверждение первым

Если подтверждение законно завершилось до дедлайна:

- Reservation становится CONFIRMED;
- создаётся Booking;
- Occupancy сохраняется.

Scheduler больше не истекает эту Reservation.

## 21.4. Истечение первым

Если Reservation уже EXPIRED:

- подтверждение невозможно;
- Booking не создаётся;
- Occupancy освобождена.

## 21.5. PostgreSQL now()

PostgreSQL now() возвращает время начала транзакции.

Поэтому после ожидания блокировки нельзя считать его свежим временем.

Для дедлайна используется согласованный источник времени, полученный после ожидания.

---

# 22. Освобождение просроченного удержания при новой записи

## 22.1. Проблема

Scheduler может опоздать.

ACTIVE Reservation уже истекла по expiresAt, но её Occupancy ещё существует.

## 22.2. Утверждённое правило

Создание новой Reservation может согласованно обработать конфликтующее просроченное удержание.

## 22.3. Действия

1. Найти конфликтующую Occupancy.
2. Определить исходную Reservation.
3. Получить необходимую строковую блокировку.
4. Повторно проверить статус и expiresAt.
5. Если Reservation всё ещё ACTIVE и истекла — перевести в EXPIRED.
6. Удалить её Occupancy.
7. Повторно проверить свободное время.
8. Продолжить создание новой Reservation.

## 22.4. Ограничение

Нельзя удалять Occupancy, не проверив исходную Reservation.

Нельзя освобождать Occupancy CONFIRMED Booking из-за истечения старого TTL Reservation.

## 22.5. Конкурентность

Операция использует общий порядок блокировок.

Scheduler не должен захватывать календарные advisory locks после получения Reservation row lock.

---

# 23. Отмена Reservation

## 23.1. Операция

Отмена ACTIVE Reservation выполняется атомарно.

## 23.2. Изменения

- Reservation → CANCELLED;
- фиксируется cancelledAt;
- фиксируется cancellationInitiator;
- фиксируется причина при необходимости;
- удаляется Occupancy.

## 23.3. История

Reservation сохраняется.

## 23.4. Конкурентность

Отмена должна быть согласована с подтверждением и истечением Reservation.

Все переходы одной Reservation используют совместимую строковую блокировку и повторную проверку состояния.

---

# 24. Отмена Booking

## 24.1. Основной сценарий

В одной транзакции:

1. Проверить инициатора.
2. Получить необходимые блокировки.
3. Проверить допустимость отмены.
4. Определить своевременность.
5. Перевести Booking в CANCELLED.
6. Сохранить cancellation metadata.
7. Удалить Occupancy.
8. Выполнить COMMIT.

## 24.2. Исторические условия

Используется clientCancellationNoticeSnapshot.

Текущая политика специалиста не изменяет условия ранее созданной Booking.

## 24.3. Поздняя отмена

Клиент может отменить Booking после дедлайна своевременной отмены, но до начала консультации.

Отдельный статус LATE_CANCELLED не требуется.

## 24.4. После начала консультации

Обычная клиентская отмена запрещена.

## 24.5. Порядок строковых блокировок

Если операция одновременно изменяет Reservation и Booking, используется согласованный порядок:

`Reservation → Booking`

При необходимости сначала определяется reservationId без получения конфликтующей строковой блокировки Booking.

---

# 25. Очистка Occupancy после occupiedUntil

## 25.1. Утверждённое решение

После occupiedUntil Occupancy удаляется фоновой очисткой.

## 25.2. Особенность

Очистка не связана с подтверждением SessionOutcome.

## 25.3. Проверки

Перед удалением необходимо исключить противоречивые состояния, например ACTIVE Reservation без завершённой обработки TTL.

## 25.4. Задержка очистки

Допустима.

Интервал, завершившийся в прошлом, не пересекается с новыми будущими интервалами.

## 25.5. Сохранение истории

Reservation и Booking остаются в базе.

---

# 26. Административная блокировка специалиста

## 26.1. Утверждённое бизнес-правило

При административной блокировке специалиста:

- новые Reservation запрещаются;
- все ACTIVE Reservation немедленно отменяются;
- связанные Occupancy освобождаются;
- подтверждённые Booking автоматически не отменяются.

## 26.2. Атомарность

Запрет новых записей и отмена ACTIVE Reservation должны фиксироваться в одной согласованной транзакции.

## 26.3. Основной алгоритм

```text
BEGIN

1. Проверить полномочия администратора.

2. Получить SpecialistBookingAccess FOR UPDATE.

3. Проверить текущий статус допуска.

4. Найти все ACTIVE Reservation специалиста.

5. Получить Reservation FOR UPDATE
   в детерминированном порядке.

6. Повторно проверить их состояния.

7. Перевести оставшиеся ACTIVE Reservation
   в CANCELLED.

8. Установить cancellationInitiator = ADMIN.

9. Удалить их Occupancy.

10. Запретить новые Reservation и подтверждения.

11. Сохранить запись административного действия.

12. COMMIT.
```

## 26.4. Конкурентное создание Reservation

Если Reservation успевает завершиться первой, административная блокировка после получения FOR UPDATE должна обнаружить её и отменить.

Если блокировка завершилась первой, новая Reservation после ожидания получит отказ.

## 26.5. Конкурентное подтверждение

Подтверждение Reservation получает BookingAccess FOR SHARE до Reservation FOR UPDATE.

Поэтому административная блокировка и подтверждение не могут независимо игнорировать состояние допуска.

Если подтверждение законно завершилось первым, создаётся Booking.

Если блокировка получила доступ первой, подтверждение запрещено.

## 26.6. Ограничение

Поведение уже подтверждённых Booking при последующей длительной административной блокировке требует отдельной бизнес-политики.

В текущем MVP они не отменяются автоматически.

---

# 27. Изменение minimumBookingNotice

## 27.1. Изменение политики

Применяется эксклюзивное изменение SpecialistBookingPolicy.

## 27.2. Создание Reservation

Используется совместная блокировка той же политики.

## 27.3. Гарантия

Новая Reservation использует согласованное значение minimumBookingNotice.

## 27.4. Исторические Reservation

Изменение minimumBookingNotice не сокращает TTL уже созданных Reservation и само по себе не запрещает их подтверждение.

---

# 28. Изменение clientCancellationNotice

## 28.1. Изменение

Изменяется текущая SpecialistBookingPolicy.

## 28.2. Новые записи

Получают новое значение при создании Reservation.

## 28.3. Существующие записи

Используют clientCancellationNoticeSnapshot.

## 28.4. Гарантия

Специалист не может задним числом ухудшить условия отмены уже согласованной консультации простым изменением текущей настройки.

---

# 29. Изменение ServiceOffering

## 29.1. Изменение

ServiceOffering редактируется в собственной транзакции.

## 29.2. Конкурентные Reservation

Пока Reservation удерживает FOR SHARE, несовместимое изменение строки ожидает.

## 29.3. Новые условия

После COMMIT изменения новые Reservation используют актуальные параметры.

## 29.4. Исторические записи

Существующие Reservation и Booking не изменяются.

## 29.5. Важное ограничение

Изменение ServiceOffering не должно получать календарные locks в порядке, обратном созданию Reservation.

В утверждённой модели редактирование услуги не изменяет уже существующие Occupancy.

---

# 30. Изменение часового пояса

## 30.1. Утверждённое правило

Специалист может изменить свой timeZone.

## 30.2. Существующие Booking

Сохраняют исходные абсолютные времена Instant.

## 30.3. ACTIVE Reservation

Также сохраняют:

- sessionStart;
- sessionEnd;
- occupiedUntil;
- expiresAt;
- согласованные условия.

Они могут быть подтверждены до TTL по обычным правилам.

## 30.4. WeeklyScheduleVersion

Локальные часы остаются прежними.

После смены timeZone будущая доступность интерпретируется в новом часовом поясе.

## 30.5. DateSchedule

Сохраняются локальная дата и интервалы.

Новая интерпретация производится с новым ZoneId.

## 30.6. Конфликтующие Booking

Если после изменения timeZone существующая Booking оказывается вне нового рабочего графика:

- она не переносится автоматически;
- не отменяется автоматически;
- сохраняет исходный Instant;
- остаётся действующим обязательством.

## 30.7. Предупреждение

При затронутых будущих Booking и ACTIVE Reservation специалист должен получить предупреждение и явно подтвердить изменение.

## 30.8. Транзакционная координация

Изменение timeZone использует:

`SpecialistTimeZoneGuard FOR UPDATE`

Операции, рассчитывающие локальные даты для резервирования или изменения расписания, используют:

`SpecialistTimeZoneGuard FOR SHARE`

## 30.9. Гарантия

Новая Reservation не должна быть создана с частично старой и частично новой интерпретацией календаря.

## 30.10. Сохранение истории

Существующие Instant не пересчитываются.

При необходимости восстановления исторической временной конфигурации потребуется аудит изменения timeZone.

---

# 31. DST

## 31.1. Проблема

При переходах на летнее или зимнее время локальное время может:

- существовать однозначно;
- не существовать;
- существовать дважды.

## 31.2. Утверждённая политика MVP

Новая Reservation запрещается, если выбранное локальное начало консультации неоднозначно или не существует.

## 31.3. Java ZoneRules

Для проверки используется:

`ZoneRules.getValidOffsets(LocalDateTime)`

Возможные результаты:

- 0 offsets — время не существует;
- 1 offset — время однозначно;
- 2 offsets — время неоднозначно.

## 31.4. Отображение доступности

AvailabilityService не должен предлагать запрещённые локальные начала.

## 31.5. Окончательная проверка

ReservationService обязан повторно проверить допустимость времени.

Нельзя полагаться только на результат предварительного поиска доступности.

## 31.6. Существующие Booking

Booking с уже сохранённым Instant не меняется при DST-переходе.

## 31.7. Дополнительное ограничение

Для консультаций, длительность которых пересекает DST-переход, требуется отдельная точная политика расчёта локального и абсолютного окончания.

Она должна учитывать, что локальный час может пропускаться или повторяться.

До её утверждения реализация не должна автоматически считать любое преобразование корректным.

---

# 32. Работа со временем

## 32.1. Instant

Абсолютные времена Reservation, Booking и Occupancy представлены как Instant.

В PostgreSQL используется TIMESTAMPTZ.

## 32.2. Локальный календарь

Рабочий график использует:

- LocalDate;
- LocalTime;
- DayOfWeek;
- ZoneId.

## 32.3. Clock

Для определения текущего времени используется согласованный источник Clock.

Это позволяет тестировать:

- TTL;
- дедлайны;
- границы суток;
- DST;
- конкурентные ожидания.

## 32.4. Проверка после блокировки

Свежий момент времени определяется после получения критической блокировки, если бизнес-правило зависит от фактического времени выполнения операции.

## 32.5. PostgreSQL now()

Не следует использовать PostgreSQL now() как свежий момент после длительного ожидания.

Он представляет начало текущей транзакции.

---

# 33. Failure handling

## 33.1. Бизнес-ошибки

Возможные причины:

- занятое время;
- недопустимый график;
- неактивная услуга;
- заблокированный специалист;
- истёкшая Reservation;
- недопустимая отмена;
- ошибка временного интервала;
- конфликт изменения расписания.

## 33.2. PostgreSQL conflicts

Необходимо обрабатывать:

- unique violation;
- exclusion violation;
- deadlock detected;
- другие ошибки целостности.

## 33.3. Rollback

Неуспешная критическая операция откатывается полностью.

## 33.4. Retry

Повторное выполнение разрешается только для операций с определённой политикой идемпотентности.

Retry выполняет необходимые бизнес-проверки заново.

## 33.5. Транзакции после SQL-ошибки

Нельзя продолжать обычную работу в PostgreSQL-транзакции, которая перешла в ошибочное состояние.

Повторная попытка должна использовать корректную новую транзакционную границу.

# 34. Производительность

## 34.1. Приоритет

Корректность бронирования важнее максимальной пропускной способности.

## 34.2. Совместные блокировки

FOR SHARE позволяет нескольким независимым клиентам одновременно читать согласованную конфигурацию.

## 34.3. Календарные блокировки

Обычное резервирование блокирует только затронутые даты.

## 34.4. Редактирование недельного графика

Может временно блокировать значительно больший календарный диапазон.

Это допустимый компромисс для относительно редкой операции редактирования конфигурации.

## 34.5. Длительность транзакции

Внутри критических транзакций запрещаются неоправданные долгие операции:

- отправка email;
- сетевые запросы;
- ожидание пользовательского ввода;
- длительная внешняя обработка.

## 34.6. Monitoring

Полезные метрики:

- время ожидания блокировок;
- длительность создания Reservation;
- число exclusion conflicts;
- число deadlock;
- задержка expiration scheduler;
- количество устаревших Occupancy;
- длительность обновления недельного графика.

# 35. Тестирование

Критические сценарии должны проверяться на PostgreSQL через интеграционные тесты.

## 35.1. Reservation concurrency

Две пересекающиеся Reservation одного специалиста.

Ожидается не более одной успешной.

## 35.2. Independent dates

Две непересекающиеся Reservation на разные даты.

Обе могут успешно завершиться.

## 35.3. ServiceOffering modification

Reservation и изменение длительности или перерыва.

Snapshot и Occupancy должны соответствовать одному состоянию услуги.

## 35.4. DateSchedule modification

Reservation и закрытие одной даты.

Операции не должны игнорировать друг друга.

## 35.5. WeeklyScheduleVersion modification

Изменение шаблона одновременно с созданием Reservation в затронутом горизонте.

## 35.6. Booking horizon

Увеличение горизонта 14 → 90 дней одновременно с изменением регулярного графика.

## 35.7. Confirm versus Expire

Одновременные операции над одной Reservation.

Не допускается противоречивое состояние.

## 35.8. Expired hold cleanup

Создание Reservation при существующем просроченном удержании.

## 35.9. Administrative blocking

Административная блокировка одновременно с:

- созданием Reservation;
- подтверждением Reservation;
- фоновым истечением Reservation.

После успешной блокировки не остаётся ACTIVE Reservation специалиста.

## 35.10. Time zone change

Смена ZoneId одновременно с созданием Reservation.

Не допускается смешение двух временных конфигураций.

## 35.11. Existing Booking preservation

Смена ZoneId сохраняет существующие абсолютные времена Booking.

## 35.12. DST gap

Невозможное локальное начало запрещено.

## 35.13. DST overlap

Неоднозначное локальное начало запрещено.

## 35.14. Break across midnight

Перерыв, заканчивающийся на следующую календарную дату, корректно учитывается Occupancy и календарными блокировками.

## 35.15. Deadlock

Конкурентные сценарии проверяются на отсутствие воспроизводимых циклов ожидания, обусловленных некорректным порядком получения ресурсов.

## 35.16. Multiple application instances

Механизмы не должны зависеть от локального состояния одной JVM.

# 36. Архитектурные запреты

1. Не использовать AvailabilitySlot как единицу бронирования.
2. Не защищать двойную запись только предварительной проверкой.
3. Не блокировать Specialist FOR UPDATE для каждой Reservation.
4. Не создавать ACTIVE Reservation без Occupancy.
5. Не подтверждать Reservation после expiresAt.
6. Не оставлять ACTIVE Reservation после успешной административной блокировки специалиста.
7. Не отменять существующую Booking автоматически при блокировке специалиста.
8. Не менять исторические условия Booking при обновлении ServiceOffering.
9. Не применять новую clientCancellationNotice задним числом.
10. Не изменять сохранённые Instant при смене timeZone.
11. Не создавать Reservation на неоднозначное или несуществующее локальное начало.
12. Не захватывать календарные locks после Reservation row lock в нарушающем общий порядок сценарии.
13. Не считать READ COMMITTED достаточной защитой без ограничений и блокировок.
14. Не использовать локальные JVM-locks как единственную защиту.
15. Не смешивать проверку SessionOutcome с жизненным циклом Occupancy.
16. Не выполнять внешние уведомления внутри критической транзакции без отдельного обоснования.
17. Не рассчитывать, что Hibernate автоматически перечитает сущность после ожидания PostgreSQL-lock.
18. Не повторять ошибочную транзакцию без нового согласованного контекста.

# 37. Оставшиеся технические вопросы

Перед реализацией необходимо завершить:

## 37.1. PostgreSQL locking

- точный алгоритм формирования 64-битных advisory keys;
- проверку всех смешанных блокировок;
- влияние FK-блокировок;
- порядок Hibernate flush;
- политику retry после deadlock.

## 37.2. Calendar

- точную границу защищённого горизонта;
- поведение изменения горизонта при конкурентных запросах;
- критерии проверки ранее существовавших обязательств.

## 37.3. Time zone

- физическую модель TimeZoneGuard;
- аудит смены ZoneId;
- точную политику консультаций, пересекающих DST-переход.

## 37.4. Business policies

- обработку ACTIVE Reservation при обычном закрытии графика специалистом;
- окончательные правила административных ограничений уже подтверждённых консультаций;
- идемпотентность команд клиента.

## 37.5. Persistence

- соответствие DDL и JPA mapping;
- необходимые составные FK;
- целостность Booking и Reservation при конкурентных обновлениях.

Открытые вопросы не отменяют утверждённые бизнес-правила.

# 38. Итог

PsyWeb использует сильную транзакционную согласованность на базе PostgreSQL.

Основные механизмы:

- READ COMMITTED;
- GiST exclusion constraint;
- SELECT FOR SHARE;
- SELECT FOR UPDATE;
- transaction-level advisory locks;
- явные транзакционные границы;
- повторное чтение после блокировок;
- исторические snapshots;
- централизованная межмодульная оркестрация.

Создание Reservation атомарно создаёт Occupancy.

Подтверждение Reservation сохраняет Occupancy.

Отмена и истечение освобождают занятость.

После occupiedUntil занятость удаляется независимо от SessionOutcome.

Административная блокировка немедленно отменяет ACTIVE Reservation.

Изменение ServiceOffering и SpecialistBookingPolicy не изменяет согласованные условия.

Смена timeZone сохраняет существующие абсолютные времена и изменяет только интерпретацию будущего расписания.

Новая Reservation запрещается на несуществующее или неоднозначное локальное начало при DST.

**Статус: DRAFT — архитектурная стратегия утверждена; окончательный SQL/JPA-протокол требует интеграционной проверки.**
