## Overview

This section defines how the system handles concurrent operations in the booking domain. The primary goal is to guarantee data consistency under high concurrency, especially in scenarios where multiple clients attempt to book the same availability slot simultaneously.

The booking system is designed as a strongly consistent transactional system.

---

# Core Problem

The critical concurrency problem in the system is:

> Multiple clients attempting to book the same availability slot at the same time.

This can lead to:

- double booking
- inconsistent slot state
- race conditions between service layer and database state

---

# Concurrency Strategy

The system uses a combined approach:

## 1. Database-level constraints

## 2. Transactional service-layer logic

## 3. Locking mechanisms where required

---

# Transactional Boundaries

Consistency-sensitive Reservation and Booking operations execute inside explicit service-level transactions.

The current implementation already separates Reservation lifecycle orchestration from Booking confirmation.

---

## Reservation Creation

The current Reservation creation entry point is:

```text
ReservationService.createReservation(...)
```

The operation:

```text
validate clientId / slotId
→ reject an already existing ACTIVE Reservation for the Slot
→ load ACTIVE client
→ reserve the AvailabilitySlot through AvailabilitySlotService
→ obtain current time from injected Clock
→ create ACTIVE Reservation
→ expiresAt = now + ReservationProperties.ttl
→ save and flush Reservation
```

Reservation creation and the Slot transition occur inside one transaction.

The current implementation also relies on the database constraint:

```text
unique_active_reservation_slot
```

as the final protection against multiple ACTIVE Reservations for the same Slot.

If that constraint is violated, the persistence error is translated to:

```text
ActiveReservationAlreadyExistsException
```

---

## Reservation TTL

Reservation TTL is platform-owned configuration.

It is not configured per Specialist.

The current configuration is represented by:

```text
ReservationProperties
```

with prefix:

```text
psyweb.reservation
```

Current properties are:

```text
Duration ttl
Duration expirationScanInterval
int expirationBatchSize
```

The current `application.yml` values are:

```yaml
psyweb:
  reservation:
    ttl: 10m
    expiration-scan-interval: 1m
    expiration-batch-size: 100
```

Reservation creation computes:

```text
createdAt = now
expiresAt = now + ttl
```

The `expiresAt` value stored on the Reservation is the business source of truth.

A Reservation is expired when:

```text
now >= expiresAt
```

Expiration does not depend on whether the background scheduler has already processed the row.

---

## Reservation Confirmation

The current confirmation entry point is:

```text
BookingService.confirmReservation(...)
```

Before checking and mutating Reservation state, the operation loads the Reservation through:

```text
ReservationService.getReservationForUpdate(...)
```

which uses a pessimistic write lock on the Reservation row.

The current flow is conceptually:

```text
lock Reservation
→ obtain current time from Clock
→ validate ownership
→ check expiresAt
→ require ACTIVE status
→ validate client
→ transition AvailabilitySlot RESERVED → BOOKED
→ validate Specialist eligibility
→ transition Reservation ACTIVE → CONFIRMED
→ create CONFIRMED Booking
→ commit
```

The Reservation row lock serializes competing lifecycle operations on the same Reservation.

---

## Expired Confirmation Path

Scheduler cleanup is not the authority for deciding whether a Reservation may still be confirmed.

Confirmation independently evaluates:

```text
now >= expiresAt
```

If the Reservation is already expired at confirmation time:

```text
ACTIVE Reservation
→ EXPIRED

RESERVED AvailabilitySlot
→ FREE
```

and confirmation fails with:

```text
ReservationExpiredException
```

The current confirmation transaction is configured so that this expiration state is not rolled back merely because the confirmation request returns the expiration business error.

This preserves the expired state instead of leaving an overdue Reservation ACTIVE.

---

## Reservation Cancellation

The current cancellation flow uses:

```text
ReservationService.cancelReservation(...)
```

The Reservation is loaded using a pessimistic write lock before mutation.

The operation coordinates:

```text
Reservation ACTIVE → CANCELLED
AvailabilitySlot RESERVED → FREE
```

inside one transaction.

---

## Explicit Reservation Expiration

The current service also supports explicit expiration through:

```text
ReservationService.expireReservation(...)
```

The Reservation is loaded for update before expiration is evaluated.

The operation coordinates:

```text
Reservation ACTIVE → EXPIRED
AvailabilitySlot RESERVED → FREE
```

inside one transaction.

---

# Automatic Reservation Expiration

Automatic cleanup of overdue ACTIVE Reservations is already implemented.

The implementation consists of:

```text
ReservationExpirationScheduler
→ ReservationService.expireExpiredReservations()
→ ReservationRepository
```

The scheduler is an infrastructure trigger only.

It does not directly mutate Reservation or AvailabilitySlot state.

Spring scheduling is enabled in the application configuration.

---

## Scheduler Trigger

`ReservationExpirationScheduler` uses:

```java
@Scheduled(
    fixedDelayString = "${psyweb.reservation.expiration-scan-interval}"
)
```

The current configured interval is:

```text
1 minute
```

The interval is external configuration rather than a hardcoded business constant.

Because fixed delay is used, the next invocation is scheduled after the previous invocation finishes and the configured delay passes.

---

## Expiration Query

Each scheduler run obtains one current timestamp from the injected `Clock`.

It then selects Reservation rows satisfying:

```text
status = ACTIVE
AND
expires_at <= now
```

The query is not restricted to Reservations that expired only during the most recent scan interval.

Therefore, overdue ACTIVE Reservations left behind after application downtime are still eligible for cleanup on a later run.

---

## Batch Processing

The scheduler does not load all overdue Reservations at once.

The configured batch size is currently:

```text
100
```

The repository query uses:

```text
LIMIT :batchSize
```

and deterministic ordering:

```text
ORDER BY expires_at, id
```

This processes the oldest overdue Reservations first and keeps each transaction bounded.

The current service processes one selected batch per scheduler invocation.

Remaining overdue Reservations are eligible for later scheduler runs.

---

## Scheduler Locking

The expiration batch query uses PostgreSQL row locking:

```sql
FOR UPDATE SKIP LOCKED
```

`FOR UPDATE` locks each selected Reservation row for the current transaction.

`SKIP LOCKED` means another concurrent scheduler worker does not wait for already locked Reservation rows.

Instead, it may process different eligible rows.

This allows multiple workers or application instances to perform expiration cleanup without intentionally processing the same locked Reservation concurrently.

No separate distributed-lock service is required for the MVP scheduler.

---

## Expiration Processing

For every selected Reservation, the service verifies expiration against the same captured `now` value.

For a valid overdue ACTIVE Reservation:

```text
Reservation ACTIVE → EXPIRED
AvailabilitySlot RESERVED → FREE
```

The changes execute within the expiration transaction.

Already non-ACTIVE Reservations are excluded by the repository query and are not intentionally reprocessed by the scheduler.

---

## Failure and Recovery

`expiresAt` remains the business source of truth even if a scheduler invocation fails.

If an overdue Reservation remains:

```text
status = ACTIVE
AND
expiresAt <= futureNow
```

a later scheduler run can select it again.

Therefore, ordinary scheduler downtime does not require:

- a recovery table;
- a message broker;
- a separate expiration event store.

The cleanup process catches up by querying all currently overdue ACTIVE rows.

---

# Current Reservation Locking Strategy

The current Booking module uses different persistence mechanisms for different concurrency problems.

## Single Reservation lifecycle operations

For operations such as:

```text
confirmation
cancellation
explicit expiration
```

the Reservation row is loaded with:

```text
PESSIMISTIC_WRITE
```

through:

```text
findForUpdateById(...)
```

This serializes concurrent state changes targeting the same Reservation.

---

## Scheduler expiration batches

For background cleanup, the repository uses:

```text
FOR UPDATE SKIP LOCKED
```

This both protects selected rows and allows multiple workers to make progress without waiting on the same Reservation batch.

---

## ACTIVE Reservation uniqueness

Reservation creation also has database-backed protection:

```text
one ACTIVE Reservation per AvailabilitySlot
```

through the partial uniqueness constraint identified by:

```text
unique_active_reservation_slot
```

The application performs a pre-check for an existing ACTIVE Reservation, while the database remains the final persistence guard under concurrency.

---

# Controlled Time

Reservation lifecycle decisions use an injected:

```text
java.time.Clock
```

rather than directly relying on uncontrolled system time inside business logic.

Current examples include:

- Reservation creation;
- Reservation expiration;
- Reservation confirmation;
- AvailabilitySlot creation;
- Booking cancellation.

Production provides the Clock through:

```text
TimeConfiguration
```

Tests may provide a fixed Clock so temporal boundaries are deterministic.

The exact platform timezone policy is intentionally not defined by this document.

That decision belongs to the separate timezone-policy work and must not be inferred from the existence of the Clock abstraction.

# Database-Level Protection

Even when application-level locking is used, PostgreSQL protects business-critical persistent invariants.

Database constraints are a safety boundary, not a replacement for transactional domain logic.

---

## 1. One ACTIVE Reservation per Slot

A slot may have multiple historical Reservations, but only one may be `ACTIVE` at a time.

This is enforced with a partial unique index equivalent to:

`reservation(slot_id) WHERE status = 'ACTIVE'`

This protects the temporary hold invariant against concurrent Reservation creation.

---

## 2. One CONFIRMED Booking Occupancy per Slot

`booking.slot_id` is intentionally not globally unique.

A cancelled Booking may release the slot, after which another Reservation and Booking may be created for the same AvailabilitySlot.

Therefore, one slot may have multiple historical Booking records.

However, only one Booking may remain:

`status = CONFIRMED`

for the slot at a time.

This is protected with a partial unique index equivalent to:

`booking(slot_id) WHERE status = 'CONFIRMED'`

The constraint prevents concurrent or inconsistent confirmation flows from producing multiple current Booking occupancies for the same slot while preserving cancelled Booking history.

---

## 3. Reservation Produces at Most One Booking

`booking.reservation_id` is unique.

A Reservation may therefore produce at most one Booking.

This protects against repeated or concurrent confirmation attempts creating duplicate Bookings from the same Reservation.

---

## 4. Concurrent AvailabilitySlot Creation

Two concurrent requests must not both create overlapping active AvailabilitySlots for the same specialist.

A normal application flow still performs overlap validation before persistence.

However:

`query for overlap → observe none → insert`

is not by itself concurrency-safe.

The database must provide a serialization or constraint mechanism that prevents conflicting active intervals from both being committed.

The exact PostgreSQL implementation is finalized separately.

Possible implementation strategies may include:

* an exclusion constraint over specialist and time range;
* another database-backed locking or serialization strategy with equivalent correctness.

The architectural requirement is independent of the final mechanism:

> overlapping active specialist availability cannot be committed successfully by concurrent transactions.

Historical `CANCELLED` slots must not participate in the active-overlap restriction.

---

## 5. Domain State Value Protection

Enum-like domain states persisted as VARCHAR use database CHECK constraints.

The database must reject values outside the currently documented state models.

Application enums and database CHECK constraints must evolve together through Flyway migrations.

---

## 6. Foreign Key Integrity

Foreign keys ensure that:

* Reservation cannot reference a nonexistent AvailabilitySlot;
* Booking cannot reference a nonexistent Reservation;
* Booking cannot reference nonexistent AvailabilitySlot, User, Specialist, or Service records;
* dependent records preserve the relational model expected by transactional business operations.

---

## 7. Defense in Depth

Critical concurrency correctness uses multiple layers:

1. domain and service validation;
2. explicit transaction boundaries;
3. row locking or other concurrency control where required;
4. database constraints for persistable invariants.

No single application pre-check is treated as sufficient protection against concurrent writes.

---

# Transaction Isolation Level

Recommended isolation level:

## READ COMMITTED (default PostgreSQL)

Combined with:

- explicit row locking for critical operations

Higher isolation levels are not required due to explicit locking strategy.

# Reservation Flow Under Concurrency

Consider two clients attempting to reserve the same slot concurrently.

```text
T1 → request Reservation for slot A
T2 → request Reservation for slot A

T1 acquires lock on slot A
T2 waits

T1:
  validates slot status = FREE
  validates booking deadline
  creates ACTIVE Reservation
  updates slot status = RESERVED
  commits

T2:
  acquires lock after T1 commit
  observes slot status = RESERVED
  Reservation creation is rejected
```

The partial unique constraint for an ACTIVE Reservation provides an additional database-level guarantee if concurrent execution reaches persistence unexpectedly.

The result is:

* one successful ACTIVE Reservation;
* one `RESERVED` AvailabilitySlot;
* no conflicting temporary holds;
* no direct Booking creation during this step.

---

# Failure Handling Strategy

When concurrency conflict occurs:

- system throws domain-specific exception
- client receives controlled error response
- no partial updates are allowed

Examples:

- SlotAlreadyBookedException
- BookingConflictException

---

# Consistency Rules

The system enforces the following invariants:

## 1. One ACTIVE Reservation per Slot

A slot may have multiple historical Reservations, but only one Reservation may hold it at a time.

---

## 2. One Active Booking Occupancy per Slot

A slot may have multiple historical Bookings after cancellation and rebooking, but conflicting active occupancy is not allowed.

---

## 3. Reservation Creation Is Atomic

Creating an ACTIVE Reservation and transitioning the slot:

`FREE → RESERVED`

must succeed or fail together.

---

## 4. Reservation Confirmation Is Atomic

The following changes form one consistency-sensitive operation:

* Reservation `ACTIVE → CONFIRMED`;
* Booking creation;
* AvailabilitySlot `RESERVED → BOOKED`.

No partial state may be committed.

---

## 5. Release Operations Are Consistent

Reservation cancellation or expiration must coordinate:

`RESERVED → FREE`

Client Booking cancellation must coordinate:

`BOOKED → FREE`

Specialist availability removal must coordinate the related Reservation or Booking handling with:

`AvailabilitySlot → CANCELLED`

---

## 6. Historical Data Is Preserved

Reservation and Booking history is retained.

Concurrency guarantees restrict current holds and occupancy rather than enforcing a permanent one-Reservation or one-Booking relationship for the lifetime of a slot.

# Integration Test Verification

The concurrency guarantees in this document require PostgreSQL-backed integration verification.

Sequential unit tests are not sufficient proof for behavior involving:

- partial unique constraints;
- database row locking;
- transaction rollback;
- concurrent Reservation creation;
- concurrent AvailabilitySlot creation;
- Booking occupancy constraints.

The required invariant-to-test mapping is defined in:

`16. Integration Test Traceability.md`

Concurrency tests must use independent transactions and intentionally create the conflicting execution window rather than relying on accidental thread scheduling.

- Pessimistic locking introduces contention
- However, booking conflicts are expected behavior in this domain
- System optimizes for correctness, not throughput in booking operations

# Summary

The concurrency model ensures:

- strict prevention of double booking
- transactional integrity of booking flow
- safe handling of concurrent slot requests
- predictable system behavior under load
