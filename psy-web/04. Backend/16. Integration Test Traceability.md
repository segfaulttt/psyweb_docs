# Integration Test Traceability

## Overview

This document maps architecture-critical PsyWeb business invariants to the integration-test coverage required to verify them.

It defines the testing contract for consistency-sensitive behavior.

The purpose is not to list every individual JUnit test method.

Instead, each architectural invariant is mapped to:

* the type of integration scenario that must exist;
* the persistent state that must be verified;
* the relevant concurrency or transaction behavior;
* the implementation backlog responsible for introducing the behavior where applicable.

Until a corresponding implementation task is completed, an entry in this document represents required future integration coverage rather than a claim that the test already exists.

---

# Integration Test Environment

Business-critical persistence and concurrency tests must run against PostgreSQL-compatible behavior.

Recommended integration environment:

* Spring Boot test context;
* PostgreSQL through Testcontainers;
* real Spring Data repositories;
* real transaction management;
* production-equivalent Flyway migrations.

An in-memory database must not be treated as sufficient proof for PostgreSQL-specific guarantees such as:

* partial unique indexes;
* row locking;
* transaction behavior;
* PostgreSQL-specific concurrency constraints;
* future exclusion constraints.

For transaction-sensitive scenarios, tests must verify persisted state by reading the database again after the tested operation completes or fails.

# 1. Reservation Exclusivity

## Invariant

For a single AvailabilitySlot:

> at most one Reservation may be ACTIVE at a time.

A slot may retain multiple historical Reservations.

The invariant concerns only the current temporary hold.

## Required Integration Coverage

### Sequential Conflict

Given:

* a FREE AvailabilitySlot;
* one successfully created ACTIVE Reservation.

When:

* another client attempts to create another Reservation for the same slot.

Then:

* the second Reservation is rejected;
* exactly one ACTIVE Reservation exists;
* the slot remains RESERVED;
* no second successful hold is persisted.

### Concurrent Conflict

Given:

* one FREE AvailabilitySlot;
* two eligible clients.

When:

* both clients attempt to reserve the slot concurrently.

Then:

* exactly one request succeeds;
* exactly one ACTIVE Reservation is committed;
* the other request fails with a controlled business conflict;
* the slot ends in RESERVED state;
* no double hold is persisted.

### Database Constraint Protection

The persistence layer must also be tested directly or through an integration scenario demonstrating that the database rejects a second:

`Reservation(status = ACTIVE)`

for the same `slot_id`.

## Verification Level

* Spring + PostgreSQL integration test;
* concurrency integration test;
* database constraint verification.

## Related Implementation Backlog

* Reservation concurrency handling;
* service-layer conflict handling;
* database ACTIVE Reservation uniqueness guarantee.

# 2. AvailabilitySlot State Transitions

## Invariant

AvailabilitySlot follows the documented lifecycle:

* creation → `FREE`
* `FREE → RESERVED`
* `RESERVED → FREE`
* `RESERVED → BOOKED`
* `BOOKED → FREE`
* active state → `CANCELLED`

`CANCELLED` is terminal.

## Required Integration Coverage

### Reservation Creation

Verify:

`FREE → RESERVED`

together with creation of an ACTIVE Reservation.

### Reservation Cancellation

Verify:

`RESERVED → FREE`

together with:

`Reservation → CANCELLED`.

### Reservation Expiration

Verify:

`RESERVED → FREE`

together with:

`Reservation → EXPIRED`.

### Reservation Confirmation

Verify:

`RESERVED → BOOKED`

together with:

* Reservation → CONFIRMED;
* Booking creation.

### Client Booking Cancellation

Verify:

`BOOKED → FREE`

together with:

`Booking → CANCELLED`.

### Specialist Slot Removal

Verify the applicable terminal transitions:

* `FREE → CANCELLED`;
* `RESERVED → CANCELLED`;
* `BOOKED → CANCELLED`.

Associated Reservation or Booking state must remain consistent with the removal workflow.

### Terminal State

Attempting to reactivate a CANCELLED slot must fail.

The persisted slot must remain CANCELLED.

## Verification Level

* Spring + PostgreSQL integration tests;
* persistent lifecycle-state assertions.

# 3. Booking Confirmation Atomicity

## Invariant

Reservation confirmation consists of one consistency-sensitive business operation:

* Reservation `ACTIVE → CONFIRMED`;
* Booking creation;
* AvailabilitySlot `RESERVED → BOOKED`.

The system must never commit only part of this transition.

## Required Integration Coverage

### Successful Confirmation

Given:

* ACTIVE and unexpired Reservation;
* associated RESERVED slot;
* eligible client and specialist.

After confirmation, re-read the database and verify:

* Reservation = CONFIRMED;
* exactly one Booking exists for the Reservation;
* Booking = CONFIRMED;
* AvailabilitySlot = BOOKED.

### Failure During Confirmation

Cause a failure that prevents the confirmation operation from completing.

After the failure, verify that no inconsistent intermediate state remains.

Examples of invalid partial state that must never be committed:

* CONFIRMED Reservation without Booking;
* Booking without BOOKED slot;
* BOOKED slot without corresponding Booking;
* multiple Bookings created from one Reservation.

### Repeated Confirmation

Attempt to confirm the same Reservation more than once.

Verify:

* at most one Booking exists;
* `booking.reservation_id` uniqueness remains intact;
* no duplicate confirmation state is committed.

## Verification Level

* Spring transaction integration test;
* PostgreSQL persistence assertions;
* DB uniqueness constraint verification.

## Related Implementation Backlog

* atomic Reservation confirmation;
* Booking/Reservation cardinality guarantees.

# 4. Reservation Expiration and Rollback Semantics

## Invariant

An expired Reservation must not remain incorrectly ACTIVE merely because confirmation failed with an exception.

If confirmation discovers that the Reservation has expired:

* confirmation is rejected;
* Reservation must persist as EXPIRED;
* associated RESERVED slot must be released to FREE;
* no Booking may be created.

## Required Integration Coverage

### Expired Reservation During Confirmation

Given:

* persisted ACTIVE Reservation;
* persisted RESERVED AvailabilitySlot;
* `expiresAt` already passed.

When:

* confirmation is attempted.

Then:

* confirmation fails;
* after the exception, the test re-reads state from PostgreSQL;
* Reservation is EXPIRED;
* AvailabilitySlot is FREE;
* no Booking exists.

The test must specifically verify committed database state after the exception.

It is not sufficient to assert only the exception type or in-memory entity state.

### Explicit Expiration

When an ACTIVE Reservation expires through the normal expiration workflow:

* Reservation becomes EXPIRED;
* slot becomes FREE;
* both changes remain persistent;
* the historical Reservation is retained.

## Verification Level

* Spring + PostgreSQL integration test;
* transaction-boundary verification;
* post-exception database re-read.

## Related Implementation Backlog

* expired Reservation confirmation rollback fix.

# 5. Rebooking After Cancellation

## Invariant

Client cancellation releases Booking occupancy:

`Booking CONFIRMED → CANCELLED`

`AvailabilitySlot BOOKED → FREE`

Historical Booking data remains stored.

The same slot may later produce another Reservation and Booking if it remains bookable.

## Required Integration Coverage

### Rebooking Before Booking Deadline

Given:

* confirmed Booking;
* client cancels before session start;
* slot returns to FREE;
* booking deadline has not passed.

Verify that:

* original Booking remains CANCELLED;
* a new ACTIVE Reservation may be created;
* the slot transitions to RESERVED again;
* after confirmation, a new Booking is created;
* both historical and current Booking records exist;
* only one Booking remains CONFIRMED.

### Cancellation After Booking Deadline

Given:

* client cancels;
* slot returns to FREE;
* booking deadline has already passed.

Verify that:

* Booking becomes CANCELLED;
* slot becomes FREE;
* a new Reservation is rejected;
* no artificial AvailabilitySlot state is introduced.

This proves the distinction:

`FREE != necessarily bookable`.

## Verification Level

* Spring + PostgreSQL integration tests;
* temporal business-rule verification;
* historical-state persistence assertions.

# 6. Ownership and Eligibility

## Invariant

Reservation operations are not authorized solely because the caller owns an ACTIVE account.

Reservation creation requires:

* `UserRole.CLIENT`;
* `UserStatus.ACTIVE`.

Cancellation and other ownership-sensitive operations require the caller to be the appropriate resource owner or to use an explicitly authorized administrative workflow.

## Required Integration Coverage

### Eligible Reservation Creation

ACTIVE CLIENT may create a Reservation when all slot conditions are satisfied.

### Wrong Role

An ACTIVE User with a non-CLIENT role must not create a client Reservation.

Verify that:

* the operation fails;
* no Reservation is persisted;
* slot state does not change.

### Blocked / Inactive Client

A client that does not satisfy the required account status must not create a Reservation.

Verify no Reservation or slot-state mutation is committed.

### Reservation Ownership

A client must not cancel or confirm another client's Reservation.

Verify:

* operation rejected;
* Reservation state unchanged;
* AvailabilitySlot state unchanged.

### Booking Ownership

Client-owned Booking operations must reject an unrelated client.

### Administrative Exception

Where an administrative workflow is explicitly allowed, verify that it succeeds only through the authorized administrative path rather than by bypassing domain rules.

### Identifier Validation

Public service operations must reject invalid or missing identifiers consistently without performing persistence changes.

## Verification Level

* Spring service integration tests;
* PostgreSQL persistence assertions;
* security/application-authorization integration where endpoint-level authorization is relevant.

## Related Implementation Backlog

* Reservation eligibility and ownership rules;
* Booking/Reservation API ownership rules.

# 7. Database Constraint Guarantees

## Invariant

Business-critical database guarantees must be executable facts, not documentation-only assumptions.

## Required Integration Coverage

The integration suite must prove the behavior of constraints protecting:

### User Email

Duplicate email identity must be rejected according to the finalized normalization policy.

Until that policy is implemented, tests should reflect only the actual stored-value uniqueness behavior.

### Reservation

A second ACTIVE Reservation for one slot is rejected.

### Booking From Reservation

A second Booking for the same Reservation is rejected.

### Active Booking Occupancy

A second CONFIRMED Booking for the same slot is rejected while historical CANCELLED Bookings remain allowed.

### Enum-Like Status Values

The persistence schema must reject values outside documented CHECK constraints.

Application enums and database accepted values must remain aligned.

## Verification Level

* PostgreSQL/Testcontainers integration tests;
* migration-backed schema;
* constraint violation assertions.

# 8. Locking and Concurrency Guarantees

## Invariant

Correctness must hold under genuinely concurrent transactions.

Passing sequential service tests is not sufficient proof of reservation or scheduling exclusivity.

## Required Integration Coverage

### Concurrent Reservation Creation

Run at least two independent transactions against the same FREE slot.

Verify exactly one successful Reservation.

### Reservation Confirmation Conflict

Competing confirmation or persistence attempts must not create:

* multiple Bookings from one Reservation;
* multiple CONFIRMED Booking occupancies for one slot.

### Concurrent AvailabilitySlot Creation

Once the dedicated overlap-concurrency mechanism is implemented, run concurrent attempts to create overlapping active slots for the same specialist.

Verify:

* at most one conflicting interval is committed;
* the other transaction fails;
* historical CANCELLED slots do not incorrectly participate in active overlap protection.

### Lock Release

After the transaction holding a database lock commits or rolls back, competing operations must be able to continue normally.

Tests must not pass merely because both operations happened sequentially by accident.

Concurrency tests should coordinate threads/transactions deliberately so the conflict window actually exists.

## Verification Level

* multithreaded Spring integration test;
* independent database transactions;
* PostgreSQL locking/constraint behavior;
* Testcontainers.

## Related Implementation Backlog

* overlapping AvailabilitySlot race protection;
* Reservation concurrency handling;
* Reservation confirmation atomicity.

# 9. Booking Cutoff and Cancellation Timing

## Invariant

Temporal business rules must remain independent.

### Booking Cutoff

A new Reservation requires:

`currentTime < bookingDeadline`

but an ACTIVE Reservation created before the deadline may still be confirmed after the deadline while:

`currentTime < expiresAt`.

### Client Cancellation

Late cancellation uses the same Booking status:

`CANCELLED`

and lateness is derived from:

`cancelledAt >= clientCancellationDeadline`

before session start.

## Required Integration Coverage

Verify boundary scenarios around:

* immediately before bookingDeadline;
* at/after bookingDeadline;
* Reservation created before cutoff and confirmed after cutoff;
* Reservation expiration independent from cutoff;
* client cancellation before cancellation deadline;
* client cancellation after cancellation deadline but before session start.

Tests should use a controllable application clock rather than relying on real waiting or timing sleeps.

## Verification Level

* Spring + PostgreSQL integration tests;
* deterministic clock/time integration.

# Implementation Traceability Policy

This document defines required architectural verification.

As implementation progresses:

* concrete integration-test classes may be linked to these invariant groups;
* multiple invariants may be verified by one scenario;
* one invariant may require several integration scenarios;
* individual JUnit method names do not belong in architecture documentation unless they materially improve maintainability.

A code change that modifies an architecture-critical invariant must update:

1. the relevant domain or architecture documentation;
2. the database guarantee where applicable;
3. the corresponding integration coverage.

A business invariant is not considered implementation-complete merely because a unit test passes when its correctness depends on:

* database constraints;
* transaction rollback;
* locking;
* concurrent execution;
* Flyway schema behavior.

# Summary

Integration-test traceability focuses on architecture-critical guarantees rather than raw test count.

The required coverage proves:

* Reservation exclusivity;
* AvailabilitySlot state-machine persistence;
* atomic Reservation confirmation;
* correct expiration semantics after failed confirmation;
* cancellation and rebooking behavior;
* role, ownership and eligibility rules;
* database constraint enforcement;
* locking and concurrency guarantees;
* temporal booking and cancellation rules.

The concrete test suite will evolve together with implementation tasks, while this document remains the architectural contract describing what integration behavior must be proven.
