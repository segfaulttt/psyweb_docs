
# 16. Трассировка интеграционных тестов (Integration Test Traceability)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — требования к интеграционному покрытию целевой архитектуры

---

# 1. Назначение документа

Документ связывает критические бизнес-инварианты PsyWeb с интеграционными проверками, необходимыми для подтверждения их корректной реализации.

Основная задача — определить, какие гарантии архитектуры должны быть доказаны тестами.

Документ описывает:

- проверяемый инвариант;
- необходимые сценарии;
- ожидаемое состояние PostgreSQL;
- требования к конкурентному выполнению;
- границы транзакционной проверки;
- связь с будущими задачами реализации.

Документ не является перечнем всех JUnit-тестов.

Один интеграционный тест может проверять несколько инвариантов.

Один инвариант может требовать нескольких независимых тестовых сценариев.

**Наличие сценария в документе не означает, что соответствующий тест уже реализован.**

Фактическое покрытие определяется по исходному коду и результатам запуска тестов.

---

# 2. Целевая модель тестирования

## 2.1. Основной принцип

Бизнес-инварианты, зависящие от PostgreSQL, должны проверяться на PostgreSQL.

Unit tests полезны для проверки отдельных правил, но не заменяют интеграционные тесты:

- транзакций;
- строковых блокировок;
- advisory locks;
- ограничений целостности;
- поведения Hibernate;
- конкурентных операций.

## 2.2. Рекомендуемая среда

Для интеграционных тестов используются:

- Spring Boot Test;
- PostgreSQL через Testcontainers;
- реальные Spring Data JPA Repository;
- реальные транзакции Spring;
- Flyway migrations;
- контролируемый Clock.

## 2.3. Ограничения in-memory баз

H2 и другие in-memory базы не являются достаточным доказательством работы PostgreSQL-специфических механизмов.

Особенно это касается:

- GiST exclusion constraints;
- btree_gist;
- transaction-level advisory locks;
- FOR UPDATE;
- FOR SHARE;
- SKIP LOCKED;
- PostgreSQL SQLSTATE;
- реального поведения конкурентных транзакций.

## 2.4. Проверка сохранённого состояния

Для критических сценариев необходимо проверять состояние данных после завершения операции.

Недостаточно проверить только:

- возвращённый результат;
- выброшенное исключение;
- изменённое поле Java-объекта;
- состояние Hibernate persistence context.

После COMMIT или ROLLBACK данные необходимо повторно прочитать из PostgreSQL в независимом контексте.

## 2.5. Конкурентные тесты

Конкурентные проверки должны использовать независимые транзакции.

Необходимо управлять моментами выполнения так, чтобы действительно воспроизводилось конкурирующее обращение к данным.

Случайный запуск двух потоков без контроля порядка не является достаточным доказательством корректной конкуренции.

# 3. Обновление предметной модели

## 3.1. Отказ от AvailabilitySlot

Целевая архитектура PsyWeb не использует хранимые AvailabilitySlot.

Поэтому больше не требуется подтверждать переходы:

```text id="unab4e"
FREE → RESERVED
RESERVED → BOOKED
BOOKED → FREE
RESERVED → FREE
```

## 3.2. Новая модель

Вместо них используются:

- ServiceOffering;
- WeeklyScheduleVersion;
- DateSchedule;
- Reservation;
- Booking;
- ScheduleOccupancy.

## 3.3. Доступность

Availability рассчитывается динамически.

Свободное время не имеет собственного сохраняемого статуса.

## 3.4. Действующее удержание

При создании ACTIVE Reservation одновременно создаётся ScheduleOccupancy.

После подтверждения Occupancy сохраняется.

При отмене или истечении Reservation Occupancy удаляется.

## 3.5. Защита от пересечений

Вместо уникальности ACTIVE Reservation по slot_id используется запрет пересекающихся Occupancy одного специалиста.

Окончательная защита обеспечивается PostgreSQL exclusion constraint.

# 4. Создание Reservation и Occupancy

## 4.1. Инвариант

Успешное создание Reservation должно атомарно создавать:

- ACTIVE Reservation;
- связанную ScheduleOccupancy.

Недопустимо сохранение только одной из этих сущностей.

## 4.2. Успешный сценарий

Дано:

- ACTIVE клиент;
- активная ServiceOffering;
- специалист с эффективным допуском;
- допустимое время;
- подходящее расписание;
- отсутствие конфликтующей Occupancy.

После создания необходимо проверить:

- Reservation существует;
- Reservation.status = ACTIVE;
- snapshot услуги сохранён;
- expiresAt установлен;
- Occupancy существует;
- Occupancy связана с Reservation;
- границы Occupancy корректны.

## 4.3. Ошибка создания Occupancy

Если INSERT Occupancy завершается ошибкой, Reservation не должна сохраняться как отдельное успешно созданное удержание.

## 4.4. Ошибка сохранения Reservation

Если Reservation не была успешно сохранена, Occupancy также не должна существовать.

## 4.5. Исторические данные

Snapshot должен соответствовать значениям ServiceOffering и BookingPolicy, использованным при создании.

## 4.6. Уровень проверки

- Spring integration test;
- PostgreSQL;
- проверка транзакционного отката;
- повторное чтение из базы.

# 5. Предотвращение пересечения Occupancy

## 5.1. Инвариант

Для одного специалиста не могут одновременно существовать две пересекающиеся ScheduleOccupancy.

## 5.2. Интервальная модель

Используются полуоткрытые интервалы:

`[sessionStart, occupiedUntil)`

## 5.3. Последовательный конфликт

Дано:

- существующая Occupancy;
- новое время, пересекающее её.

При попытке создания второй Reservation:

- операция отклоняется;
- новая Reservation не сохраняется;
- новая Occupancy не сохраняется;
- исходная Occupancy остаётся неизменной.

## 5.4. Конкурентный конфликт

Дано:

- два клиента;
- две конкурентные транзакции;
- пересекающиеся интервалы одного специалиста.

Ожидается:

- не более одной успешной конкурирующей Reservation;
- отсутствие пересекающихся Occupancy;
- контролируемая обработка проигравшей операции.

## 5.5. Соприкасающиеся интервалы

Для интервалов:

```text id="dzw24n"
[10:00, 11:30)
[11:30, 12:30)
```

пересечения нет.

При соблюдении остальных ограничений обе Occupancy допустимы.

## 5.6. Частичное пересечение

Для интервалов:

```text id="d59xr4"
[10:00, 11:30)
[11:15, 12:00)
```

вторая Occupancy должна быть отклонена.

## 5.7. Разные специалисты

Пересекающиеся временные интервалы разных специалистов допускаются.

## 5.8. Ограничение PostgreSQL

Проверяется реальное действие:

```sql
EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
)
```

## 5.9. Уровень проверки

- PostgreSQL constraint integration test;
- concurrent transaction test;
- проверка SQLSTATE 23P01;
- проверка отсутствия частично сохранённой Reservation.

# 6. Кардинальность Reservation и Booking

## 6.1. Инвариант

Одна Reservation может создать не более одной Booking.

## 6.2. Ограничение

PostgreSQL должен обеспечивать:

`UNIQUE(bookings.reservation_id)`

## 6.3. Успешное подтверждение

После подтверждения:

- Reservation.status = CONFIRMED;
- существует одна Booking;
- Booking.status = CONFIRMED;
- первоначальная Occupancy сохраняется.

## 6.4. Повторное подтверждение

Попытка подтвердить Reservation повторно не должна создавать вторую Booking.

## 6.5. Конкурентное подтверждение

Две одновременные операции подтверждения одной Reservation не должны создавать две Booking.

## 6.6. Нарушение UNIQUE

Прямая попытка создать вторую Booking должна быть отклонена PostgreSQL.

## 6.7. Уровень проверки

- Spring integration test;
- PostgreSQL UNIQUE constraint;
- concurrent transaction test.

# 7. Атомарность подтверждения Reservation

## 7.1. Инвариант

Подтверждение представляет одну согласованную бизнес-операцию:

```text id="0ot4gj"
Reservation ACTIVE → CONFIRMED
    +
Booking creation
    +
Occupancy preserved
```

## 7.2. Успешный сценарий

После COMMIT проверяется:

- Reservation = CONFIRMED;
- Booking существует;
- Booking = CONFIRMED;
- Occupancy осталась связанной с Reservation;
- интервал Occupancy не изменился.

## 7.3. Ошибка создания Booking

При ошибке INSERT Booking переход Reservation в CONFIRMED не должен оставаться частично зафиксированным.

## 7.4. Ошибка перехода состояния

Если Reservation нельзя подтвердить, Booking не создаётся.

## 7.5. Повторная операция

Повторное подтверждение не должно менять исторические условия.

## 7.6. Уровень проверки

- Spring transaction integration test;
- post-rollback database verification;
- PostgreSQL constraint test.

# 8. Истечение Reservation

## 8.1. Инвариант

ACTIVE Reservation не может быть подтверждена при:

`now >= expiresAt`

## 8.2. Успешное истечение

После обработки:

- Reservation.status = EXPIRED;
- Occupancy удалена;
- Booking отсутствует;
- Reservation сохранена в истории.

## 8.3. Истечение при подтверждении

Если подтверждение обнаруживает истёкший TTL:

- подтверждение отклоняется;
- переход в EXPIRED сохраняется согласно утверждённому транзакционному протоколу;
- Occupancy удаляется;
- Booking не создаётся.

## 8.4. Проверка rollback semantics

Недостаточно проверить только ReservationExpiredException.

После завершения операции необходимо повторно прочитать PostgreSQL и убедиться, что требуемое состояние действительно зафиксировано.

## 8.5. Граница времени

Проверяются:

- `now < expiresAt`;
- `now = expiresAt`;
- `now > expiresAt`.

## 8.6. Clock

В тестах используется фиксированный или управляемый Clock.

Ожидание реального истечения TTL через Thread.sleep не требуется.

## 8.7. Уровень проверки

- Spring transaction integration test;
- controlled Clock;
- post-exception database re-read.

# 9. Expiration Scheduler

## 9.1. Инвариант

Фоновая обработка должна завершать просроченные ACTIVE Reservation без нарушения конкурентных переходов.

## 9.2. Выборка

Используется:

`FOR UPDATE SKIP LOCKED`

## 9.3. Необходимые сценарии

Проверяются:

1. Обработка просроченной ACTIVE Reservation.
2. Отсутствие повторного истечения CONFIRMED Reservation.
3. Пропуск строк, заблокированных другой транзакцией.
4. Повторная обработка после освобождения блокировки.
5. Идемпотентность повторного запуска.
6. Отсутствие удаления Occupancy подтверждённой Booking.

## 9.4. Конкурентное подтверждение

При конкуренции Confirmation и Expiration результат должен соответствовать тому, какая операция законно получила возможность выполнить переход.

Нельзя допускать состояния:

- CONFIRMED Reservation без Booking;
- EXPIRED Reservation с новой Booking;
- EXPIRED Reservation с оставшейся Occupancy.

## 9.5. Уровень проверки

- PostgreSQL integration test;
- controlled concurrency;
- independent transactions.

# 10. Очистка просроченного удержания

## 10.1. Инвариант

Новая Reservation может освободить конфликтующую просроченную ACTIVE Reservation без ожидания следующего запуска scheduler.

## 10.2. Сценарий

Дано:

- ACTIVE Reservation;
- истёкший expiresAt;
- существующая конфликтующая Occupancy.

При попытке создания новой Reservation:

1. Получаются календарные блокировки.
2. Определяется конфликтующая Reservation.
3. Она блокируется FOR UPDATE.
4. Повторно проверяются status и expiresAt.
5. При подтверждённом истечении выполняется переход в EXPIRED.
6. Occupancy удаляется.
7. Повторно проверяется доступность.
8. Создаются новая Reservation и Occupancy.

## 10.3. Ожидаемое состояние

После COMMIT:

- старая Reservation = EXPIRED;
- старая Occupancy отсутствует;
- новая Reservation = ACTIVE;
- новая Occupancy существует.

## 10.4. Защита CONFIRMED

Если исходная Reservation уже CONFIRMED, её Occupancy не освобождается по TTL.

## 10.5. Конкурентность

Необходимо проверить одновременное выполнение:

- opportunistic expiration;
- scheduler expiration;
- confirmation.

## 10.6. Уровень проверки

- Spring + PostgreSQL integration test;
- concurrent transaction test.

# 11. Отмена ACTIVE Reservation

## 11.1. Инвариант

Отмена ACTIVE Reservation должна одновременно освобождать её Occupancy.

## 11.2. Успешный сценарий

После COMMIT:

- Reservation.status = CANCELLED;
- cancelledAt установлен;
- cancellationInitiator установлен;
- Occupancy удалена;
- Reservation сохранена.

## 11.3. Повторная отмена

Повторная операция не должна создавать противоречивое состояние.

Точная API-семантика повторного запроса определяется отдельно.

## 11.4. Конкурентность

Проверяется отмена одновременно с:

- подтверждением;
- истечением TTL;
- административной блокировкой.

## 11.5. Уровень проверки

- Spring transaction integration test;
- concurrent state-transition test.

# 12. Отмена CONFIRMED Booking

## 12.1. Инвариант

Допустимая отмена Booking приводит к:

```text id="jrye6o"
Booking CONFIRMED → CANCELLED
    +
DELETE Occupancy
```

Исходная Reservation остаётся CONFIRMED.

## 12.2. Успешная отмена

Проверяются:

- Booking.status = CANCELLED;
- Reservation.status = CONFIRMED;
- cancelledAt установлен;
- cancellationInitiator сохранён;
- Occupancy отсутствует;
- Booking остаётся в истории.

## 12.3. Ошибка удаления Occupancy

Если обязательное освобождение Occupancy не выполнено, нельзя фиксировать частичную отмену Booking.

## 12.4. Повторная отмена

Повторный запрос не должен создавать новый переход или менять исторические метаданные без утверждённого основания.

## 12.5. Уровень проверки

- Spring transaction integration test;
- persisted-state assertions.

# 13. Повторное бронирование после отмены

## 13.1. Инвариант

Освобождение Occupancy не означает автоматическую доступность времени.

## 13.2. Повторное бронирование до дедлайна

Дано:

- исходная Booking отменена;
- Occupancy удалена;
- актуальное расписание допускает выбранное время;
- minimumBookingNotice ещё соблюдается.

Ожидается возможность создать новую Reservation.

## 13.3. Повторное бронирование после дедлайна

Если:

`now >= bookingDeadline`

новая Reservation запрещена.

## 13.4. Историческая целостность

После повторной записи:

- исходная CANCELLED Booking сохраняется;
- новая Reservation создаётся отдельно;
- новая Booking возникает после подтверждения;
- исторические записи не перезаписываются.

## 13.5. Изменённое расписание

Если специалист изменил рабочее расписание так, что время больше не является рабочим, отсутствие Occupancy не должно разрешать новую Reservation.

## 13.6. Уровень проверки

- Spring + PostgreSQL integration test;
- controlled Clock;
- historical persistence assertions.

# 14. Booking Deadline и MinimumBookingNotice

## 14.1. Инвариант

Для новой Reservation требуется:

`now < bookingDeadline`

Где:

`bookingDeadline = sessionStart - effectiveMinimumBookingNotice`

## 14.2. Границы

Проверяются:

- до дедлайна;
- ровно в дедлайн;
- после дедлайна.

## 14.3. Нулевой notice

Если minimumBookingNotice равен нулю, дедлайн совпадает с sessionStart.

## 14.4. Независимость TTL

Reservation, созданная до bookingDeadline, может быть подтверждена после этого дедлайна при условии:

`now < expiresAt`

и соблюдении остальных требований подтверждения.

## 14.5. Изменение политики

Изменение minimumBookingNotice не должно задним числом аннулировать существующую ACTIVE Reservation.

## 14.6. Уровень проверки

- deterministic time integration tests;
- BookingPolicy integration.

# 15. ClientCancellationNotice

## 15.1. Инвариант

Условия клиентской отмены фиксируются в snapshot Reservation.

## 15.2. Дедлайн

`clientCancellationDeadline = sessionStart - clientCancellationNoticeSnapshot`

## 15.3. Своевременная отмена

Проверяется отмена до clientCancellationDeadline.

## 15.4. Поздняя отмена

Проверяется отмена:

`cancelledAt >= clientCancellationDeadline`

при:

`cancelledAt < sessionStart`

## 15.5. Начало консультации

При:

`now >= sessionStart`

обычная клиентская отмена запрещена.

## 15.6. Исторический snapshot

Изменение текущего clientCancellationNotice специалиста не должно менять классификацию отмены существующей Booking.

## 15.7. Отсутствие штрафа

Поздняя отмена до начала консультации разрешена для MVP.

Она не создаёт автоматического денежного взыскания.

## 15.8. Статус

Поздняя отмена сохраняет BookingStatus.CANCELLED.

Отдельный LATE_CANCELLED не используется.

## 15.9. Уровень проверки

- controlled Clock;
- Spring + PostgreSQL integration tests;
- snapshot verification.

# 16. Эффективный допуск специалиста

## 16.1. Инвариант

Новая Reservation и подтверждение ACTIVE Reservation требуют эффективного допуска специалиста.

## 16.2. Условия

```text id="h43v71"
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

## 16.3. Основные комбинации

Проверяются:

- ACTIVE / APPROVED / TRUE;
- ACTIVE / APPROVED / FALSE;
- ACTIVE / PENDING / TRUE;
- ACTIVE / REJECTED / TRUE;
- ACTIVE / SUSPENDED / TRUE;
- BLOCKED / APPROVED / TRUE.

## 16.4. Создание Reservation

Если допуск отсутствует:

- Reservation не создаётся;
- Occupancy не создаётся.

## 16.5. Подтверждение

Если допуск утрачен:

- новая Booking не создаётся;
- ACTIVE Reservation обрабатывается согласно согласованному административному протоколу.

## 16.6. Уровень проверки

- Spring + PostgreSQL integration tests;
- eligibility policy verification.

# 17. Административная блокировка специалиста

## 17.1. Инвариант

При административной потере допуска специалиста:

- все ACTIVE Reservation отменяются;
- соответствующие Occupancy удаляются;
- CONFIRMED Booking сохраняются;
- изменение допуска и отмены выполняются атомарно.

## 17.2. Успешный сценарий

Дано:

- специалист имеет несколько ACTIVE Reservation;
- существуют подтверждённые Booking;
- администратор выполняет блокировку.

После COMMIT проверяется:

- эффективный допуск отсутствует;
- ACTIVE Reservation больше нет;
- бывшие ACTIVE Reservation стали CANCELLED;
- cancellationInitiator = ADMIN;
- их Occupancy удалены;
- подтверждённые Booking не изменились;
- Occupancy подтверждённых Booking сохранены;
- административный аудит записан.

## 17.3. Ошибка во время блокировки

При сбое одной из обязательных операций необходимо проверить откат всего административного действия.

Нельзя оставлять частично отменённый набор ACTIVE Reservation при уже зафиксированной блокировке.

## 17.4. Конкурентное создание

Одновременно запускаются:

- создание Reservation;
- административная блокировка.

Проверяется:

- создание до блокировки может успешно завершиться;
- административная операция затем отменяет такую ACTIVE Reservation;
- создание после блокировки отклоняется;
- не остаётся ACTIVE Reservation при запрещённом допуске.

## 17.5. Конкурентное подтверждение

Одновременно выполняются:

- подтверждение ACTIVE Reservation;
- блокировка.

Если подтверждение зафиксировано первым, Booking сохраняется.

Если блокировка зафиксирована первой, подтверждение отклоняется.

## 17.6. Конкурентное истечение

Проверяется взаимодействие административной отмены с Expiration Scheduler.

Недопустимы двойные переходы и несогласованное освобождение Occupancy.

## 17.7. Уровень проверки

- Spring + PostgreSQL integration test;
- независимые конкурентные транзакции;
- lock-order verification;
- post-commit persistence assertions.

# 20. ServiceOffering и snapshots

Reservation сохраняет согласованные условия выбранной ServiceOffering.

## 20.2. Основные значения

Проверяются snapshots:

- title;
- duration;
- breakDuration;
- price;
- currency.

## 20.3. Изменение услуги

После создания Reservation специалист изменяет ServiceOffering.

Необходимо проверить:

- Reservation snapshot не изменился;
- существующая Booking использует исторические условия;

## 20.5. Конкурентность

Создание Reservation одновременно с изменением ServiceOffering должно использовать согласованный протокол FOR SHARE.

# 21. Режимы расписания

Проверяются:

Существующий OVERRIDE полностью заменяет регулярный шаблон даты.

Проверяются:

- отсутствие MANUAL;

## 21.5. Неактивные данные

После смены режима данные прежнего режима сохраняются, но не должны использоваться при расчёте новой доступности.

# 22. Рабочие интервалы

## 22.1. Инвариант

Рабочие интервалы одной конфигурации не должны пересекаться.

## 22.4. Переход через полночь

Рабочие интервалы через локальную полночь запрещены.

## 22.5. Перерыв

Перерыв после консультации может выходить за рабочее окно и пересекать полночь.

## 22.6. Уровень проверки

- Schedule/Availability tests;
- PostgreSQL constraint verification.

# 26. DST

## 26.1. Утверждённое правило

Локальное начало консультации запрещено, если оно:

- не существует в данном ZoneId;
- является неоднозначным.

## 26.2. Gap

Проверяется отсутствие допустимых начал в пропущенном локальном времени.

## 26.3. Overlap

Проверяется запрет неоднозначного локального начала.

## 26.4. Проверка Reservation

Попытка напрямую создать Reservation с запрещённым локальным началом должна быть отклонена независимо от результата предварительного Availability.

## 26.5. Существующие Booking

DST-переход не должен изменять сохранённые абсолютные времена.

## 26.6. Открытый вопрос

Правила консультаций, пересекающих DST-переход, ещё не утверждены.

После согласования потребуется отдельное интеграционное покрытие.

## 26.7. Уровень проверки

- deterministic temporal tests;
- Reservation integration tests.

# 27. Календарные advisory locks

## 27.1. Инвариант

Создание Reservation и изменение рабочего расписания должны использовать согласованный протокол календарных блокировок.

## 27.2. Ключ блокировки

Концептуально:

`(specialistId, localDate)`

Физическое представление ключа должно быть стабильным и детерминированным.

## 27.3. Несколько дат

Если Occupancy затрагивает несколько локальных дат, необходимые блокировки должны захватываться в стабильном порядке.

## 27.4. Разные специалисты

Операции разных специалистов не должны ошибочно сериализоваться из-за коллизий или неправильного построения ключа.

## 27.5. Независимые даты

Создание Reservation на непересекающиеся даты одного специалиста должно допускать независимое выполнение, когда нет другого общего ограничивающего ресурса.

## 27.6. Изменение DateSchedule

Проверяется конкурентное создание Reservation и изменение DateSchedule той же даты.

## 27.7. Изменение WeeklyScheduleVersion

Проверяется конкурентное изменение регулярного шаблона и создание Reservation в затронутом горизонте.

## 27.8. Ожидаемый результат

Новая Reservation должна соответствовать согласованной версии расписания.

Недопустимо создать Reservation на основании устаревшей конфигурации после завершения конфликтующего изменения.

## 27.9. Уровень проверки

- independent PostgreSQL transactions;
- controlled lock acquisition;
- race-condition integration tests.

# 28. Изменение расписания и существующие обязательства

## 28.1. Инвариант

Обычное изменение расписания не отменяет:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 28.2. DateSchedule

Специалист закрывает дату с существующей ACTIVE Reservation.

## 28.4. Смена режима

При переходе REGULAR ↔ FLOATING существующие обязательства остаются действительными.

## 28.5. Предупреждение

Если изменение затрагивает существующие обязательства, проверяется предусмотренный механизм предупреждения и подтверждения.

## 28.6. Уровень проверки

- Schedule integration tests;
- Booking/Reservation integration tests;
- concurrent schedule-modification tests.

# 29. Целостность базы данных

## 29.1. Основной принцип

Бизнес-критические ограничения должны проверяться на уровне реальной схемы PostgreSQL.

## 29.2. User

Проверяются:

## 29.3. Specialist

Проверяются:

## 29.4. ServiceOffering

- внешние ключи.

## 29.5. Schedule

Проверяются:

- корректность временных границ;
- ограничения рабочих интервалов;

## 29.6. Reservation

Проверяются:

- внешние ключи;

## 29.7. Booking

# 30. SessionOutcome

## 30.1. Инвариант

Booking не считается успешно проведённой только на основании достижения sessionEnd.

## 30.2. Независимые отчёты

Клиент и специалист сообщают результат независимо.

## 30.3. OCCURRED

Два совместимых OCCURRED должны приводить к подтверждённо успешному результату.

## 30.4. DID_NOT_OCCUR

Совместимые отрицательные отчёты обрабатываются по утверждённым правилам Outcome.

## 30.5. Один ответ

Если в пределах окна ответила только одна сторона, применяется утверждённое правило разрешения после завершения окна.

## 30.6. Противоречивые отчёты

Несовместимые ответы приводят к спору.

## 30.7. Отсутствие ответов

Если ни одна сторона не ответила, консультация не считается автоматически проведённой.

## 30.8. Окно

Проверяются границы 24-часового периода после завершения консультации.

## 30.9. Уровень проверки

- Outcome integration tests;
- controlled Clock;
- PostgreSQL persistence assertions.

# 31. Разрешение споров Outcome

## 31.1. Инвариант

Противоречивый результат консультации не должен разрешаться произвольно одним из участников.

## 31.2. Полномочия

Решение принимает уполномоченный ADMIN.

## 31.3. Атомарность

Административное решение и изменение SessionOutcome должны сохраняться согласованно.

## 31.4. Повторное решение

Недопустимое повторное разрешение спора должно отклоняться либо обрабатываться по специально утверждённому сценарию пересмотра.

## 31.5. Review

Если результат признан успешно проведённым, он может создать основание для Review.

Если результат не подтверждает проведение, право на Review не возникает.

## 31.6. Уровень проверки

- Admin/Outcome integration tests;
- authorization verification;
- persisted-state assertions.

# 32. Review

## 32.1. Инвариант

Один клиент может иметь только один Review на одного специалиста.

## 32.2. Уникальность

Проверяется:

`UNIQUE(client_id, specialist_id)`

## 32.3. Eligibility

Создание Review требует хотя бы одной подтверждённо успешной консультации.

## 32.4. Недостаточные основания

Создание Review запрещено, если существует только:

- CONFIRMED Booking;
- неподтверждённый Outcome;

Клиент может изменять собственные rating и comment.

## 32.6. Неизменяемые поля

При редактировании сохраняются:

- clientId;
- specialistId;
- eligibilityBookingId;
- createdAt.

## 32.7. Конкурентное создание

Два одновременных запроса создания Review одной пары не должны создавать две строки.

## 32.8. Уровень проверки

- Review integration tests;
- PostgreSQL UNIQUE;
- composite FK;
- concurrent transaction test.

# 33. Notification и события

## 33.1. Инвариант

Notification не должен представлять незафиксированное бизнес-действие как успешно выполненное.

## 33.2. Rollback

Если Booking transaction откатилась, внешнее уведомление об успешном подтверждении не должно быть отправлено.

## 33.3. После COMMIT

События обрабатываются после успешной фиксации соответствующих изменений.

## 33.4. Доставка

Ошибка доставки Notification не должна откатывать уже зафиксированную Booking.

## 33.5. Идемпотентность

Если реализована повторная обработка событий, необходимо проверить отсутствие нежелательных дубликатов Notification.

## 33.6. Transactional outbox

Если выбран outbox, дополнительно проверяются:

- атомарность записи бизнес-состояния и OutboxEvent;
- повторное чтение;
- обработка после сбоя;
- конкурентные обработчики.

## 33.7. Уровень проверки

- event-processing integration tests;
- PostgreSQL transactions;
- delivery adapter tests, если внешняя доставка реализована.

# 34. Обработка ошибок PostgreSQL

## 34.1. UNIQUE

Проверяется правильная предметная интерпретация известных UNIQUE violations.

## 34.2. Exclusion constraint

Нарушение Occupancy exclusion constraint должно приводить к контролируемой ошибке конфликта бронирования.

## 34.3. Deadlock

Deadlock не должен автоматически трактоваться как занятое время консультации.

## 34.4. Rollback

После SQL-ошибки не должно оставаться частично сохранённого бизнес-состояния.

## 34.5. Retry

Если реализован retry, он должен начинаться в новой транзакции и повторять необходимые проверки.

## 34.6. Уровень проверки

- PostgreSQL integration tests;
- constraint identification;
- transaction-boundary verification.

# 35. Конкурентные тесты

## 35.1. Независимость транзакций

Необходимо запускать реальные независимые транзакции.

## 35.2. Управление порядком

Тест должен управлять моментами:

- получения блокировки;
- ожидания;
- изменения состояния;
- COMMIT;
- повторной проверки.

## 35.3. Недостаточность Thread.sleep

Thread.sleep сам по себе не гарантирует, что нужное пересечение транзакций действительно произошло.

## 35.4. Обязательные сценарии

Необходимо проверить:

1. Две Reservation на пересекающиеся интервалы.
2. Подтверждение и истечение одной Reservation.
3. Подтверждение и отмену одной Reservation.
4. Создание Reservation и изменение DateSchedule.
5. Создание Reservation и изменение WeeklyScheduleVersion.
6. Создание Reservation и изменение ServiceOffering.
7. Создание Reservation и изменение TimeZoneGuard.
8. Создание Reservation и административную блокировку.
9. Подтверждение Reservation и административную блокировку.
10. Expiration Scheduler и административную отмену.
11. Повторное создание Review.
12. Конкурентное редактирование Review, если выбран соответствующий механизм защиты.

## 35.5. Проверка завершения

После всех конкурентных операций необходимо повторно прочитать итоговое состояние PostgreSQL.

## 35.6. Deadlock

Тесты должны выявлять несогласованный порядок блокировок, а не маскировать его неограниченными повторными попытками.

# 37. Политика актуализации тестового покрытия

## 37.1. Назначение

Документ определяет требования к будущим интеграционным тестам.

## 37.2. Связь с реализацией

После реализации сценариев допускается дополнять трассировку ссылками на:

- конкретные тестовые классы;
- соответствующие Jira-задачи;
- миграции Flyway;
- архитектурные решения.

## 37.3. Необязательность перечня методов

Не требуется перечислять в архитектурной документации каждый JUnit test method.

## 37.4. Изменение инварианта

При изменении критического бизнес-инварианта необходимо пересмотреть:

1. предметную документацию;
2. ограничения PostgreSQL;
3. интеграционное покрытие;
4. связанные API-контракты при необходимости.

## 37.5. Критерий завершённости

Бизнес-инвариант не считается полностью проверенным только на основании unit test, если его корректность зависит от:

- PostgreSQL constraints;
- транзакционного отката;
- конкурентного выполнения;
- строковых блокировок;
- advisory locks;
- Flyway schema.

## 37.6. Фактическое покрытие

Статус реализации интеграционных тестов должен определяться по актуальному исходному коду и результатам тестового запуска.

Нельзя отмечать сценарий реализованным только потому, что он перечислен в этой матрице.
