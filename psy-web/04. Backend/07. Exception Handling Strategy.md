## Overview

This section defines the global error handling strategy of the PsyWeb backend system. The goal is to ensure consistent, predictable, and structured error responses across all modules.

The system avoids leaking internal exceptions to clients and standardizes error representation at the API level.

---

# Global Strategy

The backend uses a centralized exception handling mechanism based on Spring’s `@ControllerAdvice`.

All exceptions are:

- translated into structured HTTP responses
- mapped to meaningful error codes
- separated into domain and system-level errors

---

# Exception Categories

The system defines three main categories of exceptions:

---

## 1. Business Exceptions

These represent domain rule violations.

Examples:

- SlotAlreadyBookedException
- BookingConflictException
- ReviewNotAllowedException
- CancellationNotAllowedException

Characteristics:

- expected runtime conditions
- safe to expose to client
- mapped to 4xx responses

---

## 2. Authentication and Authorization Exceptions

Examples:

- InvalidCredentialsException
- UnauthorizedAccessException
- AccessDeniedException

Characteristics:

- related to security context
- mapped to 401 or 403 HTTP codes

---

## 3. System Exceptions

Examples:

- DatabaseConnectionException
- UnexpectedNullStateException
- ExternalServiceException

Characteristics:

- internal failures
- not exposed directly to client
- mapped to 500 Internal Server Error

---

# Standard Error Response Format

All exceptions are returned in a unified structure:

```
{  "timestamp": "2026-01-01T12:00:00Z",  "status": 400,  "error": "BAD_REQUEST",  "message": "Slot is already booked",  "path": "/api/bookings"}
```

---

# HTTP Status Mapping

## 400 Bad Request

- validation errors
- invalid request payload
- business rule violations

---

## 401 Unauthorized

- missing JWT
- invalid JWT
- expired token

---

## 403 Forbidden

- valid authentication
- insufficient permissions

---

## 404 Not Found

- requested entity does not exist
- invalid resource reference

---

## 409 Conflict

- concurrency violations
- double booking attempts
- state conflicts

---

## 500 Internal Server Error

- unexpected system failures
- unhandled exceptions
- infrastructure issues

---

# Global Exception Handler

The system uses a centralized handler:

Responsibilities:

- catch all exceptions
- map exceptions to HTTP responses
- ensure consistent response format
- hide internal stack traces from clients

---

# Validation Error Handling

Request validation errors are handled separately:

- DTO validation errors are collected
- returned as structured field-level errors

Example:

```
{  "status": 400,  "error": "VALIDATION_ERROR",  "fields": {    "email": "must be a valid email",    "password": "must not be blank"  }}
```

---

# Domain Exception Design Rule

Each business module defines its own exceptions.

Example:

- booking module → BookingConflictException
- availability module → SlotAlreadyBookedException

This ensures:

- domain isolation
- clear responsibility boundaries

---

# Logging Strategy

- Business exceptions: logged at INFO or WARN level
- System exceptions: logged at ERROR level with stack trace
- Authentication failures: logged without sensitive data

---

# Key Design Principles

## 1. No raw exceptions to client

Internal errors must always be transformed.

## 2. Consistent response format

All errors follow unified schema.

## 3. Domain-driven exceptions

Each module owns its own error types.

## 4. Clear separation of error types

Business vs security vs system failures.

---

# Summary

The exception handling strategy ensures:

- predictable API error behavior
- clean separation of domain and infrastructure errors
- safe exposure of error information to clients
- maintainable and scalable error structure across modules
