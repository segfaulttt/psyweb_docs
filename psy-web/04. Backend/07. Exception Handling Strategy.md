
# 07. Стратегия обработки исключений (Exception Handling Strategy)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — существующая иерархия сохранена, целевая модель ошибок требует реализации

---

# 1. Назначение документа

Документ определяет стратегию обработки ошибок backend PsyWeb.

Основные задачи:

- единое представление ожидаемых бизнес-ошибок;
- сохранение устойчивых машинных кодов ошибок;
- разделение ошибок по их смыслу;
- локализация конкретных исключений внутри модулей-владельцев;
- преобразование известных конфликтов PostgreSQL в предметные ошибки;
- централизованная обработка ошибок REST API;
- защита внутренних технических сведений;
- согласованное поведение транзакций при ошибках.

В PsyWeb необходимо различать:

1. Ошибки валидации входных данных.
2. Ошибки существования ресурсов.
3. Ошибки авторизации.
4. Конфликты с текущим состоянием данных.
5. Недопустимые переходы состояний.
6. Истечение временных ограничений.
7. Ошибки инфраструктуры и программирования.

Не каждая ошибка должна приводить к одинаковому HTTP-ответу.

Не каждое исключение является доменным.

---

# 2. Текущее состояние реализации

В исходной реализации PsyWeb уже существует общая иерархия доменных исключений.

Она включает:

- DomainException;
- BaseDomainException;
- ValidationException;
- NotFoundException;
- ConflictException;
- ForbiddenException;
- InvalidStateException;
- ExpiredException.

Также реализованы конкретные исключения модулей и стабильные строковые коды ошибок.

В некоторых существующих сценариях ошибки ограничений PostgreSQL уже преобразуются в предметные исключения.

Полноценный централизованный REST-обработчик на основе @RestControllerAdvice в исходной документации ещё не был реализован.

Поэтому далее разделяются:

- существующий контракт исключений;
- целевые предметные ошибки новой архитектуры;
- будущая обработка HTTP-ответов.

Этот документ не утверждает, что устаревшие классы AvailabilitySlot уже удалены из приложения.

---

# 3. Контракт DomainException

## 3.1. Назначение

DomainException является общим контрактом ожидаемых предметных ошибок.

Его назначение — предоставлять стабильный машинный код ошибки.

## 3.2. Существующий интерфейс

```java
public interface DomainException {
    String code();
}
```

## 3.3. Особенность

DomainException — интерфейс.

Он не наследуется от Throwable и сам по себе не является исключением Java.

## 3.4. Машинный код

Метод code() возвращает строковый идентификатор ошибки.

Например:

`RESERVATION_EXPIRED`

Код должен оставаться стабильным при изменении человекочитаемого текста сообщения.

## 3.5. Использование

Клиентское приложение должно ориентироваться на машинный код, а не пытаться определять тип ошибки по тексту message.

---

# 4. BaseDomainException

## 4.1. Назначение

BaseDomainException является общей абстрактной реализацией для доменных исключений.

## 4.2. Наследование

```text id="sny572"
RuntimeException
    ↑
BaseDomainException
    implements DomainException
```

## 4.3. Данные

BaseDomainException содержит:

- стабильный код ошибки;
- сообщение;
- необязательную исходную причину.

## 4.4. Абстрактность

BaseDomainException не должен использоваться как универсальное исключение, создаваемое непосредственно в бизнес-коде.

Конкретная ошибка должна отражать установленный предметный смысл.

## 4.5. Cause

При преобразовании известной инфраструктурной ошибки исходное исключение может сохраняться как cause.

Это позволяет:

- предоставить вызывающему коду понятную предметную ошибку;
- сохранить техническую информацию для диагностики.

Внешний API не должен раскрывать полную цепочку cause.

---

# 5. Общая иерархия

Существующая структура:

```text id="niha37"
DomainException (interface)
          ↑ implements
BaseDomainException
          |
          ├── ValidationException
          |
          ├── NotFoundException
          |
          ├── ConflictException
          |
          ├── ForbiddenException
          |
          ├── InvalidStateException
          |
          └── ExpiredException
```

Все шесть категорий являются абстрактными классами.

Они наследуются от BaseDomainException.

Конкретные исключения находятся в соответствующих бизнес-модулях.

## 5.1. Принцип минимализма

Не требуется создавать отдельную общую категорию для каждой новой бизнес-ситуации.

Новая конкретная ошибка должна по возможности использовать одну из существующих категорий.

## 5.2. Разграничение

Общая категория описывает характер ошибки.

Конкретное исключение описывает предметную ситуацию.

---

# 6. ValidationException

## 6.1. Назначение

ValidationException представляет недопустимые входные или предметные данные.

## 6.2. Существующие примеры

В исходной реализации:

- InvalidUserDataException;
- InvalidSpecialistDataException;
- InvalidAvailabilitySlotDataException;
- InvalidReservationDataException;
- InvalidBookingDataException.

InvalidAvailabilitySlotDataException относится к прежней архитектуре.

Его наличие в текущем коде не означает, что AvailabilitySlot сохраняется в целевой модели.

## 6.3. Целевые примеры

После перехода к динамической доступности возможны:

- некорректная длительность ServiceOffering;
- отрицательный перерыв;
- некорректный рабочий интервал;
- начало консультации вне 15-минутной сетки;
- недопустимый диапазон дат Availability;
- некорректное значение rating;
- некорректные параметры административного действия.

## 6.4. Граница с HTTP

ValidationException не заменяет Bean Validation.

Ошибки десериализации JSON и нарушения ограничений DTO могут возникать до вызова прикладного сервиса.

## 6.5. Предметная проверка

Бизнес-валидация должна оставаться в модуле, владеющем соответствующим правилом.

Например, проверка допустимости начала консультации принадлежит Availability и Booking, а не Common.

---

# 7. NotFoundException

## 7.1. Назначение

NotFoundException означает отсутствие запрашиваемого ресурса.

## 7.2. Существующие примеры

- UserNotFoundException;
- SpecialistNotFoundException;
- AvailabilitySlotNotFoundException;
- ReservationNotFoundException;
- BookingNotFoundException.

AvailabilitySlotNotFoundException относится к старой реализации.

## 7.3. Целевые примеры

В новой модели могут потребоваться:

- ServiceOfferingNotFoundException;
- ReservationNotFoundException;
- BookingNotFoundException;
- ReviewNotFoundException;
- SessionOutcomeNotFoundException.

Этот перечень концептуальный.

Не следует создавать перечисленные классы заранее, если конкретный сценарий ещё не реализуется.

## 7.4. Принадлежность

Конкретное исключение располагается в модуле-владельце ресурса.

---

# 8. ConflictException

## 8.1. Назначение

ConflictException представляет конфликт с существующим состоянием данных или конкурентной операцией.

## 8.2. Существующий пример

В прежней модели используется:

`ActiveReservationAlreadyExistsException`

Он выражает ситуацию, когда для AvailabilitySlot уже существует ACTIVE Reservation.

## 8.3. Старая защита PostgreSQL

В исходной реализации использовалось ограничение:

`unique_active_reservation_slot`

Оно защищало уникальность ACTIVE Reservation по slot_id.

## 8.4. Новая модель

Целевая архитектура не использует AvailabilitySlot.

Вместо уникальности Reservation для одного слота применяется защита от пересечения временных интервалов ScheduleOccupancy.

## 8.5. Новый предметный конфликт

Возможное исключение:

`BookingConflictException`

Оно может означать, что выбранный интервал больше не доступен.

Например:

- другой клиент создал пересекающуюся Reservation;
- подтверждённая Booking уже занимает время;
- конфликт обнаружен при окончательной проверке;
- PostgreSQL отклонил вставку конфликтующей Occupancy.

## 8.6. Отсутствие ложной универсальности

Не всякая ошибка создания Reservation является BookingConflictException.

Например:

- неактивная ServiceOffering;
- отсутствие допуска специалиста;
- истёкший bookingDeadline;
- некорректный локальный старт;
- отсутствие рабочего окна

имеют самостоятельный предметный смысл.

Они не должны автоматически классифицироваться как конфликт занятого интервала.

## 8.7. Ограничения PostgreSQL

Известное нарушение GiST exclusion constraint может преобразовываться в предметный BookingConflictException.

При этом необходимо точно установить, какое ограничение нарушено.

## 8.8. Другие конфликты

ConflictException также может применяться к:

- попытке создать второй Review той же пары клиент–специалист;
- конкурентному изменению сущности;
- конфликтующему расписанию;
- повторной несовместимой операции.

Конкретные исключения принадлежат соответствующим модулям.

---

# 9. ForbiddenException

## 9.1. Назначение

ForbiddenException представляет предметный отказ в выполнении действия из-за отсутствия необходимых прав.

## 9.2. Существующие примеры

- UserAccessForbiddenException;
- ReservationOwnershipException.

## 9.3. Целевые ситуации

К этой категории могут относиться:

- попытка подтвердить чужую Reservation;
- попытка отменить чужую Booking;
- изменение чужого расписания;
- редактирование чужого Review;
- чтение чужого Notification;
- недостаточные административные полномочия.

## 9.4. Отличие от Authentication

Отсутствие JWT или неправильная подпись токена — не доменная ForbiddenException.

Такие ошибки принадлежат Spring Security.

## 9.5. Отличие от Business State

Пользователь может иметь право выполнить операцию, но столкнуться с недопустимым состоянием объекта.

Например:

- клиент владеет Reservation;
- Reservation уже EXPIRED;
- подтверждение запрещено.

Это не обязательно ForbiddenException.

## 9.6. Specialist Booking Eligibility

Отсутствие профессионального допуска специалиста или административная блокировка бронирования должны возвращать соответствующую предметную ошибку.

Конкретную категорию необходимо выбирать по смыслу операции.

Не следует считать любую невозможность бронирования ошибкой HTTP-авторизации клиента.

---

# 10. InvalidStateException

## 10.1. Назначение

InvalidStateException представляет операцию, недопустимую при текущем состоянии сущности.

## 10.2. Существующие примеры

- InvalidSpecialistStateException;
- SpecialistNotEligibleException;
- InvalidAvailabilitySlotStateException;
- InvalidReservationStateException;
- InvalidBookingStateException.

InvalidAvailabilitySlotStateException относится к прежней модели.

## 10.3. Целевые примеры

- подтверждение Reservation со статусом CANCELLED;
- подтверждение Reservation со статусом CONFIRMED;
- отмена уже CANCELLED Booking;
- недопустимый переход approvalStatus;
- повторное разрешение SessionOutcome без предусмотренного механизма пересмотра;
- изменение состояния объекта в обход разрешённого перехода.

## 10.4. Отличие от ValidationException

ValidationException описывает недопустимые данные.

InvalidStateException описывает недопустимую операцию над объектом в его текущем состоянии.

## 10.5. Отличие от ConflictException

Недопустимый переход состояния может возникнуть без конкурентного конфликта.

И наоборот, конкурентный конфликт может возникнуть при формально допустимой операции.

Эти ситуации следует различать.

---

# 11. ExpiredException

## 11.1. Назначение

ExpiredException представляет ресурс или бизнес-операцию, ограниченные временем.

## 11.2. Существующий пример

`ReservationExpiredException`

## 11.3. TTL Reservation

Подтверждение разрешено только при:

`now < expiresAt`

При:

`now >= expiresAt`

Reservation больше не может быть подтверждена.

## 11.4. Особенность состояния

Фактическое наступление дедлайна и сохранённый статус EXPIRED не всегда возникают одновременно.

Например, scheduler может обработать Reservation с небольшой задержкой.

## 11.5. Дедлайн бронирования

Для создания новой Reservation действует:

`now < bookingDeadline`

Нарушение этого условия означает, что создавать новое удержание уже поздно.

## 11.6. Окно SessionOutcome

Отправка отчёта о консультации ограничена утверждённым 24-часовым окном.

При нарушении соответствующего временного правила может использоваться предметная ошибка.

## 11.7. Классификация

Не обязательно создавать отдельный общий тип исключения для каждого временного ограничения.

Конкретные классы и коды должны отражать устойчивую предметную семантику.

---

# 12. Стабильные коды ошибок

## 12.1. Назначение

Машинный код позволяет клиентскому приложению различать ошибки без анализа текстовых сообщений.

## 12.2. Существующие коды

В исходной реализации предусмотрены:

```text id="vq6xeh"

USER_NOT_FOUND
USER_ACCESS_FORBIDDEN

SPECIALIST_INVALID_DATA
SPECIALIST_NOT_FOUND
SPECIALIST_INVALID_STATE
SPECIALIST_NOT_ELIGIBLE

AVAILABILITY_SLOT_INVALID_DATA
AVAILABILITY_SLOT_NOT_FOUND
AVAILABILITY_SLOT_INVALID_STATE

RESERVATION_INVALID_DATA
RESERVATION_NOT_FOUND
RESERVATION_INVALID_STATE
RESERVATION_EXPIRED
RESERVATION_OWNERSHIP_VIOLATION
ACTIVE_RESERVATION_ALREADY_EXISTS

BOOKING_INVALID_DATA
BOOKING_NOT_FOUND

```

## 12.3. Устаревающие коды

После отказа от AvailabilitySlot следующие коды не входят в новую целевую предметную модель:

```text id="orsn68"

```

Они могут временно оставаться в коде до завершения соответствующего рефакторинга.

## 12.4. Предлагаемые целевые коды

Для новых сценариев могут использоваться:

```text id="qwpg7q"

SERVICE_OFFERING_NOT_AVAILABLE

RESERVATION_TIME_INVALID
RESERVATION_BOOKING_DEADLINE_PASSED
RESERVATION_CONFLICT

SCHEDULE_CONFLICT

REVIEW_ALREADY_EXISTS
REVIEW_NOT_ALLOWED
VERIFIED_CONSULTATION_REQUIRED

SESSION_OUTCOME_INVALID_STATE
SESSION_OUTCOME_REPORTING_WINDOW_EXPIRED
```

Это предложения, а не уже реализованные коды.

Окончательный набор утверждается при создании соответствующих исключений и API-контрактов.

## 12.5. Стабильность

После публичного использования код ошибки должен сохранять своё значение.

Изменение формулировки message не должно менять code().

## 12.6. Отказ от общего кода для всех ошибок

Не следует возвращать один универсальный код BUSINESS_ERROR для всех предметных отказов.

Это лишило бы клиентское приложение возможности корректно различать ситуации.

# 13. Размещение исключений по модулям

## 13.1. Common

Пакет:

`com.psyweb.common.exception`

содержит общие контракты и абстрактные категории.

## 13.2. Booking

В Booking размещаются конкретные исключения, относящиеся к:

- Reservation;
- Booking;
- их переходам;
- истечению;
- конфликтам занятости;
- отменам.

## 13.3. Schedule

Schedule владеет ошибками:

- рабочего расписания;
- версий недельного графика;
- отдельных дат;
- изменения календарной конфигурации.

## 13.4. Review

Review владеет ошибками:

- отсутствия права на отзыв;
- повторного создания;
- недопустимой оценки;
- нарушения принадлежности.

## 13.5. Outcome

Outcome владеет ошибками:

- отчётов участников;
- окна подтверждения;
- конфликтующих переходов;
- разрешения результата.

## 13.6. Admin

Admin владеет ошибками:

- административных действий;
- полномочий;
- недопустимых решений;
- конфликтов административного состояния.

## 13.7. Запрет

Common не должен содержать все предметные исключения PsyWeb.

Конкретная ошибка остаётся у своего владельца.

# 14. Преобразование ошибок PostgreSQL

## 14.1. Основной принцип

PostgreSQL обеспечивает часть бизнес-инвариантов непосредственно на уровне базы данных.

Известное нарушение ограничения может быть преобразовано в предметное исключение.

## 14.2. GiST exclusion constraint

Для ScheduleOccupancy применяется запрет пересечения временных интервалов одного специалиста.

Концептуально:

```sql
EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
)
```

## 14.3. Конфликт занятости

При нарушении соответствующего ограничения:

```text id="w0i0k0"
PostgreSQL exclusion violation
    ↓
Persistence exception
    ↓
Known constraint identification
    ↓
BookingConflictException
```

## 14.4. PostgreSQL SQLSTATE

Для нарушения exclusion constraint используется SQLSTATE:

`23P01`

Для нарушения UNIQUE:

`23505`

Для deadlock:

`40P01`

Однако одного SQLSTATE не всегда достаточно, чтобы определить предметный смысл ошибки.

## 14.5. Проверка имени ограничения

При преобразовании необходимо учитывать конкретное имя нарушенного ограничения.

Например, нарушение UNIQUE Review и нарушение UNIQUE Booking имеют разные бизнес-причины.

## 14.6. Составные FK

Нарушения внешних ключей могут свидетельствовать:

- о несуществующем ресурсе;
- о несогласованности участников;
- об ошибке порядка сохранения;
- о нарушении внутреннего инварианта.

Они не должны автоматически отображаться как 404 или 409 без анализа причины.

## 14.7. Deadlock

Deadlock является конфликтом конкурентного выполнения.

Он не обязательно означает, что выбранное время уже занято.

Следовательно, нельзя безусловно преобразовывать каждый deadlock в BookingConflictException.

## 14.8. Повторная попытка

При необходимости retry выполняется в новой транзакции.

Бизнес-предусловия проверяются повторно.

## 14.9. Неизвестные ограничения

Неизвестное нарушение базы данных не должно маскироваться под ожидаемую бизнес-ошибку.

Оно остаётся инфраструктурным сбоем до установления причины.

# 15. Особенности Spring Data JPA и транзакций

## 15.1. Момент возникновения ошибки

Ограничение PostgreSQL может быть нарушено во время:

- INSERT;
- UPDATE;
- flush;
- COMMIT.

## 15.2. save()

Вызов save() не гарантирует немедленного выполнения SQL.

## 15.3. saveAndFlush()

Принудительный flush может позволить обнаружить известное нарушение ограничения до выхода из сервисного метода.

Однако корректность такого приёма должна проверяться с учётом транзакционного контекста.

## 15.4. Состояние транзакции

После ошибки SQL транзакция PostgreSQL может оказаться в состоянии, требующем полного отката.

Нельзя перехватить нарушение ограничения и продолжить обычную работу в той же повреждённой транзакции.

## 15.5. Перевод исключения

Преобразование persistence exception должно выполняться на уровне, где известен предметный смысл конкретного ограничения.

## 15.6. Граница COMMIT

Если ошибка возникает только при COMMIT, внутренний try/catch сервисного метода может её не перехватить.

Поэтому стратегия преобразования ошибок должна учитывать фактические границы Spring TransactionInterceptor.

# 16. Истечение Reservation и транзакционные исключения

## 16.1. Проблема

Подтверждение Reservation может обнаружить, что TTL истёк.

В таком случае необходимо:

- запретить подтверждение;
- при предусмотренном сценарии перевести Reservation в EXPIRED;
- освободить Occupancy;
- сообщить клиенту об истечении.

## 16.2. Риск отката

Если после сохранения EXPIRED выбрасывается RuntimeException, стандартные правила @Transactional могут откатить изменение.

В результате система вернётся к ACTIVE Reservation с прежней Occupancy.

## 16.3. Требование

Нельзя одновременно предполагать:

- что переход в EXPIRED успешно сохранён;
- что любой выброшенный RuntimeException автоматически откатывает транзакцию;
- что дополнительной настройки не требуется.

## 16.4. Возможные решения

Допустимы варианты:

1. Возвращать типизированный результат операции после фиксации перехода.
2. Явно настроить rollback policy для конкретной ожидаемой ошибки.
3. Вынести переход в отдельную корректную транзакционную операцию с ясными границами.

## 16.5. Утверждение конкретного подхода

Финальный механизм должен быть согласован с Booking Service Layer и подтверждён интеграционными тестами.

## 16.6. Недопустимый результат

Нельзя оставить Reservation CONFIRMED при истёкшем TTL.

Нельзя создать Booking, если подтверждение проиграло истечению.

# 17. Ошибки Authentication и Security

## 17.1. Отдельный источник

Ошибки Spring Security не обязаны наследоваться от BaseDomainException.

## 17.2. Примеры

- отсутствующий JWT;
- неправильная подпись;
- просроченный токен;
- неверные учётные данные;
- отсутствие Authentication.

## 17.3. AuthenticationEntryPoint

Ошибки аутентификации обрабатываются механизмами Spring Security.

## 17.4. AccessDeniedHandler

Отказы в доступе могут обрабатываться AccessDeniedHandler.

## 17.5. Общий формат

При возможности ответы Security должны соответствовать общему API-формату ошибок.

При этом не нужно преобразовывать каждую security exception в предметную DomainException.

# 18. Неожиданные системные ошибки

## 18.1. Примеры

- недоступность PostgreSQL;
- ошибка соединения;
- ошибка конфигурации;
- непредвиденное исключение Hibernate;
- ошибка программирования;
- сбой внешней зависимости.

## 18.2. Классификация

Такие ошибки не являются автоматически доменными.

## 18.3. Клиентский ответ

Внешнему клиенту возвращается безопасный ответ без внутренних подробностей.

## 18.4. Диагностика

В технических логах сохраняется достаточная информация для расследования.

## 18.5. Запрет

Нельзя преобразовывать произвольный RuntimeException в 400 Bad Request только ради единообразия.

# 19. Целевой Global Exception Handler

## 19.1. Назначение

Централизованный обработчик переводит исключения приложения в согласованные HTTP-ответы.

## 19.2. Инструмент

Для REST API используется:

`@RestControllerAdvice`

## 19.3. Основные обязанности

Handler должен:

- определять категорию известного исключения;
- извлекать стабильный код DomainException;
- выбирать предусмотренный HTTP status;
- формировать безопасный ErrorResponse;
- отдельно обрабатывать Bean Validation;
- отдельно учитывать Security;
- скрывать технические подробности;
- корректно обрабатывать неожиданные ошибки.

## 19.4. Использование существующей иерархии

Нельзя создавать вторую параллельную иерархию API-исключений, полностью дублирующую уже существующие доменные категории.

## 19.5. Граница ответственности

DomainException не должен содержать HttpStatus как обязательное поле.

HTTP-семантика определяется на границе представления.

# 20. Целевые HTTP-статусы

Предварительное соответствие:

| Категория | HTTP |
|---|---|
| ValidationException | 400 Bad Request |
| NotFoundException | 404 Not Found |
| ConflictException | 409 Conflict |
| ForbiddenException | 403 Forbidden |
| InvalidStateException | Предметный 4xx |
| ExpiredException | Предметный 4xx |
| Неаутентифицированный запрос | 401 Unauthorized |
| Неожиданная ошибка | 500 Internal Server Error |

## 20.1. InvalidStateException

Необходимо определить согласованную HTTP-семантику для конкретных ошибок состояния.

409 Conflict может подходить для некоторых сценариев, но не должен назначаться автоматически без API-контракта.

## 20.2. ExpiredException

Точный HTTP status определяется контрактом конкретной временной ошибки.

Например, истечение Reservation отличается по смыслу от истечения JWT.

## 20.3. Авторизация

Отсутствие аутентификации соответствует категории 401.

Недостаточность полномочий аутентифицированного пользователя соответствует категории 403.

## 20.4. Скрытие ресурса

Для отдельных чувствительных ресурсов API может возвращать 404 вместо раскрытия факта существования чужого объекта.

Такая политика должна быть предусмотрена явно.

# 21. ErrorResponse

## 21.1. Назначение

ErrorResponse обеспечивает единый машиночитаемый формат ошибки.

## 21.2. Предлагаемые поля

```text id="dc8skf"
ErrorResponse
    code
    message
    timestamp
    path?
    details?
```

## 21.3. code

Стабильный идентификатор ошибки.

Для DomainException используется значение code().

## 21.4. message

Безопасное человекочитаемое описание.

Клиент не должен использовать message как машинный идентификатор.

## 21.5. timestamp

Время формирования ответа.

## 21.6. path

Необязательный путь запроса.

## 21.7. details

Необязательные структурированные сведения, например о нарушениях DTO-валидации.

## 21.8. Ограничение

Конкретный окончательный DTO должен быть согласован с DTO and Mapping Strategy.

Не следует объявлять предварительный набор полей уже реализованным.

# 22. DTO Validation

## 22.1. Отдельная категория ошибок

Ошибки запроса могут быть обнаружены до вызова доменного сервиса.

## 22.2. Примеры

- некорректный JSON;
- отсутствие обязательного поля;
- неправильный тип значения;
- Bean Validation;
- некорректный формат даты.

## 22.3. Соответствие API

Они должны возвращаться в согласованном формате ошибок.

## 22.4. Разделение ответственности

DTO Validation проверяет структуру и простые ограничения ввода.

Domain Validation проверяет предметные правила.

Например, корректная дата в JSON ещё не означает, что на неё разрешено создать Reservation.

---

# 23. Логирование ошибок

## 23.1. Ожидаемые ошибки

Обычные бизнес-отказы не обязательно требуют полного ERROR stack trace.

Например:

- ReservationExpiredException;
- ReviewAlreadyExistsException;
- известный BookingConflictException.

## 23.2. Неожиданные ошибки

Внутренние сбои должны сохранять информацию, достаточную для диагностики.

## 23.3. Чувствительные данные

Запрещено логировать:

- пароли;
- passwordHash;
- JWT;
- секреты;
- чувствительные подробности консультаций;
- избыточные персональные сведения.

## 23.4. Cause

Технический cause может сохраняться для диагностики.

Его содержание не должно безусловно включаться в публичный ErrorResponse.

## 23.5. Повторное логирование

Следует избегать многократного логирования одной ожидаемой ошибки на каждом уровне вызовов.

# 24. Архитектурные правила

1. DomainException остаётся интерфейсом с методом code().
2. BaseDomainException остаётся абстрактным RuntimeException.
3. Существующие шесть категорий являются основой иерархии.
4. Конкретные исключения принадлежат своим модулям.
5. Common не зависит от бизнес-доменов.
6. Машинные коды ошибок должны быть стабильными.
7. Человекочитаемое сообщение не используется для программного определения типа ошибки.
8. Authentication exceptions не обязаны наследоваться от DomainException.
9. Известные нарушения PostgreSQL могут преобразовываться в предметные исключения.
10. Неизвестные infrastructure failures не маскируются под бизнес-конфликты.
11. Нарушение GiST exclusion constraint обрабатывается с учётом конкретного ограничения.
12. Deadlock не считается автоматически конфликтом занятого времени.
13. Ошибка Hibernate может возникать при flush или COMMIT.
14. После SQL-ошибки нельзя продолжать работу в повреждённой транзакции.
15. Намеренно сохраняемые переходы состояния требуют явной rollback policy.
16. HTTP-статусы не должны определять структуру доменной иерархии.
17. REST-ответы не раскрывают stack trace и внутренние SQL-детали.
18. Устаревшие AvailabilitySlot-исключения удаляются только вместе с рефакторингом соответствующей модели.
19. Нельзя создавать новую общую категорию исключений без необходимости.
20. Публичная семантика машинных кодов должна сохранять совместимость.

# 25. Тестирование

## 25.1. Базовая иерархия

Проверяются:

- DomainException.code();
- BaseDomainException;
- сохранение message;
- сохранение cause;
- наследование категорий.

## 25.2. Модульные исключения

Проверяются:

- корректная категория;
- стабильный код;
- осмысленное сообщение;
- отсутствие лишних зависимостей.

## 25.3. Booking

Проверяются:

- истечение Reservation;
- неверный переход Reservation;
- неверный переход Booking;
- конфликт ScheduleOccupancy;
- отказ в поздней или недопустимой отмене согласно утверждённым правилам;
- отсутствие допуска специалиста.

Поздняя отмена до начала консультации сама по себе является допустимой операцией.

## 25.4. PostgreSQL

Проверяются:

- UNIQUE violation;
- GiST exclusion violation;
- FK violation;
- deadlock;
- преобразование известного ограничения;
- сохранение неизвестной ошибки как системной.

## 25.5. Транзакции

Проверяется:

- откат после неожиданного сбоя;
- невозможность частичного создания Reservation и Occupancy;
- согласованное освобождение Occupancy;
- обработка истечения Reservation при подтверждении;
- корректность транзакционного retry.

## 25.6. HTTP

После реализации API проверяются:

- 400;
- 401;
- 403;
- 404;
- 409;
- 500;
- единый ErrorResponse;
- Bean Validation;
- ошибки Security;
- отсутствие утечек технических сведений.

## 25.7. Инфраструктура

Для PostgreSQL-специфических проверок используется реальный PostgreSQL, например через Testcontainers.

# 27. Открытые вопросы

## 27.1. HTTP mapping

Нужно окончательно определить соответствие InvalidStateException и ExpiredException конкретным HTTP-статусам.

## 27.2. ErrorResponse

Требуется утвердить точный состав полей.

## 27.3. Новые коды

Нужно согласовать окончательный список кодов по мере реализации соответствующих доменов.

## 27.4. Перевод ошибок PostgreSQL

Необходимо определить место преобразования исключений, возникающих при flush и COMMIT.

## 27.5. Retry

Требуется определить, какие технические конфликты допускают автоматическое повторение операции.

## 27.6. Reservation expiration

Нужно окончательно утвердить способ фиксации перехода ACTIVE → EXPIRED, если истечение обнаружено во время подтверждения.

## 27.7. Совместимость

Нужно определить порядок удаления старых AvailabilitySlot-исключений и кодов после рефакторинга.

# 28. Итог

PsyWeb использует существующую иерархию доменных исключений:

```text id="371j1c"
DomainException
    ↑ implements
BaseDomainException
    |
    ├── ValidationException
    ├── NotFoundException
    ├── ConflictException
    ├── ForbiddenException
    ├── InvalidStateException
    └── ExpiredException
```

Конкретные исключения находятся внутри соответствующих модулей.

Главные гарантии:

- устойчивые машинные коды;
- разделение ошибок по смыслу;
- отсутствие зависимости домена от HTTP;
- преобразование только известных инфраструктурных конфликтов;
- сохранение исходного cause для диагностики;
- согласованная обработка транзакционных ошибок;
- использование существующей иерархии при реализации REST;
- постепенный отказ от исключений старой модели AvailabilitySlot.

**Статус: DRAFT — базовая иерархия уже существует; новые доменные ошибки и централизованный HTTP-обработчик требуют реализации.**
