## Overview

This document defines the exception architecture of PsyWeb.

The current backend already implements a shared domain-exception hierarchy with stable machine-readable error codes.

The complete REST error-mapping layer based on `@ControllerAdvice` is still target/backlog functionality.

Therefore, this document separates:

- current domain exception architecture;
- future HTTP/API exception mapping.

---

# Current Domain Exception Contract

Expected business/domain failures use the shared contract:

```text
DomainException
```

Current interface:

```java
public interface DomainException {
    String code();
}
```

`DomainException` is a contract only.

It is not itself a `Throwable`.

---

# BaseDomainException

The common implementation base is:

```text
BaseDomainException
```

with the relationship:

```text
BaseDomainException
extends RuntimeException
implements DomainException
```

It stores:

```text
stable code
message
optional cause
```

Conceptually:

```text
DomainException
        ↑ implements
BaseDomainException
        ↑
category exception
        ↑
module-specific exception
```

`BaseDomainException` is abstract and is not thrown directly.

Its `code()` value is intended to remain stable even when a human-readable message changes.

---

# Current Category Hierarchy

The current common exception categories are:

```text
ValidationException
NotFoundException
ConflictException
ForbiddenException
InvalidStateException
ExpiredException
```

All of them are abstract and extend:

```text
BaseDomainException
```

The implemented hierarchy is:

```text
DomainException
        ↑ implements
BaseDomainException
        ├── ValidationException
        ├── NotFoundException
        ├── ConflictException
        ├── ForbiddenException
        ├── InvalidStateException
        └── ExpiredException
```

These categories describe business error semantics rather than HTTP transport semantics.

---

# ValidationException

Represents invalid input or invalid domain data.

Examples of currently implemented module exceptions include:

```text
InvalidUserDataException
InvalidSpecialistDataException
InvalidAvailabilitySlotDataException
InvalidReservationDataException
InvalidBookingDataException
```

These exceptions represent validation failures inside the domain/service model.

They are distinct from Bean Validation / malformed HTTP request errors, which belong to the future API layer.

---

# NotFoundException

Represents failure to find a requested domain resource.

Current examples include:

```text
UserNotFoundException
SpecialistNotFoundException
AvailabilitySlotNotFoundException
ReservationNotFoundException
BookingNotFoundException
```

The concrete exception remains owned by the module that owns the resource.

---

# ConflictException

Represents a conflict with persisted state or a concurrent operation.

Current example:

```text
ActiveReservationAlreadyExistsException
```

This exception is used when another ACTIVE Reservation already occupies the same AvailabilitySlot.

The same business exception may wrap an underlying persistence exception when a known database constraint detects the conflict.

For example:

```text
PostgreSQL uniqueness conflict
→ persistence exception
→ ActiveReservationAlreadyExistsException
```

The infrastructure exception may be retained as `cause` while the outward business meaning remains stable.

Future overlap protection follows the same pattern:

```text
SlotOverlapException
extends ConflictException
```

but `SlotOverlapException` is still backlog functionality.

---

# ForbiddenException

Represents a business authorization or ownership failure.

Current examples include:

```text
UserAccessForbiddenException
ReservationOwnershipException
```

This category is distinct from authentication failures.

For example:

```text
valid business identity
+
operation is not allowed for this actor/resource
→ ForbiddenException
```

Authentication/security-framework exceptions do not have to inherit from this hierarchy.

---

# InvalidStateException

Represents an operation that is invalid because of the current lifecycle state of an entity.

Current examples include:

```text
InvalidSpecialistStateException
SpecialistNotEligibleException
InvalidAvailabilitySlotStateException
InvalidReservationStateException
InvalidBookingStateException
```

Examples of this semantic category:

```text
confirm non-ACTIVE Reservation
reserve non-FREE AvailabilitySlot
approve Specialist that is not PENDING
```

The distinction from validation is intentional:

```text
ValidationException
→ input/value itself is invalid

InvalidStateException
→ requested operation is invalid for current entity state
```

---

# ExpiredException

Represents a time-bounded domain resource that is no longer valid because its deadline has passed.

Current example:

```text
ReservationExpiredException
```

Reservation expiration is distinct from a generic invalid state because expiration has explicit temporal semantics:

```text
now >= expiresAt
```

---

# Stable Error Codes

Concrete module exceptions define stable machine-readable codes.

Examples from the current implementation include:

```text
USER_INVALID_DATA
USER_NOT_FOUND
USER_ACCESS_FORBIDDEN

SPECIALIST_INVALID_DATA
SPECIALIST_NOT_FOUND
SPECIALIST_INVALID_STATE
SPECIALIST_NOT_ELIGIBLE

AVAILABILITY_SLOT_INVALID_DATA
AVAILABILITY_SLOT_NOT_FOUND
AVAILABILITY_SLOT_INVALID_STATE

RESERVATION_INVALID_DATA
RESERVATION_NOT_FOUND
RESERVATION_INVALID_STATE
RESERVATION_EXPIRED
RESERVATION_OWNERSHIP_VIOLATION
ACTIVE_RESERVATION_ALREADY_EXISTS

BOOKING_INVALID_DATA
BOOKING_NOT_FOUND
BOOKING_INVALID_STATE
```

The stable code is part of the domain-error contract.

Human-readable exception messages are not intended to act as machine-readable identifiers.

---

# Module Ownership

The shared hierarchy belongs to:

```text
common.exception
```

The common module owns only generic contracts and categories.

It must not depend on:

- User;
- Specialist;
- AvailabilitySlot;
- Reservation;
- Booking;
- Review;
- other business-domain classes.

Concrete exceptions remain inside their owning modules.

For example:

```text
common.exception.ConflictException
        ↑
booking.exception.ActiveReservationAlreadyExistsException
```

This keeps business meaning local while preserving a common error architecture.

---

# Persistence Error Translation

Known database constraint violations may be translated into domain exceptions when the database error represents an established business invariant.

Current example:

```text
unique_active_reservation_slot
```

may result in:

```text
ActiveReservationAlreadyExistsException
```

The technical persistence exception may be retained as:

```text
cause
```

through `BaseDomainException`.

Unknown database failures must not be arbitrarily reclassified as business conflicts.

Unexpected persistence/infrastructure failures remain system errors.

---

# Security and Authentication Errors

Authentication/security failures are not required to inherit from the domain exception hierarchy.

Examples include future:

```text
invalid credentials
missing JWT
invalid JWT
expired authentication token
```

These belong to the security layer.

This is separate from business authorization such as ownership or professional eligibility.

---

# Unexpected System Errors

Unexpected infrastructure/programming failures are not domain exceptions merely because they occur during a business operation.

Examples may include:

```text
database connectivity failure
unexpected infrastructure failure
programming error
external dependency failure
```

These remain internal system errors.

Their technical details and stack traces must not be exposed to API clients.

---

# Current vs Target REST Error Handling

## Current Implementation

The current `PsyWeb/main` contains:

```text
DomainException
BaseDomainException
six shared category exceptions
module-specific concrete domain exceptions
stable exception codes
optional cause support
known persistence-conflict translation in Reservation flow
```

The current backend does not yet contain the final centralized REST exception-mapping infrastructure.

In particular, there is currently no completed:

```text
@ControllerAdvice / @RestControllerAdvice
standard ErrorResponse contract
final HTTP status mapping for all exception categories
central DTO-validation error response
```

---

# Target Global Exception Handler

The target HTTP layer will use centralized exception handling.

Conceptually:

```text
Controller / Service / Domain
→ exception
→ global exception handler
→ stable API error response
```

The handler is responsible for:

- translating known domain categories to appropriate HTTP statuses;
- exposing stable domain error codes;
- returning safe human-readable messages;
- handling DTO/request validation separately;
- mapping security errors through the security/API boundary;
- hiding internal exception details;
- mapping unexpected failures to HTTP 500.

The future handler must reuse the existing domain hierarchy rather than introduce a parallel exception taxonomy.

---

# Target HTTP Semantics

Exact API response DTO design belongs to the REST/error-handling implementation.

The expected semantic mapping is:

```text
ValidationException
→ 400 Bad Request

NotFoundException
→ 404 Not Found

ConflictException
→ 409 Conflict

ForbiddenException
→ 403 Forbidden

InvalidStateException
→ business 4xx mapping defined by the API contract

ExpiredException
→ business 4xx mapping defined by the API contract
```

Authentication failures are expected to use:

```text
401 Unauthorized
```

while authenticated-but-forbidden access uses:

```text
403 Forbidden
```

The exact mapping for lifecycle-state and temporal errors must be defined by the API error contract rather than inferred from exception class names alone.

---

# Request Validation

Future HTTP DTO validation remains separate from domain exceptions.

For example:

```text
malformed request JSON
Bean Validation failure
missing required request field
```

may be rejected before a domain service is called.

Domain validation remains responsible for business/domain invariants after request mapping.

The two mechanisms must not be conflated.

---

# Logging

Logging policy must distinguish expected and unexpected failures.

Expected domain exceptions generally do not require full ERROR stack traces merely because they extend RuntimeException.

Unexpected system/infrastructure errors should retain sufficient diagnostic context internally.

Sensitive authentication data, passwords, JWTs, and other secrets must not be logged.

Detailed logging policy remains an infrastructure concern rather than part of the exception inheritance model.

---

# Design Rules

## 1. Shared categories stay small

Do not create a new common base category for every feature-specific situation.

---

## 2. Concrete exceptions remain meaningful

A module-specific exception is appropriate when its name/code communicates a stable business concept.

---

## 3. Do not use generic exceptions when domain meaning is known

Known business failures should use the appropriate domain category/concrete exception.

Migration from older generic exceptions may happen feature by feature rather than through unrelated mass refactoring.

---

## 4. Do not convert unknown failures into business errors

Only known infrastructure failures that map to a known invariant should be translated into domain exceptions.

---

## 5. Stable code is machine-readable identity

Client-facing integrations should eventually rely on:

```text
exception.code()
```

rather than parsing human-readable messages.

---

# Summary

The current PsyWeb exception architecture is:

```text
DomainException
→ BaseDomainException
→ small set of semantic categories
→ module-owned concrete exceptions
```

The hierarchy and stable error codes are already implemented.

The centralized REST error-response layer remains target/backlog functionality and must be built on top of this existing hierarchy rather than replacing it.
