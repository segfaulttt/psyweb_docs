
# 04. Процесс аутентификации (Authentication Flow)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**Безопасность:** Spring Security + JWT + Refresh Sessions  
**Статус:** DRAFT — целевая архитектура согласована, реализация выполняется поэтапно

---

# 1. Назначение документа

Документ описывает backend-архитектуру аутентификации PsyWeb.

В область документа входят:

- вход пользователя в аккаунт;
- проверка пароля;
- выпуск и проверка JWT access token;
- создание и управление refresh-сессиями;
- refresh-token rotation;
- отзыв сессий;
- интеграция со Spring Security;
- согласованность конкурентных операций;
- HTTP-контракты аутентификации;
- требования к безопасности и тестированию.

Аутентификация отвечает на вопрос:

**Кто обращается к системе?**

Авторизация определяет, разрешено ли аутентифицированному пользователю выполнить конкретную операцию.

PsyWeb разделяет:

1. Authentication.
2. Account eligibility.
3. Role-based authorization.
4. Resource ownership and participation.
5. Specialist professional eligibility.
6. Specialist booking eligibility.
7. Domain-state validation.

Успешный login не означает автоматического разрешения любой бизнес-операции.

Документ описывает целевую архитектуру. Реализованность отдельных компонентов необходимо проверять по актуальному исходному коду.

# 2. Исходная модель и архитектурные решения

## 2.1. User

В User Domain предусмотрены:

- UserRole;
- UserStatus;
- email;
- passwordHash;
- поиск пользователя;
- нормализация email;
- операции управления состоянием аккаунта.

Состояния UserStatus:

```text
ACTIVE
BLOCKED
```

Успешный login возможен только для ACTIVE пользователя.

## 2.2. Specialist

Состояния SpecialistStatus:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Профессиональный статус специалиста не определяет возможность входа в ACTIVE аккаунт.

Проверка профессионального допуска выполняется отдельно.

## 2.3. Пароли

Для пользовательских паролей PsyWeb использует Argon2id.

Пароль сохраняется только в виде passwordHash.

Auth module не должен самостоятельно вводить альтернативную политику хеширования или нормализации email.

## 2.4. Принятая модель токенов

Для MVP используются:

| Параметр | Решение |
|---|---|
| Access token | Подписанный JWT |
| Access token TTL | 15 минут |
| Access token storage | In-memory React |
| Refresh token | Криптографически случайный opaque token |
| Refresh token transport | HttpOnly cookie |
| Refresh session TTL | 7 дней |
| Session expiration | Абсолютная |
| Refresh rotation | Строгая, при каждом успешном refresh |
| Refresh persistence | PostgreSQL |
| Replay detection | По истории токенов |
| Grace period | Не используется |
| Access JWT immediate revocation on logout | Post-MVP |

Refresh-token инфраструктура входит в MVP.

Отдельный Redis, access-token blacklist и обычная stateful HTTP session не требуются.

# 3. Архитектурные границы

## 3.1. Auth Module

Auth module отвечает за:

- login;
- выпуск access tokens;
- refresh-token lifecycle;
- управление refresh-сессиями;
- logout;
- logout-all.

Auth module владеет RefreshSession и RefreshToken.

## 3.2. User Module

User module владеет:

- User;
- UserRole;
- UserStatus;
- email;
- passwordHash;
- изменением состояния аккаунта.

Auth module использует публичные сервисные контракты User module.

Прямой доступ к UserRepository из Auth module не предусматривается.

## 3.3. Security Infrastructure

Security infrastructure отвечает за:

- проверку access JWT;
- проверку актуального состояния аккаунта;
- формирование Authentication;
- заполнение SecurityContext;
- обработку HTTP 401 и 403;
- применение правил доступа к маршрутам;
- CSRF-защиту соответствующих запросов.

Для JWT-аутентификации предпочтительно использовать стандартные компоненты Spring Security.

Собственный JWT-filter не является обязательным требованием.

## 3.4. Application Services

Booking, Availability, Specialist, Review и другие модули используют доверенную идентичность пользователя.

Они самостоятельно выполняют проверки:

- ownership;
- participation;
- professional eligibility;
- booking eligibility;
- domain-state invariants.

Auth module не должен становиться владельцем предметных правил бронирования.

# 4. Компоненты аутентификации

Целевая структура:

```text
AuthController
    |
    v
AuthService
    |
    +----> User Service Contract
    |
    +----> JwtService
    |
    +----> RefreshSessionService
                 |
                 +----> RefreshSessionRepository
                 |
                 +----> RefreshTokenRepository
```

Security infrastructure интегрируется с Auth и User через согласованные интерфейсы.

## 4.1. AuthController

Отвечает за HTTP-границу:

- приём request DTO;
- валидацию;
- вызов прикладных сервисов;
- формирование response DTO;
- установку и очистку cookies;
- HTTP status codes.

Controller не реализует refresh rotation, криптографию или SQL.

## 4.2. AuthService

Координирует сценарии:

- login;
- refresh;
- logout;
- logout-all.

Отвечает за согласованность выпуска токенов и взаимодействия Auth с User module.

Предварительные логические операции:

```java
AuthResult login(String email, String password);

AuthResult refresh(String rawRefreshToken);

void logout(String rawRefreshToken);

void logoutAll(Long userId);
```

Эти сигнатуры иллюстрируют API сервиса.

Окончательные типы параметров, результатов и транзакционные аннотации определяются при реализации.

## 4.3. JwtService

Отвечает за:

- генерацию JWT;
- подпись;
- проверку JWT;
- извлечение и проверку технических claims.

Не отвечает за:

- хранение RefreshSession;
- проверку пароля;
- предметную авторизацию;
- управление Booking.

## 4.4. RefreshSessionService

Отвечает за:

- создание сессии;
- генерацию refresh token;
- хеширование токена;
- сохранение метаданных;
- атомарную rotation;
- обнаружение replay;
- отзыв одной сессии;
- отзыв всех сессий пользователя.

Сервис управляет жизненным циклом сессии, а не только отдельным токеном.

## 4.5. PasswordEncoder

Для проверки паролей используется Argon2id через согласованный PasswordEncoder.

Пароль не сравнивается с passwordHash обычным строковым сравнением.

# 5. Login Flow

## 5.1. HTTP endpoint

```http
POST /api/auth/login
```

Request DTO:

```json
{
  "email": "client@example.com",
  "password": "example-password"
}
```

Пример содержит исключительно демонстрационные значения.

## 5.2. Общая последовательность

```text
AuthController
    |
    v
AuthService
    |
    v
User lookup by normalized email
    |
    v
Password verification (Argon2id)
    |
    v
Current UserStatus.ACTIVE
    |
    v
Generate access JWT
    |
    v
Create RefreshSession
    |
    v
Generate and persist RefreshToken hash
    |
    v
Transaction commit
    |
    v
HTTP 200 + Access JWT + Refresh Cookie
```

## 5.3. Нормализация email

Используется единая политика User Domain:

```text
trim
    |
    v
lowercase(Locale.ROOT)
    |
    v
validate canonical email
```

AuthService не должен реализовывать независимую нормализацию email.

## 5.4. Проверка credentials

Успешный login требует:

```text
Valid credentials
AND UserStatus.ACTIVE
```

При UserStatus.BLOCKED вход запрещён независимо от правильности пароля.

## 5.5. SpecialistStatus

ACTIVE специалист может войти независимо от того, находится он в состоянии:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

Professional eligibility проверяется после аутентификации при выполнении соответствующей бизнес-операции.

## 5.6. Создание сессии

Каждый независимый login создаёт новую RefreshSession.

В рамках этой сессии создаётся первый RefreshToken.

В PostgreSQL сохраняется только хеш refresh token.

## 5.7. Успешный ответ

HTTP 200:

```json
{
  "accessToken": "<signed-access-jwt>",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

Refresh token передаётся через Set-Cookie.

Исходный refresh token не включается в JSON.

## 5.8. Ошибки

Неверные credentials приводят к HTTP 401.

Ошибки не должны раскрывать:

- существование конкретного email;
- исходный пароль;
- passwordHash;
- внутренние сведения об аккаунте.

Для login необходимо предусмотреть защиту от чрезмерного количества попыток входа.

# 6. JWT Access Token

## 6.1. Назначение

Access JWT подтверждает аутентифицированную идентичность пользователя при обращении к защищённым REST API.

## 6.2. Срок действия

15 минут.

## 6.3. Claims

Предусматриваются:

- `sub` — User ID;
- `role` — UserRole;
- `exp` — срок действия;
- `iat` — момент выдачи;
- `iss` — issuer;
- `aud` — audience.

## 6.4. Исключённые данные

В JWT не сохраняются изменяемые права и состояния:

- UserStatus;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

В JWT запрещено включать:

- пароль;
- passwordHash;
- refresh token;
- signing key;
- ненужные персональные данные.

## 6.5. Подпись

JWT имеет криптографическую подпись.

При проверке контролируются:

- допустимый алгоритм;
- подпись;
- expiration;
- issuer;
- audience;
- обязательные claims.

Signing keys загружаются из внешней защищённой конфигурации.

## 6.6. Хранение на frontend

Access JWT находится только в памяти React.

Не используется долговременное хранение в localStorage или sessionStorage.

## 6.7. Серверное хранение

Access JWT не сохраняется в PostgreSQL.

При обычном защищённом запросе не требуется искать RefreshSession.

# 7. Protected Request Flow

## 7.1. Последовательность

```text
HTTP Request
    |
    v
Authorization: Bearer <access JWT>
    |
    v
Spring Security Filter Chain
    |
    v
JWT validation
    |
    v
Extract user identity
    |
    v
Load current User
    |
    v
Require UserStatus.ACTIVE
    |
    v
Create Authentication
    |
    v
SecurityContext
    |
    v
Authorization
    |
    v
Controller
    |
    v
Application Service
```

## 7.2. Актуальное состояние пользователя

Проверка подписи JWT не заменяет проверку текущего UserStatus.

Для защищённого запроса требуется:

`UserStatus.ACTIVE`

Роль и полномочия должны интерпретироваться с учётом доверенного актуального состояния аккаунта.

## 7.3. Последующая блокировка

Если User был ACTIVE при выпуске JWT, но затем получил BLOCKED, защищённые запросы с ранее выданным JWT отклоняются.

## 7.4. Ограничение MVP

Обычный logout не обеспечивает мгновенный отзыв уже выданного access JWT.

При ACTIVE аккаунте такой JWT технически может оставаться действительным до истечения 15 минут.

Мгновенный отзыв access JWT при обычном отзыве сессии относится к post-MVP.

## 7.5. SecurityContext

Authentication содержит необходимые сведения о доверенной идентичности пользователя.

Domain Entities не должны зависеть от SecurityContext.

# 8. Refresh Persistence Model

## 8.1. Общая модель

Для refresh-token lifecycle используются две самостоятельные сущности:

- RefreshSession;
- RefreshToken.

RefreshSession представляет отдельный сеанс входа.

RefreshToken представляет одно поколение refresh token внутри этого сеанса.

```text
User
 |
 | 1:N
 v
RefreshSession
 |
 | 1:N
 v
RefreshToken
```

## 8.2. UUID strategy

Все новые самостоятельные сущности проектируются с UUIDv4 primary keys.

Для Auth module:

- RefreshSession.id — UUID;
- RefreshToken.id — UUID.

Существующие User IDs остаются BIGINT.

Тип внешнего ключа должен соответствовать типу идентификатора связанной сущности.

Массовая миграция существующих сущностей на UUID не входит в задачу.

## 8.3. RefreshSession

Предварительная модель:

| Поле | PostgreSQL | Назначение |
|---|---|---|
| id | UUID PK | Идентификатор сессии |
| user_id | BIGINT FK | Владелец |
| created_at | TIMESTAMPTZ | Создание |
| expires_at | TIMESTAMPTZ | Абсолютное истечение |
| revoked_at | TIMESTAMPTZ NULL | Отзыв |
| last_used_at | TIMESTAMPTZ NULL | Последний успешный refresh |

## 8.4. Состояние RefreshSession

Отдельный status enum не обязателен.

Состояние определяется по:

- revokedAt;
- expiresAt;
- текущему времени.

Сессия действительна, только если она не отозвана и её срок не истёк.

## 8.5. RefreshToken

Предварительная модель:

| Поле | PostgreSQL | Назначение |
|---|---|---|
| id | UUID PK | Идентификатор записи |
| session_id | UUID FK | Принадлежность сессии |
| token_hash | VARCHAR(64) | SHA-256 в hex |
| issued_at | TIMESTAMPTZ | Время выдачи |
| consumed_at | TIMESTAMPTZ NULL | Время успешного использования |

Отдельный expiresAt для RefreshToken не вводится.

Срок действия каждого поколения определяется по RefreshSession.expiresAt.

## 8.6. Хеширование refresh token

Refresh token генерируется из криптографически стойких случайных байтов.

Предусматривается не менее 256 бит энтропии.

В PostgreSQL сохраняется:

```text
SHA-256(rawRefreshToken)
```

Argon2id предназначен для пользовательских паролей и не требуется для криптографически случайных refresh tokens с достаточной энтропией.

Исходный refresh token не сохраняется в PostgreSQL.

## 8.7. История

При rotation предыдущая запись не удаляется.

У неё устанавливается consumedAt.

Новая запись создаётся в той же RefreshSession.

История сохраняется:

- весь срок жизни сессии;
- дополнительно 24 часа после её завершения.

После этого данные могут удаляться фоновой задачей.

## 8.8. Cleanup

Cleanup выполняется периодически.

Не допускается удалять историю использованных токенов во время действующей сессии.

При значительном объёме данных очистка выполняется пакетами.

# 9. Database Constraints

## 9.1. Первичные ключи

RefreshSession и RefreshToken используют UUID primary keys.

## 9.2. Внешние ключи

Предусматриваются:

```text
RefreshSession.userId -> User.id
RefreshToken.sessionId -> RefreshSession.id
```

## 9.3. Уникальность токена

Каждый tokenHash уникален.

Одинаковый хеш не может принадлежать нескольким RefreshToken records.

## 9.4. Один текущий токен

В одной сессии одновременно допускается не более одного неиспользованного refresh token.

Для этого рассматривается частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX uq_refresh_token_current
ON refresh_token (session_id)
WHERE consumed_at IS NULL;
```

Это проектный пример. Точные имена таблиц, индексов и миграций определяются при реализации.

## 9.5. Дополнительные индексы

Предусматриваются индексы для:

- поиска токена по tokenHash;
- поиска сессий пользователя;
- получения истории токенов сессии;
- очистки истёкших сессий.

Индексы должны соответствовать реальным запросам.

## 9.6. Ограничение транзакций

Database constraints дополняют, но не заменяют транзакционную защиту rotation.

## 9.7. Обучение перед реализацией

Перед написанием Flyway-миграций необходимо отдельно разобрать теорию PostgreSQL indexes:

- B-tree;
- UNIQUE indexes;
- partial indexes;
- composite indexes;
- влияние индексов на INSERT/UPDATE/DELETE;
- выбор индексов планировщиком;
- EXPLAIN ANALYZE.

Этот этап выполняется непосредственно перед реализацией индексов.

# 10. Refresh Flow

## 10.1. HTTP endpoint

```http
POST /api/auth/refresh
```

Access JWT для этой операции не требуется.

Refresh token передаётся в HttpOnly cookie.

## 10.2. Успешный результат

HTTP 200:

```json
{
  "accessToken": "<new-signed-access-jwt>",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

Одновременно устанавливается новая refresh cookie.

## 10.3. Rotation

Логическая последовательность:

1. Получить raw refresh token из cookie.
2. Вычислить его SHA-256.
3. Найти RefreshToken.
4. Определить владельца и RefreshSession.
5. Получить необходимые транзакционные блокировки.
6. Повторно проверить состояние User, Session и Token.
7. Сгенерировать новый access JWT.
8. Сгенерировать новый refresh token.
9. Пометить старый токен использованным.
10. Сохранить новый tokenHash.
11. Зафиксировать транзакцию.
12. Вернуть access JWT и установить новую cookie.

## 10.4. Проверка состояния

Успешный refresh требует:

```text
UserStatus.ACTIVE

AND Session not revoked

AND Session not expired

AND Token not consumed
```

## 10.5. Строгая rotation

Каждый успешно использованный refresh token становится недействительным для повторного применения.

Grace period не используется.

## 10.6. Replay detection

Повторное предъявление ранее использованного токена обнаруживается через сохранённую историю.

При подтверждённом replay отзывается затронутая refresh-сессия.

HTTP-ответ не раскрывает подробности внутренней истории токенов.

## 10.7. Ошибки

Отсутствующий, неизвестный, истёкший или отозванный refresh token не позволяет получить новый access JWT.

Основной ответ:

`401 Unauthorized`

## 10.8. Потерянный HTTP-ответ

Успешный PostgreSQL commit не гарантирует получение ответа браузером.

Если после rotation соединение разорвалось до получения новой cookie, клиент может остаться со старым токеном.

Для MVP допускается необходимость повторного login.

# 11. Concurrency Model

## 11.1. Основной инвариант

Одна действующая refresh-сессия не может иметь два одновременно действительных refresh tokens.

## 11.2. Transaction Boundary

Rotation выполняется атомарно.

Проверка, потребление старого токена и создание нового должны быть согласованы одной транзакцией.

## 11.3. Row Locking

Для операций, изменяющих цепочку токенов, используется блокировка RefreshSession.

При необходимости согласования с UserStatus также применяется блокировка соответствующего User.

## 11.4. Порядок блокировок

При необходимости нескольких блокировок применяется единый порядок:

```text
User
    |
    v
RefreshSession
    |
    v
RefreshToken
```

Это уменьшает вероятность deadlock.

## 11.5. Предварительный поиск

Для определения sessionId и userId допускается предварительное чтение RefreshToken без блокировки.

Такой поиск не является окончательной проверкой.

После получения блокировок состояние повторно проверяется.

## 11.6. Administrative User Blocking

Login и refresh должны быть согласованы с конкурентным изменением UserStatus.

После завершения административной блокировки новые операции выдачи токенов не должны успешно предоставлять рабочий доступ.

Механизм согласованного доступа к User реализуется через публичный контракт User module.

## 11.7. Rollback при replay

Если при replay необходимо отозвать сессию, отзыв должен быть зафиксирован до формирования HTTP-ошибки.

Нельзя допускать откат отзыва из-за необработанного RuntimeException в той же транзакции.

## 11.8. Генерация JWT

Генерация JWT должна быть согласована с транзакцией выдачи refresh token.

Ошибка генерации JWT не должна приводить к частично завершённой rotation в PostgreSQL.

Фиксация БД и доставка HTTP-ответа при этом остаются разными операциями.

## 11.9. Transaction Isolation

Для MVP рассматривается PostgreSQL READ COMMITTED с явными блокировками строк и database constraints.

Необходимость более высокого isolation level должна подтверждаться конкретными конкурентными сценариями.

# 12. Multiple Browser Tabs

## 12.1. Общая refresh cookie

Вкладки одного браузерного профиля могут использовать одну refresh cookie.

Access JWT каждой вкладки хранится в её JavaScript-памяти.

## 12.2. Проблема конкурентного refresh

Две вкладки могут одновременно отправить один и тот же refresh token.

При строгой rotation второй запрос может быть распознан как replay.

## 12.3. Выбранная стратегия

Для PsyWeb принят вариант C:

- single-flight внутри вкладки;
- межвкладочная координация;
- строгая серверная rotation.

## 12.4. Frontend Implementation

Для координации рассматриваются:

- BroadcastChannel;
- Web Locks API;
- эквивалентные механизмы.

Точный frontend-протокол определяется при реализации.

## 12.5. Security Boundary

Frontend-координация уменьшает случайные гонки, но не обеспечивает безопасность токенов.

Backend самостоятельно гарантирует корректность rotation.

# 13. Logout

## 13.1. Текущая сессия

```http
POST /api/auth/logout
```

Logout отзывает текущую RefreshSession.

Для определения сессии используется refresh cookie.

Действующий access JWT не обязателен.

## 13.2. Успешный ответ

HTTP 204 No Content.

Refresh cookie очищается.

## 13.3. Идемпотентность

Повторный logout должен быть безопасным.

Уже отозванная или отсутствующая сессия не должна приводить к восстановлению аутентификации.

## 13.4. Logout All

```http
POST /api/auth/logout-all
```

Операция требует действующего access JWT.

Отзываются все refresh-сессии текущего пользователя.

User ID определяется из SecurityContext.

## 13.5. Конкурентность

Logout и refresh одной сессии должны быть транзакционно согласованы.

Logout-all должен быть согласован с конкурентным login и refresh.

## 13.6. Ранее выданный access JWT

Отзыв RefreshSession не делает автоматически недействительным ранее выданный access JWT.

При ACTIVE пользователе он может оставаться действительным до expiration.

Мгновенный отзыв access JWT при logout относится к post-MVP.

# 14. HTTP Authentication API

## 14.1. Login

```text
POST /api/auth/login
```

Доступ: публичный.

Успех:

- HTTP 200;
- access JWT в JSON;
- refresh token в HttpOnly cookie.

## 14.2. Refresh

```text
POST /api/auth/refresh
```

Доступ: без access JWT, но с действительным refresh token.

Успех:

- HTTP 200;
- новый access JWT;
- новая refresh cookie.

## 14.3. Logout

```text
POST /api/auth/logout
```

Доступ: по refresh cookie.

Успех:

- HTTP 204;
- отзыв текущей сессии;
- очистка cookie.

## 14.4. Logout All

```text
POST /api/auth/logout-all
```

Доступ: действующий access JWT.

Успех:

- HTTP 204;
- отзыв refresh-сессий пользователя.

## 14.5. Current User

```text
GET /api/auth/me
```

Доступ: действующий access JWT.

Возвращает минимальный безопасный User DTO.

Не возвращает JPA Entity или passwordHash.

## 14.6. Authentication Errors

Предусматриваются:

- HTTP 400 — некорректный request;
- HTTP 401 — отсутствие или недействительность аутентификации;
- HTTP 403 — недостаточно прав или неуспешная CSRF-проверка.

Формат ответа согласовывается с GlobalExceptionHandler.

## 14.7. Cache-Control

Ответы с access JWT должны исключаться из HTTP-кэширования.

Предусматривается:

```http
Cache-Control: no-store
```

# 15. Cookies, CSRF и CORS

## 15.1. Production Architecture

Frontend и backend размещаются через один origin.

Пример:

```text
https://psyweb.example/
https://psyweb.example/api/...
```

Домен приведён для иллюстрации.

## 15.2. Development

React использует Vite dev server и proxy для `/api/...`.

Реальные dev-настройки cookies и HTTPS должны быть отдельно проверены.

## 15.3. Refresh Cookie

Целевая production-конфигурация:

```http
Set-Cookie: __Host-psyweb-refresh=<token>;
  HttpOnly;
  Secure;
  SameSite=Strict;
  Path=/;
  Max-Age=604800
```

Не устанавливается Domain.

## 15.4. CSRF Protection

Cookie-based операции должны быть защищены от CSRF.

Целевая интеграция:

- Spring Security;
- CookieCsrfTokenRepository;
- SPA-compatible CSRF handling;
- X-XSRF-TOKEN header;
- строгая проверка Origin.

Предусматривается bootstrap endpoint:

```text
GET /api/auth/csrf
```

## 15.5. Обязательные проверки

Нужно подтвердить:

- корректное формирование CSRF-токена;
- невозможность выполнения cookie-based операций без необходимой CSRF-проверки;
- работу защиты после login и logout;
- защиту от подмены cookie;
- соответствие используемой версии Spring Security;
- отсутствие случайного открытия защищённых маршрутов.

CSRF не должен отключаться глобально только потому, что приложение использует JWT.

## 15.6. CORS

Production CORS не должен разрешать произвольные origins.

Для same-origin frontend/API открытый CORS не требуется.

## 15.7. Security Headers

Требуется предусмотреть безопасные HTTP-заголовки и защиту от XSS.

HttpOnly запрещает прямое чтение refresh cookie JavaScript, но не устраняет последствия произвольного исполнения вредоносного кода на странице.

# 16. Specialist Authorization Integration

## 16.1. Professional Eligibility

Условие профессионального допуска:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
```

## 16.2. Booking Eligibility

Дополнительное разрешение на бронирования:

```text
SpecialistBookingAccess.bookingAllowed = TRUE
```

## 16.3. Полный критерий

Для профессиональных сценариев бронирования требуется:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
AND SpecialistBookingAccess.bookingAllowed = TRUE
```

Инициатором клиентской Reservation при этом остаётся CLIENT.

## 16.4. Независимость ограничений

Изменение UserStatus или approvalStatus не снимает автоматически отдельное ограничение bookingAllowed.

## 16.5. Место проверки

Проверка professional eligibility и bookingAllowed принадлежит соответствующим прикладным сервисам.

JWT authentication не должен загружать SpecialistBookingAccess для каждого защищённого HTTP-запроса.

# 17. Administrative Booking Concurrency

## 17.1. Область ответственности

Транзакционная координация административной блокировки специалиста и операций бронирования относится к Booking/Admin business flow.

Она не реализуется внутри JWT authentication.

## 17.2. Согласованный протокол

Создание и подтверждение Reservation используют:

`SpecialistBookingAccess FOR SHARE`

Административная операция, лишающая специалиста допуска, использует:

`SpecialistBookingAccess FOR UPDATE`

## 17.3. Административная блокировка

В одной транзакции необходимо:

1. Получить BookingAccess FOR UPDATE.
2. Изменить необходимое состояние допуска.
3. Найти ACTIVE Reservation специалиста.
4. Отменить их с соблюдением порядка блокировок.
5. Удалить соответствующие ScheduleOccupancy.
6. Сохранить административный аудит.
7. Выполнить COMMIT.

## 17.4. Confirmed Booking

Уже подтверждённые Booking не отменяются автоматически только из-за изменения bookingAllowed.

## 17.5. Независимость от Auth

Эти правила не заменяют проверку UserStatus при login, refresh или обработке access JWT.

# 18. Authentication Rules

## AU-001. Valid Credentials

Успешный login требует корректных учётных данных.

## AU-002. Active Account

Login и refresh требуют UserStatus.ACTIVE.

## AU-003. SpecialistStatus Independence

Для ACTIVE пользователя роль SPECIALIST не требует APPROVED для самого login.

## AU-004. Minimal Access JWT

JWT содержит необходимые identity claims и технические сведения.

## AU-005. Current Account State

Защищённые запросы проверяют актуальный UserStatus.

## AU-006. Trusted Identity

Идентичность инициатора защищённой операции определяется через SecurityContext.

## AU-007. Authentication vs Authorization

Аутентификация не заменяет проверку прав на конкретную бизнес-операцию.

## AU-008. Professional Eligibility

Специалист допускается к профессиональным операциям только при выполнении условий соответствующей policy.

## AU-009. Booking Access

Для операций бронирования отдельно проверяется bookingAllowed.

## AU-010. Refresh Rotation

Каждый успешный refresh потребляет текущий токен и создаёт новый.

## AU-011. Refresh Expiration

Срок refresh-сессии составляет 7 дней и не продлевается при rotation.

## AU-012. Replay Detection

Повторное использование ранее потреблённого refresh token должно обнаруживаться.

## AU-013. Session Revocation

Logout отзывает текущую сессию.

Logout-all отзывает все сессии пользователя.

## AU-014. Atomicity

Rotation выполняется атомарно с соблюдением согласованного порядка блокировок.

## AU-015. CSRF

Cookie-based auth endpoints проходят предусмотренную CSRF и Origin проверку.

## AU-016. Secret Handling

Пароли, исходные refresh tokens и signing keys не сохраняются в публичном репозитории и не логируются.

# 19. Testing Strategy

## 19.1. Login Tests

Проверяются:

- успешный login;
- неправильный пароль;
- неизвестный email;
- нормализация email;
- UserStatus.BLOCKED;
- login специалиста при всех допустимых SpecialistStatus;
- отсутствие чувствительных данных в ответе.

## 19.2. JWT Tests

Проверяются:

- корректная подпись;
- неправильная подпись;
- неподдерживаемый алгоритм;
- expired JWT;
- некорректные claims;
- issuer;
- audience.

## 19.3. Refresh Tests

Проверяются:

- успешная rotation;
- отсутствие refresh cookie;
- неизвестный токен;
- consumed token;
- expired session;
- revoked session;
- UserStatus.BLOCKED;
- создание новой пары токенов;
- отсутствие двух одновременно активных поколений.

## 19.4. Replay Detection Tests

Проверяются:

- обнаружение старого токена;
- определение связанной сессии;
- сохранение revocation в PostgreSQL;
- корректная обработка RuntimeException и rollback.

## 19.5. Concurrency Tests

Проверяются:

- два одновременных refresh;
- refresh одновременно с logout;
- refresh одновременно с logout-all;
- refresh одновременно с административной блокировкой;
- login одновременно с административной блокировкой.

## 19.6. Multi-Device Tests

Проверяются:

- независимые refresh-сессии;
- logout одного устройства;
- logout-all;
- невозможность дальнейшего refresh отозванной сессии.

## 19.7. Security Tests

Проверяются:

- защищённые маршруты;
- HTTP 401 и 403;
- CSRF;
- Origin validation;
- cookie flags;
- очистка cookie;
- отсутствие secrets в ответах;
- невозможность использования refresh cookie вместо access JWT для обычных business endpoints.

## 19.8. Booking Authorization Tests

Отдельно проверяются:

- professional eligibility;
- bookingAllowed;
- ownership;
- участие пользователя в Booking;
- конкурентная административная блокировка.

Эти тесты относятся к соответствующим бизнес-модулям.

# 20. Security and Public Repository

## 20.1. Разрешено публиковать

В публичном Git-репозитории могут находиться:

- Java source code;
- JPA Entities;

- JWT signing private keys;
- реальные refresh tokens;
- access tokens реальных пользователей;
- пароли;
- заполненные секретами .env;
- production credentials;
- HMAC secrets;
- дампы PostgreSQL с персональными данными;
- журналы с authentication secrets.

Секреты загружаются через внешнюю конфигурацию.

В репозитории допускаются только placeholder или демонстрационные значения.

## 20.4. Проверка перед коммитом

Перед push необходимо проверять staged diff и исключать случайное попадание секретов.

Если секрет уже попал в Git, удаления файла недостаточно: секрет подлежит отзыву или замене.

# 23. Итог

Для backend PsyWeb выбрана модель:

**Stateless JWT Access Authentication + Stateful Refresh Sessions.**

Основные принципы:

- User подтверждает credentials через Argon2id;
- access JWT действует 15 минут;
- refresh-сессия действует 7 дней;
- refresh token является opaque random secret;
- PostgreSQL хранит только хеши и метаданные refresh tokens;
- новые auth-сущности используют UUIDv4;
- strict rotation выполняется атомарно;
- история токенов сохраняется для replay detection;
- Auth использует публичные контракты User module;
- UserStatus проверяется по актуальному состоянию;
- SpecialistStatus и BookingAccess определяют отдельные бизнес-ограничения;
- Spring Security предоставляет доверенную идентичность;
- cookie-based операции требуют CSRF-защиты;
- logout отзывает refresh-сессии;
- мгновенный отзыв access JWT остаётся post-MVP;
- реальные секреты не должны попадать в публичный Git-репозиторий.

**Статус: DRAFT — целевая backend-архитектура аутентификации согласована, реализация и технические контракты проверяются отдельно.**
