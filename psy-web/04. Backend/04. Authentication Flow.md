## Overview

This section describes the authentication mechanism used in the PsyWeb backend system. The system is based on stateless JWT authentication integrated with Spring Security.

The goal of the authentication flow is to ensure secure access control, role-based authorization, and stateless request validation.

---

# Authentication Strategy

The system uses:

- JWT (JSON Web Token) for authentication
- BCrypt for password hashing
- Spring Security for request filtering and authorization
- Stateless session management (no server-side sessions)

---

# Authentication Flow (Login)

## Step-by-step process

```
Client → AuthController → AuthService → UserRepository → Password Verification → JWT Generation → Response
```

---

## 1. Client Request

User sends credentials:

- email
- password

---

## 2. AuthController

Responsibilities:

- receive login request DTO
- validate input format
- delegate authentication logic to service layer

No business logic is performed in this layer.

---

## 3. AuthService

Core authentication logic:

- retrieve user by email
- verify password using BCrypt
- validate user status (ACTIVE / BLOCKED / PENDING)
- determine user role

If authentication is successful:

- generate JWT token

---

## 4. Password Verification

Password validation uses BCrypt:

- stored password is hashed
- incoming password is matched against hash
- mismatch results in authentication failure

---

## 5. JWT Generation

JWT token contains:

- userId
- role
- issuedAt
- expirationTime

Token is signed using server-side secret key.

---

## 6. Response

Backend returns:

- JWT token
- basic user metadata (optional)
- role information

---

# Authentication Flow (Subsequent Requests)

For every secured request:

```
Client → Security Filter → JWT Validation → SecurityContext → Controller → Service → Response
```

---

## 1. JWT Extraction

Spring Security filter extracts token from:

- Authorization header (Bearer token)

---

## 2. Token Validation

System validates:

- signature integrity
- expiration time
- token structure

If invalid → request is rejected with 401 Unauthorized.

---

## 3. SecurityContext Setup

If valid:

- user identity is extracted
- role is extracted
- authentication object is stored in SecurityContext

This enables role-based access checks in downstream layers.

---

## 4. Authorization Check

After authentication:

- endpoint access is validated based on role
- method-level security may be applied (if enabled)

---

## 5. Controller Execution

Request proceeds to controller only if:

- authentication is valid
- authorization rules are satisfied

---

# Security Model

## 1. Stateless Architecture

- No server-side sessions
- Each request is independently authenticated
- JWT is the only source of identity

---

## 2. Role-Based Access Control (RBAC)

Supported roles:

- CLIENT
- SPECIALIST
- ADMIN

Access decisions are based on:

- role from JWT
- endpoint restrictions
- service-level ownership validation

---

## 3. Ownership Validation

In addition to RBAC:

- users can only access their own resources
- enforced at service layer

---

## 4. Token Expiration Strategy

JWT tokens have a fixed expiration time.

After expiration:

- user must re-authenticate
- old token becomes invalid

---

# Security Boundaries

- Auth module is responsible only for identity verification and token issuance
- Security filters handle request-level validation
- Business modules must not implement authentication logic
- Authorization is enforced both at filter level and service level

---

# Summary

The authentication system is built on:

- stateless JWT-based security
- centralized token validation via Spring Security filters
- strict separation between authentication and business logic
- role-based and ownership-based access control
