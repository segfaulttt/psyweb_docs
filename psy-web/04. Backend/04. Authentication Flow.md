
# 04. Процесс аутентификации (Authentication Flow)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**Безопасность:** Spring Security + JWT  
**Статус:** DRAFT — целевой контракт утверждён, реализация инфраструктуры требует проверки

---

# 1. Назначение документа

Документ описывает архитектуру аутентификации пользователей PsyWeb.

Аутентификация устанавливает личность пользователя, выполняющего запрос.

Она отвечает на вопрос:

**Кто обращается к системе?**

При этом PsyWeb разделяет четыре понятия:

1. Аутентификация пользователя.
2. Состояние учётной записи.
3. Авторизация на выполнение операции.
4. Профессиональный допуск специалиста и его право принимать бронирования.

Успешная аутентификация не означает автоматического разрешения любой бизнес-операции.

Например, специалист может успешно войти в систему, но не иметь права принимать новые Reservation.

---

# 2. Текущее состояние реализации

В исходной реализации PsyWeb уже предусмотрены:

- UserRole;
- UserStatus;
- поиск пользователей;
- поиск только ACTIVE пользователей;
- нормализация email;
- SpecialistStatus;
- проверка профессиональной пригодности специалиста.

В существующей модели UserStatus содержит:

- ACTIVE;
- BLOCKED.

Статуса UserStatus.PENDING нет.

Существующий SpecialistStatus содержит:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

В новой архитектурной документации для состояния модерации специалиста используется название:

`Specialist.approvalStatus`

Окончательное имя Java enum и соответствие существующей реализации необходимо согласовать при рефакторинге.

На момент исходной документации JWT-инфраструктура ещё не была реализована полностью.

Поэтому описанные далее AuthController, JWT Filter и SecurityContext относятся к целевой архитектуре, пока их наличие не подтверждено актуальным исходным кодом.

---

# 3. Целевая стратегия аутентификации

Для MVP используется:

- Spring Security;
- JWT access tokens;
- BCrypt для проверки паролей;
- stateless HTTP authentication;
- проверка актуального состояния User при защищённых запросах.

Серверная HTTP-сессия для хранения аутентифицированного состояния не требуется.

## 3.1. Основной принцип

JWT подтверждает идентичность пользователя.

JWT не является постоянным источником истины о его текущих полномочиях.

## 3.2. Изменяемое состояние

После выдачи JWT могут измениться:

- User.status;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

Такие изменения должны учитываться при выполнении защищённых операций.

## 3.3. Граница ответственности

Authentication не определяет:

- доступность времени консультации;
- возможность создать Reservation;
- возможность подтвердить Reservation;
- право изменить Booking;
- право оставить Review.

Эти решения принимаются соответствующими механизмами авторизации и доменными сервисами.

# 4. Процесс входа (Login Flow)

## 4.1. Общая схема

```text
Client
    ↓
AuthController
    ↓
AuthService
    ↓
User lookup
    ↓
Password verification
    ↓
UserStatus validation
    ↓
JWT generation
    ↓
AuthenticationResponse
```

## 4.2. Входные данные

Пользователь передаёт:

- email;
- password.

Конкретные endpoint и DTO определяются в API-контрактах.

## 4.3. Поиск пользователя

Перед поиском email нормализуется по правилам User Domain.

Утверждённая политика:

```text
trim
    ↓
lowercase(Locale.ROOT)
    ↓
validate canonical email
```

Создание аккаунта, изменение email и поиск при входе должны использовать одну согласованную политику.

AuthService не должен реализовывать независимую нормализацию email с другими правилами.

## 4.4. Проверка пароля

AuthService:

1. Находит User по каноническому email.
2. Получает сохранённый passwordHash.
3. Проверяет переданный пароль через PasswordEncoder.
4. Проверяет состояние аккаунта.
5. При успехе формирует JWT.

## 4.5. Условие успешного входа

Успешный вход требует:

```text
Valid credentials
AND UserStatus.ACTIVE
```

## 4.6. Заблокированный аккаунт

Если:

`UserStatus.BLOCKED`

вход запрещён даже при правильном пароле.

## 4.7. Ошибки входа

Ошибки не должны раскрывать пароль, passwordHash или другие чувствительные сведения.

Публичный формат ошибок должен соответствовать общей стратегии обработки исключений.

---

# 5. Профессиональный статус специалиста и Login

## 5.1. Основной принцип

Профессиональный статус специалиста не является состоянием аутентификации.

Пользователь с ролью SPECIALIST может войти в систему при:

`UserStatus.ACTIVE`

даже если его заявка ещё не одобрена.

## 5.2. Возможные состояния

В исходной реализации предусмотрены:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

В целевой архитектуре они относятся к модерационному состоянию специалиста.

## 5.3. Доступ после входа

Специалист со статусом PENDING, REJECTED или SUSPENDED может иметь ограниченный доступ к собственному аккаунту.

Например:

- просмотр собственного профиля;
- просмотр состояния модерации;
- действия, явно разрешённые правилами соответствующего статуса.

При этом он не получает автоматически право выполнять профессиональные операции.

## 5.4. Разделение

Следующие утверждения различаются:

- пользователь может аутентифицироваться;
- пользователь имеет роль SPECIALIST;
- специалист прошёл модерацию;
- специалист имеет право принимать новые бронирования.

Они не должны объединяться в одну проверку.

# 6. Контракт JWT

## 6.1. Назначение

После успешного Login backend выдаёт подписанный JWT access token.

## 6.2. Минимальные claims

Для MVP токен содержит необходимые сведения:

- userId;
- role;
- expiration.

Могут присутствовать стандартные технические claims JWT, необходимые для проверки токена.

## 6.3. Исключённые данные

JWT не должен использовать как долговременные авторизационные claims:

- UserStatus;
- SpecialistApprovalStatus;
- SpecialistBookingAccess.bookingAllowed.

Эти значения являются изменяемыми.

## 6.4. Причина

Если администратор заблокировал пользователя после выдачи JWT, старый токен не должен сохранять ему доступ.

Аналогично изменение состояния модерации специалиста должно влиять на профессиональную авторизацию без ожидания истечения токена.

## 6.5. Защита

JWT должен:

- иметь проверяемую подпись;
- содержать ограниченный срок действия;
- проверяться на каждом защищённом запросе;
- отклоняться при неправильной структуре или подписи.

Точный алгоритм подписи и стратегия управления ключами относятся к реализации Security.

# 7. Обработка защищённого запроса

## 7.1. Общая последовательность

```text
HTTP Request
    ↓
Authorization: Bearer JWT
    ↓
Spring Security Filter Chain
    ↓
JWT signature validation
    ↓
Expiration validation
    ↓
Extract userId / role
    ↓
Load current User
    ↓
Require UserStatus.ACTIVE
    ↓
Create Authentication
    ↓
SecurityContext
    ↓
Authorization
    ↓
Controller
    ↓
Application Service
```

## 7.2. Проверка токена

Security Filter должен проверить:

- присутствие токена для защищённого endpoint;
- подпись;
- срок действия;
- обязательные claims;
- корректность идентификатора пользователя.

## 7.3. Недействительный токен

Недействительный или просроченный JWT не создаёт аутентифицированную идентичность.

## 7.4. Актуальный User

После проверки JWT Security загружает текущее состояние User.

Защищённый запрос требует:

`UserStatus.ACTIVE`

## 7.5. Пример последующей блокировки

```text
User.status = ACTIVE
    ↓
User successfully logs in
    ↓
JWT issued
    ↓
Administrator blocks User
    ↓
User.status = BLOCKED
    ↓
User sends request with old JWT
    ↓
JWT signature remains valid
    ↓
Current User.status is checked
    ↓
Request rejected
```

## 7.6. Отсутствие blacklist

Для MVP не требуется:

- Redis token blacklist;
- отдельное хранилище отозванных access tokens;
- распределённая серверная сессия.

Проверка актуального UserStatus является основным механизмом прекращения доступа заблокированного аккаунта.

---

# 8. SecurityContext

## 8.1. Назначение

После успешной аутентификации Spring Security создаёт Authentication и помещает его в SecurityContext.

## 8.2. Данные

Authentication содержит сведения, необходимые для установления:

- userId;
- роли;
- факта успешной аутентификации.

## 8.3. Использование

Прикладные операции получают доверенную идентичность вызывающего пользователя.

Она используется для:

- проверки владельца Reservation;
- проверки владельца Booking;
- проверки владельца Schedule;
- проверки принадлежности Review;
- проверки административных полномочий.

## 8.4. Запрет доверия пользовательскому вводу

Нельзя принимать clientId, specialistId или administratorId из JSON как самостоятельное доказательство того, кто выполняет операцию.

## 8.5. Независимость домена

Domain Entities не должны зависеть непосредственно от SecurityContext.

Идентичность инициатора передаётся в прикладные операции через согласованные контракты.

---

# 9. Профессиональный допуск специалиста

## 9.1. Основная проверка

Профессиональный допуск зависит от:

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
```

## 9.2. Ограниченные статусы

Специалисты со статусами PENDING, REJECTED или SUSPENDED не считаются одобренными для профессиональных операций.

## 9.3. Отдельное право принимать бронирования

Для создания новых Reservation и подтверждения существующих ACTIVE Reservation необходимо дополнительное условие:

`SpecialistBookingAccess.bookingAllowed = TRUE`

## 9.4. Полное условие бронирования

```text
UserRole.SPECIALIST
AND UserStatus.ACTIVE
AND Specialist.approvalStatus = APPROVED
AND SpecialistBookingAccess.bookingAllowed = TRUE
```

Роль SPECIALIST здесь характеризует учётную запись, которой принадлежит профиль специалиста.

Инициатором клиентской Reservation при этом остаётся авторизованный CLIENT.

## 9.5. Независимость ограничений

Одобрение специалиста не снимает отдельную административную блокировку bookingAllowed.

Разблокировка аккаунта также не должна автоматически отменять ограничение BookingAccess.

## 9.6. Где выполняется проверка

Полное условие бронирования проверяется при выполнении соответствующего бизнес-сценария.

Не следует загружать и блокировать BookingAccess при каждом HTTP-запросе специалиста, если операция не связана с бронированием.

---

# 10. Координация административных изменений

## 10.1. Проблема

Административная блокировка специалиста может происходить одновременно с созданием или подтверждением Reservation.

Простой проверки статуса без транзакционной координации недостаточно.

## 10.2. Утверждённый механизм

Создание и подтверждение Reservation используют:

`SpecialistBookingAccess FOR SHARE`

Административная операция, лишающая специалиста допуска, использует:

`SpecialistBookingAccess FOR UPDATE`

## 10.3. Административная блокировка

В одной транзакции необходимо:

1. Получить BookingAccess FOR UPDATE.
2. Изменить необходимое состояние допуска.
3. Найти ACTIVE Reservation специалиста.
4. Отменить их с соблюдением порядка блокировок.
5. Удалить соответствующие ScheduleOccupancy.
6. Сохранить административный аудит.
7. Выполнить COMMIT.

## 10.4. CONFIRMED Booking

Уже подтверждённые Booking не отменяются автоматически.

## 10.5. Граница Authentication

Этот протокол не является частью JWT Filter.

Он принадлежит прикладной и административной бизнес-логике.

SecurityContext определяет, кто выполняет операцию, но не заменяет необходимую транзакционную координацию.

---

# 11. Разграничение Authentication и Authorization

## 11.1. Authentication

Устанавливает:

- идентичность пользователя;
- роль;
- актуальное разрешённое состояние аккаунта.

## 11.2. Authorization

Определяет, разрешено ли конкретное действие.

Может зависеть от:

- UserRole;
- UserStatus;
- Specialist.approvalStatus;
- BookingAccess;
- принадлежности ресурса;
- участия в консультации;
- текущего состояния Reservation или Booking;
- предметных временных ограничений.

## 11.3. Примеры

ACTIVE CLIENT не может подтвердить чужую Reservation.

ACTIVE SPECIALIST без APPROVED не может выполнять операции, требующие профессионального допуска.

APPROVED SPECIALIST с bookingAllowed = FALSE не может принимать новые бронирования.

ADMIN не может произвольно менять BookingStatus в обход бизнес-правил.

## 11.4. Разделение проверок

Общие проверки доступа могут выполняться Spring Security.

Предметные проверки выполняются сервисами соответствующих модулей.

---

# 12. Безопасность паролей

## 12.1. Хранение

Пароли не хранятся в открытом виде.

В PostgreSQL сохраняется passwordHash.

## 12.2. Проверка

Целевой AuthService использует BCrypt через настроенный PasswordEncoder.

## 12.3. Запреты

Нельзя:

- логировать исходные пароли;
- возвращать passwordHash в API;
- передавать пароль в доменные события;
- сравнивать пароль с hash обычным строковым сравнением.

## 12.4. Ответственность

Проверка пароля относится к Authentication.

Бизнес-модули Booking, Schedule или Review не должны повторно проверять пароль при каждой операции.

---

# 13. Срок действия JWT

## 13.1. Ограниченный срок

Access token имеет конечное время действия.

## 13.2. Истечение

После expiration токен отклоняется.

## 13.3. Повторная аутентификация

Для MVP после истечения access token пользователь выполняет повторный Login.

## 13.4. Refresh token

Refresh-token инфраструктура не является обязательной частью первоначального MVP.

Она может быть спроектирована отдельно при появлении соответствующих требований.

---

# 14. Logout

## 14.1. Stateless-модель

При обычном Logout клиентское приложение удаляет сохранённый access token.

## 14.2. Серверная сессия

Backend не хранит аутентифицированную HTTP-сессию для последующего удаления при Logout.

## 14.3. Ранее выданный токен

Удаление токена на одном клиентском устройстве не отзывает автоматически другие копии этого JWT.

До expiration криптографическая подпись остаётся действительной.

## 14.4. Блокировка аккаунта

Если пользователь заблокирован, актуальная проверка UserStatus прекращает доступ к защищённым операциям независимо от срока жизни JWT.

## 14.5. Будущее расширение

Принудительный отзыв токенов может быть добавлен позднее.

Для этого потребуется отдельная инфраструктурная модель.

---

# 15. Правила аутентификации

## AU-001. Корректные учётные данные

Успешный Login требует правильных учётных данных.

## AU-002. Активный аккаунт

Успешный Login требует:

`UserStatus.ACTIVE`

BLOCKED аккаунт не может выполнить вход.

## AU-003. Независимость Login от модерации

Для ACTIVE пользователя с ролью SPECIALIST аутентификация не зависит от Specialist.approvalStatus.

## AU-004. Минимальный JWT

JWT содержит только необходимые стабильные identity claims и технические сведения.

## AU-005. Актуальное состояние аккаунта

При каждом защищённом запросе проверяется текущее состояние User.

## AU-006. Разделение Authentication и Authorization

Аутентификация устанавливает личность, но не гарантирует разрешение конкретной бизнес-операции.

## AU-007. Эффективный допуск специалиста

При создании и подтверждении Reservation проверяются:

- User.status = ACTIVE;
- Specialist.approvalStatus = APPROVED;
- SpecialistBookingAccess.bookingAllowed = TRUE.

## AU-008. Независимость административных ограничений

Изменение approvalStatus или UserStatus не снимает автоматически отдельное ограничение bookingAllowed.

## AU-009. Доверенный SecurityContext

Идентичность инициатора защищённого действия определяется через SecurityContext, а не через произвольные идентификаторы запроса.

## AU-010. Транзакционная координация

JWT Filter не заменяет транзакционные проверки допуска при конкурентных операциях Booking.

# 16. Текущая реализация и целевая архитектура

## 16.1. Отражено в исходной реализации

В исходной документации подтверждены:

- UserRole;
- UserStatus.ACTIVE / BLOCKED;
- поиск User;
- поиск ACTIVE User;
- нормализация email;
- SpecialistStatus;
- профессиональная проверка специалиста.

Этот перечень описывает состояние, зафиксированное исходной документацией, а не результат повторной проверки актуального приложения.

## 16.2. Целевая инфраструктура

Требуется обеспечить:

- AuthController;
- AuthService;
- BCrypt login verification;
- JWT generation;
- JWT Security Filter;
- Spring SecurityContext;
- актуальную проверку UserStatus;
- защищённые HTTP endpoints;
- обработку ошибок аутентификации.

## 16.3. Целевая бизнес-интеграция

Дополнительно требуется согласовать:

- Specialist.approvalStatus;
- SpecialistBookingAccess;
- административные блокировки;
- проверку допуска при создании Reservation;
- проверку допуска при подтверждении Reservation.

## 16.4. Проверка реализации

Наличие требований в этом документе не означает, что они уже реализованы.

Фактическое состояние следует устанавливать по исходному коду PsyWeb и интеграционным тестам.

# 17. Тестирование

## 17.1. Login

Проверяются:

- успешный вход;
- неправильный пароль;
- неизвестный email;
- нормализация email;
- BLOCKED User.

## 17.2. JWT

Проверяются:

- корректная подпись;
- неправильная подпись;
- истёкший токен;
- отсутствие обязательных claims;
- некорректный формат.

## 17.3. Актуальный UserStatus

Проверяется ситуация, когда пользователь получает JWT, а затем блокируется.

Старый JWT не должен разрешать защищённый запрос.

## 17.4. SpecialistStatus

Проверяется возможность аутентификации ACTIVE специалиста в состояниях:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

При этом профессиональная авторизация должна соблюдать ограничения соответствующего состояния.

## 17.5. BookingAccess

Проверяется, что APPROVED специалист с bookingAllowed = FALSE не может принимать новые Reservation.

## 17.6. Ownership

Проверяется невозможность выполнять операции над чужими Reservation и Booking.

## 17.7. Конкурентность

Транзакционную координацию административной блокировки с созданием и подтверждением Reservation необходимо проверять интеграционными тестами PostgreSQL.

Эти проверки относятся к Booking и Admin, но подтверждают корректность разделения Authentication и бизнес-допуска.

---

# 18. Итог

PsyWeb использует целевую stateless-модель аутентификации на основе JWT и Spring Security.

Основные принципы:

- JWT устанавливает идентичность пользователя;
- пароль проверяется через BCrypt;
- для защищённых запросов требуется актуальный ACTIVE User;
- Professional eligibility специалиста не определяет право на Login;
- право принимать бронирования требует отдельной проверки BookingAccess;
- Authentication не подменяет Authorization;
- предметные ограничения выполняются соответствующими бизнес-сервисами;
- административные изменения допуска координируются транзакционно;
- ранее выданный JWT не должен позволять обойти последующую блокировку аккаунта;
- фактическое состояние реализации отделяется от утверждённой целевой архитектуры.

**Статус: DRAFT — целевой контракт определён, соответствие текущей реализации требует отдельной проверки.**
