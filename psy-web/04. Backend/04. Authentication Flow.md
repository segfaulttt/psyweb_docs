# Authentication Flow

## Overview

This document defines the authentication contract for the PsyWeb backend.

PsyWeb separates:

- account authentication;
- account eligibility;
- role-based authorization;
- specialist professional eligibility.

Authentication answers:

> Who is making the request?

Authorization and domain eligibility determine what that authenticated user may do.

---

# Current Implementation Status

The current `PsyWeb/main` already implements the account and specialist state required by the authentication contract:

- `UserRole`;
- `UserStatus.ACTIVE / BLOCKED`;
- unrestricted and ACTIVE-only User lookup;
- `SpecialistStatus.PENDING / APPROVED / REJECTED / SUSPENDED`;
- specialist professional eligibility;
- canonical email normalization.

The JWT authentication infrastructure itself is not yet implemented in the current backend.

The following sections therefore describe the approved target authentication contract and must not be interpreted as already implemented HTTP/security infrastructure.

---

# Target Authentication Strategy

The target authentication model uses:

- JWT access tokens;
- BCrypt password verification;
- Spring Security;
- stateless HTTP authentication;
- centralized validation of the current User account state.

No server-side authenticated HTTP session is required for MVP.

---

# 1. Login Flow

Target flow:

```text
Client
→ AuthController
→ AuthService
→ User lookup
→ password verification
→ UserStatus validation
→ JWT generation
→ response
```

## 1.1 Login Request

The client submits:

- email;
- password.

The exact REST DTO and endpoint contract belong to the API/security implementation.

---

## 1.2 Email Lookup

User email is canonicalized according to the current User-domain rule before lookup.

The implemented normalization rule is:

```text
trim
→ lowercase using Locale.ROOT
→ validate canonical email
```

User creation, email changes, and email lookup use the same normalization policy.

Authentication must therefore not introduce a second independent email-normalization rule.

---

## 1.3 Credential Validation

The target authentication service:

1. loads the User by normalized email;
2. verifies the supplied password against the stored password hash;
3. checks the current account status.

Successful login requires:

```text
valid credentials
+
UserStatus.ACTIVE
```

`UserStatus.BLOCKED` prevents successful authentication.

The User domain currently defines only:

```text
ACTIVE
BLOCKED
```

There is no `UserStatus.PENDING`.

---

# 2. SpecialistStatus and Login

`SpecialistStatus` is not authentication state.

A User with role `SPECIALIST` may authenticate when:

```text
UserStatus.ACTIVE
```

regardless of whether the linked Specialist currently has:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

These statuses affect professional authorization after authentication.

They do not determine whether the account credentials themselves are valid.

This separation allows PENDING, REJECTED, and SUSPENDED specialists to retain limited account-level access such as viewing moderation state or participating in explicitly allowed owner/moderation workflows without receiving professional specialist privileges.

---

# 3. JWT Contract

After successful authentication, the backend issues a signed JWT access token.

For MVP the token contains only the minimum stable identity claims required by the security layer:

- `userId`;
- `role`;
- expiration.

Mutable account or professional state is not stored as an authorization source inside the JWT.

In particular, the token does not contain:

- `UserStatus`;
- `SpecialistStatus`.

Both values may change after token issuance.

An old token must not permanently preserve privileges that are no longer valid.

---

# 4. Protected Request Flow

Target protected-request flow:

```text
Client
→ Bearer JWT
→ Security Filter
→ signature / expiration validation
→ extract userId and role
→ load current User
→ require UserStatus.ACTIVE
→ create authenticated principal
→ authorization
→ Controller
→ Service
```

## 4.1 JWT Validation

For each protected request, the security layer validates:

- token presence where authentication is required;
- token signature;
- token expiration;
- required token structure.

An invalid or expired token does not establish an authenticated principal.

---

## 4.2 Current User Reload

A valid token alone is not sufficient to authorize protected business operations.

After extracting `userId`, the security layer must obtain the current User state from persistence.

The current account must satisfy:

```text
UserStatus.ACTIVE
```

This check is centralized in the security layer rather than manually duplicated across every controller and service method.

Consequently:

```text
User receives JWT while ACTIVE
→ administrator changes UserStatus to BLOCKED
→ old JWT is still cryptographically valid
→ protected request reloads current User
→ BLOCKED is detected
→ request is rejected
```

For MVP, the additional User lookup on protected requests is accepted.

Token blacklist, Redis-backed revocation, and similar infrastructure are not required.

---

# 5. SecurityContext

After successful token validation and current-account validation, the security layer creates an authenticated principal and stores it in Spring Security's `SecurityContext`.

The authenticated identity may then be used for:

- role checks;
- ownership validation;
- participant validation;
- domain-specific authorization.

JWT establishes identity.

It does not replace current persisted business state.

---

# 6. Specialist Professional Eligibility

Authentication of a SPECIALIST does not imply permission to perform professional operations.

The current implemented domain eligibility rule is:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

Only this combination represents a professionally eligible specialist.

`PENDING`, `REJECTED`, and `SUSPENDED` specialists may authenticate when their User account is ACTIVE, but they are not professionally eligible.

Professional eligibility is enforced by reusable specialist/domain authorization logic rather than by encoding `SpecialistStatus` into the JWT.

---

# 7. Authentication and Authorization Boundary

Authentication and authorization remain separate concerns.

Authentication establishes:

```text
userId
+
UserRole
+
current ACTIVE account
```

Authorization may additionally depend on:

```text
SpecialistStatus
+
resource ownership
+
resource participation
+
business state
```

Examples:

- ACTIVE CLIENT authentication does not imply ownership of every Reservation;
- ACTIVE SPECIALIST authentication does not imply professional eligibility;
- APPROVED specialist eligibility does not imply access to another specialist's resources.

---

# 8. Password Security

The target authentication implementation uses BCrypt for password verification.

Passwords must never be stored in plain text.

Persistence stores only a password hash.

Authentication compares the supplied raw password with the persisted hash through the configured password encoder.

Raw passwords must not be logged or persisted.

---

# 9. Token Expiration

JWT access tokens have a finite lifetime.

After expiration:

- the token is rejected;
- the client must authenticate again unless a separate renewal mechanism is introduced later.

Refresh-token infrastructure is not required for the initial MVP authentication design.

---

# 10. Logout

The target MVP uses stateless access-token authentication.

Ordinary logout therefore consists of removing the access token on the client side.

The backend does not maintain a server-side authenticated session that must be destroyed.

An already issued token remains cryptographically valid until expiration, but current account-state validation still prevents a BLOCKED User from using that token for protected operations.

Explicit token revocation may be introduced later if product or security requirements justify it.

---

# Authentication Rules

## AU-001 — Valid Credentials Required

Successful login requires valid credentials.

---

## AU-002 — Active User Required

Login requires:

```text
UserStatus.ACTIVE
```

`UserStatus.BLOCKED` prevents login.

---

## AU-003 — SpecialistStatus Does Not Control Login

For an ACTIVE User with role SPECIALIST, login is independent of:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

These states control specialist authorization and professional eligibility.

---

## AU-004 — Minimal JWT Claims

The MVP JWT contains:

```text
userId
role
expiration
```

Mutable account and specialist statuses are not used as persistent JWT authorization claims.

---

## AU-005 — Current Account State Required

Every protected request must enforce the current persisted `UserStatus`.

A previously issued token must not allow a User to bypass a later transition:

```text
ACTIVE → BLOCKED
```

---

## AU-006 — Authentication Does Not Replace Authorization

Successful authentication establishes caller identity.

Permission for an operation is evaluated separately through role, ownership, specialist eligibility, and domain state.

---
