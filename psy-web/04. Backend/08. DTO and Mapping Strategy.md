
# 08. Стратегия DTO и маппинга (DTO and Mapping Strategy)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**Статус:** DRAFT — архитектурные принципы определены, конкретные DTO проектируются вместе с API

---

# 1. Назначение документа

Документ определяет правила передачи данных между слоями и модулями backend PsyWeb.

DTO (Data Transfer Object) используются для отделения внешних API-контрактов от внутренней структуры доменной модели и хранения данных.

Основные задачи:

- предотвращение передачи JPA-сущностей через REST API;
- ограничение раскрываемых данных;
- независимость API от структуры PostgreSQL;
- разделение ответственности Controller, Service и Repository;
- обеспечение стабильных межмодульных контрактов;
- явное преобразование данных;
- корректная передача временных значений;
- сохранение исторической согласованности Reservation и Booking.

DTO не являются доменными сущностями и не должны заменять их бизнес-поведение.

---

# 2. Основной архитектурный принцип

**JPA-сущности не должны передаваться напрямую через публичный API.**

Взаимодействие с клиентским приложением осуществляется через Request DTO и Response DTO.

Концептуально:

```text
HTTP Request
    ↓
Request DTO
    ↓
Controller
    ↓
Application Service
    ↓
Domain / Repository
    ↓
Application Result
    ↓
Response DTO
    ↓
HTTP Response
```

При этом состав внутренних объектов зависит от конкретного сценария.

Не требуется создавать отдельный DTO для каждого промежуточного вызова внутри одного модуля.

---

# 3. Категории DTO

В PsyWeb используются три основные категории:

1. Request DTO.
2. Response DTO.
3. Internal DTO / межмодульные контракты.

## 3.1. Request DTO

Request DTO представляет данные, поступающие от клиентского приложения.

Примеры целевых контрактов:

- LoginRequest;
- CreateReservationRequest;
- ConfirmReservationRequest;
- CreateServiceOfferingRequest;
- UpdateDateScheduleRequest;
- CreateReviewRequest;
- UpdateReviewRequest;
- SubmitSessionOutcomeReportRequest.

Названия предварительные и уточняются при проектировании API.

Характеристики:

- содержат пользовательский ввод;
- проверяются на уровне HTTP;
- не содержат бизнес-логики;
- не предоставляют прямой доступ к внутренним JPA-сущностям.

## 3.2. Response DTO

Response DTO представляет данные, возвращаемые клиентскому приложению.

Примеры:

- UserResponse;
- SpecialistProfileResponse;
- ServiceOfferingResponse;
- AvailableStartResponse;
- ReservationResponse;
- BookingResponse;
- ReviewResponse;
- SessionOutcomeResponse.

Характеристики:

- безопасны для внешнего представления;
- не содержат управляемых JPA-объектов;
- имеют явно определённый набор полей;
- могут объединять сведения из нескольких модулей;
- предпочтительно являются immutable.

## 3.3. Internal DTO

Internal DTO используются для передачи данных между модулями или прикладными компонентами.

Примеры концептуальных контрактов:

- ServiceOfferingSnapshotData;
- SpecialistBookingEligibilityData;
- EffectiveScheduleData;
- OccupiedIntervalData;
- VerifiedConsultationData.

Эти названия не означают обязательное создание соответствующих Java-классов.

Характеристики:

- не являются внешними API-контрактами;
- не раскрывают изменяемые JPA-сущности;
- передают только необходимые сведения;
- имеют определённого владельца;
- сохраняют независимость модульных границ.

---

# 4. Разделение слоёв

## 4.1. Controller

Controller отвечает за:

- приём HTTP-запроса;
- десериализацию Request DTO;
- запуск технической валидации;
- получение аутентифицированной идентичности;
- вызов прикладного сервиса;
- формирование HTTP-ответа.

Controller не должен:

- обращаться непосредственно к Repository для выполнения бизнес-операции;
- изменять состояния Reservation или Booking;
- рассчитывать доступность консультаций;
- управлять транзакционными блокировками;
- создавать JPA-сущности;
- выполнять доменную бизнес-валидацию.

## 4.2. Application Service

Application Service:

- принимает входные данные прикладного сценария;
- определяет транзакционную границу;
- вызывает необходимые доменные контракты;
- выполняет бизнес-операцию;
- формирует результат для вызывающего слоя.

Результатом может быть:

- специализированный DTO;
- immutable application result;
- value object;
- другой явно согласованный тип.

## 4.3. Repository

Repository работает с моделью хранения соответствующего модуля.

Он может возвращать:

- JPA-сущности;
- projections;
- результаты специализированных запросов.

Repository не должен формировать публичный REST-контракт.

## 4.4. Domain

Domain содержит:

- сущности;
- value objects;
- правила;
- инварианты;
- переходы состояний.

Domain не должен зависеть от HTTP Request DTO или Response DTO.

# 5. Стратегия маппинга

## 5.1. Основной подход

Для PsyWeb используется ручной маппинг.

Преобразование выполняется явно.

## 5.2. Где выполняется маппинг

Маппинг может находиться:

- в выделенном Mapper;
- в прикладном сервисе для простого внутреннего преобразования;
- на границе Controller при преобразовании готового application result в Response DTO.

Предпочтительно выделять Mapper, если преобразование становится достаточно сложным или переиспользуемым.

## 5.3. Ограничение Controller

Controller может вызывать Mapper, но не должен самостоятельно содержать сложные преобразования доменных сущностей и бизнес-правила.

## 5.4. Примеры

Возможные компоненты:

- ReservationMapper;
- BookingMapper;
- SpecialistProfileMapper;
- ReviewMapper.

Не следует создавать Mapper без фактической потребности.

## 5.5. Преимущества ручного маппинга

- прозрачность преобразований;
- предсказуемое поведение;
- удобство отладки;
- контроль раскрываемых полей;
- отсутствие скрытых правил генерации;
- возможность учитывать особенности исторических snapshots.

## 5.6. MapStruct

MapStruct может быть добавлен позднее.

Он полезен для сокращения однотипного кода преобразования.

Но его использование не является обязательным требованием MVP.

---

# 6. Правила преобразования

## 6.1. Entity → DTO

Преобразование должно явно определять, какие поля разрешено раскрывать.

## 6.2. DTO → Entity

Request DTO не должен автоматически превращаться в полностью управляемую JPA-сущность с заполненными пользовательским вводом внутренними полями.

Создание и изменение сущности выполняются через разрешённую доменную операцию.

## 6.3. Частичные обновления

При обновлении необходимо изменять только поля, которые разрешены конкретным бизнес-сценарием.

Например, клиент при редактировании Review может изменить rating и comment, но не clientId или eligibilityBookingId.

## 6.4. Идентификаторы

Идентификаторы из запроса используются для поиска ресурсов.

Они не доказывают принадлежность ресурса пользователю.

## 6.5. Защита от mass assignment

Клиентское приложение не должно иметь возможность произвольно устанавливать:

- ReservationStatus;
- BookingStatus;
- административные статусы;
- cancellationInitiator;
- внутренние временные поля;
- результаты SessionOutcome.

Такие значения определяются соответствующими бизнес-операциями.

---

# 7. Валидация Request DTO

## 7.1. Bean Validation

Для проверки входных данных могут использоваться:

- @NotNull;
- @NotBlank;
- @Size;
- @Min;
- @Max;
- @Email;
- другие стандартные ограничения.

## 7.2. Техническая валидация

На уровне DTO проверяются:

- обязательность полей;
- корректность формата;
- ограничения длины;
- простые числовые диапазоны.

## 7.3. Доменная валидация

Предметные правила выполняются в соответствующих сервисах.

Примеры:

- попадание консультации в рабочее окно;
- minimumBookingNotice;
- bookingHorizonDays;
- Reservation TTL;
- конфликт ScheduleOccupancy;
- допустимый переход BookingStatus;
- право на создание Review.

## 7.4. Почему этого недостаточно на уровне DTO

DTO может содержать технически корректное время консультации, которое уже занято другим клиентом.

Bean Validation не может гарантировать, что бизнес-состояние останется неизменным до сохранения Reservation.

## 7.5. Использование @Future

Аннотация @Future может быть дополнительной технической проверкой.

Однако она не заменяет бизнес-проверку актуального времени, выполняемую в критической транзакции.

Для операций с конкурентными блокировками важно получить свежее время после их захвата.

## 7.6. Ошибки

Ошибки DTO Validation обрабатываются на HTTP-границе.

Доменные исключения используют существующую иерархию DomainException.

# 8. DTO для ServiceOffering

## 8.1. Входная модель

При создании или изменении услуги специалист передаёт разрешённые поля.

Например:

- title;
- description;
- durationMinutes;
- breakDurationMinutes;
- price;
- currency.

## 8.2. Внутренние поля

Следующие сведения не должны произвольно определяться клиентом:

- идентификатор владельца;
- служебные timestamps;
- внутренние ограничения доступа.

## 8.3. Выходная модель

ServiceOfferingResponse может содержать сведения, необходимые для выбора услуги.

## 8.4. Активность

Включение и отключение услуги выполняется через отдельное разрешённое бизнес-действие.

Не следует допускать произвольную модификацию внутренних полей путём автоматического маппинга всего JSON в Entity.

---

# 9. DTO для Availability

## 9.1. Предварительный расчёт

Клиент выбирает ServiceOffering и диапазон дат.

AvailabilityService возвращает доступные начала консультаций.

## 9.2. Отсутствие AvailabilitySlot

В новой модели отсутствуют:

- CreateSlotRequest;
- SlotResponse;
- SlotStatus.

Эти контракты относятся к старой архитектуре.

## 9.3. Целевой ответ

AvailableStartResponse может содержать:

- serviceOfferingId;
- sessionStart;
- локальное представление времени;
- ZoneId специалиста.

Точный набор полей определяется API-контрактом.

## 9.4. Предварительный характер

Ответ AvailabilityService не является Reservation.

Он не создаёт Occupancy и не гарантирует сохранение доступности.

## 9.5. Повторная проверка

При создании Reservation выбранное время проверяется заново.

---

# 10. DTO для Reservation

## 10.1. Создание

Концептуальный CreateReservationRequest содержит:

- serviceOfferingId;
- sessionStart.

clientId определяется через SecurityContext.

## 10.2. Необходимые проверки

Приложение проверяет:

- роль и состояние клиента;
- ServiceOffering;
- эффективный допуск специалиста;
- расписание;
- временные ограничения;
- Occupancy.

## 10.3. Создание Entity

Reservation создаётся прикладным сценарием после успешной проверки бизнес-предусловий.

## 10.4. Исторический snapshot

При создании Reservation сохраняются согласованные условия услуги.

Snapshot не должен строиться на основании произвольных данных Request DTO.

Он формируется из проверенного состояния ServiceOffering и соответствующих политик.

## 10.5. Ответ

ReservationResponse может содержать:

- reservationId;
- status;
- sessionStart;
- sessionEnd;
- expiresAt;
- сведения об услуге;
- согласованную цену и валюту.

## 10.6. Подтверждение

ConfirmReservationRequest, если он требуется выбранным API-дизайном, не должен содержать произвольный BookingStatus.

Подтверждение создаёт Booking согласно бизнес-правилам.

---

# 11. DTO для Booking

## 11.1. Создание

Booking не создаётся непосредственно из произвольного CreateBookingRequest.

Он возникает после подтверждения ACTIVE Reservation.

## 11.2. Исторические условия

BookingResponse должен использовать условия сохранённой Reservation.

## 11.3. Запрет обращения к текущей услуге

Если специалист изменил ServiceOffering после создания Reservation, ответ об исторической Booking не должен подменять согласованные условия новыми.

## 11.4. Возможные поля

BookingResponse может содержать:

- bookingId;
- reservationId;
- clientId;
- specialistId;
- status;
- sessionStart;
- sessionEnd;
- исторические сведения об услуге;
- историческую стоимость;
- cancellation metadata при наличии прав на просмотр.

## 11.5. Отмена

Запрос на отмену не должен позволять клиенту самостоятельно выбирать cancellationInitiator.

Инициатор определяется по доверенному контексту выполнения операции.

## 11.6. Поздняя отмена

Поздняя отмена определяется из:

- cancelledAt;
- sessionStart;
- clientCancellationNoticeSnapshot.

Она не требует отдельного BookingStatus.

---

# 12. DTO для Schedule

## 12.1. Назначение

Schedule API предоставляет специалисту операции управления рабочим графиком.

## 12.2. Основные объекты

Контракты могут отражать:

- SpecialistScheduleSettings;
- WeeklyScheduleVersion;
- WeeklyWorkingInterval;
- DateSchedule;
- DateScheduleInterval.

## 12.3. Режимы

DTO должен явно различать:

- REGULAR;
- FLOATING.

## 12.4. Локальные даты и время

Рабочее расписание передаётся через локальные значения:

- LocalDate;
- LocalTime.

## 12.5. ZoneId

Интерпретация рабочего расписания зависит от текущего ZoneId специалиста.

## 12.6. Пустой OVERRIDE

DTO должен позволять отличить:

- отсутствие DateSchedule OVERRIDE;
- существующий OVERRIDE без рабочих интервалов.

Это разные бизнес-ситуации.

## 12.7. Исторические обязательства

Обычное изменение расписания не должно через маппинг менять существующие Reservation и Booking.

## 12.8. Предупреждения

Если изменение затрагивает существующие обязательства, результат операции может содержать сведения для предупреждения пользователя.

Точный контракт предупреждения и подтверждения изменения определяется отдельно.

---

# 13. DTO для SessionOutcome

## 13.1. Назначение

SessionOutcome отдельно определяет результат проведения консультации.

## 13.2. Отчёт участника

Запрос может содержать:

- bookingId;
- утверждение OCCURRED или DID_NOT_OCCUR;
- структурированную причину при DID_NOT_OCCUR;
- дополнительные сведения в разрешённых случаях.

## 13.3. Идентичность автора

Участник определяется через SecurityContext.

Нельзя позволять одному пользователю передавать произвольный participantId и выдавать себя за другую сторону.

## 13.4. Результат

Response DTO может содержать:

- статус обработки Outcome;
- результат, если он разрешён;
- наличие спора;
- временные сведения.

## 13.5. Административное решение

Решение по спору выполняется через отдельный административный контракт.

## 13.6. Разделение

DTO не должен самостоятельно определять, какой результат консультации считать окончательным.

Эта логика принадлежит Outcome.

---

# 14. DTO для Review

## 14.1. Создание

CreateReviewRequest содержит:

- specialistId;
- rating;
- comment.

## 14.2. Eligibility

Право на первоначальное создание Review проверяется через подтверждённый SessionOutcome.

## 14.3. Один Review на пару

Уникальность определяется:

`(clientId, specialistId)`

## 14.4. Редактирование

UpdateReviewRequest позволяет менять:

- rating;
- comment.

## 14.5. Неизменяемые поля

Клиент не может изменять:

- clientId;
- specialistId;
- eligibilityBookingId;
- createdAt.

## 14.6. Выходная модель

ReviewResponse может содержать:

- reviewId;
- specialistId;
- rating;
- comment;
- createdAt;
- updatedAt;
- безопасное представление сведений об авторе.

Состав публичной информации об авторе определяется отдельно.

---

# 15. Временные значения

## 15.1. Instant

Абсолютные моменты времени используются для:

- sessionStart;
- sessionEnd;
- occupiedUntil;
- expiresAt;
- cancelledAt;
- createdAt.

## 15.2. API-представление

Для абсолютного времени должен использоваться однозначный формат.

Предпочтительно ISO 8601 с явным offset либо UTC-представление Instant.

## 15.3. LocalDate

LocalDate используется для календарных дат специалиста.

## 15.4. LocalTime

LocalTime используется для локальных границ рабочего расписания.

## 15.5. ZoneId

ZoneId необходим для интерпретации локального расписания специалиста.

Например:

`Europe/Amsterdam`

## 15.6. Разграничение

Локальное время рабочего окна не равнозначно абсолютному моменту консультации.

DTO должны сохранять это различие.

## 15.7. DST

DTO может передавать технически корректную локальную дату и время, которые являются неоднозначными или несуществующими в конкретном ZoneId.

Такие ситуации проверяются соответствующей бизнес-политикой.

## 15.8. Исторические времена

Изменение ZoneId специалиста не должно приводить к пересчёту сохранённых абсолютных времён Reservation и Booking.

---

# 16. Агрегация данных

## 16.1. Назначение

Response DTO может объединять информацию из нескольких модулей.

Например, BookingResponse может содержать:

- сведения о консультации;
- исторические условия услуги;
- безопасные сведения о специалисте;
- состояние Booking.

## 16.2. Application Service

Получение данных из нескольких модулей координируется прикладным сервисом или специализированным query-компонентом.

## 16.3. Repository

Repository не должен самостоятельно формировать публичный JSON-контракт.

## 16.4. Производительность

При агрегации необходимо учитывать:

- количество SQL-запросов;
- N+1 проблему;
- границы транзакции;
- объём передаваемых данных.

## 16.5. Источник истины

Исторические поля берутся из snapshot.

Актуальные профильные сведения могут браться из соответствующего модуля, если это явно предусмотрено контрактом.

---

# 17. Безопасность DTO

## 17.1. Чувствительные данные

Внешние DTO не должны раскрывать:

- passwordHash;
- JWT signing secrets;
- внутренние токены;
- конфиденциальные технические данные;
- неразрешённые административные сведения;
- сведения о чужих консультациях.

## 17.2. Внутренние статусы

Не все внутренние статусы запрещены для API.

Например, ReservationStatus может быть необходим клиенту.

Однако раскрываемые состояния и поля должны определяться явно.

## 17.3. Принадлежность

Наличие поля clientId в DTO не предоставляет клиенту право управлять соответствующим объектом.

## 17.4. Mass assignment

Автоматическое копирование произвольных полей Request DTO в Entity запрещено для состояний и служебных данных, управляемых системой.

## 17.5. Агрегация

Объединение данных нескольких модулей не должно обходить их правила доступа.

---

# 18. Internal DTO и модульные границы

## 18.1. Назначение

Межмодульные контракты позволяют одному модулю получать необходимые сведения другого без прямой зависимости от его persistence-модели.

## 18.2. Владелец

Каждый контракт должен иметь определённого владельца.

## 18.3. Иммутабельность

Для передачи данных предпочтительны immutable объекты.

## 18.4. Ограничение

Не следует передавать изменяемые JPA-сущности через публичную межмодульную границу.

## 18.5. Общий модуль

Внутренние DTO не нужно автоматически переносить в Common.

Например, результат VerifiedOutcomeQuery принадлежит контракту Outcome, а не Common.

## 18.6. Разделение операций

Query-контракты предоставляют данные.

Command-контракты выполняют разрешённые изменения.

Не следует использовать DTO как способ обойти владельца бизнес-операции.

---

# 19. Иммутабельность

## 19.1. Предпочтительная модель

Для простых DTO в Java 21 могут использоваться record.

## 19.2. Преимущества

- явный состав полей;
- отсутствие лишних setters;
- удобство тестирования;
- предсказуемое представление данных.

## 19.3. Ограничения

record не является обязательным решением для всех DTO.

Конкретный тип выбирается с учётом сериализации, Bean Validation и требований API.

## 19.4. Вложенные объекты

Необходимо учитывать, что record не гарантирует глубокую иммутабельность изменяемых вложенных объектов.

Для коллекций предпочтительно использовать неизменяемые представления.

---

# 20. Обработка ошибок

## 20.1. Техническая валидация

Ошибки десериализации и Bean Validation обрабатываются на HTTP-границе.

## 20.2. Доменные ошибки

Бизнес-ошибки представлены существующей иерархией DomainException.

## 20.3. ErrorResponse

Предлагаемый универсальный ErrorResponse может содержать:

- code;
- message;
- timestamp;
- path;
- details.

Окончательный набор полей определяется Exception Handling Strategy и API-контрактом.

## 20.4. Разделение

DTO не должен содержать обработку исключений как бизнес-поведение.

Mapper также не должен самостоятельно выбирать предметную категорию ошибки.

---

# 21. Производительность

## 21.1. Минимально необходимые поля

Response DTO должен содержать только данные, необходимые конкретному сценарию.

## 21.2. Пагинация

Для коллекций предусматривается пагинация:

- Review;
- Notification;
- Booking history;
- другие большие списки.

## 21.3. Избыточная загрузка

Нельзя автоматически загружать все связанные JPA-сущности только ради формирования одного Response DTO.

## 21.4. Projections

Для сложных запросов чтения могут использоваться JPA projections.

Они не должны подменять доменную модель в изменяющих операциях.

## 21.5. MapStruct

Переход на MapStruct возможен при наличии повторяющегося однотипного маппинга.

Он не является самостоятельной целью архитектуры.

---

# 22. Тестирование

## 22.1. Request DTO

Проверяются:

- обязательные поля;
- числовые диапазоны;
- корректность форматов;
- ограничения длины.

## 22.2. Response DTO

Проверяются:

- состав разрешённых данных;
- отсутствие чувствительных полей;
- корректное представление статусов;
- корректность временных значений.

## 22.3. Mapping

Проверяются:

- корректность преобразования;
- отсутствие изменения исходных данных;
- обработка NULL;
- исторические snapshots;
- сохранение идентификаторов.

## 22.4. Reservation и Booking

Проверяется, что исторические Response DTO не меняются вследствие последующего изменения ServiceOffering.

## 22.5. Schedule

Проверяется различие между:

- отсутствующим OVERRIDE;
- пустым OVERRIDE.

## 22.6. Outcome

Проверяется, что API не раскрывает результат как окончательно успешный до разрешения SessionOutcome.

## 22.7. Review

Проверяется, что UpdateReviewRequest не может изменить автора, специалиста или eligibilityBookingId.

## 22.8. Безопасность

Проверяется невозможность передачи внутренних служебных полей через массовое присваивание.

---

# 23. Архитектурные правила

1. JPA-сущности не возвращаются напрямую через REST API.
2. Request DTO содержит пользовательский ввод, а не предметную бизнес-логику.
3. Response DTO явно определяет разрешённые поля.
4. Controller не выполняет бизнес-транзакции.
5. Repository не формирует публичный API-контракт.
6. Маппинг выполняется явно.
7. Ручной маппинг является основным подходом.
8. MapStruct остаётся необязательной будущей оптимизацией.
9. DTO не определяет переходы ReservationStatus и BookingStatus.
10. Нельзя доверять идентификаторам инициатора из Request DTO.
11. Нельзя автоматически копировать все поля запроса в JPA Entity.
12. Межмодульные контракты не должны передавать изменяемые JPA-сущности.
13. Исторические условия Booking берутся из Reservation snapshot.
14. Абсолютное и локальное время не смешиваются.
15. Предварительная Availability не представляется как сохранённый слот.
16. DTO не создаёт ScheduleOccupancy.
17. Право на Review определяется доменными правилами, а не наличием поля bookingId.
18. API-модели не должны обходить модульные границы.
19. Общие DTO добавляются в Common только при действительной универсальности.
20. Конкретные DTO проектируются по мере реализации соответствующих API.

---

# 24. Открытые вопросы

## 24.1. API-контракты

Требуется определить точный состав Request DTO и Response DTO для каждого endpoint.

## 24.2. Формат времени

Необходимо утвердить единое представление Instant и правила передачи ZoneId.

## 24.3. Частичное обновление

Нужно определить правила PATCH/PUT и различие между отсутствующим полем и явно переданным NULL.

## 24.4. Пагинация

Необходимо согласовать универсальный контракт постраничных ответов.

## 24.5. ErrorResponse

Нужно утвердить окончательную структуру ответа об ошибке.

## 24.6. Предупреждения Schedule

Требуется определить формат предупреждений об изменении расписания, затрагивающем существующие Reservation и Booking.

## 24.7. MapStruct

Возможность перехода на MapStruct рассматривается после накопления достаточного количества однотипного маппинга.

---

# 25. Итог

Стратегия DTO и маппинга PsyWeb обеспечивает разделение внешнего API, прикладной логики и persistence-модели.

Основные принципы:

- JPA Entity не передаются напрямую через API;
- входные и выходные DTO проектируются отдельно;
- бизнес-правила остаются внутри соответствующих доменов;
- преобразования выполняются явно;
- межмодульные контракты не раскрывают изменяемые persistence-сущности;
- исторические Reservation и Booking используют сохранённые snapshots;
- локальное и абсолютное время передаются без неоднозначности;
- API не предоставляет доступ к служебным состояниям и полям;
- конкретные DTO появляются вместе с соответствующими пользовательскими сценариями.

**Статус: DRAFT — основные архитектурные правила определены, точные API-контракты и DTO требуют дальнейшего проектирования.**
