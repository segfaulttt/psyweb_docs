## Overview

This section defines how data is transferred between layers of the backend system and how domain entities are separated from external API contracts.

The system enforces strict separation between persistence models (JPA entities) and API models (DTOs) to ensure maintainability, security, and flexibility of the architecture.

---

# Core Principle

## Entities must never be exposed through API

The system strictly prohibits returning JPA entities directly from controllers.

All external communication must use DTOs.

---

# DTO Categories

The system defines three main DTO types:

---

## 1. Request DTOs

Used for incoming client data.

Examples:

- CreateBookingRequest
- LoginRequest
- CreateSlotRequest
- CreateReviewRequest

Characteristics:

- validated using Bean Validation
- represent user input only
- contain no business logic

---

## 2. Response DTOs

Used for API responses.

Examples:

- BookingResponse
- UserResponse
- SpecialistProfileResponse
- SlotResponse

Characteristics:

- immutable structure
- safe for external exposure
- may aggregate multiple entities

---

## 3. Internal DTOs (Service-level contracts)

Used for communication between modules (optional but recommended).

Examples:

- BookingContext
- SlotAvailabilityInfo

Characteristics:

- not exposed externally
- used for internal decoupling

---

# Layer Separation Rule

## Controller layer

- accepts Request DTOs
- returns Response DTOs

## Service layer

- converts Request DTOs → domain logic
- returns Response DTOs or domain models internally

## Repository layer

- only works with JPA entities

---

# Mapping Strategy

The system uses manual mapping as the primary strategy.

---

## Option 1. Manual Mapping (Recommended)

Mapping is done explicitly in service or dedicated mapper classes.

Example:

- BookingMapper
- UserMapper

### Advantages:

- full control
- no hidden behavior
- easier debugging
- better alignment with domain logic

---

## Option 2. MapStruct (Optional future improvement)

Can be introduced later for:

- reducing boilerplate
- compile-time safety

However, it is not required at the current stage.

---

# Mapping Rules

## 1. Entity → DTO conversion happens only in service layer

Controllers must never perform mapping.

---

## 2. DTO → Entity conversion must be validated

All incoming data must pass validation before entity creation.

---

## 3. No bidirectional mapping in controllers

Controllers remain unaware of entity structure.

---

## 4. Sensitive data must never be included in DTOs

Examples:

- password_hash
- internal status flags
- system metadata

---

# Example Mapping Flow (Booking)

```
CreateBookingRequest→ BookingService→ Slot validation→ Booking entity creation→ BookingRepository.save()→ BookingResponse returned
```

---

# Aggregation Strategy

Response DTOs may aggregate data from multiple entities.

Example:  
BookingResponse may include:

- service details
- specialist info
- slot time
- booking status

This is handled in service layer, not in repository.

---

# Validation Strategy

Request DTOs use Bean Validation:

- @NotNull
- @NotBlank
- @Size
- @Future (for timestamps)

Validation errors are handled globally by exception handler.

---

# Key Design Rules

## 1. Strict separation of layers

DTOs isolate API from domain model.

---

## 2. Entities are internal only

They belong exclusively to persistence layer.

---

## 3. Mapping is explicit

No hidden or automatic transformation logic in controllers.

---

## 4. Service layer is the mapping boundary

All conversions happen here or in dedicated mapper classes.

---

# Summary

The DTO and mapping strategy ensures:

- clean separation between API and database models
- controlled data exposure
- maintainable and testable architecture
- flexibility for future evolution (e.g., MapStruct integration)
