
# 15. Проектирование модуля Common

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — целевая архитектура общего модуля

---

# 1. Назначение документа

Документ определяет назначение, структуру и архитектурные ограничения модуля Common в PsyWeb.

Common предоставляет небольшую совокупность переиспользуемых компонентов, которые не принадлежат конкретному бизнес-домену.

Основные задачи:

- предотвращение дублирования действительно общей инфраструктуры;
- обеспечение согласованной обработки ошибок;
- предоставление универсальных технических типов;
- поддержка единых соглашений между модулями;
- снижение повторения вспомогательного кода;
- сохранение архитектурных границ модульного монолита.

Common не является самостоятельным бизнес-доменом.

Он не управляет Reservation, Booking, Schedule, Review или другими предметными сущностями.

---

# 2. Основной архитектурный принцип

Common должен:

- содержать только переиспользуемые компоненты, независимые от конкретного домена;
- не зависеть от бизнес-модулей;
- оставаться небольшим и стабильным;
- предоставлять понятные универсальные контракты;
- не содержать скрытых бизнес-правил;
- не становиться посредником для обхода модульных границ.

Другие модули могут зависеть от Common.

Однако возможность импортировать Common из любого модуля не означает, что любую совместно используемую логику следует помещать именно туда.

**Основное правило: принадлежность компонента определяется его ответственностью, а не количеством мест использования.**

---

# 3. Место Common в архитектуре

Концептуальная структура:

```text
                    Application
                         |
          +--------------+--------------+
          |              |              |
       Booking        Schedule        Review
          |              |              |
          +--------------+--------------+
                         |
                       Common
```

Стрелки концептуально обозначают возможность зависимости бизнес-модулей от Common.

Обратные зависимости запрещены.

Common не должен знать о существовании конкретных бизнес-модулей.

## 3.1. Разрешённые зависимости

Common может использовать:

- стандартную библиотеку Java;
- небольшие универсальные библиотеки;
- необходимые инфраструктурные зависимости при наличии обоснования.

## 3.2. Запрещённые зависимости

Common не зависит от:

- Booking;
- Schedule;
- Availability;
- Service;
- Specialist;
- User;
- Auth;
- Review;
- Outcome;
- Notification;
- Admin.

## 3.3. Направление взаимодействия

Common предоставляет общие инструменты.

Он не вызывает бизнес-сервисы и не координирует предметные операции.

---

# 4. Состав Common

В Common допускаются следующие категории компонентов:

1. Базовые классы исключений.
2. Универсальные технические типы.
3. Небольшие вспомогательные функции.
4. Общие технические константы.
5. Ограниченный набор универсальных DTO.
6. Общие механизмы, действительно независимые от бизнес-доменов.

Каждый новый компонент должен проходить проверку необходимости размещения в Common.

---

# 5. Общие enum

## 5.1. Принцип

Enum может находиться в Common только тогда, когда его значения и смысл не принадлежат отдельному бизнес-домену.

Использование enum несколькими модулями само по себе не является достаточным основанием.

## 5.2. Доменные enum

Следующие перечисления не должны автоматически размещаться в Common:

| Enum | Предпочтительный владелец |
|---|---|
| UserRole | User / Security contract |
| UserStatus | User |
| SpecialistApprovalStatus | Specialist |
| ReservationStatus | Booking |
| BookingStatus | Booking |
| ScheduleMode | Schedule |
| DateSchedulePurpose | Schedule |
| SessionOutcomeStatus | Outcome |
| NotificationType | Notification |
| CancellationInitiator | Booking, если используется только для отмен записей |

Точное расположение `UserRole` определяется архитектурой User и Security.

Если нескольким модулям необходим UserRole, предпочтительно предоставить стабильный контракт владельца, а не перемещать все статусы пользователей в Common.

## 5.3. Устаревшие enum

Следующие перечисления больше не соответствуют целевой модели:

- SlotStatus;
- FREE / BOOKED / BLOCKED как статусы AvailabilitySlot.

PsyWeb больше не использует хранимую сущность AvailabilitySlot.

Поэтому её статусы не должны сохраняться в Common ради обратной совместимости с устаревшей архитектурой.

## 5.4. ReviewRating

В текущей модели Review использует целочисленную оценку от 1 до 5.

Диапазон принадлежит домену Review.

Не требуется выделять общесистемный ReviewRating в Common.

При необходимости Review может использовать собственный value object или доменную проверку.

## 5.5. Правила для enum

Enum:

- должен иметь определённого владельца;
- не должен содержать зависимостей от внешних сервисов;
- не должен использоваться как средство переноса чужой бизнес-логики;
- должен иметь согласованное представление при сохранении в PostgreSQL.

Доменные переходы состояний реализуются в соответствующем модуле, а не в Common.

# 6. Базовая иерархия исключений

## 6.1. Назначение

Common предоставляет базовые типы исключений для согласованной обработки ошибок.

Цель — единая техническая структура, а не централизованное хранение всех бизнес-исключений платформы.

## 6.2. Предлагаемая иерархия

Концептуально:

```text
RuntimeException
    |
    └── DomainException
            |
            ├── NotFoundException
            |
            ├── ValidationException
            |
            ├── ConflictException
            |
            └── OperationNotAllowedException
```

Это концептуальная схема, не обязательное требование создать отдельный Java-класс для каждой категории.

Окончательная иерархия определяется документом Exception Handling Strategy и существующей реализацией.

## 6.3. Базовый DomainException

Базовое исключение может содержать:

- технически стабильный код ошибки;
- описание;
- причину;
- необходимые безопасные метаданные.

Оно не должно содержать сведений о конкретной Reservation или Booking как обязательную часть своего контракта.

## 6.4. Доменные исключения

Конкретные исключения принадлежат соответствующим модулям.

Примеры:

Booking:

- ReservationExpiredException;
- BookingConflictException;
- InvalidBookingStateException.

Schedule:

- ScheduleConflictException;
- InvalidWorkingIntervalException.

Review:

- ReviewAlreadyExistsException;
- VerifiedConsultationRequiredException.

Admin:

- InvalidModerationActionException.

## 6.5. Запрет централизованного хранения

Не следует размещать все исключения проекта в одном пакете Common.

Это размывает границы доменов и создаёт ненужную связанность.

## 6.6. Совместимость

Если в проекте уже существует утверждённая иерархия исключений, новый дизайн должен согласовываться с ней.

Нельзя параллельно создавать другую несовместимую иерархию только ради этого документа.

# 7. Обработка ошибок

## 7.1. Разделение ответственности

Common предоставляет универсальные типы и контракты ошибок.

HTTP-слой отвечает за преобразование исключений в HTTP-ответы.

## 7.2. Global Exception Handler

Централизованный обработчик должен обеспечивать:

- согласованный формат ошибки;
- корректный HTTP status;
- безопасное описание;
- необходимые метаданные;
- отсутствие раскрытия внутренней инфраструктуры.

## 7.3. Предметные ошибки

Конкретное соответствие доменного исключения и HTTP status определяется Exception Handling Strategy.

Common не должен самостоятельно решать, что истечение Reservation означает определённый HTTP status.

## 7.4. Инфраструктурные ошибки

Технические исключения PostgreSQL и Hibernate преобразуются на соответствующем уровне.

Например, нарушение GiST exclusion constraint может означать конфликт занятого времени.

Но такая интерпретация принадлежит Booking, а не Common.

## 7.5. Безопасность

В ответах API нельзя раскрывать:

- SQL-запросы;
- stack trace;
- внутренние имена таблиц;
- пароли;
- токены;
- чувствительные сведения пользователей.

# 8. Универсальные DTO

## 8.1. Назначение

Common может содержать DTO, которые действительно используются независимо от конкретной предметной области.

## 8.2. ErrorResponse

Возможный общий контракт:

```text
ErrorResponse:
    code
    message
    timestamp
    path?
    details?
```

Точный набор полей должен соответствовать Exception Handling Strategy.

## 8.3. PaginatedResponse

При необходимости может использоваться универсальная модель:

```text
PaginatedResponse<T>:
    items
    page
    size
    totalElements
    totalPages
```

## 8.4. ApiResponse

Общая обёртка ApiResponse<T> не является обязательной.

Если Spring REST API использует обычные HTTP-статусы и отдельные DTO, дополнительная обёртка может быть избыточной.

## 8.5. Ограничения

Общие DTO:

- не должны ссылаться на JPA-сущности;
- не должны включать бизнес-правила;
- не должны требовать изменения при добавлении нового доменного статуса;
- не должны заменять специализированные DTO модулей.

## 8.6. Доменные DTO

Следующие DTO не принадлежат Common:

- ReservationResponse;
- BookingResponse;
- AvailableStartResponse;
- ServiceOfferingResponse;
- ReviewResponse;
- SessionOutcomeResponse.

Их владельцами являются соответствующие модули или API-слои.

---

# 9. Вспомогательные классы

## 9.1. Основной принцип

В Common допускаются небольшие stateless utilities.

Они должны быть:

- независимыми от бизнес-моделей;
- простыми для тестирования;
- предсказуемыми;
- без скрытых побочных эффектов.

## 9.2. DateTime utilities

Возможные технические операции:

- форматирование временных значений;
- преобразование универсальных временных представлений;
- работа с общими форматами дат;
- проверки технической корректности временных данных.

## 9.3. Разграничение с Availability

Следующие правила не относятся к Common:

- проверка 15-минутной сетки консультаций;
- расчёт bookingDeadline;
- вычисление occupiedUntil;
- проверка попадания консультации в рабочее окно;
- проверка доступности по ScheduleOccupancy;
- определение допустимого начала консультации при DST.

Они относятся к AvailabilityPolicy и связанным доменным контрактам.

## 9.4. String utilities

Допускаются универсальные операции со строками, если стандартных средств Java недостаточно.

Не следует создавать вспомогательные классы, просто дублирующие методы стандартной библиотеки.

## 9.5. Validation utilities

Допускаются проверки, не имеющие предметной семантики.

Бизнес-валидация остаётся у соответствующего домена.

## 9.6. ID generation

Общие генераторы идентификаторов добавляются только при необходимости.

При использовании PostgreSQL IDENTITY не требуется создавать отдельный универсальный генератор идентификаторов для всех сущностей.

# 10. Clock и работа со временем

## 10.1. Проблема

В PsyWeb множество операций зависит от текущего времени:

- TTL Reservation;
- minimumBookingNotice;
- clientCancellationNotice;
- booking horizon;
- начало консультации;
- 24-часовое окно SessionOutcome.

## 10.2. Общий Clock

Для получения текущего времени рекомендуется использовать внедряемый `java.time.Clock`.

Это упрощает:

- тестирование временных границ;
- воспроизводимость тестов;
- согласованность работы сервисов;
- исключение случайного использования системного времени напрямую.

## 10.3. Размещение

Универсальная техническая конфигурация Clock может находиться в общем инфраструктурном слое.

Если Common используется для такой конфигурации, она должна оставаться независимой от бизнес-доменов.

## 10.4. Бизнес-правила времени

Сам Clock не определяет:

- допустимость новой Reservation;
- дедлайн отмены Booking;
- окончание окна Outcome;
- горизонт записи.

Эти правила принадлежат доменам.

## 10.5. Время после блокировки

При операциях, зависящих от текущего момента, необходимо учитывать время ожидания PostgreSQL-блокировок.

Например, подтверждение Reservation должно проверять TTL после получения критической блокировки.

Это правило описывается в Transaction and Concurrency Model.

# 11. Временные типы

## 11.1. Instant

Абсолютные времена консультаций представлены через Instant.

В PostgreSQL используется TIMESTAMPTZ.

## 11.2. LocalDate

Используется для локальных календарных дат специалиста.

## 11.3. LocalTime

Используется для локальных рабочих интервалов.

## 11.4. ZoneId

Используется для интерпретации локального расписания.

## 11.5. Duration

Используется для описания временных промежутков, например TTL и уведомлений.

## 11.6. Разграничение

Common может предоставлять универсальную инфраструктуру работы с этими типами.

Но не должен определять предметные правила их применения к Booking или Schedule.

---

# 12. Константы

## 12.1. Общие константы

В Common могут размещаться технические константы, используемые независимо от предметных модулей.

Например:

- единые технические форматы;
- общие ограничения пагинации;
- универсальные коды технических ошибок.

## 12.2. Доменные константы

Следующие значения не следует автоматически переносить в Common:

- Reservation TTL;
- bookingGridMinutes;
- minimumBookingNotice;
- clientCancellationNotice;
- bookingHorizonDays;
- SessionOutcome reporting window;
- максимальный рейтинг Review.

Несмотря на использование несколькими сервисами, они имеют конкретных предметных владельцев.

## 12.3. Reservation TTL

TTL устанавливается платформой, но относится к жизненному циклу Reservation.

Его значение должно находиться в согласованной конфигурации Booking.

## 12.4. Сетка бронирования

Шаг 15 минут относится к правилам Availability.

## 12.5. Outcome window

24-часовое окно относится к Outcome.

## 12.6. Устаревшие константы

Константы, связанные с количеством AvailabilitySlot или их статусами, не используются в новой архитектуре.

Например:

- maxSlotsPerDay;
- SlotStatus defaults.

# 13. Работа с PostgreSQL

## 13.1. Граница ответственности

Common не должен владеть PostgreSQL-репозиториями бизнес-сущностей.

## 13.2. Транзакционная инфраструктура

Общие технические механизмы могут быть вынесены в инфраструктурный слой при необходимости.

Однако Common не должен самостоятельно определять транзакционные границы Booking, Schedule или Admin.

## 13.3. CalendarLockCoordinator

CalendarLockCoordinator использует PostgreSQL transaction-level advisory locks.

Несмотря на техническую реализацию, он выражает конкретный механизм календарной координации.

Его не следует автоматически размещать в Common.

Предпочтительно использовать специализированный инфраструктурный компонент календарной подсистемы.

## 13.4. Advisory-lock keys

Алгоритм формирования ключей календарных блокировок относится к протоколу Schedule/Booking concurrency.

Он не является универсальной строковой или числовой утилитой.

## 13.5. Exclusion constraints

GiST exclusion constraint для ScheduleOccupancy принадлежит модели Booking.

Common не должен содержать его предметную интерпретацию.

## 13.6. Репозитории

В Common не размещаются:

- ReservationRepository;
- BookingRepository;
- ScheduleRepository;
- ReviewRepository;
- другие доменные Repository.

# 14. Бизнес-политики

## 14.1. Общий принцип

Бизнес-политика остаётся внутри предметного домена или отдельного согласованного доменного компонента.

Количество потребителей политики не является основанием для её переноса в Common.

## 14.2. AvailabilityPolicy

Отвечает за:

- доступные начала консультаций;
- рабочие окна;
- временные ограничения;
- пересечение Occupancy;
- допустимость времени.

Это не компонент Common.

## 14.3. CancellationPolicy

Отвечает за:

- допустимость отмены;
- своевременность отмены;
- позднюю отмену;
- использование исторических условий.

Это не компонент Common.

## 14.4. SpecialistBookingEligibility

Правило эффективного допуска специалиста зависит от:

- User.status;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

Это предметное правило.

Оно не должно находиться в Common.

## 14.5. OutcomeResolutionPolicy

Правила разрешения результата консультации относятся к Outcome.

## 14.6. ReviewEligibilityPolicy

Право на отзыв относится к Review и интеграции с Outcome.

---

# 15. Общие контракты и межмодульные зависимости

## 15.1. Публичные доменные контракты

Если один модуль предоставляет данные другому, это не означает, что интерфейс должен находиться в Common.

Например:

- ServiceOfferingQuery;
- ScheduleQuery;
- OccupancyQuery;
- VerifiedOutcomeQuery;
- BookingObligationQuery.

Это контракты соответствующих доменных границ.

## 15.2. Dependency inversion

При необходимости интерфейсы располагаются так, чтобы зависимости реализаций оставались ациклическими.

## 15.3. Запрет Shared Domain

Нельзя создавать в Common универсальную модель, содержащую все поля:

- Reservation;
- Booking;
- Specialist;
- Schedule;
- Review.

Такой подход фактически уничтожил бы модульные границы.

## 15.4. DTO вместо JPA Entity

Для межмодульных контрактов предпочтительны:

- идентификаторы;
- immutable DTO;
- value objects;
- специализированные результаты запросов.

JPA-сущности не должны становиться общими объектами, доступными для изменения из любого модуля.

# 16. Dependency Rules

## 16.1. Common

Common не зависит от бизнес-модулей.

## 16.2. Бизнес-модули

Бизнес-модули могут использовать Common.

## 16.3. Запрет циклов

Common не должен участвовать в циклических зависимостях.

## 16.4. Отсутствие сервисной оркестрации

Common не должен вызывать несколько бизнес-сервисов для выполнения пользовательского сценария.

Эта ответственность принадлежит Application Service.

## 16.5. Проверка зависимостей

При необходимости можно использовать архитектурные тесты для контроля импортов и зависимостей пакетов.

---

# 17. Стабильность Common

## 17.1. Принцип

Common должен меняться относительно редко.

Изменения в общем модуле способны затронуть значительную часть приложения.

## 17.2. Минимальная поверхность API

Следует избегать большого количества публичных классов без подтверждённой необходимости.

## 17.3. Совместимость

Изменения базовых исключений и DTO должны учитывать существующих потребителей.

## 17.4. Отказ от преждевременных абстракций

Не требуется создавать универсальные механизмы на случай гипотетического будущего использования.

## 17.5. Локальное дублирование

Небольшое техническое дублирование между двумя модулями иногда предпочтительнее преждевременного введения сложной общей абстракции.

# 18. Тестирование Common

## 18.1. Исключения

Проверяются:

- создание базовых исключений;
- сохранение кода ошибки;
- корректная причина;
- безопасная структура метаданных.

## 18.2. DTO

Проверяется корректность универсальных контрактов, если они содержат поведение, требующее тестирования.

## 18.3. Utilities

Stateless helpers проверяются обычными unit tests.

## 18.4. Clock

Тесты подтверждают возможность использования фиксированного Clock.

## 18.5. Архитектурные тесты

Необходимо проверить:

- отсутствие зависимостей Common от бизнес-пакетов;
- отсутствие Repository бизнес-модулей в Common;
- отсутствие доменных state machine;
- соблюдение направлений зависимостей.

## 18.6. Ограничение

Common не должен содержать интеграционные тесты, проверяющие бизнес-поведение Reservation или Booking.

Такие тесты принадлежат соответствующим модулям.

# 19. Архитектурные запреты

1. Не размещать бизнес-правила в Common.
2. Не размещать ReservationStatus и BookingStatus в Common без специального архитектурного обоснования.
3. Не сохранять SlotStatus после отказа от AvailabilitySlot.
4. Не размещать ScheduleOccupancy в Common.
5. Не размещать AvailabilityPolicy в Common.
6. Не размещать CancellationPolicy в Common.
7. Не размещать SpecialistBookingEligibility в Common.
8. Не размещать OutcomeResolutionPolicy в Common.
9. Не размещать ReviewEligibilityPolicy в Common.
10. Не размещать Repository бизнес-модулей в Common.
11. Не размещать межмодульную оркестрацию в Common.
12. Не создавать универсальные DTO, содержащие поля конкретных доменных сущностей.
13. Не переносить все исключения проекта в один общий пакет.
14. Не дублировать возможности стандартной библиотеки Java без необходимости.
15. Не создавать технические абстракции без реальных потребителей.
16. Не использовать Common для обхода архитектурных границ.
17. Не превращать Common в источник истины для состояний других модулей.

# 20. Открытые вопросы

## 20.1. Иерархия исключений

Необходимо синхронизировать окончательные базовые типы с Exception Handling Strategy и существующим кодом.

## 20.2. Универсальные DTO

Требуется определить, необходимы ли:

- PaginatedResponse;
- ApiResponse;
- дополнительные технические контракты.

## 20.3. UserRole

Нужно окончательно определить расположение UserRole с учётом User и Security.

## 20.4. Clock

Необходимо выбрать конкретный пакет и конфигурацию предоставления Clock.

## 20.5. Инфраструктурные компоненты

Точное расположение CalendarLockCoordinator и связанных компонентов должно соответствовать Module Architecture и Service Layer Design.

## 20.6. Архитектурные тесты

Можно отдельно определить правила проверки границ модулей через ArchUnit или аналогичный инструмент.

---

# 21. Итог

Common в PsyWeb является небольшим общим модулем, предназначенным для переиспользуемых технических компонентов.

Он может содержать:

- базовые исключения;
- универсальные DTO;
- небольшие stateless utilities;
- общие технические типы;
- технические константы;
- инфраструктурные компоненты, не имеющие предметной ответственности.

При этом:

- доменные состояния остаются у своих владельцев;
- бизнес-политики не переносятся в Common;
- межмодульные контракты принадлежат соответствующим границам;
- Repository и прикладная оркестрация не размещаются в Common;
- модуль не зависит от бизнес-доменов;
- минимализм и стабильность важнее количества переиспользуемых классов.

**Статус: DRAFT — архитектурные границы определены, конкретные общие контракты уточняются при реализации.**
