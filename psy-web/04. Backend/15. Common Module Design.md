## Overview

This section defines the common module of the PsyWeb backend system. It serves as a shared foundation for all other modules and contains reusable components that are independent of specific business domains.

The common module is designed to prevent duplication and enforce consistency across the entire system.

---

# Core Principle

The common module must:

- contain only reusable, domain-agnostic components
- not depend on any business module
- be safe to import everywhere in the system
- remain stable and rarely changed

---

# Contents of Common Module

---

## 1. Enums

Shared system-wide enums used across modules.

Examples:

- UserRole (CLIENT, SPECIALIST, ADMIN)
- BookingStatus (CREATED, CONFIRMED, CANCELLED, COMPLETED, NO_SHOW)
- SlotStatus (FREE, BOOKED, BLOCKED)
- SpecialistStatus (PENDING, APPROVED, REJECTED)
- ReviewRating (1–5)

Rules:

- enums must be immutable
- must not contain business logic
- must be reused across all modules

---

## 2. Base Exception Classes

Common exception hierarchy:

- BaseException
- BusinessException
- NotFoundException
- ValidationException
- AuthorizationException

Purpose:

- unify error handling across system
- support global exception handler mapping
- enforce consistent error structure

---

## 3. Utility Classes

Stateless helpers used across modules.

Examples:

- DateTime utilities (UTC conversion, formatting)
- ID generators (if needed)
- validation helpers
- string utilities

Rules:

- must not depend on Spring context unless necessary
- must be reusable and testable

---

## 4. Constants

System-wide constants such as:

- default cancellation window (e.g. 24 hours)
- pagination defaults
- system limits (max slots per day, etc.)

---

## 5. Shared DTO Contracts (limited usage)

Only allowed if truly cross-domain.

Examples:

- ErrorResponse
- PaginatedResponse<T>
- ApiResponse<T>

Rules:

- must remain generic
- must not leak domain-specific logic

---

# Dependency Rules

## Common module:

- must NOT depend on any other module
- must NOT contain business logic
- must NOT contain repository or service logic

## All other modules:

- can depend on common module freely

---

# Architectural Role

The common module acts as:

- foundation layer for all modules
- source of shared contracts and types
- consistency enforcer across system boundaries

---

# Design Constraints

## 1. No domain logic allowed

Business rules must never be placed in common module.

---

## 2. Stability requirement

Frequent changes in this module are discouraged because:

- it impacts entire system
- it increases coupling risk

---

## 3. Minimalism principle

Only truly shared components belong here.

---

# Integration with System

Common module is used by:

- auth (roles, exceptions)
- booking (statuses, constants)
- availability (slot status, time utils)
- review (rating enums)
- admin (shared responses, exceptions)

---

# Summary

The common module:

- centralizes shared system components
- ensures consistency across all backend modules
- prevents duplication of enums, exceptions, and utilities
- enforces strict architectural separation
- acts as the foundational layer of the modular monolith
