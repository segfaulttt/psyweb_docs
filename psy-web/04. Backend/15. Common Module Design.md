## Overview

This section defines the current role of the `common` package in the PsyWeb backend.

The common layer contains reusable technical contracts and infrastructure components that are independent from specific business modules.

Its purpose is to provide shared foundations without becoming a generic storage place for business-domain concepts.

---

# Core Principle

The common layer must:

- contain only cross-cutting, domain-agnostic components;
- not depend on User, Specialist, Availability, Booking, Review, Admin, or other business modules;
- remain safe for business modules to depend on;
- avoid owning business lifecycle rules;
- avoid becoming a dumping ground for unrelated utilities or constants.

---

# Current Common Package

The current `PsyWeb/main` contains three relevant common areas:

```text
common.exception
common.persistence
common.config
```

These are already implemented.

---

# 1. Common Exception Architecture

The shared domain-exception hierarchy lives in:

```text
com.psyweb.common.exception
```

Current types:

```text
DomainException
BaseDomainException
ValidationException
NotFoundException
ConflictException
ForbiddenException
InvalidStateException
ExpiredException
```

---

## DomainException

`DomainException` defines the common contract for expected business/domain failures.

Current contract:

```java
public interface DomainException {
    String code();
}
```

It provides a stable machine-readable error code.

It is not itself a Throwable.

---

## BaseDomainException

The common implementation base is:

```text
BaseDomainException
```

with:

```text
BaseDomainException
extends RuntimeException
implements DomainException
```

It stores:

```text
code
message
optional cause
```

`BaseDomainException` is abstract and must not be instantiated directly.

---

## Category Exceptions

The common layer defines a deliberately small set of abstract categories:

```text
ValidationException
NotFoundException
ConflictException
ForbiddenException
InvalidStateException
ExpiredException
```

Hierarchy:

```text
DomainException
        ↑ implements
BaseDomainException
        ├── ValidationException
        ├── NotFoundException
        ├── ConflictException
        ├── ForbiddenException
        ├── InvalidStateException
        └── ExpiredException
```

These categories provide shared semantics without introducing business-module dependencies.

---

## Module-Specific Exceptions

Concrete business exceptions remain in their owning modules.

Examples:

```text
user.exception
specialist.exception
availability.exception
booking.exception
```

Typical relationship:

```text
common.exception.ConflictException
        ↑
booking.exception.ActiveReservationAlreadyExistsException
```

or:

```text
common.exception.ExpiredException
        ↑
booking.exception.ReservationExpiredException
```

The common layer does not know about the corresponding business entities.

---

## Stable Error Codes

Concrete module exceptions define stable machine-readable codes.

The common hierarchy only provides the storage and contract for those codes.

Human-readable messages are not used as stable machine identifiers.

The future REST exception layer should consume this hierarchy rather than introducing a parallel error model.

---

# 2. Duration Persistence

The current common persistence utility is:

```text
DurationMinutesConverter
```

located in:

```text
com.psyweb.common.persistence
```

It implements:

```text
AttributeConverter<Duration, Integer>
```

and converts:

```text
java.time.Duration
↔
whole INTEGER minutes
```

The converter supports null values for optional persistence fields.

For non-null values, only whole-minute Durations are accepted.

Sub-minute values are rejected.

This converter is currently used by Specialist temporal settings such as:

```text
minimumBookingNotice
clientCancellationNotice
```

The common converter defines technical persistence representation.

Business validation and ownership of those settings remain in the Specialist domain.

---

# 3. Time Configuration

The current common configuration contains:

```text
TimeConfiguration
```

located in:

```text
com.psyweb.common.config
```

It exposes a Spring-managed:

```text
java.time.Clock
```

bean.

Current production configuration uses:

```java
Clock.systemDefaultZone()
```

Business services receive `Clock` through dependency injection instead of directly depending on uncontrolled system time.

Current consumers include temporal logic in:

```text
AvailabilitySlotService
ReservationService
BookingService
```

Tests may inject:

```text
Clock.fixed(...)
```

to make temporal behavior deterministic.

The existence of `TimeConfiguration` does not define the final platform timezone policy.

Timezone semantics are owned by separate documentation/backlog work.

---

# Business Enums Do Not Belong to Common

Business-state enums remain in their owning modules.

Examples include:

```text
UserRole
UserStatus

SpecialistStatus

AvailabilityStatus

ReservationStatus
BookingStatus
```

These types describe domain-specific state and therefore should not be centralized in `common` merely because multiple modules reference them.

For example:

```text
BookingStatus
```

belongs to the Booking domain.

Likewise:

```text
SpecialistStatus
```

belongs to the Specialist domain.

The common layer must not become an artificial owner of domain lifecycle models.

---

# Shared Constants

Business configuration should not be moved into static common constants merely because several classes use it.

For example:

```text
Reservation TTL
expiration scan interval
expiration batch size
```

are currently externalized through:

```text
ReservationProperties
```

rather than stored as common constants.

Similarly, specialist-level temporal policies remain part of the Specialist model.

Cross-cutting constants should exist in common only when they are truly domain-independent and stable.

---

# Shared Utilities

The common layer may contain reusable technical utilities only when they have a genuine cross-module use case.

A utility should not be added merely to avoid writing a few lines in a business module.

Examples of potentially valid common concerns include:

```text
generic persistence conversion
generic time abstraction/configuration
generic error contracts
```

Examples of concerns that should remain outside common include:

```text
booking-deadline calculation
specialist eligibility
reservation expiration rules
review eligibility
availability state transitions
```

Those are business logic.

---

# Shared DTOs

There is currently no requirement for the common layer to own generic API wrapper DTOs such as:

```text
ApiResponse
PaginatedResponse
ErrorResponse
```

If such contracts are introduced later, they must be justified by actual cross-module API use.

The common layer must not introduce speculative shared DTO abstractions before they are needed.

---

# Dependency Rules

## Common layer

The common layer:

- must not depend on business modules;
- must not own business Entities;
- must not own business Repositories;
- must not own business Services;
- must not encode business lifecycle rules.

---

## Business modules

Business modules may depend on common technical contracts.

Examples:

```text
booking
→ common.exception
→ common.config

specialist
→ common.exception
→ common.persistence

availability
→ common.exception
→ common.config
```

Dependency direction must not be reversed.

---

# Current Common Responsibilities

The current implementation provides:

```text
shared domain-exception contract
shared domain-exception category hierarchy
stable error-code support
optional exception cause support
Duration ↔ whole-minute persistence conversion
injectable application Clock configuration
```

These responsibilities are already present in `PsyWeb/main`.

---

# Target / Backlog Responsibilities

The following may integrate with common contracts later but are not currently implemented as common infrastructure:

```text
central REST error response model
global @ControllerAdvice
generic API response wrappers
additional domain-independent persistence converters
additional cross-cutting infrastructure utilities
```

They must not be described as current functionality until implemented.

---

# Design Constraints

## 1. Domain independence

Common code must not depend on:

```text
User
Specialist
AvailabilitySlot
Reservation
Booking
SessionOutcome
Review
```

or any other business entity.

---

## 2. Minimalism

A component belongs in common only when it is genuinely reusable across module boundaries.

---

## 3. No lifecycle ownership

Common infrastructure may support a business rule technically, but it must not own the rule itself.

For example:

```text
DurationMinutesConverter
```

knows how to persist a Duration.

It does not know what:

```text
minimumBookingNotice
```

means.

Likewise:

```text
Clock
```

provides time.

It does not decide when a Reservation expires.

---

## 4. Stable dependency direction

Business modules may depend on common.

Common must not depend on business modules.

This keeps the common layer reusable and prevents circular coupling.

---

# Summary

The current PsyWeb common layer is intentionally small.

It currently owns:

```text
common.exception
→ shared domain error hierarchy

common.persistence
→ DurationMinutesConverter

common.config
→ injectable Clock configuration
```

Business statuses, lifecycle rules, policies, and entities remain inside their owning modules.

The common layer provides technical foundations only and must remain independent from domain-specific behavior.
