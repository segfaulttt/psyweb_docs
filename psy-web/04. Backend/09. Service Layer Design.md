## Overview

The service layer is the application/use-case boundary of the current PsyWeb backend.

Services coordinate:

- domain entities;
- repositories owned by their module;
- other module services where a use case crosses domain boundaries;
- transactional state changes;
- business validation that spans more than one entity.

The current `PsyWeb/main` contains service implementations for:

```text
UserService
SpecialistService
AvailabilitySlotService
ReservationService
BookingService
```

Auth, Admin, Review, SessionOutcome, and other future service layers remain target/backlog unless implemented by their own tasks.

---

# Service Layer Principles

## 1. Services Orchestrate Use Cases

Services coordinate business operations.

They do not replace domain behavior.

For example:

```text
BookingService
→ validates the use case
→ coordinates Reservation / User / Specialist / Availability
→ invokes domain transitions
→ persists the result
```

while an entity such as:

```text
Reservation
AvailabilitySlot
Specialist
Booking
```

still validates its own lifecycle transition.

---

## 2. Repository Ownership

Repositories belong to the module that owns their entity.

Examples:

```text
UserRepository
→ user

SpecialistRepository
→ specialist

AvailabilitySlotRepository
→ availability

ReservationRepository
BookingRepository
→ booking
```

Another module must not bypass the owning service boundary by directly mutating its repository.

---

## 3. Transaction Boundaries

Consistency-sensitive application operations use service-level transaction boundaries.

Current examples include:

```text
Reservation creation
Reservation cancellation
Reservation expiration
Reservation confirmation
Booking cancellation
Specialist lifecycle mutations
```

The exact transaction is determined by the business operation rather than by a rule that every service method must always be transactional.

---

## 4. Services Remain Cohesive

Each service should represent a clear domain/use-case responsibility.

A service should not accumulate unrelated functionality merely because it already participates in several workflows.

# Current UserService

`UserService` owns User retrieval and account-state checks used by other services.

Current public operations include:

```text
getUser(...)
getActiveUser(...)
findUserByEmail(...)
```

Email lookup uses the same canonicalization rule as User persistence:

```text
trim
→ lowercase using Locale.ROOT
→ validate
```

The distinction between unrestricted and ACTIVE-only lookup is current implementation.

Detailed semantics and documentation of those lookup APIs are owned by the dedicated User documentation task and are not duplicated here.

---

# Current SpecialistService

`SpecialistService` owns Specialist retrieval, professional eligibility checks, and Specialist lifecycle mutations.

Current operations include:

```text
getSpecialist(...)
getEligibleSpecialist(...)

approveSpecialist(...)
rejectSpecialist(...)
resubmitSpecialist(...)
suspendSpecialist(...)
reinstateSpecialist(...)
```

---

## Current Lifecycle

Current SpecialistStatus values are:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Current transitions are:

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

The Specialist entity validates whether the transition is legal.

The Service owns the use-case operation and persistence.

---

## Current Eligibility

`getEligibleSpecialist(...)` requires:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

Failure produces:

```text
SpecialistNotEligibleException
```

Professional eligibility is distinct from authentication.

---

## Current vs Target Moderation Boundary

Current SpecialistService already performs:

```text
approve
reject
resubmit
suspend
reinstate
```

on Specialist state.

It does not yet implement the complete target administrative workflows around those state changes.

Target/backlog includes:

```text
immutable SpecialistModerationAction history
suspension cancellation cascade
ADMIN authorization/orchestration
structured moderation reasons
```

Those workflows may coordinate other module services but must not move Specialist lifecycle ownership out of SpecialistService.

# Current AvailabilitySlotService

`AvailabilitySlotService` owns operations on AvailabilitySlot.

Current public operations are:

```text
createSlot(Long specialistId, LocalDateTime startTime, LocalDateTime endTime)

reserveSlot(Long slotId)

releaseReservation(Long slotId)

releaseBooking(Long slotId)

findBySpecialist(Long specialistId)

getFreeSlot(Long id)

confirmBooking(Long slotId)

cancelSlot(
    Long slotId,
    LocalDateTime cancelledAt,
    CancellationInitiator initiator,
    CancellationReason reason
)
```

All AvailabilitySlot state mutations are requested through this service boundary.

Booking and Reservation services do not invoke AvailabilitySlot mutator methods directly.

---

## Current Slot Creation

Current `createSlot(...)` performs:

```text
validate specialistId
validate startTime / endTime
require startTime > now
require startTime < endTime
require eligible Specialist
application overlap pre-check
create FREE AvailabilitySlot
persist Slot
```

Time is obtained through injected:

```text
Clock
```

---

## Current Overlap Pre-Check

The Repository query uses:

```text
existing.startTime < newEnd
&&
existing.endTime > newStart
```

which implements half-open interval overlap semantics:

```text
[startTime, endTime)
```

The current pre-check still has two known gaps relative to the approved target:

```text
CANCELLED rows are not excluded
PostgreSQL exclusion constraint is not implemented
```

The current overlap branch also still throws a generic:

```text
IllegalArgumentException
```

The approved target uses:

```text
SlotOverlapException
```

for both application and database conflict detection.

---

## Current Slot State Operations

AvailabilitySlotService currently coordinates:

```text
FREE → RESERVED
RESERVED → FREE
RESERVED → BOOKED
BOOKED → FREE
active state → CANCELLED
```

The Availability module owns these Slot state transitions.

Booking and Reservation services request them through this service boundary rather than invoking AvailabilitySlot mutator methods directly.

Current terminal cancellation also persists:

```text
cancelledAt
CancellationInitiator
CancellationReason
```

through:

```text
cancelSlot(...)
```

This operation owns the local AvailabilitySlot transition only.

It must not be confused with the complete specialist-removal or administrative suspension use case.

Those workflows additionally coordinate related Reservation and Booking state and remain target/backlog functionality.

---

## Booking Deadline Boundary

The current Specialist model stores:

```text
minimumBookingNotice
```

but AvailabilitySlotService does not yet implement the final:

```text
bookingDeadline
```

calculation/enforcement.

The current AvailabilitySlot also does not contain the optional per-slot override.

Therefore:

```text
Specialist default notice
→ current data

slot override
→ target/backlog

booking deadline enforcement
→ target/backlog
```

Detailed Availability state-machine and Reservation-creation ownership documentation remains with the dedicated Availability documentation task.

---

# Current ReservationService

Reservation lifecycle is implemented through a dedicated:

```text
ReservationService
```

rather than being folded into BookingService.

Current responsibilities include:

```text
Reservation creation
Reservation lookup
Reservation locking
Reservation cancellation
explicit Reservation expiration
automatic expiration batch processing
```

---

## Reservation Creation

Current flow:

```text
validate clientId / slotId
→ check for existing ACTIVE Reservation
→ require ACTIVE User
→ AvailabilitySlotService.reserveSlot(...)
→ capture now from Clock
→ create ACTIVE Reservation
→ expiresAt = now + configured TTL
→ saveAndFlush
```

The operation is transactional.

---

## ACTIVE Reservation Conflict

Current protection uses defense in depth:

```text
application pre-check
+
PostgreSQL partial unique index
```

The database constraint is:

```text
unique_active_reservation_slot
```

When that known constraint detects a concurrent conflict, ReservationService converts the persistence failure into:

```text
ActiveReservationAlreadyExistsException
```

and retains the technical exception as the cause.

Unknown database failures are not reclassified as that business exception.

---

## Reservation Locking

Mutation-sensitive Reservation operations use pessimistic write locking through:

```text
findForUpdateById(...)
```

Current callers include cancellation and Booking confirmation flows.

---

## Reservation Expiration

ReservationService uses injected:

```text
Clock
```

for expiration decisions.

Expiration boundary:

```text
now >= expiresAt
```

Current explicit expiration performs:

```text
ACTIVE Reservation → EXPIRED
AvailabilitySlot RESERVED → FREE
```

inside a transaction.

---

## Automatic Expiration Batch

Current:

```text
expireExpiredReservations()
```

captures one current time and loads one batch with:

```text
status = ACTIVE
expires_at <= now
ORDER BY expires_at, id
FOR UPDATE SKIP LOCKED
```

Batch size comes from:

```text
ReservationProperties.expirationBatchSize()
```

Each still-expired Reservation is transitioned to EXPIRED and releases its Slot.

The scheduler itself delegates to this service operation.

---

# Current BookingService

`BookingService` currently owns confirmed Booking use cases.

Current public responsibilities include:

```text
Reservation confirmation
Booking creation
Booking cancellation
client Booking query
specialist Booking query
```

---

## Reservation Confirmation

Current flow:

```text
validate reservationId / clientId
→ pessimistically lock Reservation
→ capture now from Clock
→ verify Reservation ownership
→ handle Reservation expiration
→ require ACTIVE Reservation
→ require ACTIVE User
→ AvailabilitySlot RESERVED → BOOKED
→ require eligible Specialist
→ Reservation ACTIVE → CONFIRMED
→ create CONFIRMED Booking
→ persist Booking
```

The operation is transactional.

---

## Expiration During Confirmation

If:

```text
now >= reservation.expiresAt
```

confirmation does not create a Booking.

Instead:

```text
Reservation → EXPIRED
AvailabilitySlot → FREE
```

and:

```text
ReservationExpiredException
```

is raised.

The confirmation transaction uses:

```text
dontRollbackOn = ReservationExpiredException.class
```

so the expiration state is preserved rather than rolled back with the business error.

---

## Booking Cancellation

Current cancellation performs:

```text
load Booking
→ capture now from Clock
→ Booking → CANCELLED
→ AvailabilitySlot BOOKED → FREE
```

inside a transaction.

The current implementation does not yet enforce the complete approved:

```text
clientCancellationNotice
late-cancellation classification
cancellationInitiator
cancellationReason
```

model.

Those parts remain target/backlog.

---

## Current Legacy BookingStatus

The current Booking domain still contains:

```text
CONFIRMED
CANCELLED
COMPLETED
NO_SHOW
```

The approved target removes:

```text
COMPLETED
NO_SHOW
```

from Booking lifecycle and moves attendance/result semantics to SessionOutcome.

This cleanup is future implementation/schema work.

# Target Auth Service

The final Auth service is:

```text
target / backlog
```

It will own authentication orchestration such as:

```text
credential verification
login
JWT generation
```

Target login requires:

```text
valid credentials
+
UserStatus.ACTIVE
```

An ACTIVE Specialist may authenticate regardless of SpecialistStatus.

Professional eligibility remains enforced separately through the Specialist boundary.

The Auth service must not own UserStatus or SpecialistStatus.

---

# Target Admin Service

A dedicated Admin service/application boundary is also:

```text
target / backlog
```

Its role is orchestration.

Target use cases include:

```text
Specialist moderation
suspension/reinstatement orchestration
User moderation
future SessionOutcome dispute resolution
```

Admin must call the owning module's service rather than directly modifying its Repository.

For example:

```text
Admin use case
→ SpecialistService.suspendSpecialist(...)
```

---

# Target Post-Session Services

Approved future Booking-domain service behavior includes:

```text
SessionOutcome creation
SessionReport submission
automatic outcome resolution
timeout finalization

administrative dispute resolution
```

These services are not currently implemented.

# Review / Chat / Notification Boundary

Detailed Review behavior belongs to its dedicated backlog/documentation scope.

Chat and Notification services are also future/separate scope.

They do not change ownership of the current User, Specialist, Availability, Reservation, or Booking domains.

# Service Interaction Model

Current implemented cross-module interactions include:

```text
AvailabilitySlotService
→ SpecialistService

ReservationService
→ UserService
→ AvailabilitySlotService

BookingService
→ ReservationService
→ UserService
→ SpecialistService
→ AvailabilitySlotService
```

These dependencies do not transfer entity ownership.

For example:

```text
BookingService
→ AvailabilitySlotService.confirmBooking(...)
```

means Booking coordinates a use case while Availability still owns the Slot transition.

# Current Transaction Examples

## Reservation Creation

```text
ReservationService.createReservation(...)
→ ACTIVE User
→ FREE Slot becomes RESERVED
→ ACTIVE Reservation created
→ commit
```

The application pre-check and database ACTIVE-Reservation uniqueness protect the hold invariant.

---

## Reservation Cancellation

```text
ReservationService.cancelReservation(...)
→ lock Reservation
→ ACTIVE → CANCELLED
→ RESERVED Slot → FREE
→ commit
```

---

## Reservation Expiration

```text
ReservationService.expireReservation(...)
→ lock Reservation
→ ACTIVE → EXPIRED
→ RESERVED Slot → FREE
→ commit
```

---

## Reservation Confirmation

```text
BookingService.confirmReservation(...)
→ lock Reservation
→ validate ownership / expiration / state
→ validate current User
→ RESERVED Slot → BOOKED
→ validate Specialist eligibility
→ ACTIVE Reservation → CONFIRMED
→ create Booking
→ commit
```

---

## Booking Cancellation

```text
BookingService.cancelBooking(...)
→ CONFIRMED Booking → CANCELLED
→ BOOKED Slot → FREE
→ commit
```

# Design Constraints

The service layer must preserve the following rules:

- domain ownership does not move between modules;
- repositories are not shared as public cross-module mutation APIs;
- entities continue to enforce their own local lifecycle invariants;
- service orchestration remains cohesive;
- transaction boundaries cover all state changes required for one consistency-sensitive use case;
- current implementation and target/backlog behavior remain explicitly separated.

# Summary

The current service layer is built around five implemented service boundaries:

```text
User
Specialist
Availability
Reservation
Booking
```

Services coordinate use cases and transactions while domain entities retain lifecycle invariants and each module retains ownership of its own persistence.

Future Auth, Admin, SessionOutcome, Review, Chat, and Notification behavior must be added without blurring those existing ownership boundaries.
