
# 09. Проектирование сервисного слоя PsyWeb

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**СУБД:** PostgreSQL 16+  
**Статус:** DRAFT — утверждённая целевая архитектура, с открытыми техническими деталями

---

# 1. Назначение документа

Документ определяет архитектуру сервисного слоя PsyWeb.

Рассматриваются:

- ответственность сервисов;
- владение бизнес-состоянием;
- межмодульные контракты;
- направление зависимостей;
- транзакционные границы;
- конкурентные операции;
- взаимодействие с PostgreSQL;
- правила безопасности;
- обработка ошибок;
- особенности времени и расписания;
- последовательность будущей реализации.

Документ описывает целевой дизайн серверной части.

Приведённые сигнатуры являются концептуальными. Окончательные Java-интерфейсы, типы аргументов и DTO согласуются при проектировании реализации.

# 2. Архитектурные принципы

## 2.1. Разделение ответственности

Каждый модуль отвечает за собственную предметную область.

Например:

- Service владеет ServiceOffering.
- Schedule владеет рабочими правилами.
- Booking владеет Reservation, Booking и ScheduleOccupancy.
- Outcome владеет результатом консультации.
- Review владеет отзывами.

Другой модуль не должен самостоятельно изменять чужое бизнес-состояние.

## 2.2. Тонкие контроллеры

Контроллер:

1. Получает HTTP-запрос.
2. Проверяет его формат.
3. Получает идентичность вызывающего пользователя.
4. Вызывает прикладной сервис.
5. Формирует HTTP-ответ.

Контроллер не должен самостоятельно:

- открывать критическую бизнес-транзакцию;
- изменять JPA-сущности;
- реализовывать переходы состояний;
- вычислять допустимость бронирования;
- обращаться к нескольким Repository для выполнения бизнес-операции.

## 2.3. Сервисный слой

Сервисный слой:

- выполняет бизнес-сценарии;
- проверяет права и инварианты;
- координирует модули;
- управляет транзакциями;
- обращается к Repository своего модуля;
- преобразует технические конфликты в предметные ошибки.

## 2.4. Доменная модель

Инварианты отдельных сущностей должны по возможности находиться внутри доменной модели.

Например, Reservation не должна допускать произвольные переходы между состояниями.

Однако правила, требующие информации из нескольких сущностей или модулей, обычно выполняются на уровне прикладной или доменной службы.

## 2.5. Отсутствие циклических зависимостей

Циклы между реализациями модулей запрещены.

Допустимы направленные межмодульные зависимости через стабильные интерфейсы.

Для сложных бизнес-сценариев используется прикладная оркестрация.

## 2.6. Транзакционное владение

У каждой изменяющей бизнес-операции должна быть определена внешняя транзакционная граница.

Внутренние сервисы могут присоединяться к ней, но не должны самостоятельно фиксировать половину общего бизнес-сценария.

## 2.7. Простота архитектуры

Не нужно создавать интерфейс для каждого метода, даже если его никто не использует за пределами модуля.

Публичные контракты вводятся там, где они выражают реальные границы ответственности.

# 3. Основные виды сервисов

## 3.1. Application Service

Выполняет пользовательский или административный сценарий.

Примеры:

- ReservationApplicationService;
- ScheduleChangeApplicationService;
- AdministrativeBlockingService.

Может координировать несколько модулей в одной транзакции.

## 3.2. Domain Service

Реализует предметную логику, которая не принадлежит одной сущности.

Примеры:

- AvailabilityPolicy;
- CancellationPolicy;
- ScheduleIntervalPolicy.

Обычно не управляет HTTP и не зависит от контроллеров.

## 3.3. Command Service

Изменяет состояние принадлежащего модулю домена.

Примеры:

- ReservationCommandService;
- BookingCommandService;
- ScheduleCommandService.

## 3.4. Query Service

Предоставляет данные другим сценариям без изменения бизнес-состояния.

Примеры:

- ScheduleQueryService;
- OccupancyQueryService;
- BookingObligationQueryService.

## 3.5. Infrastructure Service

Обеспечивает технический механизм.

Примеры:

- CalendarLockCoordinator;
- Clock;
- NotificationDeliveryAdapter.

Инфраструктурная служба не принимает бизнес-решения вместо доменного сервиса.

# 4. Межмодульная оркестрация

## 4.1. Проблема Schedule и Booking

Booking необходимо знать, когда специалист работает.

Schedule необходимо знать, какие обязательства уже существуют.

Прямые зависимости реализаций в обе стороны привели бы к циклу:

```text
BookingService → ScheduleService
ScheduleService → BookingService
```

Это запрещённая архитектура.

## 4.2. Решение

Операции, затрагивающие одновременно Schedule и Booking, координируются отдельным прикладным слоем.

Концептуальное название:

`SchedulingApplicationService`

Допускается разделение на более узкие сервисы:

- ReservationApplicationService;
- ScheduleChangeApplicationService;
- WeeklyScheduleChangeCoordinator.

Эти названия предварительные.

## 4.3. Направление зависимостей

```text
REST Controller
    |
    v
Scheduling Application Layer
    |
    +---- Service Module
    |
    +---- Specialist Module
    |
    +---- Schedule Module
    |
    +---- Booking Module
    |
    +---- AvailabilityPolicy
    |
    +---- CalendarLockCoordinator
```

Модули Schedule и Booking не вызывают реализации друг друга.

## 4.4. Владение состоянием

Координатор:

- устанавливает порядок операций;
- управляет транзакцией;
- получает необходимые блокировки;
- вызывает контракты модулей.

Координатор не становится владельцем Reservation или расписания.

## 4.5. Допустимые зависимости

AvailabilityService вправе использовать:

- ScheduleQuery;
- ServiceOfferingQuery;
- OccupancyQuery.

ReservationApplicationService вправе использовать:

- ScheduleQuery;
- ServiceOfferingQuery;
- BookingCommand;
- AvailabilityPolicy.

ScheduleChangeApplicationService вправе использовать:

- ScheduleQuery;
- ScheduleCommand;
- BookingObligationQuery;
- BookingCommand.

При этом BookingCommand не вызывает ScheduleChangeApplicationService.

# 5. Транзакционные правила

## 5.1. Общий принцип

Каждая критическая бизнес-команда выполняется атомарно.

Примеры:

- создать Reservation и Occupancy;
- подтвердить Reservation и создать Booking;
- отменить Reservation и удалить Occupancy;
- отменить Booking и удалить Occupancy;
- заблокировать специалиста и отменить все ACTIVE Reservation;
- изменить недельную версию и её интервалы;
- разрешить спор и обновить SessionOutcome.

## 5.2. Spring @Transactional

@Transactional размещается на внешней прикладной операции, определяющей транзакционную границу.

Внутренние команды присоединяются к действующей транзакции.

## 5.3. Propagation

Для составных команд обычно используется REQUIRED.

Не следует применять REQUIRES_NEW к части операции, которая должна откатиться вместе с остальными изменениями.

## 5.4. Spring proxy

Самовызов метода внутри одного класса может не проходить через Spring transactional proxy.

Транзакционная архитектура должна учитывать реальное поведение Spring AOP.

## 5.5. Внешние операции

Во время критической транзакции не выполняются без необходимости:

- отправка email;
- HTTP-запросы во внешние системы;
- длительная обработка файлов;
- ожидание пользовательского ответа.

## 5.6. Изоляция

Базовый уровень:

`READ COMMITTED`

Он используется вместе с явными блокировками и ограничениями PostgreSQL.

# 6. Общий протокол блокировок

## 6.1. Используемые механизмы

- SELECT FOR SHARE.
- SELECT FOR UPDATE.
- PostgreSQL transaction-level advisory locks.
- GiST exclusion constraint.
- Повторное чтение данных после ожидания блокировок.

## 6.2. Shared configuration locks

Для чтения конфигурации при создании Reservation используются совместные блокировки.

Они позволяют нескольким клиентам параллельно читать одинаковые настройки.

## 6.3. Calendar locks

Применяются к затронутым календарным датам.

Логический ключ:

`(specialistId, localDate)`

Используется стабильное преобразование в PostgreSQL BIGINT.

## 6.4. Row locks

Для конкурентных переходов состояния Reservation применяется SELECT FOR UPDATE.

## 6.5. Основной порядок создания Reservation

```text
ServiceOffering FOR SHARE
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
SpecialistBookingPolicy FOR SHARE
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
Calendar advisory locks
    ↓
Reservation row locks при необходимости
    ↓
INSERT Reservation
    ↓
INSERT ScheduleOccupancy
```

## 6.6. Важное ограничение

Сложные команды, которые изменяют несколько видов состояния, должны использовать единый порядок захвата ресурсов.

Нельзя допустить противоположных последовательностей:

```text
Transaction A:
    Calendar lock
    → Reservation lock

Transaction B:
    Reservation lock
    → Calendar lock
```

## 6.7. Реальные SQL-блокировки

Явный порядок необходимо дополнительно проверить с учётом:

- Hibernate flush;
- foreign keys;
- locking queries;
- блокировок индексов;
- конкурентных UPDATE;
- каскадных операций.

Протокол не объявляется полностью проверенным до интеграционных тестов.

# 7. CalendarLockCoordinator

## 7.1. Назначение

Единый инфраструктурный механизм календарной координации.

## 7.2. Предлагаемый контракт

```text
lockDates(
    specialistId,
    affectedLocalDates
)
```

## 7.3. Предусловия

- существует активная транзакция;
- даты уже определены;
- все необходимые даты передаются одним согласованным набором.

## 7.4. Порядок

Даты сортируются по возрастанию.

Блокировки захватываются в одном порядке всеми операциями.

## 7.5. Технический механизм

PostgreSQL:

`pg_advisory_xact_lock`

## 7.6. Ключи

Используется стабильный 64-битный ключ, сформированный из:

- пространства имён;
- specialistId;
- localDate.

Одинаковые логические значения всегда должны формировать один ключ.

Коллизии между разными значениями могут создавать дополнительное ожидание, но не должны ослаблять защиту одинаковых логических ресурсов.

## 7.7. Ограничение

CalendarLockCoordinator не проверяет рабочие часы.

Он обеспечивает координацию.

Бизнес-проверка остаётся в соответствующем сценарии.

# 11. SpecialistService

## Ответственность

- управление профилем специалиста;
- предоставление базовых данных;
- проверка approval status;
- изменение обычных профильных атрибутов.

## Предлагаемые операции

```text
getSpecialist(specialistId)

updateSpecialistProfile(specialistId, command)

getSpecialistPublicProfile(specialistId)
```

## Разделение ответственности

Обычное изменение профиля не должно блокировать все клиентские бронирования специалиста.

Поэтому выделяются отдельные логические ресурсы:

- SpecialistBookingAccess;
- SpecialistBookingPolicy;
- SpecialistScheduleSettings;
- SpecialistTimeZoneGuard.

Они не обязаны принадлежать четырём разным бизнес-модулям.

Но если требуется независимая блокировка, физическое хранение в одной строке PostgreSQL может быть неподходящим.

# 12. SpecialistBookingAccessService

## 12.1. Назначение

Управляет разрешением специалисту принимать и подтверждать новые записи.

## 12.2. Основной контракт

```text
getBookingAccess(specialistId)

requireBookingAllowed(specialistId)
```

Для изменяющих операций предоставляется внутренний контракт получения согласованного состояния под блокировкой.

## 12.3. Создание Reservation

Используется:

`SpecialistBookingAccess FOR SHARE`

Затем проверяется, что бронирование разрешено.

## 12.4. Подтверждение Reservation

Также используется:

`SpecialistBookingAccess FOR SHARE`

Причём до получения Reservation FOR UPDATE.

## 12.5. Изменение допуска

Административная операция использует:

`SpecialistBookingAccess FOR UPDATE`

## 12.6. Инвариант

После успешной административной блокировки специалиста:

- новые Reservation запрещены;
- подтверждение прежних ACTIVE Reservation запрещено;
- ACTIVE Reservation отменены;
- CONFIRMED Booking автоматически не отменяются.

## 12.7. Граница ответственности

Проверка допуска может предоставляться этим сервисом.

Полный сценарий административной блокировки выполняется отдельным координатором, поскольку требует изменений в Booking и Admin.

---

# 13. SpecialistBookingPolicyService

## 13.1. Ответственность

Управляет:

- minimumBookingNotice;
- clientCancellationNotice.

## 13.2. Предлагаемые операции

```text
getBookingPolicy(specialistId)

updateMinimumBookingNotice(
    specialistId,
    duration
)

updateClientCancellationNotice(
    specialistId,
    duration
)
```

## 13.3. Создание Reservation

Политика читается под FOR SHARE.

## 13.4. Изменение

Изменение выполняется с эксклюзивной блокировкой соответствующей строки.

## 13.5. MinimumBookingNotice

Для новой Reservation:

`bookingDeadline = sessionStart - effectiveMinimumBookingNotice`

Создание допустимо, пока текущее время строго раньше bookingDeadline.

Изменение настройки не изменяет TTL уже созданных Reservation.

## 13.6. ClientCancellationNotice

При создании Reservation значение фиксируется в историческом snapshot.

Booking использует согласованные условия, а не актуальную настройку специалиста.

## 13.7. Возможные переопределения

В прежней модели рассматривался индивидуальный minimumBookingNotice для AvailabilitySlot.

После отказа от слотов способ переопределения в новой Service-first модели отдельно не утверждён.

До согласования он не должен автоматически переноситься в ServiceOffering или другую сущность.

# 14. ServiceOfferingService

## Ответственность

- создание услуги;
- изменение условий;
- деактивация;
- получение действующих услуг;
- проверка принадлежности специалисту.

## Предлагаемые операции

```text
createOffering(specialistId, command)

updateOffering(offeringId, command)

deactivateOffering(offeringId)

getOffering(offeringId)

getActiveOfferings(specialistId)
```

## 14.1. Snapshot-контракт

```text
ServiceOfferingSnapshotSource:
    offeringId
    specialistId
    title
    durationMinutes
    breakDurationMinutes
    price
    currency
    active
```

## 14.2. Резервирование

При создании Reservation выбранная ServiceOffering читается под FOR SHARE.

## 14.3. Гарантия согласованности

Все исторические условия и границы Occupancy рассчитываются из одного согласованного состояния услуги.

## 14.4. Конкурентное редактирование

Если Reservation первой получила FOR SHARE, изменение услуги ожидает завершения транзакции.

Если изменение завершилось первым, Reservation получает новые условия.

## 14.5. Существующие записи

Редактирование ServiceOffering не изменяет ранее созданные Reservation или Booking.

## 14.6. Ограничение

Изменение ServiceOffering не должно захватывать календарные блокировки в обратном порядке относительно операции резервирования.

---

# 15. ScheduleQueryService

## Ответственность

Предоставляет эффективные рабочие интервалы.

## Предлагаемые операции

```text
getScheduleSettings(specialistId)

getEffectiveWorkingIntervals(
    specialistId,
    localDate
)

getEffectiveWorkingIntervals(
    specialistId,
    fromDate,
    toDate
)
```

## 15.1. REGULAR

Для указанной даты:

1. Найти действующую WeeklyScheduleVersion.
2. Проверить наличие DateSchedule с purpose=OVERRIDE.
3. Если OVERRIDE существует — использовать его интервалы.
4. Иначе использовать интервалы недельной версии.

Пустой OVERRIDE означает нерабочую дату.

## 15.2. FLOATING

Для даты используется DateSchedule с purpose=MANUAL.

Если MANUAL отсутствует, дата считается нерабочей.

## 15.3. Неактивные правила

Правила другого режима могут сохраняться в PostgreSQL, но не участвуют в вычислении актуальной доступности.

## 15.4. Важный инвариант

В критической транзакции данные расписания повторно читаются после получения соответствующих календарных блокировок.

# 16. ScheduleManagementService

## Ответственность

- управление режимом графика;
- управление недельными версиями;
- управление расписанием конкретных дат;
- изменение горизонта;
- проверка базовых инвариантов интервалов.

## Предлагаемые операции

```text
changeScheduleMode(specialistId, mode)

changeBookingHorizon(
    specialistId,
    horizonDays
)

createWeeklyScheduleVersion(
    specialistId,
    command
)

replaceDateSchedule(
    specialistId,
    localDate,
    purpose,
    intervals
)

removeDateSchedule(
    specialistId,
    localDate,
    purpose

```

## 16.1. Рабочие интервалы

Каждый интервал должен удовлетворять:

`startTime < endTime`

Рабочие окна через полночь запрещены.

Интервалы одной даты не должны пересекаться.

## 16.2. Изменение DateSchedule

Для отдельной даты используется календарная координация.

После получения блокировок проверяются существующие Reservation и Booking.

## 16.3. Изменение WeeklyScheduleVersion

Применяется более широкий протокол:

- TimeZoneGuard FOR SHARE;
- ScheduleSettings FOR UPDATE;
- календарные блокировки защищённого горизонта;
- повторная проверка действующих версий;
- проверка обязательств;
- атомарное изменение периодов и интервалов.

## 16.4. Изменение режима и горизонта

Изменение режима или bookingHorizonDays рассматривается как операция, способная повлиять на доступность новых Reservation.

Оно не должно выполняться в обход календарной координации.

## 16.5. Существующие обязательства

Подтверждённые Booking нельзя отменять молча.

Если операция требует отмены, она должна использовать разрешённый командный контракт Booking.

## 16.6. Открытый бизнес-вопрос

Поведение ACTIVE Reservation при обычном изменении графика специалистом ещё не утверждено.

Не следует считать его аналогичным административной блокировке.

# 17. SpecialistTimeZoneService

## 17.1. Назначение

Отвечает за изменение часового пояса специалиста.

## 17.2. Предлагаемые операции

```text

    specialistId,
    newZoneId
)

changeTimeZone(
    specialistId,
    newZoneId,
    conflictAcknowledgement
)
```

## 17.3. Предварительная проверка

Перед изменением необходимо определить влияние нового ZoneId на будущие обязательства.

Сервис предоставляет сведения о затронутых Booking и ACTIVE Reservation.

## 17.4. Подтверждение специалиста

Если изменение затрагивает существующие обязательства, требуется явное подтверждение специалиста.

Предварительный результат проверки не является гарантией, что к моменту подтверждения данные не изменились.

Окончательная проверка проводится внутри изменяющей транзакции.

Изменение ZoneId получает:

`SpecialistTimeZoneGuard FOR UPDATE`

- существующие Booking сохраняют Instant;
- ACTIVE Reservation сохраняют Instant и expiresAt;
- Occupancy не пересчитывается;
- локальные шаблоны графика сохраняются;
- новая доступность рассчитывается с новым ZoneId;
- автоматический перенос не выполняется.

## 17.7. Согласование с Schedule

Команда смены ZoneId должна координироваться с изменением регулярного и датированного графика.

TimeZoneGuard обеспечивает стабильную интерпретацию календаря для конкурентных операций.

## 17.8. Ограничение

Смена ZoneId не может выполняться как обычное изменение строкового поля через UpdateSpecialistProfile.

Это самостоятельный бизнес-сценарий.

# 21. ReservationApplicationService

## 21.1. Назначение

Оркестрирует создание Reservation.

Это центральный прикладной сценарий записи клиента.

## 21.2. Публичная операция

```text
createReservation(
    authenticatedClientId,
    serviceOfferingId,
    sessionStart
)
```

## 21.3. Транзакция

Создание Reservation выполняется в одной транзакции PostgreSQL.

## 21.4. Алгоритм

```text
BEGIN

1. Проверить клиента.

2. Получить ServiceOffering FOR SHARE.

3. Проверить услугу и specialistId.

4. Получить BookingAccess FOR SHARE.

5. Проверить доступ специалиста к бронированию.

6. Получить BookingPolicy FOR SHARE.

7. Получить TimeZoneGuard FOR SHARE.

8. Получить актуальный ZoneId.

9. Рассчитать sessionEnd и occupiedUntil.

10. Проверить корректность локального начала.

11. Определить затронутые календарные даты.

12. Захватить Calendar advisory locks.

13. Повторно прочитать Schedule.

14. Проверить режим и рабочее окно.

15. Проверить booking horizon.

16. Проверить minimumBookingNotice.

17. Проверить Occupancy.

18. Обработать конфликтующие просроченные
    ACTIVE Reservation при необходимости.

19. Повторно проверить доступность.

20. Сформировать snapshot.

21. Создать Reservation.

22. Создать ScheduleOccupancy.

23. COMMIT.
```

## 21.5. Snapshot

В момент резервирования фиксируются:

- название услуги;
- durationMinutes;
- breakDurationMinutes;
- price;
- currency;
- clientCancellationNotice;
- абсолютные границы консультации;
- другие согласованные исторические условия, если они предусмотрены моделью.

## 21.6. Инвариант

Reservation и Occupancy создаются атомарно.

## 21.7. Защита PostgreSQL

GiST exclusion constraint остаётся окончательной защитой от пересекающихся Occupancy.

## 21.8. Граница модуля

ApplicationService обращается к BookingCommand, но не изменяет BookingRepository непосредственно.

# 23. ReservationExpirationService

## Ответственность

Обрабатывает истечение временных удержаний.

## Предлагаемые операции

```text
expireReservation(reservationId)

```

## Основной алгоритм

1. Получить Reservation FOR UPDATE.
2. Повторно проверить ACTIVE.
3. Определить актуальное время.

Внутренняя команда не должна пытаться захватить календарные блокировки повторно в противоречащем порядке.

## Важный инвариант

Нельзя удалить Occupancy подтверждённой Booking только из-за истечения старого TTL Reservation.

# 24. BookingService

## Ответственность

- подтверждение Reservation;
- создание Booking;
- отмена Booking;
- проверка состояний;
- сохранение истории.

## Предлагаемые операции

```text
confirmReservation(
    reservationId,
    authenticatedClientId
)

cancelBookingByClient(
    bookingId,
    authenticatedClientId
)

cancelBookingBySpecialist(
    bookingId,
    authenticatedSpecialistId,
    reason
)
```

## 24.1. Подтверждение

Транзакционный порядок:

```text
BEGIN

1. Определить specialistId Reservation.

2. Получить SpecialistBookingAccess FOR SHARE.

3. Получить Reservation FOR UPDATE.

4. Повторно проверить владельца и состояние.

5. Получить свежее время.

6. Проверить now < expiresAt.

7. Проверить действующее удержание.

8. Reservation → CONFIRMED.

9. Создать Booking.

10. Сохранить Occupancy.

11. COMMIT.
```

Предварительное определение specialistId не является проверкой права.

Авторитетные данные подтверждаются после получения блокировки Reservation.

## 24.2. Повторное подтверждение

Два параллельных подтверждения не создают две Booking.

Используются:

- Reservation FOR UPDATE;
- проверка статуса;
- UNIQUE(bookings.reservation_id).

## 24.3. Отмена

При допустимой отмене:

- сохраняется Booking.CANCELLED;
- сохраняются cancellation metadata;
- Occupancy удаляется;
- история остаётся.

## 24.4. Поздняя отмена

Сравниваются:

- cancelledAt;
- sessionStart;
- clientCancellationNoticeSnapshot.

Поздняя отмена до начала консультации допускается в MVP.

После начала консультации обычная клиентская отмена запрещена.

# 27. WeeklyScheduleChangeCoordinator

## Назначение

Специализированная оркестрация массового изменения регулярного расписания.

Может быть частью ScheduleChangeApplicationService.

## Основной протокол

```text
BEGIN

1. TimeZoneGuard FOR SHARE.

2. ScheduleSettings FOR UPDATE.

3. Определить защищённый календарный горизонт.
```

- порядок FK- и JPA-блокировок.

# 28. AdministrativeBlockingService

## 28.1. Назначение

Координирует административную блокировку специалиста.

## 28.2. Утверждённое правило

После успешной блокировки:

- новые Reservation запрещены;
- подтверждения ACTIVE Reservation запрещены;
- все ACTIVE Reservation отменены;
- их Occupancy удалены;
- CONFIRMED Booking сохранены.

## 28.3. Предлагаемая операция

```text
blockSpecialist(
    administratorId,
    specialistId,
    reason
)
```

## 28.4. Транзакционный алгоритм

```text
BEGIN

1. Проверить полномочия администратора.

2. SpecialistBookingAccess FOR UPDATE.

3. Проверить текущее состояние доступа.

4. Найти все ACTIVE Reservation специалиста.

5. Получить Reservation FOR UPDATE
   в детерминированном порядке.

6. Повторно проверить их состояния.

7. Отменить оставшиеся ACTIVE Reservation.

8. Зафиксировать ADMIN как инициатора.

9. Удалить соответствующие Occupancy.

10. Заблокировать новые Reservation
    и подтверждения.

11. Сохранить административное действие.

12. COMMIT.
```

## 28.5. Конкурентное подтверждение

BookingService сначала получает BookingAccess FOR SHARE.

Поэтому блокировка специалиста и подтверждение одной Reservation не могут независимо игнорировать друг друга.

## 28.6. Конкурентное создание

ReservationApplicationService также удерживает BookingAccess FOR SHARE.

Административная блокировка получает эксклюзивную блокировку и ожидает завершения уже начатых критических операций.

## 28.7. Атомарность

Нельзя зафиксировать административную блокировку, оставив ACTIVE Reservation из-за частично выполненной отмены.

## 28.8. Производительность

Операция может затрагивать несколько Reservation.

Для MVP приоритетом является атомарная корректность.

При дальнейшем росте нагрузки можно отдельно оценить необходимую оптимизацию.

## Предлагаемые операции

```text

    bookingId,
    reporterId,
    command
)

```

## Правила

- отсутствие ответов не означает успешного проведения.

## Конкурентность

Два одновременных отчёта не должны приводить к потере одного ответа.

Точный способ блокировки и разрешения определяется Outcome Domain Design.

# 32. ReviewService

## Ответственность

- создание Review;
- проверка eligibility;
- редактирование;
- получение отзывов;
- расчёт рейтинга специалиста.

## Предлагаемые операции

```text
createReview(
    clientId,
    specialistId,
    command
)

updateReview(
    reviewId,
    clientId,
    command
)

getReviewByClientAndSpecialist(
    clientId,
    specialistId
)

getSpecialistReviews(
    specialistId,
    pagination
)

getSpecialistRatingSummary(
    specialistId
)
```

## Утверждённое правило

**Один клиент может оставить одному специалисту один отзыв за всё время.**

Для создания необходима хотя бы одна подтверждённо успешная консультация.

## Хранение

UNIQUE(client_id, specialist_id).

eligibilityBooking указывает на консультацию, первоначально подтвердившую право на отзыв.

## Редактирование

Редактируется существующая Review.

Новая Booking не позволяет создать второй отзыв.

## Конкурентность

UNIQUE защищает от конкурентного создания дубликатов.

Для параллельного редактирования может использоваться optimistic locking.

Конкретная реализация утверждается в Notification Domain Design.

Межмодульные контракты предпочтительно передают:

## 36.3. Проверка зависимостей

Итоговый граф Java-зависимостей должен быть ациклическим.

# 37. Временная модель сервисов

## 37.1. Instant

Reservation и Occupancy используют абсолютные моменты времени.

## 37.2. ZoneId

Schedule использует локальное время специалиста.

## 37.3. Clock

Сервисы используют согласованный источник текущего времени.

Предпочтительно внедрение java.time.Clock.

## 37.4. TTL

Подтверждение Reservation выполняется только при:

`now < expiresAt`

Свежий now определяется после получения критических блокировок.

## 37.5. PostgreSQL now()

PostgreSQL now() возвращает начало транзакции.

Нельзя считать его актуальным временем после длительного ожидания блокировки.

## 37.6. DST

Если локальное начало не существует или неоднозначно, новая Reservation запрещена.

## 37.7. Открытое правило

Нужно отдельно определить поведение консультации, пересекающей DST-переход, когда её начало однозначно.

До утверждения нельзя считать такой интервал автоматически допустимым.

---

# 38. Обработка ошибок

Сервисы должны выражать ошибки предметной области.

Примеры:

- BookingConflictException;
- ReservationExpiredException;
- InvalidReservationStateException;
- InvalidBookingStateException;
- ScheduleConflictException;
- SpecialistBookingBlockedException;
- InvalidServiceOfferingException;
- InvalidBookingTimeException.

Названия предварительные.

## 38.1. PostgreSQL exclusion violation

Преобразуется в ошибку занятости.

## 38.2. UNIQUE violation

Используется для защиты уникальных бизнес-инвариантов.

## 38.3. Deadlock

Операция откатывается.

Повторная попытка допустима только по согласованной политике.

## 38.4. API

HTTP-слой преобразует ошибки централизованным exception handler.

## 38.5. Rollback

Нельзя сохранять частично выполненную критическую операцию.

# 42. Итог

Сервисная архитектура PsyWeb разделяет:

- владение бизнес-сущностями;
- координацию межмодульных сценариев;
- доменные вычисления;
- операции чтения;
- изменяющие команды;
- инфраструктуру конкурентности.

Ключевые принципы:

1. Schedule владеет графиком.
2. Booking владеет Reservation, Booking и Occupancy.
3. Service владеет ServiceOffering.
4. Availability вычисляет доступность.
5. SchedulingApplicationService координирует межмодульные операции.
6. Shared configuration locks защищают согласованность условий.
7. Calendar advisory locks координируют операции по датам.
8. PostgreSQL exclusion constraint предотвращает пересечение занятости.
9. Reservation и Booking сохраняют исторические условия.
10. Admin blocking атомарно отменяет ACTIVE Reservation.
11. Изменение timeZone не переносит существующие консультации.
12. DST-политика запрещает неоднозначные и несуществующие локальные начала.
13. Результат SessionOutcome независим от существования Occupancy.
14. Review уникален для пары клиент–специалист.

**Статус: DRAFT — целевая сервисная архитектура согласована; реализационные детали должны быть проверены интеграционно.**
