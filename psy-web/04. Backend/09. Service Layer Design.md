## Overview

This section defines the structure and responsibilities of the service layer in the PsyWeb backend system.

The service layer is the core of the application, where all business rules, domain logic, and transactional operations are implemented.

It acts as the boundary between the API layer (controllers) and the persistence layer (repositories).

---

# Core Responsibility

The service layer is responsible for:

- enforcing business rules
- coordinating multiple repositories
- managing transactional consistency
- executing domain logic
- validating business constraints beyond DTO validation

---

# Service Layer Design Principle

## One module = one service boundary

Each module owns its own service layer and business logic.

Examples:

- BookingService
- AvailabilityService
- UserService
- SpecialistService

---

# Service Layer Rules

## 1. No business logic in controllers

Controllers only delegate execution to services.

---

## 2. No direct repository usage outside service layer

Repositories must not be accessed from controllers or other modules directly.

---

## 3. Services are the only transaction boundary

All @Transactional operations must be defined at service level.

---

## 4. Services must remain cohesive

Each service must represent a single domain responsibility.

## user service

Responsibilities:

---

## specialist service

Responsibilities:

* Specialist retrieval and management
* Specialist data validation
* Specialist approval state ownership
* approval transition validation
* approve Specialist application
* reject Specialist application

The Specialist service owns approval state changes.

Allowed approval transitions currently are:

`PENDING → APPROVED`

`PENDING → REJECTED`

Approval operations must reject invalid source states.

For example, an already APPROVED or REJECTED Specialist must not silently pass through the PENDING-only approval workflow.

The Specialist service does not decide which administrator is authorized to perform administrative actions. Authorization of the administrative use case belongs to the Admin/API security boundary.

### Scope Boundary

SpecialistService operates on Specialist core responsibilities.

Core operations must not gradually become a generic public-profile editor.

Public profile management, when introduced, should use explicit profile-oriented operations and models.

Professional qualifications and credential verification should likewise use structured qualification and verification models rather than generic Specialist fields.

In particular:

- `bio` is not required for Specialist core;
- public page composition is not part of the core Specialist service for MVP;
- Specialist approval and credential verification are separate business concerns;
- future qualification verification must not be represented by reusing Specialist approval state.

The initial MVP SpecialistService may therefore remain focused on identity, approval lifecycle, and operational settings required by core workflows.

---

## availability service

Responsibilities:

* slot creation
* slot lookup
* schedule management
* time conflict validation
* AvailabilitySlot lifecycle management
* AvailabilitySlot state transition validation
* bookability validation
* booking deadline calculation
* slot reservation and release operations requested through the module service boundary
* specialist slot removal

The Availability service owns AvailabilitySlot state transitions.

It does not own Reservation or Booking lifecycle.

---

## booking service (core service)

Responsibilities:

* temporary Reservation creation
* Reservation expiration and cancellation
* Reservation confirmation
* Booking creation from confirmed Reservation
* Reservation lifecycle management
* Booking lifecycle management
* Booking cancellation
* post-session SessionReport submission
* automatic SessionOutcome resolution
* reporting-window timeout handling
* transition to DISPUTED for conflicting reports
* coordination of administrative dispute resolution
* coordination of AvailabilitySlot transitions through the Availability service boundary
* transactional integrity enforcement for cross-module booking operations

The Booking service owns Reservation and Booking lifecycle.

It coordinates AvailabilitySlot changes but does not own AvailabilitySlot state or modify Availability persistence directly.

This is the most critical transactional service in the system.

## admin service

Responsibilities:

* orchestrate Specialist approval and rejection
* user moderation
* system-level administrative operations
* post-session dispute resolution

For Specialist approval, AdminService coordinates the administrative use case but delegates the actual Specialist state transition to SpecialistService.

Typical flow:

`Admin request`
→ validate ADMIN authority
→ load target Specialist through Specialist boundary
→ request approve or reject operation
→ SpecialistService validates current approval state
→ Specialist approval state changes
→ persist through Specialist-owned repository

AdminService must not access SpecialistRepository directly.

# Service Interaction Model

Services may call services owned by other modules through explicit public boundaries.

## Allowed:

* AdminService → SpecialistService for Specialist approval and rejection
* BookingService → AvailabilityService for slot validation and AvailabilitySlot lifecycle operations
* BookingService → UserService for client eligibility checks
* BookingService → SpecialistService for specialist eligibility checks
* ReviewService → BookingService for booking and session outcome validation

Cross-module service calls do not transfer ownership of domain state.

For Specialist approval:

* AdminService initiates the administrative use case;
* SpecialistService owns validation and mutation of `approval_status`;
* SpecialistRepository remains private to the Specialist module.

For booking flows:

* BookingService may request `FREE → RESERVED`, but Availability owns the AvailabilitySlot transition;
* BookingService may request `RESERVED → BOOKED`, but it must not modify the AvailabilitySlot repository directly;
* specialist slot removal is handled through Availability ownership while related Booking or Reservation changes are coordinated consistently.

## Not allowed:

* circular module dependencies
* direct access to another module's repository
* modifying another module's persistent state by bypassing its service boundary

# Transaction Management

## Rule

Only service layer defines transactional boundaries.

---

## Reservation Creation Example

`BookingService.createReservation()`
→ validate client
→ request Availability service validation for the target slot
→ validate slot is FREE and still bookable
→ coordinate slot locking when required
→ create ACTIVE Reservation
→ request AvailabilitySlot transition `FREE → RESERVED`
→ commit transaction

Reservation creation and the AvailabilitySlot transition must succeed or fail together.

---

## Reservation Confirmation Example

`BookingService.confirmReservation()`
→ validate Reservation ownership
→ validate Reservation is ACTIVE and unexpired
→ validate associated slot state
→ transition Reservation to CONFIRMED
→ create Booking
→ request AvailabilitySlot transition `RESERVED → BOOKED`
→ commit transaction

Reservation confirmation, Booking creation, and the AvailabilitySlot transition form one atomic business operation.

---

# Domain Consistency Rule

Services must ensure:

- state transitions are valid
- no invalid domain states are persisted
- business invariants are enforced before DB commit

---

# Error Handling in Services

Services are responsible for:

- throwing domain-specific exceptions
- validating business rules
- preventing invalid state transitions

Examples:

- SlotAlreadyBookedException
- BookingConflictException
- InvalidBookingStateException

---

# Key Design Constraints

## 1. Services must not be anemic

Business logic must not be delegated to controllers or repositories.

---

## 2. Services must not become god objects

Each service must remain focused on a single domain.

---

## 3. Booking service is the transactional core

All critical consistency logic flows through this service.

---

## 4. Cross-module communication is service-based only

No direct entity or repository sharing between modules.

---

# Summary

The service layer is designed to:

- centralize business logic
- ensure transactional safety
- enforce domain rules consistently
- maintain modular separation between business domains
- act as the backbone of the entire backend architecture
