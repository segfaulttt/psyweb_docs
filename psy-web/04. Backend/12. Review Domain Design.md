## Overview

This section defines the review domain of the PsyWeb system. It is responsible for managing client feedback after completed consultations and contributes to specialist reputation within the marketplace.

The review domain is strictly tied to the booking lifecycle and can only be accessed after successful completion of an appointment.

---

# Core Concept

A review represents client feedback for a consultation whose post-session outcome has been conclusively resolved as `OCCURRED`.

Review eligibility is based on SessionOutcome rather than BookingStatus.

A CONFIRMED Booking alone does not prove that the consultation took place.

A CANCELLED, unresolved, disputed, DID_NOT_OCCUR, or UNVERIFIED session is not eligible for review.

---

# Review Entity

## Fields

- id
- booking_id
- client_id
- specialist_id
- rating (1–5)
- comment
- created_at

---

# Business Rules

## 1. Review eligibility

A review can only be created when:

- the Booking exists;
- the Booking belongs to the requesting client;
- a SessionOutcome exists for the consultation;
- SessionOutcome.resolution_status = RESOLVED;
- SessionOutcome.final_outcome = OCCURRED.

BookingStatus alone does not determine review eligibility.

The following outcomes do not allow review creation:

- PENDING;
- DISPUTED;
- RESOLVED → DID_NOT_OCCUR;
- UNVERIFIED;
- cancelled Booking.
---

## 2. One review per booking

Each booking can have at most one review.

Enforced via:

- unique constraint on booking_id

---

## 3. Ownership restriction

Only the client who created the booking can submit a review.

---

## 4. Specialist association

Review is always linked to:

- the specialist who provided the service
- the booking context

---

# Review Creation Flow

CreateReviewRequest
→ validate Booking exists
→ validate Booking belongs to client
→ load SessionOutcome
→ validate resolution_status = RESOLVED
→ validate final_outcome = OCCURRED
→ validate review uniqueness rule
→ persist Review

---

# Rating System

## Rating scale

- 1 = very poor
- 2 = poor
- 3 = neutral
- 4 = good
- 5 = excellent

---

## Aggregation rule (future-ready)

Specialist rating is derived from:

- average of all review ratings

Stored as:

- cached value in SpecialistProfile.rating_avg

---

# Data Consistency Rules

## 1. Review immutability

Once created:

- rating cannot be modified
- comment cannot be modified (optional policy choice, but currently assumed immutable)

---

## 2. Booking and SessionOutcome dependency

Review requires both:

- the relevant Booking context;
- a finalized SessionOutcome proving that the consultation occurred.

A CONFIRMED Booking without a RESOLVED → OCCURRED SessionOutcome is not sufficient.
---

## 3. Referential integrity

- booking_id must exist
- client_id must match booking.client_id
- specialist_id must match booking.specialist_id

---

# Query Patterns

# Indexing Strategy

Recommended indexes:

- booking_id (unique)
- specialist_id
- client_id

These support fast retrieval of review data.

# Error Scenarios

Common exceptions:

# Integration with Other Domains

## Booking domain

- Booking provides consultation ownership and context
- SessionOutcome determines whether the consultation is eligible for review
- Review requires a finalized OCCURRED outcome

## Specialist domain

- rating_avg updated based on reviews

## User domain

- client identity validated for ownership

---

# Consistency Rules

- reviews require a RESOLVED SessionOutcome with final outcome OCCURRED
- BookingStatus alone never enables review creation
- no orphan reviews allowed
- one review per booking invariant is enforced at DB level

---

# Summary

The review domain:

- enforces post-consultation feedback logic
- ensures feedback is available only for consultations verified as OCCURRED
- maintains data integrity through uniqueness constraints
- provides foundation for specialist rating system
- acts as a trust layer for marketplace quality
