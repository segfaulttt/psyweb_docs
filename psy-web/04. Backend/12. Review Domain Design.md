
# 12. Проектирование домена Review

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — бизнес-правила согласованы, детали реализации требуют проверки

---

# 1. Назначение документа

Документ определяет архитектуру домена Review в PsyWeb.

Домен отвечает за отзывы клиентов о специалистах после подтверждённо состоявшихся консультаций.

Основные задачи:

- проверка права клиента на создание отзыва;
- создание Review;
- предотвращение повторного создания отзыва для одной пары клиент–специалист;
- редактирование существующего Review;
- сохранение связи отзыва с консультацией, подтвердившей право на его создание;
- получение отзывов специалиста;
- расчёт агрегированного рейтинга;
- обеспечение целостности и авторизации;
- согласованная обработка конкурентных операций.

Review является частью репутационной системы платформы.

Он не определяет, состоялась ли консультация, и не управляет состояниями Booking.

Право на создание Review устанавливается на основании результата консультации, принадлежащего домену Outcome.

---

# 2. Основная концепция

## 2.1. Review как отзыв о специалисте

Review представляет оценку специалиста конкретным клиентом.

В отличие от модели отзыва о каждой отдельной консультации, в PsyWeb используется единый отзыв на всё взаимодействие клиента со специалистом.

Клиент может иметь множество консультаций с одним специалистом, но только один Review.

## 2.2. Утверждённое правило

**Один клиент может оставить одному специалисту только один Review за всё время.**

После создания клиент может редактировать этот Review.

Повторные консультации не создают право на второй отзыв.

## 2.3. Основание для создания

Для первоначального создания Review необходима хотя бы одна консультация соответствующей пары клиент–специалист, результат которой подтверждён как успешно состоявшийся.

Сам факт подтверждения Booking недостаточен.

## 2.4. Независимость от количества консультаций

Количество подтверждённых или успешно проведённых консультаций не изменяет ограничение уникальности Review.

Пример:

- клиент прошёл одну успешную консультацию — может создать Review;
- прошёл ещё пять успешных консультаций — может редактировать существующий Review;
- создать второй Review тому же специалисту нельзя.

---

# 3. Ответственность домена

Review владеет:

- сущностью Review;
- проверкой права на создание отзыва;
- созданием и редактированием;
- контролем уникальности;
- получением отзывов;
- расчётом рейтинга;
- авторизацией операций над отзывом.

Другие модули предоставляют необходимую информацию.

| Модуль | Ответственность |
|---|---|
| User | Идентичность пользователя |
| Client | Профиль клиента |
| Specialist | Профиль специалиста |
| Booking | История консультаций и их участники |
| Outcome | Подтверждённый результат консультации |
| Review | Отзывы и рейтинг |
| Admin | Административные решения в пределах утверждённых полномочий |

Review не изменяет Booking или SessionOutcome.

Интеграция выполняется через публичные межмодульные контракты.

---

# 4. Модель Review

## 4.1. Поля

| Поле | Назначение |
|---|---|
| id | Идентификатор Review |
| clientId | Автор отзыва |
| specialistId | Специалист, которому оставлен отзыв |
| eligibilityBookingId | Консультация, подтвердившая первоначальное право на отзыв |
| rating | Оценка от 1 до 5 |
| comment | Текст отзыва |
| createdAt | Время первоначального создания |
| updatedAt | Время последнего изменения |

## 4.2. Идентичность отзыва

Review идентифицируется собственным id.

В предметной области его уникальность определяется парой:

`(clientId, specialistId)`

## 4.3. EligibilityBooking

Поле eligibilityBookingId ссылается на конкретную Booking, которая послужила основанием для первоначального создания Review.

Она должна:

- существовать;
- принадлежать указанному клиенту;
- относиться к указанному специалисту;
- иметь подтверждённо успешный SessionOutcome на момент создания Review.

## 4.4. Неизменяемые поля

После создания Review не изменяются:

- id;
- clientId;
- specialistId;
- eligibilityBookingId;
- createdAt.

## 4.5. Изменяемые поля

Клиент может редактировать:

- rating;
- comment.

При изменении обновляется updatedAt.

## 4.6. Сохранение истории

Review не удаляется автоматически после завершения консультации или очистки ScheduleOccupancy.

Историческая Booking, связанная через eligibilityBookingId, должна сохраняться.

Правила удаления или скрытия Review в рамках модерации требуют отдельного согласования.

---

# 5. Право на создание Review

## 5.1. Основное условие

Клиент может создать Review, если существует хотя бы одна Booking, удовлетворяющая следующим условиям:

1. Booking принадлежит этому клиенту.
2. Booking относится к выбранному специалисту.
3. Для Booking существует результат SessionOutcome.
4. SessionOutcome подтверждает, что консультация успешно состоялась.

## 5.2. Недостаточные условия

Право на Review не возникает только на основании:

- создания ACTIVE Reservation;
- подтверждения Reservation;
- создания CONFIRMED Booking;
- достижения запланированного времени окончания;
- удаления Occupancy;
- неподтверждённого заявления одной стороны о проведении консультации.

## 5.3. Проверка успешного результата

Домен Review не должен самостоятельно интерпретировать отдельные ответы клиента и специалиста.

Он получает результат через контракт Outcome, например:

`VerifiedOutcomeQuery`

Контракт должен однозначно сообщать, подтверждено ли успешное проведение конкретной консультации.

## 5.4. Двустороннее подтверждение

В утверждённой модели Outcome клиент и специалист независимо сообщают о проведении консультации.

Совместимые ответы OCCURRED подтверждают успешное проведение.

Также существуют правила обработки:

- совместимых отрицательных ответов;
- единственного ответа после истечения окна;
- противоречивых ответов;
- отсутствия обоих ответов;
- административного разрешения споров.

Review использует окончательно разрешённый результат, а не промежуточные заявления.

## 5.5. Открытые результаты

Если результат консультации:

- ещё ожидает подтверждения;
- находится в споре;
- не подтверждён как успешный,

создание Review не разрешается на основании этой консультации.

## 5.6. Отсутствие ответов

Если ни одна сторона не сообщила о результате и консультация осталась непроверенной, право на Review не возникает автоматически.

## 5.7. Несколько успешных консультаций

Если клиент имеет несколько подтверждённо успешных консультаций с одним специалистом, для первоначального основания выбирается одна подходящая Booking.

Способ выбора должен быть детерминированным.

Предлагаемый вариант — самая ранняя успешно подтверждённая консультация.

Точное правило выбора является реализационной деталью и не меняет права клиента на один Review.

---

# 6. Уникальность Review

## 6.1. Бизнес-инвариант

Для одной пары клиент–специалист существует не более одного Review.

## 6.2. Ограничение PostgreSQL

```sql
CONSTRAINT uq_review_client_specialist
    UNIQUE (client_id, specialist_id)
```

## 6.3. Почему не UNIQUE(booking_id)

В PsyWeb Review не создаётся отдельно для каждой консультации.

У одного клиента может существовать множество Booking с одним специалистом.

Уникальность по booking_id позволяла бы создать несколько Review одному специалисту, что противоречит утверждённому правилу.

## 6.4. Конкурентные запросы

Два одновременных запроса создания Review от одного клиента одному специалисту не должны создавать дубликаты.

Предварительная проверка наличия Review полезна, но недостаточна.

Окончательная защита обеспечивается UNIQUE в PostgreSQL.

## 6.5. Повторное создание

Если Review уже существует, система отклоняет попытку создать ещё один.

Клиент должен использовать операцию редактирования существующего отзыва.

---

# 7. Создание Review

## 7.1. Инициатор

Review создаёт авторизованный клиент.

Его идентичность определяется через доверенный SecurityContext.

Нельзя принимать произвольный clientId из запроса как доказательство авторства.

## 7.2. Входные данные

Концептуальная команда:

```text
createReview(
    authenticatedClientId,
    specialistId,
    rating,
    comment
)
```

eligibilityBookingId предпочтительно определять на сервере после проверки успешных консультаций.

Если API принимает идентификатор Booking, он должен проверяться как неподтверждённый пользовательский ввод.

## 7.3. Проверки

Перед созданием:

1. Проверить идентичность клиента.
2. Проверить существование специалиста.
3. Проверить допустимость rating.
4. Проверить ограничения comment.
5. Проверить отсутствие Review этой пары.
6. Получить сведения о подтверждённо успешных консультациях пары.
7. Определить eligibilityBookingId.
8. Создать Review.
9. Зафиксировать транзакцию.

## 7.4. Транзакционный сценарий

```text
Client отправляет CreateReviewRequest
    ↓
ReviewService
    ↓
Проверка авторизации
    ↓
Проверка rating и comment
    ↓
Проверка существующего Review
    ↓
VerifiedOutcomeQuery
    ↓
Определение подходящей Booking
    ↓
Создание Review
    ↓
UNIQUE(client_id, specialist_id)
    ↓
COMMIT
```

## 7.5. Проверка после конкурентного изменения

Если за время операции другой запрос уже создал Review, PostgreSQL отклонит вторую вставку.

Нарушение уникальности преобразуется в предметную ошибку.

## 7.6. Историческое основание

После создания eligibilityBookingId не изменяется при последующих консультациях.

Новая успешная Booking не заменяет первоначальное основание отзыва.

---

# 8. Редактирование Review

## 8.1. Утверждённое правило

Клиент может редактировать собственный Review.

## 8.2. Изменяемые данные

Разрешено обновление:

- rating;
- comment.

## 8.3. Неизменяемые данные

Запрещается менять:

- автора;
- специалиста;
- первоначальную eligibilityBooking;
- дату создания.

## 8.4. Авторизация

Редактирование доступно только владельцу Review.

Владелец определяется по clientId, сверяемому с идентичностью из SecurityContext.

## 8.5. Сценарий

```text
Client отправляет UpdateReviewRequest
    ↓
ReviewService
    ↓
Получение Review
    ↓
Проверка владельца
    ↓
Проверка rating и comment
    ↓
Изменение разрешённых полей
    ↓
Обновление updatedAt
    ↓
COMMIT
```

## 8.6. Повторная проверка Outcome

Обычное редактирование существующего Review не должно требовать новой успешно проведённой консультации.

Право на первоначальное создание уже было установлено и зафиксировано.

Возможные административные исправления ошибочного Outcome и их влияние на Review требуют отдельной политики.

## 8.7. Конкурентное редактирование

Если клиент одновременно отправляет несколько изменений, необходимо определить поведение конкурентных обновлений.

Предлагаемый механизм — optimistic locking через @Version.

Окончательное решение принимается при реализации.

---

# 9. Оценка специалиста

## 9.1. Шкала

Rating принимает целые значения от 1 до 5.

| Значение | Интерпретация |
|---|---|
| 1 | Очень плохо |
| 2 | Плохо |
| 3 | Нейтрально |
| 4 | Хорошо |
| 5 | Отлично |

## 9.2. Ограничение

```sql
CHECK (rating BETWEEN 1 AND 5)
```

Проверка должна существовать как на уровне приложения, так и на уровне PostgreSQL.

## 9.3. Комментарий

Review может содержать текстовый комментарий.

В целевой схеме comment допускает NULL.

Необходимость дополнительных ограничений длины и содержимого определяется отдельно.

## 9.4. Недопустимые значения

Запрещаются:

- rating меньше 1;
- rating больше 5;
- дробные оценки, если тип принимает только целые значения.

---

# 10. Агрегированный рейтинг

## 10.1. Назначение

Агрегированный рейтинг отражает среднюю оценку специалиста на основании существующих Review.

## 10.2. Формула

Для специалиста с N отзывами:

`averageRating = SUM(rating) / N`

## 10.3. Один клиент — один голос

Поскольку один клиент может иметь только один Review на специалиста, повторные консультации этого клиента не увеличивают число его оценок.

При редактировании Review новая оценка заменяет прежнюю в расчёте среднего рейтинга.

## 10.4. Отсутствие отзывов

Если Review отсутствуют, рейтинг не должен автоматически считаться равным нулю.

Рекомендуется представлять отсутствие рейтинга отдельно от числового значения.

## 10.5. Источник истины

Источником истины являются актуальные Review.

Обязательное поле ratingAvg в SpecialistProfile не требуется.

## 10.6. Кэширование

Кэширование среднего рейтинга может быть добавлено позднее при возникновении подтверждённой необходимости.

Если кэш появится, он будет производным значением.

Его обновление должно учитывать создание и редактирование Review.

## 10.7. Дополнительные данные

Для интерфейса может предоставляться:

- averageRating;
- reviewCount.

Окончательные правила округления среднего рейтинга определяются на уровне API и представления.

---

# 11. Связь с Booking

## 11.1. Исторический контекст

Review связан с клиентом и специалистом.

eligibilityBookingId указывает на Booking, подтвердившую право на создание отзыва.

## 11.2. Подтверждение Booking недостаточно

Статус CONFIRMED означает только существование записи.

Он не подтверждает фактическое проведение консультации.

## 11.3. Исторические Booking

Booking сохраняется после:

- окончания консультации;
- обработки SessionOutcome;
- освобождения Occupancy.

Это позволяет сохранить основание Review.

## 11.4. Соответствие участников

eligibilityBooking должна относиться к тем же clientId и specialistId, что и Review.

В PostgreSQL это защищается составным внешним ключом.

## 11.5. Независимость Occupancy

Review не ссылается на ScheduleOccupancy.

Удаление Occupancy не влияет на Review и eligibilityBooking.

---

# 12. Связь с Outcome

## 12.1. Источник подтверждения

Outcome владеет результатом консультации.

Review не должен анализировать отдельные OutcomeReport и самостоятельно разрешать споры.

## 12.2. Межмодульный контракт

Предлагается использовать интерфейс:

`VerifiedOutcomeQuery`

Возможные операции:

```text
hasVerifiedSuccessfulConsultation(
    clientId,
    specialistId
)

findEligibleBookings(
    clientId,
    specialistId
)

isVerifiedSuccessful(
    bookingId
)
```

Это концептуальные контракты.

Точные сигнатуры определяются при проектировании сервисного слоя.

## 12.3. Консультации в споре

Консультация с неразрешённым спором не подтверждает право на Review.

## 12.4. Административное разрешение

Если администратор разрешил спор и итоговый SessionOutcome подтверждает успешное проведение, соответствующая Booking может стать основанием для Review.

## 12.5. Отсутствие подтверждения

Если консультация осталась непроверенной, она не является достаточным основанием.

---

# 13. Целостность данных

## 13.1. Первичный ключ

Каждая Review имеет собственный id.

## 13.2. Внешние ключи

Review ссылается на:

- Client;
- Specialist;
- eligibilityBooking.

## 13.3. Составной FK

Используется связь:

```sql
FOREIGN KEY (
    eligibility_booking_id,
    client_id,
    specialist_id
)
REFERENCES bookings(
    id,
    client_id,
    specialist_id
)
```

Она предотвращает указание Booking другого клиента или другого специалиста.

## 13.4. Уникальность

```sql
UNIQUE (client_id, specialist_id)
```

## 13.5. Допустимость рейтинга

```sql
CHECK (rating BETWEEN 1 AND 5)
```

## 13.6. Ограничения CHECK

CHECK не может самостоятельно проверить подтверждённость SessionOutcome в другой таблице.

Право на первоначальное создание проверяется доменным сервисом.

## 13.7. Историческая целостность

Нельзя удалять eligibilityBooking обычными операциями, если на неё ссылается Review.

Политика физического удаления исторических данных отдельно не утверждена.

---

# 14. Конкурентность и транзакции

## 14.1. Создание

Создание Review выполняется в одной транзакции.

## 14.2. Повторное создание

Конкурентные запросы защищаются:

`UNIQUE(client_id, specialist_id)`

## 14.3. Предварительная проверка

Проверка отсутствия Review до INSERT не заменяет ограничение базы данных.

## 14.4. Конкурентное редактирование

Для предотвращения незаметной потери обновлений может использоваться optimistic locking.

## 14.5. Проверка eligibility

При создании Review необходимо использовать подтверждённый результат Outcome.

Если в будущем появится механизм пересмотра уже подтверждённых результатов, потребуется согласовать конкурентность такого пересмотра и создания Review.

## 14.6. Границы модулей

ReviewService не должен напрямую изменять Booking или SessionOutcome.

Данные других модулей получаются через публичные контракты.

---

# 15. Получение отзывов

## 15.1. Отзывы специалиста

Основная операция:

```text
getSpecialistReviews(
    specialistId,
    pagination
)
```

## 15.2. Отзыв конкретного клиента

Возможная операция:

```text
getReviewByClientAndSpecialist(
    clientId,
    specialistId
)
```

## 15.3. Агрегированный рейтинг

Возможная операция:

```text
getSpecialistRatingSummary(
    specialistId
)
```

## 15.4. Пагинация

Список отзывов должен поддерживать пагинацию.

Это предотвращает загрузку всех отзывов специалиста при каждом запросе.

## 15.5. Сортировка

Предпочтительная сортировка по умолчанию:

`createdAt DESC, id DESC`

Окончательные правила сортировки могут быть расширены после проектирования API.

## 15.6. DTO

Контроллеры возвращают DTO, а не JPA-сущности.

Публичное представление отзыва не должно раскрывать лишние персональные данные клиента.

# 16. Индексирование

## 16.1. Уникальный индекс

Ограничение:

`UNIQUE(client_id, specialist_id)`

создаёт индекс для проверки уникальности и поиска отзыва определённой пары.

## 16.2. Индекс специалиста

Для получения отзывов специалиста рекомендуется индекс по specialist_id.

## 16.3. Пагинация

При необходимости индекс может учитывать сортировку created_at и id.

Окончательная конфигурация должна соответствовать фактическим SQL-запросам.

## 16.4. Избыточные индексы

Не следует создавать дополнительный индекс, полностью дублирующий уже существующий UNIQUE.

## 16.5. Производительность

При большом количестве отзывов необходимо проверить запросы расчёта рейтинга через EXPLAIN ANALYZE.

Кэширование рассматривается только после оценки реальной нагрузки.

---

# 17. Авторизация

## 17.1. Создание

Создать Review может только клиент, имеющий подтверждённо успешную консультацию с указанным специалистом.

## 17.2. Редактирование

Редактировать Review может только его автор.

## 17.3. Просмотр

Просмотр отзывов специалиста предполагается доступным через публичные операции чтения с соблюдением правил представления пользовательских данных.

## 17.4. Административные операции

Возможные действия администратора, включая скрытие или модерацию отзывов, должны быть отдельно описаны в Admin Domain Design.

Наличие роли ADMIN не означает автоматического права редактировать содержимое отзыва от имени клиента.

## 17.5. SecurityContext

Идентичность автора устанавливается по доверенному SecurityContext.

Нельзя полагаться только на clientId, переданный клиентским приложением.

# 18. Ошибки домена

Возможные предметные ошибки:

- ReviewNotFoundException;
- ReviewNotAllowedException;
- ReviewAlreadyExistsException;
- ReviewValidationException;
- UnauthorizedReviewAccessException;
- VerifiedConsultationRequiredException.

Названия предварительные.

Они должны соответствовать общей Exception Handling Strategy PsyWeb.

## 18.1. Нет успешной консультации

Создание Review запрещено.

## 18.2. Review уже существует

Повторное создание отклоняется.

Клиент может воспользоваться редактированием.

## 18.3. Некорректный rating

Запрос отклоняется.

## 18.4. Чужой Review

Редактирование запрещено.

## 18.5. Конкурентный INSERT

Нарушение UNIQUE преобразуется в понятную доменную ошибку.

# 19. Интеграция с Notification

Review может формировать событие:

`ReviewCreated`

При редактировании возможно событие:

`ReviewUpdated`

Обработка уведомлений принадлежит Notification.

Публикация события не должна приводить к внешнему действию по операции, которая впоследствии откатилась.

Для надёжной доставки может применяться согласованный механизм transactional outbox.

Точные события и требования к уведомлению специалиста определяются в Notification Domain Design.

# 20. Тестирование

## 20.1. Создание

Проверить:

- создание после подтверждённо успешной консультации;
- отказ без успешной консультации;
- отказ при неподтверждённом Outcome;
- отказ при неразрешённом споре;
- создание после успешного административного разрешения Outcome.

## 20.2. Уникальность

Проверить:

- первый Review создаётся;
- второй Review той же пары запрещён;
- Review другому специалисту разрешён при наличии eligibility;
- Review другого клиента тому же специалисту разрешён при наличии eligibility.

## 20.3. Редактирование

Проверить:

- изменение rating;
- изменение comment;
- обновление updatedAt;
- сохранение createdAt;
- сохранение eligibilityBookingId;
- запрет изменения чужого Review.

## 20.4. Рейтинг

Проверить:

- среднюю оценку нескольких Review;
- пересчёт после редактирования;
- специалиста без отзывов;
- корректное количество Review.

## 20.5. PostgreSQL

Интеграционные тесты проверяют:

- UNIQUE(client_id, specialist_id);
- составной FK на Booking;
- CHECK рейтинга;
- сохранение Review после освобождения Occupancy;
- конкурентное создание одного Review.

## 20.6. Конкурентность

Особенно важно проверить:

1. Два одновременных запроса создания Review для одной пары.
2. Конкурентное редактирование.
3. Создание Review одновременно с разрешением SessionOutcome.
4. Повторные запросы после ошибки уникальности.

## 20.7. Тестовая инфраструктура

PostgreSQL-ограничения необходимо проверять на настоящем PostgreSQL, например с использованием Testcontainers.

---

# 21. Основные инварианты

1. Review принадлежит одной паре клиент–специалист.
2. Один клиент может иметь не более одного Review на одного специалиста.
3. Повторные консультации не позволяют создать второй Review.
4. Review можно редактировать.
5. rating находится в диапазоне 1–5.
6. Review создаётся только после подтверждённо успешной консультации.
7. CONFIRMED Booking сама по себе не даёт права на Review.
8. Неподтверждённый SessionOutcome не даёт права на Review.
9. Review не разрешает споры между участниками консультации.
10. eligibilityBookingId принадлежит той же паре клиент–специалист.
11. eligibilityBookingId не меняется при редактировании.
12. Автор Review определяется через доверенный SecurityContext.
13. Чужой Review нельзя редактировать.
14. Удаление Occupancy не удаляет Review.
15. Агрегированный рейтинг рассчитывается по актуальным Review.
16. PostgreSQL защищает уникальность и допустимый диапазон rating.
17. Домен Review не изменяет состояния Booking и SessionOutcome.

---

# 22. Открытые вопросы

## 22.1. Политика удаления

Необходимо определить, разрешено ли клиенту удалять Review или для MVP поддерживаются только создание и редактирование.

Текущая утверждённая модель гарантирует редактирование, но не определяет удаление.

## 22.2. Модерация

Требуется отдельно согласовать:

- скрытие отзывов;
- основания для модерации;
- уведомление автора;
- административный аудит.

## 22.3. Ограничения комментария

Необходимо определить:

- максимальную длину;
- правила обработки пустого текста;
- требования к содержимому.

## 22.4. Конкурентное редактирование

Требуется окончательно выбрать механизм optimistic locking либо иную согласованную стратегию.

## 22.5. Изменение Outcome после создания Review

Если в будущем появится пересмотр подтверждённого успешного Outcome, необходимо определить последствия для ранее созданного Review.

Автоматическое удаление Review без отдельного решения не предполагается.

## 22.6. Историческое основание

Необходимо утвердить точный критерий выбора eligibilityBookingId при наличии нескольких подходящих консультаций.

## 22.7. Представление рейтинга

Требуется определить точность среднего рейтинга и правила округления в API.

---

# 23. Итог

Домен Review PsyWeb предоставляет репутационную модель, в которой клиент оценивает специалиста, а не каждую отдельную консультацию.

Основные правила:

- один Review на пару клиент–специалист;
- наличие подтверждённо успешной консультации для первоначального создания;
- независимость права на отзыв от простого статуса Booking.CONFIRMED;
- возможность редактирования rating и comment;
- сохранение исторической eligibilityBooking;
- защита уникальности средствами PostgreSQL;
- расчёт рейтинга по актуальным отзывам;
- отдельная ответственность Outcome за подтверждение факта проведения консультации.

**Статус: DRAFT — бизнес-модель согласована; открытые детали требуют отдельного решения перед реализацией.**
