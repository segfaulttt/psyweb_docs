## Overview

This document defines the approved MVP model of the Review domain.

Review functionality is currently target/backlog functionality and is not yet implemented in `PsyWeb/main`.

A Review represents feedback from one Client about one Specialist after at least one consultation between them has been conclusively resolved as having occurred.

The Review belongs to the relationship:

```text
Client + Specialist
```

rather than to one particular Booking.

---

# Core Concept

A Client may create a Review for a Specialist when there exists at least one historical consultation for that Client-Specialist pair whose SessionOutcome has been finalized as:

```text
resolutionStatus = RESOLVED
finalOutcome = OCCURRED
```

The method by which the SessionOutcome reached `RESOLVED / OCCURRED` does not affect Review eligibility.

Eligible examples include:

```text
CLIENT OCCURRED
+
SPECIALIST OCCURRED
```

or:

```text
one OCCURRED report
+
reporting timeout
```

or:

```text
DISPUTED
+
admin resolution to OCCURRED
```

Review eligibility therefore depends on the final SessionOutcome, not directly on BookingStatus and not on dual confirmation as a separate requirement.

---

# Review Entity

## Target Fields

```text
id
client_id
specialist_id
rating
comment
created_at
updated_at
```

There is no:

```text
booking_id
```

in the target Review entity.

A Review does not represent feedback for one particular Booking.

Historical Booking and SessionOutcome data are used only to determine whether the Client-Specialist relationship is eligible for Review creation.

---

# Business Rules

## 1. Review Eligibility

The first Review may be created when there exists at least one Booking for the same Client and Specialist whose associated SessionOutcome satisfies:

```text
resolutionStatus = RESOLVED
finalOutcome = OCCURRED
```

The following do not create Review eligibility:

```text
Booking without finalized SessionOutcome
SessionOutcome.PENDING
SessionOutcome.DISPUTED
SessionOutcome.UNVERIFIED
SessionOutcome RESOLVED / DID_NOT_OCCUR
```

A CANCELLED Booking does not create eligibility by itself.

If the same Client and Specialist have another historical consultation with:

```text
RESOLVED / OCCURRED
```

that successful consultation is sufficient.

---

## 2. Eligibility Does Not Expire

After the first qualifying:

```text
RESOLVED / OCCURRED
```

SessionOutcome exists for the Client and Specialist, Review eligibility remains valid for the MVP.

The Client may create the Review:

```text
immediately
later
after additional consultations
```

provided that a Review for the same Client and Specialist does not already exist.

Eligibility is derived from historical Booking and SessionOutcome data.

It is not stored as a separate boolean or eligibility table.

---

## 3. One Review Per Client-Specialist Relationship

A Client may have at most one Review for a particular Specialist.

The database invariant is:

```text
UNIQUE(client_id, specialist_id)
```

Multiple consultations between the same Client and Specialist do not create multiple Review records.

---

## 4. Review Ownership

Only the Client who owns the Review may modify it.

A Specialist cannot create or edit a Client's Review.

Administrative moderation, when implemented, is a separate administrative use case and does not transfer Review ownership.

---

## 5. Review Editing

An existing Review may be edited.

Editable fields are:

```text
rating
comment
```

On update:

```text
created_at
```

remains unchanged.

```text
updated_at
```

is updated.

A new completed consultation is not required in order to edit an existing Review.

---

# Review Creation Flow

Target flow:

```text
authenticated Client
→ select Specialist
→ verify that Review(client, specialist) does not already exist
→ verify existence of at least one RESOLVED / OCCURRED SessionOutcome
   for a Booking belonging to the same Client and Specialist
→ validate rating and comment
→ create Review
→ persist Review
```

The Review stores the Client-Specialist relationship.

The qualifying Booking is not stored as `booking_id` in Review.

---

# Review Update Flow

Target flow:

```text
authenticated Client
→ load Review
→ verify Review ownership
→ validate new rating/comment
→ update existing Review
→ preserve created_at
→ update updated_at
```

Update does not perform a new SessionOutcome eligibility check.

The existence of the Review already means that creation eligibility was previously satisfied.

---

# Rating

## Rating Scale

The MVP rating range is:

```text
1..5
```

---

## Specialist Rating

For the MVP, Specialist rating is derived directly from Review data.

The query-time projection consists of:

```text
AVG(review.rating)
COUNT(review.id)
```

There is no persisted or cached:

```text
rating_avg
```

field in Specialist for the MVP.

When a Specialist has no Reviews:

```text
review count = 0
average rating = absent / null
```

The presentation layer may display the average rounded to one decimal place.

Example:

```text
4.666...
→ 4.7
```

The stored Review ratings themselves are not rounded or modified.

---

## Future Optimization

A cached rating or dedicated projection may be introduced later if performance requirements justify it.

Such a cache would be derived data.

Reviews remain the source of truth.

A future optimization must not change the Review ownership or one-per-client-specialist invariant.

---

# Persistence Model

Target Review persistence must enforce:

```text
client_id NOT NULL
specialist_id NOT NULL
rating NOT NULL
created_at NOT NULL
updated_at NOT NULL

rating BETWEEN 1 AND 5

UNIQUE(client_id, specialist_id)
```

`comment` may be nullable.

The target model does not contain:

```text
booking_id
```

---

# Query Patterns

Expected Review queries include:

```text
find Review by client + specialist
find Reviews by specialist
calculate AVG rating for specialist
count Reviews for specialist
paginate Reviews for specialist
```

There is no primary Review query by Booking because Review is not owned by a Booking.

---

# Integration with Other Domains

## Booking / SessionOutcome

Booking history provides the relationship context.

SessionOutcome is the source of truth for whether a consultation occurred.

Review creation requires existence of at least one:

```text
RESOLVED / OCCURRED
```

SessionOutcome for the same Client and Specialist.

Review does not modify Booking or SessionOutcome.

---

## Specialist

A Specialist may receive Reviews from multiple Clients.

The MVP Specialist rating is derived from Reviews at query time.

Specialist does not store `rating_avg` as Review-owned source data.

---

## User

The Client identity stored by Review references User.

Only the Review's Client owner may update the Review.

---

# Current vs Target Boundary

## Current `PsyWeb/main`

Review persistence and ReviewService are not yet implemented.

There is currently no active Review table/entity/service contract in production code.

---

## Approved Target

The approved MVP Review model is:

```text
one Review per Client + Specialist
editable Review
eligibility from historical RESOLVED / OCCURRED SessionOutcome
no booking_id in Review
query-time AVG + COUNT rating
no persisted Specialist.rating_avg
```

Implementation belongs to the corresponding Review feature tasks.

---

# Summary

The Review domain:

```text
belongs to Client + Specialist relationship
requires at least one successful historical consultation
uses final SessionOutcome as eligibility source of truth
allows one Review per Client-Specialist pair
allows the existing Review to be edited
does not store booking_id
does not require dual participant confirmation specifically
does not persist rating_avg in Specialist for MVP
derives Specialist AVG + COUNT from Reviews
```
