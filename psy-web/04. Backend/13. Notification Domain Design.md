
# 13. Проектирование домена Notification

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — целевая архитектура, детали доставки требуют согласования

---

# 1. Назначение документа

Документ описывает архитектуру домена Notification в PsyWeb.

Домен отвечает за информирование пользователей о значимых событиях платформы.

Основные задачи:

- получение информации о бизнес-событиях;
- определение получателей уведомлений;
- создание внутриплатформенных Notification;
- хранение истории уведомлений;
- получение уведомлений пользователем;
- отметка уведомлений как прочитанных;
- подготовка к внешней доставке через email и другие каналы;
- обработка ошибок доставки;
- обеспечение независимости уведомлений от основных бизнес-транзакций.

Notification является вспомогательным доменом.

Он не управляет Reservation, Booking, SessionOutcome, Review или административными состояниями пользователей.

---

# 2. Основная концепция

## 2.1. Notification

Notification представляет системное сообщение, предназначенное конкретному пользователю.

Уведомление возникает в результате значимого события платформы.

Примеры:

- подтверждение консультации;
- отмена консультации;
- истечение Reservation;
- изменение административного статуса специалиста;
- разрешение результата консультации;
- получение нового отзыва.

## 2.2. Источник уведомлений

Уведомления формируются системой.

Пользователь не создаёт произвольные системные Notification напрямую.

## 2.3. Производные данные

Notification не является источником истины о бизнес-событии.

Например:

- источником истины о подтверждении консультации является Booking;
- об отмене Reservation — Reservation;
- о результате консультации — SessionOutcome;
- о созданном отзыве — Review.

Уведомление лишь сообщает о соответствующем изменении.

## 2.4. Независимость

Основной бизнес-сценарий должен оставаться корректным, даже если Notification временно недоступен.

Ошибка отправки уведомления не должна отменять уже законно выполненную бизнес-операцию.

---

# 3. Ответственность домена

Notification владеет:

- сущностью Notification;
- формированием содержимого уведомлений;
- определением получателей;
- состоянием прочтения;
- операциями получения уведомлений;
- механизмами доставки, если они реализованы;
- обработкой ошибок доставки.

Остальные домены отвечают за собственные бизнес-события.

| Модуль | Ответственность |
|---|---|
| Booking | Reservation и Booking |
| Specialist | Профиль и состояние специалиста |
| Outcome | Результат консультации |
| Review | Отзывы |
| Admin | Административные решения |
| Chat | Сообщения, будущая функциональность |
| Notification | Уведомления получателей |

Notification не изменяет бизнес-состояние модулей-источников.

---

# 4. Архитектурный подход

## 4.1. Event-driven взаимодействие

Целевая архитектура предусматривает событийное взаимодействие между бизнес-модулями и Notification.

Концептуальная последовательность:

```text
Бизнес-операция
    ↓
Изменение доменного состояния
    ↓
Успешный COMMIT
    ↓
Публикация или обработка события
    ↓
Notification
    ↓
Создание уведомления
    ↓
Доставка пользователю
```

## 4.2. Модульный монолит

PsyWeb является модульным монолитом.

Для реализации событийного взаимодействия не требуется отдельный микросервис Notification.

## 4.3. Message broker

RabbitMQ, Kafka или другой брокер сообщений не является обязательной частью MVP.

Его внедрение допускается в будущем при наличии соответствующих требований.

## 4.4. Асинхронная обработка

Обработка уведомлений может выполняться асинхронно.

Однако механизм асинхронности должен учитывать границы транзакций PostgreSQL.

## 4.5. Eventual consistency

Для Notification допускается eventual consistency.

Между фиксацией Booking и появлением соответствующего уведомления может существовать небольшая задержка.

---

# 5. Разделение бизнес-события и уведомления

## 5.1. Domain Event

Domain Event сообщает о произошедшем изменении предметной области.

Например:

`BookingConfirmed`

## 5.2. Notification

Notification представляет информацию, подготовленную для конкретного получателя.

Один Domain Event может привести:

- к одному Notification;
- к нескольким Notification;
- к отсутствию Notification, если событие не требует уведомления.

## 5.3. Пример

Событие:

`BookingConfirmed`

Возможные получатели:

- клиент;
- специалист.

Notification создаёт отдельное уведомление для каждого получателя.

## 5.4. Разделение ответственности

Booking определяет, что консультация подтверждена.

Notification определяет, кому и каким образом сообщить об этом.

---

# 6. События Reservation

Reservation имеет отдельный жизненный цикл до создания Booking.

Поэтому события Reservation и Booking не должны смешиваться.

## 6.1. ReservationCreated

Reservation успешно создана.

Существует временное удержание консультации.

Возможное назначение уведомления:

- информация клиенту о необходимости подтвердить запись;
- отображение срока подтверждения.

Для MVP необходимость отдельного сохранённого Notification на каждую Reservation должна оцениваться с учётом короткого TTL.

Само создание события не означает обязательную отправку email.

## 6.2. ReservationCancelled

ACTIVE Reservation отменена.

Событие может содержать:

- reservationId;
- clientId;
- specialistId;
- cancellationInitiator;
- cancellationReason;
- occurredAt.

## 6.3. ReservationExpired

TTL Reservation истёк, и состояние было переведено в EXPIRED.

Событие должно отражать состоявшийся переход состояния.

Нельзя считать Reservation истёкшей только потому, что наступило expiresAt, если переход ещё не был зафиксирован.

## 6.4. Административная отмена

При административной блокировке специалиста его ACTIVE Reservation немедленно отменяются.

Соответствующие события должны сохранять информацию о том, что инициатором является ADMIN.

Notification не выполняет такую отмену самостоятельно.

---

# 7. События Booking

## 7.1. BookingConfirmed

Reservation успешно подтверждена, создана Booking.

Возможные получатели:

- клиент;
- специалист.

Событие должно содержать идентификаторы, необходимые для формирования уведомления.

## 7.2. BookingCancelled

Подтверждённая Booking отменена.

Событие должно различать инициатора отмены.

Например:

- CLIENT;
- SPECIALIST;
- ADMIN, если соответствующий сценарий будет предусмотрен.

## 7.3. Поздняя отмена

Поздняя отмена не является отдельным статусом Booking.

При необходимости информация о поздней отмене может быть передана в событии или получена из исторических данных.

## 7.4. Завершение запланированного времени

Достижение sessionEnd не означает автоматически успешное проведение консультации.

Поэтому старое событие AppointmentCompleted не должно публиковаться только на основании окончания времени.

## 7.5. Отсутствие на консультации

Событие NoShowRecorded из прежней модели не должно означать окончательно установленный факт отсутствия стороны без правил SessionOutcome.

Такие ситуации обрабатываются доменом Outcome.

---

# 8. События Outcome

## 8.1. Назначение

Outcome устанавливает результат консультации на основании утверждённого процесса подтверждения.

## 8.2. Возможные события

Концептуально:

- SessionOutcomeReportSubmitted;
- SessionOutcomeResolved;
- SessionOutcomeDisputed.

Окончательный набор событий согласуется с Outcome Domain Design.

## 8.3. Подтверждённое проведение

Уведомление об успешно проведённой консультации может формироваться после разрешения SessionOutcome.

## 8.4. Спор

При возникновении противоречивых заявлений может потребоваться уведомление администратора или участников.

Политика получателей определяется отдельно.

## 8.5. Отсутствие подтверждения

Если результат остался непроверенным, Notification не должен представлять консультацию как успешно проведённую.

---

# 9. События Specialist и Admin

## 9.1. SpecialistApproved

Специалист прошёл модерацию.

Уведомление может информировать о результате рассмотрения.

## 9.2. SpecialistRejected

Заявка специалиста отклонена.

При необходимости указывается причина, допустимая для раскрытия получателю.

## 9.3. SpecialistBlocked

Специалист подвергнут административной блокировке.

Notification может информировать его об ограничении.

## 9.4. SpecialistBookingAccessRestored

Право принимать записи восстановлено явной административной операцией.

Одобрение специалиста само по себе не снимает отдельную блокировку bookingAllowed.

## 9.5. Ограничение

Notification не изменяет:

- User.status;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

Он отражает уже выполненное административное действие.

---

# 10. События Review

## 10.1. ReviewCreated

Клиент создал Review специалисту.

Возможный получатель — специалист.

## 10.2. ReviewUpdated

Клиент изменил существующий Review.

Необходимость отдельного уведомления о редактировании определяется продуктовой политикой.

## 10.3. Уникальность Review

Один клиент может иметь только один Review на одного специалиста.

Notification не должен предполагать существование отдельного Review на каждую Booking.

## 10.4. Право на Review

Право на создание отзыва определяется Review и Outcome.

Notification не участвует в проверке eligibility.

---

# 11. События Chat

**Статус:** будущая функциональность.

Возможное событие:

`MessageSent`

При реализации Chat оно может использоваться для:

- внутриплатформенного уведомления;
- push-уведомления;
- обновления интерфейса в реальном времени.

Сам Chat остаётся владельцем сообщений.

Notification не хранит историю переписки вместо Chat.

---

# 12. Модель Notification

## 12.1. Основные поля

Целевая сущность Notification содержит:

| Поле | Назначение |
|---|---|
| id | Идентификатор уведомления |
| recipientId | Получатель |
| type | Тип уведомления |
| payload | Данные для формирования содержимого |
| createdAt | Время создания |
| readAt | Время прочтения |

## 12.2. recipientId

Notification принадлежит одному пользователю.

Один бизнес-event может сформировать несколько Notification с разными recipientId.

## 12.3. type

Тип позволяет определить назначение уведомления и правила отображения.

Примеры:

- BOOKING_CONFIRMED;
- BOOKING_CANCELLED;
- RESERVATION_EXPIRED;
- SPECIALIST_APPROVED;
- SPECIALIST_BLOCKED;
- REVIEW_CREATED.

Это примеры, а не окончательное перечисление.

## 12.4. payload

Payload содержит данные, необходимые для отображения уведомления.

Не следует помещать в него чувствительные сведения, которые не нужны получателю.

В целевом DDL предусмотрен JSONB.

## 12.5. createdAt

Время создания Notification.

Оно не обязательно совпадает с временем возникновения исходного бизнес-события.

## 12.6. readAt

Время, когда пользователь отметил уведомление как прочитанное.

NULL означает отсутствие зафиксированного прочтения.

---

# 13. Состояние прочтения

## 13.1. Логическая модель

Вместо обязательного поля status со значениями UNREAD и READ используется readAt.

## 13.2. Непрочитанное уведомление

`readAt IS NULL`

## 13.3. Прочитанное уведомление

`readAt IS NOT NULL`

## 13.4. Отметка прочтения

Операция должна:

1. Проверить идентичность пользователя.
2. Найти Notification.
3. Проверить принадлежность recipientId.
4. Если readAt уже установлен, не создавать противоречивое состояние.
5. Иначе установить readAt.
6. Сохранить изменение.

## 13.5. Идемпотентность

Повторная отметка уведомления как прочитанного не должна приводить к ошибке только потому, что оно уже прочитано.

## 13.6. Отдельность доставки

readAt не означает успешную доставку через email или push.

Пользователь может прочитать in-app Notification независимо от состояния внешних каналов.

---

# 14. Внутриплатформенные уведомления

## 14.1. Основной канал

Для MVP базовым каналом может быть хранение и отображение in-app Notification.

## 14.2. Получение уведомлений

Концептуальный контракт:

```text
getNotifications(
    authenticatedRecipientId,
    pagination
)
```

## 14.3. Отметка прочтения

```text
markAsRead(
    notificationId,
    authenticatedRecipientId
)
```

## 14.4. Авторизация

Пользователь может получать и отмечать прочитанными только собственные уведомления.

recipientId из запроса не должен заменять идентичность, установленную SecurityContext.

## 14.5. Пагинация

Список Notification должен поддерживать пагинацию.

## 14.6. Сортировка

Рекомендуемая сортировка:

`createdAt DESC, id DESC`

## 14.7. Непрочитанные уведомления

Количество непрочитанных уведомлений может вычисляться по условию:

`recipientId = currentUser AND readAt IS NULL`

Дополнительный индекс рассматривается после анализа запросов.

---

# 15. Внешние каналы доставки

## 15.1. Возможные каналы

Архитектура предусматривает расширение на:

- email;
- push;
- WebSocket;
- другие каналы при необходимости.

## 15.2. In-app и external delivery

Внутриплатформенное Notification и попытка отправки через внешний канал представляют разные аспекты системы.

## 15.3. Email

Email может использоваться для важных уведомлений о консультациях и состоянии аккаунта.

Конкретный набор email-событий определяется отдельно.

## 15.4. Push

Push-уведомления могут быть добавлены при появлении соответствующего клиентского приложения и инфраструктуры.

## 15.5. WebSocket

WebSocket может использоваться для оперативной доставки обновлений интерфейсу.

Он не заменяет долговременное хранение Notification.

## 15.6. Отказ канала

Ошибка внешней доставки не должна автоматически удалять внутриплатформенное Notification.

---

# 16. NotificationDelivery

## 16.1. Статус модели

NotificationDelivery является возможным будущим расширением.

Она не обязательна для первоначального in-app MVP.

## 16.2. Назначение

Модель может хранить состояние доставки конкретного Notification через выбранный канал.

## 16.3. Возможные данные

- notificationId;
- channel;
- deliveryStatus;
- attempts;
- lastAttemptAt;
- deliveredAt;
- failureReason.

## 16.4. Разделение состояний

Состояние внешней доставки не должно смешиваться с readAt.

Например, email может быть отправлен, но пользователь ещё не прочитал уведомление в интерфейсе.

## 16.5. Открытые детали

До реализации необходимо определить:

- набор deliveryStatus;
- допустимое количество попыток;
- правила повторной отправки;
- обработку окончательных ошибок;
- сроки хранения истории доставок.

# 17. Публикация событий и транзакции

## 17.1. Основной принцип

Notification не должен становиться причиной частичного завершения или отката корректной бизнес-операции из-за ошибки внешней доставки.

## 17.2. Публикация до COMMIT

Нельзя выполнять необратимое внешнее действие на основании бизнес-события, если исходная транзакция ещё может откатиться.

## 17.3. Обработка после COMMIT

Простейший вариант для модульного монолита — обработка события после успешного COMMIT.

Он позволяет отделить жизненный цикл уведомления от основной бизнес-транзакции.

## 17.4. Ограничение post-commit обработки

Простая публикация после COMMIT не гарантирует доставку события.

Например, приложение может завершиться между фиксацией Booking и обработкой Notification.

## 17.5. Transactional outbox

Если требуется гарантировать сохранение намерения отправить уведомление, может использоваться transactional outbox.

В этом случае:

1. Основной модуль изменяет бизнес-состояние.
2. В той же транзакции сохраняется OutboxEvent.
3. Выполняется COMMIT.
4. Отдельный обработчик читает OutboxEvent.
5. Notification формируется или доставляется.
6. Обработчик отмечает результат обработки.

## 17.6. Граница ответственности

Outbox обеспечивает надёжную передачу события, но сам по себе не гарантирует однократное физическое выполнение внешнего действия.

Для защиты от повторов потребуются идемпотентность и ключи дедупликации.

## 17.7. Решение для MVP

Обязательное применение transactional outbox ещё не утверждено.

Перед реализацией необходимо выбрать между:

- простой post-commit обработкой с допустимым риском потери уведомления;
- надёжной доставкой через transactional outbox.

Этот выбор должен учитывать требования к уведомлениям о подтверждении и отмене консультаций.

---

# 18. Надёжность и повторная обработка

## 18.1. Eventual consistency

Создание и доставка Notification могут выполняться после завершения основной операции.

## 18.2. Повторная обработка

При ошибке обработчик может повторить операцию.

## 18.3. Дубликаты

При асинхронной доставке одно событие может быть обработано более одного раза.

Поэтому необходимо предусмотреть защиту от нежелательных дубликатов.

## 18.4. Идемпотентность

Возможная стратегия — использовать стабильный eventId для идентификации исходного события.

Если обработчик уже создал соответствующее Notification для данного получателя, повторная обработка не должна создавать дубликат без отдельной причины.

## 18.5. Retry

Для внешних каналов может применяться повторная отправка.

Параметры retry определяются отдельно.

## 18.6. Dead-letter

При внедрении message broker может использоваться dead-letter механизм.

Для текущего модульного монолита брокер не обязателен.

## 18.7. Логирование

Ошибки обработки уведомлений должны фиксироваться для диагностики.

Нельзя безусловно скрывать все ошибки, делая сбои невидимыми для эксплуатации системы.

---

# 19. Формирование содержимого

## 19.1. Шаблоны

Содержимое уведомления определяется его типом и данными payload.

## 19.2. Локализация

В будущем может поддерживаться формирование текста на выбранном пользователем языке.

## 19.3. Изменяемые данные

Нельзя бездумно полагаться на текущие значения связанных сущностей, если для уведомления важны исторические условия.

Например, после изменения ServiceOffering уведомление о ранее подтверждённой Booking должно использовать согласованные исторические данные.

## 19.4. Ссылки на сущности

Notification может содержать идентификаторы связанных бизнес-объектов.

Доступ к ним при открытии из интерфейса всё равно должен проверяться соответствующим модулем.

## 19.5. Персональные данные

Payload должен содержать только необходимую информацию.

Не следует включать подробности консультаций или чувствительные сведения без отдельной потребности и правил доступа.

---

# 20. Интеграция с Booking

## 20.1. Подтверждение

После успешного создания Booking может формироваться BookingConfirmed.

## 20.2. Отмена

После допустимой отмены Booking может формироваться BookingCancelled.

## 20.3. Reservation TTL

После перехода Reservation в EXPIRED может формироваться ReservationExpired.

## 20.4. Конкурентность

Notification должен отражать уже установленный результат конкурентной операции.

Если подтверждение проиграло истечению Reservation, нельзя отправлять уведомление об успешной Booking.

## 20.5. Административная блокировка

При блокировке специалиста все ACTIVE Reservation отменяются атомарно.

Уведомления об отмене должны формироваться на основании зафиксированных результатов операции.

## 20.6. История

Удаление ScheduleOccupancy после occupiedUntil не означает отмену Booking и само по себе не требует уведомления о таком удалении.

---

# 21. Интеграция с Outcome

## 21.1. Независимость

Outcome определяет, состоялась ли консультация.

Notification только информирует о результате.

## 21.2. Двустороннее подтверждение

Нельзя отправлять уведомление об окончательно подтверждённом успешном проведении, пока результат не разрешён по правилам Outcome.

## 21.3. Спор

При споре возможны отдельные уведомления участникам или администратору.

Политика получателей должна соответствовать правилам конфиденциальности.

## 21.4. Отсутствие ответов

Если ни одна сторона не ответила, Notification не должен самостоятельно устанавливать результат OCCURRED.

---

# 22. Интеграция с Review

## 22.1. Создание

ReviewCreated может формировать уведомление специалисту.

## 22.2. Редактирование

ReviewUpdated может использоваться при необходимости.

## 22.3. Право на отзыв

Notification не решает, имеет ли клиент право создать Review.

## 22.4. Историческая модель

Повторные консультации одной пары клиент–специалист не приводят к созданию новых Review автоматически.

---

# 23. Авторизация и безопасность

## 23.1. Доступ к уведомлениям

Пользователь может получать только собственные Notification.

## 23.2. Изменение readAt

Отметить уведомление прочитанным может его получатель.

## 23.3. Данные payload

Содержимое не должно раскрывать информацию пользователю без соответствующих полномочий.

## 23.4. Внешняя доставка

Email и push должны направляться только по адресам и устройствам, связанным с соответствующим получателем согласно утверждённой политике.

## 23.5. Проверка доступа к бизнес-объекту

Переход по ссылке из Notification не отменяет обычную авторизацию на просмотр связанной Booking, Review или другого объекта.

---

# 24. Обработка ошибок

## 24.1. Ошибки чтения

Попытка получить чужое Notification должна завершаться отказом.

## 24.2. Несуществующее Notification

Система возвращает предусмотренную предметную ошибку.

## 24.3. Ошибки формирования

Некорректное событие или payload должны фиксироваться для диагностики.

## 24.4. Ошибки доставки

Неуспешная внешняя доставка не должна изменять подтверждённые состояния Reservation или Booking.

## 24.5. Транзакционные ошибки

Ошибки сохранения Notification обрабатываются в транзакции самого Notification.

В зависимости от выбранной архитектуры доставки событие может быть повторно обработано.

## 24.6. Централизованная обработка

HTTP-ошибки преобразуются через общую Exception Handling Strategy.

---

# 25. Производительность

## 25.1. Асинхронная обработка

Тяжёлая доставка не должна увеличивать время удержания критических блокировок Booking.

## 25.2. Пагинация

История Notification загружается постранично.

## 25.3. Индексы

В целевой схеме предусмотрен индекс:

`(recipient_id, created_at DESC)`

Дополнительные индексы добавляются после анализа реальных запросов.

## 25.4. Очереди

При росте нагрузки может быть введена очередь обработки.

## 25.5. Отказоустойчивость

Механизм доставки должен учитывать временную недоступность внешних провайдеров.

---

# 26. Тестирование

## 26.1. Создание Notification

Проверяются:

- корректный получатель;
- правильный type;
- payload;
- createdAt;
- начальное значение readAt.

## 26.2. Прочтение

Проверяются:

- отметка собственного Notification;
- повторная отметка;
- отказ при попытке изменить чужое Notification;
- получение непрочитанных уведомлений.

## 26.3. События Booking

Проверяются:

- BookingConfirmed;
- BookingCancelled;
- ReservationCancelled;
- ReservationExpired.

## 26.4. Административные события

Проверяется создание уведомлений после успешной блокировки специалиста и отмены ACTIVE Reservation.

## 26.5. Outcome

Проверяется отсутствие ложных уведомлений об успешно проведённой консультации до разрешения SessionOutcome.

## 26.6. Rollback

При откате исходной бизнес-операции не должно возникать внешнего уведомления о несуществующем результате.

## 26.7. Retry

Если реализована повторная обработка, проверяются:

- временная ошибка;
- успешный повтор;
- отсутствие нежелательных дубликатов.

## 26.8. Transactional outbox

Если будет выбран outbox, необходимы интеграционные тесты:

- атомарного сохранения бизнес-состояния и OutboxEvent;
- повторной обработки;
- восстановления после сбоя;
- конкурентных обработчиков.

---

# 27. Архитектурные запреты

1. Notification не изменяет Booking и Reservation.
2. Notification не устанавливает SessionOutcome.
3. Notification не определяет право на Review.
4. Нельзя отправлять необратимое внешнее сообщение до гарантированного подтверждения бизнес-результата.
5. Ошибка email не должна отменять подтверждённую Booking.
6. readAt не используется как статус внешней доставки.
7. Нельзя считать простую post-commit обработку гарантированной доставкой.
8. Нельзя предполагать, что асинхронное событие будет обработано ровно один раз.
9. Нельзя хранить избыточные чувствительные данные в payload.
10. Нельзя предоставлять доступ к чужим Notification.
11. Нельзя трактовать окончание запланированного времени как подтверждённое успешное проведение консультации.
12. Нельзя связывать удаление Occupancy с обязательным удалением Notification.
13. Нельзя требовать обязательный message broker без подтверждённой необходимости.

Необходимо определить, какие события обязательно создают in-app Notification.

## 28.2. Внешние каналы

Требуется выбрать набор каналов, реализуемых в MVP.

Необходимо решить, используется ли transactional outbox с самого начала.

## 28.4. Дедупликация

Требуется определить способ связывания Notification с исходным eventId.

## 28.5. Повторная доставка

Нужно согласовать:

- retry;
- интервалы;
- максимальное количество попыток;
- обработку окончательной ошибки.

## 28.6. История уведомлений

Требуется определить срок хранения Notification и правила удаления.

## 28.7. Содержимое

Необходимо согласовать окончательные шаблоны уведомлений и требования к локализации.

## 28.8. Outcome

Окончательный перечень событий должен соответствовать согласованной модели SessionOutcome.

# 29. Итог

Notification в PsyWeb является самостоятельным вспомогательным модулем, который информирует пользователей о значимых бизнес-событиях.

Основные принципы:

- события исходят из модулей-владельцев бизнес-состояния;
- Notification не изменяет предметные результаты;
- уведомления являются производными данными;
- обработка допускает eventual consistency;
- внешняя доставка не должна блокировать критические бизнес-транзакции;
- readAt отражает прочтение, а не доставку;
- поддержка разных каналов возможна без изменения основных доменов;
- message broker не обязателен для модульного монолита;
- надёжная доставка может быть реализована через transactional outbox;
- окончательная стратегия доставки должна быть утверждена до реализации.

**Статус: DRAFT — целевая архитектура согласована на концептуальном уровне, детали доставки и состава уведомлений MVP остаются открытыми.**
