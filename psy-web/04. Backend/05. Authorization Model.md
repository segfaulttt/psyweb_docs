## Overview

This section defines the authorization model of the PsyWeb backend system. Authorization is responsible for controlling access to resources and operations after a user has been authenticated.

The system uses a combination of role-based access control (RBAC) and ownership-based validation at the service layer.

---

# Authorization Strategy

The system enforces authorization on two levels:

## 1. Infrastructure level (Spring Security)

- Endpoint access control based on user roles
- Request filtering before reaching controllers

## 2. Application level (Service layer)

- Ownership validation
- Business rule enforcement
- Resource-level access control

---

# Role Model

The system defines three primary roles:

## CLIENT

- Can browse specialists
- Can create bookings
- Can manage own bookings
- Can leave reviews after completed appointments

## SPECIALIST

- Can manage profile
- Can create and manage availability slots
- Can manage services
- Can view bookings related to themselves

## ADMIN

- Can manage specialist verification
- Can moderate users
- Has access to system-level operations

---

# HTTP-Level Authorization (Spring Security)

Access control is enforced at endpoint level using role restrictions.

Examples:

- CLIENT endpoints:
    - booking creation
    - booking cancellation (own bookings only)
    - review creation
- SPECIALIST endpoints:
    - slot management
    - service management
    - viewing incoming bookings
- ADMIN endpoints:
    - user management
    - specialist verification
    - system moderation

---

# Authorization Flow

```
Request → JWT Validation → Role Extraction → Endpoint Authorization → Controller Execution
```

---

# HTTP Status Codes

## 401 Unauthorized

Returned when:

- JWT token is missing
- JWT token is invalid
- JWT token is expired

At this stage, user is not authenticated.

---

## 403 Forbidden

Returned when:

- user is authenticated
- but does not have required role
- or lacks permission for specific resource

---

# Ownership-Based Authorization

Role-based access is not sufficient for business operations. The system also enforces ownership rules.

Examples:

## Booking access

- CLIENT can access only their own bookings
- SPECIALIST can access only bookings assigned to them

## Slot access

- SPECIALIST can only modify their own availability slots

## Review access

- CLIENT can only create reviews for their own completed bookings

---

# Enforcement Location

## 1. Controller layer

- minimal checks (role-based annotations if used)

## 2. Service layer (primary enforcement point)

- ownership validation
- cross-entity access validation
- business rule enforcement

---

# Key Design Rules

## 1. RBAC is not sufficient alone

Role checks define access scope, but do not guarantee resource ownership.

---

## 2. Service layer is the final authority

All sensitive authorization decisions must be validated in service methods.

---

## 3. Repository layer is authorization-agnostic

Repositories must never enforce access rules.

---

## 4. SecurityContext is the identity source

All authorization decisions rely on authenticated user identity extracted from JWT.

---

# Booking-Specific Authorization Rules

Booking module has strict rules:

- CLIENT can only create bookings for themselves
- CLIENT can only cancel their own bookings
- SPECIALIST can only view bookings assigned to them
- Only COMPLETED bookings are eligible for review creation

---

# Summary

The authorization model combines:

- role-based access control at infrastructure level
- ownership validation at service level
- strict separation of authentication and authorization concerns
- business-rule-driven access control for booking operations
