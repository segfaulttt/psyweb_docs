
# 05. Модель авторизации (Authorization Model)

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**Безопасность:** Spring Security + JWT  
**Статус:** DRAFT — целевая модель согласована, реализация выполняется поэтапно

---

# 1. Назначение документа

Документ описывает архитектуру авторизации backend PsyWeb.

Авторизация определяет, имеет ли пользователь право выполнить конкретную операцию.

Она учитывает:

- UserRole;
- актуальный UserStatus;
- модерационный статус специалиста;
- отдельное разрешение на бронирование;
- принадлежность ресурса;
- участие пользователя в консультации;
- текущее состояние бизнес-объекта;
- временные и административные ограничения.

PsyWeb разделяет:

1. Authentication.
2. Account eligibility.
3. Role-based authorization.
4. Resource ownership and participation.
5. Specialist professional eligibility.
6. Specialist booking eligibility.
7. Domain-state validation.

Эти проверки дополняют друг друга.

Ни одна из них не заменяет остальные.

---

# 2. Состояние реализации

В исходной реализации PsyWeb уже присутствуют:

- UserRole;
- UserStatus.ACTIVE / BLOCKED;
- UserService.getActiveUser(...);
- SpecialistStatus;
- Specialist.isEligible();
- SpecialistService.getEligibleSpecialist(...);
- отдельные проверки принадлежности Reservation;
- доменные проверки переходов состояний.

При этом полная инфраструктура JWT, Spring Security и централизованной авторизации HTTP-запросов в исходной документации отмечена как нереализованная.

Поэтому документ различает:

- существующую предметную логику;
- утверждённую целевую архитектуру;
- правила, которые ещё предстоит реализовать.

Наличие правила в этом документе не означает, что соответствующий механизм уже реализован в актуальной ветке приложения.

---

# 3. Уровни авторизации

## 3.1. Security Layer

Spring Security отвечает за общие условия допуска к защищённым запросам:

- наличие аутентификации;
- проверку JWT;
- получение текущего User;
- проверку UserStatus.ACTIVE;
- определение UserRole;
- создание Authentication;
- заполнение SecurityContext;
- проверку общих ролевых ограничений.

Этот уровень не содержит бизнес-правил Reservation, Booking, Schedule или Outcome.

## 3.2. Application Service Layer

Прикладные сервисы проверяют права, для которых необходим доступ к предметным данным.

Например:

- принадлежность Reservation клиенту;
- принадлежность Schedule специалисту;
- участие специалиста в Booking;
- допуск специалиста к бронированию;
- полномочия администратора на конкретную операцию;
- право клиента создать Review.

Прикладные сервисы также обеспечивают необходимую транзакционную координацию проверок.

## 3.3. Domain Layer

Доменный слой отвечает за инварианты и допустимые переходы состояний.

Например, клиент может быть уполномочен подтверждать собственную Reservation, но подтверждение невозможно, если её состояние EXPIRED.

Это нарушение бизнес-предусловия, а не ошибка аутентификации.

## 3.4. Database Layer

PostgreSQL обеспечивает ограничения целостности и конкурентных изменений.

База данных не заменяет проверки полномочий пользователя.

Например, UNIQUE и exclusion constraints защищают от конфликтующих записей, но не определяют право конкретного клиента создавать Reservation.

---

# 4. Ролевая модель

В User Domain определены роли:

```text
CLIENT
SPECIALIST
ADMIN
```

Каждый пользователь обладает ролью, определяющей тип его участия в системе.

Роль сама по себе не гарантирует право на любую операцию.

---

# 5. CLIENT

## 5.1. Общие возможности

Авторизованный клиент с ACTIVE аккаунтом может выполнять разрешённые клиентские операции.

К ним относятся:

- просмотр публичных профилей специалистов;
- просмотр доступных услуг;
- получение доступного времени;
- создание собственных Reservation;
- подтверждение собственных Reservation;
- отмена собственных ACTIVE Reservation;
- отмена собственных CONFIRMED Booking по установленным правилам;
- просмотр собственных консультаций;
- отправка отчёта о результате собственной консультации;
- создание и редактирование разрешённых Review;
- просмотр собственных Notification.

## 5.2. Принадлежность

Клиент не получает право обращаться с чужой Reservation только потому, что имеет роль CLIENT.

## 5.3. Создание Reservation

Для создания Reservation необходимы:

- активная учётная запись клиента;
- соответствующая роль;
- существующая активная ServiceOffering;
- эффективный допуск специалиста;
- соблюдение правил Availability;
- отсутствие конфликтующей Occupancy.

## 5.4. Подтверждение Reservation

Клиент может подтверждать только собственную ACTIVE Reservation.

Дополнительно проверяются:

- TTL;
- эффективный допуск специалиста;
- наличие корректной Occupancy;
- другие утверждённые бизнес-ограничения.

## 5.5. Отмена Booking

Клиент может отменить собственную CONFIRMED Booking до начала консультации.

После sessionStart обычная клиентская отмена запрещена.

Поздняя отмена до начала разрешена и фиксируется без отдельного BookingStatus.

## 5.6. Review

Создание Review разрешается при наличии хотя бы одной подтверждённо успешной консультации с соответствующим специалистом.

Клиент может редактировать собственный Review.

Повторное создание Review тому же специалисту запрещено.

---

# 6. SPECIALIST

## 6.1. Аутентификация

UserRole.SPECIALIST не означает автоматического профессионального допуска.

Специалист может войти в систему, если UserStatus.ACTIVE, независимо от своего модерационного статуса.

## 6.2. Профессиональные операции

К профессиональным операциям относятся:

- управление ServiceOffering;
- управление собственным рабочим расписанием;
- просмотр назначенных консультаций;
- участие в подтверждении результата консультации;
- выполнение других функций, требующих одобренного специалиста.

Точные требования к статусу для каждой операции определяются соответствующим доменом.

## 6.3. Профессиональный допуск

Для операций, требующих профессиональной пригодности, необходимы:

```text
UserRole.SPECIALIST

AND UserStatus.ACTIVE

AND Specialist.approvalStatus = APPROVED
```

## 6.4. Неодобренные специалисты

Специалист со статусом PENDING, REJECTED или SUSPENDED не получает профессиональных полномочий.

При этом он может сохранять ограниченный доступ к собственному аккаунту, если UserStatus.ACTIVE.

Например:

- просмотр профиля;
- просмотр результата модерации;
- выполнение явно разрешённых действий в рамках повторного рассмотрения.

## 6.5. Принадлежность ресурсов

Специалист может изменять только принадлежащие ему:

- ServiceOffering;
- SpecialistScheduleSettings;
- WeeklyScheduleVersion;
- DateSchedule.

Он не может изменять расписание другого специалиста.

## 6.6. Участие в Booking

Специалист может получать данные консультаций, в которых он участвует.

Право просмотра не означает право произвольно менять состояние Booking.

## 6.7. Ограниченные операции

Конкретные права специалиста на отмену Booking, изменение расписания, участие в Outcome и другие действия регулируются соответствующими доменами.

---

# 7. ADMIN

## 7.1. Назначение

ADMIN выполняет утверждённые административные операции.

## 7.2. Возможности

К ним относятся:

- рассмотрение заявок специалистов;
- одобрение и отклонение;
- административная блокировка;
- восстановление отдельных разрешений;
- просмотр необходимых данных для модерации;
- разрешение споров SessionOutcome;
- другие явно предусмотренные административные операции.

## 7.3. Ограничения

ADMIN не может обходить бизнес-инварианты.

Например:

- нельзя создать вторую Booking из одной Reservation;
- нельзя произвольно изменить результат SessionOutcome;
- нельзя обойти уникальность Review;
- нельзя нарушить согласованный порядок блокировок.

## 7.4. Межмодульные операции

Административные действия выполняются через сервисные контракты модулей-владельцев.

Admin не должен напрямую изменять Repository других модулей.

## 7.5. Аудит

Критические административные действия должны сохранять сведения об инициаторе, времени, причине и результате.

---

# 8. UserStatus

В текущей модели UserStatus определены:

```text
ACTIVE
BLOCKED
```

## 8.1. ACTIVE

Пользователь может проходить дальнейшие проверки роли, принадлежности и предметных ограничений.

## 8.2. BLOCKED

Пользователь не может выполнять защищённые операции.

Наличие JWT, полученного до блокировки, не отменяет это ограничение.

## 8.3. Проверка актуального состояния

Spring Security должен проверять текущий UserStatus при защищённом запросе.

## 8.4. Изменение статуса

Если административное изменение UserStatus приводит к потере допуска специалиста к бронированию, оно должно выполняться по согласованному протоколу BookingAccess.

---

# 9. Модерационный статус специалиста

## 9.1. Текущие значения

Исходная реализация использует SpecialistStatus:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

В целевой модели состояние модерации представлено полем:

`Specialist.approvalStatus`

## 9.2. PENDING

Заявка ожидает рассмотрения.

Профессиональные операции, требующие одобрения, недоступны.

## 9.3. APPROVED

Заявка одобрена.

Профессиональные операции доступны при выполнении остальных требований.

## 9.4. REJECTED

Заявка отклонена.

Профессиональный допуск отсутствует.

## 9.5. SUSPENDED

Профессиональная деятельность специалиста приостановлена.

Профессиональный допуск отсутствует.

## 9.6. Login

Ни один из перечисленных статусов сам по себе не запрещает вход в ACTIVE пользовательский аккаунт.

## 9.7. Номенклатура

При реализации необходимо согласовать использование SpecialistStatus и SpecialistApprovalStatus, чтобы не создавать два независимых источника модерационного состояния.

---

# 10. Профессиональный допуск специалиста

## 10.1. Основное правило

Профессиональный допуск требует:

```text
UserRole.SPECIALIST

AND UserStatus.ACTIVE

AND Specialist.approvalStatus = APPROVED
```

## 10.2. Ответственность

Проверка принадлежит Specialist Domain.

## 10.3. Повторное использование

Другие модули должны использовать согласованный контракт проверки специалиста.

Не следует независимо реализовывать разные варианты professional eligibility в Booking, Schedule и Service.

## 10.4. Отдельное разрешение бронирования

Профессиональный допуск не равнозначен разрешению принимать новые бронирования.

Для бронирования предусмотрена дополнительная административная настройка.

---

# 11. SpecialistBookingAccess

## 11.1. Назначение

SpecialistBookingAccess представляет отдельное административное ограничение права специалиста принимать новые записи.

Основное поле:

`bookingAllowed`

## 11.2. Значение TRUE

Значение TRUE означает отсутствие отдельного ограничения BookingAccess.

При этом специалист всё ещё должен удовлетворять требованиям UserStatus и approvalStatus.

## 11.3. Значение FALSE

Значение FALSE запрещает:

- создание новых Reservation;
- подтверждение существующих ACTIVE Reservation.

## 11.4. Независимость

bookingAllowed не заменяет:

- UserStatus;
- Specialist.approvalStatus;
- UserRole.

## 11.5. Восстановление

Повторное одобрение специалиста не должно автоматически устанавливать bookingAllowed = TRUE.

Для снятия отдельного ограничения требуется явная авторизованная операция.

---

# 12. Эффективный допуск к бронированию

## 12.1. Утверждённое правило

Специалист имеет право принимать новые Reservation и подтверждения при:

```text
UserRole.SPECIALIST

AND UserStatus.ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

## 12.2. Примеры

| UserStatus | approvalStatus | bookingAllowed | Бронирование |
|---|---|---|---|
| ACTIVE | APPROVED | TRUE | Разрешено |
| ACTIVE | APPROVED | FALSE | Запрещено |
| ACTIVE | PENDING | TRUE | Запрещено |
| ACTIVE | REJECTED | TRUE | Запрещено |
| ACTIVE | SUSPENDED | TRUE | Запрещено |
| BLOCKED | APPROVED | TRUE | Запрещено |

## 12.3. Availability

AvailabilityService не должен предлагать бронируемое время специалиста, у которого отсутствует эффективный допуск.

## 12.4. Reservation

Создание Reservation проверяет эффективный допуск внутри критической транзакции.

## 12.5. Confirmation

Подтверждение ACTIVE Reservation также проверяет эффективный допуск.

## 12.6. Изменения допуска

Административная операция, лишающая специалиста допуска, должна одновременно обработать существующие ACTIVE Reservation.

---

# 13. Транзакционная координация BookingAccess

## 13.1. Проблема

Администратор может заблокировать специалиста одновременно с созданием или подтверждением Reservation.

Проверки статуса вне транзакции недостаточно.

## 13.2. Создание Reservation

Операция использует:

`SpecialistBookingAccess FOR SHARE`

До получения календарных advisory locks.

## 13.3. Подтверждение Reservation

Используется:

```text
SpecialistBookingAccess FOR SHARE
    ↓
Reservation FOR UPDATE
```

## 13.4. Административная блокировка

Используется:

```text
SpecialistBookingAccess FOR UPDATE
    ↓
Reservation FOR UPDATE
```

## 13.5. Атомарная отмена

При блокировке все ACTIVE Reservation специалиста отменяются в той же транзакции.

Связанные ScheduleOccupancy удаляются.

## 13.6. Подтверждённые Booking

CONFIRMED Booking сохраняются.

## 13.7. Конкурентное подтверждение

Если подтверждение завершилось раньше административной блокировки, Booking сохраняется.

Если блокировка зафиксирована первой, подтверждение запрещается.

## 13.8. Запрет обхода

Нельзя напрямую изменить UserStatus или approvalStatus так, чтобы специалист потерял допуск, но его ACTIVE Reservation остались без обработки.

---

# 14. Принадлежность ресурсов

## 14.1. Основной принцип

Роль пользователя не определяет принадлежность конкретного ресурса.

При выполнении операции проверяется связь между аутентифицированным пользователем и запрашиваемым объектом.

## 14.2. Reservation

Клиент может:

- создавать собственные Reservation;
- подтверждать собственные Reservation;
- отменять собственные ACTIVE Reservation.

Принадлежность проверяется по clientId.

## 14.3. Booking

Клиент может управлять собственной Booking только в рамках разрешённых переходов.

Специалист может выполнять предусмотренные операции с Booking, где specialistId соответствует его профилю.

## 14.4. Schedule

Специалист может изменять своё расписание.

## 14.5. ServiceOffering

Специалист может управлять принадлежащими ему услугами в пределах своих полномочий.

## 14.6. Review

Клиент может редактировать только собственный Review.

## 14.7. Notification

Пользователь может получать и отмечать прочитанными только собственные Notification.

## 14.8. Outcome

Отправлять отчёт о результате консультации могут только её участники в рамках установленного окна и правил Outcome.

---

# 15. Авторизация Reservation

## 15.1. Создание

Инициатором является аутентифицированный CLIENT.

Проверяются:

- его роль;
- UserStatus.ACTIVE;
- действительность выбранной ServiceOffering;
- эффективный допуск специалиста;
- временные ограничения;
- отсутствие конфликтующей Occupancy.

## 15.2. Подтверждение

Проверяются:

- принадлежность Reservation клиенту;
- статус ACTIVE;
- TTL;
- эффективный допуск специалиста;
- согласованность Occupancy.

## 15.3. Отмена

Клиент может отменить собственную ACTIVE Reservation.

Административная отмена использует отдельный разрешённый сценарий.

## 15.4. Истечение

Expiration Scheduler выполняет системную операцию.

Она не требует пользовательской роли CLIENT, поскольку инициируется доверенным внутренним механизмом.

## 15.5. Запрет повторных переходов

CONFIRMED, CANCELLED и EXPIRED Reservation не могут быть повторно подтверждены или возвращены в ACTIVE.

---

# 16. Авторизация Booking

## 16.1. Просмотр

Клиент и специалист могут просматривать Booking, в которой участвуют, согласно утверждённым правилам.

## 16.2. Отмена клиентом

Клиент может отменить собственную CONFIRMED Booking при:

`now < sessionStart`

## 16.3. Поздняя отмена

Поздняя отмена до начала консультации не лишает клиента права отменить Booking.

Она фиксируется на основании clientCancellationNoticeSnapshot.

## 16.4. Отмена специалистом

Специалист может инициировать отмену собственной Booking через предусмотренный Booking Domain сценарий.

## 16.5. Административные операции

Исключительная административная отмена требует отдельного утверждённого основания и командного контракта.

## 16.6. После начала

Обычная клиентская отмена после sessionStart запрещена.

---

# 17. Авторизация Schedule

## 17.1. Владение

Рабочим расписанием управляет соответствующий специалист.

## 17.2. Объекты

К управляемой конфигурации относятся:

- SpecialistScheduleSettings;
- WeeklyScheduleVersion;
- WeeklyWorkingInterval;
- DateSchedule;
- DateScheduleInterval.

## 17.3. Режимы

Специалист может управлять расписанием в режимах REGULAR и FLOATING по соответствующим правилам.

## 17.4. Существующие обязательства

Изменение расписания не отменяет автоматически ACTIVE Reservation и CONFIRMED Booking.

## 17.5. Бизнес-валидация

Даже уполномоченный специалист не может сохранить некорректные или пересекающиеся рабочие интервалы.

## 17.6. Конкурентность

Операции редактирования расписания используют согласованный календарный протокол блокировок.

---

# 18. Авторизация SessionOutcome

## 18.1. Участники

Отчёт о результате консультации вправе отправить:

- клиент соответствующей Booking;
- специалист соответствующей Booking.

## 18.2. Временное окно

Для MVP установлен период 24 часа после консультации.

## 18.3. Отчёты

Участники независимо сообщают:

- OCCURRED;
- DID_NOT_OCCUR.

При отрицательном результате требуется предусмотренная бизнес-правилами причина.

## 18.4. Споры

При несовместимых ответах возникает спор.

## 18.5. Разрешение

Разрешать спор может уполномоченный ADMIN через контракт Outcome.

## 18.6. Ограничения

Нельзя:

- отправлять отчёт за другого участника;
- разрешать чужой спор без административных полномочий;
- считать консультацию успешно проведённой только по факту окончания времени;
- обходить правила SessionOutcome.

---

# 19. Авторизация Review

## 19.1. Создание

Клиент может создать Review после хотя бы одной подтверждённо успешной консультации с соответствующим специалистом.

## 19.2. Уникальность

Один Review на пару:

`(clientId, specialistId)`

## 19.3. Редактирование

Редактировать Review может только автор.

## 19.4. Повторные консультации

Повторные успешные консультации не позволяют создать второй Review тому же специалисту.

## 19.5. Проверка eligibility

Review использует подтверждённый результат Outcome.

Сама CONFIRMED Booking недостаточна.

## 19.6. Административная модерация

Полномочия на скрытие или удаление Review требуют отдельного решения.

---

# 20. Авторизация административных операций

## 20.1. Роль

Для административных операций требуется ADMIN.

## 20.2. Дополнительные ограничения

Наличие роли ADMIN не заменяет проверку:

- допустимого сценария;
- состояния объекта;
- причин и оснований;
- необходимого аудита.

## 20.3. Модерация специалиста

Администратор выполняет утверждённые переходы approvalStatus.

Если специалист теряет допуск к бронированию, применяется транзакционный протокол обработки ACTIVE Reservation.

## 20.4. Блокировка пользователя

Администратор может изменять UserStatus через соответствующий доменный контракт.

## 20.5. Разрешение споров

Администратор принимает решение через OutcomeResolutionCommand.

## 20.6. Границы модулей

Admin не должен напрямую менять чужие Repository в обход предметных сервисов.

---

# 21. Целевой процесс авторизации запроса

```text
HTTP Request
    ↓
JWT validation
    ↓
Current User lookup
    ↓
Require UserStatus.ACTIVE
    ↓
SecurityContext
    ↓
Role check
    ↓
Controller
    ↓
Application Service
    ↓
Resource ownership / participation
    ↓
Specialist eligibility if required
    ↓
Domain-state validation
    ↓
Transactional business operation
```

Каждый этап отвечает на отдельный вопрос.

| Этап | Вопрос |
|---|---|
| JWT | Кто отправил запрос? |
| UserStatus | Разрешён ли доступ аккаунту? |
| UserRole | Может ли эта категория пользователя выполнять операцию? |
| Ownership | Принадлежит ли ресурс инициатору? |
| Professional eligibility | Допущен ли специалист к профессиональной деятельности? |
| BookingAccess | Может ли специалист принимать бронирования? |
| Domain-state validation | Допустима ли операция в текущем состоянии? |

# 22. Ролевая защита Spring Security

## 22.1. Общий принцип

Spring Security может обеспечивать ролевую защиту HTTP endpoint или методов.

Примеры:

```java
@PreAuthorize("hasRole('CLIENT')")
```

```java
@PreAuthorize("hasRole('SPECIALIST')")
```

```java
@PreAuthorize("hasRole('ADMIN')")
```

## 22.2. Ограничение

Ролевая аннотация не гарантирует принадлежность ресурса.

## 22.3. Проверка внутри сервиса

Например, CLIENT может иметь право вызвать метод подтверждения Reservation, но сервис должен отдельно проверить, что Reservation принадлежит именно этому клиенту.

## 22.4. Текущее состояние

Наличие аннотаций в документе не означает, что method-level security уже реализован.

# 23. Ошибки авторизации

## 23.1. Неаутентифицированный пользователь

Примеры:

- отсутствует необходимый JWT;
- JWT имеет неверную подпись;
- JWT истёк.

Типичная категория HTTP:

`401 Unauthorized`

## 23.2. Недостаточно полномочий

Примеры:

- неправильная роль;
- UserStatus.BLOCKED;
- пользователь пытается изменить чужой ресурс;
- специалист не имеет необходимого допуска.

Типичная категория HTTP:

`403 Forbidden`

Для заблокированного аккаунта точное поведение на границе аутентификации определяется Security-конфигурацией: такой запрос может быть отклонён до создания Authentication.

## 23.3. Предметная ошибка

Примеры:

- Reservation уже EXPIRED;
- Booking уже CANCELLED;
- выбранный интервал занят;
- истёк bookingDeadline;
- неверный переход состояния.

Это не обязательно ошибки авторизации.

Они обрабатываются через соответствующую доменную категорию.

## 23.4. Сокрытие существования ресурсов

Для отдельных чувствительных ресурсов API может намеренно не раскрывать их существование постороннему пользователю.

Такая политика требует отдельного решения в HTTP-контрактах.

# 24. Repository Boundary

## 24.1. Основной принцип

Repository обеспечивает доступ к данным, но не выполняет пользовательскую авторизацию.

## 24.2. Разделение

Авторизация выполняется на уровнях:

- Security;
- Application Service;
- Domain-specific policies.

## 24.3. Ограничение

Нельзя считать, что отсутствие фильтра по clientId в Repository автоматически разрешает любому пользователю изменять возвращённую сущность.

## 24.4. Межмодульные зависимости

Другой модуль не должен напрямую использовать Repository владельца ресурса, чтобы обойти проверку полномочий.

---

# 25. Тестирование

## 25.1. Роли

Проверяются разрешённые и запрещённые операции:

- CLIENT;
- SPECIALIST;
- ADMIN.

## 25.2. UserStatus

Проверяются:

- ACTIVE;
- BLOCKED;
- старый JWT после административной блокировки.

## 25.3. SpecialistStatus

Проверяются:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

## 25.4. BookingAccess

Проверяется, что специалист с:

`approvalStatus = APPROVED`

и

`bookingAllowed = FALSE`

не может принимать новые Reservation.

## 25.5. Ownership

Проверяются:

- подтверждение чужой Reservation;
- отмена чужой Booking;
- изменение чужого Schedule;
- редактирование чужого Review;
- чтение чужих Notification.

## 25.6. Outcome

Проверяются:

- отчёт клиента о собственной консультации;
- отчёт специалиста;
- запрет третьему лицу;
- административное разрешение спора.

## 25.7. Конкурентность

Интеграционные тесты должны проверить:

1. Создание Reservation одновременно с блокировкой специалиста.
2. Подтверждение Reservation одновременно с блокировкой.
3. Изменение UserStatus одновременно с созданием Reservation.
4. Изменение approvalStatus одновременно с подтверждением.
5. Повторную административную блокировку.

## 25.8. PostgreSQL

Конкурентные сценарии проверяются на реальном PostgreSQL, например через Testcontainers.

# 26. Текущая реализация и целевая модель

## 26.1. Отражено в исходном коде на момент предыдущей документации

- UserRole;
- UserStatus.ACTIVE / BLOCKED;
- UserService.getActiveUser(...);

- SpecialistService.getEligibleSpecialist(...);
- отдельные проверки принадлежности;
- доменные инварианты.

## 26.2. Целевая инфраструктура

- JWT Authentication;
- SecurityContext;
- централизованные ролевые проверки;
- method-level security;
- проверки актуального UserStatus;

- отдельный SpecialistBookingAccess;

Актуальное состояние реализации необходимо проверять отдельно по PsyWeb/main.

# 27. Основные инварианты

1. Authentication и Authorization являются разными механизмами.
2. Роль сама по себе не даёт доступа к любому ресурсу.
3. BLOCKED User не может выполнять защищённые операции.
4. Неодобренный специалист не получает профессиональный допуск.
5. Профессиональный допуск не равнозначен разрешению бронирования.
6. BookingAccess не заменяет UserStatus и approvalStatus.
7. Создание и подтверждение Reservation требуют эффективного допуска специалиста.
8. Административная блокировка отменяет все ACTIVE Reservation специалиста атомарно.
9. CONFIRMED Booking при такой блокировке сохраняются.
10. Повторное одобрение специалиста не снимает отдельный bookingAllowed = FALSE.
11. Клиент может управлять только собственными Reservation и Booking.
12. Специалист может управлять только собственным Schedule и ServiceOffering.
13. Участники консультации могут выполнять только предусмотренные операции Outcome.
14. Review может создать только клиент с подтверждённо успешной консультацией.
15. ADMIN не обходит доменные инварианты.
16. Репозитории не принимают решения о пользовательских полномочиях.
17. Бизнес-валидация остаётся необходимой после успешной авторизации.

# 28. Открытые вопросы

## 28.1. Номенклатура статусов специалиста

Требуется окончательно согласовать:

- SpecialistStatus;
- SpecialistApprovalStatus;
- поле approvalStatus.

## 28.2. Права неодобренного специалиста

Необходимо уточнить полный перечень разрешённых действий для:

- PENDING;
- REJECTED;
- SUSPENDED.

## 28.3. Блокировка клиента

Требуется определить последствия блокировки клиентского аккаунта для существующих ACTIVE Reservation и CONFIRMED Booking.

## 28.4. Административные исключения

Необходимо определить точные полномочия на исключительную отмену Booking после начала консультации.

## 28.5. Модерация Review

Нужно согласовать возможность скрытия, удаления и обжалования отзывов.

## 28.6. HTTP-контракты

Точные endpoint, DTO и политика сокрытия существования чужих ресурсов определяются при проектировании API.

## 28.7. Реализация

Нужна отдельная проверка фактического соответствия текущего Spring Security и сервисного слоя целевой модели.

# 29. Итог

Модель авторизации PsyWeb разделяет:

```text
Authentication
    ↓
Current UserStatus
    ↓
UserRole
    ↓
Resource ownership / participation
    ↓
Professional eligibility
    ↓
Booking eligibility if required
    ↓
Domain-state validation
```

Основные принципы:

- Spring Security обеспечивает общую защиту запросов;
- прикладные сервисы проверяют доступ к конкретным ресурсам;
- доменные модели защищают переходы состояний;
- PostgreSQL обеспечивает целостность конкурентных изменений;
- профессиональный допуск специалиста отделён от его права принимать бронирования;
- административные изменения допуска координируются транзакционно;
- подтверждённые Booking сохраняются при административной блокировке;
- право на Review зависит от SessionOutcome;
- полномочия ADMIN не позволяют обходить бизнес-правила.

**Статус: DRAFT — целевая модель согласована, детали отдельных административных полномочий и текущая реализация требуют проверки.**
