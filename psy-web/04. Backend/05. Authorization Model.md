# Authorization Model

## Overview

This document defines the authorization model of the PsyWeb backend.

Authorization is separate from authentication.

Authentication establishes the identity of the caller.

Authorization determines whether that caller may perform a specific operation based on:

- `UserRole`;
- current `UserStatus`;
- `SpecialistStatus`, when professional specialist functionality is involved;
- resource ownership or participation;
- current business state.

PsyWeb combines infrastructure-level authorization with service/domain-level business rules.

---

# Current Implementation Status

The current `PsyWeb/main` does not yet contain the final Spring Security/JWT authorization infrastructure.

There is currently no complete controller/security layer that centrally enforces authenticated roles and ownership for HTTP requests.

However, several authorization and eligibility rules already exist in the domain/service layer.

Implemented examples include:

- `UserService.getActiveUser(...)` requires `UserStatus.ACTIVE`;
- `SpecialistService.getEligibleSpecialist(...)` requires professional specialist eligibility;
- `Specialist.isEligible()` requires:
  - `UserRole.SPECIALIST`;
  - `UserStatus.ACTIVE`;
  - `SpecialistStatus.APPROVED`;
- individual business services already enforce some resource-specific rules, such as Reservation ownership during confirmation.

The remaining Spring Security, authenticated-principal and endpoint authorization behavior described below is target architecture unless explicitly marked as current implementation.

---

# 1. Authorization Layers

The target authorization model uses several complementary layers.

## 1.1 Security Layer

The security layer is responsible for coarse-grained request access such as:

- requiring authentication;
- validating the current authenticated account;
- checking required `UserRole`;
- establishing the authenticated principal.

This layer must not contain domain lifecycle logic.

---

## 1.2 Service Layer

The service layer owns authorization rules that require persisted business data, such as:

- resource ownership;
- resource participation;
- specialist professional eligibility;
- cross-entity access validation;
- business-specific access constraints.

The service layer must not assume that matching a role automatically grants access to a particular resource.

---

## 1.3 Domain Layer

Domain entities enforce valid state transitions and invariants.

A caller may be authorized to attempt an operation while the domain operation itself is still invalid.

For example:

```text
authorized client
+
own Reservation
+
Reservation not ACTIVE
=
authorization may succeed,
business operation still fails
```

Authorization and domain-state validation therefore remain separate concerns.

---

# 2. Role Model

The User domain defines three roles:

```text
CLIENT
SPECIALIST
ADMIN
```

A role describes the type of platform actor.

Role alone is never sufficient to determine access to every operation.

---

## 2.1 CLIENT

Target CLIENT capabilities include:

- working with their own Reservations;
- working with their own Bookings;
- viewing public specialist information;
- participating in consultation-related client workflows;
- performing other client-owned operations defined by their modules.

Protected CLIENT operations require an ACTIVE User account.

Resource-specific operations additionally require ownership or participation where applicable.

---

## 2.2 SPECIALIST

A User with role SPECIALIST is not automatically professionally eligible.

Professional specialist eligibility currently requires:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

This rule is already implemented by the Specialist domain and `SpecialistService`.

Professional operations include functionality such as:

- managing active availability;
- participating as the specialist in Booking workflows;
- other operations explicitly requiring an eligible specialist.

`PENDING`, `REJECTED`, and `SUSPENDED` specialists are not professionally eligible.

They may still retain limited account-level owner or moderation access when their linked User remains ACTIVE.

---

## 2.3 ADMIN

ADMIN represents an administrative platform actor.

Target administrative capabilities include:

- User moderation;
- Specialist moderation;
- dispute resolution;
- explicitly defined system-management workflows.

ADMIN authority does not bypass domain invariants.

Administrative operations must use the owning module's service API rather than directly changing another module's persistence state.

---

# 3. UserStatus

`UserStatus` controls account-level eligibility.

Current values are:

```text
ACTIVE
BLOCKED
```

## ACTIVE

The account is enabled.

An ACTIVE User may proceed to role, ownership and domain-specific authorization checks.

## BLOCKED

The account is disabled from protected platform operations.

A BLOCKED User must not be treated as eligible merely because they still possess an otherwise valid authentication token.

The target security layer therefore validates the current persisted User state for protected requests.

---

# 4. SpecialistStatus

The Specialist domain currently defines:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

These statuses describe professional approval state, not account authentication state.

## PENDING

The specialist is awaiting moderation.

Professional specialist operations are unavailable.

## APPROVED

The specialist passed moderation.

Professional operations are available only when the linked User is also ACTIVE and has role SPECIALIST.

## REJECTED

The approval or resubmission attempt was rejected.

The User account may remain ACTIVE.

Professional specialist operations are unavailable.

## SUSPENDED

A previously APPROVED specialist has been administratively suspended from professional activity.

The User account may remain ACTIVE.

Professional specialist operations are unavailable until reinstatement.

---

# 5. Professional Specialist Eligibility

The implemented eligibility rule is:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

`Specialist.isEligible()` evaluates this rule.

`SpecialistService.getEligibleSpecialist(...)` exposes it as a reusable service-level boundary.

Modules that require an operational specialist should depend on this eligibility boundary rather than duplicating approval checks independently.

---

# 6. Ownership and Participation

Role checks do not establish ownership.

Target resource-level authorization requires the relevant service to verify that the authenticated actor owns or participates in the requested resource.

Examples include:

- a client acting on their own Reservation;
- a client acting on their own Booking;
- a specialist managing their own availability;
- a specialist accessing a Booking in which they participate;
- a participant interacting with their own post-session workflow.

The exact ownership rules belong to the module that owns the resource.

---

# 7. Current Ownership Enforcement

Ownership enforcement is currently only partially implemented because the authenticated HTTP principal/security infrastructure is still backlog work.

Some business-level ownership checks already exist.

For example, Booking confirmation verifies that the Reservation belongs to the supplied client before confirmation continues.

Other endpoint-level ownership rules must not be documented as fully implemented until authenticated-principal integration and the corresponding service contracts are complete.

---

# 8. Target Request Authorization Flow

Once authentication/security infrastructure is implemented, a protected request follows the target flow:

```text
Request
→ JWT validation
→ current User lookup
→ require UserStatus.ACTIVE
→ authenticated principal
→ coarse-grained role authorization
→ Controller
→ service-level ownership / eligibility checks
→ domain-state validation
→ business operation
```

Each stage answers a different question.

```text
JWT validation
→ Is the request authenticated?

UserStatus
→ Is the account currently enabled?

UserRole
→ Is this type of actor allowed to attempt the operation?

SpecialistStatus
→ Is this specialist professionally eligible?

Ownership / participation
→ May this actor access this specific resource?

Domain state
→ Is the operation valid right now?
```

---

# 9. Role-Based Authorization

The target Spring Security layer may enforce coarse role requirements such as:

```java
@PreAuthorize("hasRole('CLIENT')")
```

```java
@PreAuthorize("hasRole('SPECIALIST')")
```

```java
@PreAuthorize("hasRole('ADMIN')")
```

These examples describe the target security boundary.

The current backend does not yet contain the completed method-level security infrastructure.

Role annotations must not replace ownership or business-state validation.

---

# 10. Specialist Authorization

Professional specialist operations require more than `UserRole.SPECIALIST`.

A request requiring professional eligibility must ultimately satisfy:

```text
SPECIALIST role
+
ACTIVE User
+
APPROVED Specialist
```

This requirement must use the reusable Specialist eligibility policy.

The following statuses do not satisfy professional eligibility:

```text
PENDING
REJECTED
SUSPENDED
```

Their permitted account-level or moderation operations must be explicitly defined rather than obtained through professional eligibility.

---

# 11. Administrative Authorization

Administrative authority grants access only to explicitly defined administrative use cases.

A valid orchestration is:

```text
Admin use case
→ owning module service
→ domain transition
→ owning module persistence
```

For example:

```text
Admin
→ SpecialistService
→ Specialist status transition
```

The Admin module must not directly modify `SpecialistRepository` merely because the caller has role ADMIN.

The same ownership principle applies to Booking, Availability, User and future SessionOutcome workflows.

---

# 12. Business-State Validation

Authorization does not replace lifecycle validation.

Examples:

- an authorized client cannot confirm a Reservation that is not confirmable;
- an eligible specialist cannot perform an invalid AvailabilitySlot transition;
- an authorized actor cannot cancel an already terminal entity;
- an administrator cannot force an invalid domain transition by bypassing the owning service.

Business-state failures belong to the domain exception model rather than being automatically treated as authorization failures.

---

# 13. Authorization Failure Categories

The eventual HTTP mapping belongs to the global error-handling/security implementation.

Conceptually, failures remain distinct.

## Unauthenticated

Examples:

- missing required token;
- invalid token;
- expired token.

Target HTTP category:

```text
401 Unauthorized
```

## Authenticated but forbidden

Examples:

- wrong role;
- blocked current account;
- ownership violation;
- specialist lacks required professional eligibility.

Target HTTP category:

```text
403 Forbidden
```

## Business validation or state failure

Examples:

- invalid lifecycle transition;
- expired Reservation;
- conflicting domain state;
- invalid input.

These are domain/business failures and must be mapped according to their domain exception category rather than automatically becoming 403.

---

# 14. Repository Boundary

Repositories are authorization-agnostic persistence components.

They do not decide whether a caller is allowed to perform an operation.

Authorization belongs to:

```text
security layer
+
service layer
+
domain invariants
```

Repositories execute persistence operations requested by the owning service.

---

# 15. Current vs Target Summary

## Already implemented

```text
UserRole
UserStatus.ACTIVE / BLOCKED
UserService.getActiveUser(...)
SpecialistStatus.PENDING / APPROVED / REJECTED / SUSPENDED
Specialist.isEligible()
SpecialistService.getEligibleSpecialist(...)
selected business-level ownership checks
domain lifecycle validation
```

## Target / backlog

```text
authenticated HTTP principal
centralized Spring Security authorization
endpoint / method-level role enforcement
centralized current-User validation for protected requests
complete ownership enforcement based on authenticated identity
security error mapping
```

The presence of these target rules in documentation must not be interpreted as evidence that the full security infrastructure already exists in `PsyWeb/main`.

---

# Summary

PsyWeb authorization intentionally separates:

```text
authentication
+
account state
+
role
+
specialist professional eligibility
+
resource ownership / participation
+
business state
```

No single role or status replaces the others.

The security layer handles identity and coarse access.

Services enforce resource-specific authorization.

Domain entities enforce lifecycle invariants.

Each module retains ownership of its own business state.
