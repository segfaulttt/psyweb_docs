## Overview

This section describes the backend architecture of the PsyWeb platform. The system is implemented as a **modular monolith using Spring Boot**, designed to support a transactional booking marketplace with strong consistency guarantees and clear domain separation.

The backend is structured to ensure scalability, maintainability, and strict separation of concerns between business domains.

---

# Architectural Style

The backend follows a:

## Modular Monolith Architecture

### Rationale:

- Faster development compared to microservices
- Strong consistency required for booking system
- Easier transactional control (single DB)
- Lower operational complexity
- Suitable for early-stage marketplace product

---

# Module Structure

The system is divided into the following business modules:

- auth
- user
- specialist
- availability
- booking
- review
- chat
- notification
- admin
- common

---

## Module Independence Rule

Each module:

- encapsulates its own service layer
- owns its own domain logic
- communicates via internal service calls (no direct DB cross-access between modules)
- depends only on `common` for shared utilities

---

# Request Flow

The backend follows a standard layered request pipeline:

```
Client → Security Filter → Controller → Service → Repository → Database → Response
```

### Responsibilities:

- **Controller** → HTTP handling, validation
- **Service** → business logic (core rules live here)
- **Repository** → data access (Spring Data JPA)
- **Database** → PostgreSQL source of truth

---

# Core Principles

## 1. Stateless Authentication

- JWT-based authentication
- No server session storage

---

## 2. Domain-Driven Service Layer

- Business rules implemented in service layer
- Controllers remain thin

---

## 3. Transactional Integrity

- Booking operations are fully transactional
- Slot reservation must be atomic

---

## 4. Role-Based Access Control (RBAC)

- CLIENT / SPECIALIST / ADMIN
- enforced at security layer + service validation

---

## 5. Data Consistency First

- system prioritizes correctness over availability in booking flows
- DB constraints + service validation used together

---

# Module Responsibilities (High-Level)

## auth

- login / register
- JWT generation
- password hashing

## user

- base user management
- profile aggregation

## specialist

- specialist profile
- verification status

## availability

- slot creation
- schedule management

## booking (CORE MODULE)

- slot reservation
- booking lifecycle
- cancellation rules

## review

- post-booking feedback
- rating aggregation

## chat (optional)

- messaging system tied to booking

## notification

- async event handling (future-ready)

## admin

- specialist approval
- moderation logic

---

# Key Architectural Decision

## Booking is the core transactional boundary

This means:

- all critical consistency rules live in booking module
- slot + booking must always be synchronized
- concurrency is handled at service + DB level

---

# Extensibility Strategy

The architecture is designed to support future growth:

- chat can evolve into real-time messaging system
- notification module can be replaced with message broker (Kafka/RabbitMQ)
- availability system can evolve into calendar engine
- payment system can be added without affecting core booking logic

---

# Summary

The backend is structured as a modular monolith with:

- strict domain separation
- centralized transactional booking logic
- PostgreSQL as single source of truth
- Spring Boot service-driven architecture
