## Overview

PsyWeb is designed as a Spring Boot modular monolith.

The current `PsyWeb/main` already contains the core backend for:

```text
user
specialist
availability
booking
common
```

Other architectural modules described in the project documentation, such as:

```text
auth
review
chat
notification
admin
```

represent target or separate backlog scope unless their implementation is explicitly present in the current codebase.

This document therefore distinguishes:

```text
current implementation
```

from:

```text
approved target architecture
```

---

# Architectural Style

## Modular Monolith

The backend uses a modular-monolith architecture.

This provides:

- one deployable Spring Boot application;
- one PostgreSQL database;
- local transactional coordination;
- explicit business-module boundaries;
- lower operational complexity than distributed services;
- the ability to evolve module boundaries later if product requirements justify it.

The architecture does not assume that the system must later become microservices.

# Module Ownership Principle

Each business module owns its own domain state and persistence responsibilities.

Cross-module collaboration must not transfer ownership.

For example:

```text
User
→ owned by user

Specialist
→ owned by specialist

AvailabilitySlot
→ owned by availability

Reservation
Booking
→ owned by booking
```

A module may call another module's service boundary when a use case spans multiple domains.

It must not directly mutate another module's repository as a shortcut.

# Current Application Layers

The implemented backend currently uses:

```text
Domain
Service
Repository
PostgreSQL
```

for core business processing.

Conceptually:

```text
Service
→ Domain
→ Repository
→ PostgreSQL
```

The service layer owns application use-case orchestration and transactional boundaries.

Domain entities own lifecycle invariants and state transitions.

Repositories own persistence access for their module.

PostgreSQL remains the persistent source of truth for database-enforced invariants.

# Core Principles

## 1. Domain Ownership

Business state remains inside the module that owns it.

Examples:

```text
SpecialistStatus
→ Specialist domain

AvailabilityStatus
→ Availability domain

ReservationStatus
BookingStatus
→ Booking domain
```

Business enums and lifecycle rules are not centralized in `common`.

---

## 2. Transactional Integrity

Consistency-sensitive workflows execute transactionally.

Current examples include:

```text
Reservation creation
Reservation cancellation
Reservation expiration
Reservation confirmation
Booking creation
Booking cancellation
AvailabilitySlot state coordination
```

Related state changes must not leave partial persistent results.

For example, successful Reservation confirmation coordinates:

```text
Reservation ACTIVE → CONFIRMED
AvailabilitySlot RESERVED → BOOKED
Booking creation
```

inside one consistency-sensitive operation.

---

## 3. Database Protection

Application validation expresses business intent and provides meaningful errors.

It is not sufficient as the only protection for concurrency-sensitive invariants.

Current database protection includes, among other constraints:

```text
User email uniqueness
lowercase email guard
Specialist status CHECK
Availability status CHECK
one ACTIVE Reservation per Slot
Reservation foreign keys
```

Additional target guarantees, such as active AvailabilitySlot overlap exclusion, require future forward migrations.

---

## 4. Controlled Time

Time-dependent business logic should not directly depend on uncontrolled wall-clock calls.

The current backend provides a Spring-managed:

```text
java.time.Clock
```

through:

```text
TimeConfiguration
```

Production currently uses:

```text
Clock.systemDefaultZone()
```

Services that perform temporal logic receive Clock through dependency injection.

Tests may use:

```text
Clock.fixed(...)
```

for deterministic behavior.

The final timezone policy is separate backlog scope and is not defined by this configuration alone.

---

## 5. Domain Exception Architecture

The current backend uses the shared domain exception hierarchy:

```text
DomainException
BaseDomainException
ValidationException
NotFoundException
ConflictException
ForbiddenException
InvalidStateException
ExpiredException
```

Concrete business exceptions remain inside their owning modules.

The centralized REST exception-mapping layer is target/backlog functionality.




```text
minimumBookingNotice
clientCancellationNotice
```

as Java `Duration`, persisted as whole integer minutes.

The full suspension cascade and immutable moderation-history model are approved target/backlog functionality.

# Current Availability Domain

The Availability module currently owns:

```text
AvailabilitySlot
AvailabilityStatus
AvailabilitySlotService
AvailabilitySlotRepository
availability-specific exceptions
```

Current statuses are:

```text
FREE
RESERVED
BOOKED
CANCELLED
```

Current slot creation validates:

```text
specialist eligibility
startTime < endTime
startTime > now
application-level overlap
```

The overlap predicate follows half-open interval semantics:

```text
newStart < existingEnd
&&
newEnd > existingStart
```

The approved PostgreSQL active-slot exclusion constraint is target/backlog.

The optional per-slot minimum-booking-notice override and final booking-deadline enforcement are also target/backlog.

Detailed Availability state-machine and service-boundary documentation remains owned by its dedicated documentation task.

Approved target Booking-domain extensions include:


These models will represent:

- post-session reporting;
- OCCURRED / DID_NOT_OCCUR outcomes;
- structured non-occurrence reasons;
- 24-hour reporting window;
- automatic resolution;
- timeout finalization;
- disputes;
- administrative dispute resolution.

They are not currently implemented in `PsyWeb/main`.

# Target Authentication and Authorization

Stateless JWT authentication is approved target architecture.

Login requires:

```text
valid credentials
+
UserStatus.ACTIVE
```

An ACTIVE Specialist may authenticate regardless of current SpecialistStatus.

Professional Specialist operations separately require:

```text
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

JWT must contain stable identity claims rather than mutable authorization state.

The final Spring Security/JWT infrastructure is not yet implemented.

---

# Target Administration

A dedicated Admin application boundary is target/backlog.

Administrative workflows may orchestrate:

```text
Specialist approval
rejection
suspension
reinstatement
user moderation
future SessionOutcome disputes
```

Admin orchestration must use owning module services.

It must not directly own or mutate Specialist, Booking, User, or Availability persistence.

# Summary

PsyWeb is a modular monolith with current implementation concentrated in:

```text
user
specialist
availability
booking
common
```

The architecture prioritizes:

- clear domain ownership;
- transactional consistency;
- database-backed integrity;
- explicit current-vs-target documentation;
- deterministic temporal logic;
- incremental forward-only schema evolution.

Features that exist only as approved architecture or backlog must not be treated as already implemented.
