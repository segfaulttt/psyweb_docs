## Overview

This section defines the Booking domain of the PsyWeb system.

The Booking module currently owns two implemented lifecycle concepts:

* Reservation — a temporary hold on an AvailabilitySlot before booking confirmation;
* Booking — a confirmed consultation created from a successfully confirmed Reservation.

Post-session attendance and session result are designed as a separate target model through SessionOutcome rather than being encoded into Booking status.

The current `PsyWeb/main` already implements Reservation and Booking core lifecycle behavior.

The SessionOutcome / SessionReport / DisputeResolution model described later in this document is approved target architecture and is not yet implemented in the current backend.

This separation prevents:

* temporary Reservation state;
* confirmed appointment state;
* cancellation state;
* post-session attendance/result

from being mixed into a single status model.

---

# Core Concepts

## Reservation

A Reservation represents temporary client intent to book an AvailabilitySlot.

The current Reservation entity contains:

```text
id
client
slot
status
createdAt
expiresAt
```

Current Reservation statuses are:

```text
ACTIVE
CONFIRMED
EXPIRED
CANCELLED
```

A newly created Reservation starts as:

```text
ACTIVE
```

and temporarily holds the associated AvailabilitySlot:

```text
AvailabilitySlot FREE → RESERVED
```

---

### Reservation Creation

The current Reservation creation flow is implemented by:

```text
ReservationService.createReservation(...)
```

Conceptually:

```text
validate clientId and slotId
→ reject existing ACTIVE Reservation for the Slot
→ load ACTIVE client
→ reserve Slot through AvailabilitySlotService
→ obtain current time from injected Clock
→ create ACTIVE Reservation
→ createdAt = now
→ expiresAt = now + ReservationProperties.ttl
→ persist Reservation
```

Reservation creation and the Slot transition execute in one transaction.

The current database additionally protects the invariant:

```text
at most one ACTIVE Reservation per AvailabilitySlot
```

through the partial uniqueness constraint identified as:

```text
unique_active_reservation_slot
```

The application pre-check provides an early business failure.

The database remains the final persistence guard for concurrent attempts.

---

### Reservation TTL

Reservation TTL is platform-owned configuration.

It is not configured per Specialist and is independent from:

```text
minimumBookingNotice
clientCancellationNotice
```

The current configuration is provided through:

```text
ReservationProperties
```

with prefix:

```text
psyweb.reservation
```

Current properties are:

```text
Duration ttl
Duration expirationScanInterval
int expirationBatchSize
```

The current application configuration is:

```yaml
psyweb:
  reservation:
    ttl: 10m
    expiration-scan-interval: 1m
    expiration-batch-size: 100
```

Reservation creation computes:

```text
expiresAt = createdAt + ttl
```

The persisted `expiresAt` value is the business source of truth for Reservation expiration.

---

### Expiration Boundary

An ACTIVE Reservation is considered expired when:

```text
now >= expiresAt
```

Equivalent implementation rule:

```text
!expiresAt.isAfter(now)
```

Therefore:

```text
now == expiresAt
```

already means that the Reservation is expired.

Scheduler execution time does not define expiration.

An overdue Reservation is no longer confirmable even if the background expiration scheduler has not processed it yet.

---

### Reservation Confirmation

An ACTIVE and unexpired Reservation may be confirmed.

The current confirmation flow is coordinated by:

```text
BookingService.confirmReservation(...)
```

The Reservation is loaded using a pessimistic write lock before its state is checked and changed.

Conceptually:

```text
lock Reservation
→ obtain now from Clock
→ validate Reservation ownership
→ reject / expire overdue Reservation
→ require ReservationStatus.ACTIVE
→ validate client eligibility
→ transition Slot RESERVED → BOOKED
→ validate Specialist eligibility
→ Reservation ACTIVE → CONFIRMED
→ create CONFIRMED Booking
```

The Reservation domain itself also prevents confirmation when:

```text
status != ACTIVE
```

or:

```text
now >= expiresAt
```

---

### Reservation Expiration

Expiration transitions:

```text
Reservation ACTIVE → EXPIRED
AvailabilitySlot RESERVED → FREE
```

The Reservation domain allows expiration only when the Reservation is still ACTIVE and:

```text
now >= expiresAt
```

Expiration and Slot release are coordinated transactionally.

---

### Automatic Expiration

Automatic cleanup of overdue Reservations is already implemented.

The current flow is:

```text
ReservationExpirationScheduler
→ ReservationService.expireExpiredReservations()
→ ReservationRepository
```

The scheduler runs using the configured:

```text
expirationScanInterval
```

which is currently:

```text
1 minute
```

Each run selects ACTIVE Reservations satisfying:

```text
expiresAt <= now
```

The query is not limited to only recently expired Reservations.

Therefore, overdue rows left behind after application downtime remain eligible for processing on a later run.

---

### Expiration Batch Processing

The current expiration query uses:

```text
LIMIT expirationBatchSize
```

with the configured value:

```text
100
```

Rows are ordered by:

```text
expires_at
id
```

so older overdue Reservations are selected first with deterministic ordering.

One scheduler invocation processes one selected batch.

Remaining overdue Reservations remain eligible for later runs.

---

### Expiration Concurrency

The current expiration repository query uses PostgreSQL:

```sql
FOR UPDATE SKIP LOCKED
```

This means:

```text
FOR UPDATE
→ selected Reservation rows are locked for mutation

SKIP LOCKED
→ another worker skips rows already locked by another transaction
```

This allows concurrent workers to process separate overdue Reservation rows without intentionally processing the same locked row at the same time.

No separate distributed scheduler lock is required for the current MVP design.

---

### Reservation Cancellation

A Reservation may be cancelled only while:

```text
status = ACTIVE
```

Cancellation transitions:

```text
Reservation ACTIVE → CANCELLED
AvailabilitySlot RESERVED → FREE
```

The Reservation is loaded using a pessimistic write lock before cancellation.

The Reservation and Slot changes execute in the same transaction.

---

### Reservation Terminal Semantics

The following Reservation states no longer represent an active temporary hold:

```text
CONFIRMED
EXPIRED
CANCELLED
```

A CONFIRMED Reservation records the historical fact that its temporary hold was successfully converted into a Booking.

A later Booking cancellation does not rewrite the Reservation back to CANCELLED.

The Reservation lifecycle and Booking lifecycle represent separate facts.

---

## Booking

A Booking represents a confirmed consultation created from a successfully confirmed Reservation.

A Booking does not represent the temporary hold stage.

There is no Booking before Reservation confirmation succeeds.

The current `PsyWeb/main` still contains the legacy BookingStatus values:

```text
CONFIRMED
CANCELLED
COMPLETED
NO_SHOW
```

and the current Booking entity still contains legacy domain operations for:

```text
CONFIRMED → COMPLETED
CONFIRMED → NO_SHOW
```

The existing applied database constraint also still permits these legacy values.

This is current implementation state, not the approved target model.

The approved target Booking lifecycle is:

```text
CONFIRMED
CANCELLED
```

Post-session attendance and non-occurrence must move to the separate:

```text
SessionOutcome
```

model.

Therefore:

```text
COMPLETED
NO_SHOW
```

are legacy current implementation that must not be treated as part of the target architecture.

Their removal requires a future code/schema change through the relevant implementation work and a forward-only Flyway migration.

Existing applied migrations must not be edited.

---

## SessionOutcome

SessionOutcome represents the approved target model for what happened after the scheduled consultation.

It is intentionally separate from Booking status.

The Booking lifecycle answers:

> Does a confirmed appointment exist, or was it cancelled?

The SessionOutcome lifecycle answers:

> Did the scheduled consultation actually occur?

The target model includes:

```text
SessionOutcome
SessionReport
DisputeResolution
```

with outcome-resolution states such as:

```text
PENDING
DISPUTED
RESOLVED
UNVERIFIED
```

These classes and persistence structures are not yet present in the current `PsyWeb/main`.

Therefore, all SessionOutcome behavior later in this document must be read as approved target/backlog behavior until the corresponding implementation tasks are completed.

---

# Booking Status Model

Booking uses the following statuses:

* `CONFIRMED`
* `CANCELLED`

There is no `CREATED` Booking status.

Temporary pre-confirmation state belongs to Reservation.

There is no `NO_SHOW` Booking status.

No-show claims belong to the post-session outcome reporting model.

There is no `COMPLETED` Booking status.

Successful completion is derived from a finalized SessionOutcome whose final outcome is `OCCURRED`.

---

# Booking Status Semantics

## CONFIRMED

The Reservation has been successfully confirmed and the consultation exists.

A CONFIRMED Booking may be:

* upcoming;
* currently within its scheduled time;
* past its scheduled time while post-session outcome is unresolved;
* historical after a final SessionOutcome has been established.

Time determines whether the appointment is upcoming or past.

BookingStatus does not duplicate that temporal information.

---

## CANCELLED

The confirmed consultation was cancelled through the normal cancellation workflow.

`CANCELLED` is terminal.

A cancelled Booking is not reactivated.

If availability is released and another client later books the same AvailabilitySlot, a new Reservation and a new Booking are created.

---

# Booking Creation

A Booking is created only through confirmation of an existing ACTIVE Reservation.

Typical flow:

`ACTIVE Reservation`
→ validate ownership
→ validate Reservation is unexpired
→ validate client eligibility
→ validate specialist eligibility
→ validate AvailabilitySlot is RESERVED
→ Reservation becomes CONFIRMED
→ Booking is created with CONFIRMED status
→ AvailabilitySlot transitions `RESERVED → BOOKED`

Reservation confirmation, Booking creation, and the AvailabilitySlot transition form one atomic business operation.

No direct:

`FREE → BOOKED`

transition exists.

---

# Booking Cancellation

Booking cancellation and post-session outcome reporting are separate workflows.

Ordinary Booking cancellation applies only before the scheduled session starts.

A CONFIRMED Booking may be cancelled by the client according to the cancellation policy defined by the specialist.

---

## Client Cancellation Notice

A specialist defines:

`clientCancellationNotice`

This value represents how long before the scheduled session a client is expected to cancel without the cancellation being considered late.

It is independent from:

`minimumBookingNotice`

The two settings solve different problems:

* `minimumBookingNotice` controls how late a new Reservation may be created;
* `clientCancellationNotice` classifies cancellation of an already confirmed Booking.

The client cancellation deadline is:

`clientCancellationDeadline = slot.startTime - clientCancellationNotice`

If `clientCancellationNotice = 0`:

`clientCancellationDeadline = slot.startTime`

---

## Normal Client Cancellation

When:

`cancelledAt < clientCancellationDeadline`

the cancellation is considered on-time.

The Booking transitions:

`CONFIRMED → CANCELLED`

and the AvailabilitySlot transitions:

`BOOKED → FREE`

Cancellation metadata records:

* `cancelledAt`;
* `cancellationInitiator = CLIENT`.

The Booking remains stored as historical data.

---

## Late Client Cancellation

A client may still cancel a CONFIRMED Booking after the cancellation deadline as long as the scheduled session has not yet started.

When:

`clientCancellationDeadline <= cancelledAt < slot.startTime`

the cancellation is considered late.

Late cancellation does not introduce a separate Booking status.

The Booking still transitions:

`CONFIRMED → CANCELLED`

The AvailabilitySlot still transitions:

`BOOKED → FREE`

Whether the cancellation was late is derived from the timestamps:

`cancelledAt`

and:

`clientCancellationDeadline`

The system must not encode the same fact redundantly through a status such as:

`LATE_CANCELLED`

---

## MVP Consequences of Late Cancellation

For the MVP, late cancellation has:

* no monetary penalty;
* no automatic account restriction;
* no automatic reliability penalty;
* no special Booking status.

The cancellation timing remains persisted so it can later be used for analytics or future reliability policies.

Introducing penalties, fees, reliability scoring, or cancellation limits requires a separate explicit product rule.

---

## Rebooking After Client Cancellation

Client cancellation releases the Booking occupancy:

`AvailabilitySlot BOOKED → FREE`

However:

`FREE`

does not automatically mean:

`bookable`

Whether another client may create a Reservation is evaluated independently using the existing booking cutoff:

`bookingDeadline = slot.startTime - effectiveMinimumBookingNotice`

Therefore, after cancellation the slot may be:

* FREE and still bookable;
* FREE but already non-bookable.

No additional AvailabilitySlot status is introduced for this distinction.

---

## Interaction With Reservation Cutoff

The booking cutoff affects creation of a new Reservation.

It does not cancel an already existing ACTIVE Reservation merely because the cutoff passes.

An ACTIVE Reservation created before `bookingDeadline` may still be confirmed after the cutoff provided that:

* it remains ACTIVE;
* its own `expiresAt` has not passed;
* all other confirmation rules remain satisfied.

Reservation TTL and booking cutoff are therefore independent temporal rules.

---

## Specialist Availability Removal

Specialist removal of occupied availability is different from client Booking cancellation.

When a specialist removes availability associated with a CONFIRMED Booking:

* the Booking is cancelled consistently;
* cancellation metadata records the applicable initiator and time;
* AvailabilitySlot transitions `BOOKED → CANCELLED`;
* the slot is not returned to FREE.

The removed AvailabilitySlot remains historical and terminal.

---

# Reliability and Cancellation History

Reliability must be based on actual participation in the Booking lifecycle.

Unbooked AvailabilitySlots are not evidence of client or specialist reliability.

In particular, a slot that:

* remains FREE;
* passes its booking deadline;
* is never reserved;
* is never converted into a Booking

must not affect participant reliability.

Any future reliability model should derive its inputs from confirmed Booking history and relevant finalized outcomes or cancellation metadata.

For MVP:

* no automatic reliability score is calculated from late cancellation;
* no penalty is inferred from unused specialist availability;
* cancellation and outcome history is retained so future policies can be introduced explicitly.

---

# Boundary Between Cancellation and Post-Session Outcome

Cancellation answers:

> Was the confirmed appointment cancelled before the session began?

Post-session outcome answers:

> What happened when a non-cancelled appointment reached its scheduled session time?

A correctly cancelled Booking does not enter the post-session outcome workflow.

Once the scheduled session has started, ordinary cancellation is no longer used to represent attendance or non-attendance.

Claims such as client no-show or specialist no-show belong to SessionOutcome reporting.

---

# Target Post-Session Outcome Model

The following post-session model is approved target architecture.

It is not yet implemented in the current `PsyWeb/main`.

The target model does not introduce a separate `Session` entity.

`Booking` remains the source of the scheduled appointment, while consultation time is obtained through:

```text
Booking
→ AvailabilitySlot
→ startTime / endTime
```

Post-session state is represented by three separate persistence entities:

```text
SessionOutcome
SessionReport
DisputeResolution
```

---

# SessionOutcome

`SessionOutcome` represents the process and final result of determining what happened during a non-cancelled confirmed consultation.

A Booking may have at most one SessionOutcome.

Target cardinality:

```text
Booking 1 → 0..1 SessionOutcome
```

Target fields:

```text
id
bookingId
resolutionStatus
finalOutcome
finalReason
createdAt
reportingDeadline
disputedAt
finalizedAt
```

`bookingId` is unique.

---

## Resolution Status

The target resolution states are:

```text
PENDING
DISPUTED
RESOLVED
UNVERIFIED
```

They describe the resolution process, not Booking lifecycle.

---

## PENDING

`PENDING` means that post-session reporting is still unresolved.

Properties:

```text
finalOutcome = null
finalReason = null
finalizedAt = null
```

Participant reports may still be submitted while the reporting window is open.

---

## DISPUTED

`DISPUTED` means that both participant reports exist but cannot be safely resolved automatically.

Properties:

```text
finalOutcome = null
finalReason = null
finalizedAt = null
disputedAt != null
```

Administrative resolution is required.

---

## RESOLVED

`RESOLVED` means a final factual outcome has been established.

Final outcome is one of:

```text
OCCURRED
DID_NOT_OCCUR
```

A resolved outcome requires:

```text
finalOutcome != null
finalizedAt != null
```

When:

```text
finalOutcome = OCCURRED
```

then:

```text
finalReason = null
```

When:

```text
finalOutcome = DID_NOT_OCCUR
```

then:

```text
finalReason != null
```

---

## UNVERIFIED

`UNVERIFIED` means that the reporting window expired without either participant submitting a report.

Properties:

```text
finalOutcome = null
finalReason = null
finalizedAt != null
```

The platform does not infer:

```text
OCCURRED
```

or:

```text
DID_NOT_OCCUR
```

from absence of reports.

`UNVERIFIED` is terminal for the MVP.

---

# Automatic SessionOutcome Creation

The approved target strategy uses automatic/eager SessionOutcome creation.

After the scheduled session has ended, the system creates a PENDING SessionOutcome for each non-cancelled:

```text
BookingStatus.CONFIRMED
```

The temporal boundary is:

```text
now >= AvailabilitySlot.endTime
```

A cancelled Booking does not enter the ordinary post-session workflow.

The target flow is:

```text
CONFIRMED Booking
+
now >= slot.endTime
→
SessionOutcome(PENDING)
```

Creation must be idempotent.

Database uniqueness on:

```text
booking_id
```

provides the persistence safety net against duplicate SessionOutcome creation.

The scheduler/configuration mechanism for automatic creation belongs to the corresponding implementation task and is not currently implemented.

---

# Reporting Window

The approved MVP reporting window is:

```text
24 hours after AvailabilitySlot.endTime
```

Therefore:

```text
reportingDeadline =
slot.endTime + 24 hours
```

The reporting interval is half-open:

```text
[slot.endTime, reportingDeadline)
```

A report is accepted when:

```text
now >= slot.endTime
&&
now < reportingDeadline
```

At:

```text
now == reportingDeadline
```

the reporting window is already closed.

The 24-hour duration must come from type-safe application configuration rather than being duplicated as a magic constant in business logic.

---

# SessionReport

`SessionReport` represents one participant's immutable statement about whether the consultation occurred.

Target cardinality:

```text
SessionOutcome 1 → 0..2 SessionReport
```

Target fields:

```text
id
sessionOutcomeId
actorType
reportedOutcome
reason
details
reportedAt
```

`actorType` is:

```text
CLIENT
SPECIALIST
```

A separate `authorId` is not required in the target persistence model.

The concrete participant identity is derived through:

```text
SessionOutcome
→ Booking
```

while `actorType` identifies which side submitted the report.

---

## One Report per Participant

The database target enforces:

```text
UNIQUE(session_outcome_id, actor_type)
```

Therefore:

- CLIENT may submit at most one report;
- SPECIALIST may submit at most one report.

Submitted reports are immutable.

They are not replaced or rewritten during later automatic or administrative resolution.

---

# Reported Outcome

A SessionReport contains:

```text
OCCURRED
```

or:

```text
DID_NOT_OCCUR
```

---

## OCCURRED Report

When:

```text
reportedOutcome = OCCURRED
```

the report must contain:

```text
reason = null
details = null
```

---

## DID_NOT_OCCUR Report

When:

```text
reportedOutcome = DID_NOT_OCCUR
```

a structured reason is mandatory.

The shared target enum is:

```text
SessionNonOccurrenceReason
```

with values:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
OTHER
```

For:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
```

free-text `details` are optional.

For:

```text
OTHER
```

`details` are mandatory and nonblank.

---

# Automatic Resolution With Two Reports

When both participants submit reports, the system evaluates the pair.

---

## OCCURRED + OCCURRED

```text
CLIENT: OCCURRED
SPECIALIST: OCCURRED
```

Result:

```text
SessionOutcome.resolutionStatus = RESOLVED
finalOutcome = OCCURRED
finalReason = null
```

---

## Compatible DID_NOT_OCCUR Reports

Two `DID_NOT_OCCUR` reports resolve automatically only when both use the same structured reason and that reason is not `OTHER`.

Example:

```text
CLIENT: DID_NOT_OCCUR / TECHNICAL_PROBLEM
SPECIALIST: DID_NOT_OCCUR / TECHNICAL_PROBLEM
```

Result:

```text
RESOLVED
DID_NOT_OCCUR
TECHNICAL_PROBLEM
```

---

# Conflicting Reports

A dispute is created when two participant reports cannot be automatically reconciled.

Conflict examples include:

```text
OCCURRED
vs
DID_NOT_OCCUR
```

different structured reasons:

```text
CLIENT_NO_SHOW
vs
SPECIALIST_NO_SHOW
```

or any pair in which at least one report uses:

```text
OTHER
```

Therefore:

```text
OTHER + OTHER
```

also creates a dispute.

The same enum value does not prove that two free-text explanations describe the same factual event.

The system does not:

- compare `details` using string equality;
- interpret free text automatically;
- attempt semantic reconciliation of `OTHER` explanations.

Conflict results in:

```text
PENDING → DISPUTED
```

with:

```text
disputedAt = now
finalOutcome = null
finalReason = null
finalizedAt = null
```

Both original SessionReports remain unchanged.

---

# Single Report at Timeout

If exactly one participant submitted a report before `reportingDeadline` and the second participant did not respond:

```text
PENDING
→
RESOLVED
```

after the reporting window closes.

The final result is copied from the submitted report.

For:

```text
OCCURRED
```

the result becomes:

```text
RESOLVED / OCCURRED
```

For:

```text
DID_NOT_OCCUR
```

the submitted structured reason becomes `finalReason`.

This rule also applies to a single:

```text
DID_NOT_OCCUR / OTHER
```

report.

A single `OTHER` report does not create a dispute merely because the second participant did not respond.

The original report `details` remain stored as audit context and are not duplicated into an additional SessionOutcome free-text field for MVP.

---

# No Reports at Timeout

If no SessionReport exists when the reporting deadline is reached:

```text
PENDING
→
UNVERIFIED
```

No final outcome or reason is inferred.

The system does not automatically conclude:

- that the consultation occurred;
- that the consultation did not occur;
- that either participant was responsible.

No automatic reliability or punitive consequence is derived from the absence of both reports.

---

# DisputeResolution

`DisputeResolution` represents the administrator's resolution of a conflicting SessionOutcome.

Target cardinality:

```text
SessionOutcome 1 → 0..1 DisputeResolution
```

Target fields:

```text
id
sessionOutcomeId
adminId
finalOutcome
reason
comment
resolvedAt
```

The database target enforces:

```text
UNIQUE(session_outcome_id)
```

A DisputeResolution exists only for a:

```text
SessionOutcome.resolutionStatus = DISPUTED
```

---

## Admin Resolution to OCCURRED

When the administrator determines that the consultation occurred:

```text
DisputeResolution.finalOutcome = OCCURRED
reason = null
```

Administrative `comment` is optional.

The SessionOutcome becomes:

```text
DISPUTED → RESOLVED
```

with:

```text
finalOutcome = OCCURRED
finalReason = null
finalizedAt = resolvedAt
```

---

## Admin Resolution to DID_NOT_OCCUR

When the administrator determines that the consultation did not occur:

```text
DisputeResolution.finalOutcome = DID_NOT_OCCUR
reason != null
```

Supported reasons use the same:

```text
SessionNonOccurrenceReason
```

enum.

For:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
```

admin comment is optional.

For:

```text
OTHER
```

admin comment is mandatory and nonblank.

After resolution:

```text
SessionOutcome.resolutionStatus = RESOLVED
finalOutcome = DID_NOT_OCCUR
finalReason = selected reason
finalizedAt = resolvedAt
```

---

# Dispute Audit Semantics

Administrative dispute resolution does not rewrite participant history.

The target persistence model retains:

```text
original CLIENT SessionReport
original SPECIALIST SessionReport
DisputeResolution
final SessionOutcome state
```

The original reports remain immutable even when the administrator chooses a different final factual outcome.

`DisputeResolution` therefore acts as separate audit data rather than replacing participant reports.

---

# Target Lifecycle Summary

```text
CONFIRMED Booking
+
now >= slot.endTime
→ SessionOutcome(PENDING)

PENDING
├─ compatible two reports
│  → RESOLVED
│
├─ conflicting two reports
│  → DISPUTED
│  → admin resolution
│  → RESOLVED
│
├─ one report + reporting timeout
│  → RESOLVED
│
└─ zero reports + reporting timeout
   → UNVERIFIED
```

For MVP:

```text
RESOLVED
UNVERIFIED
```

are terminal outcome states.

# Target Persistence Constraints

The target persistence model requires forward-only schema changes.

Applied Flyway migrations must not be edited to introduce SessionOutcome support.

A future migration adds persistence for:

```text
session_outcome
session_report
dispute_resolution
```

Key database guarantees include:

```text
UNIQUE session_outcome(booking_id)

UNIQUE session_report(
    session_outcome_id,
    actor_type
)

UNIQUE dispute_resolution(
    session_outcome_id
)
```

Database CHECK constraints should protect enum/value consistency and final-state nullability where practical.

Service/domain validation remains responsible for business rules that cannot be expressed safely or clearly as relational constraints.

# Review Eligibility

Review eligibility belongs to the Client-Specialist relationship rather than to one specific Booking.

A Client may create the first Review for a Specialist when there exists at least one historical Booking for the same Client-Specialist pair whose SessionOutcome satisfies:

```text
resolutionStatus = RESOLVED
finalOutcome = OCCURRED
```

The way in which that final outcome was reached does not affect eligibility.

Eligible resolution paths include:

```text
CLIENT OCCURRED + SPECIALIST OCCURRED
one OCCURRED report + reporting timeout
admin-resolved dispute → OCCURRED
```

Dual participant confirmation is therefore not required as a separate Review condition.

The following do not enable Review creation:

```text
Booking without finalized outcome
PENDING SessionOutcome
DISPUTED SessionOutcome
UNVERIFIED SessionOutcome
RESOLVED / DID_NOT_OCCUR SessionOutcome
```

A CANCELLED Booking does not create eligibility by itself, but it also does not erase eligibility created by another historical `RESOLVED / OCCURRED` consultation between the same Client and Specialist.

Once the Client-Specialist pair has at least one qualifying successful consultation, that eligibility does not expire in the MVP.

The Review itself does not store a Booking identifier.

One Client may have at most one Review for the same Specialist.

# Concurrency and Transaction Rules

Reservation and Booking operations remain strongly consistent.

Critical atomic operations include:

## Reservation Creation

* create ACTIVE Reservation;
* transition AvailabilitySlot `FREE → RESERVED`.

## Reservation Confirmation

* Reservation `ACTIVE → CONFIRMED`;
* Booking creation;
* AvailabilitySlot `RESERVED → BOOKED`.

## Reservation Cancellation or Expiration

* Reservation → `CANCELLED` or `EXPIRED`;
* AvailabilitySlot `RESERVED → FREE`.

## Booking Cancellation

* Booking `CONFIRMED → CANCELLED`;
* apply the corresponding AvailabilitySlot transition.

Post-session reporting does not modify AvailabilitySlot occupancy.

# Domain Invariants

The Booking domain enforces the following invariants:

* a Booking is created only from a confirmed Reservation;
* a Reservation produces at most one Booking;
* Booking has no provisional CREATED state;
* a cancelled Booking cannot be reactivated;
* ordinary cancellation is separate from post-session attendance reporting;
* BookingStatus does not encode no-show or attendance outcome;
* each participant may submit at most one immutable SessionReport;
* a final OCCURRED or DID_NOT_OCCUR result is produced only through outcome resolution;
* conflicting participant claims are not resolved automatically;
* absence of both reports does not imply successful completion;
* review eligibility requires a finalized OCCURRED outcome.

---

# Summary

The Booking domain:

* owns Reservation and Booking lifecycle;
* creates Booking only after Reservation confirmation;
* uses BookingStatus only for confirmed-versus-cancelled appointment lifecycle;
* keeps post-session result separate from BookingStatus;
* collects independent CLIENT and SPECIALIST reports;
* resolves compatible reports automatically;
* accepts a single submitted report after the reporting timeout;
* marks sessions with no reports as UNVERIFIED;
* routes conflicting claims to administrative dispute resolution;
* enables reviews only after a finalized OCCURRED outcome;
* preserves historical Reservation, Booking, report, outcome, and dispute data.
