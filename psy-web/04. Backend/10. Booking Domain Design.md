## Overview

This section defines the core domain model of the PsyWeb system: the booking lifecycle.

The booking domain is the central part of the entire backend system and defines how clients interact with specialist availability through time-based reservations.

All critical business rules of the platform are enforced within this domain.

---

# Core Concept

A booking represents a confirmed reservation of a specific availability slot between a client and a specialist for a selected service.

The booking is the single source of truth for the consultation lifecycle.

---

# Booking States

The booking entity follows a strict state machine.

## Status list

- CREATED
- CONFIRMED
- CANCELLED
- COMPLETED
- NO_SHOW

---

# State Descriptions

## CREATED

Initial state after booking creation.

- slot is reserved
- waiting for confirmation logic (if applicable)
- system ensures slot is not available for others

---

## CONFIRMED

Booking is fully accepted and active.

- consultation is scheduled
- slot is definitively occupied
- used for upcoming appointments

---

## CANCELLED

Booking has been cancelled by client or specialist.

Rules:

- cancellation rules apply (e.g. 24h constraint)
- slot may be released depending on business rules

---

## COMPLETED

Consultation has been successfully finished.

Rules:

- enables review creation
- final state of successful booking

---

## NO_SHOW

Client did not attend the consultation.

Rules:

- marks failed attendance
- may affect reputation system in future extensions

---

# State Transition Rules

Booking transitions are strictly controlled:

```
CREATED → CONFIRMED → COMPLETEDCREATED → CANCELLEDCONFIRMED → CANCELLEDCONFIRMED → NO_SHOW
```

Invalid transitions are rejected at service layer.

---

# Core Business Rules

## 1. One Active Booking Occupancy per Slot

An AvailabilitySlot may have multiple historical Bookings because a cancelled Booking may be followed by a new Reservation and Booking for the same slot.

However, only one active Booking may occupy a slot at a time.

Therefore:

* `booking.slot_id` is not globally unique;
* historical cancelled Bookings remain stored;
* a new Booking may be created for the same slot after its previous Booking is cancelled and the slot becomes available again;
* concurrent conflicting occupancy must still be prevented through transactional coordination and database-level integrity guarantees.

---

## 2. Booking Is Created from a Confirmed Reservation

A Booking is not created directly from a `FREE` AvailabilitySlot.

The normal flow is:

`FREE slot`
→ ACTIVE Reservation
→ `RESERVED` slot
→ Reservation confirmation
→ CONFIRMED Booking
→ `BOOKED` slot

Booking creation therefore requires:

* an existing Reservation;
* the Reservation to be `ACTIVE` and unexpired before confirmation;
* the Reservation to belong to the requesting client;
* the AvailabilitySlot to be in `RESERVED` state for that Reservation.

There is no direct `FREE → BOOKED` AvailabilitySlot transition.

---

## 3. Cancellation policy

Default rule:

- cancellation allowed only within configured time window (e.g. 24 hours before start)

This rule is enforced in BookingService.

---

## 4. Review eligibility

A review can only be created if:

- booking status is COMPLETED

---

## 5. Ownership rules

- client can only manage their own bookings
- specialist can only access their assigned bookings

---

# Booking Creation Flow

A Booking is created by confirming an existing temporary Reservation.

Typical flow:

`ConfirmReservationRequest`
→ validate authenticated client
→ load Reservation
→ validate Reservation ownership
→ verify Reservation is ACTIVE and unexpired
→ verify associated AvailabilitySlot is RESERVED
→ validate client and specialist eligibility
→ transition Reservation to CONFIRMED
→ transition AvailabilitySlot `RESERVED → BOOKED`
→ create Booking with CONFIRMED status
→ commit transaction

Reservation confirmation, AvailabilitySlot transition, and Booking creation form one atomic business operation.

If any part fails, the system must not persist a partial confirmation state.

---

# Cancellation and Slot Removal Flow

Booking cancellation and specialist availability removal have different effects on AvailabilitySlot state.

## Client Booking Cancellation

When a client cancels a confirmed Booking:

`Booking CONFIRMED → CANCELLED`

and:

`AvailabilitySlot BOOKED → FREE`

The Booking cancellation and slot release must be committed consistently.

Returning the slot to `FREE` does not automatically make it bookable again. A new Reservation may only be created if the slot is still before its booking deadline.

---

## Specialist Availability Removal

When a specialist removes availability associated with an active Booking:

`AvailabilitySlot BOOKED → CANCELLED`

The associated Booking must be handled consistently as part of the same business operation.

The slot does not return to `FREE`.

`CANCELLED` AvailabilitySlot is terminal and remains stored as historical data.

If the specialist later wants to offer the same time again, a new AvailabilitySlot must be created.

---

# Completion Flow

```
System/Specialist action→ validate booking is CONFIRMED→ update status to COMPLETED→ enable review creation
```

---

# Concurrency Considerations

Booking and Reservation flows are highly sensitive to race conditions.

To prevent inconsistent availability:

* concurrent Reservation creation for the same slot must be protected;
* at most one ACTIVE Reservation may hold a slot at a time;
* Reservation creation and `FREE → RESERVED` must be atomic;
* Reservation confirmation, Booking creation, and `RESERVED → BOOKED` must be atomic;
* Reservation cancellation or expiration and `RESERVED → FREE` must be coordinated consistently;
* Booking cancellation and the corresponding AvailabilitySlot transition must be coordinated consistently;
* database-level guarantees must protect critical concurrency invariants.

`booking.slot_id` must not be globally unique because the same AvailabilitySlot may have multiple historical Bookings after cancellation and rebooking.

Concurrency correctness must not rely only on application-level pre-checks.

---

# Domain Invariants

The system enforces the following invariants:

- A slot cannot have more than one active booking
- A booking must always reference a valid slot
- Completed bookings are immutable in terms of slot assignment
- Cancelled bookings cannot be reactivated

---

# Error Scenarios

Common domain errors:

- SlotAlreadyBookedException
- InvalidBookingStateException
- BookingCancellationNotAllowedException
- BookingNotFoundException

---

# Summary

The booking domain is designed to:

- enforce strict lifecycle control over appointments
- guarantee consistency of slot reservation
- prevent double booking under all conditions
- serve as the central transactional boundary of the system
- support future extensions like payments, notifications, and analytics
