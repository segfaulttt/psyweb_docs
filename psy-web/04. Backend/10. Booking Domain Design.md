# 10. Проектирование домена Booking

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — бизнес-модель согласована, детали реализации требуют проверки

---

# 1. Назначение документа

Документ определяет архитектуру домена Booking в PsyWeb.

Домен отвечает за жизненный цикл резервирования и подтверждённых консультаций между клиентами и специалистами.

В его обязанности входят:

- создание временных Reservation;
- подтверждение Reservation;
- создание и управление Booking;
- отмена Reservation и Booking;
- обработка истечения Reservation;
- управление действующей занятостью через ScheduleOccupancy;
- сохранение истории консультаций;
- проверка принадлежности записей;
- согласованная обработка конкурентных операций.

PsyWeb использует динамический расчёт доступности.

Система не создаёт и не хранит предварительно сформированные AvailabilitySlot.

Доступное время вычисляется на основании:

- ServiceOffering;
- настроек расписания специалиста;
- версий регулярного расписания;
- расписания отдельных дат;
- действующих ScheduleOccupancy;
- правил предварительной записи;
- допуска специалиста к бронированию.

Домен Booking является владельцем жизненного цикла Reservation, Booking и ScheduleOccupancy.

При этом он не владеет правилами рабочего расписания, конфигурацией услуг, административной модерацией или результатами проведения консультаций.

Операции, затрагивающие несколько модулей, координируются прикладными сервисами.

---

# 2. Основная концепция

Процесс записи на консультацию состоит из трёх связанных сущностей:

1. Reservation.
2. Booking.
3. ScheduleOccupancy.

Каждая сущность имеет отдельную ответственность.

## 2.1. Reservation

Reservation представляет временное удержание выбранного времени консультации.

Она создаётся, когда клиент выбирает:

- ServiceOffering;
- время начала консультации;
- допустимый интервал в расписании специалиста.

Reservation сохраняет согласованные условия консультации.

ACTIVE Reservation имеет ограниченный срок действия, который устанавливается платформой.

Она может быть:

- подтверждена;
- отменена;
- завершена по истечении TTL.

## 2.2. Booking

Booking представляет подтверждённую запись на консультацию.

Booking создаётся только после успешного подтверждения ACTIVE Reservation.

Она ссылается на исходную Reservation и использует сохранённые в ней условия.

Booking не создаёт независимое резервирование времени.

## 2.3. ScheduleOccupancy

ScheduleOccupancy представляет временной интервал, который в настоящий момент препятствует созданию пересекающихся Reservation.

Она создаётся одновременно с ACTIVE Reservation.

При подтверждении Reservation существующая Occupancy сохраняется.

При отмене или истечении Reservation Occupancy удаляется.

При допустимой отмене подтверждённой Booking её Occupancy освобождается.

После завершения занятого интервала Occupancy удаляется фоновой очисткой.

История Reservation и Booking сохраняется независимо от Occupancy.

---

# 3. Ответственность домена

Модуль Booking владеет:

- Reservation;
- Booking;
- ScheduleOccupancy;
- переходами состояний;
- обработкой истечения Reservation;
- метаданными отмены;
- созданием и освобождением занятости.

Остальные модули имеют собственную ответственность.

| Модуль | Ответственность |
|---|---|
| User | Идентичность и состояние учётной записи |
| Client | Профиль клиента |
| Specialist | Профиль и допуск специалиста |
| Service | ServiceOffering |
| Schedule | Конфигурация рабочего расписания |
| Availability | Расчёт доступного времени |
| Booking | Жизненный цикл Reservation, Booking и Occupancy |
| Outcome | Подтверждение результата консультации |
| Review | Отзывы о специалистах |
| Notification | Уведомления пользователей |
| Admin | Административные решения и модерация |

Booking не изменяет напрямую сущности, принадлежащие Schedule, Service, Specialist или Outcome.

Межмодульные сценарии выполняются через прикладную оркестрацию.

# 4. Модель Reservation

## 4.1. Основные поля

| Поле | Назначение |
|---|---|
| id | Идентификатор Reservation |
| clientId | Клиент |
| specialistId | Специалист |
| serviceOfferingId | Выбранная услуга |
| status | Текущее состояние Reservation |
| sessionStart | Абсолютное время начала консультации |
| sessionEnd | Абсолютное время окончания консультации |
| createdAt | Время создания Reservation |
| expiresAt | Дедлайн подтверждения |
| cancelledAt | Время отмены |
| cancellationInitiator | Инициатор отмены |
| cancellationReason | Причина отмены |

Дополнительно Reservation содержит исторические снимки согласованных условий.

## 4.2. Snapshot услуги

В Reservation сохраняются:

- название услуги;
- длительность консультации;
- длительность перерыва после консультации;
- цена;
- валюта.

Эти значения считываются из одного согласованного состояния ServiceOffering при создании Reservation.

Последующее изменение или деактивация ServiceOffering не изменяет snapshot.

## 4.3. Snapshot правил отмены

Reservation сохраняет:

`clientCancellationNoticeSnapshot`

Это значение определяет условия отмены, действовавшие при создании Reservation.

После подтверждения Booking продолжает использовать первоначально согласованное правило.

Специалист не может задним числом изменить условия отмены существующей Booking путём изменения текущей BookingPolicy.

## 4.4. Историческая целостность

Reservation сохраняется после:

- подтверждения;
- отмены;
- истечения;
- отмены связанной Booking;
- удаления Occupancy.

Исторические условия не должны восстанавливаться из текущей ServiceOffering или BookingPolicy, поскольку эти объекты могут изменяться.

---

# 5. Состояния Reservation

Reservation имеет четыре состояния.

## 5.1. ACTIVE

Reservation временно удерживает время консультации.

Инварианты:

- существует связанная ScheduleOccupancy;
- выбранный интервал был допустим при создании;
- подтверждение возможно до истечения TTL с учётом остальных бизнес-ограничений;
- срок действия определяется платформой.

ACTIVE Reservation ещё не является подтверждённой Booking.

## 5.2. CONFIRMED

Reservation успешно подтверждена.

Для неё создана Booking.

Первоначальная Occupancy сохраняется и продолжает блокировать пересекающиеся интервалы.

Исторический snapshot Reservation не изменяется.

## 5.3. CANCELLED

Reservation отменена до подтверждения.

Сохраняются:

- cancelledAt;
- cancellationInitiator;
- cancellationReason, если применимо.

Связанная Occupancy удаляется.

Повторная активация CANCELLED Reservation запрещена.

## 5.4. EXPIRED

Срок подтверждения Reservation истёк, и соответствующий переход состояния был обработан.

Occupancy удаляется.

EXPIRED Reservation нельзя подтвердить или повторно активировать.

---

# 6. Переходы состояний Reservation

Разрешённые переходы:

```text
ACTIVE → CONFIRMED
ACTIVE → CANCELLED
ACTIVE → EXPIRED
```

Запрещённые переходы:

```text
CANCELLED → ACTIVE
EXPIRED → ACTIVE
CONFIRMED → ACTIVE
CONFIRMED → CANCELLED
```

Отмена уже подтверждённой консультации изменяет состояние Booking, а не исходной CONFIRMED Reservation.

## 6.1. Предусловия переходов

Каждый переход должен проверять:

- текущее состояние Reservation;
- права инициатора;
- применимые временные ограничения;
- административные ограничения;
- согласованность связанной Occupancy.

## 6.2. Конкурентность

Конкурентные переходы одной Reservation сериализуются посредством строковой блокировки PostgreSQL.

Критические условия повторно проверяются после получения блокировки.

---

# 7. Модель Booking

## 7.1. Создание

Booking создаётся исключительно из успешно подтверждённой ACTIVE Reservation.

Каждая Booking ссылается на одну Reservation.

Одна Reservation может породить не более одной Booking.

## 7.2. Основные поля

| Поле | Назначение |
|---|---|
| id | Идентификатор Booking |
| reservationId | Исходная Reservation |
| clientId | Клиент |
| specialistId | Специалист |
| status | Состояние Booking |
| createdAt | Время создания подтверждённой записи |
| cancelledAt | Время отмены |
| cancellationInitiator | Инициатор отмены |
| cancellationReason | Причина отмены |

Booking использует исторические условия исходной Reservation.

## 7.3. Принадлежность

Клиент и специалист Booking должны совпадать с участниками соответствующей Reservation.

Этот инвариант защищается в том числе ограничениями базы данных.

## 7.4. Неизменяемость условий

После подтверждения согласованные условия консультации нельзя незаметно изменить.

Следующие операции не изменяют существующие Booking:

- обновление ServiceOffering;
- изменение рабочего расписания;
- изменение BookingPolicy;
- смена часового пояса специалиста.

Перенос консультации не реализуется посредством прямого изменения временных полей Reservation или Booking.

В будущем перенос должен быть отдельным бизнес-сценарием.

---

# 8. Состояния Booking

Жизненный цикл подтверждённой записи отделён от результата проведения консультации.

## 8.1. CONFIRMED

Консультация успешно забронирована.

Согласованные абсолютные времена начала и окончания сохранены.

Occupancy остаётся до предусмотренного освобождения или фоновой очистки после occupiedUntil.

## 8.2. CANCELLED

Подтверждённая консультация отменена.

Сохраняются метаданные отмены.

Occupancy освобождается.

Booking остаётся в базе для истории и аналитики.

## 8.3. Результат консультации

Фактическое проведение консультации определяется через SessionOutcome.

Достижение запланированного времени окончания само по себе не означает успешное проведение.

Прежняя модель непосредственного перехода Booking в COMPLETED или NO_SHOW недостаточна для согласованного механизма двухстороннего подтверждения.

Окончательный набор BookingStatus должен быть синхронизирован с Outcome Domain Design.

До завершения этого проектирования запрещается вводить дополнительные состояния, дублирующие результат SessionOutcome.

---

# 9. Переходы состояний Booking

Для подтверждённой Booking предусмотрена допустимая отмена:

```text
CONFIRMED → CANCELLED
```

Исходная Reservation остаётся CONFIRMED.

Факт проведения консультации устанавливается отдельным доменом Outcome.

## 9.1. Запрещённые операции

Запрещается:

- повторно активировать CANCELLED Booking;
- создавать Booking из EXPIRED Reservation;
- создавать вторую Booking из той же Reservation;
- изменять исторические условия услуги;
- считать консультацию успешно проведённой без утверждённой проверки SessionOutcome.

# 10. Модель ScheduleOccupancy

## 10.1. Назначение

ScheduleOccupancy представляет занятый интервал, препятствующий созданию пересекающихся Reservation.

Она не является AvailabilitySlot.

Она не описывает все потенциально доступные интервалы.

## 10.2. Временные границы

Интервал консультации:

```text
[sessionStart, sessionEnd)
```

Полный занятый интервал:

```text
[sessionStart, occupiedUntil)
```

Где:

```text
occupiedUntil = sessionEnd + breakDuration
```

Все границы хранятся как абсолютные моменты времени.

## 10.3. Полуоткрытые интервалы

Используется семантика `[start, end)`.

Пример:

```text
Occupancy A: [10:00, 11:30)
Occupancy B: [11:30, 12:30)
```

Интервалы не пересекаются.

Но:

```text
Occupancy A: [10:00, 11:30)
Occupancy B: [11:00, 12:00)
```

Интервалы пересекаются и не могут одновременно существовать у одного специалиста.

## 10.4. Перерыв после консультации

Перерыв:

- принадлежит выбранной ServiceOffering;
- сохраняется в snapshot Reservation;
- учитывается при расчёте occupiedUntil;
- блокирует пересекающиеся Reservation;
- может выходить за рабочее окно;
- может пересекать локальную полночь.

При этом сама консультация должна целиком помещаться в одно непрерывное рабочее окно.

## 10.5. Отсутствие статуса Occupancy

ScheduleOccupancy не использует статусы:

- FREE;
- RESERVED;
- BOOKED;
- BLOCKED;
- RELEASED.

Наличие строки означает существование действующего удержания интервала.

## 10.6. Принадлежность

Каждая Occupancy принадлежит ровно одной Reservation.

Историческая Reservation может больше не иметь Occupancy.

Одна Reservation может иметь не более одной действующей Occupancy.

---

# 11. Жизненный цикл Occupancy

| Событие | Reservation | Booking | Occupancy |
|---|---|---|---|
| Создание Reservation | ACTIVE | Отсутствует | Создаётся |
| Подтверждение Reservation | CONFIRMED | CONFIRMED | Сохраняется |
| Отмена ACTIVE Reservation | CANCELLED | Отсутствует | Удаляется |
| Истечение ACTIVE Reservation | EXPIRED | Отсутствует | Удаляется |
| Отмена Booking | CONFIRMED | CANCELLED | Удаляется |
| Достижение occupiedUntil | История сохраняется | История сохраняется | Удаляется фоновой очисткой |
| Разрешение SessionOutcome | Не меняется | История сохраняется | Независима |

## 11.1. Атомарность

Изменение бизнес-состояния и освобождение Occupancy выполняются в одной транзакции.

## 11.2. Фоновая очистка

После occupiedUntil Occupancy больше не должна блокировать будущие записи.

Фоновый обработчик удаляет такую строку.

Он не должен оставлять ACTIVE Reservation без обязательного удержания вследствие некорректной очистки.

## 11.3. Независимость от Outcome

Очистка Occupancy не ожидает:

- ответа клиента;
- ответа специалиста;
- административного разрешения спора;
- создания Review.

Результат консультации и её история хранятся независимо.

# 12. Создание Reservation

## 12.1. Входные данные

Клиент выбирает:

- ServiceOffering;
- время начала консультации.

Идентичность клиента определяется через доверенный SecurityContext.

Переданный в запросе clientId не является доказательством личности.

## 12.2. Предусловия

Перед созданием проверяются:

- право клиента создавать Reservation;
- существование и активность ServiceOffering;
- эффективный допуск специалиста;
- принадлежность времени горизонту бронирования;
- соответствие локального начала 15-минутной сетке;
- допустимость локального начала по правилам DST;
- попадание консультации в непрерывное рабочее окно;
- соблюдение minimumBookingNotice;
- отсутствие конфликтующей Occupancy.

## 12.3. Транзакционный сценарий

```text
Client выбирает ServiceOffering и время
    ↓
ReservationApplicationService
    ↓
ServiceOffering FOR SHARE
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
SpecialistBookingPolicy FOR SHARE
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
Расчёт sessionEnd и occupiedUntil
    ↓
Определение затронутых локальных дат
    ↓
Calendar advisory locks
    ↓
Чтение актуального расписания
    ↓
Проверка бизнес-ограничений
    ↓
Обработка конфликтующих истёкших удержаний
    ↓
Создание Reservation со snapshot
    ↓
Создание ScheduleOccupancy
    ↓
COMMIT
```

## 12.4. Гарантии PostgreSQL

GiST exclusion constraint предотвращает существование двух пересекающихся Occupancy одного специалиста.

Calendar advisory locks дополнительно согласуют создание Reservation с изменениями расписания.

## 12.5. Предварительная доступность

AvailabilityService предоставляет предварительную информацию.

ReservationApplicationService выполняет окончательную проверку.

Время, показанное как доступное, может стать недоступным до создания Reservation.

---

# 13. TTL Reservation

## 13.1. Владелец настройки

TTL устанавливается платформой.

Специалист не может изменять его индивидуально.

## 13.2. Дедлайн

Reservation содержит expiresAt.

Подтверждение разрешается только при:

```text
now < expiresAt
```

При равенстве подтверждение запрещено.

## 13.3. Получение текущего времени

Актуальное время определяется после получения критической строковой блокировки Reservation.

PostgreSQL `now()` возвращает время начала транзакции и не подходит как источник свежего времени после длительного ожидания блокировки.

## 13.4. Expiration Scheduler

Фоновый обработчик периодически ищет ACTIVE Reservation с истёкшим TTL.

```text
Получение кандидатов
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка статуса
    ↓
Получение актуального времени
    ↓
Проверка expiresAt
    ↓
ACTIVE → EXPIRED
    ↓
DELETE Occupancy
    ↓
COMMIT
```

## 13.5. SKIP LOCKED

При пакетной обработке допускается:

```sql
FOR UPDATE SKIP LOCKED
```

Пропущенные строки должны оставаться доступными для следующих запусков.

## 13.6. Идемпотентность

Повторная обработка уже истёкшей Reservation не должна создавать новые изменения или нарушать согласованность.

---

# 14. Подтверждение Reservation

## 14.1. Предусловия

Для подтверждения необходимы:

- существующая Reservation;
- соответствие клиента владельцу;
- статус ACTIVE;
- `now < expiresAt`;
- корректная связанная Occupancy;
- действующий эффективный допуск специалиста.

## 14.2. Эффективный допуск

Подтверждение разрешено при одновременном выполнении:

```text
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

Нельзя проверять исключительно bookingAllowed и игнорировать блокировку аккаунта или отсутствие одобрения специалиста.

Любая административная операция, лишающая специалиста допуска, должна использовать согласованный транзакционный протокол.

## 14.3. Порядок блокировок

```text
BEGIN
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка допуска и состояния
    ↓
Получение актуального времени
    ↓
Проверка now < expiresAt
    ↓
Reservation → CONFIRMED
    ↓
Создание Booking
    ↓
Сохранение Occupancy
    ↓
COMMIT
```

## 14.4. Уникальность

База данных обеспечивает:

```text
UNIQUE(bookings.reservation_id)
```

Одна Reservation не может создать две Booking.

## 14.5. Изменение услуги и расписания

Подтверждение не выполняет повторный поиск доступности.

Законно созданная Reservation может быть подтверждена, если:

- она остаётся ACTIVE;
- TTL не истёк;
- специалист сохраняет допуск;
- отсутствует иное утверждённое ограничение.

Обычное изменение расписания не аннулирует Reservation.

Изменение ServiceOffering не влияет на исторический snapshot.

---

# 15. Отмена ACTIVE Reservation

## 15.1. Условия

ACTIVE Reservation может быть отменена разрешённой бизнес-операцией.

Инициатор и причина сохраняются в необходимых случаях.

## 15.2. Изменения

В одной транзакции:

```text
ACTIVE → CANCELLED
```

И:

```text
DELETE ScheduleOccupancy
```

## 15.3. Метаданные

Сохраняются:

- cancelledAt;
- cancellationInitiator;
- cancellationReason, когда применимо.

## 15.4. Конкурентность

Отмена согласуется с:

- подтверждением;
- истечением TTL;
- повторной отменой;
- административной блокировкой.

Текущее состояние повторно проверяется после получения необходимых блокировок.

## 15.5. Повторная активация

CANCELLED Reservation не может быть восстановлена в ACTIVE.

Для новой записи создаётся новая Reservation.

---

# 16. Отмена подтверждённой Booking

## 16.1. Отмена клиентом

Клиент может отменить собственную CONFIRMED Booking до начала консультации.

Отмена остаётся допустимой даже после дедлайна своевременной отмены.

Такая операция классифицируется как поздняя отмена.

## 16.2. Дедлайн отмены

Используется snapshot исходной Reservation:

```text
clientCancellationDeadline =
    sessionStart - clientCancellationNoticeSnapshot
```

## 16.3. Поздняя отмена

Отмена считается поздней при:

```text
cancelledAt >= clientCancellationDeadline
```

при условии, что консультация ещё не началась.

## 16.4. Последствия для MVP

Поздняя отмена:

- не создаёт автоматический денежный штраф;
- не вызывает автоматических дисциплинарных санкций;
- не требует отдельного статуса LATE_CANCELLED.

Необходимая информация сохраняется для аналитики и возможных будущих правил.

## 16.5. Ограничение по времени

Обычная отмена клиентом допустима только при:

```text
now < sessionStart
```

## 16.6. После начала консультации

После sessionStart обычная клиентская отмена запрещена.

Ситуации, когда консультация не состоялась, рассматриваются через Outcome и возможные административные сценарии.

## 16.7. Транзакционная отмена

```text
BEGIN
    ↓
Проверка инициатора
    ↓
Reservation / Booking row locks
    ↓
Повторная проверка статуса и времени
    ↓
Определение поздней отмены
    ↓
Booking → CANCELLED
    ↓
Сохранение cancellation metadata
    ↓
DELETE ScheduleOccupancy
    ↓
COMMIT
```

## 16.8. Порядок блокировок

Если нужны обе строки:

```text
Reservation → Booking
```

## 16.9. Повторная доступность

Удаление Occupancy освобождает занятый интервал.

Однако отсутствие Occupancy не означает автоматическую доступность.

Новая Reservation должна соответствовать:

- актуальному расписанию;
- горизонту бронирования;
- minimumBookingNotice;
- допуску специалиста;
- активности ServiceOffering;
- отсутствию других Occupancy.

Таким образом, интервал может быть свободен, но недоступен для новой записи.

---

# 17. Отмена специалистом

Специалист может отменить отдельную подтверждённую консультацию в рамках разрешённых бизнес-правил.

Для MVP операции выполняются по одной Booking.

Массовая отмена подтверждённых консультаций не требуется.

При отмене необходимо:

- проверить принадлежность Booking специалисту;
- проверить текущее состояние;
- сохранить инициатора и причину;
- сохранить историю;
- атомарно удалить Occupancy.

Последствия для клиента и необходимые уведомления должны быть согласованы с Notification Domain Design.

Обычная отмена специалистом не равнозначна административной блокировке.

---

# 18. Административная блокировка специалиста

## 18.1. Утверждённое правило

При административной блокировке:

- создание новых Reservation запрещается;
- подтверждение ACTIVE Reservation запрещается;
- все ACTIVE Reservation специалиста немедленно отменяются;
- связанные Occupancy удаляются;
- уже подтверждённые Booking сохраняются.

## 18.2. Атомарность

Изменение допуска и отмена ACTIVE Reservation выполняются в одной транзакции.

Недопустимо сначала заблокировать аккаунт, а затем асинхронно отменять существующие ACTIVE Reservation как независимую операцию.

## 18.3. Координация

Административная операция получает:

```text
SpecialistBookingAccess FOR UPDATE
```

До обработки Reservation и изменения допуска.

## 18.4. Основной сценарий

```text
BEGIN
    ↓
Проверка полномочий администратора
    ↓
BookingAccess FOR UPDATE
    ↓
Применение ограничения допуска
    ↓
Поиск ACTIVE Reservation специалиста
    ↓
Reservation FOR UPDATE в стабильном порядке
    ↓
Повторная проверка статусов
    ↓
ACTIVE → CANCELLED
    ↓
cancellationInitiator = ADMIN
    ↓
DELETE Occupancy
    ↓
Сохранение административного действия
    ↓
COMMIT
```

## 18.5. Конкурентное подтверждение

Подтверждение Reservation получает BookingAccess FOR SHARE до Reservation FOR UPDATE.

Следовательно:

- если подтверждение законно завершилось первым, возникшая Booking сохраняется;
- если административная блокировка завершилась первой, подтверждение запрещается.

## 18.6. Конкурентное создание Reservation

Создание Reservation также получает BookingAccess FOR SHARE.

Административная операция ожидает завершения транзакций, удерживающих совместные блокировки.

После получения эксклюзивной блокировки она должна обнаружить и отменить оставшиеся ACTIVE Reservation.

## 18.7. Эффективный допуск

Разрешение на новые записи определяется сочетанием:

- User.status;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

Изменение любого состояния, которое делает специалиста недоступным для бронирования, должно проходить через общий механизм координации BookingAccess.

## 18.8. Восстановление доступа

Повторное одобрение специалиста не снимает независимое административное ограничение bookingAllowed.

Восстановление требует явной разрешённой операции.

---

# 19. Обычные изменения расписания

## 19.1. Утверждённая политика

Обычное изменение расписания не отменяет существующие ACTIVE Reservation и CONFIRMED Booking.

Правило распространяется на:

- DateSchedule;
- WeeklyScheduleVersion;
- смену режима расписания;
- другие обычные изменения рабочего графика.

## 19.2. ACTIVE Reservation

Reservation сохраняет первоначальные условия.

Она может:

- быть подтверждена до expiresAt;
- быть отменена;
- истечь по TTL.

## 19.3. CONFIRMED Booking

Подтверждённая консультация сохраняет исходное абсолютное время.

Автоматический перенос или отмена не выполняются.

## 19.4. Предупреждение специалиста

Если изменение затрагивает существующие обязательства, специалист получает предупреждение.

Изменение расписания не должно незаметно уничтожать действующие удержания или подтверждённые записи.

## 19.5. Новые Reservation

После фиксации нового графика все новые Reservation проверяются по обновлённым условиям.

## 19.6. Occupancy

Существующие Occupancy сохраняются до предусмотренного освобождения.

---

# 20. Изменение часового пояса

## 20.1. Утверждённая политика

Специалист может изменить ZoneId.

Существующие Reservation и Booking сохраняют абсолютные временные границы.

## 20.2. Историческое время

Не пересчитываются:

- sessionStart;
- sessionEnd;
- occupiedUntil;
- expiresAt.

## 20.3. Существующие обязательства

ACTIVE Reservation и CONFIRMED Booking сохраняются.

## 20.4. Новая доступность

После изменения ZoneId будущая доступность рассчитывается по новому часовому поясу.

Локальные даты и часы рабочего расписания остаются прежними.

## 20.5. Конкурентная координация

Создание Reservation использует:

```text
SpecialistTimeZoneGuard FOR SHARE
```

Изменение ZoneId использует:

```text
SpecialistTimeZoneGuard FOR UPDATE
```

Это предотвращает смешение старой и новой временной конфигурации в пределах критической операции.

## 20.6. Предупреждения

При затрагивании существующих обязательств специалист должен явно подтвердить изменение после ознакомления с последствиями.

---

# 21. Правила DST

## 21.1. Неоднозначное локальное время

Если локальное начало консультации встречается дважды при переводе часов, новая Reservation запрещена.

## 21.2. Несуществующее локальное время

Если локальное начало попадает в пропущенный промежуток при переводе часов, новая Reservation запрещена.

## 21.3. Проверка Java

Используется:

```java
ZoneRules.getValidOffsets(LocalDateTime)
```

Допустимое локальное начало должно иметь ровно одно валидное смещение.

## 21.4. Availability

AvailabilityService не должен предлагать запрещённые начала консультаций.

## 21.5. Окончательная проверка

ReservationApplicationService повторяет проверку перед созданием Reservation и Occupancy.

## 21.6. Существующие Booking

Booking с сохранёнными Instant не изменяются при DST-переходе.

## 21.7. Открытое правило

Отдельно необходимо определить поведение консультации, которая начинается в однозначное локальное время, но пересекает сам DST-переход.

Проверки одного только начала для такого сценария недостаточно.

---

# 22. Предотвращение двойного бронирования

## 22.1. Основной инвариант

У одного специалиста не могут одновременно существовать две пересекающиеся ScheduleOccupancy.

## 22.2. Ограничение PostgreSQL

Используется GiST exclusion constraint:

```sql
EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
)
```

Для совместного использования равенства BIGINT и диапазонов требуется расширение btree_gist.

## 22.3. Почему UNIQUE недостаточно

Уникальность start_time не предотвращает пересечения интервалов.

Например:

```text
10:00–11:30
10:30–11:30
```

Время начала разное, однако интервалы пересекаются.

## 22.4. Дополнительная координация

Calendar advisory locks используются для согласования создания Reservation с изменениями расписания.

Exclusion constraint остаётся окончательной защитой PostgreSQL от пересекающихся Occupancy.

---

# 23. Транзакционная модель

## 23.1. Уровень изоляции

Базовый уровень PostgreSQL:

```text
READ COMMITTED
```

## 23.2. Создание Reservation

Целевой порядок:

```text
ServiceOffering FOR SHARE
    ↓
SpecialistBookingAccess FOR SHARE
    ↓
SpecialistBookingPolicy FOR SHARE
    ↓
SpecialistTimeZoneGuard FOR SHARE
    ↓
Calendar advisory locks
    ↓
Reservation row locks при необходимости
    ↓
INSERT Reservation
    ↓
INSERT ScheduleOccupancy
```

## 23.3. Подтверждение

```text
SpecialistBookingAccess FOR SHARE
    ↓
Reservation FOR UPDATE
```

## 23.4. Истечение TTL

```text
Reservation FOR UPDATE
```

После получения Reservation row lock scheduler не должен захватывать календарные advisory locks в порядке, конфликтующем с созданием Reservation.

## 23.5. Отмена Booking

Если требуются обе строки:

```text
Reservation FOR UPDATE
    ↓
Booking FOR UPDATE
```

## 23.6. Предотвращение deadlock

Все составные операции должны соблюдать совместимый порядок блокировок.

Фактический граф PostgreSQL-блокировок проверяется с учётом:

- Hibernate flush;
- внешних ключей;
- конкурентных INSERT;
- UPDATE;
- DELETE.

## 23.7. Ошибки конкурентности

Deadlock или нарушение exclusion constraint не должны приводить к частично зафиксированному состоянию.

Повторная попытка использует новую корректную транзакцию и повторяет необходимые бизнес-проверки.

---

# 24. Просроченная Reservation при создании новой

## 24.1. Проблема

Reservation может оставаться ACTIVE после expiresAt, если scheduler ещё не обработал её.

Связанная Occupancy продолжает существовать.

## 24.2. Утверждённое поведение

Создание новой Reservation может обработать конфликтующее просроченное удержание внутри собственной транзакции.

## 24.3. Сценарий

```text
Calendar advisory locks
    ↓
Поиск конфликтующей Occupancy
    ↓
Определение исходной Reservation
    ↓
Reservation FOR UPDATE
    ↓
Повторная проверка статуса и expiresAt
    ↓
Если ACTIVE и TTL истёк:
    Reservation → EXPIRED
    DELETE Occupancy
    ↓
Повторная проверка доступности
    ↓
Создание новой Reservation и Occupancy
```

## 24.4. Безопасность

Нельзя освобождать Occupancy подтверждённой Booking только потому, что expiresAt первоначальной Reservation уже находится в прошлом.

CONFIRMED Reservation не подлежит обработке как истёкшее временное удержание.

## 24.5. Атомарность

Освобождение просроченного удержания и создание новой Reservation выполняются согласованно в одной транзакции.

---

# 25. Принадлежность и авторизация

## 25.1. Клиент

Клиент может получать и изменять только собственные Reservation и Booking в рамках разрешённых операций.

## 25.2. Специалист

Специалист может получать данные назначенных ему консультаций.

Изменяющие операции ограничиваются его полномочиями и бизнес-правилами.

## 25.3. Администратор

Административные операции требуют специальных полномочий.

Роль ADMIN не означает автоматическое право выполнять любые клиентские действия без дополнительных правил.

## 25.4. Идентичность

Идентичность инициатора определяется доверенным SecurityContext.

Идентификаторы из HTTP-запроса не используются как самостоятельное подтверждение принадлежности.

## 25.5. Конкурентные изменения

При необходимости права и принадлежность повторно проверяются внутри транзакции после получения соответствующих блокировок.

---

# 26. Право на Review

## 26.1. Утверждённое правило

Один клиент может оставить одному специалисту только один Review за всё время.

Review допускает редактирование.

## 26.2. Необходимая консультация

Для создания Review требуется хотя бы одна консультация этой пары клиент–специалист, результат которой подтверждён как успешно состоявшийся.

## 26.3. Недостаточные условия

Сами по себе право на Review не создают:

- CONFIRMED Reservation;
- CONFIRMED Booking;
- достижение запланированного окончания консультации;
- удаление Occupancy;
- неподтверждённое заявление одной стороны о проведении консультации.

## 26.4. Ответственность

Проверка права на отзыв и создание Review относятся к интеграции Review и Outcome.

Booking предоставляет исторические сведения о клиентах и специалистах консультации.

## 26.5. Ограничение базы данных

```text
UNIQUE(client_id, specialist_id)
```

Уникальность не устанавливается по booking_id.

---

# 27. Интеграция с Outcome

## 27.1. Разделение ответственности

Booking фиксирует подтверждённую запись.

SessionOutcome определяет фактический результат консультации.

## 27.2. Независимые ответы

Клиент и специалист независимо сообщают, состоялась ли консультация.

## 27.3. Окно подтверждения

Для MVP установлено окно 24 часа после консультации.

## 27.4. Успешное проведение

Два совместимых ответа OCCURRED подтверждают успешное проведение.

Процесс разрешения результата также учитывает:

- совместимые отрицательные ответы;
- отсутствие ответа одной стороны;
- противоречивые заявления;
- полное отсутствие ответов.

## 27.5. Споры

Противоречивые ответы обрабатываются через Outcome и Admin.

## 27.6. Отсутствие ответов

Если ни одна сторона не ответила, консультация не считается автоматически состоявшейся.

## 27.7. Независимость Occupancy

Обработка SessionOutcome не определяет срок хранения действующей Occupancy.

---

# 28. Доменные инварианты

## 28.1. Reservation

1. Каждая Reservation принадлежит одному клиенту и одному специалисту.
2. Каждая Reservation ссылается на одну ServiceOffering.
3. ACTIVE Reservation должна иметь необходимую Occupancy.
4. EXPIRED Reservation не может быть подтверждена.
5. CANCELLED Reservation нельзя реактивировать.
6. CONFIRMED Reservation может создать только одну Booking.
7. Исторические условия услуги остаются неизменными.
8. TTL устанавливается платформой.

## 28.2. Booking

1. Каждая Booking создаётся из Reservation.
2. Участники Booking совпадают с участниками Reservation.
3. Отмена Booking не удаляет Reservation.
4. CANCELLED Booking нельзя реактивировать.
5. Обычная отмена клиентом после начала консультации запрещена.
6. Условия Booking не пересчитываются из текущих настроек специалиста.

## 28.3. Occupancy

1. Каждая Occupancy принадлежит одной Reservation.
2. Пересекающиеся Occupancy одного специалиста запрещены.
3. Occupancy включает перерыв после консультации.
4. Используются полуоткрытые интервалы.
5. Occupancy не имеет статуса жизненного цикла.
6. Освобождение Occupancy сохраняет исторические записи.
7. Очистка после occupiedUntil не зависит от разрешения Outcome.

## 28.4. Административные ограничения

1. Допуск к бронированию зависит от состояния аккаунта, модерации и BookingAccess.
2. Административная блокировка немедленно отменяет ACTIVE Reservation.
3. Подтверждённые Booking не отменяются автоматически.
4. Обычные изменения расписания сохраняют существующие обязательства.
5. Смена часового пояса не изменяет абсолютные времена консультаций.

---

# 29. Ошибки домена

Возможные доменные исключения:

- ReservationNotFoundException;
- BookingNotFoundException;
- ReservationExpiredException;
- InvalidReservationStateException;
- InvalidBookingStateException;
- BookingConflictException;
- BookingCancellationNotAllowedException;
- SpecialistBookingBlockedException;
- ServiceOfferingNotAvailableException;
- InvalidBookingTimeException;
- ScheduleConflictException;
- UnauthorizedBookingOperationException.

Названия являются предварительными.

Окончательная иерархия должна соответствовать Common Module и Exception Handling Strategy.

## 29.1. Ошибки PostgreSQL

Необходимо обрабатывать:

- unique constraint violation;
- exclusion constraint violation;
- deadlock detected;
- foreign key violation.

## 29.2. Откат транзакции

Ошибка критической операции должна приводить к откату всех незавершённых изменений данной операции.

## 29.3. Преобразование ошибок

Инфраструктурные исключения преобразуются в понятные доменные или API-ошибки на соответствующей архитектурной границе.

# 30. Уведомления и доменные события

Booking может формировать события:

- ReservationCreated;
- ReservationCancelled;
- ReservationExpired;
- BookingConfirmed;
- BookingCancelled.

Административная отмена должна сохранять соответствующие причину и инициатора.

## 30.1. Момент публикации

Другие модули не должны обрабатывать событие как подтверждённое, если исходная операция впоследствии откатилась.

## 30.2. Доставка

Внешняя отправка уведомлений не должна без необходимости удерживать критические блокировки бронирования.

Для гарантированной доставки может использоваться transactional outbox.

Конкретный механизм определяется документами Events и Notification Domain Design.

# 31. Требования к тестированию

Для Booking необходимы модульные тесты и интеграционные тесты с PostgreSQL.

## 31.1. Переходы состояний

Проверяются:

- ACTIVE → CONFIRMED;
- ACTIVE → CANCELLED;
- ACTIVE → EXPIRED;
- запрет недопустимых переходов;
- отмена CONFIRMED Booking;
- предотвращение повторного подтверждения.

## 31.2. Временные ограничения

Проверяются:

- now до expiresAt;
- now = expiresAt;
- now после expiresAt;
- дедлайн minimumBookingNotice;
- отмена клиентом до sessionStart;
- поздняя отмена;
- отмена точно в sessionStart;
- перерыв через локальную полночь;
- DST gap;
- DST overlap.

## 31.3. Интеграционные проверки

Проверяются:

- UNIQUE(bookings.reservation_id);
- составные внешние ключи;
- GiST exclusion constraint;
- атомарное создание Reservation и Occupancy;
- освобождение Occupancy;
- сохранение исторических Booking.

## 31.4. Конкурентные сценарии

Особенно важны:

1. Две конкурирующие Reservation на пересекающееся время.
2. Две независимые Reservation на разные даты.
3. Подтверждение одновременно с истечением TTL.
4. Подтверждение одновременно с административной блокировкой.
5. Создание Reservation одновременно с административной блокировкой.
6. Создание Reservation одновременно с изменением расписания.
7. Создание Reservation одновременно с изменением ServiceOffering.
8. Очистка конфликтующего просроченного удержания.
9. Конкурентные отмены Booking.
10. Смена ZoneId одновременно с созданием Reservation.
11. Сохранение ACTIVE Reservation при обычном изменении расписания.

## 31.5. Инструменты

PostgreSQL-специфические инварианты проверяются на PostgreSQL, например через Testcontainers.

In-memory база данных не подходит для полноценной проверки GiST exclusion constraints и advisory locks.

# 32. Открытые технические вопросы

## 32.1. Окончательный BookingStatus

Необходимо окончательно согласовать набор BookingStatus с моделью SessionOutcome.

Нельзя создавать два независимых источника истины о фактическом завершении консультации.

## 32.2. DST

Требуется определить точное поведение консультации, пересекающей переход на летнее или зимнее время.

## 32.3. Нестандартные отмены

Административная отмена или исправление после начала консультации требуют отдельного бизнес-сценария.

## 32.4. Целостность Occupancy

Сейчас часть согласованности временных границ Occupancy и snapshot Reservation обеспечивается транзакционными командами.

Возможность дополнительных ограничений PostgreSQL рассматривается отдельно.

## 32.5. Идемпотентность

Нужны точные API-контракты идемпотентности для:

- создания Reservation;
- подтверждения Reservation;
- отмены Reservation;
- отмены Booking.

## 32.6. Проверка конкурентной модели

Полный порядок блокировок должен быть проверен с реальным SQL, генерируемым Hibernate, и с учётом блокировок внешних ключей PostgreSQL.

## 32.7. Административные состояния

Физическая реализация должна гарантировать, что все административные операции изменения эффективного допуска используют общий протокол координации BookingAccess.

# 33. Итог

Домен Booking PsyWeb использует двухэтапную запись на консультацию:

```text
Доступное время консультации
    ↓
ACTIVE Reservation + ScheduleOccupancy
    ↓
CONFIRMED Reservation + CONFIRMED Booking
    ↓
Проведение консультации
    ↓
Проверка результата через SessionOutcome
```

Альтернативные исходы Reservation:

```text
ACTIVE → CANCELLED
ACTIVE → EXPIRED
```

Отмена подтверждённой консультации:

```text
CONFIRMED Booking → CANCELLED Booking
```

Основные архитектурные гарантии:

- отсутствие хранимых AvailabilitySlot;
- динамическая доступность с выбором ServiceOffering;
- временное удержание с платформенным TTL;
- атомарное создание Reservation и Occupancy;
- сохранение Occupancy после подтверждения;
- защита от пересекающихся интервалов на уровне PostgreSQL;
- исторические snapshots условий услуги и отмены;
- независимость Booking от SessionOutcome;
- сохранение обязательств при обычном изменении расписания;
- немедленная отмена ACTIVE Reservation при административной блокировке;
- отсутствие автоматического переноса при смене ZoneId;
- один редактируемый Review на пару клиент–специалист после подтверждённо успешной консультации.

**Статус: DRAFT — бизнес-правила утверждены, реализация и интеграционные проверки ещё не завершены.**
