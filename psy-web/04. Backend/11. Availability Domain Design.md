## Overview

This section defines the availability domain of the PsyWeb system. It is responsible for managing specialist schedules, time slots, and ensuring correct interaction with the booking system.

The availability domain represents the temporal structure of the marketplace and is tightly coupled with booking operations.

---

# Core Concept

Availability is represented as discrete time slots created by specialists. Each slot represents a potential booking opportunity.

A slot is the atomic unit of time reservation in the system.

---

# Slot Model

## AvailabilitySlot Entity

The current `PsyWeb/main` AvailabilitySlot contains:

```text
id
specialist_id
start_time
end_time
availability_status
```

Current status values are:

```text
FREE
RESERVED
BOOKED
CANCELLED
```

The current entity does not contain a per-slot minimum booking notice override.

The approved target model additionally allows:

```text
minimumBookingNoticeOverride: Duration
```

persisted as nullable whole integer minutes.

A null override means:

```text
use Specialist.minimumBookingNotice
```

Therefore:

```text
Specialist minimumBookingNotice
→ current

AvailabilitySlot override
→ target / backlog
```

A slot represents a specific period of availability created by a Specialist.

Reservation and Booking remain separate Booking-domain entities.

---

# Slot Status Definitions

## FREE

The slot exists as active specialist availability and is not currently held by an ACTIVE Reservation or occupied by a confirmed Booking.

In the current implementation, `FREE` represents the Slot occupancy/lifecycle state.

The approved target model additionally distinguishes:

```text
FREE
```

from:

```text
bookable
```

After booking-deadline enforcement is implemented, a Slot may remain:

```text
FREE
```

while being non-bookable because its cutoff has passed.

That temporal bookability rule is target/backlog and is not yet enforced by the current Reservation creation flow.

---

## RESERVED

The slot is temporarily held by an `ACTIVE` Reservation.

Properties:

* the slot is not available for another Reservation;
* the hold is temporary;
* the Reservation owns its expiration time (`expiresAt`);
* Reservation cancellation or expiration releases the slot back to `FREE`;
* Reservation confirmation transitions the slot to `BOOKED`.

`RESERVED` must not be used for manual specialist blocking or generic system restrictions.

It represents only a temporary Reservation hold.

---

## BOOKED

The slot is occupied by a confirmed Booking.

A slot enters `BOOKED` only after an existing active Reservation is successfully confirmed.

The normal transition is:

`FREE → RESERVED → BOOKED`

There is no direct `FREE → BOOKED` transition.

While the slot is `BOOKED`:

* another Reservation cannot be created for it;
* its time range cannot be modified;
* its occupancy may be released through Booking cancellation according to the applicable cancellation flow.

---

## CANCELLED

The specialist has explicitly removed the availability represented by the slot.

`CANCELLED` is a terminal historical state.

A CANCELLED slot:

* is not bookable;
* is not returned to `FREE`;
* is not reactivated;
* remains stored so historical Reservation and Booking relationships are preserved.

If the specialist removes a slot that currently has an active Reservation or Booking, the related Reservation or Booking must be handled consistently as part of the same business operation.

---

# Slot Creation Rules

Slots are created by specialists.

A newly created slot starts in the `FREE` state.

Rules:

* `start_time` must be before `end_time`;
* active slots for the same specialist must not overlap;
* slot creation must respect applicable scheduling rules;
* a previously CANCELLED slot is historical and is not reused.

If the specialist wants to offer the same time again after cancelling a slot, a new `AvailabilitySlot` is created with a new identifier.

---

# Overlap Prevention

For one Specialist, active AvailabilitySlots must not overlap.

The canonical interval model is half-open:

```text
[startTime, endTime)
```

This means:

- `startTime` belongs to the Slot;
- `endTime` does not belong to the Slot;
- adjacent Slots are allowed.

For example:

```text
10:00–11:00
11:00–12:00
```

do not overlap.

But:

```text
10:00–11:00
10:30–11:30
```

do overlap.

For an existing interval:

```text
[existingStart, existingEnd)
```

and a new interval:

```text
[newStart, newEnd)
```

the overlap predicate is:

```text
newStart < existingEnd
&&
newEnd > existingStart
```

Equality at either boundary does not create an overlap.

---

## Active vs Historical Slots

The target overlap restriction applies only to active AvailabilitySlot states:

```text
FREE
RESERVED
BOOKED
```

`CANCELLED` is historical and must not participate in active-overlap protection.

Therefore, a previously cancelled Slot must not prevent creation of a new Slot for the same interval.

---

## Current Application Pre-check

The current `AvailabilitySlotService.createSlot(...)` already performs an application-level overlap pre-check through:

```text
AvailabilitySlotRepository.existsOverlappingSlot(...)
```

The repository currently uses the time predicate:

```text
existing.startTime < newEnd
&&
existing.endTime > newStart
```

This already gives the intended half-open `[start, end)` boundary semantics.

However, the current repository query does not yet filter by AvailabilitySlot status.

As a result, the current pre-check still considers historical `CANCELLED` Slots when checking overlap.

This is not the final target behavior.

The current pre-check also still reports an overlap through a generic exception rather than the final domain-specific conflict exception.

Both gaps belong to the remaining overlap-protection backlog.

---

## Target Defense-in-Depth Model

Application validation alone is not sufficient for this invariant.

A flow such as:

```text
check overlap
→ no conflict found
→ insert Slot
```

is vulnerable to concurrent requests.

Two transactions may both pass the pre-check before either transaction commits.

The approved target model therefore uses defense in depth:

```text
AvailabilitySlotService pre-check
+
PostgreSQL exclusion constraint
```

The application pre-check provides an early and understandable business failure in ordinary requests.

PostgreSQL remains the final persistence-level protection for concurrent writes.

---

## Target PostgreSQL Protection

The target database strategy uses:

```text
btree_gist
+
partial GiST exclusion constraint
```

The exclusion rule is equivalent to:

```sql
EXCLUDE USING gist (
    specialist_id WITH =,
    tsrange(start_time, end_time, '[)') WITH &&
)
WHERE (
    availability_status IN ('FREE', 'RESERVED', 'BOOKED')
)
```

For the current physical schema, this protection belongs to the `slots` table.

The intended stable constraint name is:

```text
no_overlapping_active_slots
```

`tsrange(..., '[)')` expresses the same half-open interval semantics used by the application pre-check.

The PostgreSQL `&&` operator detects intersecting ranges.

`btree_gist` allows `specialist_id` equality and temporal range overlap to participate in the same GiST exclusion constraint.

---

## Target Conflict Translation

Both protection paths represent the same business conflict:

```text
application pre-check detects overlap
```

and:

```text
PostgreSQL exclusion constraint rejects concurrent overlap
```

The target service/API behavior must translate both cases to the same domain conflict:

```text
SlotOverlapException
```

A raw SQL, Hibernate, or JPA exception must not become part of the external business contract.

`SlotOverlapException` and database-conflict translation are backlog work and are not yet implemented in the current `PsyWeb/main`.

---

## Current vs Target Summary

### Current

```text
application-level overlap pre-check
half-open boundary predicate
same-Specialist time comparison
```

### Remaining target work

```text
ignore CANCELLED Slots in overlap restriction
SlotOverlapException for application pre-check
btree_gist extension
partial GiST exclusion constraint
concurrent DB-level overlap protection
DB conflict → SlotOverlapException translation
```

Applied Flyway migrations must not be edited to introduce this protection.

The PostgreSQL constraint must be added through a new forward migration.

# Slot Lifecycle

AvailabilitySlot follows an explicit state machine.

## Allowed Transitions

| Transition             | Trigger                                                           | Result                                     |
| ---------------------- | ----------------------------------------------------------------- | ------------------------------------------ |
| creation → `FREE`      | Specialist creates availability                                   | Slot becomes active availability           |
| `FREE → RESERVED`      | An ACTIVE Reservation is created                                  | Slot is temporarily held                   |
| `RESERVED → FREE`      | Reservation is cancelled or expires                               | Temporary hold is released                 |
| `RESERVED → BOOKED`    | Reservation is successfully confirmed and Booking is created      | Slot becomes occupied                      |
| `BOOKED → FREE`        | Client cancels the confirmed Booking                              | Booking occupancy is released              |
| `FREE → CANCELLED`     | Specialist removes the availability                               | Slot becomes historical and unavailable    |
| `RESERVED → CANCELLED` | Specialist removes availability while it is reserved              | Reservation must be cancelled consistently |
| `BOOKED → CANCELLED`   | Specialist removes availability associated with an active Booking | Booking must be cancelled consistently     |

`CANCELLED` has no outgoing transitions.

The following transitions are not allowed:

* `FREE → BOOKED`
* `CANCELLED → FREE`
* `CANCELLED → RESERVED`
* `CANCELLED → BOOKED`

Reopening the same time after cancellation creates a new AvailabilitySlot instead of reactivating the cancelled one.

---

# Booking Integration

The Availability module owns the AvailabilitySlot lifecycle.

The Booking module owns Reservation and Booking lifecycles and coordinates availability transitions through the Availability module service boundary.

## Reservation Creation

Typical flow:

`FREE AvailabilitySlot`
→ Booking module validates Reservation creation
→ Availability module validates that the slot may be reserved
→ ACTIVE Reservation is created
→ AvailabilitySlot transitions `FREE → RESERVED`

Reservation creation and the slot transition must commit atomically.

---

## Reservation Cancellation or Expiration

When an ACTIVE Reservation is cancelled or expires:

`RESERVED → FREE`

The Reservation transition and slot release must commit consistently.

The released slot may be reserved again only if it is still before its booking deadline.

---

## Reservation Confirmation

When an ACTIVE and unexpired Reservation is successfully confirmed:

`RESERVED → BOOKED`

The operation includes:

* Reservation confirmation;
* Booking creation;
* AvailabilitySlot transition to `BOOKED`.

These changes belong to one consistency-sensitive business operation and must not leave a partial state.

---

## Booking Cancellation

When a client cancels a confirmed Booking:

`BOOKED → FREE`

The slot becomes unoccupied again.

Returning to `FREE` does not automatically mean that another client may reserve the slot. Bookability is evaluated separately using the booking deadline.

---

## Specialist Slot Removal

When the specialist explicitly removes availability, the slot transitions to `CANCELLED`.

Depending on its current state:

* `FREE → CANCELLED`;
* `RESERVED → CANCELLED`, with the active Reservation handled consistently;
* `BOOKED → CANCELLED`, with the active Booking handled consistently.

Specialist removal never returns the slot to `FREE`.

The slot remains stored as historical data.

---

# Booking Deadline and Effective Bookability

Booking deadline is an approved target rule with partially implemented supporting data.

---

## Current Supporting State

The current Specialist model already stores:

```text
minimumBookingNotice: Duration
```

PostgreSQL stores this value as:

```text
minimum_booking_notice_minutes INTEGER
```

using whole-minute persistence.

`Duration.ZERO` is valid.

The current AvailabilitySlot model does not yet contain its optional override.

The current Reservation creation flow also does not yet evaluate a booking deadline.

---

## Target Effective Notice

The approved target model allows:

```text
Specialist default minimumBookingNotice
```

and an optional:

```text
AvailabilitySlot override
```

The effective value is:

```text
slot override
when present

otherwise

Specialist minimumBookingNotice
```

The Slot override has priority over the Specialist default.

---

## Target Booking Deadline

The deadline is calculated rather than persisted:

```text
bookingDeadline =
slot.startTime - effectiveMinimumBookingNotice
```

A new Reservation may be created only while:

```text
currentTime < bookingDeadline
```

At the exact boundary:

```text
currentTime == bookingDeadline
```

creation of a new Reservation is no longer allowed.

If:

```text
effectiveMinimumBookingNotice = Duration.ZERO
```

then:

```text
bookingDeadline = slot.startTime
```

---

## FREE but Non-Bookable

Passing the booking deadline does not change AvailabilityStatus.

Therefore the target model permits:

```text
AvailabilityStatus.FREE
+
non-bookable
```

No additional status such as:

```text
EXPIRED
CLOSED
UNAVAILABLE
```

is introduced solely because the booking cutoff passed.

---

## Existing Reservation After Cutoff

The booking deadline controls creation of a new Reservation.

It does not invalidate an already-created ACTIVE Reservation.

A Reservation created before the cutoff may still be confirmed after the booking deadline while:

```text
Reservation.status = ACTIVE
```

and:

```text
currentTime < Reservation.expiresAt
```

Reservation TTL and minimumBookingNotice are independent temporal policies.

---

## Current vs Target

### Current

```text
Specialist.minimumBookingNotice
Duration ↔ whole-minute persistence
Reservation TTL / expiresAt
controlled Clock
```

### Target / backlog

```text
AvailabilitySlot minimumBookingNotice override
effective notice calculation
bookingDeadline calculation
new-Reservation cutoff enforcement
FREE-but-non-bookable behavior in Reservation creation/query logic
```

The target implementation belongs to the corresponding booking-cutoff work and must use controlled time rather than direct uncontrolled wall-clock access.

# Consistency Rules

## 1. Slot Status Represents Availability Lifecycle

AvailabilitySlot status represents whether the slot is:

* currently free;
* temporarily reserved;
* occupied by a Booking;
* permanently removed from active availability.

It does not by itself represent every condition required to create a new Reservation.

---

## 2. Slot Cannot Be Held or Occupied Concurrently by Multiple Clients

For a slot:

* at most one ACTIVE Reservation may exist at a time;
* at most one active Booking may occupy it at a time.

Historical Reservations and cancelled Bookings may remain associated with the same slot.

Concurrency protection requires transactional coordination and database-level integrity guarantees.

---

## 3. Slot State Must Be Consistent With Reservation and Booking State

The following relationships must hold during normal lifecycle processing:

* ACTIVE Reservation → slot is `RESERVED`;
* confirmed Reservation with active confirmed Booking → slot is `BOOKED`;
* cancelled or expired Reservation before Booking creation → slot returns to `FREE`, unless specialist removal moves it to `CANCELLED`;
* client-cancelled Booking → slot returns to `FREE`;
* specialist-removed availability → slot is `CANCELLED`.

Related state changes must be committed atomically where partial persistence would violate these invariants.

---

## 4. Historical State Is Preserved

AvailabilitySlot, Reservation and Booking records are not deleted as part of normal lifecycle transitions.

A single slot may therefore have:

* multiple historical Reservations;
* multiple historical Bookings after cancellation and rebooking;

while still allowing only one current hold or occupancy at a time.

---

# Business Constraints

## 1. No Overlapping Active Slots per Specialist

For one Specialist, `FREE`, `RESERVED`, and `BOOKED` Slots must not overlap.

Slot intervals use half-open semantics:

```text
[startTime, endTime)
```

Adjacent intervals are therefore valid.

`CANCELLED` Slots are historical and do not participate in the target overlap restriction.

The current application pre-check already uses the correct temporal overlap predicate, but still requires completion of status filtering and database-backed concurrency protection described in `Overlap Prevention`.

---

## 2. Slot Duration Consistency

If duration rules are introduced, they must be validated during slot creation.

AvailabilitySlot duration itself is derived from:

`end_time - start_time`

and does not require a separate lifecycle state.

---

## 3. Slot Time Immutability After Reservation

Once a slot has entered `RESERVED` or `BOOKED`:

* `start_time` cannot be modified;
* `end_time` cannot be modified.

Changing scheduled availability must be represented through the appropriate cancellation/removal workflow rather than silently changing the existing slot.

---

## 4. CANCELLED Is Terminal

A CANCELLED slot cannot return to:

* `FREE`;
* `RESERVED`;
* `BOOKED`.

If the specialist wants to offer the same time again, the system creates a new AvailabilitySlot.

---

## 5. Target Bookability Is Derived

The approved target model determines Reservation eligibility from more than AvailabilityStatus alone.

A Slot must eventually satisfy both:

```text
status == FREE
```

and:

```text
currentTime < bookingDeadline
```

However, bookingDeadline enforcement is not yet implemented in the current Availability/Reservation flow.

Therefore current code must not be described as already filtering every FREE Slot by the final booking-cutoff rule.

---

# Error Scenarios

## Current Exceptions

The current Availability domain uses typed exceptions including:

```text
InvalidAvailabilitySlotDataException
AvailabilitySlotNotFoundException
InvalidAvailabilitySlotStateException
```

Current overlap detection is a known exception-model gap:

```text
application overlap pre-check
→ IllegalArgumentException("Overlap")
```

This generic exception is not the approved final contract.

---

## Target Exceptions

The approved overlap contract uses:

```text
SlotOverlapException
extends ConflictException
```

for both:

```text
application overlap pre-check
```

and:

```text
PostgreSQL exclusion-constraint conflict
```

The target business error must not expose raw SQL/JPA exceptions.

Booking-cutoff rejection will likewise require a stable domain-level failure rather than relying on generic exceptions.

Exact implementation belongs to the corresponding exception/Availability tasks.

---

# Performance Considerations

Availability is a read-heavy but consistency-sensitive domain.

Important query patterns include:

* specialist slots by time range;
* FREE slots;
* client-bookable slots;
* slot lookup by identifier;
* current specialist schedule.

Indexes should support common time-based access patterns such as:

`specialist_id + start_time`

Bookability filtering may additionally depend on:

* status;
* start time;
* effective minimum booking notice.

Correctness under concurrent Reservation creation must not rely on query performance or application pre-checks alone.
