## Overview

This section defines the availability domain of the PsyWeb system. It is responsible for managing specialist schedules, time slots, and ensuring correct interaction with the booking system.

The availability domain represents the temporal structure of the marketplace and is tightly coupled with booking operations.

---

# Core Concept

Availability is represented as discrete time slots created by specialists. Each slot represents a potential booking opportunity.

A slot is the atomic unit of time reservation in the system.

---

# Slot Model

## AvailabilitySlot entity

Each slot contains:

- id
- specialist_id
- start_time
- end_time
- status (FREE / BOOKED / BLOCKED)

---

# Slot Status Definitions

## FREE

Slot is available for booking.

- visible to clients
- eligible for booking creation

---

## BOOKED

Slot has been reserved by a booking.

- no longer available for selection
- linked to a booking entity

---

## BLOCKED

Slot is unavailable due to:

- manual specialist blocking
- system restrictions
- administrative actions

---

# Slot Creation Rules

Slots are created by specialists.

Rules:

- start_time must be before end_time
- slots must not overlap for the same specialist
- slots must align with business rules (optional fixed duration logic)

---

# Overlap Prevention

The system enforces that:

> A specialist cannot have overlapping slots.

This is validated at:

- service layer (primary validation)
- database constraints (optional reinforcement depending on implementation)

---

# Slot Lifecycle

```
CREATED → FREE → BOOKED → (optional RELEASED / BLOCKED)
```

---

# Booking Integration

Availability domain is directly connected to booking domain.

## Booking interaction flow:

```
Client selects slot→ AvailabilityService validates slot state→ BookingService creates booking→ Slot status updated to BOOKED
```

---

# Consistency Rules

## 1. Slot is single source of availability

A slot always reflects current availability state.

---

## 2. Slot cannot be double-booked

Enforced via:

- booking.slot_id unique constraint
- transactional locking
- status validation

---

## 3. Slot state must reflect booking state

If booking is:

- CREATED/CONFIRMED → slot is BOOKED
- CANCELLED → slot may be released depending on policy

---

# Slot Query Patterns

Typical queries supported:

- get all free slots for specialist
- get slots by date range
- get slots by availability status
- get upcoming available slots

Indexes are designed for time-based queries.

---

# Time Handling Rules

All timestamps are:

- stored in UTC
- converted at API boundary if needed
- treated as immutable values once persisted

---

# Business Constraints

## 1. No overlapping slots per specialist

Prevents schedule conflicts.

---

## 2. Slot duration consistency (optional rule)

If enforced, slots must follow defined increments (e.g. 30 or 60 minutes).

---

## 3. Slot immutability after booking

Once a slot is BOOKED:

- time range cannot be modified
- only cancellation can affect state

---

# Error Scenarios

Common exceptions:

- SlotAlreadyExistsException
- SlotOverlapException
- SlotNotAvailableException
- InvalidSlotTimeRangeException

---

# Performance Considerations

- time-based indexing on specialist_id + start_time
- frequent read operations for slot search
- minimal write operations compared to booking domain

---

# Summary

The availability domain:

- defines the temporal structure of the system
- provides atomic booking units (slots)
- ensures strict non-overlapping scheduling
- integrates tightly with booking lifecycle
- acts as a read-heavy but consistency-critical subsystem
