
# 11. Проектирование домена Availability

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — бизнес-модель согласована, детали реализации требуют проверки

---

# 1. Назначение документа

Документ определяет архитектуру расчёта доступного времени консультаций в PsyWeb.

Домен Availability отвечает за предоставление клиентам актуальных вариантов времени для записи к специалисту.

Доступность рассчитывается динамически на основании:

- выбранной ServiceOffering;
- рабочего расписания специалиста;
- текущего режима расписания;
- горизонта бронирования;
- minimumBookingNotice;
- часового пояса специалиста;
- существующих ScheduleOccupancy;
- правил временных интервалов;
- эффективного допуска специалиста к бронированию.

Availability не создаёт Reservation или Booking и не удерживает время.

Предоставляемые результаты являются предварительными.

Окончательная проверка доступности и создание временного удержания выполняются в транзакционном сценарии ReservationApplicationService.

---

# 2. Основная концепция

## 2.1. Динамическая доступность

PsyWeb не использует заранее созданные AvailabilitySlot.

Вместо этого специалист задаёт правила рабочего времени, а система рассчитывает подходящие начала консультаций для выбранной услуги.

Возможное начало консультации не является отдельной сущностью PostgreSQL.

Оно формируется при выполнении запроса доступности.

## 2.2. Service-first подход

Клиент сначала выбирает ServiceOffering.

Затем система рассчитывает доступное время с учётом условий этой услуги.

Такой порядок необходим, поскольку разные услуги одного специалиста могут иметь разные:

- длительности консультаций;
- перерывы после консультаций;
- цены;
- условия проведения.

Длительность консультации непосредственно влияет на возможность разместить её внутри рабочего окна.

Перерыв влияет на занятость времени специалиста после консультации.

## 2.3. Отсутствие статусов доступности

В системе не существуют статусы AvailabilitySlot:

- FREE;
- RESERVED;
- BOOKED;
- BLOCKED.

Доступность является результатом вычисления, а не состоянием предварительно созданного объекта.

Вместо статусов используются:

- правила Schedule;
- существование или отсутствие конфликтующей Occupancy;
- временные ограничения;
- состояние допуска специалиста.

---

# 3. Разделение ответственности

В расчёте доступности участвуют несколько модулей.

| Модуль | Ответственность |
|---|---|
| Service | Условия ServiceOffering |
| Specialist | Допуск к бронированию и настройки |
| Schedule | Рабочие интервалы и календарные правила |
| Availability | Вычисление доступных начал |
| Booking | Reservation, Booking и действующая Occupancy |
| Admin | Ограничение права специалиста принимать записи |

## 3.1. Availability

AvailabilityService объединяет данные, необходимые для предварительного расчёта.

Он не становится владельцем ServiceOffering, Schedule или ScheduleOccupancy.

## 3.2. Schedule

Schedule владеет:

- SpecialistScheduleSettings;
- WeeklyScheduleVersion;
- WeeklyWorkingInterval;
- DateSchedule;
- DateScheduleInterval.

## 3.3. Booking

Booking владеет:

- Reservation;
- Booking;
- ScheduleOccupancy.

Availability получает занятые интервалы через публичный query-контракт Booking.

## 3.4. Межмодульные зависимости

AvailabilityService вправе зависеть от интерфейсов:

- ServiceOfferingQuery;
- ScheduleQuery;
- OccupancyQuery;
- SpecialistBookingAccessQuery;
- SpecialistBookingPolicyQuery;
- SpecialistTimeZoneQuery.

Booking не должен зависеть от реализации AvailabilityService.

Для повторного использования правил предназначен отдельный компонент AvailabilityPolicy.

---

# 4. ServiceOffering и расчёт времени

## 4.1. Входные условия услуги

ServiceOffering содержит:

- id;
- specialistId;
- title;
- durationMinutes;
- breakDurationMinutes;
- price;
- currency;
- active.

Для расчёта временных интервалов используются прежде всего:

- durationMinutes;
- breakDurationMinutes.

## 4.2. Длительность консультации

Длительность должна быть положительной.

`durationMinutes > 0`

Длительность не обязана быть кратной 15 минутам.

Например, услуга может длиться 50 минут.

## 4.3. Перерыв

Перерыв после консультации не может быть отрицательным.

`breakDurationMinutes >= 0`

Нулевой перерыв разрешён.

## 4.4. Расчёт окончания консультации

Для выбранного начала:

`sessionEnd = sessionStart + durationMinutes`

## 4.5. Расчёт занятого интервала

`occupiedUntil = sessionEnd + breakDurationMinutes`

Полный интервал занятости:

`[sessionStart, occupiedUntil)`

## 4.6. Историческая согласованность

После создания Reservation длительность консультации и перерыв фиксируются в её snapshot.

Изменение ServiceOffering не изменяет существующие Reservation, Booking и Occupancy.

---

# 5. Режимы расписания

Специалист использует один из двух режимов:

- REGULAR;
- FLOATING.

Текущий режим хранится в SpecialistScheduleSettings.

## 5.1. REGULAR

REGULAR предполагает недельное расписание, действующее в определённом календарном периоде.

Для каждой даты система определяет подходящую WeeklyScheduleVersion.

Затем проверяет существование DateSchedule с purpose=OVERRIDE.

Если OVERRIDE существует, он заменяет недельный график соответствующей даты.

## 5.2. FLOATING

FLOATING предполагает ручное задание рабочих интервалов отдельных дат.

Используется DateSchedule с purpose=MANUAL.

Если MANUAL для конкретной даты отсутствует, дата считается нерабочей.

## 5.3. Неактивные данные

При смене режима ранее созданные данные другого режима могут сохраняться.

Они не участвуют в расчёте эффективной доступности, пока соответствующий режим не активен.

## 5.4. Смена режима

Смена режима является операцией изменения календарной конфигурации.

Существующие ACTIVE Reservation и CONFIRMED Booking сохраняются.

Новая доступность рассчитывается согласно новому режиму после фиксации изменения.

---

# 6. Регулярное недельное расписание

## 6.1. WeeklyScheduleVersion

WeeklyScheduleVersion представляет полный недельный шаблон для определённого периода действия.

Основные поля:

- specialistId;
- effectiveFrom;
- effectiveUntil;
- набор WeeklyWorkingInterval.

## 6.2. Период действия

effectiveFrom включается в период.

effectiveUntil также включается, если задан.

NULL для effectiveUntil означает отсутствие установленной верхней даты.

## 6.3. Непересечение версий

У специалиста не могут одновременно действовать две WeeklyScheduleVersion на одну календарную дату.

Это дополнительно защищается PostgreSQL exclusion constraint.

## 6.4. WeeklyWorkingInterval

Рабочий интервал содержит:

- dayOfWeek;
- startTime;
- endTime.

Используются локальные значения времени.

## 6.5. Дни недели

Используется ISO-нумерация Java DayOfWeek:

- MONDAY = 1;
- TUESDAY = 2;
- WEDNESDAY = 3;
- THURSDAY = 4;
- FRIDAY = 5;
- SATURDAY = 6;
- SUNDAY = 7.

## 6.6. Отсутствующая версия

Если для даты нет действующей WeeklyScheduleVersion, регулярные рабочие интервалы для этой даты отсутствуют.

---

# 7. Расписание отдельных дат

## 7.1. DateSchedule

DateSchedule описывает правило конкретной локальной календарной даты.

Основные поля:

- specialistId;
- scheduleDate;
- purpose;
- набор DateScheduleInterval.

## 7.2. MANUAL

MANUAL используется в режиме FLOATING.

Если MANUAL существует, применяются его интервалы.

Если отсутствует, дата нерабочая.

## 7.3. OVERRIDE

OVERRIDE используется в режиме REGULAR.

Если OVERRIDE существует, он полностью заменяет недельный шаблон для этой даты.

## 7.4. Пустой OVERRIDE

DateSchedule с purpose=OVERRIDE может существовать без рабочих интервалов.

Это означает явно закрытую дату.

Отсутствие OVERRIDE и пустой OVERRIDE имеют разную семантику:

- отсутствие OVERRIDE — применяется недельный график;
- пустой OVERRIDE — дата нерабочая.

## 7.5. Уникальность

Для одной пары specialistId и scheduleDate допускается не более одной записи каждого purpose.

`UNIQUE(specialistId, scheduleDate, purpose)`

---

# 8. Определение эффективного рабочего графика

Для каждой запрошенной локальной даты AvailabilityService получает эффективные рабочие интервалы.

## 8.1. Алгоритм REGULAR

1. Определить текущий режим.
2. Найти OVERRIDE для даты.
3. Если OVERRIDE существует, использовать его интервалы.
4. Иначе найти действующую WeeklyScheduleVersion.
5. Получить интервалы соответствующего дня недели.
6. Если версия отсутствует, вернуть пустой набор.

## 8.2. Алгоритм FLOATING

1. Найти MANUAL для даты.
2. Если MANUAL существует, использовать его интервалы.
3. Иначе вернуть пустой набор.

## 8.3. Результат

Результат представляет набор локальных рабочих интервалов:

`[startTime, endTime)`

## 8.4. Ответственность

Алгоритм определения эффективных интервалов принадлежит ScheduleQueryService.

AvailabilityService использует его результат, не дублируя правила выбора версий, OVERRIDE и MANUAL.

---

# 9. Правила рабочих интервалов

## 9.1. Корректность границ

Каждый рабочий интервал удовлетворяет:

`startTime < endTime`

## 9.2. Пересечения

Рабочие интервалы одного расписания не должны пересекаться.

Защита обеспечивается:

- доменными проверками;
- ограничениями PostgreSQL.

## 9.3. Переход через полночь

Рабочие интервалы через локальную полночь запрещены.

Например, интервал 22:00–02:00 нельзя сохранить как одно рабочее окно.

## 9.4. Непрерывность

Консультация должна полностью помещаться в одно непрерывное рабочее окно.

Нельзя объединять два отдельных рабочих интервала только потому, что они находятся в одной дате.

## 9.5. Перерыв после консультации

Перерыв не обязан полностью помещаться в рабочее окно.

Он может:

- заканчиваться после рабочего времени;
- пересекать локальную полночь;
- занимать часть следующей календарной даты.

При этом Occupancy продолжает блокировать пересекающиеся консультации.

## 9.6. Граница 24:00

Представление рабочего окна, заканчивающегося ровно в 24:00, требует отдельного технического решения.

До его утверждения не следует подменять 24:00 значением 00:00 в том же локальном дне.

---

# 10. Сетка начала консультаций

## 10.1. Шаг сетки

Начала консультаций формируются с шагом 15 минут.

Примеры допустимых локальных начал:

- 09:00;
- 09:15;
- 09:30;
- 09:45;
- 10:00.

## 10.2. Время начала рабочего окна

Если рабочее окно начинается не на границе 15-минутной сетки, кандидаты формируются с ближайшей следующей допустимой границы.

Например:

Рабочее окно:

`[09:10, 12:00)`

Первые кандидаты:

- 09:15;
- 09:30;
- 09:45.

## 10.3. Длительность услуги

Длительность услуги не обязана совпадать с шагом сетки.

Для 50-минутной консультации допустимы начала 09:00, 09:15 и другие значения сетки при соблюдении остальных ограничений.

## 10.4. Запрет округления запроса

ReservationApplicationService не должен молча округлять выбранное клиентом время.

Если клиент передал начало вне утверждённой сетки, запрос должен быть отклонён как недопустимый.

---

# 11. Размещение консультации в рабочем окне

## 11.1. Основное условие

Для рабочего окна:

`[workingStart, workingEnd)`

Консультация допустима при:

`sessionStart >= workingStart`

и

`sessionEnd <= workingEnd`

## 11.2. Проверка длительности

Проверяется полная длительность консультации.

Нельзя разрешать запись только потому, что её начало попадает внутрь рабочего окна.

## 11.3. Пример

Рабочее окно:

`09:00–12:00`

Длительность консультации:

60 минут.

Начало в 11:00 допустимо.

Начало в 11:15 недопустимо, поскольку консультация закончится в 12:15.

## 11.4. Несколько рабочих окон

Если специалист работает:

- 09:00–12:00;
- 13:00–17:00,

консультация 11:30–12:30 недопустима.

Нельзя использовать перерыв между рабочими окнами как рабочее время.

---

# 12. Горизонт бронирования

## 12.1. Настройка

Горизонт новых записей хранится в SpecialistScheduleSettings.

Допустимые значения:

- 14 дней;
- 30 дней;
- 60 дней;
- 90 дней.

Значение по умолчанию:

30 дней.

## 12.2. Назначение

Горизонт ограничивает период, на который клиент может создать новую Reservation.

## 12.3. Локальная дата

Горизонт определяется с учётом текущего ZoneId специалиста.

Он не должен зависеть от системного часового пояса сервера.

## 12.4. Изменение горизонта

Изменение bookingHorizonDays влияет только на возможность создания новых Reservation.

Существующие ACTIVE Reservation и CONFIRMED Booking сохраняются.

## 12.5. Граничные даты

Точная формула включения последней календарной даты горизонта должна быть одинаковой в AvailabilityPolicy и ReservationApplicationService.

До окончательного утверждения нельзя использовать разные трактовки в поиске доступности и создании Reservation.

---

# 13. MinimumBookingNotice

## 13.1. Назначение

minimumBookingNotice определяет, насколько заранее клиент должен создать Reservation.

Это независимое правило, не связанное с условиями поздней отмены Booking.

## 13.2. Формула

`bookingDeadline = sessionStart - effectiveMinimumBookingNotice`

Новая Reservation разрешена только при:

`now < bookingDeadline`

## 13.3. Нулевое значение

Если minimumBookingNotice равен нулю:

`bookingDeadline = sessionStart`

Следовательно, создать новую Reservation можно до начала консультации.

## 13.4. Равенство дедлайну

При:

`now = bookingDeadline`

создание новой Reservation запрещено.

## 13.5. Изменение настройки

Новая настройка применяется к новым Reservation.

Уже существующая ACTIVE Reservation сохраняет первоначально установленный TTL и право быть подтверждённой по обычным правилам.

## 13.6. Индивидуальные переопределения

В предыдущей модели предусматривалось переопределение minimumBookingNotice для отдельного AvailabilitySlot.

После отказа от AvailabilitySlot новое место хранения переопределения пока не утверждено.

В текущей целевой модели используется настройка SpecialistBookingPolicy.

Механизм индивидуальных исключений должен быть согласован отдельно, если он остаётся необходимым.

---

# 14. Часовой пояс специалиста

## 14.1. Источник истины

Текущий ZoneId специалиста хранится в SpecialistTimeZoneGuard.

Он является основным источником временной конфигурации специалиста.

## 14.2. Локальное расписание

WeeklyWorkingInterval и DateScheduleInterval используют локальное рабочее время.

## 14.3. Абсолютное время

Reservation и ScheduleOccupancy используют Instant.

В PostgreSQL абсолютные времена представлены TIMESTAMPTZ.

## 14.4. Преобразование

Для выбранной локальной даты и времени система определяет абсолютный момент с учётом ZoneId специалиста.

## 14.5. Изменение ZoneId

При изменении часового пояса:

- локальные шаблоны расписания не переписываются;
- будущая доступность рассчитывается по новому ZoneId;
- существующие Reservation сохраняют абсолютные времена;
- существующие Booking сохраняют абсолютные времена;
- Occupancy не пересчитывается.

## 14.6. Согласованность

Предварительный расчёт AvailabilityService не требует длительного удержания TimeZoneGuard.

Окончательная транзакция создания Reservation получает TimeZoneGuard FOR SHARE.

---

# 15. DST

## 15.1. Назначение

Daylight Saving Time может создавать неоднозначные или несуществующие локальные времена.

PsyWeb должен учитывать такие ситуации при формировании доступности.

## 15.2. DST gap

Во время перевода часов вперёд часть локальных времён может отсутствовать.

Новую Reservation нельзя создать на несуществующее локальное начало.

## 15.3. DST overlap

Во время перевода часов назад часть локальных времён может повторяться.

Новую Reservation нельзя создать на неоднозначное локальное начало.

## 15.4. Проверка через ZoneRules

Используется:

`ZoneRules.getValidOffsets(LocalDateTime)`

Результаты:

- 0 offsets — локальное время отсутствует;
- 1 offset — время однозначно;
- 2 offsets — время неоднозначно.

Для допустимого начала должен существовать ровно один offset.

## 15.5. Генерация доступности

AvailabilityService исключает кандидатов с запрещённым локальным началом.

## 15.6. Проверка Reservation

ReservationApplicationService повторно выполняет проверку.

Нельзя полагаться исключительно на предварительно рассчитанный список.

## 15.7. Переход внутри консультации

Отдельно необходимо определить правила консультации, которая начинается в однозначное время, но пересекает DST-переход.

До согласования точного алгоритма такая ситуация не должна автоматически считаться допустимой только на основании проверки начала.

## 15.8. Исторические Booking

Существующие Booking с сохранёнными Instant не изменяются при переходах времени.

---

# 16. ScheduleOccupancy

## 16.1. Назначение

ScheduleOccupancy хранит действующие временные интервалы, уже занятые Reservation или Booking.

Она не представляет потенциально доступное время.

## 16.2. Интервал

Используется:

`[sessionStart, occupiedUntil)`

Где:

`occupiedUntil = sessionEnd + breakDuration`

## 16.3. Полуоткрытая семантика

Два интервала не конфликтуют, если конец одного точно совпадает с началом другого.

## 16.4. Источник данных

Availability получает Occupancy через OccupancyQueryService.

Он не должен напрямую изменять BookingRepository.

## 16.5. Жизненный цикл

Occupancy:

- создаётся при ACTIVE Reservation;
- сохраняется при подтверждении Booking;
- удаляется при отмене;
- удаляется при истечении Reservation;
- удаляется после occupiedUntil фоновой очисткой.

## 16.6. Отсутствие Occupancy

Отсутствие Occupancy само по себе не означает, что время доступно.

Необходимо также проверить расписание, услуги, горизонт, дедлайн и допуск специалиста.

---

# 17. Проверка пересечений

## 17.1. Правило

Кандидат недоступен, если его полный занятый интервал пересекается с существующей Occupancy того же специалиста.

## 17.2. Математическая проверка

Для двух полуоткрытых интервалов:

`[aStart, aEnd)`

и

`[bStart, bEnd)`

пересечение существует при:

`aStart < bEnd AND bStart < aEnd`

## 17.3. Пример

Существующая Occupancy:

`[10:00, 11:30)`

Новая консультация с перерывом:

`[11:00, 12:15)`

Кандидат недоступен.

## 17.4. Соприкасающиеся интервалы

Существующая Occupancy:

`[10:00, 11:30)`

Новый интервал:

`[11:30, 12:30)`

Кандидат не конфликтует.

## 17.5. Проверка PostgreSQL

Окончательная защита осуществляется через GiST exclusion constraint.

Предварительная проверка Availability не заменяет ограничение PostgreSQL.

---

# 18. Алгоритм расчёта доступности

## 18.1. Входные параметры

Концептуальный запрос:

`getAvailableStarts(specialistId, serviceOfferingId, fromDate, toDate)`

Параметры:

- specialistId;
- serviceOfferingId;
- начальная локальная дата;
- конечная локальная дата.

## 18.2. Проверка запроса

Сервис проверяет:

- корректность диапазона дат;
- существование специалиста;
- существование услуги;
- принадлежность услуги специалисту;
- активность услуги;
- возможность специалиста принимать новые записи.

## 18.3. Получение конфигурации

Загружаются:

- ServiceOffering;
- SpecialistBookingAccess;
- SpecialistBookingPolicy;
- SpecialistScheduleSettings;
- SpecialistTimeZoneGuard.

## 18.4. Получение расписания

Для каждой допустимой локальной даты определяется эффективный рабочий график.

## 18.5. Генерация кандидатов

Внутри каждого рабочего окна формируются возможные начала по 15-минутной сетке.

## 18.6. Проверка длительности

Для каждого кандидата рассчитывается sessionEnd.

Консультация должна полностью помещаться в одно непрерывное рабочее окно.

## 18.7. Проверка временных ограничений

Проверяются:

- bookingHorizonDays;
- minimumBookingNotice;
- DST;
- допустимость будущего времени начала.

## 18.8. Расчёт Occupancy

Для оставшихся кандидатов определяется occupiedUntil.

## 18.9. Исключение конфликтов

Из списка удаляются кандидаты, полный занятый интервал которых пересекается с существующей ScheduleOccupancy.

## 18.10. Результат

Сервис возвращает набор допустимых начал консультаций.

Результат не представляет созданные Reservation и не гарантирует сохранение доступности до следующего запроса.

---

# 19. Концептуальный пример

Специалист использует REGULAR.

Рабочий интервал:

`09:00–12:00`

Выбранная услуга:

- durationMinutes = 60;
- breakDurationMinutes = 15.

Существующая Occupancy:

`[10:00, 11:15)`

Предположим, что остальные условия бронирования соблюдены.

## 19.1. Кандидаты до учёта Occupancy

Возможные начала:

- 09:00;
- 09:15;
- 09:30;
- 09:45;
- 10:00;
- 10:15;
- 10:30;
- 10:45;
- 11:00.

Каждая консультация должна завершиться не позднее 12:00.

## 19.2. Проверка полного занятого интервала

Для начала 09:00:

- sessionEnd = 10:00;
- occupiedUntil = 10:15.

Пересечение с Occupancy [10:00, 11:15) существует.

Следовательно, начало 09:00 недоступно.

Для начала 11:15:

- sessionEnd = 12:15.

Консультация выходит за рабочее окно.

Следовательно, начало 11:15 также недоступно.

## 19.3. Результат

В этом примере все кандидаты конфликтуют с существующей Occupancy либо выходят за рабочее окно.

Доступных начал нет.

Пример показывает, почему при расчёте необходимо учитывать одновременно:

- длительность консультации;
- перерыв;
- рабочее окно;
- существующую занятость.

---

# 20. Предварительный характер Availability

## 20.1. Read-heavy модель

AvailabilityService преимущественно выполняет операции чтения.

Он не создаёт или изменяет Occupancy.

## 20.2. Отсутствие удержания

При получении списка доступных начал время не резервируется.

Два клиента могут одновременно увидеть одно и то же доступное начало.

Это допустимо.

## 20.3. Изменение данных

Между запросом Availability и созданием Reservation специалист может:

- изменить расписание;
- изменить ServiceOffering;
- изменить minimumBookingNotice;
- изменить timeZone;
- потерять допуск к бронированию.

Другой клиент также может создать Reservation.

## 20.4. Окончательная проверка

Поэтому ReservationApplicationService заново проверяет актуальные условия в транзакции.

## 20.5. Гарантия

Availability не обещает, что возвращённое время останется свободным.

Система гарантирует отсутствие двойного бронирования при окончательном создании Reservation.

---

# 21. Создание Reservation и конкурентность

## 21.1. Транзакционная координация

Создание Reservation выполняется не AvailabilityService, а ReservationApplicationService.

## 21.2. Основной порядок

1. ServiceOffering FOR SHARE.
2. SpecialistBookingAccess FOR SHARE.
3. SpecialistBookingPolicy FOR SHARE.
4. SpecialistTimeZoneGuard FOR SHARE.
5. Расчёт временных границ и затронутых локальных дат.
6. Calendar advisory locks.
7. Повторное чтение актуального расписания.
8. Проверка Occupancy.
9. Обработка конфликтующего просроченного удержания при необходимости.
10. Создание Reservation.
11. Создание ScheduleOccupancy.
12. COMMIT.

## 21.3. Advisory locks

Логический ключ:

`(specialistId, localDate)`

Блокировки захватываются в стабильном порядке дат.

Если перерыв пересекает локальную полночь, должны учитываться все необходимые затронутые даты.

## 21.4. PostgreSQL exclusion constraint

Дополнительно применяется:

```sql
EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
)
```

Это предотвращает пересечение действующих Occupancy одного специалиста.

## 21.5. READ COMMITTED

Базовый уровень изоляции — READ COMMITTED.

Его недостаточно без согласованного протокола блокировок и ограничений PostgreSQL.

---

# 22. Изменение расписания

## 22.1. Обычные изменения

Специалист может изменять:

- DateSchedule;
- WeeklyScheduleVersion;
- schedule mode;
- booking horizon.

## 22.2. Существующие обязательства

Обычные изменения расписания не отменяют автоматически:

- ACTIVE Reservation;
- CONFIRMED Booking.

## 22.3. Предупреждение

Если изменение затрагивает существующие обязательства, специалист должен получить соответствующее предупреждение.

## 22.4. Новая доступность

После изменения графика новые запросы используют обновлённые правила.

## 22.5. Конкурентность

Изменение расписания координируется с созданием Reservation посредством календарных блокировок и конфигурационных механизмов.

## 22.6. WeeklyScheduleVersion

Изменение регулярного расписания может затрагивать множество дат.

Для него используется специальный протокол координации защищённого горизонта.

## 22.7. Смена timeZone

Изменение часового пояса защищается TimeZoneGuard FOR UPDATE.

Reservation использует TimeZoneGuard FOR SHARE.

Существующие абсолютные времена не пересчитываются.

---

# 23. Административная блокировка

## 23.1. Эффективный допуск

Специалист может принимать новые Reservation, только если:

- User.status = ACTIVE;
- Specialist.approvalStatus = APPROVED;
- SpecialistBookingAccess.bookingAllowed = TRUE.

## 23.2. Предварительный поиск

AvailabilityService не должен предлагать доступное время специалиста, который не имеет эффективного допуска.

## 23.3. Административное изменение

Изменение состояния, лишающее специалиста допуска, выполняется через согласованный административный механизм.

## 23.4. ACTIVE Reservation

При административной блокировке все ACTIVE Reservation специалиста немедленно отменяются.

Их Occupancy удаляется.

## 23.5. CONFIRMED Booking

Подтверждённые Booking автоматически не отменяются.

## 23.6. Новая доступность

После блокировки новые доступные начала для бронирования не предоставляются.

---

# 24. API и Query-контракты

## 24.1. Основной сценарий

Предварительный сервисный контракт:

`getAvailableStarts(specialistId, serviceOfferingId, fromDate, toDate)`

## 24.2. Результат

Возможные поля результата:

- serviceOfferingId;
- specialistId;
- ZoneId специалиста;
- список абсолютных sessionStart;
- при необходимости локальное представление начала.

## 24.3. Абсолютное время

Передаваемые временные значения должны быть однозначными.

Для API предпочтительно представление абсолютного момента с явным UTC offset или Instant.

## 24.4. Локальное представление

Клиентский интерфейс может показывать время в часовом поясе специалиста или пользователя.

Однако выбор и создание Reservation должны опираться на однозначно определённое время.

## 24.5. Ограничения

Не следует возвращать JPA-сущности напрямую через REST.

Используются DTO.

## 24.6. Пагинация и диапазон

Максимальная длина одного запроса доступности должна быть ограничена.

Точный API-лимит определяется отдельно.

# 25. Ошибки домена

Типичные ошибки:

- ServiceOfferingNotFoundException;
- ServiceOfferingNotAvailableException;
- SpecialistBookingBlockedException;
- InvalidAvailabilityRangeException;
- InvalidBookingTimeException;
- ScheduleNotAvailableException;
- BookingDeadlinePassedException;
- BookingConflictException.

Названия предварительные.

Они должны быть согласованы с общей стратегией обработки исключений PsyWeb.

## 25.1. Пустая доступность

Отсутствие подходящих начал в корректном запросе не является исключительной ситуацией.

AvailabilityService возвращает пустой результат.

## 25.2. Некорректный запрос

Некорректный диапазон дат или недопустимые параметры должны приводить к соответствующей ошибке валидации.

## 25.3. Конкурентный конфликт

Если время стало занято после предварительного поиска, окончательная операция создания Reservation сообщает о конфликте.

# 26. Производительность

## 26.1. Характер нагрузки

Availability — преимущественно read-heavy подсистема.

Количество запросов доступности может существенно превышать количество созданных Reservation.

## 26.2. Пакетное чтение

При расчёте доступности на несколько дат рекомендуется загружать расписание и Occupancy для диапазона, а не выполнять отдельные запросы для каждого кандидата.

## 26.3. Индексы

Важны индексы:

- ServiceOffering по specialistId;
- DateSchedule по specialistId и scheduleDate;
- WeeklyScheduleVersion по specialistId и периоду действия;
- Occupancy по специалисту и временным пересечениям.

## 26.4. GiST

GiST exclusion constraint обеспечивает защиту от пересечений Occupancy и создаёт соответствующий индекс.

## 26.5. Вычисления

Фильтрация кандидатов должна избегать неоправданного повторения одинаковых проверок и обращений к PostgreSQL.

## 26.6. Кэширование

Кэширование доступности может рассматриваться в будущем.

Кэш не должен становиться источником истины при создании Reservation.

## 26.7. Корректность

Оптимизация предварительных запросов не должна ослаблять транзакционные гарантии Booking.

---

# 27. Тестирование

## 27.1. Расчёт рабочих интервалов

Проверяются:

- REGULAR без OVERRIDE;
- REGULAR с OVERRIDE;
- пустой OVERRIDE;
- FLOATING с MANUAL;
- FLOATING без MANUAL;
- отсутствие WeeklyScheduleVersion;
- несколько последовательных версий.

## 27.2. Генерация кандидатов

Проверяются:

- сетка 15 минут;
- рабочее окно не на границе сетки;
- длительность 50 минут;
- консультация ровно до конца рабочего окна;
- консультация за пределами рабочего окна;
- несколько отдельных рабочих окон.

## 27.3. Occupancy

Проверяются:

- пересекающиеся интервалы;
- соприкасающиеся интервалы;
- перерыв после консультации;
- перерыв через локальную полночь;
- отсутствие Occupancy;
- удаление Occupancy после отмены.

## 27.4. Временные ограничения

Проверяются:

- booking horizon;
- minimumBookingNotice;
- равенство bookingDeadline;
- нулевой minimumBookingNotice;
- различные ZoneId;
- DST gap;
- DST overlap.

## 27.5. Изменения конфигурации

Проверяются:

- изменение ServiceOffering;
- изменение расписания;
- смена режима;
- изменение горизонта;
- смена часового пояса;
- административная блокировка.

## 27.6. Конкурентность

Интеграционные тесты должны проверять:

1. Две Reservation на пересекающиеся интервалы.
2. Reservation против изменения DateSchedule.
3. Reservation против изменения WeeklyScheduleVersion.
4. Reservation против изменения ServiceOffering.
5. Reservation против изменения timeZone.
6. Reservation против административной блокировки.
7. Обработку просроченного удержания.
8. Корректность блокировок при переходе Occupancy через полночь.

## 27.7. PostgreSQL

Проверки exclusion constraints, advisory locks и транзакционных конфликтов выполняются на реальном PostgreSQL, например с использованием Testcontainers.

# 28. Инварианты Availability

1. Доступность вычисляется динамически.
2. AvailabilitySlot не существует как хранимая сущность.
3. Клиент выбирает ServiceOffering до времени.
4. Доступные начала соответствуют 15-минутной сетке.
5. Консультация целиком помещается в одно непрерывное рабочее окно.
6. Перерыв входит в Occupancy, но может выходить за рабочее окно.
7. Рабочие интервалы не пересекают локальную полночь.
8. REGULAR и FLOATING используют разные источники рабочего графика.
9. OVERRIDE имеет приоритет над WeeklyScheduleVersion.
10. Пустой OVERRIDE закрывает дату.
11. Отсутствие MANUAL при FLOATING закрывает дату.
12. Новая Reservation должна соответствовать bookingHorizonDays.
13. Новая Reservation должна соответствовать minimumBookingNotice.
14. Для начала консультации запрещены DST gap и overlap.
15. Пересекающиеся Occupancy одного специалиста запрещены.
16. Отсутствие Occupancy не означает автоматическую доступность.
17. Административно недопущенный специалист не имеет доступного времени для новых Reservation.
18. Обычное изменение расписания не отменяет существующие обязательства.
19. Смена часового пояса не изменяет абсолютное время существующих Reservation и Booking.
20. Предварительный результат Availability не резервирует время.
21. Окончательная проверка выполняется при создании Reservation.
22. Корректность конкурентного бронирования обеспечивается PostgreSQL.

# 29. Открытые вопросы

## 29.1. Booking horizon

Необходимо окончательно определить включение последней календарной даты горизонта.

## 29.2. MinimumBookingNotice

Требуется решить, сохраняются ли индивидуальные переопределения после удаления AvailabilitySlot и где они должны располагаться.

## 29.3. DST

Необходимо формализовать расчёт консультации, пересекающей DST-переход.

## 29.4. Полночь

Требуется определить представление рабочего окна, заканчивающегося в 24:00.

## 29.5. Query API

Необходимо согласовать:

- максимальный диапазон запроса;
- DTO ответа;
- локальное и абсолютное представление времени;
- возможную пагинацию.

## 29.6. Concurrency

Требуется проверить фактический порядок PostgreSQL-блокировок с учётом Hibernate, FK и flush.

# 30. Итог

Availability в PsyWeb представляет динамически вычисляемую доступность консультаций.

Система не создаёт предварительные AvailabilitySlot и не хранит статусы свободного времени.

Для расчёта используются:

- ServiceOffering;
- REGULAR/FLOATING;
- WeeklyScheduleVersion;
- DateSchedule;
- SpecialistScheduleSettings;
- SpecialistBookingPolicy;
- SpecialistTimeZoneGuard;
- SpecialistBookingAccess;
- ScheduleOccupancy.

Клиент выбирает услугу, после чего получает допустимые начала консультаций.

AvailabilityService выполняет предварительный расчёт.

ReservationApplicationService повторно проверяет условия в согласованной транзакции и создаёт Reservation вместе с Occupancy.

PostgreSQL обеспечивает окончательную защиту от двойного бронирования.
