## Overview

This document defines backend module ownership and dependency rules for the PsyWeb modular monolith.

The architecture distinguishes:

```text
current modules implemented in PsyWeb/main
```

from:

```text
approved target / backlog modules
```

A module described by the architecture must not be treated as implemented unless the corresponding code exists in the current backend.

---

# Current Module Structure

The current `PsyWeb/main` contains:

```text
com.psyweb
├── user
├── specialist
├── availability
├── booking
└── common
```

These modules contain the implemented backend core.

Approved future or separately scoped modules include:

```text
auth
review
chat
notification
admin
```

Their architectural responsibilities remain useful, but they are target/backlog unless explicitly implemented.

---

# Module Dependency Rules

## Core Rule

A module owns its domain state, persistence, and lifecycle rules.

Other modules must not access another module's repository directly.

Cross-module collaboration should happen through explicit service-level boundaries.

For example:

```text
Booking
→ Availability service boundary
→ AvailabilitySlot state change
```

does not transfer ownership of AvailabilitySlot to Booking.

---

# Current Dependency Direction

The current implemented core follows approximately:

```text
user

specialist
└── user

availability
└── specialist

booking
├── user
├── specialist
└── availability

common
└── no business-module dependency
```

This direction should remain acyclic.

# 1. User Module

```text
current implementation
```

## Responsibility

Owns platform account identity and account-level state.

## Current Contains

```text
User
UserRole
UserStatus
UserService
UserRepository
user-specific exceptions
```

Current role values are:

```text
CLIENT
SPECIALIST
ADMIN
```

Current account statuses are:

```text

BLOCKED
```

The User module also owns canonical email normalization.

---

## Owns

- User identity;
- UserRole;
- UserStatus;
- email normalization;
- account lifecycle;
- User persistence.

## Does Not Own

- Specialist professional state;
- AvailabilitySlot lifecycle;
- Reservation or Booking lifecycle;
- authentication token infrastructure.

# 2. Specialist Module

## State

```text
current implementation
```

## Responsibility

Owns specialist-specific identity, professional approval lifecycle, eligibility, and Specialist-level operational settings.

Specialist is an extension of a User account rather than a separate authentication identity.

---

## Current Contains

```text
Specialist
SpecialistStatus
SpecialistService
SpecialistRepository
specialist-specific exceptions
```

Current SpecialistStatus values are:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Current lifecycle transitions are:

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

The module owns validation of these transitions.

---

## Current Professional Eligibility

Professional eligibility requires:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

User account state and Specialist professional state remain separate.

For example:

```text
SpecialistStatus.SUSPENDED
```

does not automatically imply:

```text
UserStatus.BLOCKED
```

---

## Current Operational Settings

Specialist currently owns:

```text
minimumBookingNotice
clientCancellationNotice
```

as Java:

```text
Duration
```

persisted as whole integer minutes.

---

## Target / Backlog Extensions

The complete suspension workflow additionally requires coordinated handling of future AvailabilitySlots, Reservations, and Bookings.

Immutable:

```text
SpecialistModerationAction
```

history is also target/backlog.

These target workflows do not change Specialist ownership of the actual lifecycle state.

---

## Owns

- Specialist;
- SpecialistStatus;
- lifecycle transitions;
- eligibility rules;
- Specialist-level temporal settings.

## Depends on

```text
user
common technical infrastructure
```

## Must Not

- depend on Admin;
- allow other modules to mutate Specialist persistence directly;
- merge SpecialistStatus with UserStatus;
- use SpecialistStatus as credential-verification state.

---

## Current Overlap Boundary

The application pre-check uses half-open overlap semantics:

```text
newStart < existingEnd
&&
newEnd > existingStart
```

The PostgreSQL active-slot exclusion constraint is approved target/backlog and is not yet implemented.

---

## Booking-Deadline Boundary

```text

```

setting exists today.

However:


They must not be treated as current AvailabilitySlot functionality.

---

- AvailabilitySlot persistence.

## Depends on

```text

```

## Must Not

- own Reservation lifecycle;
- own Booking lifecycle;
- access Booking repositories.

Detailed Availability state-machine/service-boundary decisions remain owned by the dedicated Availability documentation task.


```text
login orchestration

JWT validation

```

Target login requires:

```text
valid credentials
+
UserStatus.ACTIVE
```

---

# Target Admin Module

## State

```text
target / backlog
```

Admin is an orchestration boundary rather than an owner of User, Specialist, Availability, or Booking persistence.

Target administrative workflows include:

```text
Specialist approval/rejection
Specialist suspension/reinstatement
User moderation
SessionOutcome dispute resolution
```

Admin operations must call the owning business module's service boundary.

For example:

```text
Admin workflow
→ SpecialistService.suspend(...)
```

rather than direct SpecialistRepository mutation.

---

# Target Review Module

Review-specific implementation and documentation are owned by the dedicated Review backlog.

The architectural rule remains:

```text
Review does not own Booking or SessionOutcome lifecycle
```

This document does not duplicate Review-specific eligibility or persistence rules.

---

# Target Notification Module

Notification is optional secondary processing.

It must not become required for core transactional correctness.

Core state such as:

```text
Reservation
Booking
AvailabilitySlot
Specialist
```

must remain consistent even if future notification processing is unavailable.

---

# Target Chat Module

Chat/communication is separate from Booking lifecycle ownership.

If introduced, it may depend on Booking/User relationships for access control without owning those entities.

---

# Communication Rules

## 1. Service-Level Boundaries

Cross-module use cases should use the owning module's public service operations.

---

## 2. Repository Ownership

A Repository is private to the module that owns its entity.

For example:

```text
SpecialistRepository
→ Specialist module

AvailabilitySlotRepository
→ Availability module

ReservationRepository
BookingRepository
→ Booking module
```

Other modules must not directly manipulate these repositories.

---

## 3. Cross-Module Transactions

A consistency-sensitive business use case may coordinate several module services inside one transaction where required.

This does not change entity ownership.

---

## 4. Common Is Technical, Not Business Ownership

`common` exists for genuinely reusable technical infrastructure.

It must not become a way to avoid proper domain ownership.

---

# Current vs Target Dependency Summary

## Current

```text
specialist → user

availability → specialist

booking → user
booking → specialist
booking → availability

business modules → common technical infrastructure
```

## Target / Backlog

Future modules may introduce dependencies such as:

```text
auth → user

admin → user
admin → specialist
admin → booking

review → booking

notification ← business events/information
```

These dependencies become current only when their corresponding implementations exist.

---

# Summary

The implemented PsyWeb backend currently consists of:

```text
user
specialist
availability
booking
common
```

The architecture preserves:

- single ownership of business state;
- service-level cross-module collaboration;
- private repository boundaries;
- acyclic dependencies;
- transactional booking coordination;
- a small domain-independent common layer.

Auth, Admin, Review, Chat, Notification, SessionOutcome, and other approved extensions remain target/backlog until implemented.
