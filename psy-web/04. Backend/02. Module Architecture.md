
# 02. Модульная архитектура PsyWeb

**Проект:** PsyWeb  
**Архитектурный стиль:** Spring Boot Modular Monolith  
**Язык реализации:** Java 21  
**База данных:** PostgreSQL  
**Статус:** DRAFT — целевая архитектура MVP

---

# 1. Назначение документа

Документ определяет:

- логические модули backend;
- ответственность каждого модуля;
- владельцев бизнес-сущностей;
- допустимые направления зависимостей;
- правила межмодульного взаимодействия;
- границы транзакционной согласованности;
- архитектурные ограничения;
- перспективы расширения и микросервисной декомпозиции.

PsyWeb разрабатывается как единое Spring Boot приложение, разделённое на логически самостоятельные модули.

Модульная архитектура должна обеспечивать понятную структуру кода и предотвращать превращение приложения в монолит с произвольными зависимостями.

При этом модульность не должна создавать искусственные сложности там, где достаточно обычного вызова сервиса внутри одного приложения.

---

# 2. Архитектурные принципы

## 2.1. Один владелец бизнес-состояния

Каждая бизнес-сущность имеет одного логического владельца.

Владелец отвечает за:

- жизненный цикл;
- бизнес-инварианты;
- изменение состояния;
- правила сохранения;
- публичные операции над сущностью.

Другие модули не должны самостоятельно изменять принадлежащие ему данные.

## 2.2. Управляемые зависимости

Модули могут зависеть друг от друга, если это необходимо бизнес-сценарию.

Зависимости должны быть:

- обоснованными;
- направленными;
- явными;
- по возможности ациклическими.

Циклические зависимости между бизнес-модулями не допускаются.

## 2.3. Ограничение доступа к репозиториям

Прямое обращение к репозиторию другого модуля не используется как обычный механизм взаимодействия.

Пример нежелательной зависимости:

```text
BookingService
  ├── ServiceOfferingRepository
  ├── WorkScheduleRepository
  └── SpecialistRepository
```

Предпочтительная модель:

```text
Booking application service
  ├── ServiceOffering public contract
  ├── WorkingSchedule public contract
  └── Specialist public contract
```

Исключения из этого правила требуют отдельного архитектурного обоснования.

## 2.4. Публичные контракты

Межмодульное взаимодействие осуществляется через согласованные контракты.

В качестве контракта могут выступать:

- интерфейс прикладного сервиса;
- query-интерфейс;
- неизменяемый DTO;
- идентификатор бизнес-сущности;
- доменное или прикладное событие.

Не требуется создавать отдельный Java-интерфейс для каждого метода.

Контракт определяется реальной потребностью модуля, а не требованием искусственной симметрии.

## 2.5. Разделение команд и запросов

Команды изменяют бизнес-состояние.

Запросы получают данные.

Примеры команд:

- создать Reservation;
- подтвердить Booking;
- изменить рабочий график;
- деактивировать услугу.

Примеры запросов:

- получить условия услуги;
- получить рабочие окна;
- найти доступные начала консультации;
- получить историю записей.

Разделение команд и запросов не требует внедрения полноценной CQRS-архитектуры.

## 2.6. Транзакционная согласованность

Транзакция охватывает бизнес-операцию, а не обязательно один модуль.

Если корректность операции требует изменения нескольких связанных сущностей, изменения должны быть согласованы атомарно.

Логическое разделение модулей не является основанием ослаблять критические гарантии бронирования или обновления токенов.

## 2.7. Минимальная необходимая сложность

Не допускается создание лишних абстракций, универсальных сервисов и пустых пакетов только ради архитектурной красоты.

Устаревшие сущности и методы удаляются после переноса необходимых бизнес-правил.

Обратная совместимость с первоначальной slot-centric моделью не является обязательной.

# 3. Целевая структура пакетов

```text
com.psyweb
│
├── user
├── auth
├── client
├── specialist
├── service
├── schedule
├── availability
├── booking
├── outcome
├── review
├── notification
├── admin
├── cancellation

```

`chat` относится к будущим возможностям и не обязан быть реализован в текущем MVP.

Предварительная структура отдельного модуля:

```text
module/
├── domain/
├── repository/
├── service/
├── web/
│   ├── controller/
│   ├── dto/
│   └── mapper/
├── exception/
├── config/
└── scheduler/
```

Это пример организации, а не обязательная структура каждого модуля.

Пакеты создаются только при наличии соответствующей функциональности.

# 4. Карта владения данными

| Модуль | Владеет |
|---|---|
| user | User, UserRole, UserStatus |
| auth | RefreshSession, RefreshToken, JWT lifecycle, security-specific модели |
| client | Client |
| specialist | Specialist, SpecialistStatus |
| service | ServiceOffering |
| schedule | SpecialistScheduleSettings, WeeklyScheduleVersion, WeeklyWorkingInterval, DateSchedule, DateScheduleInterval |
| availability | Правила расчёта доступности, вычисляемые результаты |
| booking | Reservation, Booking, ScheduleOccupancy, ServiceTermsSnapshot |
| outcome | SessionOutcome, SessionOutcomeReport |
| review | Review |
| notification | Notification, модели доставки |
| admin | Административные сценарии и история модерации |
| cancellation | Общие типы отмен |
| chat | ChatThread, Message |
| common | Общие технические компоненты |

## 4.1. Особенность административных споров

Сведения о результате консультации принадлежат Outcome.

Административный модуль инициирует разрешение спора, но не изменяет состояние SessionOutcome напрямую через чужой репозиторий.

История административного решения должна иметь одного владельца.

Предварительно:

- SpecialistModerationAction принадлежит Admin;
- DisputeResolution относится к Outcome как часть истории разрешения спора;
- Admin предоставляет операцию принятия решения и вызывает контракт Outcome.

Окончательное размещение DisputeResolution будет закреплено в Outcome Domain Design.

## 4.2. Особенность Availability

Availability не владеет физическими слотами.

Доступные варианты начала консультаций вычисляются из:

- ServiceOffering;
- рабочего расписания;
- ScheduleOccupancy;
- ограничений записи.

Availability не создаёт отдельную таблицу AvailabilitySlot.

## 4.3. Особенность Auth

RefreshSession и RefreshToken принадлежат Auth module.

User остаётся собственностью User module.

Auth не должен переносить User, UserStatus, passwordHash или правила изменения состояния аккаунта в собственную persistence-модель.

Auth обращается к User через публичные сервисные контракты.

# 5. User

## 5.1. Ответственность

Модуль управляет учётными записями пользователей.

Функции:

- создание пользователя;
- поиск пользователя;
- нормализация email;
- изменение учётных данных;
- изменение состояния аккаунта;
- предоставление данных для проверки активности пользователя;
- согласование проверки UserStatus с административной блокировкой.

## 5.2. Владеет

- User;
- UserRole;
- UserStatus.

## 5.3. Зависимости

```text
user → common
```

User не зависит от Auth.

## 5.4. Основные контракты

Примеры операций:

- createUser();
- getUser();
- getActiveUser();
- findUserByEmail();
- changeEmail();
- changePasswordHash();
- blockUser();
- activateUser().

Для Auth дополнительно требуется контракт, позволяющий согласованно получать актуальное состояние аккаунта при выдаче токенов.

Точный интерфейс определяется при реализации.

## 5.5. Ограничения

User не управляет консультациями, услугами и рабочим расписанием.

Нельзя добавлять в User управляемые коллекции всех бизнес-сущностей только для удобства навигации через JPA.

Auth не обращается напрямую к UserRepository.

## 5.6. Конкурентная блокировка аккаунта

Login и refresh должны быть согласованы с административным изменением UserStatus.

После успешного завершения блокировки новые операции выдачи токенов не должны предоставлять рабочий доступ.

Контракт User module должен поддерживать необходимую транзакционную координацию, не передавая Auth право самостоятельно изменять User.

# 6. Auth

## 6.1. Ответственность

Модуль управляет аутентификацией, access JWT и refresh-сессиями пользователей.

Для MVP используется:

**Stateless JWT Access Authentication + Stateful Refresh Sessions.**

Функции:

- регистрация в рамках существующего распределения ответственности;
- проверка паролей;
- login;
- выдача и проверка access JWT;
- создание refresh-сессий;
- refresh-token rotation;
- обнаружение повторного использования токенов;
- отзыв сессий;
- logout и logout-all;
- интеграция со Spring Security.

Восстановление доступа и подтверждение email остаются отдельными сценариями, объём которых определяется соответствующими задачами.

## 6.2. Владеет

- правилами аутентификации;
- RefreshSession;
- RefreshToken;
- жизненным циклом refresh-токенов;
- JWT issuance and validation;
- auth-specific security configuration;
- необходимыми контрактами и DTO аутентификации.

User, UserStatus и passwordHash принадлежат User module.

## 6.3. Зависимости

```text
auth → user
auth → common
```

Auth не обращается напрямую к UserRepository.

Auth не зависит от Booking, Schedule или ServiceOffering.

User не зависит от Auth.

## 6.4. Основные компоненты

Целевые компоненты:

- AuthController;
- AuthService;
- JwtService;
- RefreshSessionService;
- RefreshSessionRepository;
- RefreshTokenRepository;
- Spring Security integration.

PasswordEncoder использует Argon2id.

Точное размещение PasswordEncoder и Security-конфигурации определяется при реализации без нарушения модульных границ.

## 6.5. Сервисные контракты

Предварительные логические операции AuthService:

```java
AuthResult login(String email, String password);

AuthResult refresh(String rawRefreshToken);

void logout(String rawRefreshToken);

void logoutAll(Long userId);
```

Это описание ответственности, а не окончательные Java-сигнатуры.

RefreshSessionService управляет:

- созданием RefreshSession;
- сохранением RefreshToken;
- rotation;
- replay detection;
- отзывом сессий;
- очисткой истории.

JwtService отвечает за криптографические операции с access JWT.

User module предоставляет необходимые данные и проверку допуска аккаунта.

## 6.6. Access JWT

Access JWT:

- действует 15 минут;
- подписывается криптографическим ключом;
- содержит необходимые identity и технические claims;
- хранится только в памяти React;
- передаётся через Authorization: Bearer.

Проверяются:

- подпись;
- допустимый алгоритм;
- issuer;
- audience;
- expiration;
- обязательные claims.

Изменяемые состояния не используются как авторитетные claims:

- UserStatus;
- SpecialistStatus;
- SpecialistBookingAccess.bookingAllowed.

Актуальный UserStatus проверяется на каждом защищённом HTTP-запросе.

## 6.7. RefreshSession

RefreshSession представляет отдельный сеанс входа пользователя.

Срок действия:

**7 дней с момента login.**

Это абсолютный срок, который rotation не продлевает.

Разные устройства используют независимые refresh-сессии.

Вкладки одного браузерного профиля могут разделять одну refresh cookie.

## 6.8. RefreshToken

RefreshToken представляет отдельное поколение refresh token внутри RefreshSession.

Исходный токен:

- генерируется криптографически стойким генератором;
- содержит не менее 256 бит энтропии;
- передаётся браузеру через HttpOnly cookie;
- не хранится в PostgreSQL.

В базе сохраняется SHA-256 hash токена и метаданные его жизненного цикла.

Argon2id используется для пользовательских паролей, а не для хеширования криптографически случайных refresh tokens.

## 6.9. Идентификаторы

Новые самостоятельные auth-сущности используют UUIDv4:

```text
RefreshSession.id: UUID
RefreshToken.id: UUID
```

Связь с существующим User:

```text
RefreshSession.userId: Long / BIGINT
```

Переход существующих сущностей на UUID в эту задачу не входит.

## 6.10. Refresh Rotation

Каждый успешный refresh:

1. Проверяет предъявленный токен.
2. Проверяет состояние RefreshSession.
3. Проверяет актуальный UserStatus.
4. Помечает предыдущий RefreshToken использованным.
5. Создаёт новый RefreshToken.
6. Подготавливает новый access JWT.
7. Атомарно фиксирует изменения в PostgreSQL.

Одновременно в одной сессии допускается не более одного неиспользованного refresh token.

История поколений сохраняется для replay detection.

Grace period для повторного использования старого токена не предусматривается.

## 6.11. Concurrency

Rotation защищается PostgreSQL transactions, row locking и database constraints.

При необходимости нескольких блокировок используется согласованный порядок:

```text
User
  ↓
RefreshSession
  ↓
RefreshToken
```

Предварительный поиск токена не является окончательной проверкой его действительности.

После получения необходимых блокировок состояние повторно проверяется.

При подтверждённом replay связанная refresh-сессия отзывается.

Отзыв должен быть зафиксирован до формирования HTTP-ошибки.

## 6.12. Logout

Предусмотрены:

- logout текущей сессии;
- logout-all для всех сессий пользователя.

Logout отзывает текущую RefreshSession и очищает cookie.

Logout-all отзывает refresh-сессии пользователя через согласованный транзакционный сценарий.

Уже выданный access JWT при ACTIVE User может оставаться действительным до истечения срока действия.

Мгновенный отзыв access JWT при обычном logout относится к post-MVP.

## 6.13. Browser Security

Целевая production-архитектура использует один origin для React и REST API.

Локальная разработка использует Vite proxy.

Access JWT не сохраняется в localStorage или sessionStorage.

Refresh token передаётся через HttpOnly Secure SameSite cookie.

Для cookie-based операций используется CSRF protection.

Целевой механизм:

- Spring Security;
- CookieCsrfTokenRepository;
- SPA-compatible CSRF handling;
- X-XSRF-TOKEN header;
- проверка Origin.

Конкретные настройки должны быть проверены с используемой версией Spring Security.

## 6.14. Ограничения

Auth не должен зависеть от Booking, Schedule или ServiceOffering.

Auth не должен изменять UserStatus напрямую.

JWT и Spring Security отвечают за установление личности и общие правила доступа.

Проверки владения конкретной Booking, Reservation или услугой выполняются соответствующими бизнес-сценариями.

Исходные refresh tokens, пароли и signing keys не должны попадать в журналы или публичный Git-репозиторий.

# 10. Schedule

## 10.1. Ответственность

Модуль управляет правилами рабочего времени специалиста.

Поддерживаются:

- регулярный недельный график;
- плавающий график;
- версии недельного шаблона;
- исключения конкретных дат;
- горизонт записи;
- вычисление эффективных рабочих окон.

## 10.2. Владеет

- SpecialistScheduleSettings;
- WeeklyScheduleVersion;
- WeeklyWorkingInterval;
- DateSchedule;
- DateScheduleInterval.

Вычисляемая модель:

- EffectiveWorkingWindow.

## 10.3. Зависимости

```text
schedule → specialist
schedule → common
```

В базовой модели Schedule не зависит от Booking.

Изменения расписания, требующие анализа существующих записей, выполняются через отдельный согласованный прикладной сценарий.

## 10.4. Регулярный график

Режим REGULAR использует:

- WeeklyScheduleVersion;
- WeeklyWorkingInterval.

Каждая WeeklyScheduleVersion содержит полный недельный шаблон.

Версии одного специалиста не должны пересекаться по периодам действия.

Изменение с будущей даты создаёт новую версию.

## 10.5. Плавающий график

Режим FLOATING использует DateSchedule с назначением MANUAL.

Рабочие часы задаются отдельно для конкретных дат.

Автоматическое повторение отсутствует.

## 10.6. Исключения

В режиме REGULAR используется DateSchedule с назначением OVERRIDE.

OVERRIDE полностью заменяет недельное расписание выбранной даты.

Пустой OVERRIDE означает выходной.

## 10.7. Основные контракты

Предварительно:

- changeScheduleMode();
- changeBookingHorizon();
- createWeeklyScheduleVersion();
- updateWeeklyScheduleFromDate();
- setDateSchedule();
- removeDateSchedule();
- getEffectiveWorkingWindows().

## 10.8. Ограничения

Рабочие интервалы не пересекают полночь.

Консультация должна полностью помещаться в одно непрерывное рабочее окно.

Перерыв после консультации может выходить за пределы рабочего окна.

Schedule не отменяет Booking самостоятельно.

Изменение расписания должно согласовываться с существующими Reservation и Booking.

# 11. Availability

## 11.1. Ответственность

Модуль вычисляет доступные моменты начала консультаций.

Доступность зависит от:

- условий выбранной услуги;
- эффективных рабочих окон;
- действующей занятости;
- минимального срока предварительной записи;
- горизонта;
- eligibility специалиста;
- временной зоны.

## 11.2. Владеет

- алгоритмом расчёта доступности;
- правилами генерации вариантов начала;
- вычисляемыми результатами.

Availability не владеет таблицей AvailabilitySlot.

## 11.3. Логические зависимости

```text
availability → service
availability → schedule
availability → specialist
availability → occupancy query contract
```

Последний контракт предоставляется транзакционным контуром Booking.

## 11.4. Основные контракты

- findAvailableStartTimes();
- calculateSessionInterval();
- validateRequestedStart().

Точные Java-сигнатуры будут определены при проектировании сервисного слоя.

## 11.5. Ограничения

Начала консультаций предлагаются с шагом 15 минут.

Обычный запрос календаря не создаёт Reservation и не захватывает занятость.

Результат расчёта не является гарантией последующего резервирования.

Создание Reservation выполняет повторную проверку.

Availability не изменяет Occupancy и Booking.

---

# 12. Booking

## 12.1. Ответственность

Booking — транзакционное ядро записи на консультацию.

Модуль отвечает за:

- создание временных удержаний;
- подтверждение Reservation;
- создание Booking;
- отмены;
- истечение Reservation;
- фиксацию согласованных условий;
- управление действующей занятостью;
- хранение истории записей.

## 12.2. Владеет

- Reservation;
- ReservationStatus;
- Booking;
- BookingStatus;
- ScheduleOccupancy;
- ServiceTermsSnapshot.

## 12.3. Логические зависимости

```text
booking → user/client
booking → specialist
booking → service
booking → schedule
booking → common
```

Необходимые бизнес-данные получаются через согласованные контракты.

Booking не обращается к чужим репозиториям напрямую.

## 12.4. Основные контракты

- createReservation();
- confirmReservation();
- cancelReservation();
- expireReservation();
- expireExpiredReservations();
- cancelBooking();
- getBooking();
- getClientBookings();
- getSpecialistBookings();
- getOccupancies();
- getConflictingCommitments().

Не каждый контракт обязан быть отдельным интерфейсом.

## 12.5. Reservation

Reservation представляет временное удержание.

При создании фиксируются:

- специалист;
- клиент;
- услуга;
- время консультации;
- согласованные условия;
- срок действия удержания.

Создание Reservation и ScheduleOccupancy атомарно.

Истёкшая Reservation не может быть подтверждена.

## 12.6. Booking

Booking создаётся из действительной Reservation.

Одна Reservation создаёт не более одной Booking.

Подтверждение не освобождает Occupancy.

История Booking сохраняется после отмены.

## 12.7. ScheduleOccupancy

ScheduleOccupancy содержит только действующую занятость.

При создании Reservation создаётся Occupancy.

При подтверждении Booking Occupancy остаётся.

При освобождении времени Occupancy удаляется.

Reservation и Booking сохраняются независимо от удаления Occupancy.

В PostgreSQL применяется exclusion constraint на пересекающиеся занятые интервалы одного специалиста.

## 12.8. Ограничения

Booking не доверяет предварительному ответу календаря.

Нельзя обеспечивать защиту от двойного бронирования только проверкой существования строки до INSERT.

Изменение услуги не меняет snapshot.

Изменение графика не отменяет существующую Booking автоматически.

# 13. Координация Schedule и Booking

## 13.1. Назначение

Некоторые бизнес-операции требуют согласованного взаимодействия Schedule и Booking.

Примеры:

- закрытие рабочего дня с существующими консультациями;
- изменение постоянного графика;
- переключение режима расписания;
- административное ограничение специалиста;
- конкурентное создание Reservation при редактировании графика.

## 13.2. Проблема циклических зависимостей

Недопустима структура:

```text
ScheduleService
    → BookingService
        → ScheduleService
```

Вместо этого должен существовать явно определённый сценарий координации.

## 13.3. Оркестрация

Оркестрирующий прикладной сервис может:

1. Получить необходимые данные.
2. Определить затрагиваемые временные интервалы.
3. Получить согласованные блокировки.
4. Проверить конфликтующие обязательства.
5. Выполнить разрешённые изменения через владельцев данных.
6. Зафиксировать транзакцию.

Сам оркестрирующий сервис не становится владельцем чужих сущностей.

## 13.4. Архитектурное размещение

Точное размещение оркестрирующего сервиса требует отдельного решения.

Возможны:

- прикладной слой Booking;
- выделенный orchestration package;
- специализированный application service верхнего уровня.

Новый самостоятельный бизнес-модуль не создаётся автоматически.

## 13.5. Ограничения

Нельзя разделять одну атомарную операцию на несколько независимых транзакций без отдельной модели согласованности.

Нельзя изменять расписание и только после COMMIT проверять, не нарушены ли существующие Booking.

---

# 14. Конкурентность

## 14.1. Основное решение

Используется PostgreSQL exclusion constraint на ScheduleOccupancy.

Он запрещает пересекающуюся действующую занятость одного специалиста.

## 14.2. Узкая координация

Не используется общая блокировка строки Specialist для всех клиентских бронирований.

Требуется узкая координация:

- создания Reservation;
- изменения рабочего графика;
- отмен;
- истечения удержаний;
- подтверждения Reservation.

Операции по независимым временным областям должны по возможности выполняться параллельно.

## 14.3. Предварительный механизм

В качестве кандидата рассматриваются transaction-level advisory locks PostgreSQL.

Однако решение нельзя утверждать до проверки:

- границ календарных дат;
- перерывов через полночь;
- массового изменения недельного графика;
- порядка захвата нескольких блокировок;
- поведения при DST;
- защиты от deadlock;
- корректности при нескольких экземплярах приложения.

## 14.4. Дополнительный инвариант

Exclusion constraint запрещает пересечение Occupancy, но не проверяет рабочие правила Schedule.

Поэтому резервирование и изменение графика требуют общей стратегии транзакционной координации.

# 15. Outcome

## 15.1. Ответственность

Модуль устанавливает результат консультации на основании независимых подтверждений участников.

## 15.2. Владеет

- SessionOutcome;
- SessionOutcomeReport;
- историей разрешения спора, если она оформлена через DisputeResolution.

## 15.3. Зависимости

```text
outcome → booking
outcome → user
outcome → common
```

## 15.4. Основные операции

- submitOutcomeReport();
- resolveOutcomeAutomatically();
- markOutcomeDisputed();
- resolveDispute();
- getOutcome();
- isSessionSuccessfullyCompleted().

## 15.5. Инварианты

- подтверждения клиента и специалиста независимы;
- для MVP установлен период ответа 24 часа;
- совместимые ответы могут разрешяться автоматически;
- конфликтующие ответы требуют административного решения;
- отсутствие обоих ответов не считается доказательством состоявшейся консультации.

## 15.6. Ограничения

Outcome не создаёт Review.

Outcome не должен зависеть от Review или Notification для принятия основного бизнес-решения.

Результат консультации не должен произвольно устанавливаться одной стороной при наличии конфликтующего ответа.

# 16. Review

## 16.1. Ответственность

Модуль управляет отзывами клиентов о специалистах.

## 16.2. Владеет

- Review;
- правилами создания и редактирования;
- вычислением агрегированных оценок.

## 16.3. Зависимости

```text
review → outcome
review → booking
review → client
review → specialist
review → common
```

## 16.4. Утверждённые бизнес-правила

Один клиент может оставить одному специалисту только один отзыв.

Первоначальный отзыв разрешён только после подтверждённо успешной консультации.

Review связан с парой Client + Specialist.

Ссылка eligibilityBooking сохраняет консультацию, предоставившую право на отзыв.

Клиент может редактировать оценку и текст существующего отзыва.

Повторная консультация не позволяет создать второй отзыв тому же специалисту.

## 16.5. Основные операции

- createReview();
- updateReview();
- getReview();
- getSpecialistReviews();
- getClientReviewForSpecialist();
- getSpecialistRatingSummary().

## 16.6. Ограничения

Уникальность обеспечивается:

`UNIQUE(client_id, specialist_id)`.

Статус Booking.CONFIRMED не даёт право на отзыв без успешного SessionOutcome.

Review не изменяет Booking и Outcome.

Психолог не имеет права редактировать отзывы клиентов.

---

# 17. Notification

## 17.1. Ответственность

Модуль формирует и доставляет уведомления.

## 17.2. Владеет

- Notification;
- моделями доставки, если используются;
- правилами повторной отправки.

## 17.3. Взаимодействие

Предпочтительная схема:

```text
Business operation
    → committed domain fact
    → notification processing
    → delivery
```

Для надёжной асинхронной доставки может использоваться Transactional Outbox.

Наличие Outbox требует отдельного утверждения.

## 17.4. Важное разделение

Факт прочтения уведомления и статус его доставки — разные понятия.

Прочтение может храниться через readAt.

Доставка может учитываться отдельной сущностью или техническим механизмом.

## 17.5. Ограничения

Ошибка внешней отправки не откатывает уже подтверждённую Booking.

Notification не изменяет бизнес-состояние Booking, Reservation или Schedule.

Обработчики должны учитывать возможную повторную доставку событий.

## 18.6. Ограничения

# 23. Подготовка к микросервисам

## 23.1. Цель

Сохранить возможность последующего выделения функциональности без обязательного перехода к распределённой архитектуре на этапе MVP.

## 23.2. Основные правила

- чёткий владелец данных;
- направленные зависимости;
- ограниченные публичные контракты;
- отсутствие прямой зависимости от чужих репозиториев;
- минимизация передачи JPA-сущностей между модулями;
- отделение бизнес-команд от уведомлений;
- явные транзакционные границы.

## 23.3. Потенциально более независимые модули

В будущем возможно относительно независимое выделение:

- Notification;
- Chat;
- отдельных функций Auth;
- части аналитики.

Review также может быть выделен при наличии подходящих read-моделей и контракта подтверждения права на отзыв.

## 23.4. Сильно связанный контур

```text
Schedule
Availability
Reservation
Booking
ScheduleOccupancy
```

Эти компоненты разделяют критические требования к согласованности.

Их разделение на отдельные микросервисы с независимыми базами потребует переработки модели транзакций и конкурентности.

Не следует обещать независимое выделение каждого такого модуля только потому, что Java-пакеты уже разделены.

## 23.5. Особенность Auth

В текущем модульном монолите Auth и User могут участвовать в одной транзакции, например при согласованной проверке UserStatus и выдаче токенов.

Будущее выделение Auth в отдельный сервис потребует пересмотра этого протокола.

Само разделение Java-пакетов не обеспечивает распределённую атомарность.

# 24. Архитектурные запреты

В целевой архитектуре запрещены:

1. Прямое изменение чужих сущностей без согласованного контракта.
2. Циклические зависимости между модулями.
3. Скрытая оркестрация через взаимные вызовы сервисов.
4. Хранение бизнес-логики конкретного модуля в Common.
5. Создание Reservation без защиты занятости.
6. Использование предварительной доступности как гарантии успешной записи.
7. Изменение исторических условий Booking после редактирования ServiceOffering.
8. Молчаливая отмена подтверждённых Booking при изменении графика.
9. Создание нескольких Review одного клиента на одного специалиста.
10. Внешняя отправка уведомлений внутри критической транзакции без специального обоснования.
11. Использование JVM-lock как единственного средства защиты от двойной записи.
12. Разделение атомарного бизнес-процесса на независимые транзакции без согласованной стратегии.
13. Сохранение AvailabilitySlot как основной единицы бронирования.
14. Универсальные абстракции без подтверждённой необходимости.
15. Хранение исходных refresh tokens в PostgreSQL.
16. Прямое обращение Auth к UserRepository.
17. Передачу RefreshSession или RefreshToken во владение User module.
18. Использование frontend-координации как единственной защиты от конкурентного refresh.
19. Публикацию реальных signing keys, refresh tokens и других authentication secrets в Git.

# 26. Проверка модульной согласованности

Перед реализацией необходимо убедиться, что:

1. У каждой изменяемой сущности есть один владелец.
2. Межмодульные вызовы не создают циклы.
3. Репозитории не используются произвольно из чужих модулей.
4. Транзакции охватывают критические бизнес-операции.
5. Booking и Schedule используют общую согласованную стратегию конкурентного доступа.
6. Outcome является авторитетным источником результата консультации.
7. Review использует Outcome для проверки права на публикацию.
8. Admin не обходит владельцев бизнес-состояния.
9. Notification не влияет на атомарность бронирования.
10. Chat не становится зависимостью критического Booking Flow.
11. Модель допускает расширение без восстановления старых слотов.
12. Подготовка к микросервисам не ухудшает текущую надёжность.
13. RefreshSession и RefreshToken принадлежат Auth.
14. Проверки состояния User выполняются через публичный контракт User module.
15. Refresh rotation не допускает двух одновременно действительных поколений токена одной сессии.
16. Блокировка пользователя согласована с конкурентными login и refresh.

# 27. Итог

PsyWeb остаётся модульным монолитом.

Основные бизнес-границы:

- User управляет учётными записями.
- Auth управляет аутентификацией, JWT и refresh-сессиями.
- Client и Specialist управляют профилями.
- ServiceOffering определяет услуги.
- Schedule определяет разрешённое рабочее время.
- Availability вычисляет доступные начала.
- Booking владеет Reservation, Booking и ScheduleOccupancy.
- Outcome определяет результат консультации.
- Review управляет одним редактируемым отзывом клиента на специалиста.
- Notification выполняет побочные операции доставки.
- Admin координирует административные сценарии.
- Chat остаётся возможностью будущего расширения.

Сильная согласованность бронирований и refresh-token lifecycle имеет приоритет перед преждевременной микросервисной декомпозицией.

**Статус: DRAFT — модульные границы определены, точные технические контракты уточняются при реализации.**
