## Overview

This section defines the internal structure and interaction rules between backend modules in the PsyWeb modular monolith.

The system is designed to enforce strict domain boundaries while allowing controlled internal communication between modules.

---

# Module Dependency Rules

The backend follows a **controlled dependency graph**:

## Core rule:

> Modules must not access each other’s repositories directly.

All communication happens through:

- service layer calls
- shared domain contracts (DTOs or interfaces in `common` where needed)

---

# Module Dependency Map

## High-Level Dependency Flow

```text
auth → user

specialist → user

availability → specialist

booking → user
booking → specialist
booking → availability

review → user
review → specialist
review → booking

chat → user
chat → booking

admin → user
admin → specialist
admin → booking

notification ← domain events
```

Important dependency rule:

`booking → availability`

does not mean that Booking owns AvailabilitySlot state.

The Availability module owns AvailabilitySlot lifecycle and exposes service-level operations used by Booking orchestration.

The Availability module does not depend on Booking.

# Communication Rules

## 1. No direct repository access between modules

Modules interact only via service layer.

---

## 2. Booking Coordinates Reservation and Appointment Flows

The Booking module is the transactional orchestrator for operations involving:

* temporary Reservation creation;
* Reservation confirmation;
* Booking creation;
* Booking cancellation;
* post-session appointment lifecycle.

When these operations require AvailabilitySlot changes, Booking coordinates them through the Availability module's service boundary.

Ownership remains separate:

* Booking owns Reservation and Booking lifecycle;
* Availability owns AvailabilitySlot lifecycle.

Booking must never update AvailabilitySlot persistence directly.

---

## 3. Notification is async-only

- no blocking business flows
- no transactional dependency

---

## 4. Admin is cross-cutting but read-heavy

- can access multiple modules
- but should not own domain logic

# Architectural Insight (важно)

This system is designed so that:

## booking module is the “transactional heart”

Everything else is supportive.

This ensures:

- consistency of slots
- predictable state transitions
- controlled complexity growth

The module architecture enforces:
