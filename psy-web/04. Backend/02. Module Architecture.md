## Overview

This section defines the internal structure and interaction rules between backend modules in the PsyWeb modular monolith.

The system is designed to enforce strict domain boundaries while allowing controlled internal communication between modules.

---

# Module Dependency Rules

The backend follows a **controlled dependency graph**:

## Core rule:

> Modules must not access each other’s repositories directly.

All communication happens through:

- service layer calls
- shared domain contracts (DTOs or interfaces in `common` where needed)

---

# Module Dependency Map

## High-level dependency flow:

```
auth → useruser → specialist, client contextspecialist → availability, serviceavailability → bookingbooking → review, chat, notificationadmin → user, specialist, booking (read + moderation)chat → bookingreview → specialist, bookingnotification → all modules (event-driven consumers)
```

---

# Module Responsibilities & Boundaries

---

## auth

### Responsibilities:

- Authentication (login/register)
- JWT token management
- Password hashing
- SecurityContext setup

### Depends on:

- user

### Must NOT:

- access business modules (booking, specialist, etc.)

---

## user

### Responsibilities:

- Base user entity management
- Role handling (CLIENT / SPECIALIST / ADMIN)
- Profile aggregation (entry point for user identity)

### Depends on:

- none (core identity module)

---

## specialist

### Responsibilities:

- Specialist profile management
- Verification status (admin-controlled)
- Specialist metadata

### Depends on:

- user

---

## availability

### Responsibilities:

- Slot creation and management
- Schedule logic
- Time interval validation

### Depends on:

- specialist

---

## booking (CORE MODULE)

### Responsibilities:

- Slot reservation logic
- Booking lifecycle management
- Cancellation rules
- Transactional integrity

### Depends on:

- availability
- specialist
- user
- service (indirect via specialist)

---

## review

### Responsibilities:

- Post-booking reviews
- Rating calculation inputs

### Depends on:

- booking
- specialist
- user

---

## chat (optional module)

### Responsibilities:

- Chat threads per booking
- Message storage
- Communication history

### Depends on:

- booking
- user

---

## notification

### Responsibilities:

- Async system events handling
- User notifications (email/push future)

### Depends on:

- all modules (event consumers only)

### Important rule:

> notification must NOT affect core transactional logic

---

## admin

### Responsibilities:

- Specialist verification
- Moderation of users/bookings
- System-level overrides

### Depends on:

- user
- specialist
- booking

---

## common

### Responsibilities:

- shared DTOs
- enums
- base exceptions
- utilities

### Depends on:

- nothing

---

# Communication Rules

## 1. No direct repository access between modules

Modules interact only via service layer.

---

## 2. Booking is system-critical boundary

Any cross-module operation involving:

- slot reservation
- appointment lifecycle

must go through booking module.

---

## 3. Notification is async-only

- no blocking business flows
- no transactional dependency

---

## 4. Admin is cross-cutting but read-heavy

- can access multiple modules
- but should not own domain logic

---

# Architectural Insight (важно)

This system is designed so that:

## booking module is the “transactional heart”

Everything else is supportive.

This ensures:

- consistency of slots
- predictable state transitions
- controlled complexity growth

---

# Summary

The module architecture enforces:

- strict domain boundaries
- service-layer communication only
- centralized booking logic
- future-ready event-driven expansion (notification/chat)
