## Overview

This section defines the internal structure and interaction rules between backend modules in the PsyWeb modular monolith.

The system is designed to enforce strict domain boundaries while allowing controlled internal communication between modules.

---

# Module Dependency Rules

The backend follows a **controlled dependency graph**:

## Core rule:

> Modules must not access each other’s repositories directly.

All communication happens through:

- service layer calls
- shared domain contracts (DTOs or interfaces in `common` where needed)

---

# Module Dependency Map

## High-Level Dependency Flow

```text
auth → user

specialist → user

availability → specialist

booking → user
booking → specialist
booking → availability

review → user
review → specialist
review → booking

chat → user
chat → booking

admin → user
admin → specialist
admin → booking

notification ← domain events
```

Important dependency rule:

`booking → availability`

does not mean that Booking owns AvailabilitySlot state.

The Availability module owns AvailabilitySlot lifecycle and exposes service-level operations used by Booking orchestration.

The Availability module does not depend on Booking.

# Module Responsibilities & Boundaries

---

## auth

### Responsibilities:

- Authentication (login/register)
- JWT token management
- Password hashing
- SecurityContext setup

### Depends on:

- user

### Must NOT:

- access business modules (booking, specialist, etc.)

---

## user

### Responsibilities:

- Base user entity management
- Role handling (CLIENT / SPECIALIST / ADMIN)
- Profile aggregation (entry point for user identity)

### Depends on:

- none (core identity module)

---

## specialist

### Core Responsibilities:

- Specialist core identity management
- Specialist approval lifecycle
- approval state transition validation
- specialist-level operational settings required by core workflows

### Core Owns:

- Specialist
- Specialist approval state
- approval transition rules
- core specialist settings

### Approval State Machine:

- creation/application → `PENDING`
- `PENDING → APPROVED`
- `PENDING → REJECTED`

Admin may initiate an approval decision, but the state transition is executed through the Specialist module boundary.

### Separate Models / Future Scope:

Public profile is separate from Specialist core.

It may later contain:

- biography and introduction;
- photos and media;
- client-facing presentation sections;
- configurable profile-page content.

Professional qualifications are also modeled separately and may contain:

- education;
- diplomas and evidence documents;
- retraining;
- additional qualifications;
- specializations.

Qualification verification is distinct from Specialist approval.

A credential may have its own verification lifecycle without changing the meaning of `Specialist.approval_status`.

### MVP Boundary:

The MVP does not require:

- a generic `bio` field in Specialist core;
- a page builder;
- arbitrary rich profile composition;
- the complete qualifications-management subsystem.

These concerns may be introduced independently without expanding the core Specialist entity into a generic profile container.

### Depends on:

- user

### Must NOT:

- depend on admin
- expose Specialist persistence for direct cross-module modification
- merge Specialist approval state with User account status
- treat public profile content as core Specialist identity
- use one generic verification flag for both Specialist approval and professional credential verification

# Communication Rules

## 1. No direct repository access between modules

Modules interact only via service layer.

---

## 2. Booking Coordinates Reservation and Appointment Flows

The Booking module is the transactional orchestrator for operations involving:

* temporary Reservation creation;
* Reservation confirmation;
* Booking creation;
* Booking cancellation;
* post-session appointment lifecycle.

When these operations require AvailabilitySlot changes, Booking coordinates them through the Availability module's service boundary.

Ownership remains separate:

* Booking owns Reservation and Booking lifecycle;
* Availability owns AvailabilitySlot lifecycle.

Booking must never update AvailabilitySlot persistence directly.

---

## 3. Notification is async-only

- no blocking business flows
- no transactional dependency

---

## 4. Admin is cross-cutting but read-heavy

- can access multiple modules
- but should not own domain logic

# Architectural Insight (важно)

This system is designed so that:

## booking module is the “transactional heart”

Everything else is supportive.

This ensures:

- consistency of slots
- predictable state transitions
- controlled complexity growth

The module architecture enforces:

- service-layer communication only
- centralized booking logic
