
# 14. Проектирование домена Admin

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**Язык:** Java 21  
**База данных:** PostgreSQL 16+  
**Статус:** DRAFT — основные бизнес-правила утверждены, отдельные административные сценарии требуют формализации

---

# 1. Назначение документа

Документ описывает архитектуру административного домена PsyWeb.

Admin отвечает за системное управление платформой, модерацию пользователей и специалистов, административные ограничения и разрешение спорных ситуаций.

Основные задачи:

- проверка и одобрение специалистов;
- отклонение заявок специалистов;
- управление административными ограничениями;
- блокировка пользователей;
- управление допуском специалистов к бронированию;
- просмотр данных, необходимых для модерации;
- обработка исключительных ситуаций с Booking;
- разрешение споров о результатах консультаций;
- модерация содержимого платформы в пределах утверждённых полномочий;
- аудит административных действий;
- контроль соблюдения бизнес-инвариантов.

Admin обладает повышенными полномочиями, но не становится владельцем сущностей других доменов.

Административные операции выполняются через согласованные сервисные контракты соответствующих модулей.

---

# 2. Основная концепция

## 2.1. Администратор

Администратор — пользователь с ролью ADMIN, имеющий доступ к системным операциям управления платформой.

Административная роль позволяет выполнять действия, недоступные обычным клиентам и специалистам.

При этом наличие роли ADMIN не отменяет доменные ограничения и транзакционные требования.

## 2.2. Контролируемые полномочия

Административные действия могут затрагивать несколько модулей.

Например, блокировка специалиста влияет на:

- User;
- Specialist;
- SpecialistBookingAccess;
- Reservation;
- ScheduleOccupancy;
- административный аудит.

Такой сценарий требует межмодульной координации.

## 2.3. Отсутствие прямого владения

Admin не реализует собственные альтернативные версии:

- BookingService;
- ReservationService;
- ScheduleService;
- OutcomeService;
- ReviewService.

Вместо этого он использует разрешённые команды соответствующих доменов.

## 2.4. Атомарность

Если административная операция требует нескольких согласованных изменений, они выполняются в одной транзакции.

Недопустимо фиксировать только часть критического административного действия.

---

# 3. Ответственность Admin

## 3.1. Модерация специалистов

Admin может:

- рассматривать заявки специалистов;
- одобрять специалистов;
- отклонять заявки;
- изменять модерационный статус в пределах утверждённых переходов;
- применять административные ограничения;
- восстанавливать разрешённый доступ после проверки необходимых условий.

## 3.2. Модерация пользователей

Admin может:

- блокировать учётные записи;
- рассматривать нарушения правил платформы;
- анализировать необходимые сведения об активности;
- выполнять разрешённые операции восстановления доступа.

## 3.3. Модерация Booking

Admin может:

- просматривать Booking в пределах административных полномочий;
- рассматривать исключительные ситуации;
- инициировать предусмотренные бизнес-правилами административные действия;
- участвовать в разрешении споров.

## 3.4. Разрешение споров

Admin рассматривает спорные результаты консультаций, которые не удалось разрешить автоматически.

## 3.5. Модерация содержимого

Возможные будущие направления:

- модерация Review;
- обработка жалоб;
- ограничение публикации недопустимого содержимого.

Точные полномочия определяются отдельно.

## 3.6. Системный контроль

Admin может получать агрегированные сведения, необходимые для контроля состояния платформы.

Например:

- число специалистов на модерации;
- число действующих административных ограничений;
- количество спорных SessionOutcome;
- статистику отмен;
- сведения о выполненных административных действиях.

Состав доступных показателей и политика доступа должны быть согласованы с требованиями безопасности.

---

# 4. Границы домена

| Модуль | Владелец состояния | Роль Admin |
|---|---|---|
| User | User | Инициирует изменение статуса аккаунта |
| Specialist | Specialist | Рассматривает и модерирует профиль |
| Service | Service | Контролируемый доступ по отдельным правилам |
| Schedule | Schedule | Просмотр и исключительные действия при необходимости |
| Availability | Availability | Получение информации о доступности |
| Booking | Booking | Инициирует разрешённые отмены и получает сведения |
| Outcome | Outcome | Принимает административное решение по спору |
| Review | Review | Возможная модерация содержимого |
| Notification | Notification | Получает события административных действий |
| Admin | Admin | Полномочия, оркестрация, административный аудит |

## 4.1. Запрет обхода границ

AdminService не должен напрямую изменять ReservationRepository, BookingRepository или ScheduleRepository другого модуля.

Для таких действий используются публичные командные контракты.

## 4.2. Межмодульная оркестрация

Сложная операция может выполняться через отдельный прикладной координатор.

Например:

`AdministrativeBlockingService`

Такой координатор задаёт транзакционную последовательность, но не становится владельцем изменяемых сущностей.

# 5. Модель административных состояний

Для допуска специалиста используются три независимых по смыслу состояния:

1. User.status.
2. Specialist.approvalStatus.
3. SpecialistBookingAccess.bookingAllowed.

Они не должны интерпретироваться как взаимозаменяемые поля.

## 5.1. User.status

Определяет состояние учётной записи.

Для целевой модели User предусмотрены:

- ACTIVE;
- BLOCKED.

Статус PENDING относится к профессиональной модерации Specialist, а не к состоянию учётной записи User.

Конкретные переходы должны соответствовать User Domain и Authorization Model.

## 5.2. Specialist.approvalStatus

Определяет состояние рассмотрения специалиста.

Условием допуска является:

`approvalStatus = APPROVED`

В целевой модели используются четыре модерационных состояния:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

Профессиональный допуск требует `approvalStatus = APPROVED`.

Модерационный статус не заменяет User.status и не определяет самостоятельно значение bookingAllowed.

## 5.3. SpecialistBookingAccess.bookingAllowed

Представляет отдельное административное разрешение принимать новые записи и подтверждать ACTIVE Reservation.

Значение:

`TRUE` — отдельное ограничение BookingAccess не препятствует бронированию.

`FALSE` — бронирование и подтверждение запрещены.

## 5.4. Независимость состояний

Изменение approvalStatus не должно автоматически снимать отдельное ограничение bookingAllowed.

Аналогично изменение bookingAllowed не должно автоматически разблокировать User.status.

---

# 6. Эффективный допуск специалиста

## 6.1. Утверждённое правило

Специалист может принимать новые Reservation и подтверждать существующие ACTIVE Reservation только при одновременном выполнении:

```text
User.status = ACTIVE

AND Specialist.approvalStatus = APPROVED

AND SpecialistBookingAccess.bookingAllowed = TRUE
```

## 6.2. Примеры

| User.status | approvalStatus | bookingAllowed | Допуск |
|---|---|---|---|
| ACTIVE | APPROVED | TRUE | Разрешён |
| ACTIVE | APPROVED | FALSE | Запрещён |
| ACTIVE | PENDING | TRUE | Запрещён |
| ACTIVE | REJECTED | TRUE | Запрещён |
| BLOCKED | APPROVED | TRUE | Запрещён |
| BLOCKED | APPROVED | FALSE | Запрещён |

## 6.3. Проверка при Reservation

Создание Reservation должно проверять эффективный допуск специалиста.

## 6.4. Проверка при подтверждении

Подтверждение Reservation также должно проверять эффективный допуск.

## 6.5. Изменение допуска

Любая административная операция, которая лишает специалиста эффективного допуска, должна использовать общий механизм транзакционной координации через SpecialistBookingAccess.

## 6.6. Запрет обхода

Нельзя напрямую изменить User.status или Specialist.approvalStatus так, чтобы специалист потерял право принимать записи, и при этом обойти обработку его ACTIVE Reservation.


## 6.7. Публичная видимость специалиста

Публичная видимость специалиста и право принимать новые бронирования являются независимыми условиями.

### Условия публичной видимости

Специалист отображается в публичном каталоге только при одновременном выполнении:

- `User.status = ACTIVE`;
- `Specialist.approvalStatus = APPROVED`.

Значение `SpecialistBookingAccess.bookingAllowed` не влияет на публичную видимость специалиста.

### Матрица состояний

| User.status | approvalStatus | bookingAllowed | Публичный каталог | Новые записи |
|---|---|---|---|---|
| ACTIVE | PENDING | любое | Скрыт | Запрещены |
| ACTIVE | APPROVED | TRUE | Видим | Разрешены при остальных условиях |
| ACTIVE | APPROVED | FALSE | Видим | Запрещены |
| ACTIVE | REJECTED | любое | Скрыт | Запрещены |
| ACTIVE | SUSPENDED | любое | Скрыт | Запрещены |
| BLOCKED | любое | любое | Скрыт | Запрещены |

### Приостановка профессионального допуска

При переходе `APPROVED → SUSPENDED`:

1. Специалист исключается из публичного каталога.
2. Создание новых Reservation и подтверждение ACTIVE Reservation запрещаются.
3. Все ACTIVE Reservation специалиста отменяются.
4. Соответствующие ScheduleOccupancy освобождаются.
5. CONFIRMED Booking сохраняются.
6. `ServiceOffering.isActive` автоматически не изменяется.

### Административный запрет новых записей

При установке `bookingAllowed = FALSE`:

1. Профессиональный статус APPROVED сохраняется.
2. Специалист остаётся в публичном каталоге при выполнении условий видимости.
3. Публичный профиль, услуги и отзывы остаются доступными для просмотра.
4. Интерфейс сообщает, что запись временно недоступна.
5. Новые Reservation и подтверждение ACTIVE Reservation запрещаются.
6. Все существующие ACTIVE Reservation отменяются с освобождением ScheduleOccupancy.
7. CONFIRMED Booking сохраняются.
8. Активность ServiceOffering автоматически не изменяется.

### Восстановление допуска

При восстановлении `approvalStatus = APPROVED` специалист снова становится видимым в каталоге, если его User.status = ACTIVE.

При восстановлении `bookingAllowed = TRUE` новые записи становятся возможными только при соблюдении всех остальных условий бронирования.

Ранее отменённые Reservation автоматически не восстанавливаются.

### Архитектурные требования

Публичная видимость должна определяться актуальными состояниями User и Specialist.

Admin не реализует собственный механизм вычисления Availability.

Административная потеря эффективного допуска координируется транзакционно с отменой ACTIVE Reservation.

Состояние публичного каталога не заменяет проверку эффективного допуска в Booking Domain.

# 7. Проверка и одобрение специалиста

## 7.1. Назначение

Модерация необходима для допуска специалиста к работе на платформе.

## 7.2. Общий сценарий

```text
Специалист отправляет данные
    ↓
Заявка поступает на рассмотрение
    ↓
Администратор проверяет заявку
    ↓
Администратор принимает решение
    ↓
Обновляется approvalStatus
    ↓
Результат сохраняется в истории модерации
```

## 7.3. Одобрение

При одобрении специалиста устанавливается соответствующий approvalStatus.

При этом одобрение не должно автоматически отменять отдельную административную блокировку bookingAllowed.

## 7.4. Отклонение

При отклонении специалист не получает право принимать новые Reservation.

Причина решения сохраняется при необходимости.

## 7.5. Повторное рассмотрение

Повторное рассмотрение заявки допускается только по утверждённым правилам переходов approvalStatus.

Нельзя выполнять произвольные переходы без проверки состояния.

## 7.6. Конкурентность

Если решение модерации приводит к потере эффективного допуска у специалиста, уже принимающего записи, операция должна использовать механизм административного ограничения с обработкой ACTIVE Reservation.

---

# 8. Административная блокировка пользователя

## 8.1. Назначение

Администратор может заблокировать учётную запись пользователя при наличии допустимого основания.

## 8.2. Общая блокировка

При блокировке User.status переводится в BLOCKED согласно правилам User Domain.

## 8.3. Блокировка специалиста

Если пользователь является специалистом, потеря User.status = ACTIVE означает потерю эффективного допуска к бронированию.

Поэтому такая операция должна координироваться через SpecialistBookingAccess.

## 8.4. ACTIVE Reservation специалиста

Все ACTIVE Reservation специалиста немедленно отменяются.

Их ScheduleOccupancy удаляются.

## 8.5. CONFIRMED Booking специалиста

Подтверждённые Booking автоматически не отменяются.

## 8.6. Блокировка клиента

Для блокировки клиентского аккаунта последствия для его существующих ACTIVE Reservation и CONFIRMED Booking пока отдельно не утверждены.

Их нельзя автоматически приравнивать к правилам блокировки специалиста.

Это отдельный бизнес-вопрос.

## 8.7. Восстановление

Возвращение User.status в ACTIVE не должно автоматически снимать независимое ограничение bookingAllowed.

---

# 9. Административная блокировка специалиста

## 9.1. Утверждённое правило

При административной блокировке специалиста:

- новые Reservation запрещаются;
- подтверждение ACTIVE Reservation запрещается;
- все ACTIVE Reservation немедленно отменяются;
- соответствующие Occupancy удаляются;
- CONFIRMED Booking сохраняются;
- административное решение фиксируется в истории.

## 9.2. Транзакционная граница

Все обязательные изменения выполняются атомарно.

Не допускается ситуация, когда административная блокировка уже зафиксирована, а ACTIVE Reservation продолжают существовать из-за задержки фонового обработчика.

## 9.3. Основной алгоритм

```text
BEGIN
    ↓
Проверка полномочий администратора
    ↓
SpecialistBookingAccess FOR UPDATE
    ↓
Проверка текущего состояния
    ↓
Изменение необходимого административного статуса
    ↓
Получение ACTIVE Reservation специалиста
    ↓
Reservation FOR UPDATE
в детерминированном порядке
    ↓
Повторная проверка состояний
    ↓
ACTIVE → CANCELLED
    ↓
cancellationInitiator = ADMIN
    ↓
DELETE ScheduleOccupancy
    ↓
Сохранение административного действия
    ↓
COMMIT
```

## 9.4. Блокировки

Административная операция получает:

`SpecialistBookingAccess FOR UPDATE`

Создание и подтверждение Reservation используют:

`SpecialistBookingAccess FOR SHARE`

## 9.5. Конкурентное создание Reservation

Если создание Reservation законно завершилось до получения администратором эксклюзивной блокировки, административная операция должна обнаружить её и отменить.

Если блокировка завершилась первой, создание новой Reservation отклоняется.

## 9.6. Конкурентное подтверждение

Если подтверждение успело успешно завершиться первым, новая Booking сохраняется.

Если административная блокировка получила приоритет и зафиксировала запрет, подтверждение Reservation невозможно.

## 9.7. Отмена Reservation

При административной отмене:

- Reservation переходит в CANCELLED;
- сохраняется cancelledAt;
- cancellationInitiator = ADMIN;
- сохраняется причина при необходимости;
- связанная Occupancy удаляется.

## 9.8. Идемпотентность

Повторная команда блокировки не должна повторно отменять уже завершённые Reservation или создавать противоречивые состояния.

Правила повторного административного аудита необходимо определить отдельно.

---

# 10. Восстановление допуска специалиста

## 10.1. Основное правило

Восстановление права принимать записи является явной административной операцией.

## 10.2. Предусловия

Перед восстановлением необходимо проверить:

- актуальный User.status;
- актуальный Specialist.approvalStatus;
- состояние BookingAccess;
- полномочия администратора.

## 10.3. Независимые ограничения

Одобрение специалиста само по себе не снимает отдельную административную блокировку.

Разблокировка User также не должна автоматически восстанавливать bookingAllowed.

## 10.4. Существующие отменённые Reservation

Административно отменённые Reservation не восстанавливаются автоматически.

Для новой записи клиент должен создать новую Reservation.

## 10.5. Существующие Booking

Подтверждённые Booking сохраняются независимо от операции восстановления.

## 10.6. Аудит

Восстановление доступа должно быть отражено в административной истории.

---

# 11. Административная модерация Booking

## 11.1. Просмотр

Администратор может просматривать необходимые Booking и Reservation для выполнения своих полномочий.

Доступ должен быть ограничен целями административных операций.

## 11.2. Исключительные отмены

Административная отмена подтверждённой Booking может потребоваться в исключительной ситуации.

Однако окончательные условия такой отмены ещё не утверждены.

## 11.3. Запрет прямого изменения

Admin не должен напрямую устанавливать произвольный BookingStatus или удалять Occupancy в обход Booking Domain.

## 11.4. Командный контракт

Для административной отмены должен использоваться разрешённый контракт Booking.

Такой контракт обязан:

- проверить допустимость операции;
- получить необходимые блокировки;
- изменить Booking;
- сохранить метаданные;
- согласованно освободить Occupancy;
- сохранить историю.

## 11.5. После начала консультации

Обычная клиентская отмена после sessionStart запрещена.

Административные исключительные операции после начала требуют самостоятельных бизнес-правил.

До их утверждения нельзя использовать универсальную административную отмену как обход ограничения.

## 11.6. Массовая отмена

Массовая отмена подтверждённых Booking в MVP не требуется.

Обрабатываются отдельные консультации.

---

# 12. Разрешение споров SessionOutcome

## 12.1. Назначение

Admin рассматривает случаи, когда клиент и специалист предоставили противоречивые сведения о проведении консультации.

## 12.2. Источник истины

Домен Outcome владеет:

- SessionOutcome;
- SessionOutcomeReport;
- состоянием разрешения результата;
- окончательным результатом консультации.

Admin не создаёт альтернативный источник истины о проведении консультации.

## 12.3. Окно ответов

Клиент и специалист независимо сообщают о результате в пределах утверждённого 24-часового окна после консультации.

## 12.4. Автоматическое разрешение

Outcome самостоятельно обрабатывает случаи, для которых утверждены правила автоматического разрешения.

Примеры:

- два совместимых OCCURRED;
- совместимые DID_NOT_OCCUR;
- единственный ответ после завершения окна;
- отсутствие обоих ответов.

## 12.5. Спор

Административное вмешательство необходимо при противоречивых утверждениях.

Например:

- одна сторона сообщает OCCURRED;
- другая сообщает DID_NOT_OCCUR.

Также возможны противоречащие обвинения в неявке.

## 12.6. Административное решение

Администратор:

1. Получает допустимый спор.
2. Проверяет полномочия.
3. Анализирует доступные сведения.
4. Принимает разрешённое решение.
5. Передаёт его через OutcomeResolutionCommand.
6. Сохраняет административное основание.
7. Обеспечивает атомарность решения и изменения SessionOutcome.

## 12.7. Влияние на Review

Review разрешён только после подтверждённо успешной консультации.

Административное решение, подтвердившее успешное проведение, может создать основание для Review.

Если результат не подтверждает проведение, основание не возникает.

## 12.8. Ограничение

Admin не должен создавать Review или изменять оценку клиента в рамках разрешения спора.

---

# 13. Модель административного аудита

## 13.1. Назначение

Критические административные действия должны быть прослеживаемыми.

Аудит необходим для:

- восстановления истории решений;
- расследования спорных ситуаций;
- контроля действий администраторов;
- диагностики ошибок;
- проверки соблюдения внутренних правил.

## 13.2. Основные сведения

Для административного действия необходимо сохранять:

- идентификатор администратора;
- тип действия;
- затронутый объект;
- время;
- причину, если применимо;
- результат действия.

## 13.3. SpecialistModerationAction

В целевой реляционной схеме предусмотрена таблица:

`specialist_moderation_actions`

Основные поля:

- id;
- specialistId;
- administratorId;
- action;
- reason;
- createdAt.

## 13.4. Граница специализированного аудита

SpecialistModerationAction предназначена прежде всего для модерационных решений по специалисту.

Она не обязана хранить все административные события платформы.

Для других операций могут использоваться собственные записи истории.

## 13.5. DisputeResolution

Административное решение по спору хранится отдельно в модели Outcome.

## 13.6. Атомарность

Если сохранение аудита является обязательной частью операции, запись создаётся в той же транзакции, что и соответствующее изменение состояния.

## 13.7. Неизменяемость истории

Обычное редактирование профиля или повторная модерация не должны переписывать ранее сохранённые административные решения.

## 13.8. Технические логи

Application logs не заменяют структурированный административный аудит.

Логи могут использоваться дополнительно.

---

# 14. Сервисный слой Admin

## 14.1. AdminService

Предоставляет основные административные сценарии.

Концептуальные операции:

```text
approveSpecialist(
    administratorId,
    specialistId
)

rejectSpecialist(
    administratorId,
    specialistId,
    reason
)

getSpecialistModerationHistory(
    specialistId
)

getPendingSpecialists()
```

## 14.2. AdministrativeBlockingService

Отвечает за межмодульную координацию административной блокировки.

```text
blockSpecialist(
    administratorId,
    specialistId,
    reason
)
```

Внутри одной транзакции он координирует SpecialistBookingAccess, User или Specialist status, Booking и аудит.

## 14.3. Восстановление доступа

Предварительный контракт:

```text
restoreSpecialistBookingAccess(
    administratorId,
    specialistId,
    reason
)
```

## 14.4. Разрешение споров

Предварительный контракт:

```text
resolveDispute(
    administratorId,
    outcomeId,
    decision
)
```

Изменение результата выполняется через OutcomeResolutionCommand.

## 14.5. Граница ответственности

AdminService не должен напрямую использовать Repository другого бизнес-модуля для обхода его правил.

## 14.6. Идентичность администратора

Идентичность инициатора определяется доверенным SecurityContext.

Переданный в HTTP-запросе administratorId не является доказательством полномочий.

# 15. Транзакционная модель

## 15.1. Базовая изоляция

Используется PostgreSQL READ COMMITTED.

## 15.2. Дополнительная защита

Применяются:

- SELECT FOR SHARE;
- SELECT FOR UPDATE;
- транзакционная оркестрация;
- повторные проверки состояния после блокировок;
- ограничения целостности PostgreSQL.

## 15.3. Блокировка специалиста

BookingAccess блокируется FOR UPDATE.

Reservation блокируются FOR UPDATE в стабильном порядке.

## 15.4. Подтверждение Reservation

BookingAccess блокируется FOR SHARE до получения Reservation FOR UPDATE.

## 15.5. Создание Reservation

BookingAccess блокируется FOR SHARE до календарных advisory locks.

## 15.6. Отсутствие глобальной блокировки

Обычное резервирование не требует эксклюзивной блокировки всей строки Specialist.

Несколько клиентов могут одновременно выполнять независимые операции.

## 15.7. Порядок блокировок

Административные операции обязаны соблюдать совместимый порядок получения ресурсов.

Если дополнительная административная команда использует календарные блокировки, её протокол должен быть спроектирован отдельно.

Нельзя произвольно захватывать Calendar advisory locks после Reservation row locks, если это создаёт обратный порядок относительно ReservationApplicationService.

## 15.8. Проверка реализации

Фактические PostgreSQL-блокировки должны быть проверены с учётом:

- Hibernate flush;
- внешних ключей;
- конкурентных UPDATE;
- INSERT;
- DELETE.

---

# 16. Безопасность административных операций

## 16.1. RBAC

Административные endpoints доступны только пользователям с необходимыми полномочиями.

Для текущей модели базовым требованием является роль ADMIN.

## 16.2. Двойная проверка

Защита должна существовать:

- на уровне HTTP/Spring Security;
- на уровне прикладного сервиса.

## 16.3. Доверенная идентичность

Данные о вызывающем администраторе извлекаются из доверенного SecurityContext.

## 16.4. Проверка состояния

Даже уполномоченный администратор не может выполнять произвольные недопустимые переходы состояний.

## 16.5. Минимально необходимые данные

Административный доступ к персональным сведениям должен ограничиваться информацией, необходимой для конкретного действия.

## 16.6. Запрет универсального обхода

Не следует создавать административный метод, позволяющий передать произвольный статус любой сущности без проверки доменных ограничений.

## 16.7. Чувствительные сведения

Административные журналы и события не должны без необходимости содержать чувствительные данные клиентов или содержание консультаций.

---

# 17. Интеграция с User

## 17.1. Статусы аккаунта

User хранит состояние учётной записи.

## 17.2. Блокировка

UserStatus.BLOCKED запрещает специалисту принимать записи независимо от остальных настроек.

## 17.3. Координация

Изменение UserStatus специалиста, вызывающее потерю допуска, должно использовать общий механизм BookingAccess.

## 17.4. Разделение ответственности

User остаётся владельцем User.status.

Admin инициирует изменение через разрешённый контракт.

---

# 18. Интеграция со Specialist

## 18.1. approvalStatus

Specialist хранит состояние модерационного рассмотрения.

## 18.2. Независимые ограничения

approvalStatus не заменяет bookingAllowed.

## 18.3. Одобрение

Одобрение специалиста не снимает отдельную административную блокировку.

## 18.4. Отказ или приостановка

Если изменение approvalStatus приводит к потере эффективного допуска, применяется административный протокол отмены ACTIVE Reservation.

## 18.5. Профиль специалиста

Обычное редактирование биографии, имени или других профильных атрибутов не должно блокировать независимые клиентские Reservation посредством эксклюзивной блокировки всей сущности Specialist.

---

# 19. Интеграция с Booking

## 19.1. ACTIVE Reservation

При административной блокировке специалиста все ACTIVE Reservation отменяются немедленно.

## 19.2. CONFIRMED Booking

Подтверждённые Booking сохраняются.

## 19.3. Occupancy

При административной отмене ACTIVE Reservation соответствующая Occupancy удаляется атомарно.

## 19.4. История

Reservation и Booking сохраняются для истории.

## 19.5. Исключительные отмены

Ручная отмена подтверждённой Booking требует отдельного утверждённого бизнес-сценария.

## 19.6. Запрет прямого доступа

Admin не удаляет Occupancy напрямую через собственный Repository.

Он использует командные контракты Booking.

---

# 20. Интеграция с Availability и Schedule

## 20.1. Availability

Admin может получать информацию о доступности и расписании в пределах своих полномочий.

## 20.2. BookingAccess

После административной блокировки Availability не должен предлагать новые доступные начала специалиста.

## 20.3. Schedule

Обычное изменение расписания специалиста не равнозначно административной блокировке.

## 20.4. Существующие обязательства

При обычных изменениях графика сохраняются ACTIVE Reservation и CONFIRMED Booking.

## 20.5. Независимость доменов

Admin не должен реализовывать собственный алгоритм вычисления Availability.

---

# 21. Интеграция с Review

## 21.1. Текущая модель

Review представляет один редактируемый отзыв на пару клиент–специалист.

## 21.2. Право на отзыв

Review разрешён только после подтверждённо успешной консультации.

## 21.3. Будущая модерация

Admin может получить возможность рассматривать жалобы на содержимое Review.

## 21.4. Открытые вопросы

Необходимо отдельно определить:

- основания для скрытия;
- возможность удаления;
- уведомление автора;
- порядок обжалования;
- правила аудита.

## 21.5. Ограничение

Admin не может создавать Review от имени клиента или менять его rating без специально согласованного бизнес-основания.

---

# 22. Интеграция с Notification

## 22.1. Административные события

Возможные события:

- SpecialistApproved;
- SpecialistRejected;
- SpecialistBlocked;
- SpecialistBookingAccessRestored.

## 22.2. Отмена Reservation

Административная блокировка также может приводить к событиям ReservationCancelled для затронутых клиентов.

## 22.3. Независимость

Notification не выполняет административные изменения.

## 22.4. Транзакции

Уведомления формируются на основании успешно зафиксированных изменений.

## 22.5. Надёжность

Гарантированная доставка требует отдельной политики обработки событий.

---

# 23. Ошибки домена

Возможные исключения:

- UnauthorizedAdminAccessException;
- InvalidModerationActionException;
- InvalidSpecialistStatusTransitionException;
- SpecialistNotFoundException;
- UserNotFoundException;
- AdministrativeOperationConflictException;
- OperationNotAllowedException;
- DisputeNotFoundException;
- InvalidDisputeResolutionException.

Названия предварительные.

Они должны быть согласованы с Common Module и Exception Handling Strategy.

## 23.1. Недостаточные полномочия

Административная операция отклоняется.

## 23.2. Несуществующий объект

Операция возвращает соответствующую предметную ошибку.

## 23.3. Недопустимый переход

Переход состояния запрещается.

## 23.4. Конкурентный конфликт

Операция должна откатиться либо повторно проверить состояние по утверждённому протоколу.

## 23.5. Частичное выполнение

Нельзя фиксировать частичную административную блокировку специалиста.

---

# 24. Тестирование

## 24.1. Модерация специалистов

Проверить:

- одобрение заявки;
- отклонение;
- повторное рассмотрение;
- недопустимые переходы;
- сохранение истории.

## 24.2. Эффективный допуск

Проверить все основные комбинации:

- ACTIVE / APPROVED / TRUE;
- ACTIVE / APPROVED / FALSE;
- BLOCKED / APPROVED / TRUE;
- ACTIVE / PENDING / TRUE;
- ACTIVE / REJECTED / TRUE.

## 24.3. Административная блокировка

Проверить:

- перевод допуска в запрещённое состояние;
- отмену всех ACTIVE Reservation;
- сохранение CONFIRMED Booking;
- удаление Occupancy отменённых Reservation;
- запись административного аудита;
- откат всей операции при ошибке.

## 24.4. Конкурентность

Проверить:

1. Блокировку специалиста одновременно с созданием Reservation.
2. Блокировку одновременно с подтверждением Reservation.
3. Блокировку одновременно с Expiration Scheduler.
4. Две конкурентные команды блокировки.
5. Восстановление доступа одновременно с новой Reservation.
6. Изменение UserStatus одновременно с созданием Reservation.
7. Изменение approvalStatus одновременно с подтверждением Reservation.

## 24.5. Восстановление

Проверить:

- запрет неявного снятия bookingAllowed = FALSE;
- явное восстановление после проверки всех состояний;
- отсутствие автоматической реактивации CANCELLED Reservation.

## 24.6. Разрешение споров

Проверить:

- допустимое разрешение спора;
- запрет разрешения чуждым сценарию администратором без полномочий;
- сохранение решения;
- атомарное обновление SessionOutcome;
- влияние результата на Review eligibility.

## 24.7. PostgreSQL

Критические сценарии проверяются на PostgreSQL, например через Testcontainers.

Особое внимание уделяется фактическому порядку строковых блокировок.

---

# 25. Архитектурные запреты

1. Admin не владеет доменной логикой Booking, Schedule, Review или Outcome.
2. Нельзя изменять бизнес-состояние других модулей напрямую в обход их командных контрактов.
3. Нельзя обходить доменные инварианты только потому, что операцию выполняет ADMIN.
4. Нельзя считать approvalStatus единственным условием допуска специалиста.
5. Нельзя считать bookingAllowed достаточным при BLOCKED User.
6. Нельзя автоматически снимать bookingAllowed = FALSE при повторном одобрении специалиста.
7. Нельзя лишить специалиста эффективного допуска и оставить ACTIVE Reservation без согласованной обработки.
8. Нельзя откладывать обязательную административную отмену ACTIVE Reservation на независимую фоновую задачу.
9. Нельзя автоматически отменять CONFIRMED Booking только из-за административной блокировки специалиста.
10. Нельзя реактивировать административно отменённые Reservation при восстановлении доступа.
11. Нельзя произвольно менять BookingStatus в обход Booking Domain.
12. Нельзя считать консультацию проведённой без установленного SessionOutcome.
13. Нельзя подменять структурированный административный аудит только application logs.
14. Нельзя выполнять произвольные административные действия без проверки полномочий.
15. Нельзя раскрывать избыточные чувствительные данные через административные API.

# 26. Открытые вопросы

## 26.1. Полный набор статусов

Необходимо окончательно согласовать:

- UserStatus;
- SpecialistApprovalStatus;
- допустимые переходы между состояниями.

## 26.2. Блокировка клиента

Нужны отдельные правила влияния блокировки клиентского аккаунта на его ACTIVE Reservation и CONFIRMED Booking.

## 26.3. Подтверждённые Booking заблокированного специалиста

Сейчас утверждено сохранение CONFIRMED Booking.

Необходимо отдельно определить, как платформа поступает с консультациями, которые ещё предстоит провести во время длительной блокировки.

## 26.4. Исключительная отмена Booking

Нужно определить условия административной отмены после начала консультации.

## 26.5. Восстановление допуска

Требуется формализовать переходы и необходимые административные проверки.

## 26.6. Модерация Review

Необходимо определить полномочия, основания и историю административных действий.

## 26.7. DisputeResolution

Требуется уточнить:

- допустимые решения;
- возможность пересмотра;
- историю повторных решений;
- последствия изменения результата.

## 26.8. Аудит

Следует определить, требуется ли универсальная модель AdministrativeAction или достаточно специализированных записей аудита.

## 26.9. Конкурентность

Нужно проверить взаимодействие:

- BookingAccess;
- UserStatus;
- approvalStatus;
- Reservation row locks;
- FK-блокировок PostgreSQL.

# 27. Итог

Admin в PsyWeb обеспечивает системную модерацию и контролируемые административные операции.

Основные принципы:
