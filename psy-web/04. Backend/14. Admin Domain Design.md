## Overview

This section defines the admin domain of the PsyWeb system. It is responsible for system-level management operations, including user moderation, specialist verification, and administrative overrides of business entities.

The admin domain has elevated privileges and operates across multiple business modules, but does not own domain logic of those modules.

---

# Core Concept

The admin role represents a system operator with global access to management functions across the platform.

Admins can perform controlled modifications to system data, but all actions must still respect core domain invariants.

---

# Admin Responsibilities

## 1. Specialist verification

- approve specialist registrations
- reject specialist applications
- manage verification status

---

## 2. User moderation

- deactivate or block users
- review user activity
- enforce platform rules

---

## 3. Booking moderation

- view Booking and post-session outcome history
- resolve conflicting post-session outcome reports
- record administrative DisputeResolution
- cancel bookings in exceptional cases through existing domain workflows

---

## 4. System oversight

- monitor platform integrity
- access aggregated system data
- audit critical operations

---

# Access Scope

Admin has read and controlled write access to:

- user module
- specialist module
- booking module
- review module
- availability module (read-heavy access)

---

# Admin Constraints

## 1. No domain ownership

Admin does not own business logic of any module.

All changes must go through existing service layer rules.

---

## 2. No bypass of invariants

Admin actions must not violate:

- booking integrity rules
- slot consistency rules
- review constraints

---

## 3. Controlled administrative operations only

Admin may initiate privileged business operations, but state changes remain owned by the corresponding domain module.

For Specialist approval:

- Admin chooses the administrative decision;
- Specialist domain validates and applies the approval transition;
- Admin does not modify Specialist persistence directly.

Administrative authority does not transfer domain ownership.

---

# Specialist Moderation Flow

Specialist professional state is owned by the Specialist domain.

The current `Specialist` state machine already supports:

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

The corresponding service operations currently exist in `SpecialistService`:

```text
approveSpecialist(...)
rejectSpecialist(...)
resubmitSpecialist(...)
suspendSpecialist(...)
reinstateSpecialist(...)
```

Each operation delegates the state transition to the Specialist domain model.

Invalid transitions are rejected by the domain rather than being silently overwritten by an administrative caller.

---

## Current Implementation

The currently implemented Specialist moderation boundary consists of:

```text
caller
→ SpecialistService
→ load Specialist
→ Specialist domain transition
→ SpecialistRepository
```

The Specialist domain owns validation of the transition.

The service owns orchestration and persistence.

The current backend does not yet contain a dedicated Admin application module or completed ADMIN-authenticated HTTP workflow around these operations.

Therefore, the existence of `SpecialistService` moderation methods must not be interpreted as completed administrator authorization infrastructure.

---

## Initial Approval

A newly created Specialist starts with:

```text
SpecialistStatus.PENDING
```

The current domain supports:

```text
PENDING → APPROVED
```

through:

```text
SpecialistService.approveSpecialist(...)
```

and:

```text
PENDING → REJECTED
```

through:

```text
SpecialistService.rejectSpecialist(...)
```

Only a PENDING Specialist may be approved or rejected.

---

## Resubmission

A rejected Specialist may return to moderation through:

```text
REJECTED → PENDING
```

The current domain and service already implement this transition through:

```text
SpecialistService.resubmitSpecialist(...)
```

Resubmission does not directly grant professional eligibility.

The Specialist must subsequently pass moderation and reach APPROVED.

---

## Suspension and Reinstatement

The current domain and service already implement the professional-state transitions:

```text
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

through:

```text
SpecialistService.suspendSpecialist(...)
SpecialistService.reinstateSpecialist(...)
```

`SUSPENDED` is distinct from `REJECTED`.

`REJECTED` belongs to the approval/resubmission lifecycle.

`SUSPENDED` represents loss of professional eligibility after a Specialist has already been APPROVED.

The linked User account may remain ACTIVE in both cases.

---

## Professional Eligibility

Administrative state changes must remain consistent with the Specialist eligibility rule.

A Specialist is professionally eligible only when:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

Consequently, Specialists in any of these states are not professionally eligible:

```text
PENDING
REJECTED
SUSPENDED
```

Account authentication and professional eligibility are separate concerns.

---

## Target Suspension Cascade

The current implementation changes the Specialist state to SUSPENDED, but the complete suspension use case is still backlog work.

The target suspension workflow additionally requires the system to stop future professional activity associated with that Specialist.

The approved target rule uses `suspendedAt` as the temporal boundary.

Only Slots satisfying:

```text
slot.startTime > suspendedAt
```

are considered future Slots for the suspension cascade.

A Slot with:

```text
slot.startTime == suspendedAt
```

is treated as already started and is not cancelled by the suspension workflow.

The target workflow must consistently handle future:

- AvailabilitySlots;
- ACTIVE Reservations;
- CONFIRMED Bookings.

The intended cancellation metadata is:

```text
cancellationInitiator = ADMIN
cancellationReason = SPECIALIST_SUSPENDED
cancelledAt = suspendedAt
```

A Slot cancelled because of suspension remains CANCELLED and is not returned to FREE.

Reinstatement does not reactivate previously cancelled Slots.

This cascade is not yet implemented in the current backend and must remain documented as target behavior until the corresponding Availability/Booking tasks are completed.

---

## Target Moderation History

The current `SpecialistStatus` field stores only the Specialist's current professional state.

The target model introduces an immutable moderation history entity:

```text
SpecialistModerationAction
```

The target action types are:

```text
APPROVED
REJECTED
RESUBMITTED
SUSPENDED
REINSTATED
```

Each moderation action creates a new historical record instead of rewriting previous decisions.

The target moderation history may store:

- `specialistId`;
- `adminId`, where applicable;
- action type;
- structured reason code;
- optional comment;
- creation timestamp.

REJECTED and SUSPENDED decisions require structured reasons according to the moderation-history contract.

Detailed suspension/rejection reasons belong to moderation history.

They must not be duplicated into every cancelled Slot, Reservation, or Booking.

Those related entities retain only the business-level cancellation reason such as:

```text
SPECIALIST_SUSPENDED
```

`SpecialistModerationAction` is backlog functionality and is not yet present in the current persistence model.

---

## Module Ownership

Administrative authority does not transfer ownership of Specialist state or persistence to the Admin module.

The intended architecture remains:

```text
Admin use case
→ SpecialistService
→ Specialist domain transition
→ SpecialistRepository
```

Admin orchestration must not:

- directly set `approvalStatus`;
- directly access `SpecialistRepository`;
- bypass Specialist state-transition validation.

The Specialist module remains the owner of Specialist professional state.

# Booking and Outcome Moderation Flow

Post-session dispute resolution is approved target/backlog functionality.

The current `PsyWeb/main` does not yet contain:

```text
SessionOutcome
SessionReport
DisputeResolution
post-session reporting services
admin dispute-resolution use case
```

Therefore, the flow described below defines the target administrative contract rather than current implementation.

Administrative intervention is not part of normal outcome resolution.

The system resolves non-conflicting cases without an administrator.

---

## Cases That Do Not Require Admin Intervention

An administrator is not involved when:

```text
OCCURRED + OCCURRED
→ RESOLVED / OCCURRED
```

or when both participants report:

```text
DID_NOT_OCCUR
+
same non-OTHER structured reason
```

which results in:

```text
RESOLVED / DID_NOT_OCCUR
```

Admin intervention is also not required when the reporting window closes with exactly one report.

In that case:

```text
one report + timeout
→ RESOLVED using the submitted report
```

This includes a single:

```text
DID_NOT_OCCUR / OTHER
```

report.

If neither participant reports before the deadline:

```text
PENDING → UNVERIFIED
```

No administrator is required merely because the session remained unverified.

---

# Target Dispute Creation

A dispute exists only when two participant SessionReports are present and cannot be resolved automatically.

Examples include:

```text
OCCURRED
vs
DID_NOT_OCCUR
```

different structured non-occurrence reasons:

```text
CLIENT_NO_SHOW
vs
SPECIALIST_NO_SHOW
```

and any two-report case where at least one report uses:

```text
OTHER
```

Therefore:

```text
OTHER + OTHER
```

also creates a dispute.

The system does not compare or semantically interpret free-text `details` in order to auto-resolve such cases.

When conflict is detected:

```text
SessionOutcome
PENDING → DISPUTED
```

and the target outcome state records:

```text
disputedAt != null
finalOutcome = null
finalReason = null
finalizedAt = null
```

Both participant SessionReports remain immutable.

---

# Target Admin Dispute Resolution

The administrator participates only after:

```text
SessionOutcome.resolutionStatus = DISPUTED
```

Target flow:

```text
DISPUTED SessionOutcome
→ admin loads both immutable SessionReports
→ admin reviews relevant context
→ admin chooses OCCURRED or DID_NOT_OCCUR
→ DisputeResolution is created
→ SessionOutcome DISPUTED → RESOLVED
```

The Admin use case coordinates the operation but must not bypass the Session/Booking-owned business boundary or directly manipulate another module's persistence.

---

## Resolve as OCCURRED

The target administrative decision is:

```text
finalOutcome = OCCURRED
reason = null
```

Administrative comment is optional.

A `DisputeResolution` is persisted with:

```text
sessionOutcomeId
adminId
finalOutcome = OCCURRED
reason = null
comment
resolvedAt
```

The SessionOutcome becomes:

```text
resolutionStatus = RESOLVED
finalOutcome = OCCURRED
finalReason = null
finalizedAt = resolvedAt
```

---

## Resolve as DID_NOT_OCCUR

For:

```text
finalOutcome = DID_NOT_OCCUR
```

the administrator must provide a structured reason.

The shared target reason model is:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
OTHER
```

The persisted DisputeResolution contains:

```text
sessionOutcomeId
adminId
finalOutcome = DID_NOT_OCCUR
reason
comment
resolvedAt
```

For:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
```

the administrative comment is optional.

For:

```text
OTHER
```

the comment is mandatory and nonblank.

The SessionOutcome becomes:

```text
resolutionStatus = RESOLVED
finalOutcome = DID_NOT_OCCUR
finalReason = selected reason
finalizedAt = resolvedAt
```

---

# Historical and Audit Semantics

Administrative resolution must not rewrite the original participant claims.

The target model retains:

```text
CLIENT SessionReport
SPECIALIST SessionReport
DisputeResolution
final SessionOutcome state
```

`DisputeResolution` is therefore a separate immutable historical record of the administrative decision.

The target database allows at most one administrative resolution for one outcome:

```text
UNIQUE(session_outcome_id)
```

---

# Admin Boundary

The administrator does not:

- rewrite participant SessionReports;
- resolve compatible participant reports manually;
- create disputes when only one report exists;
- infer an outcome when neither participant reported;
- encode attendance through `BookingStatus`;
- directly update SessionOutcome persistence outside the owning business service;
- bypass SessionOutcome transition and validation rules.

Admin responsibility is limited to resolving a genuine:

```text
DISPUTED
```

outcome through the approved application/service boundary.

---

# Current vs Target Boundary

## Current implementation

```text
No SessionOutcome admin dispute flow exists yet.
```

## Target / backlog

```text
DISPUTED SessionOutcome lookup
admin authorization
DisputeResolution creation
structured OCCURRED / DID_NOT_OCCUR decision
reason and OTHER/comment validation
SessionOutcome DISPUTED → RESOLVED
immutable preservation of participant reports
administrative dispute audit history
```

---

# Audit Requirements

Administrative operations require traceability, but current implementation and target persistence must be distinguished.

## Current State

The current backend does not yet implement a general-purpose persisted audit model for administrative actions.

Specialist moderation currently changes the Specialist's current state without persisting immutable moderation-action history.

## Target Specialist Moderation Audit

The target Specialist moderation model uses immutable `SpecialistModerationAction` records.

A moderation action must preserve enough information to identify:

- the affected Specialist;
- the moderation action;
- the responsible administrator when the action is administrative;
- the structured reason when required;
- an optional explanatory comment;
- the time of the action.

Historical moderation records are append-only from the normal business-workflow perspective.

Changing the current Specialist state must not erase previous moderation decisions.

## Target Dispute Audit

For dispute resolution, audit data must preserve:

- SessionOutcome identifier;
- original participant reports;
- final administrative decision;
- resolution timestamp;
- optional administrative comment.

The concrete SessionOutcome and DisputeResolution persistence model is documented separately and remains target behavior until its implementation tasks are completed.

- only ADMIN role can access admin controller layer

- service layer validation is still applied
- no direct repository access bypassing rules

- ensures auditability and traceability of system-level actions
