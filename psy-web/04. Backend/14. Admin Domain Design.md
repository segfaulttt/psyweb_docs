## Overview

This section defines the admin domain of the PsyWeb system. It is responsible for system-level management operations, including user moderation, specialist verification, and administrative overrides of business entities.

The admin domain has elevated privileges and operates across multiple business modules, but does not own domain logic of those modules.

---

# Core Concept

The admin role represents a system operator with global access to management functions across the platform.

Admins can perform controlled modifications to system data, but all actions must still respect core domain invariants.

---

# Admin Responsibilities

## 1. Specialist verification

- approve specialist registrations
- reject specialist applications
- manage verification status

---

## 2. User moderation

- deactivate or block users
- review user activity
- enforce platform rules

---

## 3. Booking moderation

- view Booking and post-session outcome history
- resolve conflicting post-session outcome reports
- record administrative DisputeResolution
- cancel bookings in exceptional cases through existing domain workflows

---

## 4. System oversight

- monitor platform integrity
- access aggregated system data
- audit critical operations

---

# Access Scope

Admin has read and controlled write access to:

- user module
- specialist module
- booking module
- review module
- availability module (read-heavy access)

---

# Admin Constraints

## 1. No domain ownership

Admin does not own business logic of any module.

All changes must go through existing service layer rules.

---

## 2. No bypass of invariants

Admin actions must not violate:

- booking integrity rules
- slot consistency rules
- review constraints

---

## 3. Controlled administrative operations only

Admin may initiate privileged business operations, but state changes remain owned by the corresponding domain module.

For Specialist approval:

- Admin chooses the administrative decision;
- Specialist domain validates and applies the approval transition;
- Admin does not modify Specialist persistence directly.

Administrative authority does not transfer domain ownership.

---

# Specialist Approval Flow

A newly submitted Specialist application has:

`approval_status = PENDING`

The administrator may make one of two approval decisions:

`PENDING → APPROVED`

or:

`PENDING → REJECTED`

Typical flow:

`Specialist application is PENDING`
→ Admin reviews application
→ AdminService validates administrative authority
→ AdminService requests approval or rejection through SpecialistService
→ SpecialistService validates the current approval state
→ SpecialistService applies the transition
→ Specialist-owned persistence stores the updated approval state

Ownership is intentionally separated:

- Admin owns the administrative use case and decision;
- Specialist owns `approval_status` and its state machine;
- SpecialistService owns validation and application of the transition;
- SpecialistRepository remains internal to the Specialist module.

Admin must not directly set `approval_status` or access SpecialistRepository.

The currently documented workflow does not define a transition out of APPROVED or REJECTED. Any resubmission, reopening, suspension, or later re-verification lifecycle requires a separate explicit business rule.

# Booking and Outcome Moderation Flow

Admin intervention is not part of the normal post-session outcome workflow.

Compatible participant reports are resolved automatically.

If exactly one participant reports before the reporting deadline, that report is accepted after timeout.

If neither participant reports, the SessionOutcome becomes UNVERIFIED without administrative intervention.

Admin involvement is required only when participant reports conflict.

## Dispute Resolution Flow

```text
CLIENT and SPECIALIST submit conflicting SessionReports
→ SessionOutcome becomes DISPUTED
→ admin reviews both immutable reports and relevant context
→ admin chooses final decision: OCCURRED or DID_NOT_OCCUR
→ DisputeResolution is persisted
→ SessionOutcome becomes RESOLVED
→ final_outcome is set to the administrative decision
```

The administrator does not:

* rewrite participant SessionReports;
* infer outcomes for sessions with no reports;
* intervene in compatible reports;
* bypass Booking domain outcome rules.

DisputeResolution is retained as historical audit data.

---

# Audit Requirements

Admin actions must be traceable:

- admin_id recorded in system logs
- action type logged
- timestamp stored
- affected entity recorded

For dispute resolution, audit data must also preserve:

- SessionOutcome identifier
- both original SessionReports
- final administrative decision
- resolution timestamp
- optional administrative comment

---

# Security Rules

## 1. Admin-only endpoints

All admin endpoints are strictly protected by RBAC:

- only ADMIN role can access admin controller layer

---

## 2. Double validation

Even for admin actions:

- service layer validation is still applied
- no direct repository access bypassing rules

---

## 3. Separation of concerns

Admin module does not contain:

- booking logic
- availability logic
- review logic

It only orchestrates existing services.

---

# Error Scenarios

Common exceptions:

- UnauthorizedAdminAccessException

# Integration with Other Domains

## User domain

- status updates (ACTIVE / BLOCKED)

## Specialist domain

- verification status changes

## Booking domain

- exceptional Booking cancellation through Booking rules
- resolution of DISPUTED SessionOutcomes
- creation of historical DisputeResolution records

## Review domain

- moderation of abusive content (future extension)

---

# Consistency Rules

- all admin actions must preserve domain invariants
- no direct database manipulation outside service layer
- all changes must be consistent with business rules

---

# Summary

The admin domain:

- provides centralized system management capabilities
- enforces moderation and verification workflows
- operates across multiple modules without owning their logic
- respects all business invariants and service-layer rules
- ensures auditability and traceability of system-level actions
