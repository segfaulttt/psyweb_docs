## Overview

This section describes the core database entities of the PsyWeb platform and their relationships. The model is designed around a booking-centric marketplace architecture, where the booking flow is the central transactional process connecting clients and specialists.

---

# 1. User

Represents all system users: clients, specialists, and administrators.

### Fields:

- id (PK)
- email (unique)
- password_hash
- role (CLIENT / SPECIALIST / ADMIN)
- status (ACTIVE / BLOCKED)
- created_at

### Description:

Base authentication and identity entity for all platform users. Role determines system access level and available functionality.

---

# 2. SpecialistProfile

Extended profile for users with SPECIALIST role.

### Fields:

- id (PK)
- user_id (FK → User.id)
- first_name
- last_name
!!!!!! - bio
- approval_status

### Relationships:

- 1:1 with User
- 1:N with Service
- 1:N with AvailabilitySlot

---

# 3. ClientProfile

Extended profile for users with CLIENT role.

### Fields:

- id (PK)
- user_id (FK → User.id)
- first_name
- last_name

### Relationships:

- 1:1 with User

---

# 4. Service

Represents consultation services offered by specialists.

### Fields:

- id (PK)
- specialist_id (FK → SpecialistProfile.id)
- title
- description
- duration_minutes
- price (optional)
- is_active

### Relationships:

- N:1 with SpecialistProfile

---

# 5. AvailabilitySlot

Represents time slots created by specialists for bookings.

### Fields:

- id (PK)
- specialist_id (FK → SpecialistProfile.id)
- start_time
- end_time
- status (FREE / BOOKED / BLOCKED)

### Relationships:

- N:1 with SpecialistProfile
- 1:0..1 with Booking

### Key Rule:

Each slot can be booked only once.

---

# 6. Booking

Core transactional entity of the system.

### Fields:

- id (PK)
- client_id (FK → User.id)
- specialist_id (FK → SpecialistProfile.id)
- service_id (FK → Service.id)
- slot_id (FK → AvailabilitySlot.id)
- status (CREATED / CONFIRMED / CANCELLED / COMPLETED / NO_SHOW)
- created_at
- cancelled_at

### Relationships:

- N:1 with Client (User)
- N:1 with SpecialistProfile
- 1:1 with AvailabilitySlot
- 0..1 with Review
- 0..1 with ChatThread

### Key Rule:

Booking is the central entity ensuring consistency between client intent and specialist availability.

---

# 7. Review

Represents feedback left by clients after completed appointments.

### Fields:

- id (PK)
- booking_id (FK → Booking.id)
- client_id (FK → User.id)
- specialist_id (FK → SpecialistProfile.id)
- rating (1–5)
- comment
- created_at

### Relationships:

- 1:1 with Booking (only after COMPLETED status)

### Business Rule:

Reviews can only be created after booking completion.

---

# 8. ChatThread (Optional Module)

Represents communication channel tied to a booking.

### Fields:

- id (PK)
- booking_id (FK → Booking.id)
- client_id
- specialist_id

### Relationships:

- 1:1 with Booking
- 1:N with Message

---

# 9. Message

Individual messages inside chat threads.

### Fields:

- id (PK)
- thread_id (FK → ChatThread.id)
- sender_id
- text
- sent_at

### Relationships:

- N:1 with ChatThread

---

# Core Relationship Summary

- User → 1:1 → ClientProfile / SpecialistProfile
- SpecialistProfile → 1:N → Service
- SpecialistProfile → 1:N → AvailabilitySlot
- AvailabilitySlot → 0..1 → Booking
- Booking → 0..1 → Review
- Booking → 0..1 → ChatThread
- ChatThread → 1:N → Message

---

# Domain Rule Summary

- Booking is the central transactional entity
- Slot is the atomic unit of availability
- Review strictly depends on completed bookings
- Specialist owns services and schedule
- User identity is separated from domain profiles
