## Overview

This section describes the core database entities of the PsyWeb platform and their relationships. The model is designed around a booking-centric marketplace architecture, where the booking flow is the central transactional process connecting clients and specialists.

---

# 1. User

Represents all system users: clients, specialists, and administrators.

### Fields:

- id (PK)
- email (unique)
- password_hash
- role (CLIENT / SPECIALIST / ADMIN)
- status (ACTIVE / BLOCKED)
- created_at

### Description:

Base authentication and identity entity for all platform users. Role determines system access level and available functionality.

---

# 2. Specialist

Represents specialist-specific identity, professional approval state, and specialist-level temporal booking policies for a User with `SPECIALIST` role.

Specialist approval is independent from User account status.

### Current Fields

The current `PsyWeb/main` model contains:

* `user_id` (PK, FK → User.id)
* `first_name`
* `last_name`
* `approval_status`
* `minimum_booking_notice_minutes`
* `client_cancellation_notice_minutes`

The current Specialist status values are:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

---

### Temporal Policy Representation

In the Java domain model, both specialist temporal settings are represented as:

```text
java.time.Duration
```

The current fields are:

```text
minimumBookingNotice
clientCancellationNotice
```

Persistence stores them as whole minutes:

```text
minimum_booking_notice_minutes INTEGER
client_cancellation_notice_minutes INTEGER
```

JPA conversion is handled by:

```text
DurationMinutesConverter
```

The converter maps:

```text
Duration ↔ Integer minutes
```

Only whole-minute Duration values are supported.

The Specialist domain rejects values that are:

* null;
* negative;
* not representable as whole minutes;
* outside the supported Integer-minute range.

The database additionally enforces non-negative persisted values.

---

### Current Persistence State

The specialist-level temporal settings are already implemented and persisted.

Migration `V9__add_specialist_booking_notice_settings.sql` introduced:

```text
minimum_booking_notice_minutes INTEGER NOT NULL
client_cancellation_notice_minutes INTEGER NOT NULL
```

with non-negative CHECK constraints.

The migration temporarily used `DEFAULT 0` while adding the columns and then removed those defaults.

New application writes therefore provide explicit values rather than relying on a permanent database default.

---

### Minimum Booking Notice

`minimumBookingNotice` defines the specialist-level default policy for how long before a session new Reservations may be created.

Conceptually:

```text
bookingDeadline =
slot.startTime - effectiveMinimumBookingNotice
```

The specialist-level `Duration` setting and its persistence are already implemented.

Enforcement of the booking deadline in the Reservation creation flow is separate lifecycle functionality and must not be inferred merely from the existence of this persisted field.

---

### Per-Slot Minimum Booking Notice Override

The approved target model allows an AvailabilitySlot to optionally override the specialist default.

Target resolution rule:

```text
effectiveMinimumBookingNotice =
slot override, when present
otherwise specialist.minimumBookingNotice
```

However, the current `AvailabilitySlot` entity in `PsyWeb/main` does not yet contain or persist a per-slot minimum-booking-notice override.

Therefore:

```text
Specialist default
= current implementation

AvailabilitySlot override
= target / backlog
```

Documentation must not describe the slot override as already implemented persistence.

---

### Client Cancellation Notice

`clientCancellationNotice` is a separate Specialist-level policy.

It is persisted independently from `minimumBookingNotice`.

Conceptually:

```text
clientCancellationDeadline =
slot.startTime - clientCancellationNotice
```

The two settings represent different business rules:

```text
minimumBookingNotice
→ controls how late a new Reservation may be created

clientCancellationNotice
→ determines the cancellation cutoff for an existing confirmed Booking
```

The Specialist-level `clientCancellationNotice` field and its persistence are already implemented.

The complete Booking cancellation metadata and late-cancellation behavior belong to separate Booking lifecycle tasks and must not be treated as implemented solely because the policy value is persisted.

---

### Relationships

Current core relationships include:

* 1:1 with User;
* 1:N with AvailabilitySlot;
* future/adjacent specialist-owned models may reference Specialist according to their own module contracts.

---

### Approval Status Semantics

`PENDING` — the Specialist is waiting for moderation.

`APPROVED` — the Specialist passed moderation and may become professionally eligible when the linked User is also ACTIVE and has role SPECIALIST.

`REJECTED` — the approval or resubmission attempt was rejected.

`SUSPENDED` — a previously APPROVED Specialist was administratively removed from professional eligibility.

User account status and Specialist professional status remain separate state models.

---

### Current Approval Lifecycle

The current Specialist domain implements:

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

The corresponding domain operations are:

```text
approve()
reject()
resubmit()
suspend()
reinstate()
```

Invalid source states are rejected by the Specialist domain.

---

### Current Professional Eligibility

The current eligibility rule is:

```text
UserRole.SPECIALIST
+
UserStatus.ACTIVE
+
SpecialistStatus.APPROVED
```

This rule is implemented by `Specialist.isEligible()`.

`PENDING`, `REJECTED`, and `SUSPENDED` are not professionally eligible states.

---

### Target Moderation Extensions

The current Specialist table stores the current professional state only.

The target model introduces separate immutable moderation history through `SpecialistModerationAction`.

That future model stores moderation actions and their reasons without turning Specialist itself into a mutable audit log.

The complete suspension cascade across future AvailabilitySlots, Reservations, and Bookings is also separate backlog functionality.

---

### Model Scope

Specialist is the core specialist entity.

The following concerns are intentionally not represented as generic fields of Specialist core:

- public biography;
- arbitrary public page content;
- education history;
- diplomas and verification documents;
- professional retraining history;
- additional qualifications;
- per-credential verification state;
- moderation history records.

Public profile, professional qualification, and moderation-history models may reference Specialist, but they represent separate concepts with their own lifecycle and persistence requirements.

For MVP, the absence of these extended models does not prevent the current Specialist core lifecycle from functioning.

A future public page builder is presentation-oriented product scope and does not change the identity or professional-state model of Specialist.

# 5. AvailabilitySlot

Represents a discrete period of availability created by a Specialist.

AvailabilitySlot is owned by the Availability domain.

### Current Fields

The current `PsyWeb/main` entity contains:

```text
id
specialist_id
start_time
end_time
availability_status
```

Current status values are:

```text
FREE
RESERVED
BOOKED
CANCELLED
```

A newly created slot starts as:

```text
FREE
```

The current persistence model does not contain a per-slot minimum booking notice override.

---

### Current Relationships

```text
AvailabilitySlot N → 1 Specialist

AvailabilitySlot 1 → N Reservation history

AvailabilitySlot → Booking relationship exists through Booking.slot
```

Reservation and Booking lifecycle are owned by the Booking domain.

Availability owns only AvailabilitySlot state.

---

### Current State Semantics

```text
FREE
```

means that the slot is not currently held by a Reservation or occupied by a Booking.

```text
RESERVED
```

means that the slot is temporarily held by an ACTIVE Reservation.

```text
BOOKED
```

means that Reservation confirmation has converted the temporary hold into Booking occupancy.

```text
CANCELLED
```

means that the availability has been removed and remains historical.

The current domain supports:

```text
FREE → RESERVED
RESERVED → FREE
RESERVED → BOOKED
BOOKED → FREE
active state → CANCELLED
```

`CANCELLED` is terminal in the approved model.

---

### Current Overlap Check

Slot creation currently performs an application-level overlap pre-check using the half-open interval predicate:

```text
newStart < existingEnd
&&
newEnd > existingStart
```

This allows adjacent slots such as:

```text
10:00–11:00
11:00–12:00
```

without treating them as overlapping.

The current repository pre-check does not yet implement the complete approved active-slot semantics because historical CANCELLED rows are not excluded by that query.

The current database also does not yet contain the approved PostgreSQL exclusion constraint.

---

### Target Overlap Protection

The approved target model applies overlap protection only to active availability statuses:

```text
FREE
RESERVED
BOOKED
```

while:

```text
CANCELLED
```

is historical and must not block reuse of the same interval.

The final concurrency-safe model uses defense in depth:

```text
application pre-check
+
PostgreSQL exclusion constraint
```

with half-open interval semantics:

```text
[start_time, end_time)
```

The database constraint is target/backlog functionality and must be introduced through a new forward Flyway migration.

Applied migrations must not be edited.

---

### Target Booking Deadline

The Specialist currently stores the default:

```text
minimumBookingNotice
```

as `java.time.Duration`, persisted as whole integer minutes.

The approved target booking deadline is:

```text
bookingDeadline =
slot.startTime - effectiveMinimumBookingNotice
```

where:

```text
effectiveMinimumBookingNotice =
slot override when present
otherwise Specialist default
```

However:

```text
Specialist default
→ current implementation

AvailabilitySlot override
→ target/backlog

booking-deadline enforcement during Reservation creation
→ target/backlog
```

Therefore the current AvailabilitySlot entity must not be documented as already containing:

```text
minimum_booking_notice
```

A FREE slot may eventually be non-bookable after its cutoff without requiring another AvailabilityStatus, but that final deadline enforcement is not yet implemented.

---

### Current vs Target Boundary

#### Current

```text
AvailabilitySlot entity
FREE / RESERVED / BOOKED / CANCELLED states
slot state-transition methods
application overlap pre-check
half-open overlap predicate
controlled current time during slot creation
```

#### Target / backlog

```text
per-slot minimumBookingNotice override
bookingDeadline enforcement
CANCELLED-aware overlap pre-check
PostgreSQL active-slot exclusion constraint
database translation to SlotOverlapException
```
---

# 6. Booking

Represents a confirmed consultation created from a successfully confirmed Reservation.

Booking does not represent the temporary Reservation hold stage.

### Current Fields

The current `PsyWeb/main` Booking entity contains:

```text
id
reservation_id
client_id
specialist_id
slot_id
status
created_at
cancelled_at
```

The current entity does not contain:

```text
service_id
cancellation_initiator
```

Those must not be documented as current persisted Booking fields.

---

### Current Status Model

The current implementation still contains the legacy BookingStatus values:

```text
CONFIRMED
CANCELLED
COMPLETED
NO_SHOW
```

The Booking entity also currently contains legacy transitions for:

```text
CONFIRMED → COMPLETED
CONFIRMED → NO_SHOW
```

and the existing applied database CHECK constraint still permits all four values.

This is current implementation state.

It is not the approved target lifecycle.

---

### Approved Target Status Model

The approved target Booking lifecycle contains only:

```text
CONFIRMED
CANCELLED
```

Post-session attendance and result must not be encoded as:

```text
COMPLETED
NO_SHOW
```

inside BookingStatus.

Those concerns move to the separate target:

```text
SessionOutcome
```

model.

Therefore removal of:

```text
COMPLETED
NO_SHOW
```

requires future code and schema changes.

Existing applied Flyway migrations must not be rewritten.

---

### Current Creation Flow

A Booking is created during successful Reservation confirmation.

Current orchestration is:

```text
ACTIVE and unexpired Reservation
→ Reservation CONFIRMED
→ AvailabilitySlot RESERVED → BOOKED
→ Booking created as CONFIRMED
```

Booking creation is coordinated by `BookingService`.

---

### Current Relationships

The current entity references:

```text
Reservation
Client User
Specialist
AvailabilitySlot
```

Current JPA models:

```text
Booking → Reservation
```

and:

```text
Booking → AvailabilitySlot
```

as one-to-one associations.

The applied database history does not yet fully reflect every approved target cardinality.

In particular:

- `reservation_id` was added by a forward migration as a foreign key without the final approved database `UNIQUE` guarantee;
- the original schema made `bookings.slot_id` unique, so the current persistence history does not yet support the approved model of multiple historical Bookings for one slot after cancellation and rebooking.

These schema differences require future forward migrations.

---

### Target Cardinality

The approved target model requires:

```text
Reservation 1 → 0..1 Booking
```

protected by:

```text
UNIQUE(reservation_id)
```

and allows:

```text
AvailabilitySlot 1 → many historical Bookings
```

while permitting only one current CONFIRMED Booking occupancy.

Therefore target persistence must eventually remove the obsolete permanent uniqueness of:

```text
slot_id
```

and replace it with a constraint that protects only active/current Booking occupancy.

That change must be forward-only.

---

### Cancellation Metadata

The current Booking entity stores:

```text
cancelled_at
```

but does not yet store:

```text
cancellation_initiator
```

The approved target cancellation model records the initiator so cancellation history can distinguish actors such as:

```text
CLIENT
SPECIALIST
ADMIN
```

where required by the corresponding business workflow.

Late client cancellation remains derived from the cancellation timestamp relative to the configured cancellation deadline rather than represented by another BookingStatus.

This metadata is target/backlog unless already introduced by the corresponding implementation task.

---

### Target Post-Session Boundary

Booking answers:

> Does a confirmed appointment exist, or was it cancelled?

The separate SessionOutcome target model answers:

> What actually happened during the scheduled consultation?

Therefore:

```text
BookingStatus
```

must not become the final source of attendance/no-show truth.

---

### Current vs Target Boundary

#### Current

```text
Booking entity
CONFIRMED / CANCELLED / COMPLETED / NO_SHOW enum
legacy complete() operation
legacy markNoShow() operation
CONFIRMED Booking creation
Booking cancellation
cancelledAt
Reservation / User / Specialist / Slot relationships
```

#### Target / backlog

```text
BookingStatus reduced to CONFIRMED / CANCELLED
COMPLETED / NO_SHOW removed
post-session result moved to SessionOutcome
UNIQUE reservation_id at database level
multiple historical Bookings per slot
active Booking occupancy protected separately
cancellation initiator persistence
```

---

# 7. SessionOutcome

Represents the approved target persistence model for resolving what happened during a non-cancelled confirmed consultation.

Booking lifecycle and SessionOutcome lifecycle are separate concerns.

The current `PsyWeb/main` does not yet implement this entity or its persistence table.

Everything in this section is target/backlog state.

### Target Fields

* `id` (PK)
* `booking_id` (FK → Booking.id, unique)
* `resolution_status`
* `final_outcome` (nullable)
* `final_reason` (nullable)
* `created_at`
* `reporting_deadline`
* `disputed_at` (nullable)
* `finalized_at` (nullable)

### Resolution Status

Target values:

```text
PENDING
DISPUTED
RESOLVED
UNVERIFIED
```

### Final Outcome

When resolved, the final outcome is:

```text
OCCURRED
DID_NOT_OCCUR
```

For unresolved or unverified outcomes, `final_outcome` remains null.

### Final Reason

`final_reason` uses:

```text
SessionNonOccurrenceReason
```

with values:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
OTHER
```

`final_reason` is allowed only when:

```text
final_outcome = DID_NOT_OCCUR
```

For:

```text
final_outcome = OCCURRED
```

the reason must remain null.

---

### Relationships

Target cardinality:

```text
Booking 1 → 0..1 SessionOutcome

SessionOutcome 1 → 0..2 SessionReport

SessionOutcome 1 → 0..1 DisputeResolution
```

`booking_id` is unique so one Booking cannot produce multiple SessionOutcome rows.

---

### Creation Semantics

The approved target strategy uses automatic/eager creation.

For a non-cancelled:

```text
BookingStatus.CONFIRMED
```

post-session processing begins when:

```text
now >= AvailabilitySlot.endTime
```

The system then creates:

```text
SessionOutcome(
    resolutionStatus = PENDING
)
```

Creation must be idempotent.

A cancelled Booking does not enter the normal post-session workflow.

---

### Reporting Window

The target reporting window is:

```text
24 hours after AvailabilitySlot.endTime
```

Therefore:

```text
reportingDeadline =
slot.endTime + 24 hours
```

The valid reporting interval is:

```text
[slot.endTime, reportingDeadline)
```

A report is accepted while:

```text
now >= slot.endTime
&&
now < reportingDeadline
```

At:

```text
now == reportingDeadline
```

the reporting window is closed.

---

### Resolution Semantics

#### PENDING

The reporting process is unresolved.

Required state:

```text
final_outcome = null
final_reason = null
finalized_at = null
```

---

#### DISPUTED

Participant reports exist but conflict and require administrative resolution.

Required state:

```text
final_outcome = null
final_reason = null
disputed_at != null
finalized_at = null
```

---

#### RESOLVED

A final factual outcome has been established.

Required state:

```text
final_outcome != null
finalized_at != null
```

When:

```text
final_outcome = OCCURRED
```

then:

```text
final_reason = null
```

When:

```text
final_outcome = DID_NOT_OCCUR
```

then:

```text
final_reason != null
```

---

#### UNVERIFIED

The reporting deadline passed without any participant report.

Required state:

```text
final_outcome = null
final_reason = null
finalized_at != null
```

The system does not infer whether the session occurred.

---

### Target Lifecycle

```text
PENDING
├─ compatible two reports
│  → RESOLVED
│
├─ conflicting two reports
│  → DISPUTED
│  → admin resolution
│  → RESOLVED
│
├─ exactly one report + timeout
│  → RESOLVED
│
└─ zero reports + timeout
   → UNVERIFIED
```

For MVP:

```text
RESOLVED
UNVERIFIED
```

are terminal.

---

### Target Persistence Guarantees

The future table must protect at least:

```text
UNIQUE(booking_id)
```

Database CHECK constraints should additionally enforce final-state/nullability consistency where practical.

The schema must be introduced through a new forward Flyway migration.

Existing applied migrations must not be edited.

---

# 8. SessionReport

Represents one participant's immutable report about whether the scheduled consultation occurred.

This entity is target/backlog state and is not yet implemented in the current `PsyWeb/main`.

### Target Fields

* `id` (PK)
* `session_outcome_id` (FK → SessionOutcome.id)
* `actor_type`
* `reported_outcome`
* `reason` (nullable)
* `details` (nullable)
* `reported_at`

A separate `author_id` is intentionally not stored in the target model.

The concrete participant identity is derived through:

```text
SessionOutcome
→ Booking
```

while:

```text
actor_type
```

identifies which participant side submitted the report.

---

### Actor Type

Target values:

```text
CLIENT
SPECIALIST
```

---

### Reported Outcome

Target values:

```text
OCCURRED
DID_NOT_OCCUR
```

---

### OCCURRED Validation

When:

```text
reported_outcome = OCCURRED
```

the report requires:

```text
reason = null
details = null
```

---

### DID_NOT_OCCUR Validation

When:

```text
reported_outcome = DID_NOT_OCCUR
```

a structured reason is required.

Supported reasons:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
OTHER
```

For:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
```

`details` are optional.

For:

```text
OTHER
```

`details` are mandatory and nonblank.

---

### Immutability

Submitted SessionReports are immutable.

They are not edited, replaced, or rewritten during:

- automatic resolution;
- timeout resolution;
- administrative dispute resolution.

---

### One Report per Participant

The target database enforces:

```text
UNIQUE(session_outcome_id, actor_type)
```

Therefore one SessionOutcome may have:

```text
0..1 CLIENT report
+
0..1 SPECIALIST report
```

for a maximum of two participant reports.

---

### Automatic Compatibility

Two reports resolve automatically only when they are compatible.

Examples:

```text
OCCURRED + OCCURRED
→ RESOLVED / OCCURRED
```

and:

```text
DID_NOT_OCCUR / same non-OTHER reason
+
DID_NOT_OCCUR / same non-OTHER reason
→ RESOLVED / DID_NOT_OCCUR
```

Any pair where at least one report uses:

```text
OTHER
```

is not auto-compatible.

Therefore:

```text
OTHER + OTHER
```

also becomes a dispute.

The system does not compare free-text `details` in order to infer compatibility.

---

### Single Report at Timeout

If exactly one report exists when the reporting window closes:

```text
PENDING → RESOLVED
```

using that report's outcome and reason.

This includes:

```text
DID_NOT_OCCUR / OTHER
```

A single OTHER report does not create a dispute by itself.

---

### No Reports at Timeout

If no reports exist when the reporting window closes:

```text
PENDING → UNVERIFIED
```

No factual outcome or responsibility is inferred.

---

# 9. DisputeResolution

Represents the administrator's target persistence record for resolving a conflicting SessionOutcome.

This entity is not yet implemented in the current `PsyWeb/main`.

### Target Fields

* `id` (PK)
* `session_outcome_id` (FK → SessionOutcome.id, unique)
* `admin_id` (FK → User.id)
* `final_outcome`
* `reason` (nullable)
* `comment` (nullable)
* `resolved_at`

---

### Relationships

Target cardinality:

```text
SessionOutcome 1 → 0..1 DisputeResolution
```

and:

```text
DisputeResolution N → 1 User(ADMIN)
```

A database uniqueness constraint on:

```text
session_outcome_id
```

prevents multiple administrative resolutions for one SessionOutcome.

---

### Preconditions

A DisputeResolution may be created only when:

```text
SessionOutcome.resolutionStatus = DISPUTED
```

Dispute exists only when two participant reports conflict.

Examples include:

```text
OCCURRED
vs
DID_NOT_OCCUR
```

different DID_NOT_OCCUR reasons:

```text
CLIENT_NO_SHOW
vs
SPECIALIST_NO_SHOW
```

or any two-report case where at least one reason is:

```text
OTHER
```

---

### Resolution to OCCURRED

When:

```text
final_outcome = OCCURRED
```

then:

```text
reason = null
```

Administrative comment is optional.

The related SessionOutcome becomes:

```text
DISPUTED → RESOLVED
```

with:

```text
final_outcome = OCCURRED
final_reason = null
finalized_at = resolved_at
```

---

### Resolution to DID_NOT_OCCUR

When:

```text
final_outcome = DID_NOT_OCCUR
```

a structured reason is mandatory.

Allowed reasons:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
OTHER
```

For the first three reasons, admin comment is optional.

For:

```text
OTHER
```

admin comment is mandatory and nonblank.

The related SessionOutcome becomes:

```text
DISPUTED → RESOLVED
```

with:

```text
final_outcome = DID_NOT_OCCUR
final_reason = selected reason
finalized_at = resolved_at
```

---

### Audit Semantics

DisputeResolution does not replace the participant reports.

The target persistence model retains:

```text
original SessionReports
+
DisputeResolution
+
final SessionOutcome state
```

Administrative resolution must not rewrite the original participant claims.

---

### Target Database Guarantees

The future table must protect:

```text
UNIQUE(session_outcome_id)
```

Additional CHECK constraints should enforce outcome/reason consistency where practical.

The schema must be introduced through a new forward Flyway migration.

Applied migrations must not be rewritten.

---

### Current vs Target Boundary

The following are currently target/backlog only:

```text
SessionOutcome entity/table
SessionReport entity/table
DisputeResolution entity/table
post-session creation scheduler
report submission workflow
automatic resolution
timeout finalization
administrative dispute resolution
```

Their presence in the canonical data model describes the approved target architecture, not current production implementation.

---

Booking status alone does not make a review eligible.

# Domain Rule Summary

- Booking is the central transactional entity
- Slot is the atomic unit of availability
- Booking status represents confirmed/cancelled appointment lifecycle
- Post-session attendance is represented separately by SessionOutcome
- Review eligibility requires a RESOLVED SessionOutcome with final outcome OCCURRED
- Specialist owns services and schedule
- User identity is separated from domain profiles
