## Overview

This section describes the core database entities of the PsyWeb platform and their relationships. The model is designed around a booking-centric marketplace architecture, where the booking flow is the central transactional process connecting clients and specialists.

---

# 1. User

Represents all system users: clients, specialists, and administrators.

### Fields:

- id (PK)
- email (unique)
- password_hash
- role (CLIENT / SPECIALIST / ADMIN)
- status (ACTIVE / BLOCKED)
- created_at

### Description:

Base authentication and identity entity for all platform users. Role determines system access level and available functionality.

---

# 2. Specialist

Extended profile for users with SPECIALIST role.

### Fields:

* user_id (PK, FK → User.id)
* first_name
* last_name
* approval_status
* minimum_booking_notice

### Relationships:

- 1:1 with User
- 1:N with Service
- 1:N with AvailabilitySlot

---

# 3. ClientProfile

Extended profile for users with CLIENT role.

### Fields:

- id (PK)
- user_id (FK → User.id)
- first_name
- last_name

### Relationships:

- 1:1 with User

---

# 4. Service

Represents consultation services offered by specialists.

### Fields:

- id (PK)
- specialist_id (FK → SpecialistProfile.id)
- title
- description
- duration_minutes
- price (optional)
- is_active

### Relationships:

- N:1 with SpecialistProfile

---

# 5. AvailabilitySlot

Represents a discrete period of availability created by a specialist.

AvailabilitySlot is the atomic unit of specialist availability and preserves its lifecycle history.

### Fields:

* id (PK)
* specialist_id (FK → Specialist.user_id)
* start_time
* end_time
* status (`FREE / RESERVED / BOOKED / CANCELLED`)
* minimum_booking_notice (optional per-slot override)

### Relationships:

* N:1 with Specialist
* 1:N with Reservation
* 1:N with Booking

A slot may have multiple historical Reservations.

Only one Reservation may be `ACTIVE` for a slot at a time.

A slot may also have multiple historical Bookings because a cancelled Booking may be followed by a new Reservation and Booking for the same slot.

Only one active Booking may occupy the slot at a time.

### State Semantics:

* `FREE` — active availability with no current Reservation hold or Booking occupancy;
* `RESERVED` — temporarily held by an `ACTIVE` Reservation;
* `BOOKED` — occupied by a confirmed Booking;
* `CANCELLED` — availability explicitly removed by the specialist and retained as historical data.

`CANCELLED` is terminal.

A cancelled slot is never reactivated. If the specialist wants to offer the same time again, a new AvailabilitySlot is created.

### Bookability Rule:

`FREE` does not necessarily mean that a new Reservation may still be created.

The effective minimum booking notice is determined from:

* the AvailabilitySlot override, when present;
* otherwise, the Specialist default.

The booking deadline is:

`bookingDeadline = start_time - effectiveMinimumBookingNotice`

After this deadline, a slot may remain `FREE` while being non-bookable.

Passing the booking deadline does not introduce another AvailabilitySlot status.

### Key Rules:

* active slots for the same specialist must not overlap;
* a `CANCELLED` historical slot does not prevent creation of a new slot for the same interval;
* at most one ACTIVE Reservation may hold a slot at a time;
* at most one active Booking may occupy a slot at a time;
* historical Reservations and Bookings remain stored;
* Reservation and Booking state changes must remain consistent with AvailabilitySlot state transitions.

---

# 6. Booking

Core transactional entity of the system.

### Fields:

- id (PK)
- client_id (FK → User.id)
- specialist_id (FK → SpecialistProfile.id)
- service_id (FK → Service.id)
- slot_id (FK → AvailabilitySlot.id)
- status (CREATED / CONFIRMED / CANCELLED / COMPLETED / NO_SHOW)
- created_at
- cancelled_at

### Relationships:

- N:1 with Client (User)
- N:1 with SpecialistProfile
- 1:1 with AvailabilitySlot
- 0..1 with Review
- 0..1 with ChatThread

### Key Rule:

Booking is the central entity ensuring consistency between client intent and specialist availability.

---

# 7. Review

Represents feedback left by clients after completed appointments.

### Fields:

- id (PK)
- booking_id (FK → Booking.id)
- client_id (FK → User.id)
- specialist_id (FK → SpecialistProfile.id)
- rating (1–5)
- comment
- created_at

### Relationships:

- 1:1 with Booking (only after COMPLETED status)

### Business Rule:

Reviews can only be created after booking completion.

---

# 8. ChatThread (Optional Module)

Represents communication channel tied to a booking.

### Fields:

- id (PK)
- booking_id (FK → Booking.id)
- client_id
- specialist_id

### Relationships:

- 1:1 with Booking
- 1:N with Message

---

# 9. Message

Individual messages inside chat threads.

### Fields:

- id (PK)
- thread_id (FK → ChatThread.id)
- sender_id
- text
- sent_at

### Relationships:

- N:1 with ChatThread

---

# Core Relationship Summary

* User → 1:0..1 → Specialist
* Specialist → 1:N → Service
* Specialist → 1:N → AvailabilitySlot
* AvailabilitySlot → 1:N → Reservation
* Reservation → 1:0..1 → Booking
* AvailabilitySlot → 1:N → Booking
* Booking → 0..1 → Review
* Booking → 0..1 → ChatThread
* ChatThread → 1:N → Message

---

# Domain Rule Summary

- Booking is the central transactional entity
- Slot is the atomic unit of availability
- Review strictly depends on completed bookings
- Specialist owns services and schedule
- User identity is separated from domain profiles
