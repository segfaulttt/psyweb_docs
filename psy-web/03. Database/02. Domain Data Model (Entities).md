
# 02. Доменная модель данных PsyWeb

**Проект:** PsyWeb  
**Архитектура:** Spring Boot Modular Monolith  
**СУБД:** PostgreSQL  
**Статус:** DRAFT — целевая доменная модель MVP

---

# 1. Назначение документа

Документ определяет бизнес-сущности PsyWeb, их ответственность, поля, типы, связи, ограничения и основные правила жизненного цикла.

Доменная модель служит основой для:

- ER-диаграммы;
- реляционной схемы PostgreSQL;
- проектирования Java-сущностей;
- сервисного слоя;
- транзакционной модели;
- API;
- интеграционных тестов.

Документ описывает целевую модель, которая будет реализована после переработки backend.

Она не должна автоматически считаться описанием текущего состояния исходного кода.

## 1.1. Принципы проектирования

1. Каждое самостоятельное бизнес-понятие имеет определённого владельца.
2. Сущности не создаются только ради симметрии модулей.
3. Исторические сведения о консультациях сохраняются.
4. Изменение текущего расписания и услуг не меняет условия прошлых записей.
5. Доступность рассчитывается динамически.
6. Занятость защищена от конкурентных пересечений.
7. Доменные правила не зависят от клиентского интерфейса.
8. Система остаётся пригодной для расширения без преждевременного внедрения микросервисов.

## 1.2. Статус решений

В документе различаются:

- **Утверждено** — согласованное архитектурное решение.
- **Предлагается** — проектная модель для последующей проверки.
- **Открыто** — решение пока не принято.

Неутверждённые особенности нельзя считать обязательным требованием при реализации.

# 2. Соглашения о типах данных

| Назначение | Java | PostgreSQL |
|---|---|---|
| Идентификатор существующей сущности | Long | BIGINT |
| Идентификатор новой самостоятельной сущности | UUID | UUID |
| Абсолютный момент времени | Instant | TIMESTAMPTZ |
| Календарная дата | LocalDate | DATE |
| Локальное время суток | LocalTime | TIME |
| День недели | DayOfWeek | SMALLINT |
| Часовой пояс | ZoneId | VARCHAR |
| Длительность | Duration | INTEGER, минуты |
| Денежная сумма | BigDecimal | NUMERIC |
| Валюта | String / Currency | CHAR(3) |
| Булево значение | boolean | BOOLEAN |
| Доменное перечисление | enum | VARCHAR |

## 2.1. Идентификаторы

Для новых самостоятельных сущностей PsyWeb используется UUIDv4.

Существующие сущности с Long/BIGINT сохраняют свои идентификаторы. Массовая миграция существующих таблиц на UUID не предусматривается.

Тип внешнего ключа соответствует типу первичного ключа связанной сущности.

Пример:

- User.id — Long/BIGINT;
- RefreshSession.id — UUID;
- RefreshSession.userId — Long/BIGINT;
- RefreshToken.id — UUID;
- RefreshToken.sessionId — UUID.

UUID является идентификатором, а не заменой проверки прав доступа.

Выбранная стратегия не гарантирует автоматического повышения производительности или масштабируемости.

## 2.2. Абсолютное время

Конкретные моменты времени хранятся как Instant:

- создание и истечение Reservation;
- начало и конец консультации;
- создание и отмена Booking;
- занятые интервалы;
- timestamps административных действий.

В PostgreSQL используется TIMESTAMPTZ.

## 2.3. Календарное время

Повторяющиеся правила расписания задаются через:

- LocalDate;
- LocalTime;
- DayOfWeek;
- ZoneId.

Это необходимо, поскольку правило «каждый понедельник в 10:00» не является отдельным абсолютным моментом времени.

LocalDateTime не используется как замена Instant для сохранения конкретных консультаций.

## 2.4. Длительности

Для бизнес-длительностей используется Duration.

При сохранении в PostgreSQL применяется целое количество минут.

Должны проверяться:

- допустимый знак;
- отсутствие дробных минут;
- установленный диапазон;
- отсутствие переполнения при конвертации.

## 2.5. Денежные значения

Для денежных сумм используется BigDecimal.

Использование float и double запрещено.

Стоимость и валюта консультации фиксируются при резервировании.

Точная валютная политика MVP ещё требует согласования.

## 2.6. Обозначения ограничений

- PK — первичный ключ;
- FK — внешний ключ;
- UQ — уникальность;
- NN — NOT NULL;
- NULL — необязательное значение;
- CHECK — проверочное ограничение.

# 3. User

**Модуль:** user  
**Таблица:** users  
**Статус:** существующая сущность, преимущественно сохраняется.

## 3.1. Назначение

User представляет учётную запись пользователя платформы.

Роль определяет категорию пользователя и доступные функции.

Профильные данные клиента и специалиста хранятся отдельно.

## 3.2. Поля

| Поле | Java | Ограничения |
|---|---|---|
| id | Long | PK |
| email | String | NN, UQ |
| passwordHash | String | NN |
| role | UserRole | NN |
| status | UserStatus | NN |
| createdAt | Instant | NN |
| emailVerifiedAt | Instant | NULL |

## 3.3. Перечисления

UserRole:

- CLIENT;
- SPECIALIST;
- ADMIN.

UserStatus:

- ACTIVE;
- BLOCKED.

## 3.4. Связи

- User — Client: 1:0..1.
- User — Specialist: 1:0..1.
- User — Reservation: 1:N для клиента.
- User — Booking: 1:N для клиента.
- User — Notification: 1:N.
- User — RefreshSession: 1:N.

## 3.5. Инварианты

1. Email обязателен и уникален.
2. Email нормализуется.
3. PasswordHash не может быть пустым.
4. Роль и статус обязательны.
5. Изменение email сбрасывает подтверждение адреса.
6. Блокированный пользователь не может выполнять операции, требующие активного аккаунта.
7. Наличие роли не заменяет проверку прав на конкретный бизнес-объект.

## 3.6. Доменные методы

- normalizeEmail();
- changeEmail();
- changePasswordHash();
- verifyEmail();
- block();
- activate();
- isEmailVerified() — предлагаемый вспомогательный метод.

## 3.7. Ограничения

User не содержит управляемые коллекции всех консультаций, отзывов и сообщений.

Проверка введённого пароля относится к Auth.

User не зависит от Booking, Schedule и ServiceOffering.

# 5. Specialist

**Модуль:** specialist  
**Таблица:** specialists  
**Статус:** существующая сущность, расширяется.

## 5.1. Назначение

Specialist — профессиональный профиль психолога.

Профиль отвечает за модерационный статус и общие настройки записи, но не содержит всю логику расписания.

## 5.2. Поля

| Поле | Java | Ограничения |
|---|---|---|
| id | Long | PK, FK → User |
| user | User | NN |
| firstName | String | NN |
| lastName | String | NN |
| approvalStatus | SpecialistStatus | NN |
| minimumBookingNotice | Duration | NN, >= 0 |
| clientCancellationNotice | Duration | NN, >= 0 |
| timeZone | ZoneId | NN, предлагается |

## 5.3. SpecialistStatus

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

## 5.4. Связи

Специалист может иметь:

- несколько ServiceOffering;
- несколько WeeklyScheduleVersion;
- несколько DateSchedule;
- несколько Reservation;
- несколько Booking;
- несколько действующих ScheduleOccupancy.

Настройки режима рабочего графика выносятся в SpecialistScheduleSettings.

## 5.5. Инварианты

1. User имеет роль SPECIALIST.
2. Профессиональные операции требуют допустимого статуса специалиста.
3. MinimumBookingNotice неотрицателен.
4. ClientCancellationNotice неотрицателен.
5. Значения длительностей представлены целыми минутами.
6. Часовой пояс должен быть допустимым IANA ZoneId.
7. Изменение часового пояса не может автоматически переносить существующие Booking.

## 5.6. Доменные методы

- approve();
- reject();
- resubmit();
- suspend();
- reinstate();
- isEligible();
- changeFirstName();
- changeLastName();
- changeMinimumBookingNotice();
- changeClientCancellationNotice().

## 5.7. Ограничения

MinimumBookingNotice и ClientCancellationNotice являются разными настройками.

Первое значение определяет предельный момент создания Reservation.

Второе участвует в определении своевременности отмены Booking.

Поздняя отмена не требует отдельного статуса Booking.

Для MVP поздняя отмена сохраняется для аналитики, но не влечёт автоматического денежного штрафа.

**Модуль:** schedule  
**Таблица:** specialist_schedule_settings  
**Статус:** новая сущность.

## 7.1. Назначение

## 7.2. Поля

## 7.3. ScheduleMode

# 8. WeeklyScheduleVersion

**Модуль:** schedule  
**Таблица:** weekly_schedule_versions  
**Статус:** утверждённая концепция.

## 8.1. Назначение

Хранит полную версию повторяющегося недельного графика.

Изменение расписания с выбранной даты создаёт новую версию недельного шаблона.

## 8.2. Поля

| Поле | Java | Ограничения |
|---|---|---|
| id | Long | PK |
| specialist | Specialist | FK, NN |
| effectiveFrom | LocalDate | NN |
| effectiveUntil | LocalDate | NULL |
| createdAt | Instant | NN |

## 8.3. Связи

- Specialist — WeeklyScheduleVersion: 1:N.
- WeeklyScheduleVersion — WeeklyWorkingInterval: 1:N.

Набор интервалов версии может быть пустым.

## 8.4. Инварианты

1. Каждая версия содержит полный недельный шаблон.
2. Версии одного специалиста не пересекаются по периодам действия.
3. Для конкретной даты существует не более одной применимой версии.
4. EffectiveUntil не предшествует EffectiveFrom.
5. Изменение недельного шаблона выполняется согласованно.
6. Будущие версии не должны случайно перезаписываться при изменении текущей.

## 8.5. Методы

- isEffectiveOn(date);
- closeEffectivePeriod(date).

Создание новой версии и перенос границ предыдущей версии выполняются на сервисном уровне.

## 8.6. Ограничения

Необходимо определить политику:

- изменения уже запланированных будущих версий;
- удаления версий;
- сохранения предыдущих версий;
- конфликта с существующими записями.

Не допускается формировать две одновременно действующие версии одного специалиста.

# 10. DateSchedule

**Модуль:** schedule  
**Таблица:** date_schedules  
**Статус:** утверждённая концепция.

## 10.1. Назначение

Единая модель рабочего расписания конкретной даты.

Используется как для плавающего графика, так и для разовых исключений постоянного.

## 10.2. Поля

| Поле | Java | Ограничения |
|---|---|---|
| id | Long | PK |
| specialist | Specialist | FK, NN |
| date | LocalDate | NN |
| purpose | DateSchedulePurpose | NN |
| createdAt | Instant | NN |
| updatedAt | Instant | NN |

## 10.3. DateSchedulePurpose

- MANUAL.
- OVERRIDE.

## 10.4. Уникальность

UNIQUE(specialist_id, date, purpose).

## 10.5. Связи

- Specialist — DateSchedule: 1:N.
- DateSchedule — DateScheduleInterval: 1:N.

## 10.6. Правила

MANUAL:

- используется при FLOATING;
- задаёт часы конкретной даты;
- не повторяется автоматически.

OVERRIDE:

- используется при REGULAR;
- полностью заменяет часы этой даты из недельной версии;
- пустой список интервалов означает выходной.

При отсутствии OVERRIDE используется недельное расписание.

При отсутствии MANUAL в режиме FLOATING дата нерабочая.

Сохранённые правила неактивного режима не применяются.

## 10.7. Методы

- replaceIntervals();
- clearIntervals();
- isClosed();

## 10.8. Ограничения

DateSchedule не должен автоматически отменять существующие консультации.

Изменение конкретной даты должно проверять конфликтующие обязательства.

# 13. ScheduleOccupancy

**Модуль:** booking  
**Таблица:** schedule_occupancies  
**Статус:** утверждённая концепция действующей занятости.

## 13.1. Назначение

Представляет временной интервал, закреплённый за Reservation или связанной с ней Booking.

ScheduleOccupancy является источником истины о занятом времени.

Reservation и Booking остаются источниками истины о бизнес-состоянии записи.

## 13.2. Поля

| Поле | Java | Ограничения |
|---|---|---|
| id | Long | PK |
| specialist | Specialist | FK, NN |
| reservation | Reservation | FK, NN, UQ |
| startTime | Instant | NN |
| sessionEndTime | Instant | NN |
| occupiedUntil | Instant | NN |

## 13.3. Интервалы

Консультация:

[startTime, sessionEndTime)

Занятость:

[startTime, occupiedUntil)

occupiedUntil включает обязательный перерыв.

## 13.4. Инварианты

1. startTime < sessionEndTime.
2. sessionEndTime <= occupiedUntil.
3. У одного специалиста нет пересекающихся Occupancy.
4. Occupancy создаётся атомарно с Reservation.
5. Подтверждение Booking не освобождает Occupancy.
6. При отмене или истечении Reservation Occupancy удаляется.
7. При допустимой отмене Booking Occupancy удаляется.
8. История Reservation и Booking сохраняется.
9. Удаление происходит в согласованной транзакции.

## 13.5. Методы

- occupiedRange();
- belongsToSpecialist();
- matchesReservation().

Физическое удаление выполняется через сервис и репозиторий.

Отдельное поле releasedAt не используется.

## 13.6. PostgreSQL

Применяется exclusion constraint на:

- specialist_id;
- tstzrange(start_time, occupied_until, '[)').

Поскольку таблица содержит только действующую занятость, фильтр по releasedAt не нужен.

## 13.7. Ограничения

Должна быть определена политика освобождения Occupancy после окончания консультации.

Завершение календарного времени и подтверждение факта проведения консультации — разные процессы.

Удаление Occupancy не должно автоматически изменять исторический результат Booking.

# 19. Review

**Модуль:** `review`  
**Таблица:** `reviews`  
**Статус:** утверждённая бизнес-модель

## 19.1. Назначение

Review представляет отзыв клиента о специалисте.

Отзыв относится к специалисту в целом, а не к отдельной консультации.

Один клиент может оставить одному специалисту только один отзыв независимо от количества проведённых консультаций.

Создание отзыва разрешается только после консультации, успешное проведение которой подтверждено в соответствии с правилами SessionOutcome.

После публикации клиент может редактировать собственный отзыв, но не может создавать дополнительные отзывы тому же специалисту.

## 19.2. Поля

| Поле | Java | PostgreSQL | Ограничения |
|---|---|---|---|
| id | Long | BIGINT | PK |
| client | Client | BIGINT | FK, NOT NULL |
| specialist | Specialist | BIGINT | FK, NOT NULL |
| eligibilityBooking | Booking | BIGINT | FK, NOT NULL |
| rating | int | SMALLINT | NOT NULL |
| comment | String | TEXT | NULL |
| createdAt | Instant | TIMESTAMPTZ | NOT NULL |
| updatedAt | Instant | TIMESTAMPTZ | NULL |

`eligibilityBooking` — консультация, которая послужила подтверждением права клиента оставить отзыв.

Последующие консультации не изменяют эту связь автоматически.

## 19.3. Кардинальности

- Client → Review: 1:N.
- Specialist → Review: 1:N.
- Booking → Review: 1:0..1.

Один клиент может оставить отзывы разным специалистам.

Один специалист может получить отзывы от разных клиентов.

Для одной пары Client + Specialist допускается только один отзыв.

## 19.4. Уникальность

Обязательное ограничение PostgreSQL:

`UNIQUE(client_id, specialist_id)`

Это ограничение защищает от создания двух отзывов одному специалисту в том числе при конкурентных запросах.

Уникальность не определяется только по `booking_id`.

## 19.5. Оценка

Используется пятибалльная шкала:

- 1 — очень плохо;
- 2 — плохо;
- 3 — нейтрально;
- 4 — хорошо;
- 5 — отлично.

Допустимый диапазон:

`1 <= rating <= 5`

Оценка обязательна.

Текстовый комментарий необязателен.

## 19.6. Создание отзыва

Для создания Review должны выполняться все условия:

1. Автор является клиентом платформы.
2. Специалист существует.
3. Между клиентом и специалистом была хотя бы одна консультация.
4. Результат выбранной консультации подтверждён как успешно состоявшийся.
5. Консультация принадлежит этому клиенту и специалисту.
6. У пары клиент–специалист ещё нет отзыва.
7. Оценка находится в разрешённом диапазоне.

Проверка права на отзыв должна опираться на SessionOutcome.

Наличие Booking со статусом CONFIRMED само по себе недостаточно.

После успешного создания Review сохраняется ссылка на eligibilityBooking.

## 19.7. Редактирование отзыва

Клиент может редактировать собственный отзыв.

Разрешено изменять:

- rating;
- comment.

При редактировании обновляется `updatedAt`.

Не разрешено изменять:

- автора;
- специалиста;
- исходную eligibilityBooking;
- дату первоначального создания.

Редактирование не создаёт новую строку Review.

Повторная успешная консультация с тем же специалистом не требуется для редактирования уже опубликованного отзыва.

Психолог не имеет права редактировать отзыв клиента.

## 19.8. Доменные методы

Предлагаемые методы сущности:

- `changeRating(int newRating)`;
- `changeComment(String newComment)`;
- `updateContent(int rating, String comment, Instant updatedAt)`;
- `belongsToClient(Long clientId)`;
- `belongsToSpecialist(Long specialistId)`.

Необязательно реализовывать все перечисленные методы одновременно.

Следует выбрать минимальный интерфейс, который не дублирует одну и ту же операцию.

Предпочтительно использовать единый метод изменения содержания отзыва, если клиентский запрос обновляет оценку и текст вместе.

## 19.9. Сервисный слой

Предлагаемый ReviewService:

- `createReview(clientId, specialistId, rating, comment)`;
- `updateReview(reviewId, clientId, rating, comment)`;
- `getReview(reviewId)`;
- `getSpecialistReviews(specialistId, pageable)`;
- `getClientReviewForSpecialist(clientId, specialistId)`;
- `getSpecialistRatingSummary(specialistId)`.

При создании Review сервис самостоятельно определяет допустимую eligibilityBooking либо проверяет переданную клиентом консультацию.

Нельзя доверять утверждению клиента о том, что консультация состоялась.

## 19.10. Репозиторий

Предполагаемые операции:

- поиск отзыва по clientId и specialistId;
- проверка существования отзыва для пары clientId и specialistId;
- получение отзывов специалиста с пагинацией;
- получение агрегированных оценок;
- сохранение нового или изменённого отзыва.

Защита от дубликатов должна обеспечиваться не только предварительной проверкой в сервисе, но и ограничением UNIQUE в PostgreSQL.

## 19.11. Агрегированный рейтинг

Средняя оценка специалиста вычисляется по его отзывам.

Источник истины — таблица `reviews`.

При редактировании оценки изменяется результат агрегирования.

Для MVP не требуется обязательно хранить среднюю оценку внутри Specialist.

В будущем возможно кэширование агрегатов при появлении подтверждённой необходимости оптимизации.

## 19.12. Ограничения безопасности

1. Клиент может создавать и редактировать только собственные отзывы.
2. Специалист не может изменять отзывы клиентов.
3. Проверка принадлежности отзыва выполняется на сервере.
4. Проверка права на создание отзыва выполняется через авторитетные данные Booking и SessionOutcome.
5. Конкурентные попытки создания отзыва не должны нарушать уникальность.
6. Нельзя создавать отзыв на основании неподтверждённой или спорной консультации.

## 19.13. Открытые вопросы

Отдельно требуется утвердить:

- возможность удаления собственного отзыва;
- основания административного скрытия или удаления;
- срок, в течение которого допускается редактирование;
- необходимость хранения истории редакций;
- правила публичного отображения отзывов.

До принятия отдельных решений ограничения по сроку редактирования не вводятся.

## 19.14. Итоговые инварианты

1. **Один клиент — один отзыв на одного специалиста.**
2. Для первоначального создания необходима успешно подтверждённая консультация.
3. Повторные консультации не дают права создать второй отзыв.
4. Существующий отзыв можно редактировать.
5. Автор и специалист после создания не меняются.
6. Источник права на публикацию сохраняется в eligibilityBooking.
7. Оценка находится в диапазоне от 1 до 5.
8. Уникальность пары клиент–специалист обеспечивается PostgreSQL.
9. Review не изменяет Booking или SessionOutcome.
10. Публичные агрегаты вычисляются из актуальных отзывов.

# 20. Notification

**Модуль:** notification  
**Статус:** проектируемая модель.

## 20.1. Назначение

Поддержка уведомлений о значимых событиях платформы.

## 20.2. Возможные каналы

- внутриплатформенные уведомления;
- email;
- push;
- WebSocket для будущих сценариев.

## 20.3. Важное уточнение

В исходной Notification Domain Design модель Notification имела статус READ/UNREAD.

В новой предварительной модели предлагались статусы PENDING/SENT/FAILED.

Это разные состояния:

- READ/UNREAD — прочитал ли пользователь уведомление;
- PENDING/SENT/FAILED — удалось ли доставить уведомление.

Объединять их в одно поле status неправильно.

Это модель внутриплатформенного уведомления.

Состояние прочтения определяется по readAt.

## 20.5. Возможная NotificationDelivery

## 20.6. События

Концептуальные события:

- ReservationCreated;
- ReservationExpired;

- BookingCancelled;
- SessionOutcomeResolved;
- SpecialistApproved;
- SpecialistRejected;
- SpecialistSuspended;
- ReviewCreated.

События должны отражать реально произошедшие бизнес-факты.

## 20.7. Инварианты

1. Ошибка внешней доставки не отменяет Booking.
2. Отправка не выполняется как блокирующее внешнее действие внутри критической транзакции.
3. Допускается eventual consistency для доставки.
4. Повторные попытки должны быть контролируемыми.
5. Обработчики должны учитывать возможную повторную доставку события.

## 20.8. Ограничения

# 21. Auth: RefreshSession и RefreshToken

**Модуль:** auth  
**Статус:** утверждённая целевая модель MVP.

## 21.1. Назначение

Для управления долгоживущей аутентификацией используются две самостоятельные сущности:

- RefreshSession — отдельный сеанс входа пользователя;
- RefreshToken — одно поколение refresh token внутри сеанса.

Модель обеспечивает:

- независимые сессии разных устройств;
- абсолютный срок действия сессии;
- одноразовое использование refresh tokens;
- атомарную rotation;
- обнаружение повторного использования токенов;
- отзыв одной или всех сессий пользователя;
- сохранение истории поколений.

Access JWT не сохраняется в этих таблицах.

## 21.2. RefreshSession

**Таблица:** `refresh_sessions`  
**Модуль:** auth

### Назначение

RefreshSession представляет отдельный сеанс аутентификации пользователя.

Одна учётная запись может иметь несколько независимых refresh-сессий.

Каждый самостоятельный login создаёт новую сессию.

### Поля

| Поле | Java | PostgreSQL | Ограничения |
|---|---|---|---|
| id | UUID | UUID | PK, NN |
| userId | Long | BIGINT | FK, NN |
| createdAt | Instant | TIMESTAMPTZ | NN |
| expiresAt | Instant | TIMESTAMPTZ | NN |
| revokedAt | Instant | TIMESTAMPTZ | NULL |
| lastUsedAt | Instant | TIMESTAMPTZ | NULL |

Идентификатор создаётся по UUIDv4.

`userId` ссылается на существующий `User.id`, имеющий тип BIGINT.

### Срок действия

RefreshSession действует 7 дней с момента успешного login.

Срок действия абсолютный.

Успешная rotation не продлевает `expiresAt`.

Инвариант:

```text id="lmx1qh"
expiresAt = createdAt + 7 days
```

### Отзыв

`revokedAt` содержит момент отзыва сессии.

NULL означает отсутствие явного отзыва.

Сессия действительна только при выполнении условий:

```text id="bb6m35"
revokedAt IS NULL
AND currentTime < expiresAt
```

Истечение срока не требует изменения отдельного status enum.

### lastUsedAt

Поле обновляется при успешном refresh.

Создание сессии само по себе не является refresh.

Поле не влияет на абсолютный срок действия.

### Инварианты

1. Каждая RefreshSession принадлежит одному User.
2. Срок сессии не продлевается при rotation.
3. Отозванная сессия не может использоваться для refresh.
4. Истёкшая сессия не может использоваться для refresh.
5. В одной действующей сессии допускается не более одного текущего неиспользованного refresh token.
6. Отзыв одной сессии не означает автоматический отзыв остальных сессий пользователя.
7. Logout-all отзывает все refresh-сессии пользователя.
8. Изменение UserStatus на BLOCKED запрещает новые успешные refresh-операции.

## 21.3. RefreshToken

**Таблица:** `refresh_tokens`  
**Модуль:** auth

### Назначение

RefreshToken представляет отдельное поколение refresh token, выданного в рамках RefreshSession.

Запись предназначена для управления одноразовым использованием и обнаружения replay.

### Поля

| Поле | Java | PostgreSQL | Ограничения |
|---|---|---|---|
| id | UUID | UUID | PK, NN |
| sessionId | UUID | UUID | FK, NN |
| tokenHash | String | VARCHAR(64) | UNIQUE, NN |
| issuedAt | Instant | TIMESTAMPTZ | NN |
| consumedAt | Instant | TIMESTAMPTZ | NULL |

Идентификатор создаётся по UUIDv4.

`sessionId` ссылается на RefreshSession.id.

### Генерация токена

Исходный refresh token генерируется криптографически стойким генератором случайных чисел.

Токен содержит не менее 256 бит энтропии.

Refresh token является opaque secret и не содержит пользовательских claims.

### Хранение

В PostgreSQL сохраняется SHA-256 хеш исходного токена.

При выбранном hex-представлении SHA-256 длина значения составляет 64 символа.

Исходный refresh token не сохраняется в базе.

Не допускается хранить его в журналах или доменных событиях.

### Срок действия

RefreshToken не содержит отдельного `expiresAt`.

Его срок действия определяется связанной RefreshSession.

Это исключает дублирование абсолютного срока сессии.

### consumedAt

NULL означает, что токен ещё не был успешно использован для rotation.

При успешной rotation устанавливается момент использования.

Использованный токен остаётся в истории.

### Инварианты

1. Каждый RefreshToken принадлежит одной RefreshSession.
2. tokenHash уникален.
3. Исходное значение токена не хранится в PostgreSQL.
4. Использованный токен не может повторно выполнять refresh.
5. В одной сессии не допускается более одного неиспользованного токена.
6. Успешная rotation сохраняет историю предыдущего поколения.
7. Истёкшая или отозванная RefreshSession делает связанные токены непригодными для refresh.
8. Отдельный status enum для RefreshToken не требуется.

## 21.4. Связи

```text id="92cgja"
User
  |
  | 1:N
  v
RefreshSession
  |
  | 1:N
  v
RefreshToken
```

Кардинальности:

- User → RefreshSession: 1:N;
- RefreshSession → RefreshToken: 1:N.

Один пользователь может иметь несколько независимых сессий.

Одна сессия содержит историю нескольких поколений refresh token.

## 21.5. Refresh Rotation

При успешном refresh:

1. Сервер получает исходный refresh token из HttpOnly cookie.
2. Вычисляет SHA-256.
3. Находит соответствующий RefreshToken.
4. Определяет RefreshSession и владельца.
5. Получает необходимые транзакционные блокировки.
6. Повторно проверяет актуальное состояние User, RefreshSession и RefreshToken.
7. Генерирует новый access JWT и новый refresh token.
8. Устанавливает consumedAt предыдущего RefreshToken.
9. Создаёт новое поколение RefreshToken.
10. Фиксирует изменения в PostgreSQL.
11. Возвращает access JWT и устанавливает новую refresh cookie.

Rotation не продлевает срок RefreshSession.

В одной сессии одновременно не может существовать два неиспользованных refresh tokens.

## 21.6. Replay Detection

Повторное предъявление RefreshToken с заполненным consumedAt является повторным использованием ранее потреблённого токена.

При подтверждённом replay связанная RefreshSession отзывается.

Необходимо обеспечить сохранение revocation в PostgreSQL до формирования HTTP-ответа об ошибке.

Нельзя допускать, чтобы исключение автоматически откатывало уже выполненный отзыв сессии.

Для MVP grace period не применяется.

Если HTTP-ответ с новой cookie потерян после успешной rotation, пользователю может потребоваться повторный login.

## 21.7. Конкурентность

Rotation выполняется атомарно внутри транзакции PostgreSQL.

Используются:

- строковые блокировки;
- повторная проверка состояния после получения блокировок;
- уникальные ограничения;
- единый порядок захвата ресурсов.

При необходимости нескольких блокировок используется порядок:

```text id="a7dwer"
User
    ↓
RefreshSession
    ↓
RefreshToken
```

Auth module получает данные User через публичный контракт User module.

Прямое обращение к UserRepository из Auth не допускается.

Проверка UserStatus при login и refresh согласовывается с административной блокировкой аккаунта.

## 21.8. Database Constraints

Обязательные ограничения:

- PRIMARY KEY для RefreshSession.id;
- PRIMARY KEY для RefreshToken.id;
- FOREIGN KEY RefreshSession.userId → User.id;
- FOREIGN KEY RefreshToken.sessionId → RefreshSession.id;
- UNIQUE для RefreshToken.tokenHash;
- не более одного RefreshToken с consumedAt = NULL для одной RefreshSession.

Последний инвариант может обеспечиваться частичным уникальным индексом PostgreSQL.

Точный DDL определяется в Relational Schema.

## 21.9. История и удаление

История RefreshToken сохраняется:

- весь срок действия RefreshSession;
- ещё 24 часа после окончания сессии.

После этого данные удаляются периодической cleanup-задачей.

История не удаляется при каждой rotation.

Удаление выполняется с соблюдением внешних ключей.

## 21.10. Граница ответственности

Auth module владеет RefreshSession и RefreshToken.

User module владеет User и UserStatus.

Refresh-сессии не являются заменой SecurityContext или обычными HTTP-сессиями Spring.

Обычный защищённый REST-запрос использует Bearer access JWT и не требует загрузки RefreshSession.

Подробная архитектура определяется в:

`04. Backend/04. Authentication Flow.md`

# 30. Жизненные циклы

## 30.1. Reservation

ACTIVE → CONFIRMED  
ACTIVE → CANCELLED  
ACTIVE → EXPIRED

После CONFIRMED создаётся Booking.

Подтверждение после expiresAt запрещено.

## 30.2. ScheduleOccupancy

Создаётся при успешной Reservation.

Сохраняется после подтверждения Booking.

Удаляется при допустимом освобождении времени.

Не имеет отдельного статуса RELEASED.

## 30.3. Booking

Создаётся как подтверждённая консультация.

Может быть отменена по бизнес-правилам.

После консультации результат устанавливается через SessionOutcome.

История Booking не удаляется из-за отмены или завершения.

## 30.4. SessionOutcome

Участники независимо сообщают результат.

Совместимые ответы могут разрешаться автоматически.

Конфликт приводит к спору.

Отсутствие ответов не подтверждает успешное проведение.

# 32. Архитектурная проверка

Перед переходом к PostgreSQL DDL необходимо удостовериться, что:

1. У каждой сущности есть определённый владелец.
2. Нет двух противоречащих источников истины.
3. Динамическая доступность не зависит от прежних AvailabilitySlot.
4. Snapshot условий не изменяется.
5. Конкурентная запись не создаёт пересекающихся консультаций.
6. Изменение графика не отменяет Booking молча.
7. Рабочие окна не пересекают полночь.
8. Перерывы могут выходить за пределы рабочего окна.
9. Review связан с подтверждённой проведённой консультацией.
10. Административные действия не обходят бизнес-инварианты.
11. Возможности будущего чата не усложняют критический контур бронирования.
12. Разделение на модули не нарушает транзакционную целостность.
13. RefreshSession и RefreshToken принадлежат Auth module.
14. Новые самостоятельные auth-сущности используют UUIDv4.
15. Внешние ключи сохраняют тип идентификатора связанной сущности.
16. Refresh-token rotation атомарна и сохраняет историю использованных поколений.
17. UserStatus проверяется через публичный контракт User module.

# 33. Итог

Целевая доменная модель PsyWeb строится вокруг:

- каталога услуг;
- версионируемого регулярного графика;
- расписания отдельных дат;
- вычисляемой доступности;
- действующей занятости;
- временной Reservation;
- подтверждённой Booking;
- независимого подтверждения результата консультации.

История консультаций сохраняется независимо от действующей занятости.

Возможности отзывов, уведомлений, модерации, чата и будущих интеграций имеют самостоятельные границы.

**Статус: DRAFT.**

Окончательные ограничения и кардинальности проверяются при проектировании ER Diagram и PostgreSQL DDL.
