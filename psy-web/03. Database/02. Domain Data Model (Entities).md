## Overview

This section describes the core database entities of the PsyWeb platform and their relationships. The model is designed around a booking-centric marketplace architecture, where the booking flow is the central transactional process connecting clients and specialists.

---

# 1. User

Represents all system users: clients, specialists, and administrators.

### Fields:

- id (PK)
- email (unique)
- password_hash
- role (CLIENT / SPECIALIST / ADMIN)
- status (ACTIVE / BLOCKED)
- created_at

### Description:

Base authentication and identity entity for all platform users. Role determines system access level and available functionality.

---

# 2. Specialist

Extended profile for users with SPECIALIST role.

### Fields:

* user_id (PK, FK → User.id)
* first_name
* last_name
* approval_status
* minimum_booking_notice

### Relationships:

- 1:1 with User
- 1:N with Service
- 1:N with AvailabilitySlot

---

# 3. ClientProfile

Extended profile for users with CLIENT role.

### Fields:

- id (PK)
- user_id (FK → User.id)
- first_name
- last_name

### Relationships:

- 1:1 with User

---

# 4. Service

Represents consultation services offered by specialists.

### Fields:

- id (PK)
- specialist_id (FK → SpecialistProfile.id)
- title
- description
- duration_minutes
- price (optional)
- is_active

### Relationships:

- N:1 with SpecialistProfile

---

# 5. AvailabilitySlot

Represents a discrete period of availability created by a specialist.

AvailabilitySlot is the atomic unit of specialist availability and preserves its lifecycle history.

### Fields:

* id (PK)
* specialist_id (FK → Specialist.user_id)
* start_time
* end_time
* status (`FREE / RESERVED / BOOKED / CANCELLED`)
* minimum_booking_notice (optional per-slot override)

### Relationships:

* N:1 with Specialist
* 1:N with Reservation
* 1:N with Booking

A slot may have multiple historical Reservations.

Only one Reservation may be `ACTIVE` for a slot at a time.

A slot may also have multiple historical Bookings because a cancelled Booking may be followed by a new Reservation and Booking for the same slot.

Only one active Booking may occupy the slot at a time.

### State Semantics:

* `FREE` — active availability with no current Reservation hold or Booking occupancy;
* `RESERVED` — temporarily held by an `ACTIVE` Reservation;
* `BOOKED` — occupied by a confirmed Booking;
* `CANCELLED` — availability explicitly removed by the specialist and retained as historical data.

`CANCELLED` is terminal.

A cancelled slot is never reactivated. If the specialist wants to offer the same time again, a new AvailabilitySlot is created.

### Bookability Rule:

`FREE` does not necessarily mean that a new Reservation may still be created.

The effective minimum booking notice is determined from:

* the AvailabilitySlot override, when present;
* otherwise, the Specialist default.

The booking deadline is:

`bookingDeadline = start_time - effectiveMinimumBookingNotice`

After this deadline, a slot may remain `FREE` while being non-bookable.

Passing the booking deadline does not introduce another AvailabilitySlot status.

### Key Rules:

* active slots for the same specialist must not overlap;
* a `CANCELLED` historical slot does not prevent creation of a new slot for the same interval;
* at most one ACTIVE Reservation may hold a slot at a time;
* at most one active Booking may occupy a slot at a time;
* historical Reservations and Bookings remain stored;
* Reservation and Booking state changes must remain consistent with AvailabilitySlot state transitions.

---

# 6. Booking

Represents a confirmed consultation created from a successfully confirmed Reservation.

Booking does not represent the temporary hold stage. Temporary pre-confirmation state belongs to Reservation.

### Fields:

* id (PK)
* reservation_id (FK → Reservation.id, unique)
* client_id (FK → User.id)
* specialist_id (FK → Specialist.user_id)
* service_id (FK → Service.id)
* slot_id (FK → AvailabilitySlot.id)
* status (`CONFIRMED / CANCELLED`)
* created_at
* cancelled_at
* cancellation_initiator

### Relationships:

* 1:1 with Reservation
* N:1 with Client (User)
* N:1 with Specialist
* N:1 with Service
* N:1 with AvailabilitySlot
* 0..1 with SessionOutcome
* 0..1 with Review
* 0..1 with ChatThread

### Status Semantics:

`CONFIRMED` means that a confirmed appointment exists.

`CANCELLED` means that the confirmed appointment was cancelled through the normal cancellation workflow.

`CANCELLED` is terminal.

Booking does not use:

* `CREATED` — temporary pre-confirmation state belongs to Reservation;
* `COMPLETED` — successful completion is represented by a finalized SessionOutcome with final outcome `OCCURRED`;
* `NO_SHOW` — attendance and no-show claims belong to SessionReport and SessionOutcome.

### Key Rules:

* a Booking is created only from an ACTIVE and unexpired Reservation during successful confirmation;
* one Reservation may produce at most one Booking;
* Booking status represents appointment lifecycle, not post-session attendance;
* ordinary cancellation is separate from post-session outcome reporting;
* a cancelled Booking is not reactivated;
* historical Bookings remain stored.

---

# 7. SessionOutcome

Represents the post-session resolution for a non-cancelled Booking.

Booking status and SessionOutcome represent separate concerns.

### Fields:

* id (PK)
* booking_id (FK → Booking.id, unique)
* resolution_status (`PENDING / DISPUTED / RESOLVED / UNVERIFIED`)
* final_outcome (`OCCURRED / DID_NOT_OCCUR`, nullable until resolved)
* reporting_deadline
* finalized_at

### Relationships:

* 1:1 with Booking
* 1:0..2 with SessionReport
* 1:0..1 with DisputeResolution

### Resolution Semantics:

* `PENDING` — reporting window is open and no final result exists yet;
* `DISPUTED` — participant reports conflict and administrative resolution is required;
* `RESOLVED` — final outcome is established as `OCCURRED` or `DID_NOT_OCCUR`;
* `UNVERIFIED` — reporting window expired without reports from either participant.

A RESOLVED outcome must have a final_outcome.

An UNVERIFIED outcome does not infer OCCURRED or DID_NOT_OCCUR.

### Key Rules:

* the reporting window lasts 24 hours after the scheduled session end;
* a non-cancelled Booking may have at most one SessionOutcome;
* if both reports are compatible, the outcome may be resolved automatically;
* if exactly one participant reports, that report is accepted after timeout;
* if neither participant reports, the outcome becomes UNVERIFIED;
* conflicting reports become DISPUTED;
* reviews are enabled only after a RESOLVED outcome with final_outcome = OCCURRED.

---

# 8. SessionReport

Represents one participant's immutable report about whether the scheduled consultation occurred.

### Fields:

* id (PK)
* session_outcome_id (FK → SessionOutcome.id)
* author_id (FK → User.id)
* response (`OCCURRED / DID_NOT_OCCUR`)
* reason
* details
* created_at

### Relationships:

* N:1 with SessionOutcome
* N:1 with User

### Key Rules:

* CLIENT and SPECIALIST report independently;
* each participant may submit at most one report for the SessionOutcome;
* submitted reports are immutable;
* `DID_NOT_OCCUR` requires a structured reason;
* supported reasons include:

  * `CLIENT_NO_SHOW`
  * `SPECIALIST_NO_SHOW`
  * `TECHNICAL_PROBLEM`
  * `OTHER`
* `OTHER` requires free-text details.

---

# 9. DisputeResolution

Represents an administrative decision for conflicting post-session reports.

### Fields:

* id (PK)
* session_outcome_id (FK → SessionOutcome.id, unique)
* admin_id (FK → User.id)
* decision (`OCCURRED / DID_NOT_OCCUR`)
* comment
* resolved_at

### Relationships:

* 1:1 with SessionOutcome
* N:1 with User (Admin)

### Key Rules:

* DisputeResolution exists only for a DISPUTED SessionOutcome;
* an administrator resolves the dispute to OCCURRED or DID_NOT_OCCUR;
* the SessionOutcome becomes RESOLVED after the decision;
* the resolution remains stored as historical audit data.

---

# 10. Review

Represents feedback left by clients after completed appointments.

### Fields:

- id (PK)
- booking_id (FK → Booking.id)
- client_id (FK → User.id)
- specialist_id (FK → SpecialistProfile.id)
- rating (1–5)
- comment
- created_at

### Relationships:

- 1:1 with Booking

### Business Rule:

Review eligibility is determined by post-session outcome.

A review may only be created when the associated consultation has:

- SessionOutcome.resolution_status = RESOLVED
- SessionOutcome.final_outcome = OCCURRED

Booking status alone does not make a review eligible.

---

# 11. ChatThread (Optional Module)

Represents communication channel tied to a booking.

### Fields:

- id (PK)
- booking_id (FK → Booking.id)
- client_id
- specialist_id

### Relationships:

- 1:1 with Booking
- 1:N with Message

---

# 12. Message

Individual messages inside chat threads.

### Fields:

- id (PK)
- thread_id (FK → ChatThread.id)
- sender_id
- text
- sent_at

### Relationships:

- N:1 with ChatThread

---

# Core Relationship Summary

* User → 1:0..1 → Specialist
* Specialist → 1:N → Service
* Specialist → 1:N → AvailabilitySlot
* AvailabilitySlot → 1:N → Reservation
* Reservation → 1:0..1 → Booking
* AvailabilitySlot → 1:N → Booking
* Booking → 0..1 → SessionOutcome
* SessionOutcome → 0..2 → SessionReport
* SessionOutcome → 0..1 → DisputeResolution
* Booking → 0..1 → Review
* Booking → 0..1 → ChatThread
* ChatThread → 1:N → Message

---

# Domain Rule Summary

- Booking is the central transactional entity
- Slot is the atomic unit of availability
- Booking status represents confirmed/cancelled appointment lifecycle
- Post-session attendance is represented separately by SessionOutcome
- Review eligibility requires a RESOLVED SessionOutcome with final outcome OCCURRED
- Specialist owns services and schedule
- User identity is separated from domain profiles
