# ER Diagram

## Entities

The table below distinguishes current persisted/domain state from approved target/backlog entities and fields.

| Entity | State | Primary Key | Foreign Keys | Fields |
|---|---|---|---|---|
| **User** | current | `id` | — | `email`, `password`, `role`, `status`, `created_at` |
| **Specialist** | current | `user_id` | `user_id → User.id` | `first_name`, `last_name`, `approval_status (PENDING / APPROVED / REJECTED / SUSPENDED)`, `minimum_booking_notice_minutes`, `client_cancellation_notice_minutes` |
| **Service** | target / separate scope | `id` | `specialist_id → Specialist.user_id` | `title`, `description`, `duration_minutes`, `price`, `is_active` |
| **AvailabilitySlot** | current | `id` | `specialist_id → Specialist.user_id` | `start_time`, `end_time`, `availability_status (FREE / RESERVED / BOOKED / CANCELLED)` |
| **Reservation** | current | `id` | `client_id → User.id`, `slot_id → AvailabilitySlot.id` | `status (ACTIVE / CONFIRMED / EXPIRED / CANCELLED)`, `created_at`, `expires_at` |
| **Booking** | current legacy state | `id` | `reservation_id → Reservation.id`, `client_id → User.id`, `specialist_id → Specialist.user_id`, `slot_id → AvailabilitySlot.id` | `status (CONFIRMED / CANCELLED / COMPLETED / NO_SHOW)`, `created_at`, `cancelled_at` |
| **SessionOutcome** | target / backlog | `id` | `booking_id → Booking.id` | `resolution_status`, `final_outcome`, `final_reason`, `created_at`, `reporting_deadline`, `disputed_at`, `finalized_at` |
| **SessionReport** | target / backlog | `id` | `session_outcome_id → SessionOutcome.id` | `actor_type`, `reported_outcome`, `reason`, `details`, `reported_at` |
| **DisputeResolution** | target / backlog | `id` | `session_outcome_id → SessionOutcome.id`, `admin_id → User.id` | `final_outcome`, `reason`, `comment`, `resolved_at` |
| **Review** | separate Review scope | `id` | `client_id → User.id`, `specialist_id → Specialist.user_id` | `rating`, `comment`, `created_at`, `updated_at` |
| **SpecialistModerationAction** | target / backlog | `id` | `specialist_id → Specialist.user_id`, `admin_id → User.id` | `action_type`, `reason_code`, `comment`, `created_at` |
| **ChatThread** | separate scope | `id` | `booking_id → Booking.id`, `client_id → User.id`, `specialist_id → Specialist.user_id` | `created_at` |
| **Message** | separate scope | `id` | `thread_id → ChatThread.id`, `sender_id → User.id` | `text`, `sent_at` |

Important current/target differences:

```text
AvailabilitySlot.minimum_booking_notice
→ target per-slot override, not current persistence

Booking.COMPLETED / NO_SHOW
→ current legacy implementation, not approved target

SessionOutcome / SessionReport / DisputeResolution
→ approved target, not current implementation

SpecialistModerationAction
→ approved target, not current implementation
```

### Derived Attributes

`AvailabilitySlot.duration` is not stored separately.

It is calculated as:

`end_time - start_time`

## Relationships

| Relationship | Cardinality | Description |
|---|---|---|
| User → Specialist | `1 : 0..1` | A user may have zero or one Specialist profile |
| Specialist → Service | `1 : *` | A specialist may offer multiple services |
| Specialist → AvailabilitySlot | `1 : *` | A specialist may create multiple availability slots |
| User (Client) → Reservation | `1 : *` | A client may create multiple reservations |
| AvailabilitySlot → Reservation | `1 : *` | A slot may have multiple historical reservations, but only one ACTIVE reservation at a time |
| Reservation → Booking | `1 : 0..1` | A reservation may produce at most one booking |
| User (Client) → Booking | `1 : *` | A client may have multiple historical bookings |
| Specialist → Booking | `1 : *` | A specialist may have multiple historical bookings |
| AvailabilitySlot → Booking | `1 : *` | A slot may have multiple historical bookings because cancelled bookings may be followed by rebooking |
| Service → Booking | `1 : *` | A service may be referenced by multiple bookings |
| Booking → SessionOutcome | `1 : 0..1` | A booking may have at most one session outcome |
| SessionOutcome → SessionReport | `1 : 0..2` | A session may have at most one report from each participant |
| SessionOutcome → DisputeResolution | `1 : 0..1` | A session outcome may have at most one administrative dispute resolution |
| User (Client) → Review | `1 : *` | A client may review multiple specialists |
| Specialist → Review | `1 : *` | A specialist may receive multiple reviews |
| Booking → ChatThread | `1 : 0..1` | A booking may have at most one chat thread |
| ChatThread → Message | `1 : *` | A chat thread contains multiple messages |
| Specialist → SpecialistModerationAction | `1 : *` | A specialist may have multiple historical moderation actions |
| User (Admin) → SpecialistModerationAction | `1 : *` | An admin may perform multiple moderation actions |

## Relationship Constraints

### User ↔ Specialist

`User 1 ─── 0..1 Specialist`

`Specialist.user_id` is both:

- the primary key of `Specialist`;
- a foreign key referencing `User.id`.

A Specialist does not have an independent primary key.

---

### Specialist ↔ AvailabilitySlot

`Specialist 1 ─── * AvailabilitySlot`

Each availability slot belongs to exactly one specialist.

A specialist may create multiple slots.

---

### AvailabilitySlot ↔ Reservation

`AvailabilitySlot 1 ─── * Reservation`

A slot may have multiple historical reservations.

Only one reservation may be `ACTIVE` for a slot at a time.

Historical `EXPIRED` and `CANCELLED` reservations remain stored.

---

### Reservation ↔ Booking

Approved target cardinality:

```text
Reservation 1 ─── 0..1 Booking
```

One Reservation must eventually produce at most one Booking.

The target database guarantee is:

```text
UNIQUE(booking.reservation_id)
```

Current state differs:

- the Booking entity already references one Reservation;
- `reservation_id` exists in current persistence;
- the applied schema does not yet enforce the final approved `UNIQUE(reservation_id)` constraint.

Therefore:

```text
Reservation → Booking uniqueness
→ target database guarantee
```

and requires a future forward migration.

---

### AvailabilitySlot ↔ Booking

Approved target cardinality:

```text
AvailabilitySlot 1 ─── * Booking history
```

A slot may eventually retain multiple historical Bookings when a cancelled Booking is followed by a later Reservation and Booking for the same AvailabilitySlot.

Only one current confirmed occupancy may exist at a time.

Current persistence is not yet aligned with this target.

The original applied schema made:

```text
bookings.slot_id
```

permanently unique, and the current JPA association is also modeled as one-to-one.

Therefore multiple historical Bookings per slot are:

```text
target / backlog
```

and require a forward schema/domain alignment change.

---

### Booking ↔ SessionOutcome

Approved target cardinality:

```text
Booking 1 ─── 0..1 SessionOutcome
```

This relationship is target/backlog and is not currently implemented.

A SessionOutcome is created only for a non-cancelled confirmed Booking after:

```text
now >= AvailabilitySlot.endTime
```

The target database protects:

```text
UNIQUE(session_outcome.booking_id)
```

Booking status and post-session outcome are separate concerns.

The current Booking implementation still contains legacy statuses:

```text
COMPLETED
NO_SHOW
```

but the approved target BookingStatus is limited to:

```text
CONFIRMED
CANCELLED
```

with attendance/result represented by SessionOutcome instead.

---

### SessionOutcome ↔ SessionReport

Approved target cardinality:

```text
SessionOutcome 1 ─── 0..2 SessionReport
```

This model is not currently implemented.

Each report identifies its side through:

```text
actor_type = CLIENT / SPECIALIST
```

There is intentionally no separate:

```text
author_id
```

in the approved target SessionReport model.

One report per participant is protected by:

```text
UNIQUE(session_outcome_id, actor_type)
```

Reports are immutable.

A report contains:

```text
reported_outcome = OCCURRED / DID_NOT_OCCUR
```

For `DID_NOT_OCCUR`, a structured reason is required:

```text
CLIENT_NO_SHOW
SPECIALIST_NO_SHOW
TECHNICAL_PROBLEM
OTHER
```

`OTHER` requires nonblank details.

---

### SessionOutcome ↔ DisputeResolution

Approved target cardinality:

```text
SessionOutcome 1 ─── 0..1 DisputeResolution
```

This relationship is also target/backlog.

DisputeResolution exists only when two participant reports conflict and the SessionOutcome transitions:

```text
PENDING → DISPUTED
```

The target administrative record contains:

```text
admin_id
final_outcome
reason
comment
resolved_at
```

rather than a generic `decision` field.

One administrative resolution per outcome is protected by:

```text
UNIQUE(session_outcome_id)
```

After resolution:

```text
DISPUTED → RESOLVED
```

while both original SessionReports remain immutable.

Exactly one participant report at timeout does not create a dispute.

Zero reports at timeout result in:

```text
UNVERIFIED
```

---

### Client ↔ Specialist Review

A client may create at most one review for a particular specialist.

The existing review may be edited later.

This is enforced by:

`UNIQUE(client_id, specialist_id)`

A review may only be created for a session whose final outcome is `OCCURRED`.

---

### Specialist ↔ SpecialistModerationAction

Approved target cardinality:

```text
Specialist 1 ─── * SpecialistModerationAction
```

and:

```text
User(ADMIN) 1 ─── * SpecialistModerationAction
```

`SpecialistModerationAction` is approved target/backlog persistence and is not currently implemented.

The target history is immutable and records moderation actions such as:

```text
APPROVED
REJECTED
RESUBMITTED
SUSPENDED
REINSTATED
```

together with:

```text
specialist_id
admin_id
action_type
reason_code
comment
created_at
```

The moderation history does not replace or overwrite Specialist lifecycle state.

Suspension or rejection does not delete Specialist historical data.

---

### Booking ↔ ChatThread

`Booking 1 ─── 0..1 ChatThread`

A booking may have one associated chat thread.

The chat thread and its messages are separate from the booking lifecycle.

## Core Cardinality and Consistency Constraints

### Current Guarantees

The current implementation/persistence already provides or models:

- `User.email` uniqueness;
- Specialist shared identity through `user_id`;
- one ACTIVE Reservation per AvailabilitySlot through a partial unique index;
- Reservation lifecycle history;
- AvailabilitySlot lifecycle states `FREE / RESERVED / BOOKED / CANCELLED`;
- Specialist lifecycle states `PENDING / APPROVED / REJECTED / SUSPENDED`;
- Specialist temporal settings persisted as whole minutes;
- Booking references to Reservation, Client, Specialist, and AvailabilitySlot.

The current Booking implementation still contains legacy:

```text
COMPLETED
NO_SHOW
```

states.

The current slot/booking persistence also still contains older cardinality restrictions that do not yet support the complete target rebooking model.

---

### Approved Target Guarantees

Future forward migrations and implementation work must provide:

```text
Booking.reservation_id UNIQUE
```

so one Reservation produces at most one Booking.

The target model must allow:

```text
AvailabilitySlot
→ multiple historical Bookings
```

while protecting at most one current confirmed occupancy.

Availability overlap protection must use active-slot half-open interval semantics:

```text
[start_time, end_time)
```

with historical:

```text
CANCELLED
```

slots excluded from the database-level conflict constraint.

The target post-session model requires:

```text
Booking 1 → 0..1 SessionOutcome
SessionOutcome 1 → 0..2 SessionReport
SessionOutcome 1 → 0..1 DisputeResolution
```

with:

```text
UNIQUE SessionOutcome.booking_id

UNIQUE (
    SessionReport.session_outcome_id,
    SessionReport.actor_type
)

UNIQUE DisputeResolution.session_outcome_id
```

Participant SessionReports remain immutable.

A final SessionOutcome may be:

```text
RESOLVED / OCCURRED
RESOLVED / DID_NOT_OCCUR
UNVERIFIED
```

while:

```text
DISPUTED
```

requires administrative resolution.

The target Specialist moderation history is immutable and preserved separately from current Specialist status.

All target schema changes must be introduced through forward Flyway migrations.

Applied migrations must not be rewritten.
