# 2. Выбор PostgreSQL

## 2.1. Основная СУБД

PsyWeb использует PostgreSQL в качестве основной реляционной базы данных.

## 2.2. Причины выбора

PostgreSQL предоставляет:

- ACID-транзакции;
- внешние ключи;
- CHECK;
- UNIQUE;
- составные ключи;
- индексы;
- строковые блокировки;
- transaction-level advisory locks;
- GiST exclusion constraints;
- поддержку TIMESTAMPTZ;
- надёжные механизмы конкурентного доступа.

## 2.3. Приоритет согласованности

Для платформы бронирования недопустима ситуация, когда два клиента успешно резервируют пересекающееся время одного специалиста.

Поэтому корректность конкурентных операций имеет приоритет перед максимальной параллельностью записи.

## 2.4. Единая база данных

На этапе MVP используется модульный монолит с одной PostgreSQL.

Это позволяет выполнять согласованные изменения нескольких модулей в одной транзакции.

Разделение логических модулей не требует разделения их по самостоятельным физическим базам данных.

# 3. Подход к моделированию данных

## 3.1. Реляционная модель

Основные бизнес-объекты представлены отдельными таблицами.

Связи между ними обеспечиваются внешними ключами.

## 3.2. Доменные границы

Каждая таблица имеет определённого владельца в архитектуре приложения.

Например:

| Данные | Владелец |
|---|---|
| users | User |
| specialists | Specialist |
| service_offerings | Service |
| weekly_schedule_versions | Schedule |
| date_schedules | Schedule |
| reservations | Booking |
| bookings | Booking |
| schedule_occupancies | Booking |
| session_outcomes | Outcome |
| reviews | Review |
| notifications | Notification |

## 3.3. Физическая и логическая связанность

Внешние ключи могут связывать таблицы разных модулей.

Однако наличие FK не означает, что один модуль имеет право напрямую изменять Repository другого.

Межмодульные изменения выполняются через согласованные сервисные контракты.

## 3.4. Источник истины

Для каждого состояния должен существовать определённый источник истины.

Например:

- результат консультации принадлежит Outcome;
- состояние Reservation принадлежит Booking;
- рабочее расписание принадлежит Schedule;
- актуальная занятость принадлежит Booking через ScheduleOccupancy.

Нельзя хранить несколько независимо изменяемых копий одного бизнес-состояния.

# 4. Соглашения об именовании

## 4.1. Таблицы

Для целевой схемы используется:

- snake_case;
- множественное число.

Примеры:

```text id="h4nd1q"
users
specialists
service_offerings
reservations
bookings
schedule_occupancies
reviews
```

## 4.2. Историческая схема

В уже существующих Flyway-миграциях могут использоваться другие имена таблиц, в том числе единственное число.

Целевое соглашение не означает необходимость немедленно переименовать все существующие таблицы.

Изменение выполняется через новые миграции с учётом текущей схемы и JPA.

## 4.3. Колонки

Используется snake_case.

Примеры:

```text id="bq0y47"
created_at
session_start
session_end
password_hash
specialist_id
```

## 4.4. Первичные ключи

Для таблиц с самостоятельным идентификатором используется:

`id`

Для таблиц с shared primary key допускается идентификатор родительской сущности.

Например:

`specialists.user_id`

## 4.5. Внешние ключи

Внешние ключи используют суффикс:

`_id`

## 4.6. Длительности

Значения, сохраняемые в целых минутах, используют суффикс:

`_minutes`

## 4.7. Временные поля

Для абсолютных timestamps предпочтительно использовать явные имена, отражающие назначение поля:

- created_at;
- updated_at;
- expires_at;
- cancelled_at.

Для консультаций могут использоваться согласованные имена session_start и session_end.

## 4.8. Ограничения

Ограничения получают стабильные и осмысленные имена.

Например:

- uq_bookings_reservation;
- uq_reviews_client_specialist;
- fk_booking_reservation;
- chk_review_rating.

Точные имена определяются DDL и миграциями.

Они важны для диагностики и предметного преобразования ошибок PostgreSQL.

# 5. Стратегия идентификаторов

## 5.1. Основное решение

Для новых самостоятельных сущностей PsyWeb используются UUIDv4 primary keys.

Существующие сущности с Long/BIGINT сохраняют текущие идентификаторы.

Массовая миграция существующих таблиц на UUID не предусматривается.

## 5.2. UUIDv4

Для новых самостоятельных сущностей:

- Java: UUID;
- PostgreSQL: UUID;
- алгоритм генерации: UUID version 4.

UUID используется как идентификатор, а не как механизм аутентификации, авторизации или защиты от перебора ресурсов.

Генерация UUID должна быть согласована между Java и PostgreSQL.

## 5.3. Существующая схема

Существующие BIGINT primary keys не изменяются автоматически.

При работе с ними сохраняется действующая стратегия генерации идентификаторов.

Например:

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

Изменение существующего primary key требует отдельной проверки:

- JPA mappings;
- внешних ключей;
- последовательностей;
- существующих данных;
- миграционной совместимости.

## 5.4. Внешние ключи

Тип внешнего ключа соответствует типу primary key связанной сущности.

Допускается использование UUID и BIGINT в одной реляционной модели.

Пример:

```text
User.id: BIGINT
RefreshSession.id: UUID
RefreshSession.userId: BIGINT
RefreshToken.id: UUID
RefreshToken.sessionId: UUID
```

Наличие UUID primary key не требует изменения идентификаторов связанных существующих сущностей.

## 5.5. Производительность

UUID занимает больше места, чем BIGINT, и имеет иные характеристики индексирования.

Выбор UUIDv4 является архитектурным решением PsyWeb, но сам по себе не гарантирует масштабируемость.

Влияние выбранной стратегии на индексы и производительность проверяется при реализации и анализе PostgreSQL-запросов.

## 5.6. Внешний API

Тип идентификатора в PostgreSQL не должен автоматически определять всю структуру публичного API.

UUID не заменяет проверку ownership и authorization.

Передача клиенту идентификатора ресурса не означает предоставление прав на этот ресурс.

# 6. Представление enum

## 6.1. Основное решение

Для MVP предпочтительно использовать:

`VARCHAR + CHECK`

## 6.2. Значения

Значения статусов записываются в UPPER_SNAKE_CASE.

Примеры:

- ACTIVE;
- CONFIRMED;
- CANCELLED;
- EXPIRED.

## 6.3. Преимущества

Такой подход позволяет:

- читать сохранённые значения без специальных PostgreSQL ENUM types;
- контролировать допустимые состояния;
- изменять перечень значений через Flyway;
- согласовывать схему с Java enum.

## 6.4. Синхронизация

Java enum и PostgreSQL CHECK должны оставаться согласованными.

При добавлении нового значения требуется соответствующее изменение схемы.

## 6.5. Неутверждённые перечни

Если полный список значений ещё не согласован, не следует преждевременно фиксировать окончательный CHECK.

Однако отсутствие CHECK должно быть осознанным временным решением, а не заменой проверки данных.

# 7. User и email

## 7.1. Email как идентификатор

Email является каноническим идентификатором учётной записи.

## 7.2. Нормализация

Перед сохранением и поиском применяется:

```text id="x80u94"
trim
    ↓
lowercase(Locale.ROOT)
    ↓
validation
```

## 7.3. Пример

```text id="t03mm6"
"  User.Name@Example.COM  "
    ↓
"user.name@example.com"
```

## 7.4. Единая политика

Нормализация должна использоваться:

- при создании User;
- при изменении email;
- при поиске User;
- при Login.

Не допускается реализация нескольких несовместимых правил нормализации.

## 7.5. Provider-specific transformations

PsyWeb не выполняет автоматическое удаление:

- точек в локальной части;
- суффиксов +alias;
- других provider-specific элементов.

Поэтому:

```text id="1byirw"
john+test@gmail.com
```

и:

```text id="1l6x8g"
john@gmail.com
```

рассматриваются как разные email.

## 7.6. Ограничения PostgreSQL

Хранимый email защищается:

`UNIQUE(email)`

Также предусмотрено:

```sql
CHECK (email = lower(email))
```

## 7.7. Историческая миграция

В исходной реализации ограничение нормализации вводилось миграцией:

`V7__add_email_normalization_constraint.sql`

Её нельзя переписывать для согласования с новой целевой схемой.

# 8. UserStatus и UserRole

## 8.1. Роли

В User Domain предусмотрены:

- CLIENT;
- SPECIALIST;
- ADMIN.

## 8.2. Текущие статусы аккаунта

Существующая реализация UserStatus использует:

- ACTIVE;
- BLOCKED.

## 8.3. Расхождение с целевым DDL

В текущем проектном Relational Schema дополнительно присутствует:

`UserStatus.PENDING`

Этот статус не подтверждён существующим Authentication Flow.

До принятия отдельного решения нельзя считать PENDING утверждённым состоянием User.

## 8.4. Правило согласования

При окончательной подготовке миграций необходимо синхронизировать:

- User enum;
- Authorization Model;
- Authentication Flow;
- PostgreSQL CHECK.

Добавление нового статуса не должно происходить только ради соответствия одному документу.

# 9. Specialist и административные состояния

## 9.1. Профиль

Specialist хранит профильные данные и модерационное состояние специалиста.

## 9.2. Approval

В целевой схеме используется:

`approval_status`

## 9.3. Существующая реализация

Исходная реализация использует SpecialistStatus:

- PENDING;
- APPROVED;
- REJECTED;
- SUSPENDED.

Окончательная терминология SpecialistStatus / SpecialistApprovalStatus требует синхронизации.

## 9.4. Независимость допуска

approvalStatus не является единственным условием разрешения бронирования.

Для новых Reservation используются:

- User.status;
- Specialist.approvalStatus;
- SpecialistBookingAccess.bookingAllowed.

## 9.5. Изменение допуска

Административная операция, лишающая специалиста права принимать записи, должна использовать согласованный транзакционный протокол.

# 10. Разделение конфигурации специалиста

## 10.1. Основное решение

Конфигурация специалиста разделяется на самостоятельные физические таблицы.

## 10.2. SpecialistBookingAccess

Хранит:

`booking_allowed`

Используется для административного допуска и синхронизации конкурентных операций.

## 10.3. SpecialistBookingPolicy

Хранит правила:

- minimumBookingNotice;
- clientCancellationNotice.

## 10.4. SpecialistScheduleSettings

Хранит настройки:

- scheduleMode;
- bookingHorizonDays;
- другие утверждённые параметры графика.

## 10.5. SpecialistTimeZoneGuard

Хранит текущий ZoneId специалиста.

Используется для согласования изменения часового пояса с созданием Reservation.

## 10.6. Причина разделения

Отдельные таблицы позволяют применять разные блокировки к различным группам конфигурации.

Изменение профиля специалиста не должно без необходимости блокировать все операции бронирования.

## 10.7. Источник истины

Каждая настройка должна иметь одного владельца.

Не следует параллельно хранить независимо изменяемые значения minimumBookingNotice в Specialist и SpecialistBookingPolicy.

# 11. Duration

## 11.1. Java-модель

Для временных промежутков может использоваться:

`java.time.Duration`

## 11.2. Хранение

Поддерживаемые длительности сохраняются в целых минутах.

## 11.3. Конвертер

`DurationMinutesConverter`


Значения должны:

- быть представимыми в целых минутах;
- соответствовать допустимому диапазону;

## 11.5. Примеры

- minimum_booking_notice_minutes;

## 11.8. Иная точность

Если в будущем понадобится хранение секунд или более высокой точности, это потребует отдельного решения.

# 12. Динамическая Availability

## 12.1. Основное решение

PsyWeb отказывается от предварительно создаваемых AvailabilitySlot.

## 12.2. Источники расчёта

Доступность определяется из:

- ServiceOffering;
- SpecialistBookingAccess;
- SpecialistBookingPolicy;
- SpecialistScheduleSettings;
- SpecialistTimeZoneGuard;
- WeeklyScheduleVersion;
- DateSchedule;
- ScheduleOccupancy.

## 12.3. Отсутствие статуса свободного времени

Свободное время не хранится как отдельная строка с FREE.

Оно вычисляется на основании действующего расписания и отсутствия конфликтующей занятости.

## 12.4. Предварительная доступность

Результат AvailabilityService не создаёт удержание.

## 12.5. Окончательная проверка

При создании Reservation все критические условия проверяются повторно в транзакции.

## 12.6. Последствие для схемы

Устаревшие объекты:

- availability_slot;
- slot_id в Reservation;
- slot_id в Booking;
- индексы по состояниям AvailabilitySlot

не входят в целевую модель.

# 13. Рабочее расписание

## 13.1. Режимы

Поддерживаются:

- REGULAR;
- FLOATING.

## 13.2. REGULAR

Использует версии недельного расписания.

## 13.3. WeeklyScheduleVersion

Каждая версия определяет полный недельный шаблон на период действия.

## 13.4. Периоды действия

Периоды версий одного специалиста не должны пересекаться.

## 13.5. WeeklyWorkingInterval

Хранит:

- день недели;
- локальное начало;
- локальное окончание.

## 13.6. DateSchedule

Позволяет определить расписание отдельной даты.

## 13.7. OVERRIDE

В REGULAR режиме DateSchedule OVERRIDE заменяет недельный шаблон соответствующей даты.

Пустой OVERRIDE означает закрытую дату.

## 13.8. MANUAL

В FLOATING режиме используются DateSchedule MANUAL.

Отсутствие MANUAL означает отсутствие рабочего времени на соответствующую дату.

## 13.9. Переключение режимов

Данные неактивного режима сохраняются.

## 13.10. История обязательств

Обычное изменение рабочего расписания не отменяет ACTIVE Reservation и CONFIRMED Booking.

---

# 14. Временные интервалы

## 14.1. Рабочие интервалы

Рабочий интервал определяется локальными границами.

Для обычного интервала требуется:

`startTime < endTime`

## 14.2. Пересечения

Рабочие интервалы одной применимой конфигурации не должны пересекаться.

## 14.3. Консультация

Вся консультация должна помещаться в один непрерывный рабочий интервал.

## 14.4. Перерыв

Перерыв после консультации может выходить за рабочее окно и пересекать полночь.

## 14.5. Полуоткрытая модель

Для занятости используется:

`[start, end)`

## 14.6. Соприкасающиеся интервалы

Интервалы, соприкасающиеся границами, не пересекаются.

## 14.7. Открытый вопрос

Представление окончания рабочего окна в 24:00 требует отдельного решения.

# 15. ServiceOffering

## 15.1. Назначение

ServiceOffering представляет конкретную услугу специалиста.

## 15.2. Основные данные

- title;
- description;
- durationMinutes;
- breakDurationMinutes;
- price;
- currency;
- isActive.

## 15.3. Ограничения

Длительность консультации должна быть положительной.

Перерыв не может быть отрицательным.

## 15.4. Выбор услуги

Клиент сначала выбирает ServiceOffering, затем доступное начало консультации.

## 15.5. Конкурентное изменение

При создании Reservation ServiceOffering должна быть прочитана согласованно с возможным изменением или деактивацией.

## 15.6. Исторические условия

Изменение ServiceOffering не должно автоматически менять уже созданные Reservation и Booking.

# 16. Reservation

## 16.1. Назначение

Reservation представляет временное удержание выбранного времени.

## 16.2. Статусы

Целевая модель:

```text id="07kbhn"
ACTIVE
CONFIRMED
CANCELLED
EXPIRED
```

## 16.3. Переходы

```text id="tkt60v"
ACTIVE → CONFIRMED
ACTIVE → CANCELLED
ACTIVE → EXPIRED
```

## 16.4. История

Reservation сохраняется после подтверждения, отмены или истечения.

## 16.5. TTL

expiresAt определяется системной политикой.

TTL не настраивается специалистом.

## 16.6. Snapshot

Reservation хранит исторические условия услуги и необходимые правила отмены.

## 16.7. Уникальность

Reservation не является уникальной по выбранному времени сама по себе.

Проверка занятости выполняется через ScheduleOccupancy.

---

# 17. ScheduleOccupancy

## 17.1. Назначение

ScheduleOccupancy представляет действующую занятость времени специалиста.

## 17.2. Основные поля

- id;
- reservationId;
- specialistId;
- startTime;
- occupiedUntil.

## 17.3. Интервал

```text id="dzw8lk"
[sessionStart, occupiedUntil)
```

Где:

`occupiedUntil = sessionEnd + breakDuration`

## 17.4. Создание

Occupancy создаётся атомарно с ACTIVE Reservation.

## 17.5. Подтверждение

При создании Booking Occupancy сохраняется.

## 17.6. Отмена Reservation

Occupancy удаляется.

## 17.7. Истечение Reservation

Occupancy удаляется.

## 17.8. Отмена Booking

Occupancy удаляется.

## 17.9. Очистка

После occupiedUntil строка Occupancy может быть удалена фоновым механизмом.

Это не означает удаления Reservation или Booking.

## 17.10. Источник истины

ScheduleOccupancy содержит только текущие интервалы, которые должны блокировать новые бронирования.

Она не является полной историей консультаций.

---

# 18. Запрет пересечений Occupancy

## 18.1. Основной инвариант

Для одного специалиста нельзя сохранять две пересекающиеся Occupancy.

## 18.2. PostgreSQL

Используется GiST exclusion constraint.

Концептуально:

```sql
EXCLUDE USING gist (
    specialist_id WITH =,
    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
)
```

## 18.3. btree_gist

Для сочетания equality по specialist_id и пересечения range требуется соответствующая поддержка GiST.

В целевой схеме используется:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

## 18.4. Защита

Ограничение защищает от:

- одинакового времени;
- частичного пересечения;
- полного включения интервала;
- пересечения за счёт перерыва;
- конкурентных INSERT.

## 18.5. Разные специалисты

Пересекающиеся интервалы разных специалистов разрешены.

## 18.6. Принадлежность

Occupancy должна относиться к тому же специалисту, что и Reservation.

Для этого может использоваться составной FK, предусмотренный целевой схемой.

## 18.7. Уникальность связи

Одна Reservation не должна иметь несколько независимых Occupancy.

Используется:

`UNIQUE(reservation_id)`

---

# 19. Booking

## 19.1. Назначение

Booking представляет подтверждённую запись на консультацию.

## 19.2. Создание

Booking возникает при подтверждении ACTIVE Reservation.

## 19.3. Уникальность

Одна Reservation может породить не более одной Booking.

PostgreSQL обеспечивает:

`UNIQUE(reservation_id)`

## 19.4. Статусы

Для целевой MVP-модели используются:

- CONFIRMED;
- CANCELLED.

## 19.5. Факт проведения

BookingStatus не определяет, состоялась ли консультация.

Это ответственность SessionOutcome.

## 19.6. Отмена

Допустимая отмена Booking освобождает Occupancy.

## 19.7. История

CANCELLED Booking остаётся в базе данных.

## 19.8. Перезапись

Повторное бронирование после отмены создаёт новую Reservation и новую Booking.

Старая Booking не используется повторно.

---

# 20. Исторические snapshots

## 20.1. Назначение

Snapshot сохраняет условия, действовавшие при создании Reservation.

## 20.2. Данные

Могут сохраняться:

- наименование услуги;
- длительность;
- перерыв;
- цена;
- валюта;
- clientCancellationNoticeSnapshot.

## 20.3. Источник

Snapshot формируется из проверенных данных ServiceOffering и политики специалиста.

## 20.4. Неизменяемость

Последующие изменения настроек не должны изменять уже согласованные условия.

## 20.5. Booking

Booking использует snapshot исходной Reservation.

## 20.6. Минимизация дублирования

Не следует дублировать snapshot в Booking без конкретной необходимости.

Booking сохраняет связь с Reservation.

---

# 21. Отмена и временные ограничения

## 21.1. MinimumBookingNotice

Создание Reservation требует:

`now < bookingDeadline`

## 21.2. Дедлайн

`bookingDeadline = sessionStart - effectiveMinimumBookingNotice`

## 21.3. Независимость TTL

ACTIVE Reservation может подтверждаться после bookingDeadline, если ещё не истекла по TTL.

## 21.4. ClientCancellationNotice

Используется исторический snapshot.

## 21.5. Поздняя отмена

Поздней считается отмена при:

`cancelledAt >= clientCancellationDeadline`

## 21.6. Статус

Поздняя отмена сохраняет BookingStatus.CANCELLED.

## 21.7. Начало консультации

Обычная клиентская отмена после sessionStart запрещена.

## 21.8. Повторная доступность

Освобождение Occupancy не означает автоматическую возможность новой Reservation.

Актуальные правила расписания и дедлайнов применяются повторно.

---

# 22. SessionOutcome

## 22.1. Назначение

SessionOutcome представляет результат консультации.

## 22.2. Независимость

SessionOutcome не должен заменяться BookingStatus.COMPLETED.

## 22.3. Отчёты

Клиент и специалист независимо сообщают о результате консультации.

## 22.4. Временное окно

Для MVP предусмотрено 24 часа после окончания консультации.

## 22.5. Возможные результаты

- успешно состоялась;
- не состоялась;
- спорная;
- непроверенная.

Точные значения enum определяются Outcome Domain.

## 22.6. Отсутствие ответов

Нельзя автоматически считать консультацию успешной, если ни одна сторона не ответила.

## 22.7. Административное разрешение

Противоречивые отчёты разрешаются через отдельный административный процесс.

## 22.8. Целостность

SessionOutcome связан с конкретной Booking.

---

# 23. Review

## 23.1. Основное решение

Один клиент может иметь только один Review на одного специалиста.

## 23.2. Уникальность

PostgreSQL обеспечивает:

`UNIQUE(client_id, specialist_id)`

## 23.3. Право на создание

Нужна хотя бы одна подтверждённо успешная консультация этой пары.

## 23.4. EligibilityBooking

Review ссылается на Booking, послужившую первоначальным основанием.

## 23.5. Соответствие участников

eligibilityBooking должна относиться к той же паре клиент–специалист.

Это защищается составным FK.

## 23.6. Редактирование

Клиент может изменять rating и comment.

## 23.7. Рейтинг

Средняя оценка специалиста вычисляется по актуальным Review.

Кэширование не является обязательным для MVP.

# 24. Транзакционная стратегия

## 24.1. Базовая изоляция

Используется:

`READ COMMITTED`

## 24.2. Основной принцип

Критические бизнес-изменения выполняются атомарно.

## 24.3. Reservation creation

Атомарно:

- проверка допуска;
- проверка расписания;
- проверка занятости;
- INSERT Reservation;
- INSERT Occupancy.

## 24.4. Confirmation

Атомарно:

- проверка ACTIVE и TTL;
- Reservation → CONFIRMED;
- INSERT Booking.

Occupancy сохраняется.

## 24.5. Expiration

Атомарно:

- Reservation → EXPIRED;
- DELETE Occupancy.

## 24.6. Reservation cancellation

Атомарно:

- Reservation → CANCELLED;
- cancellation metadata;
- DELETE Occupancy.

## 24.7. Booking cancellation

Атомарно:

- Booking → CANCELLED;
- cancellation metadata;
- DELETE Occupancy.

## 24.8. Administrative blocking

Атомарно:

- изменение допуска;
- отмена ACTIVE Reservation;
- удаление их Occupancy;
- административный аудит.

# 25. Блокировки PostgreSQL

## 25.1. Строковые блокировки

Используются:

- FOR SHARE;
- FOR UPDATE;
- FOR UPDATE SKIP LOCKED.

## 25.2. Calendar advisory locks

Для согласования создания Reservation и изменения расписания используются transaction-level advisory locks.

## 25.3. Ключи

Концептуальный ключ:

`(specialistId, localDate)`

## 25.4. Порядок

При необходимости блокировки нескольких дат они захватываются в стабильном порядке.

## 25.5. BookingAccess

Создание и подтверждение Reservation используют:

`SpecialistBookingAccess FOR SHARE`

Административная операция лишения допуска использует:

`SpecialistBookingAccess FOR UPDATE`

## 25.6. TimeZoneGuard

Создание Reservation использует:

`FOR SHARE`

Изменение ZoneId использует:

`FOR UPDATE`

## 25.7. BookingPolicy

Создание Reservation получает согласованный snapshot политики.

Для этого используется предусмотренная транзакционным протоколом строковая блокировка.

## 25.8. Ограничения

Локальные JVM-locks не являются достаточной защитой при нескольких экземплярах приложения.

## 25.9. Реальная проверка

Фактическое взаимодействие блокировок необходимо проверить на PostgreSQL с учётом Hibernate flush и FK.

---

# 26. Конкурентность и database constraints

## 26.1. Принцип

Проверка:

`check → insert`

не является самостоятельной гарантией отсутствия конфликтов.

## 26.2. Occupancy

Конфликтующие вставки защищаются GiST exclusion constraint.

## 26.3. Booking

Повторное создание Booking защищается UNIQUE(reservation_id).

## 26.4. Review

Повторное создание Review защищается UNIQUE(client_id, specialist_id).

## 26.5. Reservation TTL

Переходы одной Reservation согласуются строковой блокировкой.

## 26.6. Expiration Scheduler

Для пакетной обработки применяется:

`FOR UPDATE SKIP LOCKED`

## 26.7. Изменение расписания

Calendar advisory locks предотвращают создание новых Reservation на основании неконсистентной конфигурации.

## 26.8. Предметные ошибки

Известные нарушения ограничений PostgreSQL могут преобразовываться в доменные исключения.

Нельзя маскировать неизвестные инфраструктурные ошибки под ожидаемый конфликт бронирования.

# 27. Работа со временем

## 27.1. Абсолютные моменты

Используются:

`Instant` в Java и `TIMESTAMPTZ` в PostgreSQL.

## 27.2. Локальное расписание

Используются:

- LocalDate;
- LocalTime;
- ZoneId.

## 27.3. Часовой пояс

Текущий ZoneId специалиста хранится отдельно.

## 27.4. Смена ZoneId

Существующие абсолютные времена Reservation и Booking не изменяются.

## 27.5. DST

Новое начало консультации должно иметь ровно один допустимый UTC offset.

## 27.6. Неоднозначное время

Начало консультации в DST overlap запрещается.

## 27.7. Несуществующее время

Начало консультации в DST gap запрещается.

## 27.8. Временная точность

Временные значения сохраняются с точностью, необходимой для корректной проверки дедлайнов.

## 27.9. Clock

Для бизнес-проверок используется внедряемый Clock.

# 28. Удаление данных и история

## 28.1. Основное правило

Исторические бизнес-сущности не удаляются автоматически после завершения соответствующего процесса.

## 28.2. Reservation

Сохраняется после:

- CONFIRMED;
- CANCELLED;
- EXPIRED.

## 28.3. Booking

Сохраняется после CANCELLED и завершения консультации.

## 28.4. SessionOutcome

Сохраняется для истории результата и разрешения споров.

## 28.5. Review

Сохраняется как отзыв о специалисте.

## 28.6. Occupancy

Может удаляться, когда больше не должна блокировать время.

## 28.7. ON DELETE

Для исторически значимых связей предпочтительно ON DELETE RESTRICT.

CASCADE используется только для действительно зависимых дочерних данных, удаление которых согласовано с бизнес-моделью.

# 29. Индексирование

## 29.1. Принцип

Индексы создаются для:

- защиты инвариантов;
- поддержки важных запросов;
- обеспечения приемлемой производительности.

## 29.2. Основные направления

- User email;
- активные услуги специалиста;
- расписание дат;
- версии недельного графика;
- Occupancy специалиста по времени;
- ACTIVE Reservation по expiresAt;
- Booking клиента;
- Booking специалиста;
- Review специалиста.

## 29.3. Дублирование

UNIQUE и exclusion constraints уже создают соответствующие индексы.

Не следует создавать их полные дубликаты.

## 29.4. Анализ

Реальная эффективность индексов проверяется через:

`EXPLAIN ANALYZE`

## 29.5. Избыточные индексы

Индексы ускоряют чтение, но увеличивают стоимость INSERT, UPDATE и DELETE.

Создавать их без подтверждённой необходимости не следует.

# 30. Flyway

## 30.1. Назначение

Flyway управляет последовательными изменениями PostgreSQL-схемы.

## 30.2. Неизменяемость истории

Уже применённые миграции нельзя:

- редактировать;
- переименовывать;
- переставлять;
- использовать повторно для другой архитектуры.

## 30.3. Исходная миграционная база

В исходной документации зафиксированы миграции:

```text id="w0mw0b"
V1
V2
V3
V4
V5
V6
V7
V8
V9
V10
V11
V12
```

## 30.4. Последняя указанная миграция

`V12__add_cancellation_metadata.sql`

Она относится к прежней модели Reservation, Booking и AvailabilitySlot.

## 30.5. Следующая версия

Если актуальная ветка приложения действительно заканчивается на V12, следующая миграция должна иметь версию V13.

Перед реализацией необходимо проверить фактическую директорию Flyway.

## 30.6. Forward migrations

Все новые изменения выполняются через новые миграции.

Это относится к:

- новым таблицам;
- новым FK;
- изменению CHECK;
- изменению UNIQUE;
- удалению старых колонок;
- замене AvailabilitySlot на ScheduleOccupancy;
- изменению типов данных;
- индексам.

## 30.7. Ошибки checksum

Нельзя исправлять несовпадение Flyway checksum путём произвольного переписывания применённой миграции.

## 30.8. Целевая DDL

Проектный Relational Schema не является готовой последовательностью миграций.

Для существующей базы необходимо разработать порядок перехода от фактической схемы к целевой.

# 31. Стратегия перехода от прежней схемы

## 31.1. Исходное состояние

Первоначальная модель использует AvailabilitySlot.

## 31.2. Целевое состояние

Новая модель использует:

- ServiceOffering;
- Schedule;
- Reservation;
- Booking;
- ScheduleOccupancy.

## 31.3. Разделение этапов

Необходимо отдельно:

1. Проверить существующую схему.
2. Проверить данные.
3. Определить зависимости от AvailabilitySlot.
4. Создать новые таблицы.
5. Перенести необходимые настройки.
6. Обновить связи Reservation и Booking.
7. Реализовать новый сервисный слой.
8. Проверить ограничения и транзакции.
9. Удалить устаревшие объекты.

## 31.4. Порядок

Точный порядок должен учитывать внешние ключи и совместимость приложения.

## 31.5. Отсутствие production-данных

Если production-данных нет, допускается упрощённая миграционная стратегия для локальной разработки.

Однако это не отменяет требований к корректности Flyway.

## 31.6. Проверка данных

Перед удалением старых таблиц необходимо определить, требуется ли сохранение имеющихся локальных данных.

## 31.7. Запрет частичного состояния

Нельзя оставлять приложение, в котором новая Booking продолжает ссылаться на устаревший slot_id без согласованной модели.

- `refresh_sessions`;
- `refresh_tokens`.

### RefreshSession

Содержит:

- id — UUIDv4 primary key;
- user_id — BIGINT foreign key;
- created_at — TIMESTAMPTZ;
- expires_at — TIMESTAMPTZ;
- revoked_at — TIMESTAMPTZ, nullable;
- last_used_at — TIMESTAMPTZ, nullable.

Сессия действует 7 дней с момента успешного login.

Rotation не продлевает абсолютный срок действия сессии.

### RefreshToken

Содержит:

- id — UUIDv4 primary key;
- session_id — UUID foreign key;
- token_hash — SHA-256 fingerprint;
- issued_at — TIMESTAMPTZ;
- consumed_at — TIMESTAMPTZ, nullable.

Исходное значение refresh token не сохраняется в PostgreSQL.

Срок действия токена определяется через связанную RefreshSession. Дублировать expires_at в RefreshToken не требуется.

### Ограничения

В рамках одной сессии допускается не более одного неиспользованного refresh token.

token_hash должен быть уникальным.

Каждая успешная rotation атомарно:

1. Проверяет актуальное состояние пользователя, сессии и токена.
2. Помечает предыдущий токен использованным.
3. Создаёт новое поколение токена.
4. Сохраняет изменения в PostgreSQL.

Повторное использование ранее потреблённого токена приводит к отзыву затронутой сессии.

Отзыв при replay должен фиксироваться до формирования HTTP-ошибки.

### История и очистка

История поколений сохраняется до завершения срока жизни сессии и ещё 24 часа после него.

После этого данные удаляются периодической cleanup-задачей.

### Конкурентность

Для согласованных изменений используются транзакции PostgreSQL, строковые блокировки и database constraints.

При необходимости нескольких блокировок применяется порядок:

```text
User → RefreshSession → RefreshToken
```

Точные индексы, Flyway-миграции и стратегия блокировок проверяются при реализации.

Подробная модель описана в:

# 35. Итог

База данных PsyWeb строится на PostgreSQL с приоритетом транзакционной согласованности.

Основные решения:

- реляционная модель с явными владельцами данных;
- единые соглашения именования;
- ограничения FK, UNIQUE и CHECK;
- отказ от предварительно созданных AvailabilitySlot;
- динамический расчёт Availability;
- раздельная конфигурация специалиста;
- версионируемый недельный график;
- отдельное расписание конкретных дат;
- временное удержание через Reservation и ScheduleOccupancy;
- GiST exclusion constraint против пересечений;
- сохранение исторических snapshots;
- одна Booking на Reservation;
- SessionOutcome как самостоятельная модель результата;
- один Review на пару клиент–специалист;
- PostgreSQL row locks и advisory locks;
- неизменяемая история Flyway;
- проверка критических инвариантов на реальном PostgreSQL.
- новые самостоятельные сущности используют UUIDv4, существующие BIGINT-идентификаторы сохраняются;
- refresh-token lifecycle реализуется через RefreshSession и RefreshToken с атомарной rotation, хранением SHA-256 хешей и историей использованных токенов.


**Статус: DRAFT — целевая модель согласована концептуально, SQL и миграции должны быть проверены перед реализацией.**
