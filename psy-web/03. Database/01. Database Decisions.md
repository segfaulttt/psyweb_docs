## Overview

This section defines the core design decisions for the relational database structure of the PsyWeb platform. The database is designed to support a transactional booking-based marketplace system with strict consistency guarantees around scheduling and appointments.

The primary focus is correctness of booking operations, data integrity, and predictable relational modeling aligned with the domain architecture of the system.

---

## 1. Database Type

The system uses **PostgreSQL** as the primary relational database.

### Rationale:

- Strong ACID compliance required for booking consistency
- Robust support for constraints and transactions
- Mature indexing capabilities for time-based queries (availability slots)
- Suitable for relational domain model with strict integrity rules

---

## 2. Data Modeling Approach

The database follows a **relational-first domain-driven design approach**:

- Each core domain entity is mapped to a dedicated table
- Relationships are enforced via foreign keys
- Business invariants are enforced primarily at the service layer, with partial DB-level constraints where applicable

---

## 3. Naming Conventions

To ensure consistency between database schema and JPA entities, the following naming rules are applied:

### Tables

- `snake_case`
- singular form

Examples:

- `user`
- `specialist_profile`
- `availability_slot`
- `booking`

### Columns

- `snake_case`

Examples:

- `created_at`
- `start_time`
- `password_hash`

### Primary Keys

- Standardized as:
    - `id` (primary key)
- Foreign keys:
    - `<entity>_id` (e.g., `user_id`, `slot_id`)

### Enums

- Stored as strings or PostgreSQL enums (decision depends on implementation stage)
- Values in `UPPER_SNAKE_CASE`

Examples:

- `ACTIVE`
- `CANCELLED`
- `BOOKED`

## 5. Core Domain Consistency Rule

The Booking system is the transactional core of the platform.

Critical business state must remain protected even when multiple requests execute concurrently.

Application-level validation is required for business semantics and meaningful errors, but it must not be the only protection for persistent invariants that can be violated by concurrent requests.

---

## 6. Schema and Migration Consistency Constraints

Only business-critical persistence guarantees are treated as architectural constraints.

Not every technical index or query optimization is part of the domain contract.

### 6.1 User Email Normalization and Uniqueness

Email is a canonical account identifier.

The normalization policy is already defined and implemented.

Before persistence or lookup, email is normalized as:

```text
trim surrounding whitespace
→ lowercase using Locale.ROOT
→ validate normalized email
```

Example:

```text
"  User.Name@Example.COM  "
→
"user.name@example.com"
```

The application stores only the canonical normalized value.

The same normalization policy is used for:

- User creation;
- email changes;
- lookup by email;
- future authentication/login lookup.

Provider-specific transformations are intentionally not applied.

For example, PsyWeb does not:

- remove dots from the local part;
- remove `+alias` suffixes;
- attempt to merge provider-specific aliases.

Therefore:

```text
john+test@gmail.com
```

and:

```text
john@gmail.com
```

remain distinct email identities.

### Application Guarantee

The current User domain centralizes normalization in:

```text
User.normalizeEmail(...)
```

The normalization logic must not be independently reimplemented by different services.

### Database Guarantee

The database persists the canonical lowercase representation.

The existing:

```text
UNIQUE(email)
```

constraint therefore protects uniqueness of canonical stored email values.

Migration:

```text
V7__add_email_normalization_constraint.sql
```

also adds the database guard:

```sql
CHECK (email = lower(email))
```

This prevents accidentally persisting uppercase email values through a path that bypasses normal application construction or lookup logic.

Application normalization and database constraints therefore protect different parts of the same invariant:

```text
application
→ canonicalizes input

database
→ rejects non-lowercase persisted values
→ enforces uniqueness of canonical values
```

---

### 6.2 One ACTIVE Reservation per AvailabilitySlot

A slot may have multiple historical Reservations.

Only one Reservation may be `ACTIVE` for a slot at a time.

The database enforces this invariant with a partial uniqueness constraint equivalent to:

`UNIQUE reservation(slot_id) WHERE status = 'ACTIVE'`

This protects Reservation creation even if concurrent application requests reach persistence unexpectedly.

---

### 6.3 One Booking per Confirmed Reservation

A Reservation may produce at most one Booking.

The database enforces:

`UNIQUE booking(reservation_id)`

Repeated or concurrent confirmation attempts therefore cannot create multiple Booking records from the same Reservation.

---

### 6.4 One CONFIRMED Booking Occupancy per AvailabilitySlot

An AvailabilitySlot may have multiple historical Booking records after cancellation and rebooking.

Therefore:

`booking.slot_id`

must not be globally unique.

However, only one current confirmed Booking may occupy the slot.

The database must therefore enforce the equivalent invariant:

`UNIQUE booking(slot_id) WHERE status = 'CONFIRMED'`

Historical `CANCELLED` Bookings do not participate in this uniqueness rule.

---

### 6.5 Enum and State Value Integrity

Persisted domain status fields must reject values outside their documented state models.

Where enum-like values are stored as `VARCHAR`, database `CHECK` constraints protect the valid value set.

Examples include:

* User role and status;
* Specialist approval status;
* AvailabilitySlot status;
* Reservation status;
* Booking status.

Application enums and database constraints must be changed together when a state model changes.

A new Java enum value must not be deployed while the database still rejects it, and an obsolete database value must not remain accepted merely because application code stopped using it.

---

### 6.6 Duration Persistence

Business rules may use `java.time.Duration` in the domain model when the value represents a configurable amount of elapsed time rather than an absolute timestamp.

The current persistence convention stores supported Duration values as whole minutes.

Java representation:

```text
java.time.Duration
```

Database representation:

```text
INTEGER minutes
```

JPA conversion is centralized through:

```text
DurationMinutesConverter
```

The converter maps:

```text
Duration
↔
Integer whole minutes
```

Sub-minute precision is not supported by this persistence contract.

Domain values using this converter must therefore be representable as a whole number of minutes.

Current examples include Specialist settings:

```text
minimumBookingNotice
→ minimum_booking_notice_minutes

clientCancellationNotice
→ client_cancellation_notice_minutes
```

Migration:

```text
V9__add_specialist_booking_notice_settings.sql
```

persists both values as non-null `INTEGER` columns and adds non-negative CHECK constraints.

The current Specialist domain additionally validates that these Duration values:

- are not null;
- are not negative;
- contain whole minutes;
- fit the supported Integer-minute persistence range.

The database representation is intentionally explicit about units through the `_minutes` column suffix.

New Duration-backed fields following the same convention should not use ambiguous column names that hide the persisted unit.

If a future requirement needs sub-minute precision or a range that cannot be represented safely by this contract, that field requires an explicit persistence decision rather than silently reusing this converter.

---

### 6.7 Availability and Booking Concurrency

Concurrency-sensitive scheduling correctness must not depend solely on:

`check → then insert/update`

logic in application code.

The persistence model must provide database-backed protection for critical scheduling conflicts.

This includes:

* one ACTIVE Reservation per slot;
* one CONFIRMED Booking occupancy per slot;
* safe Reservation confirmation;
* prevention of concurrently created overlapping active AvailabilitySlots for the same specialist.

The exact database mechanism for overlapping-slot creation may be implemented through an exclusion constraint or another transactionally safe PostgreSQL strategy.

The required architectural guarantee is that two concurrent transactions cannot both successfully persist conflicting active specialist availability.

---

### 6.8 Flyway Migration Immutability

Flyway migrations that have already been applied are immutable history.

Applied migrations:

`V1` through `V6`

must not be edited, renamed, reordered, or repurposed to represent later architectural changes.

Any schema change discovered after those migrations were applied must be introduced through a new migration.

For example:

`V7__...sql`

or a later version.

This includes:

* adding or changing constraints;
* changing enum-compatible CHECK rules;
* adding columns;
* removing obsolete columns;
* changing uniqueness guarantees;
* changing indexes that enforce business invariants.

Documentation may describe the current target schema, but implementation must reach that target through new forward migrations rather than rewriting previously applied history.

Flyway checksum failures must not be solved by casually modifying already applied migration files.

---

## 7. Transaction Strategy

Consistency-sensitive booking and availability operations execute inside explicit service-level transactions.

The transaction model is combined with database constraints and locking where required.

Important operations include:

* Reservation creation and `FREE → RESERVED`;
* Reservation confirmation, Booking creation, and `RESERVED → BOOKED`;
* Reservation cancellation or expiration and `RESERVED → FREE`;
* Booking cancellation and the corresponding slot release;
* specialist availability removal;
* concurrency-sensitive AvailabilitySlot creation.

Consistency is prioritized over accepting conflicting concurrent writes.

A business operation must either persist its complete valid state transition or leave no partial state committed.

---

## 8. Extensibility Considerations

The database design is prepared for future extensions:

- Chat system (message threads linked to bookings)
- Event-driven notifications (no direct DB dependency)
- Payment integration (external system, no internal schema coupling)
- Video consultation integration (future scheduling extensions)

---

## Summary

The database design prioritizes:

- Strong consistency for booking operations
- Clear relational structure aligned with domain model
- Predictable naming and mapping to Spring JPA entities
- Future extensibility without schema disruption
