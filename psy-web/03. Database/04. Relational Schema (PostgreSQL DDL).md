# Relational Schema

## Scope

This document distinguishes:

```text
current effective PostgreSQL schema
```

from:

```text
approved target / backlog schema changes
```

The current section reflects the effective database state produced by the already-applied Flyway migration chain in `PsyWeb/main`.

Applied Flyway migrations are immutable.

Any schema correction or extension must be introduced through a new forward migration.

The detailed migration-baseline walkthrough is owned by the dedicated migration documentation task and is not duplicated here.

# Current Effective Schema

## USERS

Current physical table:

```sql
users
```

Effective structure:

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,

    email VARCHAR(255) NOT NULL UNIQUE,

    password_hash VARCHAR(255) NOT NULL,

    role VARCHAR(50) NOT NULL
        CHECK (role IN ('ADMIN', 'CLIENT', 'SPECIALIST')),

    status VARCHAR(50) NOT NULL
        CHECK (status IN ('ACTIVE', 'BLOCKED')),

    created_at TIMESTAMP NOT NULL DEFAULT now(),

    CHECK (email = lower(email))
);
```

The application canonicalizes email before persistence:

```text
trim
→ lowercase using Locale.ROOT
→ validate
```

No provider-specific transformations such as dot removal or `+alias` removal are performed.

The database protects:

```text
UNIQUE(email)
```

and rejects non-lowercase stored values.

# SPECIALISTS

Current physical table:

```sql
specialists
```

Effective structure:

```sql
CREATE TABLE specialists (
    user_id BIGINT PRIMARY KEY
        REFERENCES users(id)
        ON DELETE CASCADE,

    first_name VARCHAR(255) NOT NULL,

    last_name VARCHAR(255) NOT NULL,

    approval_status VARCHAR(50) NOT NULL
        CHECK (
            approval_status IN (
                'PENDING',
                'APPROVED',
                'REJECTED',
                'SUSPENDED'
            )
        ),

    minimum_booking_notice_minutes INTEGER NOT NULL
        CHECK (minimum_booking_notice_minutes >= 0),

    client_cancellation_notice_minutes INTEGER NOT NULL
        CHECK (client_cancellation_notice_minutes >= 0)
);
```

`Specialist.user_id` is the shared primary key with User.

The current Java model stores:

```text
minimumBookingNotice
clientCancellationNotice
```

as:

```text
java.time.Duration
```

while PostgreSQL stores whole minutes.

Conversion is handled through:

```text
DurationMinutesConverter
```

The current Specialist lifecycle values are:

```text
PENDING
APPROVED
REJECTED
SUSPENDED
```

Current implemented transitions are:

```text
PENDING → APPROVED
PENDING → REJECTED
REJECTED → PENDING
APPROVED → SUSPENDED
SUSPENDED → APPROVED
```

Moderation reasons and moderation history are not stored directly on Specialist.

# SLOTS

Current physical table:

```sql
slots
```

Effective structure:

```sql
CREATE TABLE slots (
    id BIGSERIAL PRIMARY KEY,

    specialist_id BIGINT NOT NULL
        REFERENCES specialists(user_id),

    start_time TIMESTAMP NOT NULL,

    end_time TIMESTAMP NOT NULL,

    availability_status VARCHAR(20) NOT NULL
        CHECK (
            availability_status IN (
                'FREE',
                'RESERVED',
                'CANCELLED',
                'BOOKED'
            )
        )
);
```

Current supporting index:

```sql
CREATE INDEX idx_slots_specialist_time
ON slots(specialist_id, start_time, end_time);
```

The current persistence model does not contain:

```text
minimum_booking_notice_minutes
```

on the Slot itself.

The optional per-slot booking-notice override is approved target/backlog functionality.

# RESERVATIONS

Current physical table:

```sql
reservations
```

Effective structure:

```sql
CREATE TABLE reservations (
    id BIGSERIAL PRIMARY KEY,

    client_id BIGINT NOT NULL
        REFERENCES users(id),

    slot_id BIGINT NOT NULL
        REFERENCES slots(id),

    status VARCHAR(20) NOT NULL
        CHECK (
            status IN (
                'ACTIVE',
                'CONFIRMED',
                'EXPIRED',
                'CANCELLED'
            )
        ),

    created_at TIMESTAMP NOT NULL,

    expires_at TIMESTAMP NOT NULL
);
```

Current ACTIVE Reservation exclusivity is protected by:

```sql
CREATE UNIQUE INDEX unique_active_reservation_slot
ON reservations(slot_id)
WHERE status = 'ACTIVE';
```

Current lookup support includes:

```sql
CREATE INDEX idx_reservation_client
ON reservations(client_id);
```

A slot may therefore retain historical Reservations while allowing at most one:

```text
ACTIVE
```

Reservation at a time.

Current Reservation persistence does not yet store the full target cancellation metadata such as:

```text
cancelledAt
cancellationInitiator
cancellationReason
```

where required by future cancellation workflows.

The effective current schema contains:

```sql
CREATE TABLE bookings (
    id BIGSERIAL PRIMARY KEY,

    client_id BIGINT NOT NULL
        REFERENCES users(id),

    slot_id BIGINT NOT NULL UNIQUE
        REFERENCES slots(id),

    specialist_id BIGINT NOT NULL
        REFERENCES specialists(user_id),

    reservation_id BIGINT NOT NULL
        REFERENCES reservations(id),

    status VARCHAR(20) NOT NULL
        CHECK (
            status IN (
                'CONFIRMED',
                'CANCELLED',
                'COMPLETED',
                'NO_SHOW'
            )
        ),

    created_at TIMESTAMP NOT NULL DEFAULT now(),

    cancelled_at TIMESTAMP
);
```

Important current-state facts:

```text
slot_id
→ permanently UNIQUE in the currently applied schema

reservation_id
→ foreign key, but not yet UNIQUE

BookingStatus
→ CONFIRMED / CANCELLED / COMPLETED / NO_SHOW
```

The current Java Booking model also still contains legacy operations:

```text
CONFIRMED → COMPLETED
CONFIRMED → NO_SHOW
```

These are current implementation facts, not the approved target lifecycle.

# Target Specialist Moderation History

Current Specialist status remains the source of truth for the current professional lifecycle state.

Historical administrative actions are stored separately in target:

```text
SpecialistModerationAction
```

Conceptual persistence model:

```sql
CREATE TABLE specialist_moderation_action (
    id BIGSERIAL PRIMARY KEY,

    specialist_id BIGINT NOT NULL
        REFERENCES specialists(user_id),

    admin_id BIGINT
        REFERENCES users(id),

    action_type VARCHAR(50) NOT NULL
        CHECK (
            action_type IN (
                'APPROVED',
                'REJECTED',
                'RESUBMITTED',
                'SUSPENDED',
                'REINSTATED'
            )
        ),

    reason_code VARCHAR(50),

    comment TEXT,

    created_at TIMESTAMP NOT NULL
);
```

Target reason taxonomy:

```text
DOCUMENT_ISSUE
REQUIREMENTS_NOT_MET
POLICY_VIOLATION
OTHER
```

Target business rules include:

```text
REJECTED
SUSPENDED
→ reason_code required
```

and:

```text
reason_code = OTHER
→ nonblank comment required
```

For:

```text
RESUBMITTED
```

`admin_id` may be null because the action may be initiated by the Specialist.

For administrative decisions, `admin_id` is required.

Moderation records are immutable historical records.

New moderation actions append rows rather than rewriting previous decisions.

# Target Specialist Suspension Cascade

The current:

```text
APPROVED → SUSPENDED
```

Specialist state transition is already implemented.

The complete cascade is target/backlog.

Suspension uses the operation timestamp:

```text
suspendedAt
```

as its temporal boundary.

Only slots satisfying:

```text
slot.startTime > suspendedAt
```

are considered future for this workflow.

At equality:

```text
slot.startTime == suspendedAt
```

the session is treated as already started and is not cancelled by suspension.

The target cascade is:

```text
FREE slot
→ CANCELLED

RESERVED slot
→ CANCELLED
ACTIVE Reservation
→ CANCELLED

BOOKED slot
→ CANCELLED
CONFIRMED Booking
→ CANCELLED
```

Target cancellation history records:

```text
cancelledAt = suspendedAt
cancellationInitiator = ADMIN
cancellationReason = SPECIALIST_SUSPENDED
```

The detailed persistence shape of cancellation metadata is introduced by its owning implementation work through forward migrations.

A confirmed Reservation is not rewritten merely because its resulting Booking is later cancelled by suspension.

Cancelled Slots remain historical and are not reactivated during:

```text
SUSPENDED → APPROVED
```

# Target Per-Slot Booking Notice Override

Current persistence stores only Specialist-level:

```text
minimum_booking_notice_minutes
```

The approved target additionally allows a nullable Slot override.

Conceptual addition:

```sql
ALTER TABLE slots
ADD COLUMN minimum_booking_notice_minutes INTEGER
    CHECK (
        minimum_booking_notice_minutes IS NULL
        OR minimum_booking_notice_minutes >= 0
    );
```

Effective policy:

```text
slot.minimumBookingNotice
when non-null

otherwise

specialist.minimumBookingNotice
```

The target booking deadline is:

```text
bookingDeadline =
slot.start_time - effectiveMinimumBookingNotice
```

A new Reservation is allowed only while:

```text
now < bookingDeadline
```

This column and enforcement are not part of the current Slot persistence model.

# Target Availability Overlap Constraint

Current application code performs an overlap pre-check using:

```text
newStart < existingEnd
&&
newEnd > existingStart
```

which corresponds to half-open intervals:

```text
[start_time, end_time)
```

However, the complete concurrency-safe database guarantee is target/backlog.

Target active statuses are:

```text
FREE
RESERVED
BOOKED
```

Historical:

```text
CANCELLED
```

slots do not participate.

The approved PostgreSQL strategy uses:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

and a partial GiST exclusion constraint.

Using the current physical schema names, the intended meaning is:

```sql
ALTER TABLE slots
ADD CONSTRAINT no_overlapping_active_slots
EXCLUDE USING gist (
    specialist_id WITH =,
    tsrange(start_time, end_time, '[)') WITH &&
)
WHERE (
    availability_status IN (
        'FREE',
        'RESERVED',
        'BOOKED'
    )
);
```

This permits adjacency:

```text
10:00–11:00
11:00–12:00
```

while rejecting true overlaps for the same Specialist.

Slots owned by different Specialists may overlap.

The database conflict must eventually be translated to:

```text
SlotOverlapException
```

instead of leaking a raw persistence exception.

This protection requires a new forward migration.

# Target AvailabilitySlot → Booking History

Approved target behavior allows one Slot to retain multiple historical Bookings after cancellation and later rebooking.

Therefore permanent:

```text
UNIQUE(bookings.slot_id)
```

is incompatible with the target model.

The target schema must allow historical rows while protecting only current Booking occupancy.

Conceptually:

```sql
CREATE UNIQUE INDEX unique_confirmed_booking_slot
ON bookings(slot_id)
WHERE status = 'CONFIRMED';
```

The existing permanent slot uniqueness must be removed through a forward migration before this model can work.

Applied migration history must not be rewritten.

# Target SessionOutcome

The post-session model is approved target/backlog functionality.

Conceptual target table:

```sql
CREATE TABLE session_outcome (
    id BIGSERIAL PRIMARY KEY,

    booking_id BIGINT NOT NULL UNIQUE
        REFERENCES bookings(id),

    resolution_status VARCHAR(20) NOT NULL
        CHECK (
            resolution_status IN (
                'PENDING',
                'DISPUTED',
                'RESOLVED',
                'UNVERIFIED'
            )
        ),

    final_outcome VARCHAR(20)
        CHECK (
            final_outcome IS NULL
            OR final_outcome IN (
                'OCCURRED',
                'DID_NOT_OCCUR'
            )
        ),

    final_reason VARCHAR(50),

    created_at TIMESTAMP NOT NULL,

    reporting_deadline TIMESTAMP NOT NULL,

    disputed_at TIMESTAMP,

    finalized_at TIMESTAMP
);
```

Target invariants:

```text
PENDING / DISPUTED
→ final_outcome = null
→ finalized_at = null

RESOLVED
→ final_outcome != null
→ finalized_at != null

UNVERIFIED
→ final_outcome = null
→ final_reason = null
→ finalized_at != null

final_reason
→ allowed only when final_outcome = DID_NOT_OCCUR
```

The final implementation should enforce these rules through JPA/service validation and database CHECK constraints where practical.

Conceptual target table:

```sql
CREATE TABLE session_report (
    id BIGSERIAL PRIMARY KEY,

    session_outcome_id BIGINT NOT NULL
        REFERENCES session_outcome(id),

    actor_type VARCHAR(20) NOT NULL
        CHECK (
            actor_type IN (

            reported_outcome IN (
                'OCCURRED',
```

```text
author_id
```

in the approved SessionReport model.


```text

```

```text

OTHER
```

```text

→ reason = null
→ details = null
```

```text
DID_NOT_OCCUR
→ reason required
```

```text
reason = OTHER
→ nonblank details required
```

Reports are immutable after insertion.

# Target Review

Review persistence is approved target/backlog functionality.

Review belongs to the Client-Specialist relationship rather than to a particular Booking.

Conceptual target table:

```sql
CREATE TABLE reviews (
    id BIGSERIAL PRIMARY KEY,

    client_id BIGINT NOT NULL
        REFERENCES users(id),

    specialist_id BIGINT NOT NULL
        REFERENCES specialists(user_id),

    rating INTEGER NOT NULL
        CHECK (rating BETWEEN 1 AND 5),

    comment TEXT,

    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,

    CONSTRAINT uq_reviews_client_specialist
        UNIQUE (client_id, specialist_id)
);
```

The target Review table intentionally does not contain:

```text
booking_id
```

Review creation eligibility is derived from historical Booking and SessionOutcome data.

The persistence model does not store a dedicated eligibility flag.

For the MVP, Specialist rating is also derived from Review rows rather than stored as `rating_avg`.

Conceptually:

```sql
SELECT
    AVG(rating),
    COUNT(*)
FROM reviews
WHERE specialist_id = ?;
```

When no Reviews exist:

```text
count = 0
average = null
```

Display rounding is presentation behavior and does not change stored ratings.

A future cached rating or projection may be introduced as an optimization, but Review remains the source of truth.

This target schema must be introduced only through a future forward Flyway migration.

Applied migration history must not be rewritten.
