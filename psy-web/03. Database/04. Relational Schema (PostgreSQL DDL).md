
# 04. Реляционная схема PsyWeb (PostgreSQL DDL)

**Проект:** PsyWeb  
**СУБД:** PostgreSQL 16+  
**Архитектура:** Spring Boot Modular Monolith  
**Миграции:** Flyway  
**Статус:** DRAFT — целевая структура данных

---

# 1. Назначение

Документ описывает целевую реляционную модель PsyWeb.

В нём определяются:

- структура таблиц;
- первичные и внешние ключи;
- ограничения целостности;
- уникальность;
- индексы;
- временные интервалы;
- хранение исторических условий;
- разделение конфигурации специалиста;
- защита конкурентных бронирований;
- связи между бизнес-модулями.

SQL является проектным DDL.

До создания окончательных Flyway-миграций необходимо проверить его исполнение на PostgreSQL и согласовать с текущими JPA-сущностями.

---

# 2. Основные архитектурные решения

## 2.1. Динамическая доступность

PsyWeb не хранит заранее созданные AvailabilitySlot.

Доступность рассчитывается из:

- ServiceOffering;
- WeeklyScheduleVersion;
- WeeklyWorkingInterval;
- DateSchedule;
- DateScheduleInterval;
- ScheduleOccupancy;
- настроек специалиста.

## 2.2. Действующая занятость

ScheduleOccupancy содержит только временные интервалы, которые в данный момент должны блокировать новые записи.

При освобождении интервала строка удаляется.

Reservation и Booking сохраняют историю.

## 2.3. Исторические условия

Reservation содержит snapshot условий консультации.

Изменение ServiceOffering и правил специалиста не меняет уже согласованные условия.

## 2.4. Разделение конфигурации

Для независимых блокировок используются отдельные физические таблицы:

- specialist_booking_access;
- specialist_booking_policies;
- specialist_schedule_settings;
- specialist_time_zone_guards.

## 2.5. Review

Один клиент может иметь только один Review на одного специалиста.

Отзыв создаётся после подтверждённо успешной консультации и может редактироваться.

## 2.6. Временная модель

Абсолютные моменты представлены TIMESTAMPTZ.

Рабочий график представлен локальными DATE и TIME.

## 2.7. Auth

Для долгоживущей аутентификации используются две отдельные таблицы:

- refresh_sessions;
- refresh_tokens.

RefreshSession представляет отдельный сеанс входа пользователя.

RefreshToken представляет одно поколение refresh token в рамках этой сессии.

Срок RefreshSession составляет 7 дней с момента login и не продлевается при rotation.

В базе сохраняются только SHA-256 хеши исходных refresh tokens.

Для новых самостоятельных сущностей Auth используются UUIDv4.

# 3. Соглашения PostgreSQL

## 3.1. Идентификаторы

Для новых самостоятельных сущностей целевой архитектуры используются UUIDv4 primary keys.

В PostgreSQL применяется тип:

```sql
UUID
```

UUIDv4 может генерироваться на стороне Java.

При таком подходе приложение передаёт готовый UUID при INSERT, а колонка PostgreSQL не нуждается в DEFAULT-генераторе.

Существующие сущности с BIGINT сохраняют свои идентификаторы и действующую стратегию генерации.

Для них может использоваться:

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

Массовая миграция существующих таблиц на UUID не предусматривается.

Тип внешнего ключа соответствует типу первичного ключа связанной сущности.

Пример:

```text
User.id: BIGINT
RefreshSession.id: UUID
RefreshSession.user_id: BIGINT
RefreshToken.id: UUID
RefreshToken.session_id: UUID
```

Применение UUID не заменяет проверок ownership и authorization.

## 3.2. Именование

- snake_case;
- таблицы во множественном числе;
- первичные ключи id;
- внешние ключи с суффиксом _id;
- абсолютное время с суффиксом _at;
- длительности с суффиксом _minutes.

## 3.3. ENUM

Для MVP используются VARCHAR и CHECK.

Если полный набор значений ещё не утверждён, конкретный CHECK не фиксируется преждевременно.

## 3.4. Удаление

Исторические бизнес-объекты не удаляются автоматически вместе с родительскими сущностями.

По умолчанию применяется ON DELETE RESTRICT.

ON DELETE CASCADE допустим для вспомогательных дочерних элементов, жизненный цикл которых полностью зависит от родителя.

История RefreshToken сохраняется в пределах установленной политики retention.

Удаление RefreshSession вместе с её дочерними RefreshToken допускается только в рамках согласованного cleanup-процесса.

## 3.5. Расширения

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

Расширение используется совместно с GiST exclusion constraints.

# 4. Users

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    email VARCHAR(255) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,

    role VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    email_verified_at TIMESTAMPTZ,

    CONSTRAINT uq_users_email
        UNIQUE (email),

    CONSTRAINT chk_users_role
        CHECK (role IN (
            'CLIENT',
            'SPECIALIST',
            'ADMIN'
        )),

    CONSTRAINT chk_users_status
        CHECK (status IN (
            'ACTIVE',
            'BLOCKED',
            'PENDING'
        ))
);
```

## 4.1. Инварианты

Email должен быть нормализован согласно единой политике приложения.

UNIQUE(email) обеспечивает буквальную уникальность хранимого значения.

Регистронезависимая уникальность требует отдельной стратегии.

## 4.2. Security

Password hash не должен хранить пароль в открытом виде.

Для проверки пользовательских паролей в целевой Auth-модели применяется Argon2id.

Проверка паролей и токенов относится к Auth.

User сохраняет владение password_hash и состоянием аккаунта.

## 6.3. Booking configuration

Настройки записи и часовой пояс не размещаются непосредственно в этой таблице.

Это позволяет независимо блокировать разные группы конфигурации.

# 7. SpecialistBookingAccess

## 7.1. Назначение

Таблица хранит допуск специалиста к созданию и подтверждению Reservation.

Она используется как отдельная точка транзакционной синхронизации.

```sql
CREATE TABLE specialist_booking_access (
    specialist_id BIGINT PRIMARY KEY,

    booking_allowed BOOLEAN NOT NULL DEFAULT FALSE,

    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_booking_access_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT
);
```

## 7.2. Создание Reservation

Применяется:

```sql
SELECT *
FROM specialist_booking_access
WHERE specialist_id = :specialistId
FOR SHARE;
```

После получения блокировки проверяется booking_allowed.

## 7.3. Подтверждение Reservation

Используется та же совместная блокировка.

Она получается до блокировки конкретной Reservation.

## 7.4. Административная блокировка

Используется эксклюзивная блокировка:

```sql
SELECT *
FROM specialist_booking_access
WHERE specialist_id = :specialistId
FOR UPDATE;
```

В рамках одной транзакции:

- booking_allowed переводится в FALSE;
- ACTIVE Reservation специалиста отменяются;
- соответствующие Occupancy удаляются;
- сохраняется административное действие.

## 7.5. Инвариант

После успешного COMMIT административной блокировки у специалиста не должно оставаться ACTIVE Reservation.

Подтверждённые Booking автоматически не отменяются.

## 7.6. Инициализация

Запись BookingAccess должна создаваться при создании Specialist.

Отсутствие записи не означает разрешение на бронирование.

При отсутствии необходимой конфигурации операция должна завершаться отказом.

# 8. SpecialistBookingPolicies

## 8.1. Назначение

Хранит текущие правила:

- minimumBookingNotice;
- clientCancellationNotice.

```sql
CREATE TABLE specialist_booking_policies (
    specialist_id BIGINT PRIMARY KEY,

    minimum_booking_notice_minutes INTEGER
        NOT NULL DEFAULT 0,

    client_cancellation_notice_minutes INTEGER
        NOT NULL DEFAULT 0,

    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_booking_policy_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT chk_minimum_booking_notice
        CHECK (minimum_booking_notice_minutes >= 0),

    CONSTRAINT chk_client_cancellation_notice
        CHECK (client_cancellation_notice_minutes >= 0)
);
```

## 8.2. Конкурентность

При создании Reservation политика читается под FOR SHARE.

При изменении политики используется соответствующая эксклюзивная блокировка.

## 8.3. MinimumBookingNotice

Для новых Reservation:

`bookingDeadline = sessionStart - minimumBookingNotice`

Условие:

`now < bookingDeadline`

## 8.4. ClientCancellationNotice

Значение фиксируется в Reservation snapshot.

Последующее изменение текущей политики не меняет ранее согласованные условия.

## 8.5. Переопределения

Ранее существовало предложение индивидуального переопределения minimumBookingNotice для AvailabilitySlot.

После отказа от слотов новое место хранения такого переопределения не утверждено.

Поэтому в текущем DDL оно не добавляется автоматически.

# 9. SpecialistTimeZoneGuards

## 9.1. Назначение

Хранит текущий часовой пояс специалиста и обеспечивает его согласованное чтение.

```sql
CREATE TABLE specialist_time_zone_guards (
    specialist_id BIGINT PRIMARY KEY,

    time_zone VARCHAR(100) NOT NULL,

    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_time_zone_guard_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT
);
```

## 9.2. Источник истины

Это единственное основное хранилище текущего ZoneId специалиста.

Не следует параллельно хранить независимую копию time_zone в specialists или specialist_schedule_settings.

## 9.3. Резервирование

Используется:

`SELECT ... FOR SHARE`

Часовой пояс остаётся стабильным в пределах критической части транзакции.

## 9.4. Изменение timeZone

Используется:

`SELECT ... FOR UPDATE`

Новая конфигурация применяется после COMMIT.

## 9.5. Исторические записи

Существующие Reservation и Booking сохраняют абсолютные Instant.

Их временные границы не пересчитываются.

## 9.6. Валидация

time_zone должен быть допустимым IANA ZoneId.

Основная валидация выполняется приложением.

# 10. SpecialistScheduleSettings

## 10.1. Назначение

Хранит режим рабочего расписания и горизонт новых записей.

```sql
CREATE TABLE specialist_schedule_settings (
    specialist_id BIGINT PRIMARY KEY,

    mode VARCHAR(20) NOT NULL DEFAULT 'REGULAR',

    booking_horizon_days SMALLINT
        NOT NULL DEFAULT 30,

    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_schedule_settings_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT chk_schedule_mode
        CHECK (mode IN (
            'REGULAR',
            'FLOATING'
        )),

    CONSTRAINT chk_booking_horizon
        CHECK (
            booking_horizon_days IN (
                14, 30, 60, 90
            )
        )
);
```

## 10.2. Конкурентность

При изменении недельного графика используется:

`SpecialistScheduleSettings FOR UPDATE`

Обычное создание Reservation не должно получать эту эксклюзивную блокировку.

## 10.3. Режимы

REGULAR использует WeeklyScheduleVersion.

FLOATING использует DateSchedule с purpose=MANUAL.

## 10.4. Неактивные правила

Сохранённые правила неактивного режима не удаляются автоматически.

Они не участвуют в расчёте актуальной доступности.

## 10.5. Инициализация

Строка настроек создаётся при создании Specialist.

# 11. ServiceOfferings

## 11.1. Назначение

ServiceOffering представляет отдельную услугу специалиста.

```sql
CREATE TABLE service_offerings (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    specialist_id BIGINT NOT NULL,

    title VARCHAR(255) NOT NULL,
    description TEXT,

    duration_minutes INTEGER NOT NULL,
    break_duration_minutes INTEGER NOT NULL DEFAULT 0,

    price NUMERIC(12, 2) NOT NULL,
    currency CHAR(3) NOT NULL,

    active BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_service_offering_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT uq_service_specialist_identity
        UNIQUE (id, specialist_id),

    CONSTRAINT chk_service_duration
        CHECK (duration_minutes > 0),

    CONSTRAINT chk_service_break
        CHECK (break_duration_minutes >= 0),

    CONSTRAINT chk_service_price
        CHECK (price >= 0),

    CONSTRAINT chk_service_currency
        CHECK (currency ~ '^[A-Z]{3}$')
);
```

Создание Reservation читает ServiceOffering под FOR SHARE.

Несколько клиентов могут одновременно читать одну услугу.

Редактирование строки ожидает завершения транзакций, удерживающих несовместимые блокировки.

## 11.3. Исторические условия

Reservation фиксирует snapshot:

- title;
- durationMinutes;
- breakDurationMinutes;
- price;
- currency.

Изменение услуги не обновляет исторические записи.

## 11.4. Индекс

```sql
CREATE INDEX idx_service_offerings_active
ON service_offerings(specialist_id)
WHERE active = TRUE;
```

# 12. WeeklyScheduleVersions

## 12.1. Назначение

Каждая версия хранит полный недельный шаблон для определённого календарного периода.

```sql
CREATE TABLE weekly_schedule_versions (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    specialist_id BIGINT NOT NULL,

    effective_from DATE NOT NULL,
    effective_until DATE,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_weekly_version_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT chk_weekly_version_period
        CHECK (
            effective_until IS NULL
            OR effective_until >= effective_from
        )
);
```

## 12.2. Семантика

effective_from — включительно.

effective_until — включительно.

NULL означает отсутствие верхней границы.

## 12.3. Непересечение периодов

```sql
ALTER TABLE weekly_schedule_versions
ADD CONSTRAINT ex_weekly_schedule_versions
EXCLUDE USING gist (
    specialist_id WITH =,

    daterange(
        effective_from,
        effective_until + 1,
        '[)'
    ) WITH &&
);
```

## 12.4. Инварианты

- у специалиста нет двух версий, действующих в одну дату;
- интервалы принадлежат определённой версии;
- изменение периодов и создание новой версии атомарны;
- отсутствие действующей версии означает отсутствие регулярных рабочих интервалов для такой даты.

## 12.5. Конкурентные изменения

Изменение версий координируется через:

- TimeZoneGuard FOR SHARE;
- ScheduleSettings FOR UPDATE;
- календарные advisory locks;
- повторную проверку обязательств.

# 13. WeeklyWorkingIntervals

## 13.1. Назначение

Хранит интервалы работы в днях недели.

```sql
CREATE TABLE weekly_working_intervals (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    schedule_version_id BIGINT NOT NULL,

    day_of_week SMALLINT NOT NULL,

    start_time TIME(0) NOT NULL,
    end_time TIME(0) NOT NULL,

    CONSTRAINT fk_weekly_interval_version
        FOREIGN KEY (schedule_version_id)
        REFERENCES weekly_schedule_versions(id)
        ON DELETE CASCADE,

    CONSTRAINT chk_weekly_day
        CHECK (day_of_week BETWEEN 1 AND 7),

    CONSTRAINT chk_weekly_time
        CHECK (start_time < end_time)
);
```

## 13.2. DayOfWeek

Используется ISO-нумерация:

- 1 — понедельник;
- 7 — воскресенье.

## 13.3. Полночь

Рабочий интервал не может переходить в следующие сутки.

## 13.4. Проверка пересечений

Вводятся вычисляемые секунды суток:

```sql
ALTER TABLE weekly_working_intervals
ADD COLUMN start_second INTEGER
GENERATED ALWAYS AS (
    EXTRACT(EPOCH FROM start_time)::INTEGER
) STORED;

ALTER TABLE weekly_working_intervals
ADD COLUMN end_second INTEGER
GENERATED ALWAYS AS (
    EXTRACT(EPOCH FROM end_time)::INTEGER
) STORED;
```

Ограничение:

```sql
ALTER TABLE weekly_working_intervals
ADD CONSTRAINT ex_weekly_working_intervals
EXCLUDE USING gist (
    schedule_version_id WITH =,
    day_of_week WITH =,

    int4range(
        start_second,
        end_second,
        '[)'
    ) WITH &&
);
```

## 13.5. Примечание

Использование TIME(0) соответствует целочисленной точности секунд.

Для рабочего графика, требующего только целых минут, дополнительную проверку секунд можно добавить при окончательном проектировании.

Схема не разрешает окончание рабочего окна ровно в 24:00. Представление этой границы остаётся отдельным вопросом.

# 14. DateSchedules

## 14.1. Назначение

Хранит правила конкретной календарной даты.

```sql
CREATE TABLE date_schedules (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    specialist_id BIGINT NOT NULL,

    schedule_date DATE NOT NULL,

    purpose VARCHAR(20) NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT fk_date_schedule_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT chk_date_schedule_purpose
        CHECK (purpose IN (
            'MANUAL',
            'OVERRIDE'
        )),

    CONSTRAINT uq_date_schedule
        UNIQUE (
            specialist_id,
            schedule_date,
            purpose
        )
);
```

## 14.2. MANUAL

Используется при FLOATING.

Отсутствие MANUAL означает нерабочую дату.

## 14.3. OVERRIDE

Используется при REGULAR.

Если OVERRIDE существует, он полностью заменяет недельный график соответствующей даты.

OVERRIDE без интервалов означает выходной.

## 14.4. Удаление

Удаление DateSchedule может изменить доступность.

Поэтому операция должна проходить через сервис управления расписанием и календарную координацию.

```sql
ADD COLUMN end_second INTEGER
GENERATED ALWAYS AS (
    EXTRACT(EPOCH FROM end_time)::INTEGER
) STORED;
```

```sql
ALTER TABLE date_schedule_intervals
ADD CONSTRAINT ex_date_schedule_intervals
EXCLUDE USING gist (
    date_schedule_id WITH =,

    int4range(
        start_second,
        end_second,
        '[)'
    ) WITH &&
);
```

## 15.2. Инварианты

- startTime < endTime;
- интервалы одной DateSchedule не пересекаются;
- консультация должна целиком помещаться в одно непрерывное рабочее окно.

Обязательный перерыв может выходить за границы рабочего окна.

# 16. Reservations

## 16.1. Назначение

Reservation хранит временное удержание консультации и согласованные условия.

```sql
CREATE TABLE reservations (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    client_id BIGINT NOT NULL,
    specialist_id BIGINT NOT NULL,
    service_offering_id BIGINT NOT NULL,

    status VARCHAR(20) NOT NULL,

    session_start TIMESTAMPTZ NOT NULL,
    session_end TIMESTAMPTZ NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at TIMESTAMPTZ NOT NULL,

    cancelled_at TIMESTAMPTZ,
    cancellation_initiator VARCHAR(30),
    cancellation_reason VARCHAR(100),

    service_title_snapshot VARCHAR(255) NOT NULL,

    duration_minutes_snapshot INTEGER NOT NULL,
    break_minutes_snapshot INTEGER NOT NULL,

    price_snapshot NUMERIC(12, 2) NOT NULL,
    currency_snapshot CHAR(3) NOT NULL,

    client_cancellation_notice_minutes_snapshot
        INTEGER NOT NULL,

    CONSTRAINT fk_reservation_client
        FOREIGN KEY (client_id)
        REFERENCES clients(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT fk_reservation_specialist
        FOREIGN KEY (specialist_id)
        REFERENCES specialists(user_id)
        ON DELETE RESTRICT,

    CONSTRAINT fk_reservation_service_owner
        FOREIGN KEY (
            service_offering_id,
            specialist_id
        )
        REFERENCES service_offerings(
            id,
            specialist_id
        )
        ON DELETE RESTRICT,

    CONSTRAINT uq_reservation_participants
        UNIQUE (
            id,
            client_id,
            specialist_id
        ),

    CONSTRAINT uq_reservation_specialist
        UNIQUE (
            id,
            specialist_id
        ),

    CONSTRAINT chk_reservation_status
        CHECK (status IN (
            'ACTIVE',
            'CONFIRMED',
            'CANCELLED',
            'EXPIRED'
        )),

    CONSTRAINT chk_reservation_time
        CHECK (session_start < session_end),

    CONSTRAINT chk_reservation_expiration
        CHECK (expires_at > created_at),

    CONSTRAINT chk_reservation_duration
        CHECK (duration_minutes_snapshot > 0),

    CONSTRAINT chk_reservation_break
        CHECK (break_minutes_snapshot >= 0),

    CONSTRAINT chk_reservation_price
        CHECK (price_snapshot >= 0),

    CONSTRAINT chk_reservation_cancellation_notice
        CHECK (
            client_cancellation_notice_minutes_snapshot >= 0
        ),

    CONSTRAINT chk_reservation_session_duration
        CHECK (
            session_end - session_start =
            duration_minutes_snapshot * INTERVAL '1 minute'
        )
);
```

## 16.2. Состояния

- ACTIVE;
- CONFIRMED;
- CANCELLED;
- EXPIRED.

## 16.3. TTL

expiresAt устанавливается платформой.

Специалист не управляет TTL.

Подтверждение допустимо только при:

`now < expiresAt`

## 16.4. Snapshot

Reservation сохраняет:

- услугу и специалиста;
- название;
- длительность;
- перерыв;
- цену;
- валюту;
- клиентское правило отмены;
- абсолютные времена консультации.

## 16.5. Исторические условия

Изменение текущей ServiceOffering или BookingPolicy не изменяет snapshot.

## 16.6. Дополнительные проверки

На уровне бизнес-сценария проверяются:

- состояние клиента;
- доступ специалиста;
- активность услуги;
- допустимость рабочего времени;
- горизонт записи;
- minimumBookingNotice;
- правило DST;
- отсутствие конфликтующей Occupancy.

## 16.7. Индексы

```sql
CREATE INDEX idx_reservations_client_created
ON reservations(client_id, created_at DESC);

CREATE INDEX idx_reservations_specialist_start
ON reservations(specialist_id, session_start);

CREATE INDEX idx_reservations_active_expiration
ON reservations(expires_at)
WHERE status = 'ACTIVE';

CREATE INDEX idx_reservations_specialist_active
ON reservations(specialist_id, id)

```

Последний индекс помогает находить ACTIVE Reservation специалиста при административной блокировке.

# 17. ScheduleOccupancies

## 17.1. Назначение

ScheduleOccupancy хранит только действующую занятость.

```sql
CREATE TABLE schedule_occupancies (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    specialist_id BIGINT NOT NULL,
    reservation_id BIGINT NOT NULL,

    start_time TIMESTAMPTZ NOT NULL,
    session_end_time TIMESTAMPTZ NOT NULL,
    occupied_until TIMESTAMPTZ NOT NULL,

    CONSTRAINT fk_occupancy_reservation_owner
        FOREIGN KEY (
            reservation_id,
            specialist_id
        )
        REFERENCES reservations(
            id,
            specialist_id
        )
        ON DELETE RESTRICT,

    CONSTRAINT uq_occupancy_reservation
        UNIQUE (reservation_id),

    CONSTRAINT chk_occupancy_interval
        CHECK (
            start_time < session_end_time
            AND session_end_time <= occupied_until
        )
);
```

## 17.2. Проверка пересечений

```sql
ALTER TABLE schedule_occupancies
ADD CONSTRAINT ex_occupancy_overlap
EXCLUDE USING gist (
    specialist_id WITH =,

    tstzrange(
        start_time,
        occupied_until,
        '[)'
    ) WITH &&
);
```

## 17.3. Гарантия

Две пересекающиеся Occupancy одного специалиста не могут успешно существовать одновременно.

## 17.4. Связь с Reservation

Каждая Occupancy принадлежит одной Reservation.

Историческая Reservation может не иметь Occupancy.

## 17.5. Временная согласованность

Должны выполняться:

- start_time = Reservation.session_start;
- session_end_time = Reservation.session_end;
- occupied_until = session_end + break snapshot.

Обычные CHECK не могут сравнивать строки разных таблиц.

Эти правила обеспечиваются командой создания Reservation.

При окончательном DDL следует дополнительно оценить возможность усиления целостности составными FK или пересмотра дублирования временных полей.

## 17.6. Жизненный цикл

Создание Reservation создаёт Occupancy.

Подтверждение Booking сохраняет Occupancy.

Отмена или истечение удержания удаляет Occupancy.

Допустимая отмена Booking также удаляет Occupancy.

После occupiedUntil Occupancy удаляется фоновой очисткой.

## 17.7. Удаление

Исторические Reservation и Booking не удаляются.

Отдельные статусы Occupancy не вводятся.

## 17.8. Индексы

GiST exclusion constraint создаёт индекс для ограничения пересечений.

UNIQUE(reservation_id) также создаёт индекс.

Избыточные дублирующие индексы не требуются без анализа запросов.

# 19. Administrative Blocking

## 19.1. Атомарный сценарий

Административная блокировка должна в одной транзакции:

1. Получить BookingAccess FOR UPDATE.
2. Заблокировать ACTIVE Reservation специалиста.
3. Перевести их в CANCELLED.
4. Удалить Occupancy.
5. Запретить новые Reservation.
6. Сохранить административное действие.
7. Выполнить COMMIT.

## 19.2. Referential integrity

Удаление Occupancy не нарушает внешние ключи Reservation или Booking.

## 19.3. История

Заблокированный специалист сохраняет:

- ранее подтверждённые Booking;
- отменённые Reservation;
- модерационную историю.

## 19.4. Ограничение

Простые FOREIGN KEY и CHECK не могут гарантировать, что после блокировки не осталось ACTIVE Reservation.

Это транзакционный инвариант прикладного сценария.

# 26. RefreshSessions и RefreshTokens

## 26.1. Назначение

Для управления долгоживущей аутентификацией PsyWeb использует две самостоятельные таблицы:

- `refresh_sessions` — сеансы входа пользователя;
- `refresh_tokens` — поколения refresh token, принадлежащие сеансам.

**Статус:** утверждённая целевая модель MVP.

Таблица `authentication_sessions` из первоначального проекта больше не используется.

Основные решения:

- access JWT действует 15 минут и не хранится в PostgreSQL;
- RefreshSession действует 7 дней с момента login;
- срок сессии абсолютный и не продлевается при rotation;
- каждый успешный refresh заменяет текущее поколение токена;
- исходные refresh tokens не сохраняются в PostgreSQL;
- история использованных токенов сохраняется для replay detection.

Auth module является владельцем обеих таблиц.

---

## 26.2. RefreshSessions

RefreshSession представляет отдельный сеанс аутентификации пользователя.

Один User может иметь несколько независимых refresh-сессий.

Каждый самостоятельный успешный login создаёт новую RefreshSession.

### PostgreSQL DDL

```sql
CREATE TABLE refresh_sessions (
    id UUID PRIMARY KEY,

    user_id BIGINT NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at TIMESTAMPTZ NOT NULL,

    revoked_at TIMESTAMPTZ,
    last_used_at TIMESTAMPTZ,

    CONSTRAINT fk_refresh_session_user
        FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE RESTRICT,

    CONSTRAINT chk_refresh_session_expiration
        CHECK (expires_at > created_at),

    CONSTRAINT chk_refresh_session_revocation
        CHECK (
            revoked_at IS NULL
            OR revoked_at >= created_at
        ),

    CONSTRAINT chk_refresh_session_last_used
        CHECK (
            last_used_at IS NULL
            OR last_used_at >= created_at
        )
);
```

### Идентификатор

`id` использует UUIDv4.

UUID генерируется приложением до INSERT.

PostgreSQL хранит его в нативном типе UUID.

Существующий `User.id` сохраняет BIGINT.

### Срок действия

При login:

```text
createdAt = currentTime
expiresAt = createdAt + 7 days
```

Успешная rotation не изменяет `expires_at`.

Действительность сессии определяется условиями:

```text
revoked_at IS NULL
AND currentTime < expires_at
```

Отдельный status enum не требуется.

### Revocation

`revoked_at` заполняется при отзыве сессии.

Отозванная сессия не может использоваться для refresh.

Отзыв одной сессии не отзывает остальные сессии пользователя.

Logout-all отзывает все действующие refresh-сессии пользователя.

### last_used_at

`last_used_at` отражает момент последнего успешного refresh.

При первоначальном login значение может быть NULL.

Обновление `last_used_at` не продлевает срок сессии.

---

## 26.3. RefreshTokens

RefreshToken представляет одно поколение refresh token внутри RefreshSession.

Исходное значение токена генерируется криптографически стойким генератором случайных чисел.

Минимальная энтропия — 256 бит.

В PostgreSQL хранится только SHA-256 хеш исходного токена.

Для выбранного hex-представления SHA-256 используется VARCHAR(64).

### PostgreSQL DDL

```sql
CREATE TABLE refresh_tokens (
    id UUID PRIMARY KEY,

    session_id UUID NOT NULL,

    token_hash VARCHAR(64) NOT NULL,

    issued_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    consumed_at TIMESTAMPTZ,

    CONSTRAINT fk_refresh_token_session
        FOREIGN KEY (session_id)
        REFERENCES refresh_sessions(id)
        ON DELETE CASCADE,

    CONSTRAINT uq_refresh_token_hash
        UNIQUE (token_hash),

    CONSTRAINT chk_refresh_token_hash_format
        CHECK (
            token_hash ~ '^[0-9a-f]{64}$'
        ),

    CONSTRAINT chk_refresh_token_consumption
        CHECK (
            consumed_at IS NULL
            OR consumed_at >= issued_at
        )
);
```

### Идентификатор

`id` использует UUIDv4.

`session_id` ссылается на UUID primary key RefreshSession.

### Хранение секрета

Исходное значение refresh token не сохраняется:

- в базе данных;
- в логах;
- в доменных событиях;
- в журналируемых HTTP DTO.

SHA-256 применяется к криптографически случайному токену.

Argon2id используется для пользовательских паролей, а не для refresh-token fingerprints.

### Срок действия

RefreshToken не имеет собственной колонки `expires_at`.

Его действительность определяется через связанную RefreshSession.

Это предотвращает существование второго независимого источника истины о сроке действия.

### consumed_at

`consumed_at IS NULL` означает, что токен ещё не был успешно использован для rotation.

При успешной rotation поле заполняется.

Использованная запись сохраняется для обнаружения повторного предъявления токена.

---

## 26.4. Ограничение одного текущего токена

Для одной RefreshSession допускается не более одного RefreshToken с:

```sql
consumed_at IS NULL
```

Инвариант обеспечивается частичным уникальным индексом PostgreSQL:

```sql
CREATE UNIQUE INDEX uq_refresh_tokens_current_per_session
ON refresh_tokens(session_id)
WHERE consumed_at IS NULL;
```

Индекс запрещает одновременное существование двух непотреблённых поколений в одной сессии.

При успешной rotation необходимо сначала отметить прежнее поколение потреблённым и обеспечить выполнение соответствующего UPDATE в PostgreSQL, а затем вставить новое поколение.

Из-за особенностей порядка SQL-операций Hibernate может потребоваться явный `flush()` перед INSERT нового RefreshToken.

Фактический порядок проверяется интеграционными тестами.

**Важно:** частичный уникальный индекс гарантирует ограничение количества текущих токенов, но сам по себе не реализует всю логику refresh rotation.

---

## 26.5. Индекс сессий пользователя

Logout-all должен находить refresh-сессии определённого пользователя.

Для этого предусматривается индекс:

```sql
CREATE INDEX idx_refresh_sessions_user
ON refresh_sessions(user_id);
```

Индекс предназначен для поиска сессий по `user_id`.

Окончательная достаточность индекса проверяется по фактическим SQL-запросам и планам PostgreSQL.

---

## 26.6. Индексы RefreshToken

Для `refresh_tokens` предусмотрены:

1. Primary key index по `id`.
2. UNIQUE index по `token_hash`.
3. Частичный UNIQUE index по `session_id`, когда `consumed_at IS NULL`.

UNIQUE constraint на `token_hash` автоматически создаёт соответствующий индекс.

Отдельный дублирующий индекс на `token_hash` не нужен.

При последующей оптимизации необходимо проверить запросы очистки исторических токенов и получения поколений конкретной сессии.

Индексы добавляются только при подтверждённой необходимости.

---

## 26.7. Refresh Rotation

Каждый успешный refresh выполняется как атомарный транзакционный сценарий.

Последовательность:

1. Получить исходный refresh token из HttpOnly cookie.
2. Вычислить SHA-256 хеш.
3. Найти соответствующую запись RefreshToken.
4. Определить RefreshSession и User.
5. Получить необходимые блокировки в согласованном порядке.
6. Повторно проверить актуальное состояние User.
7. Проверить срок и revocation RefreshSession.
8. Проверить, что предъявленный RefreshToken ещё не потреблён.
9. Сгенерировать новый refresh token.
10. Установить `consumed_at` старого RefreshToken.
11. Сохранить новое поколение RefreshToken.
12. Обновить `last_used_at` RefreshSession.
13. Зафиксировать транзакцию.
14. Выдать новый access JWT и refresh cookie.

Срок RefreshSession не продлевается.

Новая refresh cookie должна иметь срок жизни, не превышающий оставшееся время до `RefreshSession.expires_at`.

---

## 26.8. Порядок блокировок

Для согласования login, refresh и административной блокировки User применяется порядок:

```text
User
  ↓
RefreshSession
  ↓
RefreshToken
```

Auth получает доступ к User через публичный контракт User module.

Прямое использование UserRepository из Auth запрещено.

Предварительный поиск токена может выполняться до получения блокировок, но его результат не является окончательным основанием для rotation.

После получения необходимых блокировок состояние всех участвующих сущностей проверяется повторно.

Конкурентные операции должны быть проверены на PostgreSQL при уровне изоляции READ COMMITTED.

---

## 26.9. Replay Detection

Повторное предъявление RefreshToken с заполненным `consumed_at` считается повторным использованием ранее потреблённого токена.

В MVP grace period не используется.

При подтверждённом replay связанная RefreshSession отзывается.

Необходимо обеспечить:

- атомарность изменения `revoked_at`;
- сохранение revocation;
- отсутствие выдачи нового refresh token;
- корректное завершение операции ошибкой аутентификации.

Нельзя допускать, чтобы исключение после установки `revoked_at` откатило транзакцию и восстановило действительность сессии.

Граница транзакции и стратегия фиксации revocation проектируются отдельно.

---

## 26.10. Logout

### Logout текущей сессии

При logout:

- определяется текущая RefreshSession;
- устанавливается `revoked_at`, если сессия ещё не отозвана;
- refresh cookie очищается;
- операция должна быть идемпотентной.

Logout не требует удаления исторических RefreshToken.

### Logout-all

При logout-all:

- пользователь проходит access JWT authentication;
- через User module проверяется актуальный UserStatus;
- выбираются refresh-сессии пользователя;
- действующие сессии отзываются согласованной транзакционной операцией.

Обычный logout не отзывает уже выпущенные access JWT немедленно.

При ACTIVE User они могут оставаться действительными до истечения 15 минут.

---

## 26.11. История и очистка

RefreshToken поколения сохраняются:

- весь срок действия RefreshSession;
- ещё 24 часа после окончания её срока действия.

Периодическая cleanup-задача удаляет сессии, для которых:

```text
currentTime >= expiresAt + 24 hours
```

Связанные RefreshToken удаляются вместе с RefreshSession согласно `ON DELETE CASCADE`.

Cleanup не должен удалять активные сессии.

При удалении сессии необходимо учитывать сохранение целостности её дочерних записей.

Политика удаления пользовательских учётных записей и связанных с ними refresh-сессий определяется отдельно.

---

## 26.12. Security-инварианты

1. Access JWT не хранится в PostgreSQL.
2. Исходные refresh tokens не сохраняются.
3. RefreshSession имеет абсолютный срок жизни 7 дней.
4. Rotation не продлевает срок сессии.
5. В каждой сессии допускается не более одного непотреблённого токена.
6. Использованные токены сохраняются для replay detection.
7. Отозванная или истёкшая сессия не может выполнять refresh.
8. Заблокированный User не может успешно выполнить refresh.
9. Проверка UserStatus согласовывается с административной блокировкой.
10. Отзыв при replay должен быть зафиксирован до формирования ошибки.
11. PostgreSQL constraints дополняют транзакционную бизнес-логику, но не заменяют её.
12. UUID не используется как самостоятельный механизм авторизации.

# 29. Межтабличные инварианты

Не все требования можно выразить через CHECK.

## 29.1. Booking ownership

Booking должна принадлежать тем же клиенту и специалисту, что и исходная Reservation.

Это обеспечивается составным FK.

## 29.2. Service ownership

Услуга Reservation должна принадлежать указанному специалисту.

Это обеспечивается составным FK.

## 29.3. Occupancy ownership

Occupancy должна принадлежать тому же специалисту, что и исходная Reservation.

Это обеспечивается составным FK.

## 29.4. Occupancy time consistency

Границы Occupancy должны соответствовать snapshot Reservation.

Обычный CHECK не может сравнить данные разных строк и таблиц.

Это обеспечивается транзакционной командой.

## 29.5. Review eligibility

eligibilityBooking должна принадлежать соответствующей паре клиент–специалист.

Это обеспечивается составным FK.

Подтверждённый успешный SessionOutcome проверяется доменным сервисом.

## 29.6. BookingAccess

Административная блокировка и отмена всех ACTIVE Reservation должны выполняться атомарно.

## 29.7. Reporter eligibility

SessionOutcomeReport может создать только участник соответствующей Booking.

Это проверяется OutcomeService.

## 29.8. Administrator authority

Административные действия могут выполнять только уполномоченные пользователи.

Это обеспечивается security и бизнес-авторизацией.

## 29.9. RefreshSession ownership

Каждая RefreshSession должна принадлежать существующему User.

Это обеспечивается FK:

```sql
refresh_sessions.user_id → users.id
```

Тип внешнего ключа — BIGINT, независимо от UUID primary key самой RefreshSession.

Auth не изменяет User через прямое обращение к UserRepository.

## 29.10. RefreshToken ownership

Каждый RefreshToken принадлежит одной RefreshSession.

Это обеспечивается FK:

```sql
refresh_tokens.session_id → refresh_sessions.id
```

Обе колонки имеют тип UUID.

## 29.11. Refresh-token validity

Для успешного refresh должны одновременно выполняться условия:

```text
User.status = ACTIVE

RefreshSession.revoked_at IS NULL

currentTime < RefreshSession.expires_at

RefreshToken.consumed_at IS NULL
```

Эти условия нельзя полностью выразить обычным CHECK, поскольку они затрагивают несколько таблиц и текущее время.

Они проверяются внутри транзакционного сценария Auth.

## 29.12. Refresh rotation

В одной RefreshSession допускается не более одного непотреблённого RefreshToken.

Это обеспечивается частичным уникальным индексом PostgreSQL.

Однако уникальный индекс не заменяет:

- проверку актуального UserStatus;
- проверку срока RefreshSession;
- проверку revocation;
- обнаружение replay;
- транзакционную координацию.

При успешной rotation изменение предыдущего токена и создание нового поколения должны быть атомарными.

# 30. Транзакционные операции

## 30.1. Создание Reservation

Атомарно:

- проверка условий;
- создание ACTIVE Reservation;
- создание Occupancy.

## 30.2. Подтверждение

Атомарно:

- проверка BookingAccess;
- проверка ACTIVE и TTL;
- Reservation → CONFIRMED;
- создание Booking.

Occupancy сохраняется.

## 30.3. Истечение Reservation

Атомарно:

- ACTIVE → EXPIRED;
- DELETE Occupancy.

## 30.4. Отмена Reservation

Атомарно:

- ACTIVE → CANCELLED;
- cancellation metadata;
- DELETE Occupancy.

## 30.5. Отмена Booking

Атомарно:

- Booking → CANCELLED;
- cancellation metadata;
- DELETE Occupancy.

## 30.6. Изменение DateSchedule

Атомарно:

- календарная координация;
- проверка обязательств;
- изменение рабочих интервалов.

## 30.7. Изменение WeeklyScheduleVersion

Атомарно:

- координация изменения конфигурации;
- проверка версий;
- проверка обязательств;
- изменение периодов;
- сохранение новой версии.

## 30.8. Административная блокировка

Атомарно:

- запрет новых записей;
- отмена ACTIVE Reservation;
- освобождение Occupancy;
- административный аудит.

## 30.9. Изменение timeZone

Атомарно:

- эксклюзивная блокировка TimeZoneGuard;
- повторная проверка обязательств;
- проверка подтверждения специалиста при конфликтах;
- изменение ZoneId.

Абсолютные времена существующих Booking и Reservation сохраняются.

## 30.10. Создание RefreshSession

Успешный login включает:

1. Проверку credentials.
2. Проверку актуального UserStatus.
3. Создание RefreshSession.
4. Создание первоначального RefreshToken.
5. Сохранение обеих записей одной транзакцией.

Сессия и её первоначальный токен не должны сохраняться независимо друг от друга.

Login согласовывается с конкурентной административной блокировкой User.

## 30.11. Refresh rotation

Атомарно:

- проверка состояния User;
- проверка RefreshSession;
- проверка текущего RefreshToken;
- установка consumed_at предыдущего токена;
- создание нового RefreshToken;
- обновление last_used_at.

Новая пара access JWT и refresh cookie выдаётся только при успешном завершении серверной операции.

В рамках одной сессии нельзя успешно подтвердить две конкурирующие rotation одного поколения.

## 30.12. Refresh-token replay

При повторном предъявлении потреблённого токена:

- определяется затронутая RefreshSession;
- сессия отзывается;
- revocation сохраняется в PostgreSQL;
- новый refresh token не выдаётся;
- клиент получает ошибку аутентификации.

Отзыв должен быть зафиксирован до формирования ошибки.

Исключение не должно приводить к откату уже выполненной revocation.

## 30.13. Logout

Logout текущей сессии:

- определяет RefreshSession;
- устанавливает revoked_at при необходимости;
- сохраняет изменение;
- очищает refresh cookie.

Операция должна быть идемпотентной.

## 30.14. Logout-all

Logout-all отзывает все refresh-сессии пользователя.

Операция должна:

- проверять identity и UserStatus;
- использовать публичный контракт User module;
- согласованно отзывать соответствующие RefreshSession;
- сохранять результат транзакции.

Уже выпущенные access JWT обычным logout-all немедленно не отзываются.

# 31. Модель блокировок

| Ресурс | При резервировании | При изменении |
|---|---|---|
| ServiceOffering | FOR SHARE | UPDATE |
| BookingAccess | FOR SHARE | FOR UPDATE |
| BookingPolicy | FOR SHARE | UPDATE |
| TimeZoneGuard | FOR SHARE | FOR UPDATE |
| ScheduleSettings | Без эксклюзивной блокировки | FOR UPDATE для конфигурации |
| Calendar date | Advisory lock | Advisory lock |
| Reservation | FOR UPDATE при необходимости | FOR UPDATE |
| Booking | По сценарию | По сценарию |
| User при login/refresh | Согласованная блокировка через User contract | FOR UPDATE при блокировке аккаунта |
| RefreshSession | По сценарию | FOR UPDATE при rotation/revocation |
| RefreshToken | По сценарию | Согласованная проверка и изменение поколения |

## 31.1. Основное требование

Операции должны использовать единый порядок захвата ресурсов в пределах соответствующего бизнес-сценария.

## 31.2. PostgreSQL

Advisory locks должны быть transaction-level.

Не следует использовать локальные JVM-locks как единственный механизм.

## 31.3. FK и JPA

Реальный порядок блокировок может зависеть от:

- SQL, созданного Hibernate;
- flush;
- внешних ключей;
- UPDATE;
- INSERT;
- DELETE.

Протокол необходимо проверить интеграционно.

## 31.4. Auth lock ordering

Для операций Auth с несколькими ресурсами используется порядок:

```text
User
  ↓
RefreshSession
  ↓
RefreshToken
```

Предварительный поиск RefreshToken по token_hash может выполняться до получения блокировок.

Однако окончательная проверка токена должна выполняться после получения необходимых блокировок.

User module предоставляет публичный контракт для согласованной проверки состояния аккаунта.

Auth не обращается напрямую к UserRepository.

## 31.5. Auth и административная блокировка

После фиксации UserStatus.BLOCKED новые login и refresh не должны успешно выдавать действительные токены.

Проверка состояния пользователя должна быть согласована с конкурентным административным изменением UserStatus.

Фактический протокол необходимо проверить интеграционными тестами PostgreSQL.

## 31.6. Refresh rotation и Hibernate flush

Частичный уникальный индекс запрещает два RefreshToken с consumed_at IS NULL в одной сессии.

Поэтому при rotation необходим корректный порядок SQL:

1. Обновить предыдущий RefreshToken.
2. Обеспечить выполнение UPDATE.
3. Вставить новое поколение.

При использовании JPA может потребоваться явный flush перед INSERT.

Конкретный порядок определяется реализацией и проверяется на PostgreSQL.

# 32. Работа со временем

## 32.1. TIMESTAMPTZ

Reservation и Occupancy хранят абсолютные моменты времени.

## 32.2. LocalDate и LocalTime

Используются для регулярного и датированного расписания.

## 32.3. ZoneId

Хранится в specialist_time_zone_guards.

## 32.4. DST

При создании новой Reservation:

- несуществующее локальное начало запрещено;
- неоднозначное локальное начало запрещено.

## 32.5. Перерывы

Перерыв может выходить за границы рабочего окна и пересекать полночь.

## 32.6. Существующие Booking

Сохранённые абсолютные времена не изменяются при смене ZoneId.

## 32.7. Открытый вопрос

Политика консультации, которая начинается в однозначное время, но пересекает DST-переход, ещё требует отдельного решения.

## 32.8. Время RefreshSession

Временные поля RefreshSession и RefreshToken используют TIMESTAMPTZ.

Срок сессии:

```text
expiresAt = createdAt + 7 days
```

Успешная rotation не изменяет expiresAt.

Истечение сессии определяется сравнением абсолютных моментов времени.

## 32.9. Retention

История RefreshToken сохраняется до истечения абсолютного срока RefreshSession и ещё 24 часа.

Cleanup удаляет сессии после окончания установленного retention window.

При реализации используется единый инжектируемый Clock для прикладных временных проверок.

# 33. Индексы

## 33.1. Принцип

UNIQUE и exclusion constraints создают необходимые индексы.

Не следует создавать их дубликаты.

## 33.2. Критические запросы

Основные направления оптимизации:

- активные услуги специалиста;
- календарные версии;
- расписание конкретной даты;
- занятость по специалисту и времени;
- ACTIVE Reservation по expiresAt;
- ACTIVE Reservation специалиста;
- Booking клиента;
- Booking специалиста;
- Review специалиста;
- RefreshToken по token_hash;
- RefreshSession по user_id;
- определение текущего RefreshToken конкретной сессии.

## 33.3. Проверка

Реальные индексы должны проверяться под запросы Hibernate и SQL.

Используется EXPLAIN / EXPLAIN ANALYZE.

## 33.4. Осторожность

Количество индексов не должно расти без измеренной необходимости.

Они ускоряют чтение, но увеличивают стоимость записи.

## 33.5. Auth indexes

Для Auth предусмотрены:

- primary key index RefreshSession.id;
- primary key index RefreshToken.id;
- UNIQUE index RefreshToken.token_hash;
- частичный UNIQUE index для одного непотреблённого токена на сессию;
- индекс RefreshSession.user_id.

Частичный уникальный индекс одновременно обеспечивает инвариант:

```sql
CREATE UNIQUE INDEX uq_refresh_tokens_current_per_session
ON refresh_tokens(session_id)
WHERE consumed_at IS NULL;
```

Индекс на token_hash создаётся автоматически через UNIQUE constraint.

Дублирующий обычный индекс по token_hash не требуется.

# 34. Что удаляется из прежней модели

Устаревшие таблицы и связи:

- availability_slot;
- booking.slot_id;
- UNIQUE booking(slot_id);
- статусы FREE, BOOKED, BLOCKED у слота.

Также больше не используется уникальность Review по booking_id.

В Auth не используется первоначальная целевая таблица:

- authentication_sessions.

Вместо неё:

- refresh_sessions;
- refresh_tokens.

Новая модель разделяет сеанс входа и поколения refresh token.

В основной модели бронирования:

- расписание хранится правилами;
- доступность вычисляется;
- Reservation удерживает время через Occupancy;
- Booking ссылается на Reservation;
- Review уникален по client_id и specialist_id.

# 35. Стратегия Flyway

## 35.1. Разделение DDL и миграций

Этот документ описывает целевую структуру.

Он не заменяет последовательность Flyway-миграций.

## 35.2. Существующая база

Перед изменением миграций требуется проверить текущую схему и существующий код.

## 35.3. Отсутствие production-данных

Поскольку production-данных пользователей ещё нет, допускается контролируемая переработка локальной схемы.

При этом нельзя удалять локальные данные без проверки необходимости их сохранения.

## 35.4. Проверка миграций

Каждая миграция должна применяться на PostgreSQL.

Для интеграционных проверок рекомендуется Testcontainers.

## 35.5. Последовательность

Предлагается:

1. Пользователи и профили.
2. Конфигурация специалиста.
3. ServiceOffering.
4. Schedule.
5. Reservation.
6. Occupancy.
7. Booking.
8. Outcome.
9. Review.
10. Admin и Notification.
11. RefreshSession и RefreshToken.
12. Будущие дополнительные модули.

Фактическая последовательность зависит от внешних ключей и текущей истории миграций.

## 35.6. Auth migrations

Для Auth необходимо предусмотреть:

- создание refresh_sessions;
- создание refresh_tokens;
- foreign keys;
- CHECK constraints;
- UNIQUE token_hash;
- частичный UNIQUE index для текущего токена сессии;
- индекс поиска сессий по user_id;
- интеграционные проверки rotation и replay detection.

В существующие уже применённые Flyway-миграции изменения задним числом не вносятся.

При необходимости создаётся новая forward migration.

# 37. Открытые вопросы

## 37.1. Допуск специалиста

Необходимо окончательно согласовать связь SpecialistBookingAccess, approval_status и UserStatus.

Не должно возникнуть противоречащих независимых источников истины о разрешении новых записей.

## 37.2. Динамическая доступность

Остаётся определить способ индивидуального переопределения minimumBookingNotice после отказа от AvailabilitySlot.

## 37.3. Временная модель

- окончание рабочего окна в 24:00;
- DST-переход внутри консультации;
- аудит изменения ZoneId.

## 37.4. Конкурентность

- точная генерация advisory-lock keys;
- полный порядок смешанных блокировок;
- проверка Hibernate и FK;
- retry и идемпотентность.

## 37.5. Booking и Outcome

Окончательные статусы Booking и SessionOutcome должны быть согласованы.

## 37.6. Дополнительные модули

- политика доставки уведомлений;
- пересмотр административных решений;
- жизненный цикл сообщений Chat.

## 37.7. Integrity

Требуется решить, какие дополнительные межтабличные инварианты стоит обеспечить составными FK, а какие оставить на уровне транзакционных команд.

## 37.8. Auth implementation

Архитектурная модель RefreshSession и RefreshToken утверждена.

Перед реализацией необходимо окончательно проверить:

- User-service contract для согласования блокировок;
- последовательность SQL при refresh rotation;
- обработку replay с гарантированной фиксацией revocation;
- поведение конкурентных запросов;
- HTTP DTO и cookie lifecycle;
- совместимость Spring Security и CSRF-конфигурации;
- поведение logout-all при параллельном refresh;
- периодическую очистку истории.

Эти вопросы относятся к технической реализации, а не к необходимости пересмотра двухтабличной модели.

# 38. Итог

Реляционная схема PsyWeb использует:

- независимую конфигурацию допуска к бронированию;
- независимые правила записи и отмены;
- отдельное хранение текущего ZoneId;
- версионируемый недельный график;
- расписание конкретных дат;
- динамическую доступность;
- исторические Reservation;
- подтверждённые Booking;
- ScheduleOccupancy для действующей занятости;
- GiST exclusion constraint для защиты от пересечений;
- SessionOutcome для результата консультации;
- один редактируемый Review на пару клиент–специалист;
- административный аудит;
- RefreshSession и RefreshToken для долгоживущей аутентификации;
- UUIDv4 для новых самостоятельных auth-сущностей;
- SHA-256 для хранения refresh-token fingerprints;
- частичный уникальный индекс для контроля текущего токена сессии;
- атомарную refresh rotation и сохранение истории использованных токенов.

Существующие BIGINT primary keys сохраняются.

Схема согласована с целевой архитектурой сервисного слоя на концептуальном уровне.

**Статус: DRAFT — SQL требует проверки исполнения, а открытые бизнес-правила необходимо согласовать до окончательных миграций.**
