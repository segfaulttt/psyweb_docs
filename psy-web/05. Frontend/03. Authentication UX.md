# 1. Назначение документа

Документ описывает пользовательские сценарии аутентификации в frontend PsyWeb.

Рассматриваются:

- регистрация клиента и специалиста;
- вход в аккаунт;
- восстановление аутентифицированной сессии;
- обновление access token;
- завершение текущей сессии;
- завершение всех сессий;
- истечение срока действия аутентификации;
- обработка ошибок и ограничений доступа;
- поведение нескольких вкладок браузера;
- восстановление доступа к аккаунту.

Документ определяет ожидаемое поведение интерфейса, но не фиксирует его визуальный дизайн, структуру компонентов или конкретную реализацию frontend.

Наличие описанного сценария не означает, что соответствующий backend endpoint уже реализован.

# 3. Основные принципы

## 3.1. Authentication и Authorization

Authentication устанавливает идентичность пользователя.

Authorization определяет, какие операции этот пользователь вправе выполнять.

Успешный вход не означает автоматического доступа ко всем функциям соответствующей роли.

При определении доступа дополнительно учитываются:

- UserStatus;
- роль пользователя;
- Specialist ApprovalStatus;
- SpecialistBookingAccess;
- принадлежность ресурса;
- бизнес-условия конкретной операции.

Frontend может ограничивать доступность действий для удобства пользователя, но не заменяет backend authorization.

## 3.2. Пользовательские роли

Для MVP предусмотрены:

- CLIENT;
- SPECIALIST;
- ADMIN.

Сценарий входа является общим для предусмотренных учётных записей.

Различия между ролями влияют на последующую навигацию и доступные действия.

## 3.3. Состояние аккаунта

Защищённые операции доступны только при выполнении требований к состоянию пользователя.

В частности, `UserStatus.BLOCKED` запрещает аутентифицированный доступ.

Профессиональная модерация специалиста не является частью проверки правильности его пароля.

ACTIVE-специалист может войти в аккаунт, даже если его профессиональная заявка ещё не одобрена.

## 3.4. Сервер как источник истины

Frontend не должен самостоятельно определять:

- действительность refresh token;
- актуальный UserStatus;
- результат профессиональной модерации;
- наличие права на конкретную бизнес-операцию;
- возможность продолжать отозванную сессию.

Эти сведения и решения принадлежат backend.

# 4. Регистрация

## 4.1. Регистрация клиента

Регистрация CLIENT предусматривает создание пользовательского аккаунта с разрешёнными регистрационными данными.

Концептуальный пользовательский процесс:

```text
Client Registration
    ↓
Заполнение данных
    ↓
Локальная проверка формы
    ↓
Отправка запроса
    ↓
Backend Validation
    ↓
Результат регистрации
```

Frontend должен:

- принимать только предусмотренные регистрационной формой данные;
- показывать ошибки формата и обязательных полей;
- отображать результат backend validation;
- исключать случайную многократную отправку;
- не заявлять об успешной регистрации до подтверждения backend.

Точный набор полей и сообщения об ошибках определяются регистрационным API.

## 4.2. Регистрация специалиста

Регистрация SPECIALIST является отдельным сценарием.

Она предусматривает создание аккаунта специалиста и последующую профессиональную модерацию.

После регистрации интерфейс должен корректно различать:

- успешное создание аккаунта;
- состояние профессиональной заявки;
- возможность входа в аккаунт;
- право выполнять профессиональные операции;
- право принимать новые бронирования.

Регистрация не означает автоматического профессионального одобрения.

## 4.3. Ошибки регистрации

Frontend должен обрабатывать:

- некорректные поля;
- нарушения ограничений ввода;
- конфликт уникальности email;
- отказ в регистрации по предусмотренным правилам;
- временную недоступность backend.

Конкретная форма сообщения не должна раскрывать внутренние технические сведения.

## 4.4. Поведение после регистрации

Автоматический вход после регистрации, необходимость отдельного login и маршрут последующего перехода не фиксируются этим документом.

Они должны быть согласованы с фактическим registration/authentication contract.

# 5. Вход в аккаунт

## 5.1. Назначение

Login устанавливает аутентифицированную сессию пользователя на основании предоставленных учётных данных.

В целевой backend-модели используется email/password authentication.

## 5.2. Последовательность

```text
Login Form
    ↓
Email + Password
    ↓
Client-side Validation
    ↓
Authentication Request
    ↓
Backend Credentials Verification
    ↓
Success / Failure
```

При успешном login backend создаёт refresh-сессию и выдаёт access JWT согласно утверждённой модели.

## 5.3. Успешный вход

После успешного ответа frontend должен:

1. Принять результат аутентификации.
2. Обновить локальное состояние аутентификации.
3. Использовать полученный access JWT для защищённых запросов.
4. Получить или подтвердить необходимые сведения об аккаунте согласно доступному API.
5. Предоставить доступ к разрешённой пользовательской области.

Конкретный стартовый раздел после входа для CLIENT, SPECIALIST и ADMIN определяется при проектировании навигации.

Нельзя считать пользователя авторизованным только потому, что форма login была успешно отправлена.

## 5.4. Неверные учётные данные

Неверные credentials должны приводить к безопасному сообщению об ошибке.

Сообщение не должно раскрывать:

- существует ли указанный email;
- правильность отдельных элементов credentials;
- passwordHash;
- внутреннее состояние учётной записи сверх разрешённого API-контракта.

Frontend не должен самостоятельно определять точную причину отказа на основании предположений.

## 5.5. Повторная отправка

Во время выполнения login request интерфейс должен предотвращать случайную повторную отправку формы.

При ошибке пользователь должен иметь возможность повторить попытку после завершения предыдущего запроса.

Ограничение частоты запросов и защита от brute-force относятся к backend security.

# 6. Модель аутентифицированной сессии

## 6.1. Access Token

Утверждённая целевая модель PsyWeb использует подписанный JWT access token.

Для MVP установлен TTL:

`15 минут`

Access JWT предназначен для аутентификации защищённых запросов.

## 6.2. Хранение Access Token

В утверждённой frontend security model access JWT хранится в оперативной памяти приложения.

Не предусматривается долговременное сохранение access JWT в:

- localStorage;
- sessionStorage.

Это требование безопасности не зависит от конкретной будущей организации компонентов и frontend state.

## 6.3. Refresh Token

Refresh token представляет собой opaque token.

Для браузерного клиента он передаётся через HttpOnly cookie.

Frontend JavaScript не должен считывать значение refresh token.

Cookie используется браузером при соответствующих запросах согласно политике безопасности.

## 6.4. Refresh Session

Утверждённая модель предусматривает абсолютный срок жизни refresh-сессии:

`7 дней`

Успешный refresh не продлевает исходный срок её действия.

Истечение refresh-сессии означает необходимость новой аутентификации.

## 6.5. Token Rotation

При успешном refresh выполняется строгая rotation refresh token.

Повторное использование старого токена может быть распознано backend как replay.

Frontend должен учитывать это поведение при организации запросов и восстановлении сессии.

Механизм rotation реализуется backend.

# 7. Восстановление сессии

## 7.1. Назначение

Поскольку access JWT хранится только в памяти приложения, после перезагрузки страницы он может отсутствовать.

Это не обязательно означает, что refresh-сессия уже завершена.

Frontend может инициировать предусмотренный backend refresh flow для восстановления доступа.

## 7.2. Концептуальный сценарий

```text
Application Start
    ↓
Access JWT отсутствует
    ↓
Попытка восстановления через Refresh Flow
    ├── Success → Authenticated State
    └── Failure → Unauthenticated State
```

Восстановление не должно предполагать, что наличие cookie гарантирует действительную сессию.

## 7.3. Промежуточное состояние

До завершения проверки сессии frontend должен различать:

- ещё не установленное состояние аутентификации;
- успешно установленную аутентификацию;
- отсутствие действующей аутентификации.

Защищённые данные не должны отображаться как доступные только на основании предположения о существовании сессии.

Конкретный loading UX определяется позднее.

## 7.4. Ошибка восстановления

Если refresh невозможен, frontend должен перейти в состояние отсутствия действующей аутентификации.

Пользователь должен получить возможность выполнить новый login.

Автоматическое бесконечное повторение refresh не допускается.

## 7.5. Возврат к пользовательскому сценарию

После успешного восстановления сессии допустимо продолжить ранее запрошенный сценарий, если:

- пользователь по-прежнему обладает необходимыми правами;
- ресурс существует;
- состояние операции остаётся допустимым.

Конкретная политика восстановления навигации определяется отдельно.

Особенно важно не считать ранее выбранную Availability или ACTIVE Reservation неизменной после восстановления сессии.

---

# 8. Истечение Access Token

## 8.1. Нормальное истечение

Истечение короткоживущего access JWT является ожидаемой частью authentication lifecycle.

Само по себе оно не означает немедленное истечение refresh-сессии.

## 8.2. Обновление токена

При необходимости frontend может использовать предусмотренный backend refresh flow.

При успешном ответе:

- обновляется access JWT в памяти;
- соответствующий запрос может быть выполнен согласно принятой политике повтора;
- пользователь продолжает работу при сохранении прав доступа.

Конкретная стратегия автоматического обновления определяется при реализации.

## 8.3. Неуспешный Refresh

Если refresh token недействителен, отозван или refresh-сессия истекла, необходимо перейти в unauthenticated state.

Пользователь должен повторно войти в аккаунт.

Frontend не должен пытаться самостоятельно восстановить недействительный refresh token.

## 8.4. Повтор бизнес-запросов

Автоматическое повторение запроса после refresh требует осторожности.

Особенно это относится к операциям изменения данных:

- создание Reservation;
- подтверждение Booking;
- отмена консультации;
- изменение расписания;
- административные действия.

Повтор не должен создавать дублирующие бизнес-операции.

Политика retry и идемпотентность должны согласовываться с соответствующими API-контрактами.

# 9. Несколько вкладок браузера

## 9.1. Проблема

Несколько вкладок одного браузерного профиля могут использовать общую refresh cookie.

При этом access JWT каждой вкладки находится в её собственной памяти.

Одновременные refresh-запросы могут привести к конфликту строгой token rotation.

## 9.2. Утверждённая стратегия

Целевая архитектура предусматривает:

- single-flight refresh внутри вкладки;
- межвкладочную координацию;
- строгую серверную rotation.

Конкретный frontend-протокол ещё не утверждён.

## 9.3. Возможные механизмы

При реализации рассматриваются:

- BroadcastChannel;
- Web Locks API;
- эквивалентные механизмы.

Этот документ не выбирает конкретный механизм.

## 9.4. Граница ответственности

Frontend-координация уменьшает вероятность случайных конфликтов.

Она не заменяет серверную защиту refresh token, replay detection и транзакционные гарантии backend.

# 10. Выход из аккаунта

## 10.1. Logout текущей сессии

Пользователь должен иметь возможность завершить текущую refresh-сессию.

Утверждённая backend-модель предусматривает отзыв соответствующей RefreshSession и очистку refresh cookie.

После успешного logout frontend должен очистить локальное аутентифицированное состояние и перестать использовать access JWT текущей сессии.

## 10.2. Logout All

Целевая authentication model также предусматривает завершение всех refresh-сессий пользователя.

Такая операция должна быть доступна только при выполнении предусмотренных требований аутентификации.

Отображение отдельного пользовательского действия Logout All определяется при детализации account/security UX.

## 10.3. Ранее выданный Access JWT

В MVP отзыв refresh-сессии не обеспечивает мгновенную серверную недействительность всех ранее выданных access JWT.

Они могут оставаться технически действительными до истечения собственного срока.

Frontend должен прекращать использование локального токена после logout, но не должен заявлять о мгновенном отзыве каждого JWT на всех устройствах.

Мгновенный отзыв access JWT отнесён к post-MVP.

## 10.4. Несколько вкладок

Согласованное обновление состояния после logout в нескольких вкладках требует отдельной frontend-реализации.

Необходимо избежать ситуации, когда одна вкладка продолжает представлять пользователя как аутентифицированного только на основании устаревшего локального состояния.

Точный механизм синхронизации определяется вместе с межвкладочной координацией refresh.

# 11. Заблокированный пользователь

## 11.1. UserStatus.BLOCKED

Пользователь с `UserStatus.BLOCKED` не должен получать доступ к защищённым операциям.

Наличие ранее выданного JWT не отменяет это правило.

## 11.2. Отказ при входе

Backend запрещает login для заблокированного пользователя.

Frontend отображает безопасный результат отказа согласно утверждённому authentication error contract.

Нельзя выводить чувствительные подробности о состоянии аккаунта, если они не предусмотрены публичным контрактом.

## 11.3. Блокировка действующего пользователя

Состояние UserStatus может измениться после успешного login.

Поэтому frontend должен корректно обрабатывать последующий отказ защищённого запроса.

Frontend не является источником истины о текущем статусе пользователя.

## 11.4. Отсутствие доступа и отсутствие аутентификации

Нужно различать:

- запрос без действительной аутентификации;
- аутентифицированный запрос без необходимых полномочий;
- недоступность операции из-за бизнес-состояния.

Конкретная интерпретация ошибок определяется HTTP security/error contract.

Не каждый отказ в бизнес-операции означает, что пользователя необходимо разлогинить.

---

# 12. Профессиональный статус специалиста

## 12.1. Login и профессиональное одобрение

Специалист с ACTIVE аккаунтом может пройти authentication независимо от профессионального ApprovalStatus.

Наличие роли SPECIALIST не означает, что профессиональная заявка уже одобрена.

## 12.2. Независимые ограничения

Frontend должен различать:

- UserStatus;
- Specialist ApprovalStatus;
- SpecialistBookingAccess;
- публичную видимость профиля.

Эти состояния не должны объединяться в единый статус аккаунта.

## 12.3. Доступ к профессиональным операциям

После login специалист получает доступ только к тем операциям, которые разрешены его актуальным состоянием.

Например, неодобренный специалист может иметь доступ к предусмотренным операциям подготовки профиля и неактивных услуг.

При этом создание новых Reservation клиентами требует отдельной проверки профессионального допуска и разрешения бронирования.

## 12.4. Отображение ограничений

Интерфейс должен объяснять пользователю недоступность операции на основании разрешённых к раскрытию сведений.

Конкретные формулировки и расположение уведомлений определяются в Specialist UX.

# 13. Восстановление пароля

## 13.1. Назначение

Password recovery/reset является отдельным authentication use case.

Он предназначен для восстановления доступа пользователем, который не может использовать действующие учётные данные.

## 13.2. Текущее состояние Backend

В текущем `psyweb/main` реализованы REST endpoints:

```http
POST /api/auth/password-reset/request
POST /api/auth/password-reset/confirm
```

Первый endpoint принимает email и возвращает HTTP 202 при принятии запроса.

Второй принимает reset token и новый пароль.

При успешном подтверждении возвращается HTTP 204.

В backend присутствуют:

- `PasswordResetService`;
- `PasswordResetServiceImpl`;
- `PasswordResetToken`;
- `PasswordResetTokenRepository`;
- `PasswordResetNotificationSender`.

Текущая реализация использует одноразовые reset tokens с ограниченным сроком действия.

В `PasswordResetServiceImpl` срок действия reset token составляет 30 минут.

## 13.3. Ограничение реализации

Наличие endpoints и сервисной логики не означает готовность полного пользовательского сценария.

В текущем `local` profile используется `LocalPasswordResetNotificationSender`.

Фактическая доставка reset token в этом адаптере не реализована.

Поэтому полный password recovery flow требует дополнительной реализации и интеграционной проверки.

Связанная задача: PSY-111.

## 13.4. Требования к Frontend UX

При реализации frontend необходимо предусмотреть:

- возможность начать восстановление доступа;
- ввод email;
- безопасное отображение результата запроса;
- ввод нового пароля с подтверждением через предусмотренный reset token;
- обработку недействительного или истёкшего токена;
- обработку ошибок password policy;
- возможность вернуться к login.

Интерфейс не должен раскрывать существование конкретного email через различающиеся сообщения.

## 13.5. Открытые вопросы

До завершения backend integration и frontend implementation необходимо уточнить:

- фактический канал доставки reset token;
- структуру страниц восстановления доступа;
- способ передачи токена в frontend;
- пользовательские сообщения;
- поведение после успешной смены пароля;
- требования повторной аутентификации;
- согласованное завершение существующих сессий.

Данный документ не утверждает завершённость password recovery UX.

---

# 14. Безопасность браузерного клиента

## 14.1. Работа с токенами

Frontend не должен:

- сохранять access JWT в localStorage или sessionStorage;
- пытаться читать HttpOnly refresh cookie;
- включать токены в диагностические сообщения;
- раскрывать credentials в интерфейсных ошибках;
- считать локальные признаки авторизации достаточными для доступа к backend.

## 14.2. Cookies и CSRF

Целевая backend-модель использует защищённую refresh cookie и CSRF protection для соответствующих cookie-based операций.

Frontend должен выполнять необходимую интеграцию с CSRF-механизмом Spring Security.

Утверждённая целевая модель предусматривает SPA-compatible CSRF handling.

Точные детали bootstrap и повторного получения CSRF token определяются при реализации.

CSRF нельзя считать ненужным только потому, что access authentication использует JWT.

## 14.3. Origin и CORS

Production-модель предполагает same-origin размещение frontend и backend.

Конфигурация CORS и cookies не должна разрешать произвольные внешние origins.

Возможные отличия development environment должны тестироваться отдельно.

## 14.4. Авторизация

Скрытие кнопок, разделов или пунктов меню является только поведением интерфейса.

Окончательная авторизация выполняется backend.

Прямое обращение к защищённому ресурсу не должно обходить правила доступа.

---

# 15. Состояния Authentication UI

Frontend должен различать следующие концептуальные состояния.

| Состояние | Значение |
|---|---|
| UNAUTHENTICATED | Действительная аутентификация не установлена |
| AUTHENTICATING | Выполняется попытка входа |
| AUTHENTICATED | Аутентификация успешно установлена |
| RESTORING_SESSION | Выполняется проверка возможности восстановления сессии |
| AUTHENTICATION_FAILED | Попытка входа завершилась отказом |
| SESSION_EXPIRED | Продолжение сессии невозможно из-за истечения её срока |
| ACCESS_DENIED | Действие недоступно по правилам авторизации |

Эти названия являются описанием UX-состояний, а не обязательными JavaScript enum или backend statuses.

В частности, ACCESS_DENIED не обязательно означает прекращение аутентифицированной сессии.

Конкретная state model определяется при проектировании frontend architecture.

---

# 16. Ошибки и пользовательская обратная связь

## 16.1. Ошибки ввода

При некорректных данных frontend должен показывать понятные ошибки соответствующих полей, если это предусмотрено формой и API.

Локальная валидация не заменяет backend validation.

## 16.2. Ошибка Credentials

При отказе login интерфейс должен использовать безопасную формулировку, не позволяющую определять наличие конкретного email.

## 16.3. Истечение сессии

При невозможности продолжить аутентифицированную сессию пользователь должен получить понятную возможность выполнить новый вход.

## 16.4. Отказ в доступе

При недостаточных полномочиях frontend должен отображать отказ, не подменяя его сообщением об истёкшей сессии.

## 16.5. Сетевая ошибка

Временная недоступность backend не должна автоматически интерпретироваться как неверный пароль или заблокированный аккаунт.

## 16.6. Повтор операций

Повтор отправки запросов должен учитывать возможное изменение серверного состояния.

Особенно это касается чувствительных и изменяющих бизнес-операций.

---

# 17. Навигация после аутентификации

## 17.1. Успешный login

После login пользователь получает доступ к разрешённой области приложения.

Конкретная стартовая страница определяется отдельно.

## 17.2. Защищённый ресурс без сессии

Если пользователь обращается к защищённому разделу без действительной аутентификации, интерфейс должен предоставить возможность войти в аккаунт.

Восстановление первоначального перехода после login является отдельным UX-решением.

## 17.3. Изменение роли или полномочий

Frontend не должен предполагать неизменность полномочий в течение всей сессии.

Ранее доступные действия могут стать недоступными после изменения серверного состояния.

## 17.4. Logout

После завершения сессии защищённые пользовательские данные не должны оставаться доступны через локальное состояние интерфейса.

Конкретный маршрут после logout определяется отдельно.

# 18. Границы MVP и Post-MVP

## 18.1. MVP

В рамках утверждённой целевой модели предусмотрены:

- регистрация CLIENT и SPECIALIST;
- login;
- JWT access authentication;
- refresh sessions;
- refresh-token rotation;
- session restoration;
- logout;
- logout-all на уровне authentication API;
- проверка актуального UserStatus;
- защищённый доступ по ролям и бизнес-условиям;
- SPA-compatible CSRF protection;
- согласованная работа нескольких вкладок.

Фактическая готовность каждой возможности определяется соответствующими backend/frontend задачами.

## 18.2. Post-MVP

К возможностям после MVP относится мгновенный серверный отзыв ранее выданных access JWT при logout.

Другие security-функции не объявляются post-MVP без отдельного продуктового или архитектурного решения.


## 18.3. Отдельные задачи

Backend endpoints password recovery/reset уже присутствуют в текущей реализации, однако полный пользовательский процесс и доставка подтверждения требуют завершения и проверки.

Frontend recovery UX реализуется после согласования соответствующей интеграции.

Уточнение security error policy и отдельные чувствительные account actions выполняются в рамках соответствующих задач.

Их нельзя считать завершёнными только на основании настоящего UX-документа.

# 19. Открытые вопросы

При реализации необходимо уточнить:

1. Конкретные регистрационные формы и их поля.
2. Поведение после успешной регистрации.
3. Стартовые разделы после login для каждой роли.
4. Последовательность первоначального session restoration.
5. Политику автоматического refresh access JWT.
6. Безопасную политику retry защищённых запросов.
7. Реализацию межвкладочной координации.
8. Синхронизацию logout между вкладками.
9. Возврат пользователя к прерванному сценарию после повторного login.
10. Конкретные UX-сообщения для authentication failures.
11. Поведение при сетевой ошибке во время login или refresh.
12. Пользовательский интерфейс logout-all.
13. Окончательный password recovery/reset flow.
14. Точную интеграцию CSRF с frontend.
15. Структуру frontend authentication state и её техническую реализацию.

Эти решения должны согласовываться с актуальными API-контрактами и security requirements.

# 20. Итог

Authentication UX PsyWeb строится на разделении идентичности пользователя, действительности сессии и полномочий.

Ключевые принципы:

- успешный login не гарантирует доступ ко всем бизнес-операциям;
- access JWT хранится только в памяти приложения;
- refresh token передаётся через HttpOnly cookie;
- refresh-сессия имеет абсолютный срок действия;
- строгая token rotation требует согласованного refresh flow;
- несколько вкладок должны учитывать конкуренцию refresh-запросов;
- logout прекращает локальное использование access JWT и отзывает соответствующую refresh-сессию;
- профессиональное одобрение специалиста не является условием самого login;
- backend остаётся источником истины об аутентификации и авторизации;
- password recovery/reset требует отдельного согласования и реализации.

Документ описывает целевое поведение интерфейса и не подтверждает готовность frontend authentication implementation.

**Статус: DRAFT — основные authentication UX scenarios определены; техническая реализация и отдельные security contracts уточняются по мере разработки.**
