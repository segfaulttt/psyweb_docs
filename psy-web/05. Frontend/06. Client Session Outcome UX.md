# 1. Назначение документа

Документ описывает пользовательский сценарий подтверждения фактического результата консультации со стороны CLIENT.

Рассматриваются:

- доступ к отправке отчёта;
- сообщение о состоявшейся консультации;
- сообщение о несостоявшейся консультации;
- выбор причины;
- временные ограничения;
- просмотр состояния обработки отчётов;
- разрешение согласованных и конфликтующих ответов;
- связь окончательного результата с Review;
- обработка ошибок.

Документ не определяет физические страницы, URL, API endpoints, DTO или frontend components.

SessionOutcome является отдельной бизнес-моделью и не заменяет BookingStatus.

# 3. Основные принципы

## 3.1. Независимость от BookingStatus

CONFIRMED Booking означает подтверждённую запись на консультацию.

Она не доказывает, что консультация состоялась.

Факт проведения определяется через SessionOutcome.

Прохождение времени консультации само по себе также не подтверждает успешный результат.

## 3.2. Независимые отчёты участников

CLIENT и SPECIALIST независимо сообщают результат консультации.

Каждый участник может предоставить собственный отчёт в рамках предусмотренного временного окна.

Ответ одного участника не должен автоматически отображаться как согласованный обеими сторонами.

## 3.3. Backend как источник истины

Backend определяет:

- доступность подачи отчёта;
- начало и окончание окна отчётности;
- принадлежность консультации пользователю;
- возможность принять отчёт;
- совместимость ответов;
- необходимость административного разрешения;
- окончательный результат;
- eligibility для Review.

Frontend не должен воспроизводить эти решения на основании только локальных данных.

# 4. Доступ к сценарию

## 4.1. Переход из консультации

Клиент должен иметь возможность перейти к предусмотренному сценарию SessionOutcome из информации о собственной консультации.

Концептуальный переход:

```text
Client Area
    ↓
Consultation History / Booking Details
    ↓
Session Outcome
    ├── Report Available
    ├── Report Submitted
    ├── Awaiting Resolution
    └── Final Outcome
```

Это логическая последовательность, а не обязательная структура отдельных страниц.

## 4.2. Временное окно

Утверждённая продуктовая модель предоставляет участникам 24 часа после завершения консультации для отправки отчёта.

Frontend может отображать информацию о доступном времени, если соответствующие данные предусмотрены API.

Локальные часы браузера не определяют окончательное право отправить отчёт.

## 4.3. Недоступная отправка

Отправка может быть недоступна вследствие:

- отсутствия необходимой аутентификации;
- отсутствия принадлежности к консультации;
- неподходящего состояния консультации;
- истечения окна отчётности;
- уже отправленного отчёта;
- других предусмотренных backend-ограничений.

Причина недоступности отображается в пределах безопасного API-контракта.

# 5. Отправка отчёта

## 5.1. Возможные ответы

Клиент выбирает одно из двух значений:

- `OCCURRED` — консультация состоялась;
- `DID_NOT_OCCUR` — консультация не состоялась.

Дополнительные значения не вводятся этим документом.

## 5.2. Консультация состоялась

При выборе `OCCURRED` клиент сообщает, что консультация фактически прошла.

Этот отчёт сам по себе не обязательно устанавливает окончательный результат: он обрабатывается согласно правилам Outcome Domain.

## 5.3. Консультация не состоялась

При выборе `DID_NOT_OCCUR` клиент должен указать предусмотренную структурированную причину.

В целевой модели предусмотрены:

| Причина | Значение |
|---|---|
| `CLIENT_NO_SHOW` | Клиент не явился |
| `SPECIALIST_NO_SHOW` | Специалист не явился |
| `TECHNICAL_PROBLEM` | Техническая проблема |
| `OTHER` | Другая причина |

Названия причин соответствуют доменной модели.

Тексты пользовательских вариантов должны быть понятны и не обязательно совпадать с техническими enum.

## 5.4. Причина OTHER

При выборе `OTHER` требуется текстовое пояснение.

Frontend должен предусмотреть ввод пояснения и отображение ошибок валидации.

Ограничения длины текста определяются соответствующим API-контрактом.

## 5.5. Подтверждение отправки

Отчёт нельзя произвольно редактировать после принятия backend.

Поэтому перед отправкой необходимо ясно обозначить пользователю, что выбор является окончательным.

Конкретный способ подтверждения действия определяется UX-проектированием.

---

# 6. Неизменяемость отчёта

## 6.1. Однократная отправка

Каждый участник может отправить не более одного отчёта для соответствующей консультации.

Первоначальный отчёт сохраняется без произвольного изменения.

## 6.2. После успешной отправки

Frontend должен:

- отобразить подтверждённый результат отправки;
- исключить представление отчёта как свободно редактируемого;
- показывать доступное состояние дальнейшей обработки;
- не считать отправку отчёта автоматическим завершением SessionOutcome.

## 6.3. Повторный запрос

При повторной попытке отправки backend должен применить действующие правила.

Frontend не должен рассчитывать на возможность заменить ранее принятый отчёт другим ответом.

## 6.4. Неизвестный результат

Потерянный HTTP-ответ не доказывает, что отчёт не был сохранён.

Поскольку отправка однократная, frontend не должен бесконтрольно повторять запрос.

Если API поддерживает получение текущего состояния, необходимо проверить, был ли отчёт принят.

---

# 7. Разрешение SessionOutcome

## 7.1. Общая модель

После получения отчётов или завершения временного окна система определяет результат согласно утверждённым правилам.

Не каждый отправленный отчёт означает немедленное окончательное разрешение.

## 7.2. Два положительных ответа

Если CLIENT и SPECIALIST сообщили `OCCURRED`, консультация получает окончательно подтверждённый положительный результат.

## 7.3. Совместимые отрицательные ответы

Два ответа `DID_NOT_OCCUR` с одинаковой структурированной причиной, отличной от `OTHER`, могут автоматически разрешаться как несостоявшаяся консультация согласно утверждённой модели.

## 7.4. Противоречивые ответы

Несовместимые отчёты переводят SessionOutcome в состояние `DISPUTED`.

Например:

- CLIENT сообщает `OCCURRED`, SPECIALIST сообщает `DID_NOT_OCCUR`;
- участники указывают несовместимые причины несостоявшейся консультации.

Если один из двух отчётов содержит `OTHER`, автоматическое согласование по свободному тексту не производится.

Спор разрешается администратором.

## 7.5. Один отчёт

Если после завершения 24-часового окна имеется только один отчёт, его результат принимается в соответствии с утверждёнными правилами.

Frontend не должен преждевременно представлять единственный ответ как окончательный до наступления соответствующего условия.

## 7.6. Отсутствие отчётов

Если ни один участник не предоставил отчёт, система не должна автоматически считать консультацию состоявшейся.

Frontend должен различать отсутствие подтверждения и окончательно подтверждённый `OCCURRED`.

## 7.7. Административное разрешение

При `DISPUTED` окончательное решение принимает ADMIN.

Первоначальные отчёты участников сохраняются.

Клиентский интерфейс должен отображать доступную информацию о состоянии спора, но не предоставлять клиенту административные действия.

---

# 8. Представление состояния результата

Frontend должен различать концептуальные ситуации:

| Ситуация | Что важно пользователю |
|---|---|
| Отчёт ещё можно отправить | Доступно предусмотренное действие |
| Отчёт клиента принят | Повторная отправка не требуется |
| Результат ещё определяется | Окончательный исход не установлен |
| Возник спор | Требуется административное решение |
| Результат окончательно разрешён | Можно показать установленный итог |
| Проведение не подтверждено | Нельзя показывать консультацию как успешно состоявшуюся |

Эта таблица описывает пользовательские ситуации.

Она не вводит новые backend enum, статусы или обязательные структуры DTO.

Конкретные названия и поля для отображения должны соответствовать актуальному Outcome API.

---

# 9. Связь с Review

## 9.1. Основание для создания

Право клиента создать Review возникает после окончательного положительного результата:

```text
resolutionStatus = RESOLVED
finalOutcome = OCCURRED
```

Наличие Booking или отправленного отчёта `OCCURRED` само по себе недостаточно.

## 9.2. Единственный отчёт

Если один ответ `OCCURRED` окончательно принят после завершения окна, он может создать право на Review.

Отдельное положительное подтверждение второй стороны в этом случае не требуется.

## 9.3. Административное решение

Спор, разрешённый администратором в пользу `OCCURRED`, также может стать основанием для Review.

## 9.4. Ограничение уникальности

Для пары CLIENT–SPECIALIST допускается только один Review.

Повторные успешно проведённые консультации не дают права создать второй отзыв тому же специалисту.

Клиент может редактировать существующий Review в пределах утверждённых правил.

## 9.5. Frontend-поведение

Интерфейс не должен предлагать создание Review, если backend не подтверждает eligibility.

Подробный сценарий создания и редактирования отзыва рассматривается отдельно.

# 10. Authentication и Authorization

## 10.1. Защищённый сценарий

Отправка отчёта и просмотр собственных закрытых данных SessionOutcome требуют предусмотренной аутентификации.

## 10.2. Принадлежность

CLIENT может отправить отчёт только о консультации, в которой он участвовал.

Передача идентификатора другой Booking не должна предоставлять доступ к чужому SessionOutcome.

## 10.3. Истечение сессии

Истечение access JWT не продлевает 24-часовое окно отчётности.

После восстановления аутентификации frontend должен учитывать актуальное время и состояние Outcome.

## 10.4. Отсутствие полномочий

Отказ в отправке отчёта не обязательно означает истечение сессии.

Frontend должен различать ошибки аутентификации, авторизации и бизнес-состояния.

---

# 11. Ошибки и конкурентные изменения

## 11.1. Ошибки валидации

Frontend должен проверять обязательность выбора результата и предусмотренной причины.

Для `OTHER` требуется пояснение.

Локальная валидация не заменяет проверку backend.

## 11.2. Истечение окна

Если окно подачи отчёта завершилось до обработки запроса, окончательное решение о допустимости принимает backend.

## 11.3. Дублирующая отправка

Повторная отправка не должна использоваться для изменения ранее принятого отчёта.

## 11.4. Сетевая ошибка

Отсутствие ответа сервера не означает, что отчёт не принят.

При возможности frontend должен проверить актуальное состояние SessionOutcome перед повторными действиями.

## 11.5. Конкурентное разрешение

Пока клиент просматривает исход, специалист может отправить свой отчёт или администратор может разрешить спор.

Frontend должен учитывать возможность устаревания ранее полученных данных.

## 11.6. Техническая недоступность

Неудачная загрузка SessionOutcome не должна представляться пользователю как отсутствие отчёта или неподтверждённая консультация.

# 12. Границы ответственности

## 12.1. Frontend

Frontend отвечает за:

- представление доступного действия;
- сбор ответа клиента;
- отображение структурированных причин;
- предварительную валидацию формы;
- отправку отчёта;
- отображение полученных состояний;
- обработку ошибок;
- переход к предусмотренным последующим сценариям.

## 12.2. Backend

Backend отвечает за:

- проверку принадлежности консультации;
- соблюдение временного окна;
- однократность отправки;
- сохранение первоначальных отчётов;
- проверку совместимости ответов;
- автоматическое разрешение;
- формирование и разрешение споров;
- окончательный результат;
- eligibility для Review.

## 12.3. API Boundary

Фактические запросы, ответы, ограничения и значения статусов определяются соответствующим REST API.

Этот документ не вводит новые endpoints или DTO.

# 13. Открытые вопросы

При проектировании интерфейса необходимо отдельно определить:

1. Где пользователь переходит к SessionOutcome.
2. Как представить выбор `OCCURRED` / `DID_NOT_OCCUR`.
3. Как организовать выбор структурированной причины.
4. Как подтверждать необратимую отправку отчёта.
5. Как показывать оставшееся время отчётности.
6. Как представлять ожидающий разрешения результат.
7. Какие сведения о втором отчёте допустимо раскрывать участнику.
8. Как отображать конфликт и административное решение.
9. Как обрабатывать потерянный ответ на отправку отчёта.
10. Как уведомлять об изменении окончательного результата.
11. Как организовать переход к Review после появления eligibility.
12. Какие текстовые сообщения и состояния загрузки использовать.

Эти вопросы не меняют утверждённых правил Outcome Domain.

---

# 14. Итог

Client Session Outcome UX обеспечивает участие клиента в подтверждении фактического результата консультации.

Основные принципы:

- BookingStatus не определяет факт проведения консультации;
- клиент и специалист отправляют независимые отчёты;
- окно подачи отчётов составляет 24 часа после завершения консультации;
- каждый участник может отправить только один неизменяемый отчёт;
- при `DID_NOT_OCCUR` требуется структурированная причина;
- несовместимые отчёты приводят к спору;
- окончательный исход определяется backend;
- отсутствие обоих отчётов не подтверждает успешное проведение;
- Review разрешается только после окончательного `RESOLVED / OCCURRED`;
- интерфейс не создаёт новых бизнес-правил и не заменяет административное разрешение споров.

**Статус: DRAFT — клиентский SessionOutcome UX определён; детали представления и API-интеграции уточняются при реализации.**
