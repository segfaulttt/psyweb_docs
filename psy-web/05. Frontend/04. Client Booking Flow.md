# 1. Назначение документа

Документ описывает пользовательский сценарий записи клиента на консультацию в PsyWeb.

Рассматриваются:

- поиск и выбор специалиста;
- выбор ServiceOffering;
- просмотр динамической Availability;
- выбор времени консультации;
- создание временной Reservation;
- подтверждение Reservation;
- получение подтверждённой Booking;
- отмена временной Reservation;
- обработка истечения TTL;
- ошибки и конкурентные изменения;
- взаимодействие с Authentication UX.

Документ описывает логические действия и ожидаемые результаты для пользователя.

Он не определяет физические страницы, URL, API endpoints, Request/Response DTO, frontend framework или компонентную архитектуру.

# 3. Основные принципы бронирования

## 3.1. Service-first модель

Клиент записывается на конкретную ServiceOffering специалиста.

Доступные начала консультаций рассчитываются динамически на основании:

- расписания специалиста;
- продолжительности выбранной услуги;
- перерыва после консультации;
- существующей ScheduleOccupancy;
- ограничений по времени записи;
- горизонта бронирования;
- эффективного допуска специалиста к бронированию.

В целевой модели не используются предварительно созданные AvailabilitySlot.

## 3.2. Два этапа записи

Бронирование состоит из двух последовательных бизнес-операций:

1. Создание ACTIVE Reservation.
2. Подтверждение Reservation с созданием CONFIRMED Booking.

Просмотр доступности не является резервированием времени.

Успешная Reservation ещё не является подтверждённой Booking.

## 3.3. Мгновенное бронирование

Специалист не подтверждает каждую новую запись вручную.

Клиент самостоятельно подтверждает действующую Reservation.

Успешное подтверждение приводит к созданию Booking согласно бизнес-правилам.

## 3.4. Backend как источник истины

Frontend не принимает окончательных решений о:

- доступности времени;
- допустимости новой Reservation;
- конфликте занятых интервалов;
- действительности Reservation;
- истечении TTL;
- успешности подтверждения;
- создании Booking.

Эти решения принимает backend.

# 4. Общая последовательность

Концептуальный пользовательский сценарий:

```text
Specialist Catalog
    ↓
Specialist Profile
    ↓
ServiceOffering Selection
    ↓
Dynamic Availability
    ↓
Session Start Selection
    ↓
Create Reservation
    ├── Success → ACTIVE Reservation
    └── Failure → Error / Availability Recheck
                         ↓
                Reservation Confirmation
                    ├── Success → CONFIRMED Booking
                    ├── Expired → Reservation Expired
                    ├── Cancelled → Reservation Cancelled
                    └── Failure → Error / State Recheck
```

Этапы могут быть реализованы одной или несколькими страницами.

Количество экранов и структура навигации определяются отдельно.

# 5. Выбор специалиста

## 5.1. Каталог

Клиент получает доступ к публичному каталогу специалистов.

Интерфейс предоставляет предусмотренные возможности:

- просмотра специалистов;
- поиска;
- фильтрации по поддерживаемым критериям;
- перехода к профилю.

Точный состав фильтров определяется продуктовыми требованиями и API.

## 5.2. Профиль специалиста

Клиент должен иметь возможность ознакомиться с разрешёнными публичными сведениями о специалисте.

Профиль может включать:

- профессиональную информацию;
- предлагаемые услуги;
- условия консультаций;
- разрешённые публичные отзывы.

## 5.3. Доступность бронирования

Публичная видимость специалиста не гарантирует возможность записи.

Специалист может иметь публичный профиль, но не принимать новые Reservation.

Frontend должен различать:

- возможность просмотра профиля;
- наличие активных услуг;
- право специалиста принимать бронирования;
- фактическое наличие доступного времени.

Недоступность записи не обязательно требует скрытия публичного профиля.

---

# 6. Выбор ServiceOffering

## 6.1. Назначение

Перед просмотром доступного времени клиент выбирает конкретную ServiceOffering.

Доступность рассчитывается для выбранной услуги, а не для специалиста без учёта продолжительности консультации.

## 6.2. Сведения об услуге

Frontend должен отображать предусмотренные публичным контрактом условия услуги.

В зависимости от утверждённой модели это могут быть:

- название;
- описание;
- длительность консультации;
- стоимость и валюта;
- формат проведения.

Перечень полей определяется API.

## 6.3. Изменение выбора

При выборе другой ServiceOffering ранее полученные результаты Availability нельзя автоматически считать применимыми.

Frontend должен получить данные доступности, соответствующие новому выбору.

---

# 7. Просмотр динамической Availability

## 7.1. Назначение

После выбора услуги клиент получает предварительно доступные варианты начала консультации.

Availability не создаёт Reservation и не удерживает время.

## 7.2. Данные для отображения

Интерфейс должен предоставлять возможность выбрать допустимое начало консультации в пределах предусмотренного горизонта бронирования.

Конкретная форма представления определяется при UX-проектировании.

Это может быть календарь или другой интерфейс выбора даты и времени.

## 7.3. Предварительный характер

Отображаемое время может стать недоступным вследствие:

- Reservation другого клиента;
- создания Booking;
- изменения расписания;
- изменения доступности услуги;
- изменения допуска специалиста;
- наступления bookingDeadline.

Frontend не должен обещать гарантированную запись на основании одного результата Availability.

## 7.4. Отсутствие вариантов

Отсутствие доступного времени является допустимым бизнес-результатом.

Оно не должно представляться как техническая ошибка.

Клиенту можно предоставить возможность изменить разрешённые параметры поиска или выбрать другую услугу.

## 7.5. Обновление данных

Ранее полученные результаты Availability могут устаревать.

Frontend должен предусматривать получение актуальных данных при необходимости.

Конкретная стратегия обновления и кеширования определяется при реализации.

---

# 8. Выбор начала консультации

## 8.1. Действие клиента

Клиент выбирает один из доступных вариантов начала консультации для конкретной ServiceOffering.

Выбор ещё не создаёт Reservation.

## 8.2. Подготовка к резервированию

Перед созданием Reservation интерфейс должен располагать необходимыми данными выбранного сценария.

При необходимости пользователю отображаются условия консультации, предусмотренные API.

## 8.3. Authentication

Создание Reservation относится к защищённым операциям.

Если действительная аутентификация отсутствует, frontend должен предоставить возможность входа согласно Authentication UX.

После входа ранее выбранное время не считается автоматически доступным.

Перед продолжением необходимо учитывать актуальное состояние backend.

---

# 9. Создание Reservation

## 9.1. Назначение

Создание Reservation временно удерживает необходимый интервал консультации.

Reservation создаётся только после успешной проверки бизнес-предусловий backend.

## 9.2. Последовательность

```text
Selected ServiceOffering
    ↓
Selected Session Start
    ↓
Create Reservation Request
    ↓
Backend Validation
    ├── Success → ACTIVE Reservation
    └── Failure → No New Reservation
```

## 9.3. Проверки Backend

Backend проверяет предусмотренные условия, включая:

- право клиента выполнить операцию;
- состояние ServiceOffering;
- эффективный профессиональный допуск специалиста;
- действующее расписание;
- minimumBookingNotice;
- bookingHorizon;
- отсутствие конфликтующей ScheduleOccupancy;
- другие утверждённые бизнес-инварианты.

Frontend не должен самостоятельно воспроизводить весь алгоритм этих проверок.

## 9.4. Успешный результат

После подтверждения backend frontend должен перейти к представлению ACTIVE Reservation.

Интерфейс должен различать:

- успешно созданную Reservation;
- выбранное, но ещё не зарезервированное время;
- уже подтверждённую Booking.

## 9.5. Конкурентный конфликт

Если выбранное время занял другой клиент, backend может отказать в создании Reservation.

Frontend должен корректно обработать этот результат.

Предусматривается возможность повторно получить Availability и выбрать другой вариант.

Не следует автоматически утверждать, что Reservation существует, если backend её не подтвердил.

## 9.6. Повтор запроса

Создание Reservation является изменяющей бизнес-операцией.

При сетевой ошибке отсутствие ответа не гарантирует, что операция не была выполнена.

Frontend не должен бесконтрольно повторять создание Reservation.

Правила безопасного retry и возможная идемпотентность определяются отдельно в API-контракте.

---

# 10. ACTIVE Reservation

## 10.1. Назначение

ACTIVE Reservation удерживает выбранный интервал в течение ограниченного времени.

Reservation имеет установленный backend срок действия.

## 10.2. Reservation TTL

Reservation TTL определяется платформой.

Специалист не может изменять его продолжительность.

Точный срок и способ передачи информации об истечении должны соответствовать актуальному backend-контракту.

## 10.3. Действия клиента

Для собственной ACTIVE Reservation предусмотрены:

- просмотр информации;
- подтверждение;
- отмена.

Действия доступны только при соблюдении актуальных серверных условий.

## 10.4. Отображение времени

Frontend может отображать оставшееся время действия Reservation.

При этом локальный отсчёт не является источником истины.

Фактическая действительность Reservation определяется backend.

## 10.5. Обновление страницы

При обновлении страницы frontend не должен автоматически считать, что ранее созданная Reservation остаётся ACTIVE.

Необходимо учитывать актуальное серверное состояние.

Точный механизм восстановления сценария определяется при реализации.

---

# 11. Подтверждение Reservation

## 11.1. Назначение

Подтверждение ACTIVE Reservation создаёт CONFIRMED Booking.

Клиент подтверждает Reservation самостоятельно.

Отдельное ручное подтверждение специалистом не требуется.

## 11.2. Последовательность

```text
ACTIVE Reservation
    ↓
Client Confirmation
    ↓
Backend State Validation
    ├── Success → CONFIRMED Booking
    └── Failure → Actual Reservation State
```

## 11.3. Предусловия

Reservation должна оставаться ACTIVE и действительной на момент предусмотренной backend проверки.

Подтверждение после истечения Reservation TTL недопустимо.

## 11.4. Booking Deadline

`minimumBookingNotice` ограничивает создание новой Reservation.

Reservation, созданная до bookingDeadline, может быть подтверждена после него, если остаётся ACTIVE и не истекла.

Frontend не должен ошибочно блокировать подтверждение только потому, что наступил deadline создания новых Reservation.

## 11.5. Успешное подтверждение

После успешного подтверждения клиенту должна быть предоставлена информация о созданной Booking.

Frontend должен использовать фактический результат backend.

Один успешный сценарий подтверждения не должен создавать несколько Booking из одной Reservation.

## 11.6. Ошибка подтверждения

При отказе необходимо получить или отобразить актуальное состояние операции согласно доступному API.

Нельзя показывать успешное бронирование без подтверждения его создания сервером.

---

# 12. Подтверждённая Booking

## 12.1. Результат записи

CONFIRMED Booking означает, что клиент успешно завершил предусмотренный сценарий бронирования.

Это не означает, что сама консультация уже состоялась.

## 12.2. Информация о записи

Frontend должен отображать разрешённые сведения о подтверждённой консультации.

Исторические условия должны соответствовать сохранённым при Reservation данным.

Последующие изменения ServiceOffering не должны автоматически изменять отображаемые исторические условия Booking.

## 12.3. Дальнейшие действия

После подтверждения пользователь должен иметь возможность перейти к предусмотренным сценариям просмотра собственных консультаций.

Отмена CONFIRMED Booking, SessionOutcome и Review описываются в отдельных пользовательских сценариях.

---

# 13. Отмена ACTIVE Reservation

## 13.1. Назначение

Клиент может отменить собственную ACTIVE Reservation.

При успешной отмене удерживаемое время освобождается согласно backend business rules.

## 13.2. Последовательность

```text
ACTIVE Reservation
    ↓
Client Cancellation
    ↓
Backend State Validation
    ├── Success → CANCELLED Reservation
    └── Failure → Actual Reservation State
```

## 13.3. Согласованность состояния

Frontend не должен утверждать успешную отмену до получения достоверного результата.

Если Reservation уже истекла или была подтверждена, необходимо учитывать фактическое состояние backend.

## 13.4. История

Отмена Reservation не означает удаления её исторической записи.

Пользовательское представление истории определяется отдельным сценарием.

---

# 14. Истечение Reservation

## 14.1. Назначение

Reservation перестаёт удерживать время после истечения TTL согласно backend lifecycle.

## 14.2. Отображение

Frontend должен корректно отличать:

- ACTIVE Reservation;
- EXPIRED Reservation;
- CANCELLED Reservation;
- CONFIRMED Reservation.

Истечение TTL не является успешным подтверждением консультации.

## 14.3. Действия после истечения

После подтверждённого истечения Reservation клиент не должен пытаться подтвердить её как действующую.

Для новой записи необходимо пройти соответствующий сценарий заново с актуальными данными.

## 14.4. Конкурентное истечение

Истечение и подтверждение Reservation могут происходить конкурентно.

Frontend не должен самостоятельно решать исход по локальным часам.

Окончательный результат определяется backend.

---

# 15. Ошибки и состояния интерфейса

## 15.1. Загрузка

Во время получения Availability, создания Reservation и подтверждения Booking пользователь должен получать понятную обратную связь.

Конкретные индикаторы загрузки определяются при UX-проектировании.

## 15.2. Пустые результаты

Отсутствие доступного времени не является ошибкой системы.

## 15.3. Ошибка валидации

Frontend должен отображать безопасные и понятные ошибки входных данных.

Локальная валидация не заменяет серверную.

## 15.4. Конфликт занятости

При отказе из-за недоступности выбранного времени необходимо предоставить возможность получить актуальные варианты.

## 15.5. Истечение Reservation

При подтверждённом истечении пользователь должен видеть, что временное удержание больше не действует.

## 15.6. Ошибка Authentication

При отсутствии действительной сессии frontend должен использовать предусмотренный Authentication UX.

Возобновление сессии не продлевает автоматически TTL Reservation.

## 15.7. Ошибка Authorization

Недостаточные права не должны представляться как технический сбой или истечение Reservation.

## 15.8. Сетевая ошибка

Сетевая ошибка не доказывает, что изменяющая операция не была выполнена.

При неопределённом результате следует сверить состояние с backend, если API предоставляет такую возможность.

## 15.9. Недоступность Backend

При временной недоступности backend frontend не должен отображать неподтверждённую Reservation или Booking как успешно созданную.

---

# 16. Состояния пользовательского сценария

Для проектирования UX используются следующие концептуальные состояния:

| Состояние | Значение |
|---|---|
| SELECTING_SPECIALIST | Клиент выбирает специалиста |
| SELECTING_SERVICE | Клиент выбирает ServiceOffering |
| LOADING_AVAILABILITY | Выполняется получение доступного времени |
| SELECTING_TIME | Клиент выбирает начало консультации |
| CREATING_RESERVATION | Выполняется запрос на создание Reservation |
| RESERVATION_ACTIVE | Backend подтвердил ACTIVE Reservation |
| CONFIRMING_RESERVATION | Выполняется подтверждение Reservation |
| BOOKING_CONFIRMED | Backend подтвердил создание Booking |
| RESERVATION_EXPIRED | Reservation подтверждённо истекла |
| RESERVATION_CANCELLED | Reservation отменена |
| OPERATION_FAILED | Операция завершилась отказом |
| RESULT_UNKNOWN | Результат изменяющей операции пока не установлен |

Названия являются концептуальными UX-состояниями.

Они не являются обязательными frontend enum, backend statuses или типами API.

В частности, `RESULT_UNKNOWN` не является статусом Reservation или Booking.

# 17. Безопасность и авторизация

## 17.1. Идентичность клиента

Идентичность пользователя определяется доверенным контекстом аутентификации backend.

Frontend не должен предоставлять возможность произвольно определять другого клиента как инициатора Reservation.

## 17.2. Принадлежность

Клиент может подтверждать и отменять только собственные Reservation.

Окончательная проверка принадлежности выполняется backend.

## 17.3. Истечение сессии

Истечение access JWT не означает автоматическое истечение Reservation.

Это разные механизмы с независимыми сроками действия.

После восстановления аутентификации frontend должен учитывать актуальное состояние Reservation.

## 17.4. Защита от двойного бронирования

Отображение недоступного времени или блокировка кнопки не являются механизмами предотвращения двойной записи.

Целостность бронирования обеспечивается backend и PostgreSQL.

# 18. Границы ответственности

## 18.1. Frontend

Frontend отвечает за:

- представление пользовательского сценария;
- отображение доступных действий;
- отправку запросов;
- обработку результатов;
- отображение ошибок;
- управление локальным состоянием интерфейса.

## 18.2. Backend

Backend отвечает за:

- проверку бизнес-предусловий;
- расчёт доступности;
- создание Reservation;
- удержание времени;
- соблюдение TTL;
- проверку bookingDeadline;
- конкурентную защиту;
- подтверждение Reservation;
- создание Booking;
- сохранение исторических условий.

## 18.3. API Boundary

Форматы запросов, ответов, ошибок и идентификаторов определяются соответствующими REST API-контрактами.

Frontend-документация не устанавливает эти контракты самостоятельно.

# 19. Открытые вопросы

При дальнейшем проектировании необходимо определить:

1. Физическую структуру экранов бронирования.
2. Способ представления календаря и доступных начал консультаций.
3. Отображение продолжительности, стоимости и других условий услуги.
4. UX для специалиста, временно не принимающего новые записи.
5. Способ отображения Reservation TTL.
6. Поведение при обновлении страницы с ACTIVE Reservation.
7. Восстановление сценария после повторной аутентификации.
8. Способ сверки неизвестного результата изменяющей операции.
9. Безопасную retry/idempotency policy на уровне API.
10. UX при конкурентной попытке подтверждения и истечения Reservation.
11. Представление локального и абсолютного времени консультации.
12. Отображение ошибок и пустых состояний.
13. Точную организацию перехода к подтверждённой Booking.
14. Отдельный UX отмены CONFIRMED Booking.

Эти вопросы не должны решаться за счёт введения неутверждённых бизнес-правил.

# 20. Итог

Client Booking Flow PsyWeb строится на последовательности:

```text
Specialist
    ↓
ServiceOffering
    ↓
Dynamic Availability
    ↓
ACTIVE Reservation
    ↓
CONFIRMED Booking
```

Основные принципы:

- доступность рассчитывается для выбранной услуги;
- просмотр Availability не удерживает время;
- успешная Reservation временно удерживает необходимый интервал;
- Reservation TTL определяется платформой;
- подтверждение допустимо только для действующей ACTIVE Reservation;
- существующая Reservation может подтверждаться после bookingDeadline при соблюдении собственного TTL;
- подтверждённая Booking создаётся без ручного одобрения специалистом;
- frontend не подменяет серверные решения о доступности и состоянии;
- неопределённые результаты изменяющих операций требуют осторожной обработки;
- безопасность и конкурентная целостность обеспечиваются backend.

Документ определяет целевой пользовательский сценарий, но не фиксирует физические страницы, frontend implementation или окончательные API-контракты.

**Статус: DRAFT — Client Booking Flow определён; конкретный UX и техническая интеграция уточняются при реализации.**
