# 1. Назначение документа

Документ описывает пользовательские сценарии управления консультациями для CLIENT после создания подтверждённой Booking.

Рассматриваются:

- просмотр предстоящих консультаций;
- просмотр деталей Booking;
- история консультаций;
- отмена подтверждённой Booking;
- своевременная и поздняя отмена;
- обработка ошибок и конкурентных изменений;
- сохранение исторической информации;
- переход к сценарию SessionOutcome.

Документ не определяет конкретные страницы, URL, API endpoints, DTO, frontend framework или компоненты интерфейса.

Он описывает целевое поведение, а не фактически реализованный frontend.

# 3. Основные принципы

## 3.1. Reservation и Booking

Reservation представляет временное удержание консультации.

Booking представляет подтверждённую запись.

Frontend должен различать эти сущности и их жизненные циклы.

Создание Booking происходит после успешного подтверждения ACTIVE Reservation.

## 3.2. Booking и SessionOutcome

Подтверждённая Booking не означает, что консультация состоялась.

Фактический результат проведения консультации определяется отдельной моделью SessionOutcome.

Frontend не должен считать прошедшую по времени Booking автоматически успешно завершённой консультацией.

## 3.3. Backend как источник истины

Backend определяет:

- существование Booking;
- принадлежность Booking клиенту;
- актуальный BookingStatus;
- допустимость отмены;
- своевременность или поздний характер отмены;
- освобождение занятого времени;
- сохранение истории.

Frontend отображает результаты серверных операций и не заменяет доменные проверки.

# 4. Структура пользовательского сценария

Концептуальная структура:

```text id="f4b6ys"
Client Area
    ↓
My Consultations
    ├── Upcoming Consultations
    │       └── Booking Details
    │               └── Cancellation
    │
    └── Consultation History
            └── Booking Details
                    └── Session Outcome
```

Это логическая структура, а не утверждённое дерево страниц или маршрутов.

Предстоящие консультации и история могут быть реализованы как отдельные экраны либо как разные представления одного раздела.

---

# 5. Предстоящие консультации

## 5.1. Назначение

Клиент должен иметь возможность просматривать собственные будущие консультации.

Интерфейс предоставляет сведения, необходимые для понимания запланированной записи.

## 5.2. Доступные данные

В зависимости от публичного API-контракта могут отображаться:

- специалист;
- выбранная услуга;
- дата и время консультации;
- продолжительность;
- формат консультации;
- согласованные условия;
- актуальный статус Booking.

Точный набор полей определяется соответствующим Response DTO.

## 5.3. Доступные действия

Для будущей CONFIRMED Booking могут предусматриваться:

- просмотр деталей;
- переход к разрешённому сценарию отмены.

Доступность действия определяется актуальными бизнес-условиями.

## 5.4. Отсутствие консультаций

Если у клиента нет предстоящих консультаций, интерфейс должен отображать понятное пустое состояние.

Это не является ошибкой backend.

При необходимости пользователь может перейти к выбору специалиста и новой записи.

## 5.5. Актуальность списка

Сведения о консультациях могут изменяться из-за отмены, административных действий или других предусмотренных операций.

Frontend не должен предполагать, что ранее загруженный список всегда остаётся актуальным.

---

# 6. Детали Booking

## 6.1. Назначение

Детальное представление Booking позволяет клиенту ознакомиться с согласованными условиями конкретной консультации.

## 6.2. Исторические условия

Booking использует условия, сохранённые при создании Reservation.

Последующие изменения ServiceOffering не должны автоматически подменять:

- согласованную продолжительность;
- стоимость;
- валюту;
- другие предусмотренные исторические сведения.

Исторические данные берутся из backend.

## 6.3. Доступные операции

Набор действий зависит от:

- принадлежности Booking;
- текущего статуса;
- времени начала консультации;
- предусмотренных правил отмены;
- дополнительных бизнес-ограничений.

Наличие кнопки не является доказательством того, что операция будет разрешена backend.

## 6.4. Прямое открытие

Клиент не должен получать доступ к чужой Booking при прямом открытии её представления.

Окончательная проверка выполняется backend.

Frontend должен корректно обрабатывать отсутствие доступа или недоступность ресурса.

---

# 7. История консультаций

## 7.1. Назначение

Клиент должен иметь возможность просматривать историю собственных Booking.

История сохраняется после отмены и после прохождения времени консультации.

## 7.2. Состав истории

История должна отражать предусмотренные сервером сведения:

- исходные условия записи;
- статус Booking;
- сведения об отмене, если она произошла;
- доступный результат SessionOutcome;
- другие разрешённые исторические данные.

## 7.3. Отмена не удаляет Booking

При отмене Booking сохраняется историческая запись.

Frontend не должен представлять отмену как полное удаление консультации из системы.

## 7.4. Прошедшая консультация

Прохождение времени начала или окончания консультации само по себе не подтверждает её успешное проведение.

Для этого используется SessionOutcome.

## 7.5. Отсутствие истории

Отсутствие исторических Booking является допустимым состоянием интерфейса.

Оно не должно представляться как ошибка.

---

# 8. Клиентская отмена Booking

## 8.1. Назначение

CLIENT может отменить собственную CONFIRMED Booking до начала консультации.

Право на отмену определяется backend.

## 8.2. Последовательность

```text id="e78uoi"
Booking Details
    ↓
Client Cancellation Action
    ↓
Cancellation Request
    ↓
Backend Validation
    ├── Success → CANCELLED Booking
    └── Failure → Actual Booking State
```

Frontend не должен отображать успешную отмену до получения достоверного результата операции.

## 8.3. Основные ограничения

Отмена предусмотрена для собственной CONFIRMED Booking до начала консультации.

Frontend должен учитывать возможность изменения состояния записи между загрузкой данных и выполнением действия.

Например, консультация может уже начаться к моменту обработки запроса.

## 8.4. Подтверждение действия

Перед отправкой запроса интерфейс может предоставлять пользователю возможность подтвердить намерение отменить запись.

Точная организация подтверждения определяется при UX-проектировании.

Она не заменяет серверную проверку допустимости отмены.

## 8.5. Успешная отмена

После успешной отмены:

- Booking получает статус CANCELLED;
- сохраняются сведения об отмене;
- занятость соответствующего интервала освобождается backend;
- историческая Booking сохраняется.

Frontend должен отобразить актуальный результат операции.

---

# 9. Своевременная и поздняя отмена

## 9.1. ClientCancellationNotice

Специалист настраивает период своевременной отмены консультации.

Срок определяется относительно начала консультации:

```text id="1n18iv"
clientCancellationDeadline =
    sessionStart - clientCancellationNotice
```

При создании Reservation сохраняются согласованные условия, необходимые для последующей оценки отмены.

## 9.2. Своевременная отмена

Отмена считается своевременной в соответствии с установленным backend cutoff.

Frontend может объяснять пользователю соответствующие условия на основании разрешённых API-данных.

## 9.3. Поздняя отмена

Поздняя отмена до начала консультации допускается.

Она не требует отдельного BookingStatus.

В MVP поздняя отмена не приводит к автоматическому штрафу или денежному взысканию.

## 9.4. Представление последствий

Frontend не должен утверждать, что поздняя отмена запрещена, если она допускается действующими бизнес-правилами.

Если условия отмены отображаются пользователю, необходимо использовать согласованные исторические значения.

## 9.5. Серверное решение

Окончательная классификация отмены выполняется backend.

Локальные часы браузера не являются источником истины для определения своевременности операции.

---

# 10. Состояние после отмены

## 10.1. Статус Booking

Успешно отменённая Booking получает статус CANCELLED.

Отдельный статус LATE_CANCELLED не используется.

## 10.2. Историческая информация

Система сохраняет:

- время отмены;
- инициатора отмены;
- согласованные условия;
- другую предусмотренную историю.

Отображение этих сведений зависит от API-контракта и полномочий пользователя.

## 10.3. Освобождение времени

При допустимой отмене backend освобождает соответствующую ScheduleOccupancy.

Это не гарантирует, что другой клиент сможет немедленно записаться на то же время.

## 10.4. Повторная доступность

Повторное бронирование возможно только при соблюдении актуальных условий:

- расписания специалиста;
- minimumBookingNotice;
- горизонта бронирования;
- допуска специалиста;
- отсутствия другой занятости.

Frontend не должен автоматически показывать отменённое время как доступное без повторной проверки Availability.

---

# 11. Конкурентные изменения

## 11.1. Изменение статуса

Состояние Booking может измениться после получения данных frontend.

При выполнении действия backend проверяет актуальные бизнес-предусловия.

## 11.2. Повторная отмена

Frontend должен корректно обрабатывать ситуацию, когда Booking уже отменена.

Не следует предполагать, что повторный запрос обязательно приведёт к новому успешному переходу состояния.

Точный HTTP-контракт определяется отдельно.

## 11.3. Начало консультации

Пользователь может открыть интерфейс отмены до начала консультации, но отправить запрос уже после её начала.

Окончательное решение принимает backend по актуальному времени и состоянию.

## 11.4. Неизвестный результат операции

Сетевая ошибка или потерянный HTTP-ответ не доказывают, что отмена не произошла.

Frontend должен различать:

- подтверждённый успех;
- подтверждённый отказ;
- неизвестный результат.

Если API позволяет, неизвестный результат следует уточнить повторным чтением текущего состояния Booking.

---

# 12. Authentication и Authorization

## 12.1. Защищённые данные

Просмотр собственных Booking и их отмена относятся к защищённым пользовательским операциям.

Frontend должен использовать предусмотренный Authentication UX.

## 12.2. Истечение Access Token

Истечение access JWT не изменяет BookingStatus.

После восстановления сессии необходимо учитывать актуальные данные Booking.

## 12.3. Принадлежность ресурса

Клиент может управлять только собственными Booking.

Идентификатор Booking не является доказательством принадлежности ресурса пользователю.

## 12.4. Отсутствие полномочий

Frontend должен корректно различать:

- отсутствие аутентификации;
- недостаточные полномочия;
- недоступность конкретной бизнес-операции.

Не каждый отказ требует завершения пользовательской сессии.

# 13. Состояния интерфейса

Для проектирования UX используются концептуальные состояния:

| Состояние | Значение |
|---|---|
| LOADING_CONSULTATIONS | Загрузка списка консультаций |
| NO_UPCOMING_CONSULTATIONS | Нет предстоящих консультаций |
| NO_CONSULTATION_HISTORY | История консультаций пуста |
| VIEWING_BOOKING | Просмотр деталей Booking |
| CANCELLATION_PENDING | Выполняется запрос на отмену |
| CANCELLATION_CONFIRMED | Backend подтвердил отмену |
| CANCELLATION_REJECTED | Backend отклонил отмену |
| CANCELLATION_RESULT_UNKNOWN | Результат отмены пока неизвестен |
| ACCESS_DENIED | Доступ к операции или ресурсу запрещён |
| DATA_UNAVAILABLE | Не удалось получить необходимые данные |

Названия предназначены для описания поведения интерфейса.

Они не являются обязательными frontend enum или backend statuses.

# 14. Ошибки и пользовательская обратная связь

## 14.1. Ошибка загрузки

При невозможности получить список консультаций frontend должен отображать соответствующее состояние.

Ошибка загрузки не равнозначна отсутствию консультаций.

## 14.2. Недоступный ресурс

При отсутствии Booking или запрете доступа пользователь должен получить безопасный результат согласно API-контракту.

## 14.3. Отказ в отмене

Если backend отклонил отмену, frontend не должен изменять отображаемый статус Booking на CANCELLED.

## 14.4. Неизвестный результат

При неизвестном результате отмены нельзя сразу утверждать ни успех, ни отказ.

Следует учитывать необходимость сверки состояния с backend.

## 14.5. Успешное действие

Успех должен отображаться после достоверного подтверждения результата.

## 14.6. Повторные запросы

Изменяющие запросы нельзя бесконтрольно повторять.

Политика retry и идемпотентность определяются соответствующим API.

---

# 15. Переход к SessionOutcome

## 15.1. Отдельный бизнес-сценарий

SessionOutcome определяет, состоялась ли консультация.

Он не является частью операции отмены Booking.

## 15.2. Доступность сценария

Доступ к отправке отчёта определяется действующими правилами Outcome Domain.

Frontend не должен делать вывод о праве отправить отчёт только по тому, что консультация находится в истории.

## 15.3. Результат консультации

Необходимо различать:

- отправленные участниками отчёты;
- подтверждённый результат;
- спорный результат;
- неподтверждённый результат.

Подробный UX этого сценария описывается отдельно.

---

# 16. Границы ответственности

## 16.1. Frontend

Frontend отвечает за:

- представление консультаций;
- отображение разрешённых действий;
- отправку запросов;
- обработку результатов;
- пользовательскую обратную связь;
- управление локальным состоянием интерфейса.

## 16.2. Backend

Backend отвечает за:

- принадлежность Booking;
- авторизацию;
- проверку статусов;
- допустимость отмены;
- расчёт deadline;
- классификацию поздней отмены;
- освобождение занятости;
- сохранение истории.

## 16.3. API Boundary

Форматы запросов, ответов, ошибок и представления статусов определяются REST API-контрактами.

Frontend-документ не устанавливает новые backend endpoints или DTO.

# 17. Открытые вопросы

При реализации необходимо определить:

1. Физическую структуру разделов предстоящих и исторических консультаций.
2. Поля краткого и детального представления Booking.
3. Способ отображения даты и времени с учётом часового пояса.
4. UX подтверждения отмены.
5. Представление своевременной и поздней отмены.
6. Правила отображения исторической стоимости и условий услуги.
7. Поведение при неизвестном результате cancellation request.
8. Способ обновления списка после изменения Booking.
9. Пагинацию и сортировку истории при наличии соответствующего API.
10. Отображение отмен, инициированных специалистом или администратором.
11. Переход к отдельному сценарию SessionOutcome.
12. Тексты ошибок и пустых состояний.

Эти вопросы не должны решаться путём введения неутверждённых бизнес-правил.

---

# 18. Итог

Client Consultation Management охватывает просмотр и управление подтверждёнными консультациями.

Основные принципы:

- Booking создаётся после подтверждения Reservation;
- клиент видит собственные разрешённые консультации;
- история сохраняется после отмены;
- исторические условия не заменяются текущими настройками ServiceOffering;
- клиентская отмена допускается до начала консультации;
- поздняя отмена разрешена в MVP без автоматического денежного взыскания;
- успешная отмена переводит Booking в CANCELLED и освобождает занятость;
- повторная доступность времени проверяется отдельно;
- факт проведения консультации определяется через SessionOutcome;
- backend остаётся источником истины для статусов и бизнес-правил.

Документ не фиксирует конкретные страницы, API-контракты или frontend implementation.

**Статус: DRAFT — сценарии управления консультациями определены; UX и техническая интеграция уточняются при реализации.**
